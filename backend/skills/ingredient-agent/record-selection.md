# 选记录

候选是**记录**，不是名字。同名的多条记录可能是不同批次、不同版本、不同数据源，
要逐条看，不能按名字合并。

## 硬优先级（顺序不能颠倒）

1. **状态必须先匹配**
   - 要生档案：只选明确标了生的（raw / 生 / 생것 / 未加热）。
   - 要熟档案：只选明确标了熟的（水煮 / boiled / ゆで / 蒸）。
   - **未标生熟**的记录只能当备选：只有该状态下一个明确记录都没有时才能选，
     并且必须在 `rationale` 第一句写“该状态无明确记录，暂用未标生熟”。
2. **覆盖率**：`getRecord` 给出的已填项比例，越高越好。
   - 两条记录覆盖率差 **超过 10 个百分点** 时，**必须选覆盖率高的那条**；
     “中文口径 / 名字更像 / 来源更权威”都不构成翻盘理由。
   - 只有在覆盖率差 **≤5 个百分点** 时，才允许用第 3–5 条做取舍。
3. **关键字段齐不齐**：能量、水分、粗蛋白、粗脂肪、灰分、碳水。
   覆盖率接近时，缺粗脂肪或水分的要扣分。
4. **数值合不合理**：能量与 4/9/4 反算差太多、宏量之和超过 103g/100g，
   在方案里提示，并优先选数值自洽的那条。
5. **来源与口径**：同一条原料尽量固定一个来源；中式食材在覆盖率接近时可以优先 CFCT。

## 选了覆盖率更低的怎么办

必须在 `rationale` 里写清楚三件事：

- 低多少个百分点；
- 差在哪几类字段（例如“缺脂肪酸全项”“缺矿物质”）；
- 为什么仍然选它（通常只能是“覆盖率接近，且中文口径更合适”）。

写不出这三点，就说明应该选覆盖率高的那条。

## 同名多条怎么办

- 全部列进方案的 `candidates`，按推荐程度排序；
- 把你看重的差异写进 `findings`（例如“其中一条多 12 项矿物质”）；
- 不要自己挑一条就说“库里只有这一条”。

## 候选怎么写

- `name` 只写来源库里的**原始名字**（例如“鸡蛋白”“雞蛋白平均值”“卵白 ゆで”）；
- **不要把来源 key、编号、库名拼进名字**——`sourceType` 已经单独有字段了。

## 生熟两份

- 用户要“生 + 熟都要”时，方案里分别给出建议记录，一份档案一条来源；
- 只做生档案也完全可以，但要说明“熟档案暂缺”。

## 交方案

`chosenRecordId` / `chosenRecordName` 写你的建议；`candidates` 写备选；
`rationale` 一句话说清为什么选它。
