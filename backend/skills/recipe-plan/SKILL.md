# recipe-plan

## 目标
为这一单产出可执行的营养管理方案，而不是把档案再复述一遍。

## 顺序
1. 读设计上下文、订单、狗狗档案、健康记录。
2. 确认目标、生命阶段、健康需求、忌口/过敏、订单份数。
3. 发现档案矛盾，先指出；缺资料先查。
4. 产出方案，用 `propose_plan` 提交，等用户确认。

## 方案内容
- 摘要只写方案定位；不要复述年龄、体重、品种、BCS、性别、检验值。
- 不要提药物、用药、处方或剂量。
- 理由写 `rationale`：为什么这样定、优先级、执行建议、需要确认的点。
- 数值约束只列疾病特异性、或比通用标准更严的约束；通用项交给营养评估。
- 非数值约束写 `nonNutrient` 文案：忌口/过敏、质地/纤维/产气、工艺/形态、餐次。
- 如果疾病管理需要低渣/低纤维，要明确写避免豆类、粗纤维、菌藻等，让选材可执行。
- 方案可以没有数值约束；不要为了字段完整凑约束。
- 不需要 `mealsPerDay` 字段；餐次属于非数值约束文案。

## 数值约束取舍
- 只列疾病特异性、或比通用标准更严的数值约束；通用项交给营养评估。
- 数值约束通常 2–5 条，只保留真正影响选材/评估的；不要为每个营养素都凑一条。
- 只写更严的那一侧；默认下限不要重复写。
- 不写“每日总热量”目标，也不做总热量计算。
- 只有减重/增重/特殊能量需求才写能量密度；MAINTAIN 不写。
- 钠只有在比通用上限更严时才写。
- 胰腺炎与肿瘤蛋白目标冲突时，以胰腺炎安全为先；更高蛋白只写理由并标待确认，不作为硬约束。

## 用户修改方案
- 用户的话是最高优先级。
- 用户明确要求修改已确认方案时，用 `revise_plan` 提交修订；不要以“方案已锁定”拒绝。
- 提交后等用户点“重新确认方案”；不要自行视为已确认。
- 原选材/配方会保留；确认后继续核对，不要重造。
- 先说明风险，再按用户要求更新。

## 边界
- 不查原料库；不替用户选食材。
- 不给药物剂量；不把药物写进方案。

## 引用
- 引用用短标签，如 `SACN5-67 p5`、`FEDIAF Table III-3a`；不要贴长文档 id。
