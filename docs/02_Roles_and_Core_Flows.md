## 1. 角色

| 角色 | 端 | 能做什么 |
|---|---|---|
| 顾客（CUSTOMER） | 微信小程序 | 登录、建狗狗档案、看食谱、算饭量、下单/支付、查订单、售后、补剂、定制食谱 |
| 员工（STAFF） | 微信小程序员工页 | 订单中心、厨房生产、采购、库存、打包发货、客服、补剂汇总 |
| 管理员（ADMIN） | 管理后台 | 食谱/营养治理、订单/售后、生产/采购/库存、补剂/试吃装、财务、客服、配置、分析 |

权限按端隔离；同一个接口不要同时对三端开放，除非业务明确允许。

## 2. 主流程

### 2.1 顾客建档 → 下单 → 支付

```text
登录 → 建/选狗狗档案 → 选食谱/DIY → 算饭量/营养 → 确认订单 → 支付
→ 生成订单快照 → 进入生产/采购/发货
```

关键点：

- 狗狗档案是营养计算输入，不能只存在前端。
- 下单时冻结食谱/价格/地址快照；后续改食谱不影响历史订单。
- 支付回调必须幂等；订单状态由后端状态机推进。

### 2.2 生产

```text
已支付订单 → 排产 → 生产批次/任务 → 厨房执行 → 完成/称重/损耗 → 库存/成本
```

关键点：

- 生产按订单快照展开；不要回头读“当前食谱”。
- 批次/任务状态与订单状态显式映射。
- 完成数据进入成本/库存，不能只改展示。

### 2.3 采购 / 库存

```text
生产需求/库存预警 → 采购单 → 收货 → 入库流水 → 领料/出库 → 库存台账
```

关键点：

- 库存用流水，不直接改“剩余数量”。
- 采购 SKU 与原料本体分离（品牌/渠道/规格/价格在 SKU）。
- 任何调整要有原因/操作人。

### 2.4 发货 / 收货

```text
打包 → 发货 → 填运单 → 顾客确认收货 → 订单完成
```

关键点：

- 地址/运费是下单时快照；后续改地址不影响历史订单。
- 物流状态与订单状态解耦，但有明确映射。

### 2.5 售后

```text
顾客申请 → 客服/后台审核 → 重做/退款/补发 → 关闭
```

关键点：

- 售后有独立状态机；不要直接改订单状态“抹掉”问题。
- 退款/重做要能追溯到原订单/批次。

### 2.6 补剂

```text
浏览补剂 → 下单 → 支付 → 履约/发货 → 售后
```

关键点：

- 补剂是独立子域，不复用鲜食订单状态机。
- 补剂不挂采购 SKU；等价组/规格规则在补剂域。

### 2.7 定制食谱

```text
提交需求 → 报价/确认 → 支付 → 设计/确认 → 交付 → 售后/退款
```

关键点：

- 定制报价、定金/尾款、交付/退款都可追溯。
- 定制订单和普通鲜食订单分开处理。

### 2.8 健康 / 疫苗 / 过敏

```text
建档案 → 记录体重/体况/疫苗/过敏 → 生成提醒/报告 → 顾客查看/分享
```

关键点：

- 健康内容只做营养/护理参考，不做兽医诊断。
- 提醒/通知规则见 [通知矩阵](notification-matrix.md)。
- 分享链接只暴露必要信息，注意权限。

### 2.9 知识库 / 证据

```text
原文/来源登记 → 结构化 → 证据政策 → 引用锚点 → 被 AI/后台使用
```

关键点：

- 营养/医学结论必须有来源；AI 不凭记忆补。
- 证据政策变化要可追溯。

## 3. 跨流程规则

1. **快照优先**：订单、食谱、地址、价格都用下单时快照。
2. **状态机集中**：订单/生产/采购/售后状态转换只在 domain 层。
3. **流水优先**：库存、金额、状态历史不靠删记录。
4. **角色隔离**：CUSTOMER / STAFF / ADMIN 各端权限分开。
5. **通知显式**：哪个节点发什么通知，按通知矩阵，不靠临时加。
