## 二、✅ 走得通的部分

### 2.1 顾客入口齐全

| 位置 | 可申请的类型 |
|------|--------------|
| 订单详情中部「售后服务」板块 | 退款 / 重做 / 投诉（按状态各自判定） |
| 订单详情底部（急冻中 / 已发货） | 申请售后 |
| 订单列表卡片 | 申请售后（**写死 REFUND**） |

### 2.2 前后端状态规则完全一致

| 类型 | 允许的订单状态 |
|------|----------------|
| 退款 REFUND | PAID / PURCHASING / IN_PRODUCTION / FREEZING / SHIPPED / COMPLETED |
| 重做 REMAKE | FREEZING / SHIPPED / COMPLETED |
| 投诉 COMPLAINT | 同退款 |

前端 `utils/order-aftersale.ts` 与后端 `order.entity.ts` 的 `applyForAftersale()` **逐项对应**，没有错位。

### 2.3 申请提交可用

- 原因必填（空则前端阻断 + 后端 `ValidationError`）
- 图片可选 ≤6 张；任一上传失败即中止提交，避免提交半截数据
- 订单信息加载失败时禁止提交，避免提交到错单
- **重复提交有兜底**：识别为"已在售后中"时按成功处理

### 2.4 全额退款真的能执行 ✅（已用生产数据验证）

| 验证项 | 结果 |
|--------|------|
| 微信支付配置 | `enabled=true`，appId / mchId / 商户序列号 / APIv3 密钥 / 私钥 / 回调地址**全部已配置** |
| `allowRefund` 开关 | **true** |
| 退款流水 | **7 笔，全部 `success=true`** |
| 其中走售后审核的整单退款 | **2 笔**（`source=AFTERSALE_APPROVE`，金额分别为 ¥219.83 / ¥1.00） |

退款实现本身也很扎实：**幂等**（已成功直接返回）、**金额校验**（不得超过订单金额）、**只允许微信线上支付单发起**、**回调更新状态**。

### 2.5 审核权限正确

- 「同意退款」**仅 ADMIN 可操作**：前端按角色隐藏 + 服务层 `resolveAftersale` 二次校验
- 员工的待办列表里**过滤掉退款单**，避免越权处理

## 三、❌ 走不通：免费重做

### 3.1 问题描述

管理员在后台点「安排重做」后，`resolveAftersale('remade')` 做的事是：

```
order.transitionTo(OrderStatus.IN_PRODUCTION)   ← 仅此一步
```

**它没有清掉订单条目上旧的 `production_batch_id`。**

### 3.2 生产排产有三道关卡，全部会挡住它

| # | 关卡 | 位置 | 结果 |
|---|------|------|------|
| 1 | 候选订单只查 `status = PURCHASING` | `production.service.ts:137` | 重做单是 `IN_PRODUCTION`，**不在候选里** |
| 2 | 显式校验：非 PURCHASING 直接抛错 | `production.service.ts:153` | `Cannot include non-PURCHASING orders in production batch` |
| 3 | 只分配 `production_batch_id IS NULL` 的条目 | `prisma-production.repository.ts:93` | 重做单的条目**还挂着上一批的批次号**，分配不到新批次 |

### 3.3 后果（比"失败"更糟）

```
顾客申请重做
   ↓
管理员点「安排重做」→ 成功提示
   ↓
订单状态显示「生产中」   ← 看起来一切正常
   ↓
但没有任何新批次产生，员工的生产工作台（基于批次/分装单元）看不到这单
   ↓
顾客永远等不到货，且平台侧没有任何告警
```

**这是一个"静默失败"**：状态是绿的，货是没有的。

### 3.4 佐证

生产库里 **从没有过 REMAKE 记录**（历史上 3 次售后全部是退款），所以这个坑**目前还没被踩到**——但它是真实存在的。

## 四、⚠️ 另外两个不一致

### 4.1 7 天时效只在前端 —— ✅ **已于 2026-09-19 修复并部署**

**修复**：在领域层 `Order.applyForAftersale()` 补上同样的校验（COMPLETED 且非投诉时，超过 7 天直接拒绝）。
常量 `COMPLETED_AFTERSALE_WINDOW_MS` 与小程序端同名同值，便于对照。

**线上行为验证（已实测）**：

| 场景 | 结果 |
|------|------|
| 确认收货 3 天内 · 申请退款 | ✅ 允许 |
| 确认收货 10 天后 · 申请退款 | ⛔ 拒绝（提示"超过 7 天…可提交投诉建议"） |
| 确认收货 10 天后 · 申请重做 | ⛔ 拒绝 |
| 确认收货 10 天后 · 投诉建议 | ✅ 允许（投诉不受限，与前端一致） |
| 未完成订单（已发货）· 申请退款 | ✅ 允许（不受此规则影响） |

> 以下为修复前的原始记录。


`miniapp/src/utils/order-aftersale.ts` 里有 `COMPLETED_AFTERSALE_WINDOW_MS = 7 天`，
但**后端状态机 `applyForAftersale()` 没有这个校验**。

后果：绕过小程序直接调 `POST /orders/:id/aftersale`，可以无限期申请退款。
（当前不构成实际风险，但规则应当前后端一致。）

### 4.2 订单列表的「申请售后」写死 REFUND

`pages/orders-list/index.vue:512` → `type=REFUND`。
从列表点进去只能申请退款，想重做或投诉必须先进入订单详情页。
（小体验问题，不算阻塞。）

## 五、建议的修复优先级

| 优先级 | 问题 | 建议动作 |
|:---:|------|----------|
| **P0** | 免费重做静默失败 | 见下方方案 |
| P1 | 7 天时效前后端不一致 | 后端 `applyForAftersale` 补上 COMPLETED 的 7 天校验 |
| P2 | 列表页只能申请退款 | 改为让顾客在申请页内自由切换类型（申请页本来就支持切换） |

### P0 修复方案（供选择）

| 方案 | 做法 | 代价 |
|------|------|------|
| **A（推荐）** | 重做时**清空订单条目的批次分配**（`production_batch_id = null`、`allocated_at = null`），并把订单状态置回 **PURCHASING**，让它重新进入正常的排产流程 | 小，改一处服务逻辑 |
| B | 重做时**新建一张 0 元订单**（复用补剂商城"免费补发"的思路），原单标记为已重做 | 中，要处理金额/统计口径 |
| C | 暂不做重做：后台只保留「退款 / 仅登记」，把重做降级为人工线下处理 | 最小，但丢失一个售后选项 |
