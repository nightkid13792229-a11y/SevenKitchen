# 生命阶段判定：完整调查结论

> 日期：2026-09-19
> 范围：系统如何根据狗狗档案判定生命阶段 + 档案为空/没填完时各处的实际行为
> 方法：代码通读（附文件:行号）+ **生产数据库实证**
> 标注：【事实】= 代码或数据可直接确认；【推断】= 基于证据的推论
>
> **执行状态：方案 A 已实施并部署（2026-09-19）** —— 见文末「七、实施记录」。

## 一、结论速览（三句话）

1. **判定逻辑后端有一套权威实现**，用「生日 + 品种/体型阈值 + 活动量 + 人工覆盖」四要素，**永远能给出一个结果**（缺字段就用默认值兜底，不返回空）。
2. **数据库层面「档案不全」其实不可能发生** —— `birthday` / `breedId` / `currentWeightKg` / `activityLevel` / `lifeStageOverride` **全是非空列**，建档时也全部必填。
3. **真正会出问题的是「品种查不到」**：生产上有 **266 只混血犬（占全部狗狗 5.9%）**，因为小程序的前端算法**不认体型**，导致在这些狗身上**算不出生命阶段 → 静默放行（不提示、不拦截）**。

## 二、系统如何判定生命阶段

### 2.1 权威实现

**入口**：`resolveDogProfileStage()` — `backend/src/domain/dog/dog-stage.service.ts:85`
食谱匹配只是取它的产物：`mapDogProfileToSeriesLifeStage()` — `backend/src/domain/recipe/recipe-series.ts:73`

### 2.2 参与判定的字段

| 字段 | 作用 | 证据 |
|------|------|------|
| `birthday` | 算月龄（日历月相减）与周龄 | `dog-stage.service.ts:358-381` |
| `sizeClassOverride` | **体型优先级 1**（混血犬靠它） | `:289-298` |
| `breed.sizeCategory` | 体型优先级 2，缺失 → 中型 | `:299-306` |
| `breed.adultAgeMonths` → 体型默认 → 12 | 成犬月龄阈值 | `:308-319`、`constants.ts:81-86` |
| `breed.seniorAgeYears` → 体型默认 → 10 | 老年阈值 | `:321-332`、`constants.ts:93-98` |
| `lifeStageOverride` | **人工覆盖，优先级最高** | `:109-115` |
| `activityLevel` | **只用来细分成犬**（普通/高 vs 低运动量） | `:204-206`、`:156-160` |
| `gender` | **不参与判定**，只在繁殖期给出提示 | `:277-284` |
| `isNeutered` | **不参与判定**，只改热量系数 | `dog-calc.service.ts:179-185` |
| `bcsScore` | **完全不参与判定**，只影响热量 | `dog-calc.service.ts:283` |

### 2.3 判定优先级（伪代码）

```
1) 有人工覆盖值（且不是 NONE）        → 直接用
2) 月龄 < 成犬阈值                     → PUPPY
3) 月龄 ≥ 老年阈值                     → SENIOR
4) 其余                                → ADULT，再按活动量细分：
     活动量 = 静息/低  → 低运动量成犬或老年犬
     其余              → 普通或高运动量成犬
```

### 2.4 有两层阶段，别混淆

| 层级 | 取值 | 用途 |
|------|------|------|
| **档案层** | PUPPY / ADULT / SENIOR / PREGNANCY / LACTATION | 描述这只狗 |
| **食谱层**（对外） | PUPPY_UNDER_14_WEEKS / PUPPY_14_WEEKS_PLUS / HIGH_ACTIVITY_ADULT / LOW_ACTIVITY_ADULT_OR_SENIOR / REPRODUCTION | 决定用哪个食谱版本 |

映射规则：妊娠/哺乳 → 繁殖期；幼犬 14 周为界分两档；老年 → 低运动量成犬或老年犬；成犬按活动量分两档。

## 三、档案「不全」时的实际行为

### 3.1 【实证】数据库层面根本不可能缺字段

我查了生产库的 Prisma 模型：`birthday`、`breedId`、`currentWeightKg`、`activityLevel`、`lifeStageOverride` **全是必填列**（`prisma/schema.prisma` Dog 模型），建档流程也全部强制必填（`miniapp/src/pages/dog-create/index.vue:2160`）。

> **所以「没填生日」这种档案在真实数据里不存在。** 前端 helper 却按「生日可能为空」写，属于防御性代码，但它的兜底行为是错的（见 3.3）。

### 3.2 【实证】真正存在的是「品种查不到」——混血犬

生产数据：

| 项 | 数量 |
|---|---|
| 狗狗档案总数 | **4513** |
| 其中混血犬（用全零虚拟品种 ID） | **321** |
| 这 321 只的体型填写情况 | **全部已填**（小型 172 / 中型 143 / 大型 6） |
| 这 321 只中**没有人工覆盖生命阶段**的 | **266**（占全部狗狗 **5.9%**） |

### 3.3 于是产生了前后端口径不一致

| | 后端 | 前端 |
|---|---|---|
| 混血犬怎么判 | **用体型阈值**（`sizeClassOverride`）✅ 能判出来 | **完全不看体型**（`miniapp/src/utils/life-stage-match.ts` 里根本没有体型字段）❌ |
| 查品种失败时 | 兜底为中型犬阈值（12 月 / 10 岁）→ 仍给出阶段 | **返回 null** |
| 得到 null 之后 | — | `isRecipeLifeStageMatch(..., null)` **返回 true** → **视为"匹配"** |

**后果（同一只混血犬、同一个食谱）**：

| 页面 | 用什么判定 | 结果 |
|------|-----------|------|
| **食谱详情页** | 用后端返回的 `matchType` | ✅ **会提示**（不匹配时整卡转警示色） |
| **成品订购页** | 用前端自己算 | ❌ **算不出 → 静默放行** |
| **DIY 制作页** | 同上 | ❌ 静默放行 |
| **DIY 制作单** | 同上 | ❌ 静默放行 |

> **这就是「详情页有提醒、订购页没提醒」的根因。**

### 3.4 更大的风险面：品种接口请求失败

前端要拿品种阈值，必须先请求 `/dogs/breeds`（`recipe-order/index.vue:544-557`）。
**这个请求失败时只打日志**（`recipe-order:1303-1305`），`breeds` 保持空数组。

→ 此时**所有狗**（不只是混血犬）都算不出生命阶段 → **全部静默放行**。

这是暴露面最大的一条：一次网络抖动，整站的生命阶段提醒就全没了，而且**没有任何人会发现**。

## 五、其他发现（按严重度）

| # | 级别 | 问题 | 证据 |
|---|:---:|------|------|
| 1 | 🔴 高 | **"算不出来 = 匹配"是静默失效路径**。应该做成三态（匹配 / 不匹配 / **未知**），未知时明确告知"档案信息不足，无法确认是否适合" | `life-stage-match.ts:190-191` |

### 一条被排除的怀疑

曾有推断认为「混血犬未填体型时，算饭量会 500」。**我查了生产数据：321 只混血犬全部已填体型**（且建档时强制必填），所以**这个 500 不会发生**，仅是理论可能。✅ 已排除。

## 六、我的修复建议

### 方案 A（推荐，治本）：前端不再自己算，直接用后端结果

| 动作 | 说明 |
|------|------|
| 1 | 后端在**列表与详情**接口都返回 `lifeStageMatch`（含 `matchType` 与 `dogLifeStage`） |
| 2 | 订购页 / DIY 页 / 制作单改为读后端结果，删掉前端的 `resolveDogRecipeLifeStage` 重算 |
| 3 | 前端删掉 5 份标签映射，统一用一份 |

**收益**：口径天然一致；详情页与订购页不会再出现"一个有提示一个没有"；混血犬靠体型正确判定。
**代价**：后端接口要补字段，前端三处要改。

### 方案 B（最小改动）：把"未知"变成可见状态

| 动作 | 说明 |
|------|------|
| 1 | `isRecipeLifeStageMatch` 改为返回三态（匹配 / 不匹配 / **未知**），不再把 null 当匹配 |
| 2 | 未知时显示中性提示：「**档案信息不足，无法确认这份食谱是否适合**，建议先在档案里完善品种/体型」 |
| 3 | 前端 helper 补上**体型分支**，让混血犬能算出来（与后端对齐） |
| 4 | `/dogs/breeds` 请求失败时给出可感知的降级提示，而不是静默 |

**收益**：改动小、立刻消除"静默放行"。
**代价**：前端仍在自己算，长期仍会与后端跑偏。

### 我的建议

**先做 B 里的第 1、2 条（消除静默），再做 A（统一口径）。**
理由：第 1、2 条是**风险**（该提示的时候没提示），改动却极小；A 是**架构债**，值得做但可以排期。
