- 日期：2026-09-22
- 对象：`miniapp/src/pages/recipe-diy/index.vue`（2123 行）—— 用户点「自己做」后进入的配置页
- 参照：`miniapp/src/pages/recipe-order/index.vue`（4834 行）—— 用户点「买成品」后进入的订购页
- 状态：**已实施**（2026-09-22，`feature/dog-profile-guidance`）

---

## 一、先分清两页的定位差异

两页长得像、但目标不同，所以只能「借做法」，不能「照搬」：

| | 成品订购页 | DIY 配置页 |
|---|---|---|
| 用户来干什么 | 花钱买做好的 | 免费拿一份「怎么做」的说明书 |
| 决策终点 | 确认订单 → 付款 | 生成制作单 → 去看采购清单和补剂 |
| 最大阻力 | 「敢不敢买」（品质、到货、售后） | 「值不值得动手」（我做不做得来、能得到什么） |
| 价格角色 | 核心（价格条 + 每袋价） | 无（这页本来就不收费） |
| 页面长度 | 长（6 大区块，讲透保障） | 短（4 大区块） |

**结论**：搬家重点是「**信息组织方式**」和「**每一步都给理由**」，而不是把成品页的售后/价格内容搬过来。

## 二、成品订购页做得好的 6 个做法（值得搬）

1. **档案信息与喂食参数合成一行六项**
   成品页把「年龄 / 性别 / 体重 / 每日餐次 / 每日饭量 / 每餐约」放在狗头像下方同一个面板里（`dog-profile-facts`），选项卡与参数在同一个内嵌面板 + 分隔线，视觉归属清楚。
   → DIY 页只放了 4 项（年龄/性别/体重/餐次），把「每日饭量 / 每餐约」另起一个区块重复展示。

2. **加载失败 ≠ 没有档案**
   成品页有独立的失败态：「狗狗档案加载失败 / 请检查网络后重试，**避免重复建档**」+ 重新加载按钮（`dogsLoadFailed` / `retryDogsLoad`）。
   → DIY 页**没有这个状态**：拉列表失败时会退化成「暂无狗狗档案」+「创建狗狗档案」按钮，用户可能因此**重复建档**。

3. **长解释默认收起，用一行「问题 + 展开」引导**
   成品页把饭量算法收成一个折叠行「每日饭量是怎么算的？ 展开」，展开后是 3 条编号人话。
   → DIY 页把算法做成 5 张计算卡（DER / 零食能量 / 鲜食能量 / 每日饭量 / 每餐饭量），默认收起但体量重、术语多。

4. **互斥条件当场说明，不靠点击失败**
   成品页在开启自定义分装后，天数选项下方立刻出现一行「已启用自定义分装，上方天数选择暂不生效」。
   → DIY 页只在用户**点了变灰的天数**后才弹 toast 解释。

5. **校验提示常驻**
   成品页同时展示「分装规格不合法」和「未达最低订购量」两类提示。
   → DIY 页只有分装规格提示，没有等价的最低量提示（业务上是否需要待确认）。

6. **交付与保障用「三步时间线」讲成一个旅程**
   成品页的「交付与保障」按 预约制作 → 冷链履约 → 售后保障 排列，每步一张小卡（图 + 标题 + 一行说明），最后用一张高亮卡回答「赔什么」。
   → DIY 页完全没有对应内容，用户不知道自己会拿到什么。

另外两个一致性缺口：
- 成品页底部栏是「客服 + 价格 + 主按钮」；**DIY 页只有主按钮，没有任何客服入口**（该组件在其他页已复用）。
- 成品页天数区块标题是「快速选择备餐天数」；DIY 是「配置天数」+ 红色星号。

## 三、DIY 配置页逐区块改造方案

> 硬约束：**不要重新加回刚刚被删掉的小字说明**（「自己做」副标题、「生成制作单」上方常驻说明、补剂入口小字）。下面的方案都遵守这条。

### 区块 0 · 顶部食谱信息卡（现状 4–37 行）

**现状**：食谱名 + 适用生命阶段标签 + 三行数字（能量密度 / 营养标准 / **设计软件**）。
**问题**：
- 「设计软件 = Setar」是内部系统名，对顾客零价值，还占一行；
- 没有一句话卖点（成品页有 `sellingPoint`）；
- 营养标准是一串标准编号（FEDIAF 2021 等），放平铺三行里像参数表。

**目标**：
1. **删掉「设计软件」这一行**；
2. 食谱名下方补**一句话卖点**（沿用 `recipe.sellingPoint`，与详情页/成品页同一口径）；
3. 「营养标准」改成**可点开的背书卡**（成品页同款 `standard-card`），收起时一行，点开才是标准说明。

### 区块 1 · 选择爱犬 + 确定饭量（现状 40–83 + 116–229 行）→ 合并为一个区块

**现状**：两个区块。「选择爱犬」里 4 项档案信息；「确定饭量」里又出现 3 个数字（每日参考 / 每餐约 / 主食能量），其中**每日、每餐与上一区块语义重复**。
**目标**：
1. 合并为一个区块，**档案 + 喂食合并成一行六项**（年龄 / 性别 / 体重 / 每日餐次 / 每日饭量 / 每餐约），完全对齐成品页；
2. 「主食能量」单独降级为**小字一行**（它是热量核对值，不是决策信息）；
3. **补上加载失败态**（照搬成品页文案：避免重复建档 + 重新加载）；
4. 保留「起始喂食建议」，但改成与成品页一致的**折叠行**（「每日饭量是怎么算的？ 展开」）；
5. **「饭量计算过程」里的 5 张计算卡**（详见下方附录 A）→ 换成成品页那 3 条编号人话。

### 附录 A · 「5 张饭量计算卡」到底在哪、是什么

位置：「确定饭量」区块最下方，默认收起的折叠区「**饭量计算过程**」（`recipe-diy/index.vue:150-227`）内。

| # | 卡标题 | 内容 |
|---|---|---|
| ① | 每日能量需求 (DER) | `{{totalDer}} kcal/天` |
| ② | 每日零食能量 | `{{treatDeduction}} kcal/天`；未配置则「未配置零食」；超限追加「⚠️ 已触发10%安全上限」 |
| ③ | 每日鲜食能量 | `{{finalFoodKcal}} kcal/天` |
| ④ | **每日饭量**（高亮卡） | 公式「每日饭量 = (鲜食能量 ÷ 食谱能量密度) × 1000」+ 食谱能量密度 + `{{dailyIntakeG}} g/天` |
| ⑤ | **每餐饭量**（高亮卡） | 公式「每餐饭量 = 每日饭量 ÷ 每日餐数」+ 每日餐数 + `{{perMealG}} g/餐` |

成品页对应位置（`recipe-order/index.vue:149-159`）只有一行折叠「每日饭量是怎么算的？ 展开」，展开是 3 条编号人话 + 一句观察建议。

**判断**：成品页讲「为什么是这个数」（顾客能听懂），DIY 页讲「这个数怎么一步步算出来」（DER / 公式 / 中间值），对决策帮助小、体量大。**建议换成 3 条人话**（保留折叠），而不是直接删除。

### 附录 B · 「生命阶段二次确认」到底指什么

触发条件：狗狗生命阶段与食谱适用阶段**不一致**时，用户会被问两次。

**第 1 次 · 页面橙色卡片**（`recipe-diy/index.vue:86-113`）
选完狗后出现「生命阶段提醒」卡，写明不一致原因，按钮「切换到XX」/「我已知晓」；点「我已知晓」只是 `showWarning = false`（`dismissWarning`，`:877-879`），**不写留痕**。

**第 2 次 · 点「生成制作单」时弹窗**（`:1077-1087` → `utils/life-stage-match.ts:182-217`）
标题同为「生命阶段提醒」，内容为同一段不一致说明 + 合规话术「继续表示您已知晓并自行决定；如狗狗有明确诊断或正在遵医嘱饮食，请先咨询执业兽医。」按钮「我已知晓，继续」/「**再看看**」。确认后才写留痕（`recordLifeStageAcknowledgement`）。

**问题**：① 用户会觉得「刚确认过又问一遍」；② 第二次的取消按钮「再看看」正好是漏斗末端的放弃键。

**建议**：卡片确认时即写留痕，本次进页面不再弹窗；切换狗狗时属于新的一只狗，重新提醒（`checkLifeStageMatch` 会重新置 `showWarning = true`），逻辑不变。

### 区块 2 · 生命阶段提醒（现状 86–113 行）

**现状**：独立区块，插在「选择爱犬」和「确定饭量」之间；页面里点「我已知晓」只是隐藏卡片，点生成时**又弹一次同义模态**。
**目标**：
1. **挪进狗面板内部**（成品页的 `inline-warning-card` 做法），紧贴所选狗狗，而不是单独占一屏；
2. **去掉二次确认**：卡片上已确认过，本次进入页面就不再弹同义模态；
   ⚠️ 合规留痕（`recordLifeStageAcknowledgement`）必须保留，只是**合并 UI**，不是取消留痕。

### 区块 3 · 天数与分装（现状 231–318 行）

**现状**：标题「配置天数」+ 红星；天数选项；分装摘要 + 自定义按钮；分装非法时才提示；自定义开启后天数变灰，**点一下才 toast 说明**；保质期说明折叠。
**目标**：
1. 标题改成**「快速选择备餐天数」**（成品页口径），去掉红星（已有默认值 7 天，星号会让人以为必须动它）；
2. 开启自定义分装后，**天数选项下方常驻一行提示**「已启用自定义分装，上方天数选择暂不生效」，不再靠点击失败解释；
3. 「取消自定义分装」会**静默丢弃用户填的克数/袋数** → 加一次确认（或至少一句「已恢复默认分装」）；
4. 「保质期说明」保持折叠不动；
5. **不做最低订购量提示**——顾客自己做，没有起订量限制（业务已确认）。

### 区块 4 · 新增「你会拿到什么」（对标成品页的「交付与保障」）

**现状**：没有。用户点完按钮才知道会得到什么。
**目标**：新增一个三步卡区块，按**发生顺序**讲清产物：

| 步骤 | 一句话 |
|---|---|
| ① 生成制作单 | 采购清单（含用量与损耗）、补剂清单、制作步骤、分装与保质期建议 |
| ② 照着买 | 食材按清单自行采购；需要补剂的话可在制作单里一键下单 |
| ③ 照着做 | 按制作步骤和分装建议操作，可保存/分享制作单 |

理由：这正是 DIY 路线的「敢不敢开始」决策，也是**补剂曝光的第二个自然落点**（在用户点按钮之前就把「补剂清单」这件事说清楚）。
⚠️ 文案要短，不写价格、不写「不扣款」这类刚被删掉的说明。

### 区块 5 · 底部操作栏（现状 320–344 行）

**现状**：单按钮「生成制作单」；按钮不可用时显示一行原因（保留，这是有用的功能态）。
**目标**：
1. 左侧补**客服入口**（`CustomerServiceInlineButton`，与成品页/订单页同一组件、同一位置）；
2. 主按钮保持现状（深绿实心、固定底部）；
3. **不新增**常驻说明小字。

## 四、明确不动的部分

- 生成制作单的**逻辑与参数**（选了哪只狗、几天、分装规格怎么算）——只改呈现，不改口径；
- 保质期说明的文案；
- 底部按钮「不可用时才出现原因」的机制（这是刚保留的功能态）；
- 补剂入口（在制作单页，不在本页）；
- 不做任何价格展示（本页不收费）。

## 五、建议的实施顺序（按「收益 / 风险」分批）

**第 1 批（低风险，纯呈现）**
1. 删「设计软件」行；
2. 天数区块改名 + 去掉红星；
3. 自定义分装开启后常驻提示；
4. 补客服入口。

**第 2 批（结构合并，收益最大）**
5. 档案 + 喂食合并成一行六项，删掉重复的「确定饭量」网格；
6. 生命阶段提醒挪进狗面板；
7. 补加载失败态（避免重复建档）。

**第 3 批（内容增补，需产品确认文案）**
8. 顶部补一句话卖点 + 营养标准折叠卡；
9. 新增「你会拿到什么」三步卡；
10. 计算卡整块下线或深折叠（**需你确认**：是否还有顾客要看热量推导）；
11. 生命阶段二次确认合并（**需你确认**：合规留痕方式）。

## 六、风险与验证

| 风险 | 说明 | 应对 |
|---|---|---|
| 计算卡下线 | 可能有顾客/客服依赖热量推导做解释 | 先折叠保留，观察后再删 |
| 生命阶段确认合并 | 留痕是合规凭证 | 只合并 UI，`recordLifeStageAcknowledgement` 调用链不变，加回归断言锁住 |
| 区块合并的回归面 | 涉及 `canGenerateSheet` 的输入项 | 不加字段、只改布局；回归断言覆盖「合并后仍能生成」 |
| 已有回归测试 | `life-stage-warning.regression.spec.ts`、`supplement-purchase.regression.spec.ts` 等会命中 | 同步更新断言 |

验证方式：`npm run preview`（`miniapp/dist/dev/mp-weixin`，连本地后端）逐条走一遍，再跑全量测试。
