## 三、第 6 问的答案：这些信息营养师怎么看到

### 通路① 食谱设计器右侧栏（营养师设计时常驻）

- **犬只档案**：性别 / 年龄 / 绝育 / 品种 / 体重 / 体况评分 / 活动量 / 每日餐数 / 零食摄入 / 每日目标能量
- **「过敏与忌口」面板**（2026-10-04 第四期重做）：
  - 分两档：**确诊过敏（配方必须完全避开）** / 可疑过敏
  - **实时比对配方成分**：配方命中确诊过敏原时，面板顶部直接报警「**配方命中确诊过敏原**」
    → 这是最强的一道提醒，不依赖人工逐条核对
- **顾客在订单里填的**：喜欢的食材、忌口（两行都在）
- 顾客的定制需求（目标、体重、备注）

### 通路② 后台「定制食谱订单」详情页

- 过敏分两份对照：**档案最新** vs **下单时填写**（不一致时弹「下单后档案有更新」提示）
- 疾病史同样两份对照
- 饮食偏好（喜欢的食材 / 不吃的食材）
- 补充说明（顾客备注）

**结论**：过敏走的是"设计时自动拦截 + 报警"，偏好与备注在设计器和后台都能看到。这条链路目前是通的。

## 四、数据流变更：过敏一律写进档案（第 5 条）

| 项目 | 改造前 | 改造后 |
|---|---|---|
| 写入开关 | 勾了「需要健康管理」**且**勾了知情同意才写 | **恒写**（`syncToHealthProfile: true`） |
| 疾病史 | 顾客在定制页填 → 写进档案 | 定制页**不再收集**疾病史；营养师看档案里已有的那份（订单详情已展示"档案最新疾病史"） |
| `needsHealthManagement` | 由顾客勾选决定 | 由**是否填了过敏**推导 |

### 写入档案后，实际影响是什么（已核对代码与数据模型）

- 写入的过敏记录 `certainty` 取数据模型默认值 = **SUSPECTED（可疑）**，来源 `source` = OWNER
- 推荐过滤口径：**只有"确诊"过敏才会把食谱从推荐里拿掉**；"可疑"是**强提示 + 排在最后**，不会被静默隐藏
- 所以：**本次改造不会因为顾客填了过敏就突然让首页推荐变少**，而是让营养师侧与档案侧都看得到这条信息
- 写入是**只增不删**：不会覆盖或删除档案里已有的记录（后端按 `dogId + allergen` 去重，已存在则跳过）

## 五、改造后的页面结构

```
[ Banner ]  头像 + 狗名 + 切换 ▼（狗选择器并入；未登录/加载中/无档案 三种状态卡紧随其下）
[ 待付款单提醒 ]（保留）
[ 1 定制目标 ]  体况建议 + 每日能量摘要 + 「去制定 / 查看体重管理计划」按钮
                 方向只读：有计划跟随计划；没计划按体形给（BCS ≥6 减重 / ≤3 增重 / 其余维持）
[ 2 过敏信息 ]  常见过敏原点选（可再点取消）+ 手动录入 + AI 识别报告 + 已传报告列表
[ 3 饮食偏好 ]  喜欢的食材 / 不吃的食材
[ 4 备注 ]
[ 上传资料 ]
[ 预计交付 + 成品抵扣 ]  小字精简为"自动排最近可接单的工作日，遇节假日顺延。"
[ 提交按钮 + 支付时限提示 ]
[ 底部固定栏：下一步：支付 ¥300 ]
```

**删除项**：健康管理板块（含勾选、疾病史、只读参考、"只增不删"说明）、三个方向单选、
「下一步：支付」重复块、知情同意块。
