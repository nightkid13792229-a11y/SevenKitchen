# 疫苗板块 · 技术方案（2026-10-15）

> 三层关系：**需求**（要什么）→ **本文**（数据怎么存、接口给什么、算法怎么拆）→ **代码**。
> 本文不写实现细节，只定结构、字段、边界与顺序 —— 让工程不必在写代码时再回来问产品。

---

## 〇、给老板的一页

**改造后是四层，各干一件事：**

```
① 程序表   —— 免疫程序规格，就一张表（改数字只改一处）
② 引擎     —— 纯函数：输入（生日 + 记录 + 忽略决定）→ 输出（每一步的状态）
③ 接口     —— 只给前端一份"已经算好的东西"
④ 页面     —— 只渲染，不做任何计算
```

**为什么这么拆**：现在规则散在 3000 行里（窗口算法、宽限期、重启阈值分别写在三个地方），前端还自己算了一遍合并与顺序，所以出现"两套口径"。拆完以后：

| 现在 | 改造后 |
|---|---|
| 算法散在 3075 行里，注释与代码打架 | 一张程序表 + 四个纯函数 |
| 前端自己算合并、算顺序、算状态文案 | 前端只有渲染，连"下一针"都是后端算好的 |
| 改一个数字要翻三个文件 | 改程序表一行 |
| 测试从代码反推（代码错，测试跟着错） | 测试从程序表生成 |

**改动安全**：分 5 个提交，每步都能单独回退。

⚠️ **这一版按"模块未上线"重写过**（2026-10-15 老板指出：疫苗板块还没上生产，现有数据都是测试数据）。
上一版里那些"为了不弄坏老数据"的设计（保留废弃字段、JSON 兼容、接口只加不改、先搬文件再改）**全部去掉** —— 没有要保护的东西，就不该背这个包袱。

## 〇之二、自审：去掉"怕弄坏数据"的束缚之后，改了什么

**前提订正**：疫苗板块**尚未在正式版上线**（小程序只到体验版），生产库里那 50 只档案（测01~测49）是**测试数据**。
所以：**没有存量数据要保护，没有老客户端要兼容。**

| # | 上一版怎么写的（怕弄坏数据） | 放开后怎么改 | 为什么更好 |
|---|---|---|---|
| 1 | `nextDueDate` **保留列**，只是不读不写 | **直接删列** | 一个不再使用的字段就是下一次冲突的种子 —— 留着它，半年后一定有人问"这列是干嘛的" |
| 2 | `decisions` 用 JSON，**再加一个并列的 `reasons` 列**兼容老数据 | **整张 `DogVaccinePlan` 换成 `VaccineDecision` 表**（一条决定一行，带原因） | JSON blob 没法查、没法审计、每次加字段都要兼容；一张表解决（"已忽略几项"变成一句 count） |
| 3 | 记录上的 `status` 保留 | **删列** | 记录都是"已经打过"这一种事实；顾客端的状态选择器早就下线了，这个字段是历史残留 |
| 4 | `kinds` 读的时候还要兼容旧值 | **写入规则写死**：有 `components` 由它推，没有则按名字字面判 | 从结构上让"改了病种不算数"（冲突 A13）**不可能再发生** |
| 5 | 接口"只加字段、不改老字段语义" | **可以直接破坏性改**：删 `nextDueDate`、删 `status`、删 `audience` 参数 | 不用背兼容期，接口一次到位 |
| 6 | 第 1 步"后端只搬文件，行为零变化" | **删掉这一步** | 没有生产数据要护着，就不该"先搬一遍再改一遍" —— 那是给上线系统准备的做法 |
| 7 | 老算法用例"逐条对齐" | 改成**逐条裁决**：错的直接删（记下为什么删），对的保留 | 有些用例钉的本来就是错的行为（如"年度加强窗口差 13 个月"） |
| 8 | 前端"新旧并存、逐步切" | **整块替换**：旧的 4 个巨型组件直接删 | 没有灰度这回事，留着旧组件只会让两套逻辑并存 |
| 9 | 测试档案要迁就旧数据形状 | **按新规则重建**（脚本生成），验收样本与新算法天然一致 | 测 50 只档案本来就是为了验收，改成按新规格建更干净 |
| 10 | `audience` 参数"保留" | **删掉**（后端里本来就是 `void audience`） | 死参数 |

**仍然要守住的（放开 ≠ 乱来）**：
1. 一律走 Prisma migration，不手改库；2. 每个提交可单独回退；3. 只在体验版验证，不发布小程序正式版；4. 删列/换表前先导出一次现存测试数据（万一要对照）。

## 一、数据层

### 1.1 数据模型（重做，不再迁就旧结构）

| 表 | 现在有什么 | 改成 |
|---|---|---|
| `VaccineRecord`（接种记录） | 疫苗名、接种日、**`nextDueDate`**、`notes`、**`status`**、`attachments`、`kinds`、`components`、`productVerified` | **删 `nextDueDate`、删 `status`**；其余保留。`kinds` 写入规则写死（见 1.1.2） |
| `DogVaccinePlan`（dogId + `decisions` JSON） | JSON 存每一步的决定 | **整表删掉**，换成 `VaccineDecision`（见 1.1.1） |
| 抗体检测 | 没有 | 新增 `AntibodyTestRecord`（见 1.2） |

#### 1.1.1 忽略决定：从 JSON 换成一张表

```
VaccineDecision
  dogId      + stepKey   ← 唯一键
  decision   SKIP / DEFER / ACCEPT
  reason     NOT_NOW / STOPPED（可空）
  updatedAt
```

好处：「已忽略 N 项」变成一句 count；每个决定**有原因、有时间**，将来出问题能查；加字段不用再做 JSON 兼容。

#### 1.1.2 `kinds`（这条记录能顶哪几类）的写入规则

**写入时一律由后端算，前端不能传**：

| 情况 | 怎么算 |
|---|---|
| `components` 非空（查到了产品，或家长勾了病种） | **由病种推导类别**（唯一事实） |
| `components` 为空、但名字能按字面判类别（"狂犬""六联"） | 用字面规则直接给类别 |
| 两条都不成立 | **不保存**（需求 R6：不允许"存了但不影响计划"的记录） |

**读取时**：若 `components` 为空、而这个名字现在能在产品库里认出来了（产品库后来补齐了），**按产品库重算一次** —— 这样产品库变强，老记录跟着变准，不会留下"当年判错、永远判错"的记录。

> 这一条替代了上一版的"读时兼容旧 kinds"，从结构上消灭冲突 A13。

### 1.2 新增一张表：抗体检测

**为什么单独一张表**：它不是疫苗（字段不同、不参与"接种记录"的判读），但要在同一个列表里显示。现有架构就是"每类记录一张表"（就诊/体检/过敏/疫苗各一张），保持一致。

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` / `dogId` | — | 与其他记录表一致 |
| `testedAt` | Date | 检测日期（**决策依据**） |
| `targets` | String[] | 检了什么：`CORE`（核心三项）/ `RABIES` |
| `result` | Enum | `PASS` / `FAIL` / `UNKNOWN`（报告没给结论时用 UNKNOWN，界面写"请让兽医判读"） |
| `value` / `unit` | String? | 报告的原始数值（可空，不强求） |
| `nextReviewAt` | Date? | 下次评估时间（合格时算：检测日 + 3 年） |
| `notes` / `attachments` / `createdAt` / `updatedAt` | — | 与其他记录表一致（原件留档） |

**它怎么影响计划**：`targets=CORE` 且 `result=PASS` 时，核心疫苗当前那一针的加强标为"已被抗体检测替代"，下一次评估时间 = `nextReviewAt`。
⚠️ `targets=RABIES` **不影响计划**（只记录，用于出行证明）。

### 1.3 产品库：仍是代码表，但字段分层

**结论：不搬进数据库。** 理由：这份表要经过兽医审核、要能追溯"哪一版生效"，代码表+版本管理比数据库行更好审。

但要把字段**分成两类**，避免前端拿到不该用的东西：

| 类别 | 字段 | 谁用 |
|---|---|---|
| **对外**（接口下发） | `name`、`components`（含哪些病种）、`manufacturer`、`recommendable`（是否参与推荐） | 前端展示与选择 |
| **内部**（只在后端用） | `aliases`、`brand`、`minWeeks`、`registration`、`booster`、`note`、`earlySeries` | 匹配、归类、排期 |

因为匹配（同品牌优先、别名）**只在后端做**，所以品牌与别名不下发（需求 6.2/B9）。

## 二、算法层：一张表 + 四个纯函数

### 2.1 程序表的数据结构

每一行 = 一个步骤。字段如下（这就是"规格表"在代码里的样子）：

| 字段 | 含义 | 例 |
|---|---|---|
| `kind` | 类别 | `core` / `rabies` / `lepto` |
| `key` | 步骤标识 | `core-puppy-1` |
| `label` | **页面上写的字**（人话） | `第 1 针` / `每年一次` |
| `layer` | 层级 | `MUST`（必打）/ `SUGGEST`（强烈建议） |
| `series` | 属于首免系列还是加强 | `PRIMARY` / `BOOSTER` |
| `windowKind` | 窗口形态（见下） | `AGE` / `FLEX` / `GRACE` |
| 参数 | 随 windowKind 而定 | 年龄下限 / 最短间隔 / 最长间隔 / 宽限天数 |
| `basis` | 依据文案（展开时给家长看） | "WSAVA 2024：6~8 周起…" |
| `titerable` | 能不能被抗体检测替代 | 核心 = true；狂犬/钩端 = false |

**三种窗口形态**（需求 5.1 那张表的直接落地）：

| 形态 | 起点 | 终点 | 用在哪 |
|---|---|---|---|
| `AGE` | 生日 + 年龄下限 | 起点 + 窗口长度 | 每个系列的第一针（核心 6~8 周、狂犬 12 周+30 天、钩端 8~12 周） |
| `FLEX` | **上一针实际接种日** + 最短间隔 | 上一针 + 最长间隔 | 首免系列的后续针（2~4 周） |
| `GRACE` | 上一针 + 间隔 | 起点 + 宽限 | 所有加强针（核心 3 年+90 天、狂犬/钩端 1 年+30 天） |

**程序表逐行**（与需求附录 A 一一对应）：

| key | 类别 | 层级 | 形态 | 参数 |
|---|---|---|---|---|
| `core-puppy-1` | core | MUST | AGE | 6 周起，窗口 2 周 |
| `core-puppy-2..N` | core | MUST | FLEX | 2~4 周 |
| `core-puppy-last` | core | MUST | FLEX | 2~4 周，且**窗口起点不早于 16 周龄** |
| `core-26w` | core | MUST | AGE | 26 周起，窗口 4 周 |
| `core-adult-N` | core | MUST | GRACE | 3 年 + 90 天 |
| `rabies-1` | rabies | MUST | AGE | 12 周起，窗口 30 天 |
| `rabies-N` | rabies | MUST | GRACE | 1 年 + 30 天 |
| `lepto-primary-1` | lepto | SUGGEST | AGE | 8 周起，窗口 4 周 |
| `lepto-primary-2` | lepto | SUGGEST | FLEX | 2~4 周 |
| `lepto-repeat-N` | lepto | SUGGEST | GRACE | 1 年 + 30 天 |
| `lepto-restart-1/2` | lepto | SUGGEST | FLEX | 上一针 ≥18 个月时触发，第 1 针 [今天,+2 周]，第 2 针 [+2,+4] 周 |
| `core-early-1` | core_early | — | AGE | 4 周起；**不出现在默认计划里** |

> "针数按起始周龄反推"这条规则（需求 A.3 第 3 条）就落在 `core-puppy-*` 的**展开**上：从起始针开始每 2~4 周排一行，直到有一行落在 ≥16 周龄；起始 ≥16 周 → 只有一行（即"补一针"）。

### 2.2 引擎：四个纯函数

| 函数 | 输入 | 输出 | 关键规则 |
|---|---|---|---|
| `materializeSteps` | 生日 + 该狗的接种记录（已归类、已核对） | 步骤序列（每步带窗口） | 按 `AGE/FLEX/GRACE` 展开；**按实际接种日滚动**；一针未打且窗口已过 → 窗口挪到今天并带出原窗口 |
| `matchRecords` | 步骤序列 + 记录 | 每步：`status`（已完成/待接种/尽快补种/不做）+ 命中的记录 | ① 没核对的记录**不参与匹配**；② 先查产品库按成分能否覆盖该步；③ 库里没有按名字字面判；④ 都认不出 → 不算；⑤ **事实优先于忽略**（有记录就是已完成） |
| `pickNext` | 步骤序列 | "下一针"（唯一一条） | 按紧迫度：逾期 → 到窗口 → 未来；同级取窗口最早 |
| `buildPlanView` | 以上全部 + 忽略决定 + 抗体检测 | 给前端的视图模型（见第三章） | 计划里**只含必打 + 强烈建议**，按时间排；可选疫苗不进；`rhythm` 一句话由类别与周期生成 |

**为什么必须纯函数**：这四个函数不碰数据库，所以可以拿"生日 + 一堆记录"直接跑测试而不需要建库、不需要启服务 —— 这正是"测试从规格表生成"的前提。

### 2.3 文件拆分（前后对照）

| 现在 | 改造后 | 说明 |
|---|---|---|
| `domain/health/immunization-schedule.ts`（3075 行） | `domain/health/vaccine/schedule-table.ts` | **只有数据**：程序表 + 层级 + 依据文案 |
| 同上 | `domain/health/vaccine/engine.ts` | 四个纯函数 |
| 同上 | `domain/health/vaccine/plan-view.ts` | 视图模型组装（含 combo、下一步、节奏行） |
| `domain/health/vaccine-products.ts`（1274 行） | `domain/health/vaccine/products.ts` | 产品目录 + 病种词表（内容不变） |
| `domain/health/vaccine-catalog.ts` | 同上（合并进 products 的"下发"部分） | 目录接口的组装 |
| `application/health/vaccine-plan.service.ts` | 不变（只改调用） | 取数 + 落库 |

⚠️ 这一层**整体重写**（不是"从 3075 行里往外搬"）—— 因为模块没上线，没有"必须保持行为一致"的包袱；
旧文件在新文件跑通并验收之后直接删除。

## 三、接口层

### 3.1 主接口：一次给全（`GET /dogs/:dogId/vaccine-plan`）

前端不再自己拼，所以这一份要够用：

| 字段 | 内容 | 本次变化 |
|---|---|---|
| `next` | 下一针：`{ kindLabel, label, windowStart, windowEnd, statusLabel, missedWindow?, combo? }`；没有任何待办时为 `null` | **新增**（从 steps 里挑出来的那一条） |
| `plan[]` | 免疫计划，**已按时间从近到远排好**，只含必打 + 强烈建议 | 排序改到后端 |
| `plan[].layer` | `MUST` / `SUGGEST` | **新增**（页面上的两个标识） |
| `plan[].titerable` | 这一项能不能用抗体检测替代 | **新增** |
| `plan[].combo` | 能和谁一起打：`{ withKindLabel, windowStart, windowEnd, products[] }` | 保留；产品列表**不再截断到 3 条** |
| `plan[].basis` | 依据文案 | 保留 |
| `ignored` | `{ count, items: [{ label, kindLabel, reason }] }` | **修**：`count` 现在恒为 0（A1），改成真实值 |
| `rhythm` | 一句话："之后：狂犬与钩端每年一次，核心每 3 年一次" | **新增** |
| `pendingReview` | 有几条记录待核对 | **新增**（页面顶部那行提示） |
| `conflicts[]` | 冲突提示 | 保留；`kind` 不再硬编码（A7） |

**"下一针"和"计划"的关系**：`next` 就是 `plan` 里最先要做的那一条（或 `null`）。前端只负责把它画得更大。

### 3.2 记录与抗体检测

| 接口 | 变化（**可以直接破坏性改，不用兼容**） |
|---|---|
| 疫苗记录 CRUD | 入参删 `kinds`（后端算）、删 `nextDueDate`、删 `status`；`productVerified` 保留 |
| `GET /dogs/:id/records` | 返回**两类条目合并**：接种记录 + 抗体检测（前端一个列表渲染）；响应里**不再有** `nextDueDate` / `status` |
| 抗体检测 CRUD | **新增**四个接口 |
| `GET /vaccines/catalog` | 加**字段标签与顺序**下发（需求 6.3）；产品只下发对外字段 |
| `GET /vaccines/classify?name=` | 不变 |
| 计划接口的 `audience` 参数 | **删掉**（后端里本来就是 `void audience`，营养师与顾客拿的是同一份） |

### 3.3 录入识别链路（只取两个信息）

| 环节 | 变化 |
|---|---|
| AI 提示词 | 只输出 `{ name, date }` 列表；**删掉品牌、批号、下次到期日的抽取要求** |
| 识别结果确认页 | 只显示两列（名称 + 日期）；可改、可删 |
| "待核对"的判据 | 收敛成三条：**① 狂犬一律要核对 ② 名称在产品库里认不出 ③ 日期可疑**（原来靠"品牌对不上/复核读到不一样的字"，这两条随字段一起没了） |
| 抗体检测识别 | 同一个识别服务，另一个模板：`{ targets, result, value, unit, date }` |

### 3.4 刷新规则

**前端不做任何本地推算。** 任何写操作（新增/修改/删除记录、忽略/恢复、抗体检测）成功后，**重新拉一次主接口**，用返回结果整屏重绘。

理由：本地推算必然与后端算法分叉 —— 这就是现在"两套口径"的来源。代价是一次网络往返（可接受，且保存本来就要往返）。

## 五、测试策略

### 5.1 算法：从程序表生成用例

程序表的每一行声明它的**测试点**（如 `AGE(6,2)` 声明"生日 +6 周、窗口 2 周"），测试生成器遍历每一行，对每个窗口取三个时点：

| 时点 | 期望状态 |
|---|---|
| 窗口起点 −1 天 | 还没到（不进"下一针"） |
| 窗口起点、窗口终点 | 待接种（进"下一针"） |
| 窗口终点 +1 天 | 尽快补种（写"原建议时间…已过"） |

**关键**：用例从表生成，不是从代码反推。表改一行 → 用例自动跟着变；代码与表不一致 → 用例红。

### 5.2 端到端：11 个原型场景变成 11 组断言

原型 A–K 每一屏对应一组固定输入（生日 + 记录 + 决定）与期望输出（`next`、`plan` 的顺序与状态、`ignored.count`）。这些用**测试档案**跑，不依赖真机。

### 5.3 前端

- `domain/vaccine/*` 的纯函数用真单测（输入输出可判定）
- 组件层只保留少量结构契约（钉语义标记，**不钉中文措辞**）
- **旧测试全部保留**为回归网；当旧断言与正确行为冲突时，以行为为准并同步改断言（我们已经被"钉住 bug 的测试"坑过一次）
