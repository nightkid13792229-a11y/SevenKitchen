## 一、为什么要做（三个具体代价）

### 代价 1：同一个东西，三个页面三个名字

| 概念 | 详情页 | DIY 制作单 | 交付第 2 页 |
|---|---|---|---|
| 净用量 | `amount` | `theoreticalAmount` / `netAmount` | `netG` |
| 制备方法 | `preparationMethod` | `preparationMethod` | `preparation`（接口层改过名） |
| 占比 | `ratio`（0.4） | — | `ratioPercent`（40） |

**最危险的是 `amount`**：详情页里它是**金额**，制作单里它是**用量**。
同一个名字，一个是钱一个是重量 —— **不会报错，只会算错**。

### 代价 2：一个页面干后端的活

```js
// diy-sheet/index.vue:1975
const actualAmount = theoreticalAmount * (1 + lossRate)
```

采购量在前端算。而且损耗率取的是**全局一个数**，
跟老板定的"不同食材损耗差很多"是矛盾的。

### 代价 3：每页各写一套样式

| 页面 | 总行 | template | **script** | style |
|---|---|---|---|---|
| 食谱详情页 | 2494 | 439 | **965** | 1080 |
| DIY 配置页 | 2092 | 271 | **908** | 907 |
| DIY 制作单 | 3367 | 526 | **1603** | 1232 |
| 交付第 1 页 | 515 | 136 | **118** | 255 |
| 交付第 2 页 | 549 | 156 | **187** | 200 |

**三个旧页合计 7953 行**，交付两页合计 1064 行。
样式部分：详情页 140 条规则、DIY 配置 123 条、DIY 制作单 170 条、合计 **433 条**，
其中大量重复（表格、卡片、按钮）。

**所以"改一个字段要改 3~5 处"不是感觉，是结构决定的。**

## 三、目标：三层结构

> 一句话：**页面只做编排，展示共用组件，计算全在后端。**

```
┌─ 页面层（薄）────────────────────────────┐
│  只负责：取数据 → 组装 → 编排组件顺序        │
│  目标：每页 script < 250 行                │
└───────────────┬──────────────────────────┘
                │
┌─ 展示层（共享组件）───────────────────────┐
│  · 食谱封面块（图 + 名 + 为谁 + 狗信息）     │
│  · 一句话块                                │
│  · 核心营养成分块（含标准背书 + 报告入口）     │
│  · 食材表块（名称 + 占比）                  │
│  · 营养素表块（名称 + 浓度）                 │
│  · 用量表块（名称 + 净用量）                 │
│  · 制作步骤块                              │
│  · 储存块                                  │
│  → 四个页面共用这一套，**一套样式**           │
└───────────────┬──────────────────────────┘
                │
┌─ 逻辑层（后端 + composables）──────────────┐
│  后端算：分组、占比、净用量、补剂量、饭量       │
│  composables：收藏 / 分享 / 评价 /          │
│               生命周期版本匹配               │
│  → 页面不再自己算、不再自己拼状态             │
└──────────────────────────────────────────┘
```

### 4.3 前端：抽共享组件

> **一条设计原则（2026-10-17 定）**：**参数越少，漏传的机会越少。**
>
> 所以表格不做"可配置列" —— 需要不同列的场景就做成**两个组件**，而不是一个组件加开关。

| 组件 | 列 | 用在哪 |
|---|---|---|
| `RecipeIngredientRatioTable` | 名称 + **占比** | 详情页 / 交付第 1 页 |

> **为什么不合成一个**：详情页是"看这是什么"（要占比）、
> 制作单是"动手做"（要净用量和制备方法）——
> 一个组件加两个开关，比两个组件更容易出错。

## 四之三、DIY 两页的四条修改（老板 2026-10-17 审原型后定）

| # | 改什么 | 说明 |
|---|---|---|
| 1 | **爱犬信息收成一行小字** | 年龄 / 性别 / 体重不再占三个格子（太占篇幅），改成选择器下方一行「3 岁 · 公 · 11.2kg」。**三个格子只留给每日餐次 / 每日饭量 / 每餐饭量** |
| 2 | **天数只展示 7 / 15 / 30** | ✅ **代码里已经是**（`ORDER_CYCLE_OPTIONS = [7, 15, 30]`），且 `recipe-diy` 与 `recipe-order` **共用同一个常量** —— 无需改动。我画原型时写成 7/14/21/30 是编的 |
| 3 | **制作单「制作清单」→「基础信息」** | 那块列的是狗 / 每天多少 / 做几天，本来就是基础信息 |
| 4 | **补剂表每行加购买入口** | 现在只有「名字旁边一个小徽章（进弹窗才有去购买）」+ 底部「一键买齐」。<br />**顾客不知道列表里就能买** → 每行直接给：**已选规格 / 换一个 / 去买** |

> **第 4 条的设计**：补剂有两种来源，两种入口都要有 ——
> · **每行的「去买」** = 买这一个（联盟商品跳转、或加入自产订单）
> · **底部「一键买齐自产补剂」** = 把自产的都加上
>
> 只有底部那个按钮时，顾客会以为"补剂得一起买，不能单独挑"。

## 五、生命阶段匹配：一个被漏掉的跨页共享模块

> 老板 2026-10-17 追问："食谱详情页，成品订购、DIY 制作、食谱定制相关的页面和板块，
> 是否都应该有生命阶段的匹配模块呢？如果都应该有的话，
> 那生命阶段的匹配模块，我们是否也不能跳过去呢？"

**他的判断是对的，而且这块比"字段重复"更容易出问题 —— 因为它是逻辑重复。**

### 5.1 哪些页面需要，哪些不需要

| 页面 | 需要匹配吗 | 为什么 |
|---|---|---|
| 食谱详情页 | ✅ **需要** | 顾客在这里看食谱，要告诉他"这个版本不适合你家狗" |
| 成品订购 | ✅ **需要** | 下单必须买对版本 |
| DIY 配置页 | ✅ **需要** | 顾客要基于适合的版本配置 |
| DIY 制作单 | ✅ **需要** | 制作单要显示正确的版本 |
| **定制页（下单）** | ❌ **不需要** | 定制是营养师**为这只狗做的**，天然匹配。<br />它只用生命阶段做**展示**（"生命阶段：成犬"），不做版本切换 |
| **交付两页** | ❌ **不需要** | 同上 —— 交付的就是这只狗的那一份 |

### 5.2 现状：四个页面各写一套

| 页面 | 自有 computed | 自有函数 |
|---|---|---|
| 食谱详情页 | 9 | 4 |
| 成品订购 | 5 | 5 |
| DIY 配置 | 4 | 3 |
| DIY 制作单 | 3 | 1 |
| **合计** | **21** | **13** |

### 5.3 但算法本身在后端，已经做好了

后端返回的 `RecipeLifeStageMatchDto`（`recipe-response.dto.ts:20`）已经包含：

```js
{
  dogLifeStage, dogLifeStageLabel,
  selectedLifeStage,
  matchType: 'MATCHED' | 'MANUAL_MISMATCH' | 'FALLBACK_ADULT' | 'FALLBACK_FIRST' | 'LEGACY',
  message,          // ← 现成的提示文案
}
```

前端 `isLifeStageMismatch` 也是**读后端**的，不是自己算：

```js
const matchType = recipe.value.lifeStageMatch?.matchType
return matchType === 'MANUAL_MISMATCH' || 'FALLBACK_ADULT' || 'FALLBACK_FIRST'
```

**所以重复的不是"算法"，是"把 `matchType` 翻译成界面"这件事 —— 四个页面各翻译了三到五遍。**

### 5.4 该怎么做

| 层 | 做什么 |
|---|---|
| **后端** | 已经够了。**保持 `matchType` + `message` 不变**（不要改成前端友好文案，让前端决定措辞） |
| **共享组件** | `LifeStageVersionCard` —— 吃 `{ match, versions, selectedId }`，渲染：版本名 + 提示语 + 切换入口 |
| **共享 composable** | `useLifeStageVersionSelection()` —— 处理"切换版本"的交互（打开选择器、选中、回写） |
| **各页面** | 只传数据、只听事件，**不再自己写 `isXxxMatched` 这类 computed** |

**这一块做完，四个页面合计能删掉约 20 个 computed。**

> ⚠️ 注意一个边界：`matchType` 有 5 种，但**界面表现不必有 5 种**。
> 建议归成 3 类：
> · `MATCHED` / `LEGACY` → 正常，不提示
> · `MANUAL_MISMATCH` → 提醒"你可能选错了版本"
> · `FALLBACK_ADULT` / `FALLBACK_FIRST` → 提醒"已自动换成适合的版本"
>
> 归类的判断放在**组件内部**，页面不管。

## 五之二、详情页的三条定论（老板 2026-10-17 拍板）

原型审完后定下的三条，直接影响共享组件的参数设计：

| # | 已定 | 影响 |
|---|---|---|
| 1 | **无封面时不用"食谱名首字母"**，用交付页那套（**深色块 + 完整文字**） | 详情页的 `cover-placeholder` 删掉，统一走共享组件的兜底 |
| 2 | **详情页封面只叠食谱名**；不显示"为谁定制"和狗信息。<br />卖点、价格提示、选狗器**留在封面下方**，位置不变 | `RecipeCover` 不做复杂参数 —— 就是"给几行文字"的数组：<br />详情页传 1 条，交付页传 3 条 |

### `OrderStatusBadge` 为什么建好了却没用

建它是因为"状态标签在三个地方都要出现"（详情头 / 列表徽章 / 售后页）。

但真要接的时候发现**列表接口没给这个能力**：

| 页面 | 状态文案从哪来 |
|---|---|
| 定制订单详情 | ✅ 后端 `renderable.status.label` |
| 定制订单列表 | ✅ 后端下发的选项字典（`useOptionSet`） |
| **三单合一列表**（`orders-list`） | ❌ **页面级业务映射** —— 含退款 / 超时关闭 / 补剂特例（`PACKING`/`PACKED`）<br />后端列表接口**只回状态码，不回 `renderable.status`** |

要接这个组件，得让**后端在合并列表接口里也返回 `renderable.status`** ——
那是后端改动，不是前端替换。**硬换会破坏现有的退款/超时/补剂特例。**

所以：**组件留着，等后端接口补齐再接。** 现在不动。

---

### composable：只完成 1/4，**原因写在这里**

`useLifeStageVersion` 只接了 **DIY 制作单** 一页。为什么没接完：

| 页面 | 数据来源 | 为什么不一致 |
|---|---|---|
| DIY 制作单 | 自己 `fetchLifeStageMatch` | ✅ 与 composable 形状一致 |
| 详情页 | 结论**内嵌在配方接口**（`recipe.lifeStageMatch`） | 不单独请求，塞进去要多一次请求 |
| DIY 配置页 | `isLifeStageMatch` 是**可变 ref**，值在别处赋 | 不是 computed，形状不同 |
| 成品订购页 | 自己 fetch，但**选狗变化时要重查** | 请求时机不同 |

> **界面已经统一了**（用户看到的四页一致），但**数据流的重复还在** ——
> 每页还有约 6 行相同的状态声明。
>
> 硬塞进一个 composable 要改三页的**请求时机**，那是真重构不是机械替换。
> **半途而废比不接更糟**，所以先接一页、把边界写清楚，留给下一次。

| 7 | **四个页面的 `<style>` 规则总数** | 433 → **一套共享组件内的规则** |
| 8 | **改一次"净用量"的字段名** | **只需改 1 个文件** |
| 9 | **四个页面的生命阶段 computed 总数** | 21 → **0**（全部走共享组件） |

**第 8 条是真正的验收** —— 它直接回答老板担心的那件事。
**做法**：随便挑一个字段（比如净用量），改它的名字，然后看要改几个地方。
**能只改 1 处，这次重构才算成功。**
