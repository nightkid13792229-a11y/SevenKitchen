## 三、四件没做的事 —— 每件都有原因，**别重新踩**

### ① 长图二维码的图片

**不是代码问题。** 小程序码是**微信后台下载的静态图片**，代码生不出来。

已按「**有素材就画、没素材就不画**」实现：

- 页面探测 `miniapp/src/static/delivery/miniapp-code.png`
- 读得到 → 画；读不到 → **整块不画**（不画占位方块）

**放好图片即生效，不用改代码。** 落地说明在同目录 `README-小程序码.md`。

### ② `OrderStatusBadge` 建好了但没接

**不是漏接，是接口没准备好。**

三单合一列表（`orders-list`）的状态文案来自**页面级业务映射**，
里面有真实业务分支：已退款 / 已超时关闭 / 补剂 `PACKING`·`PACKED` 特例。

后端合并列表接口**只回状态码，不回 `renderable.status`**。

→ 要接组件，得**先让后端在列表接口里也返回 `renderable.status`**。
硬换会破坏那三个分支。**别硬换。**

### ③ `usePackagePlan` / `useDogSelection` 没抽

- `packagePlan` 被 **8 个页面**引用
- 选狗逻辑被 **7 个页面**引用

这是**大重构**，不是小抽取。半途而废比不接更糟。

### ④ `useLifeStageVersion` 只接了 1/4 页

只有 **DIY 制作单** 接了。另外三页数据流**确实不同**：

| 页面 | 数据来源 |
|---|---|
| 详情页 | 结论**内嵌在配方接口**（`recipe.lifeStageMatch`），不单独请求 |
| DIY 配置页 | `isLifeStageMatch` 是**可变 ref**，值在别处赋 |
| 成品订购页 | 自己 fetch，但**选狗变化时要重查** |

**界面已经统一了**（用户看到的四页一致），只剩数据层的重复（每页约 6 行）。
