## 四、AI 独立复核结论（含纠正我的误判）

### 1. 最关键的发现：系统本身是"双口径"设计 —— A 类不能批量改

每个原料同时挂 **RAW（生）** 和 **COOKED（熟）** 两套营养档案，而且档案备注里**明确写了称量口径**，例如黑米：

| 档案 | 备注（生产库原文摘录） |
| --- | --- |
| 黑米（生/干） | 主档案；**食谱设计器按生重称量** |
| 黑米（熟/米饭） | 同源熟制档案；**食谱设计器按熟后重量称量** |

也就是说，系统的既有约定确实是"**熟档案 ↔ 按熟重称量**"，这支持"熟档案却写生重 = 文案错"的判断方向。

**但是**：文案里写的口径 ≠ 实际称量口径。复核实测有些食谱的文案同时出现「生重」和「煮熟后称重」，说明"称生重、用生数据"在部分食谱里可能是**有意为之**。因此：
- 若按熟重称量 → 应改文案；
- 若确实按生重称量 → 该改的是档案（回到"生"）。

**这两种情况在数据里长得一模一样**，所以 A1/A2 必须先由业务确认规则，**绝不能批量替换**，否则会把本来正确的食谱改坏。A4（跨食谱混用）只是同一根因的聚合表现，建议**按"原料"而不是按"条目"**出修复清单，并补一条"**同一食谱内同一原料口径唯一性**"校验。

### 2. 复核纠正的误报（我的判定偏重）

- **B1 机器码**：原判"前台显示乱码"**不准确**——接口会把字典 ID 解析成中文（实测 148 条中 147 条可确定性还原，仅 `76b12041…` 已查不到）。真实风险是**存储形式脆弱 + 掩盖了"整条食谱没有营养档案"**，已从「高」降为「中」。
- **B3 空文案**：一律判「高」偏重。补剂/油/粉无生熟概念、按剂量称取即可，已拆出 **B3b（低，215 项）**；只有真实食材（紫薯、金针菇、鳕鱼颈背肉等）才值「高」。
- **C1 系列（油/粉/补剂写"生重"）**：**不是营养口径冲突**（油和粉不因加热改变重量，按实际重量投料与档案口径本来就一致），已全部从「中」降为「低」，并按"可安全删除的冗余词"处理；同时修掉了 C1 与 C1c 对同一句文案**重复计数**的问题。
- **A2b**：含"焯水"又已写"生重"的条目（猪肝、鸡心）不构成矛盾，判定偏严，已保留但归入"待人工确认"。

### 3. 复核发现的漏报（已修正）

| 漏报 | 影响 | 修正 |

## 七、防复发（根因）

5. 增加校验：同一食谱内口径唯一性、状态枚举规范化、分类与原料类型一致性。

**`backend/scripts/audit-preparation-basis.ts`** —— 复用与线上完全相同的规则
（`src/domain/recipe-designer/preparation-basis.ts`），代码改规则时这里自动跟着变。

```bash
cd backend
# 1) 本地只读巡检生产（需要只读隧道）
npx ts-node -r tsconfig-paths/register scripts/audit-preparation-basis.ts \
  --env-file=.env.production.readonly --out=../docs/reports

# 2) 作为检查项：发现口径不一致时返回非 0 退出码
npm run audit:preparation-basis -- --fail-on-issues
```

生产实测结果（2026-09-15，正式食谱最新版 3,206 项 + 设计器草稿 5,673 项）：

| 问题类型 | 项次 |
| --- | --- |
| 文案为空 | 452 |
| 口径不一致 | 7（全部是红小豆） |
| 机器码残留 | 2 |

**安全提示**：当"按规则改"会丢掉加热步骤时（如红小豆「煮熟后称重」→「干重」），
脚本会在建议后追加 ⚠ 提醒，要求先确认营养档案是否选错，避免照着建议把必需步骤删掉。
单测 8 例（`tests/scripts/audit-preparation-basis.spec.ts`）。
