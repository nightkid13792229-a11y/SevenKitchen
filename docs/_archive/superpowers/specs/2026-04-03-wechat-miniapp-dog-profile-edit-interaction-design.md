# 微信小程序端狗狗档案编辑交互优化设计

## 背景

当前小程序中的狗狗档案编辑主要集中在一个页面内完成：

- 狗狗列表页 [miniapp/src/pages/dog-profile-list/index.vue](/Users/zhaochen/Documents/SevenKitchen/miniapp/src/pages/dog-profile-list/index.vue) 点击卡片后，直接进入 [miniapp/src/pages/dog-create/index.vue](/Users/zhaochen/Documents/SevenKitchen/miniapp/src/pages/dog-create/index.vue)
- `dog-create` 页面同时承担：
  - 首次建档
  - 已有档案编辑
  - 喂食建议试算
  - 健康记录录入
  - 过敏/挑食补充
- 页面底部主动作长期保持为“创建档案/保存档案”，用户需要自行理解哪些改动会影响喂食建议，哪些信息是必填，哪些信息可以稍后补充

后端接口能力本身并不弱，已经具备：

- `GET /dogs/{dog_id}` 获取完整档案
- `PUT /dogs/{dog_id}` 更新档案并重算
- `POST /dogs/calc-preview` 进行不落库试算

问题不在“缺接口”，而在于当前交互把多个不同任务混在一条大表单里，导致：

- 首次建档时心理负担过高
- 日常小改动也要重新进入完整表单
- 用户不容易理解“编辑”和“重新计算建议”的关系
- 健康记录等低频重输入信息打断主线
- 保存失败、退出中断、上传失败时缺少完成率保护机制

## 目标

1. 以“完成率”和“转化率”为最高优先级，优化狗狗档案编辑体验
2. 同时覆盖三条链路：
   - 首次建档
   - 日常编辑
   - 编辑后查看喂食建议并继续后续转化
3. 把“首次建档”和“日常编辑”从同一张大表单中拆分为不同交互心智
4. 让影响喂食建议的关键字段具备更即时、更明确的反馈
5. 让健康记录类信息退出主阻塞链路，变成增强项而不是门槛
6. 为后续验证优化效果，设计完整的指标采集与看板承接方案

## 非目标

- 本次不修改后端狗狗档案的核心领域模型
- 本次不新增后端“正式草稿状态”作为必需前提
- 本次不要求先改造食谱推荐或订单流程本身
- 本次不以视觉翻新为重点，界面风格调整只服务于信息负担管理和转化提升

## 北极星指标

本次优化以以下结果为成功标准：

1. 首次建档完成率提升
2. 日常编辑保存成功率提升
3. 编辑后查看最新喂食建议的比例提升
4. 编辑后继续进入推荐食谱或下单链路的比例提升
5. 因试算失败、上传失败、退出中断造成的流失下降

## 现状分析

### 1. 单页承载过多任务

当前 [miniapp/src/pages/dog-create/index.vue](/Users/zhaochen/Documents/SevenKitchen/miniapp/src/pages/dog-create/index.vue) 在一个页面中同时包含：

- 基础档案字段
- 喂养字段
- `calc-preview` 触发与展示
- 病史/体检/过敏记录弹窗
- 过敏食物与挑食食物补充

这导致用户在单次会话中同时承担“填写、理解、判断、计算、保存、补充”的认知负担。

### 2. 首次建档与日常编辑共享同一心智

当前列表页中的 `viewDog()` 直接导航到 `dog-create?dogId=...`，意味着：

- 新用户第一次建档要面对完整编辑器
- 老用户只是想修改体重，也要重新进入几乎同样的长表单

这不符合两个场景的任务特征。

### 3. 喂食建议是能力强、呈现弱

当前页面已经具备：

- `calcStaleNotice`
- `previewCalculation()`
- `POST /dogs/calc-preview`

但交互上仍然偏手动：

- 用户要自己意识到关键字段变化会影响建议
- 用户要主动点击“每日能量计算”
- 结果被嵌在长表单中，作为一块信息，而不是一个关键反馈节点

### 4. 健康记录价值高，但不该阻塞主线

病史、体检、过敏、挑食信息对长期精准推荐很重要，但在首次建档链路中，它们属于增强信息，不应该和“先完成档案、先拿到建议”拥有同级优先级。

### 5. 当前没有现成的用户行为分析栈

仓库现状显示：

- 小程序依赖中没有 PostHog、GA4、Mixpanel、Amplitude 等分析 SDK
- 后端也没有对应的行为事件采集模块
- 管理后台现有 [admin-web/src/views/Dashboard.vue](/Users/zhaochen/Documents/SevenKitchen/admin-web/src/views/Dashboard.vue) 主要是订单、收入、生产等运营数据，不是小程序档案漏斗看板

这意味着历史精细漏斗数据无法完整补回，未来指标需要从本次方案开始设计采集。

## 设计原则

1. 首次建档像引导，不像填表
2. 日常编辑像改设置，不像重新建档
3. 健康信息是增强项，不阻塞主链路
4. 每完成一小步就给用户即时回报
5. 尽量保住进度，不让用户担心“白填了”
6. 保存语义要清楚，避免“到底有没有正式生效”的困惑
7. 方案不仅要提升体验，还要能被数据验证

## 总体方案

采用“双模式编辑流 + 任务清单感”的方案：

- 对首次建档使用多步骤引导流
- 对已有档案编辑使用“总览页 + 局部编辑”模式
- 通过自动暂存、建议状态提示、可跳过健康补充、结果页转化引导，提升完成率与后续转化

整体结构分为三层：

1. 狗狗档案总览页
2. 首次建档四步流
3. 日常编辑局部修改页/面板

## 信息架构与页面流转

### 1. 狗狗档案总览页

已有档案的默认入口不再直接进入完整编辑页，而是先进入“档案总览页”。

页面职责：

- 展示狗狗档案摘要
- 展示当前喂食建议和建议新鲜度
- 展示待完善项和可编辑模块
- 承接后续转化动作

页面结构建议：

- 顶部：狗狗信息摘要卡
  - 姓名
  - 品种/混血名称
  - 年龄
  - 当前体重
  - 最近更新时间
- 中部：喂食建议卡
  - 每日主食热量
  - 零食模式摘要
  - “建议已更新 / 建议待更新”状态
- 下部：任务卡
  - 基础档案
  - 喂养信息
  - 健康记录
- 底部主动作
  - `更新喂食建议`
  - `去看推荐食谱`
  - `继续下单`

每张任务卡显示状态：

- `已完成`
- `建议更新`
- `待补充`

### 2. 首次建档四步流

新用户从“添加爱犬”进入时，不进入总览页，而进入首建引导流。

流程如下：

1. `基础档案`
   - 姓名
   - 性别
   - 品种/混血
   - 生日
2. `喂养信息`
   - 体重
   - BCS
   - 是否绝育
   - 活动量
   - 每日餐数
   - 零食模式
3. `喂食建议`
   - 自动试算
   - 展示结果
   - 支持返回修改关键字段
4. `健康补充`
   - 病史
   - 体检
   - 过敏
   - 挑食/过敏食物
   - 明确标注为可跳过

### 3. 日常编辑局部修改流

老用户从总览页进入编辑时，不再重新走完整四步，而是进入局部编辑。

典型入口：

- 修改基础信息
- 更新体重/活动量/BCS
- 调整零食设置
- 补充健康记录

典型局部编辑模块：

1. `基础信息编辑`
   - 姓名
   - 性别
   - 品种/混血
   - 生日
2. `喂养信息编辑`
   - 体重
   - BCS
   - 绝育状态
   - 活动量
   - 每日餐数
   - 零食模式
   - 最新试算结果
3. `健康记录编辑`
   - 病史记录
   - 体检记录
   - 过敏记录
   - 过敏/挑食文本补充

## 关键交互机制

### 1. 自动暂存 + 明确提交

采用“前端自动暂存 + 明确正式提交”的策略。

#### 首次建档

- 每完成一步，自动保存本地草稿
- 用户中断后再次进入，优先提示：
  - `继续上次填写`
  - `重新开始`
- 草稿恢复只针对当前用户、当前狗档案创建流程

#### 日常编辑

- 用户进入某个局部编辑模块后，字段变化先进入“已修改未提交”状态
- 页面提示：
  - `已暂存，还未正式更新档案`
- 只有点击模块主按钮后，才执行正式更新

这样既能保住进度，又不会让用户误以为每个输入都已经落到正式档案里。

### 2. 保存语义分层

不同阶段使用不同按钮语义：

- 在步骤推进页使用 `下一步`
- 在试算节点使用 `生成喂食建议` 或 `更新建议`
- 在局部编辑页使用 `保存本次修改`
- 在建档末尾使用 `完成建档`

避免所有场景都用“保存档案”这一种模糊文案。

### 3. 建议状态从手动感知改为系统感知

当前 `previewCalculation()` 能力保留，但交互从“用户主动去算”改为“系统感知建议是否过期”。

规则：

- 以下字段变化后，标记 `建议待更新`
  - 品种
  - 生日
  - 体重
  - BCS
  - 绝育状态
  - 活动量
  - 每日餐数
  - 零食模式
  - 手动零食热量
- 在用户停止输入一段短时间后，自动轻量试算
- 或在进入“喂食建议”步骤时自动触发试算

建议延迟：

- 数字输入类：600ms 到 1000ms 防抖
- 单选切换类：立即触发或短延迟触发

### 4. 健康记录退出主阻塞链路

首建流程中，健康记录统一放在最后一步，并清晰标记：

- `可跳过，稍后补充`

日常编辑中，健康记录作为独立任务卡存在，不与基础档案、喂养信息混排。

预期效果：

- 首次建档不会因低频重输入而中断
- 健康信息仍可在总览页持续被提醒和补充

### 5. 模块级完成感

每完成一个小模块，都需要向用户明确“你已经完成了这一块”。

表现方式：

- 基础档案完成后显示摘要卡
- 喂养信息完成后立即展示最新建议
- 健康补充完成后显示 `已补充 x 项`
- 总览页任务卡显示明确状态

### 6. 退出保护要温和

用户返回或离开时，不优先使用强拦截式弹窗，而优先提示：

- `本次修改已为你暂存，可稍后继续`

只有在用户主动选择清空草稿时，才展示不可恢复确认。

3. 任务区
   - 基础档案卡
   - 喂养信息卡
   - 健康记录卡
4. 转化动作区
   - `去看推荐食谱`
   - `继续下单`

#### 交互规则

- 如果建议过期，喂食建议卡高亮为 `建议待更新`
- 如果健康信息缺失，只显示 `待补充`，不显示错误态
- 修改成功后回到总览页，高亮最近修改的任务卡和最新建议

字段：

- 姓名
- 性别
- 品种搜索
- 混血/其他
- 生日

设计重点：

- 品种搜索是核心交互，常见品种优先显示
- 混血/其他使用底部弹层或轻弹窗，不打断主表单
- 混血体型要求必须明确，因为影响计算

主按钮：

- `下一步`

#### 步骤 2：喂养信息

字段：

- 体重
- BCS
- 是否绝育
- 活动量
- 每日餐数
- 零食模式

设计重点：

- 这是和喂食建议关系最强的一步
- 重点字段周围要有解释和反馈
- 允许在本步骤内先填完再试算，不要求每改一项都明确点击计算

主按钮：

- `生成喂食建议`

#### 步骤 3：喂食建议

内容：

- 每日主食热量
- 零食扣减说明

- 返回修改入口

设计重点：

- 从“嵌在表单中的一块结果”升级为完整结果页
- 让建议成为填写完成后的即时奖励
- 让用户理解结果为什么是这样，而不是只看到数字

主按钮：

- `按这个建议继续`

次按钮：

- `返回修改喂养信息`

#### 步骤 4：健康补充

内容：

- 病史
- 体检
- 过敏
- 过敏食物与挑食食物

设计重点：

- 每个模块都做成独立卡片入口，不在同一屏展开全部输入框
- 明确提示“可跳过，稍后从档案页继续补充”

主按钮：

- `完成建档`

次按钮：

- `先跳过`

#### 基础信息编辑

适合独立子页，避免频繁切入切出时状态丢失。

## 异常处理与完成率保护

### 1. 试算失败

试算失败时：

- 不阻塞档案继续保存
- 页面展示：
  - `建议暂时未更新`
  - `档案仍可先保存`
  - `稍后可重新计算`

禁止因为 `calc-preview` 失败而让用户无法完成建档或保存编辑。

### 2. 保存失败

正式保存失败时，必须明确区分：

- 本地草稿已保留
- 正式档案未更新
- 可以重试

提示示例：

- `保存未成功，但本次填写已为你保留，可稍后继续或立即重试`

### 3. 页面加载失败

优先级：

1. 使用本地缓存展示最近可用摘要
2. 尝试恢复本地草稿
3. 只有完全无可用数据时才进入完整错误态

### 4. 健康记录上传失败

规则：

- 附件上传失败时，允许先保存文字记录
- 单条健康记录提交失败时，不影响基础档案和喂养信息保存
- 失败记录标记为 `待重试`

### 5. 草稿恢复

首次建档恢复入口：

- `继续上次填写`
- `重新开始`

日常编辑恢复入口：

- `恢复上次未提交修改`
- `丢弃并重新编辑`

### 6. 离开确认

只有以下情况才强提醒：

- 用户当前存在尚未正式提交的重要改动
- 且当前步骤尚未被本地暂存成功

其他情况统一用轻提示替代拦截弹窗。

## 指标设计

### 1. 历史指标数据现状

当前项目中没有现成的小程序行为埋点体系，因此：

- 精细历史漏斗数据无法完整查看
- 只能从业务结果和接口日志中做有限反推

目前可勉强观察的历史数据来源：

1. 数据库结果数据
   - 新增狗档案数量
   - 建档后是否产生订单
   - 不同狗档案与订单的关联情况
2. 后端接口日志
   - `/dogs`
   - `/dogs/{id}`
   - `/dogs/calc-preview`
   - `POST /dogs`
   - `PUT /dogs/{id}`

这类数据可以用于粗粒度回看，但无法还原真实前端漏斗。

需要同时观察副作用：

### 4. 数据承接与看板方案

#### 推荐承接方案

推荐采用“自有后台分析页”为主承接方式。

原因：

- 当前项目没有现成第三方分析基础设施
- 自有后台可以直接联动业务结果，例如订单与狗档案
- 团队后续查看路径更统一

#### 数据流建议

1. 小程序触发埋点事件
2. 后端新增行为事件接收接口或复用统一事件采集接口
3. 事件落入行为事件表，例如：
   - `miniapp_event`
   - 或 `dog_profile_funnel_event`
4. 后端按天或按时间窗口聚合
5. 管理后台新增“狗档案转化分析”页面

#### 管理后台新增看板建议

在 `admin-web` 中新增分析页，推荐命名：

- `Dog Profile Analytics`
- 或 `狗档案转化分析`

看板内容：

1. 首次建档漏斗
2. 日常编辑漏斗
3. 编辑后转化漏斗
4. 试算成功率趋势
5. 保存失败率趋势
6. 健康补充跳过率趋势
7. 草稿恢复使用率

#### 第三方平台作为可选加速方案

如果需要更快上线验证，也可先接入第三方产品分析平台，例如 PostHog。

适用场景：

- 希望快速查看漏斗和路径
- 暂时不想先建设后台行为看板

但长期仍建议将核心指标沉淀到自有后台中，避免业务关键数据完全依赖外部平台。

## 分阶段落地建议

### Phase 1：结构拆分

- 新增档案总览页
- 首次建档改为四步流
- 已有档案从总览页进入

### Phase 2：交互保护

- 增加本地草稿与恢复
- 增加建议新鲜度状态
- 增加自动试算
- 优化保存与离开提示

### Phase 3：数据验证

- 增加行为事件采集
- 后端聚合指标
- 管理后台分析页

这样可以先提升体验主链路，再补齐验证闭环。

## 验收标准

如果方案实施成功，应能满足以下验收结果：

1. 新用户首次建档时，不再直接面对完整大表单
2. 已有档案用户可从总览页进入局部编辑，而非每次重走完整建档页
3. 修改关键字段后，系统能明确标记并更新喂食建议状态
4. 健康记录可跳过，不阻塞建档完成
5. 中断后可以恢复草稿
6. 试算失败和附件上传失败不会阻塞主链路完成
7. 上线后能在分析看板中查看建档与编辑核心漏斗数据

## 最终结论

这次优化不应被定义为“把现有表单做得更整齐”，而应被定义为：

- 将首次建档改造成更容易完成的引导流
- 将日常编辑改造成更低成本的局部修改体验
- 将喂食建议从附属信息升级为关键反馈节点
- 将健康记录从阻塞项改造成增强项
- 将体验优化和指标验证闭环同时纳入设计

最终目标不是页面更漂亮，而是让用户更容易完成建档、更愿意更新档案，并在完成后更自然地进入推荐食谱和下单转化链路。
