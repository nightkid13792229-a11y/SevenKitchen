# 食谱原料制备方法录入优化设计

## 背景

当前食谱编辑页中的原料制备方法，仍然依赖一套全局“制备方法标签库”：

- Web 管理后台在食谱编辑页的“新增原料/编辑原料”弹窗中，通过点击标签的方式选择制备方法
- 前端保存到 `RecipeItem.preparationMethod` 的并不是可直接阅读的文案，而是逗号分隔的标签 ID
- 后端和下游链路需要再把这些 ID 翻译回中文文案，才能在食谱详情、DIY 制作单、采购清单、生产打印中展示

这套设计带来了三个明显问题：

1. 录入效率低。编辑者需要在标签池里找词，无法直接输入完整操作说明。
2. 数据语义绕。字段名叫“制备方法”，实际存的却是“标签 ID 串”，各端都要额外做翻译兼容。
3. 历史复用弱。当前没有围绕“标准原料曾经用过什么制备方法”建立快捷录入能力。

本次目标是围绕“提高原料制备方法录入效率”做一次兼容式重构，并确保小程序端、采购/生产链路和后端输出一起收口为可直接阅读的文案。

## 目标

1. 在 Web 管理后台的食谱编辑页中，把原料制备方法从“点击标签选择”改为“直接输入文案”。
2. 在“新增原料”弹窗中，当选择某个标准原料后，支持快速选择该标准原料历史上用过的制备方法。
3. 点击历史制备方法时，默认追加到当前输入内容，而不是覆盖已有内容。
4. 后端统一兼容旧数据与新数据，保证食谱详情、DIY 制作单、采购清单、生产打印继续输出可直接阅读的文案。
5. 不把用户个性化定制食谱混入“标准原料历史制备方法”的推荐来源。

## 非目标

1. 不改动订单页中独立存在的“打碎/切丁”这类下单选项枚举，它属于另一条业务链路。
2. 不要求一次性批量迁移所有历史食谱数据；允许通过兼容读取和后续自然保存逐步转新。
3. 不在本次范围内新建一套永久维护的“原料历史制备方法表”。
4. 不在本次范围内重做小程序端交互；小程序端以继续正确展示为主。

## 现状分析

### 1. Web 管理后台当前实现

`admin-web/src/views/Recipes/RecipeForm.vue` 当前存在以下实现特征：

- 原料弹窗中的 `ingredientForm.preparationMethods` 是字符串数组，但数组元素实际是 `PreparationMethod.id`
- 弹窗 UI 通过标签多选和拖拽排序来维护制备方法
- 保存时把这些 ID 用 `, ` 拼成字符串后写入 `RecipeItem.preparationMethod`
- 编辑已存在原料时，再通过 `split(', ')` 把字符串拆回 ID 数组
- 表格展示阶段再根据全局标签表把 ID 转成人类可读名称

这意味着后台编辑主流程当前强依赖全局标签表与“ID 串”存储格式。

### 2. 后端当前实现

`backend/prisma/schema.prisma` 中：

- `RecipeItem.preparationMethod` 是 `String?`，没有固定枚举约束
- `PreparationMethod` 仍是一张独立的标签库表

实际运行逻辑存在两套语义并存：

- 老数据/现行后台录入：`RecipeItem.preparationMethod` 存的是逗号分隔 UUID
- 部分新链路或兼容逻辑：已经允许把它当文案处理

现有兼容点包括：

- `recipes.controller.ts` 会把公开食谱详情里的 UUID 串翻译成中文文案
- `order.service.ts` 和 `purchasing.service.ts` 已经包含“若是 UUID 则翻译，若是普通文本则直接使用”的兼容思路
- 但管理后台的食谱详情接口仍然直接回传原始字符串，导致编辑页会看到旧格式 ID

### 3. 小程序与采购/打印链路

小程序食谱详情、DIY 制作单、采购预览、生产打印等展示链路，本质上都只需要“最终可读文案”：

- 小程序并不依赖标签管理能力
- 采购预览与生产打印更关心读者能否直接看懂如何预处理原料
- 因此，真正需要收口的是后端输出语义，而不是在小程序端继续识别旧编码

## 方案对比

### 方案 A：仅改 Web 交互，底层继续存标签 ID

做法：

- Web 弹窗支持手动输入
- 输入时仍然强制映射或回写到标签库 ID

优点：

- 变动较小

缺点：

- 仍然依赖标签表作为食谱编辑主数据源
- 文案自由度受限
- 后端和小程序仍需长期维护“ID 转文案”逻辑

### 方案 B：`RecipeItem.preparationMethod` 直接存文案，历史推荐从标准食谱反查

做法：

- Web 弹窗直接编辑文本
- 选中标准原料后，从该原料在历史标准食谱中的制备方法文案中生成快捷推荐
- 后端统一兼容旧 UUID 串和新文案

优点：

- 最贴合“提高录入效率”的核心目标
- 数据语义和字段名重新一致
- 下游链路可统一消费可读文案

缺点：

- 需要补一层兼容翻译与历史聚合逻辑

### 方案 C：在方案 B 基础上新增独立“原料历史制备方法库”

做法：

- 单独维护一张表或聚合缓存表，保存原料与历史制备方法关系

优点：

- 后续可做更复杂的推荐、频次统计与治理

缺点：

- 本次改造范围明显扩大
- 对“先把录入效率提上来”的目标来说过重

### 结论

采用方案 B：

- `RecipeItem.preparationMethod` 以“可直接阅读的文案”作为新的事实来源
- 历史推荐按标准原料从既有标准食谱中反查
- 旧标签表和相关接口暂时保留，只作为历史 UUID 翻译层，不再作为食谱编辑主流程依赖

## 总体设计

### 1. 数据语义重定义

从本次改造开始，`RecipeItem.preparationMethod` 的业务语义定义为：

- 存储食谱原料的可直接阅读制备方法文案
- 允许为空
- 不再要求为标签 ID

兼容原则：

- 如果字段值看起来是旧的 UUID 串，则后端读取时自动翻译为文案
- 如果字段值本身已是普通文案，则原样使用
- 管理后台重新编辑并保存旧食谱后，该字段自然转成新文案格式

本次不做数据库结构迁移，原因如下：

- `RecipeItem.preparationMethod` 目前就是 `String?`
- 当前问题是“值的语义”，不是“字段类型”
- 兼容式切换可以显著降低上线风险

### 2. Web 管理后台交互重构

食谱编辑页中的“新增原料”和“编辑原料”弹窗统一改为同一套录入方式。

#### 2.1 输入控件

- 原“点击标签多选”区域改为可直接输入的文案输入框
- 输入框使用多行文本输入组件，便于录入较完整的制备描述
- 保存时仅做基础清理：
  - 去掉首尾空白
  - 空字符串保存为 `undefined`
- 不对用户输入内容做激进改写，避免把完整操作说明误拆成标签列表

#### 2.2 历史制备方法快捷选择

当用户在“新增原料”或“编辑原料”弹窗中选择某个标准原料后：

- 页面异步加载该标准原料的历史制备方法
- 在输入框下方以快捷项形式展示
- 如果没有历史记录，则展示“暂无历史制备方法”

#### 2.3 点击历史项的追加规则

- 若当前输入框为空，则点击后直接填入该历史文案
- 若当前输入框已有内容，则默认以 `、` 为分隔符把历史文案追加到末尾
- 如果当前输入中已经包含该历史项完整文本，则不重复追加
- 追加后用户仍可自由手动修改

示例：

- 当前为空，点击 `去皮` -> `去皮`
- 当前为 `去皮`，点击 `蒸熟` -> `去皮、蒸熟`
- 当前为 `去皮、蒸熟`，再次点击 `蒸熟` -> 保持不变

#### 2.4 旧入口退场

以下内容从食谱编辑主流程中移除：

- 全局制备方法标签选择器
- “管理制备方法”按钮
- 依赖标签拖拽排序的交互

保留策略：

- 后端 `PreparationMethod` 表和现有接口暂不删除
- 仅作为旧数据翻译层保留
- 后续待历史数据基本完成自然转新后，再评估是否彻底下线

### 3. 后端统一兼容层

后端新增一层制备方法文本解析与输出规范，统一服务于：

- 管理后台食谱详情/保存
- 公开食谱详情
- 下单快照与价格预览
- 采购清单聚合
- 生产打印与小程序相关输出

#### 3.1 统一解析规则

定义统一 helper，行为如下：

1. 输入为空时，返回空
2. 若输入是逗号分隔的 UUID 串：
   - 查询 `PreparationMethod` 表
   - 按原顺序翻译为名称
   - 拼接为可读文案
3. 若输入不是 UUID 串：
   - 视为新格式文案
   - 返回原文案的清理版

推荐提供两个能力：

- `resolvePreparationMethodText(value)`：返回单个可读文案字符串
- `resolvePreparationMethodTokens(value)`：在采购/打印等需要数组展示时返回可读词组数组

#### 3.2 管理后台食谱详情接口

管理后台食谱详情接口返回的 `RecipeItem.preparationMethod` 必须改为“可直接展示和可直接编辑的文案”，不再返回旧 UUID 串。

这样可以确保：

- 打开旧食谱时，编辑弹窗里看到的是中文文案
- 编辑者不需要理解历史编码

#### 3.3 保存接口

管理后台保存食谱时：

- 接收前端传入的文本型 `preparationMethod`
- 直接保存到 `RecipeItem.preparationMethod`
- 不再查询或回写标签表

### 4. 历史制备方法查询能力

为支持“按标准原料快速选择历史制备方法”，后端新增一个管理后台接口：

- `GET /api/v1/admin/ingredients/:ingredientId/preparation-method-history`

返回结构建议为：

```json
[
  {
    "text": "去皮、蒸熟",
    "usageCount": 6,
    "lastUsedAt": "2026-04-10T12:00:00.000Z"
  }
]
```

#### 4.1 数据来源

仅统计“标准食谱”中的同标准原料历史记录：

- `recipe_item.ingredient_id = :ingredientId`
- `recipe.is_custom_recipe = false`

不纳入：

- 用户个性化定制食谱
- 订单快照
- 采购记录中的二次加工文本

#### 4.2 聚合规则

历史推荐使用“清洗后的文案文本”进行去重聚合：

- 先通过统一兼容 helper 把旧 UUID 串转换为文案
- 去掉首尾空白
- 把连续空白压缩为单个空格
- 把列表类分隔符的明显格式差异做最小统一：
  - `,`、`，` 统一为 `、`
  - `、` 两侧空白去掉
- 不重写词序，不拆散完整句子

聚合结果按以下优先级排序：

1. 最近使用时间降序
2. 使用次数降序
3. 文案字典序升序

#### 4.3 缓存策略

本次先不引入独立缓存表。

原因：

- 这是后台编辑链路的辅助查询，压力可控
- 先用实时查询验证交互价值
- 若后续使用频繁，再考虑在服务层增加缓存

### 5. 小程序、采购、打印链路调整

#### 5.1 小程序

小程序端不新增交互改造，重点是继续正确显示可读文案：

- 食谱详情页继续展示 `preparationMethod`
- DIY 制作单继续展示 `preparationMethod`
- 若后端已统一输出可读文本，小程序侧理论上只需保持现有展示逻辑

#### 5.2 采购与生产链路

采购清单、采购预览、生产打印等链路中，如果需要拆成数组展示：

- 一律基于“已解析为可读文本”的结果再做拆分
- 不能再默认认为 `RecipeItem.preparationMethod` 中一定是 UUID 串

目标效果：

- 采购预览看到的是 `去皮、蒸熟`
- 生产打印看到的是 `去皮、蒸熟`
- 不再出现 UUID 串或因为无法识别旧格式而空白

### 6. 与旧标签表的关系

`PreparationMethod` 表从“食谱编辑主流程的主数据源”降级为“历史翻译依赖”：

- 管理后台食谱编辑页不再依赖该表驱动选择器
- 历史食谱读取时，若识别到旧 UUID 串，仍通过该表翻译
- 现有增删改查接口暂时保留，但不再从食谱编辑页入口暴露

后续观察期结束后，再决定：

- 是否彻底下线该管理入口
- 是否迁移或清理长期未使用的旧标签数据

## 影响范围

### Web 管理后台

- `admin-web/src/views/Recipes/RecipeForm.vue`
- 可能新增专用 API 文件，例如原料历史制备方法查询接口
- 相关类型定义从“ID 数组/ID 串”收口为“文本”

### 后端

- 食谱详情/保存相关 DTO、Service、Controller
- 新增历史制备方法查询接口
- 公共制备方法解析 helper
- 采购、订单、公开食谱详情等依赖 `preparationMethod` 的服务

### 小程序

- 主要为回归验证
- 若接口输出字段保持不变且语义更稳定，原则上无需新增交互改造

## 风险与应对

### 风险 1：历史数据混杂

可能同时存在：

- UUID 串
- 中文短语
- 中文完整句子
- 不同分隔符写法

应对：

- 统一通过兼容 helper 先解析为可读文本
- 历史推荐接口只输出清洗后的文本

### 风险 2：某些下游链路仍默认字段一定是 UUID 串

应对：

- 全量排查 `preparationMethod` 的解析点
- 统一改成“先识别并解析，再使用”

### 风险 3：历史推荐出现重复或噪声文案

应对：

- 历史推荐只来自标准食谱
- 做最小必要的清洗、去重和排序
- UI 层保留自由输入，不强迫使用推荐项

## 上线策略

采用兼容式切换，顺序如下：

1. 后端先支持同时识别旧 UUID 串和新文案
2. 后端补齐历史制备方法接口
3. Web 管理后台切换为文案输入 + 历史快捷选择
4. 回归验证小程序、采购、打印等链路

这样可以保证：

- 库里即使还存在旧数据，也不会影响前台展示
- 后台切换后，新编辑内容立即按新语义存储
- 无需一次性做高风险数据迁移

## 验证要求

### 1. Web 管理后台

- 新增原料时可直接输入制备方法文案
- 选择标准原料后能拉取历史制备方法
- 点击历史项按 `、` 追加
- 重复点击同一历史项不会重复追加
- 编辑旧食谱时能看到中文文案而非 UUID

### 2. 后端

- 新格式文案可直存直出
- 旧 UUID 串可正确翻译
- 历史制备方法接口能正确聚合、去重、排序

### 3. 小程序与生产链路

- 食谱详情展示正确
- DIY 制作单展示正确
- 采购预览展示正确
- 生产打印展示正确

## 决策摘要

本次改造的最终决策为：

- 食谱原料制备方法改为直接保存人类可读文案
- 原料弹窗改为自由输入文案
- 选择标准原料后按原料提供历史制备方法快捷项
- 点击历史项默认追加，不覆盖
- 历史推荐只来自标准食谱，不混入个性化定制食谱
- 旧标签表仅保留为历史 UUID 翻译层，不再作为食谱编辑主流程依赖
