# 订单、采购、生产、库存全链路优化设计

## 背景

本轮希望以微信小程序的顾客订购交互为起点，从头到尾梳理标准成品鲜食订单链路：

```text
顾客订购成品 -> 订单计价与付款 -> 采购缺口与报销 -> 生产执行 -> 库存与成本结算 -> 发货完成
```

现有系统已经具备订单、采购、生产、库存、财务等模块，但业务规则仍有几处需要重新收束：

- 顾客订购页的信息过于技术化，饭量、原料、价格、分装之间的关系不够清楚。
- 订单原价、实际付款、补差价、退款、退差价需要分开记账。
- 采购缺口、日采类原料、可入库原料、常规库存之间需要更明确的判断规则。
- 生产端不能要求员工逐项记录每个原料实际用了多少，记录成本过高。
- 库存成本需要区分“当前批次成本”和“未来可用库存资产”。

## 目标

1. 顾客端能清楚理解购买方案、饭量参考、原料方案、分装规格和价格变化。
2. 管理端能看到订单原价、调价记录、付款记录、退款/补差价、实际收入和毛利。
3. 采购端能根据订单需求和库存可用量生成采购缺口，避免重复采购。
4. 生产端用尽量少的录入动作完成生产结果记录。
5. 库存端能区分可入库与不可入库原料，并正确影响后续采购缺口和成本。
6. 第一版优先打通标准成品鲜食正向链路，避免把特殊定制和售后复杂度提前混入主流程。

## 非目标

- 不在本轮设计自定义食谱、DIY 制作单或用户自配原料链路。
- 不把售后、退款、退差价作为订单主状态的一部分；它们通过结算记录表达。
- 不把管理员备注作为特殊加料或特殊包材入口。
- 不在第一版支持特殊加料订单与普通订单混合生产。
- 不要求员工逐项记录每一种原料的实际用量。
- 不要求员工录入自由文本异常说明。
- 不在订购页新增“快速调整饭量”功能；体重管理和 BCS 调整仍归属狗狗档案。

## 核心业务结论

### 1. 订单状态

内部订单状态沿用以下主链路：

```text
INIT -> PENDING_PAYMENT -> PAID -> PURCHASING -> IN_PRODUCTION -> FREEZING -> SHIPPED -> COMPLETED
```

顾客端不展示 `INIT`。`INIT` 只作为内部临时状态或订单创建过程状态，顾客能看到的状态从 `PENDING_PAYMENT` 开始。

顾客端文案建议：

```text
待付款 -> 已付款/待采购 -> 采购中 -> 生产中 -> 急冻中 -> 已发货 -> 已完成
```

订单草稿不作为顾客端可见状态。顾客在订购页编辑方案时，不需要先生成一个对顾客可见的草稿订单；只有顾客确认下单后，才进入待付款链路。

### 2. 订单价格与结算

订单创建时生成一份不可变的原始价格快照，保存当时的产品价格、采购方案、分装方案、包材、配送费、优惠和总价。

管理员可以多次修改付款价格。原因包括：

- 退款
- 退差价
- 补收差价
- 人工优惠
- 采购或生产后的人工结算修正

这些变化不得覆盖原始价格快照，而是通过独立的结算调整记录表达。

建议账务视图至少展示：

- 系统原始订单金额
- 累计调增金额
- 累计调减金额
- 实收金额
- 已退款金额
- 待补差价金额
- 净收入
- 预计成本
- 实际成本
- 预计毛利
- 实际毛利

补收差价不阻止采购、生产、急冻或发货。顾客端可以轻量展示“待补差价”，但不能把它设计成阻塞发货的硬状态。

### 3. 采购与报销

生产解锁条件是：

```text
采购完成 + 库存可用
```

不是：

```text
采购报销已审批
```

采购报销控制的是成本确认、财务付款、凭证和异常追踪，不阻断生产与发货。

采购任务生成时应先得到完整订单需求，再检查库存：

```text
订单需求 -> 库存可用量 -> 库存预占 -> 采购缺口 -> 采购清单
```

库存数量需要区分：

- 在库量
- 已预占量
- 可用量

生成采购清单时，对会使用库存的原料先做预占。订单取消或采购清单删除时释放预占。

### 4. 原料采购与库存分类

原料在采购和库存层面分三类：

#### 日采不入库

典型对象：

- 大多数蔬菜
- 大多数水果
- 无法稳定保存的鲜食材

规则：

- 可以生成采购缺口。
- 不纳入长期库存。
- 多买的部分不进入库存。
- 多买或剩余无法保存的部分计入当前批次损耗或成本。
- 后续订单采购缺口不使用这类剩余量抵扣。

#### 日采可入库

典型对象：

- 可冷冻保存的鲜肉
- 可稳定保存的部分鲜食原料

规则：

- 采购前检查现有库存。
- 采购缺口按可用库存抵扣后生成。
- 生产完成后，如有可保存剩余，按实际入库成本进入库存资产。
- 未来生产使用这部分库存时，再把对应入库成本计入未来批次成本。

#### 常规库存

典型对象：

- 补剂
- 包材
- 标签
- 长期保存的耗材

规则：

- 长期维护库存。
- 支持安全库存和补货提醒。
- 采购缺口优先由可用库存抵扣。
- 使用时按库存成本进入当前批次成本。

## 顾客订购页设计

### 1. 饭量计算展示

订购页应展示更通俗的饭量计算过程，例如：

```text
根据狗狗体重、年龄、绝育情况、活动水平、BCS 体态评分，系统估算每日热量需求。
再根据当前食谱的热量密度，换算为建议每日鲜食克数。
```

这里展示的是解释和参考，不是强制购买量。

订购页不新增快速调整饭量功能。减重、增重、BCS 修正、体重管理仍在狗狗档案和体重管理模块里完成，避免顾客在两个入口重复调整同一件事。

### 2. 原料采购方案

订购页提供三档原料采购方案：

```text
尽量有机来源
尽量山姆、盒马、沃集鲜
生鲜批发商
```

默认选择：

```text
尽量山姆、盒马、沃集鲜
```

采购方案会直接影响订单售价。原因是不同方案会匹配不同采购 SKU、不同来源、不同采购成本和可能不同的原料替代策略。

顾客端应把它表述为“预计原料来源方案”，不能承诺每一种原料最终一定来自某个渠道。实际采购时仍可能因为品质、缺货、价格异常进行同档或合理替代。

原料清单建议展示：

- 原料名称
- 原料用途或类别
- 本次预计用量
- 预计来源或渠道
- 采购方案说明

### 3. 产品介绍

订购页需要新增图片形式的产品介绍板块，建议覆盖：

- 产品特点
- 食材与采购原则
- 制作流程
- 分装与标签
- 急冻与冷链
- 储存与喂食方式

该板块用于建立顾客信任，不参与订单计算。

### 4. 底部固定价格栏

页面底部固定展示：

- 总金额
- 参考每日价格或每餐价格
- 立即下单按钮

价格需要随着以下项目实时变化：

- 原料采购方案
- 分装明细
- 总订购克数
- 袋数和包材
- 配送费
- 优惠或活动

## 自定义分装设计

### 1. 基本规则

订单总量不再由系统推荐周期锁死。

最终订单总量由顾客确认的分装明细汇总得到：

```text
订单总量 = Σ(每袋克数 × 袋数)
```

唯一硬约束：

```text
订单总量 >= 1kg
```

如果低于 1kg，不允许下单，并提示：

```text
本产品 1kg 起订，可增加袋数或选择更长周期。
```

### 2. 默认分装周期

订购页提供三档默认分装周期：

```text
7天
15天
30天
```

默认选中：

```text
15天
```

系统根据狗狗建议每日饭量和周期生成默认分装明细。例如建议每日 300g 时：

```text
7天  -> 约 2,100g
15天 -> 约 4,500g
30天 -> 约 9,000g
```

默认周期只是快速起点。顾客选择周期后，系统自动生成分装明细；顾客仍可继续新增、删除或修改规格。

### 3. 自定义分装明细

分装明细由多行组成：

```text
100g × 10袋
150g × 20袋
200g × 5袋
```

系统实时汇总：

- 订单总克数
- 总袋数
- 预计可吃天数
- 包材成本
- 订单总价
- 参考每日价格或每餐价格

订单快照必须保存完整分装清单，不能只保存一个 `packageSpecG` 和一个 `packageCount`。

建议快照结构语义为：

```json
[
  { "packageSpecG": 100, "packageCount": 10 },
  { "packageSpecG": 150, "packageCount": 20 },
  { "packageSpecG": 200, "packageCount": 5 }
]
```

### 4. 对生产的影响

自定义分装不等于特殊加料，也不等于特殊包材。

同一食谱、同一基础生产快照的订单，即使分装规格不同，也仍然可以合并烹饪。差异只在分装阶段体现：

```text
同一批次烹饪 -> 按订单分装 -> 按分装明细打印标签/扣减包材
```

未来如果要支持特殊加料或特殊包材，必须设计独立标准入口，并把这类订单拆成独立生产任务；不能通过管理员备注推断。

## 生产执行与成本结算

### 1. 生产任务合并

第一版只考虑标准成品鲜食订单。

可以合并生产的前提：

- 食谱一致
- 食谱快照一致
- 采购/生产口径一致
- 没有特殊加料
- 没有特殊包材

分装规格不同不阻止合并烹饪。

### 2. 员工记录方式

生产端不要求员工逐项记录每一种原料实际用了多少。

员工按照生产制作单完成制作和分装后，只记录生产结果：

- 正常完成
- 成品余量克数
- 成品缺口克数
- 可选照片凭证

不要求员工输入自由文本异常说明。

### 3. 实际出成与损耗

系统用“成品余量/缺口”反向评估食谱预设损耗率是否合理：

```text
理论成品量 - 实际可分装成品量 = 实际缺口
实际可分装成品量 - 理论成品量 = 实际余量
```

如果经常出现缺口，说明食谱预留生产损耗率可能偏低。

如果经常出现明显余量，说明食谱预留生产损耗率可能偏高，或者生产执行存在稳定差异。

成品缺口可用于：

- 支持退款或退差价计算
- 计入当前批次生产损耗
- 帮助后续调整食谱损耗率

不再单独统计每个订单的袋数和克数完成情况。系统已经知道订单预期分装明细；生产端只需要记录批次整体余量或缺口。

## 库存成本规则

库存用料按库存入库成本计入当前批次成本。

含义是：

```text
如果上次多买的牛肉有 300g 按 30 元入库，
未来某个批次使用了这 300g，
这 30 元就计入未来那个批次的实际成本。
```

成本归属规则：

- 日采不入库原料：多买和不可保存剩余计入当前批次成本或损耗。
- 日采可入库原料：当前批次实际使用部分计入当前成本，可保存剩余转为库存资产。
- 常规库存原料：使用多少，按库存成本计入当前批次。

这样可以避免把未来还能使用的库存提前算进当前订单成本，导致当前批次毛利被低估。

## 数据模型影响

### 1. 订单

订单需要保留：

- 原始价格快照
- 当前应付金额
- 实收金额
- 结算调整汇总
- 采购方案快照
- 原料清单快照
- 分装明细快照
- 生产与发货状态

### 2. 订单项

现有订单项若只支持单一 `packageSpecG` 和 `packageCount`，需要扩展为支持多行分装明细。

建议保留旧字段用于兼容展示或迁移，但新逻辑以 `packagePlan` 为准。

### 3. 结算调整记录

需要独立记录每一次金额变化：

- 调整类型
- 调整金额
- 调整原因
- 创建人
- 创建时间
- 是否需要顾客补付
- 是否已退款或已补收

### 4. 采购需求

采购需求应基于订单快照计算，而不是读取会变化的食谱实时数据。

采购需求需要记录：

- 来源订单或生产批次
- 标准原料
- 采购 SKU
- 采购方案
- 需求量
- 库存抵扣量
- 采购缺口量
- 是否可入库
- 是否需要预占库存

### 5. 生产批次

生产批次需要记录：

- 合并的订单列表
- 食谱快照
- 理论生产总量
- 预计分装总量
- 实际成品余量
- 实际成品缺口
- 包材需求
- 实际成本
- 生产完成时间

### 6. 库存流水

库存流水需要能表达：

- 采购入库
- 生产领用
- 生产剩余入库
- 预占
- 释放预占
- 损耗出库
- 盘点调整

## 端到端主流程

```text
1. 顾客进入成品订购页
2. 系统读取狗狗档案并展示建议每日饭量
3. 顾客选择原料采购方案
4. 顾客选择 7天/15天/30天默认周期，或自定义分装明细
5. 系统汇总订单总量，校验是否 >= 1kg
6. 系统实时计算总价、参考每日价、包材成本和预计可吃天数
7. 顾客确认下单，订单进入待付款
8. 顾客付款，订单进入已付款/待采购
9. 系统根据订单快照生成生产需求和采购缺口
10. 系统检查库存、预占可用库存、生成采购清单
11. 采购完成后，库存可用，生产任务解锁
12. 员工按生产制作单制作并分装
13. 员工记录正常完成、成品余量或成品缺口
14. 系统结算当前批次成本、可入库剩余和不可入库损耗
15. 产品急冻、发货、完成
16. 管理端可查看实际收入、实际成本和实际毛利
```

## 验收标准

### 顾客端

- 顾客能看到饭量计算过程，但不能在订购页直接修改体重管理参数。
- 顾客能选择三档采购方案，且价格随方案变化。
- 顾客能看到原料清单和预计来源。
- 顾客能选择 7天、15天、30天默认分装周期。
- 顾客能自定义多行分装规格。
- 分装汇总低于 1kg 时不能下单。
- 底部固定栏能实时展示总价和参考每日价或每餐价。

### 管理端

- 管理员能多次调整订单付款价格。
- 原始价格快照不会被覆盖。
- 补差价不阻止采购、生产和发货。
- 管理员能查看订单收入、成本和毛利拆分。

### 采购端

- 采购清单能按库存可用量生成缺口。
- 可入库原料能抵扣未来采购缺口。
- 不入库日采原料不会进入未来库存抵扣。
- 报销审批不阻止生产解锁。

### 生产端

- 生产任务能展示订单分装明细和包材需求。
- 分装规格不同但食谱一致的订单可以合并烹饪。
- 员工只需记录生产正常、成品余量或成品缺口。
- 系统能根据余量或缺口辅助评估食谱损耗率。

### 库存与成本

- 库存预占、释放、领用、剩余入库都有流水。
- 当前批次只承担实际使用和不可保存损耗成本。
- 可保存剩余进入库存资产，并在未来使用时计入未来批次成本。

## 后续实施建议

建议分阶段实施：

1. 先改订购页和订单快照，让新订单数据结构正确。
2. 再补结算调整记录，解决多次调价、退款和补差价。
3. 再改采购缺口和库存预占，打通采购到生产。
4. 最后优化生产完成记录、成本结算和毛利视图。

这样能先把顾客下单和订单数据打准，再逐步提升内部履约与成本精度。
