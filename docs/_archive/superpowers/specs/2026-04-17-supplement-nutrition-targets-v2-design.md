# 补剂新版营养目标切换设计

## 背景

当前补剂用量计算同时存在两套口径：

- 旧版补剂浓度：`ingredient.properties.active_nutrients`
- 新版统一营养数据：`ingredient.nutrition_profile`
- 旧版食谱目标：`recipe_item.nutrient_target_key` + `recipe_item.nutrient_target_value`

这会带来三个问题：

- 同一个补剂浓度可能在两个地方重复维护，容易不一致。
- 食谱目标用中文名称表达，依赖隐含映射，无法稳定指向新版营养字段。
- 生产单、DIY 制作单、采购单、价格计算可能读到不同来源，造成用量口径漂移。

本轮目标是彻底废除旧版补剂浓度和旧版营养目标，完全切换到新版统一营养数据和字段化食谱补充目标。

## 目标

1. 补剂浓度唯一来源为 `ingredient.nutrition_profile`。
2. 食谱补剂目标直接选择新版营养字段，不再使用中文目标名做计算键。
3. 废除 `EPA+DHA` 这类合并录入方式，EPA、DHA 等营养素分别录入、分别设目标。
4. 一个补剂原料可以绑定多个营养目标，用量按满足所有目标所需的最大值计算。
5. DIY 制作单、订单价格、采购单、生产单、打印任务统一使用同一套新版补剂计算规则。
6. 订单快照和生产快照保存创建当时的补剂营养数据与目标，避免历史订单随原料后续编辑漂移。

## 非目标

- 不在本轮重做完整食谱营养平衡算法。
- 不自动猜测历史 `EPA+DHA` 应该拆成多少 EPA 和多少 DHA。
- 不让生产单实时读取最新原料数据来重算历史订单。
- 不把旧字段作为新版计算的兜底来源。

## 核心业务规则

### 1. 补剂浓度只来自新版营养数据

所有补剂计算必须从 `ingredient.nutrition_profile` 读取浓度。

废弃计算来源：

- `properties.active_nutrients`
- `properties.marketing_highlights`
- 前端临时 `activeNutrients`

这些字段可以在迁移期短暂保留用于展示或数据核对，但不能继续参与补剂用量计算。

### 2. 食谱目标存字段路径

食谱补剂目标不再存中文计算键，而是存新版营养字段路径。

示例：

```json
[
  {
    "fieldPath": "minerals.iodine",
    "label": "碘",
    "targetValuePerKg": 660,
    "unit": "μg"
  }
]
```

鱼油不再使用 `EPA+DHA`：

```json
[
  {
    "fieldPath": "fattyAcids.epa",
    "label": "EPA",
    "targetValuePerKg": 300,
    "unit": "mg"
  },
  {
    "fieldPath": "fattyAcids.dha",
    "label": "DHA",
    "targetValuePerKg": 300,
    "unit": "mg"
  }
]
```

### 3. 多目标补剂按最大需求量计算

一个补剂可以服务多个营养目标。

计算步骤：

1. 对每个目标分别计算所需补剂用量。
2. 取所有目标所需用量中的最大值。
3. 这个最大值就是该补剂的理论添加量。

示例：

- 每粒鱼油含 EPA 180mg、DHA 120mg
- 食谱每 kg 需要 EPA 360mg、DHA 360mg
- 满足 EPA 需要 2 粒
- 满足 DHA 需要 3 粒
- 最终用量为 3 粒

不把多个目标的用量相加，因为同一粒补剂同时提供多个营养素。

### 4. 不同业务场景只改变基准重量和损耗

补剂理论添加量公式统一：

```text
目标营养总量 = 基准食材重量 kg × 每 kg 目标值
单目标所需补剂量 = 目标营养总量 ÷ 该补剂在对应字段的浓度
多目标理论补剂量 = max(所有单目标所需补剂量)
```

场景差异：

| 场景 | 基准重量 | 展示/实际添加量是否加补剂损耗 | 成本/采购需求是否加补剂损耗 |
| --- | --- | --- |
| DIY 制作单 | 食材投料总重 | 否 | 不适用 |
| 订单价格预览 | 食材成品净重 | 否 | 是 |
| 订单详情 | 订单快照净用量 | 否 | 按订单成本快照 |
| 采购单 | 采购需求量 | 不适用 | 是 |
| 生产单 | 锅次食材投料总重 | 否 | 不适用 |
| 生产打印任务 | 锅次食材投料总重 | 否 | 不适用 |

补剂损耗只服务采购备货，不代表厨房实际添加量。

## 数据模型设计

### 1. 新增食谱补剂目标结构

建议在 `recipe_item` 上新增 JSON 字段：

```text
supplement_targets jsonb
```

结构：

```ts
type SupplementTarget = {
  fieldPath: string;
  label: string;
  targetValuePerKg: number;
  unit: string;
};
```

说明：

- `fieldPath` 是计算键，例如 `minerals.iodine`。
- `label` 只用于展示，例如 `碘`。
- `targetValuePerKg` 是每 kg 食材需要补充的目标量。
- `unit` 是目标单位，应与标准营养字段单位一致。

### 2. 订单和生产快照保存完整计算上下文

订单快照中的补剂项应保存：

```ts
type RecipeSnapshotSupplementItem = {
  ingredient_id: string;
  name: string;
  ingredient_type: "SUPPLEMENT";
  supplement_targets: SupplementTarget[];
  nutrition_profile_snapshot: NutritionProfileV2;
  unit_display_label?: string;
  preparation_methods?: string[];
};
```

生产单从订单快照读取，不实时回查 `ingredient` 表。

### 3. 字段路径和单位字典

系统需要一个标准营养字段字典，至少包含：

- `macros.*`
- `minerals.*`
- `vitamins.*`
- `fattyAcids.*`
- `aminoAcids.*`
- `customItems.*` 暂不建议作为食谱补剂目标第一版入口

第一版食谱目标选择器只允许选择固定字典字段，不开放自定义项作为目标，避免计算不可控。

## 后台交互设计

### 1. 食谱编辑页

当原料类型为补剂时，原“营养目标名称 + 目标值”改为“补剂营养目标列表”。

每一行包括：

- 营养字段选择器
- 每 kg 目标值输入框
- 单位只读展示
- 删除按钮

营养字段选择器按新版营养分组展示：

- 矿物质
- 维生素
- 脂肪酸
- 氨基酸
- 宏量

选择字段后，系统自动带出展示名和单位。

### 2. 补剂原料编辑页

补剂原料不再展示旧版“有效成分含量”录入区。

统一使用标准原料的新版营养数据录入页签：

- 宏量
- 矿物质
- 维生素
- 脂肪酸
- 氨基酸
- 自定义营养项

补剂真实标签按每粒、每片、每勺或每份标注时，通过 `nutrition_profile.meta.rawBasisType` 和 `servingWeightG` 表达。

### 3. 数据校验

保存食谱时：

- 补剂原料必须至少有一个 `supplement_targets`。
- 每个目标必须有合法 `fieldPath`。
- 每个目标值必须大于 0。
- 目标字段必须能在对应补剂的 `nutrition_profile` 中读取到大于 0 的浓度。
- 同一个补剂项内不允许重复选择同一个 `fieldPath`。

保存补剂原料时：

- 不再自动写入 `properties.active_nutrients`。
- `nutrition_profile` 必须保持新版结构。
- 后台可以提示“当前补剂尚未填写任何可用于食谱目标的营养字段”。

## API 与计算模块

### 1. 统一计算模块

后端新增统一补剂计算模块，负责：

- 根据 `fieldPath` 从 `nutrition_profile` 读取浓度。
- 校验单位。
- 支持一个补剂多个目标。
- 返回理论添加量和触发最大值的目标。
- 根据业务场景决定是否应用补剂损耗。

前端小程序只负责展示和少量本地预览。生产单和采购单的权威计算应来自快照或后端返回数据。

### 2. 兼容字段命名

对外响应在迁移期可以同时返回：

- 新字段：`supplementTargets`
- 旧字段：`nutrientTargetKey`、`nutrientTargetValue`

但旧字段只用于旧页面展示兼容，不能再参与计算。

完成前端切换后移除旧字段响应。

## 数据迁移策略

### 阶段 1：建立新版结构

1. 补全标准营养字段字典，尤其是维生素、脂肪酸、氨基酸当前缺失的常用字段。
2. 新增 `recipe_item.supplement_targets`。
3. 新增后端补剂计算模块。
4. 管理端食谱编辑页切换到字段选择器。

### 阶段 2：迁移现有食谱目标

可安全自动迁移的目标：

- `碘` -> `minerals.iodine`
- `钙` -> `minerals.calcium`
- `锌` -> `minerals.zinc`
- `维生素E` -> `vitamins.vitaminE`
- `维生素D` -> `vitamins.vitaminD`
- `胆碱` -> `vitamins.choline`

需要人工确认的目标：

- `EPA+DHA`

处理规则：

- 生成清单列出所有使用 `EPA+DHA` 的食谱项。
- 不自动拆分目标值。
- 由管理员确认 EPA 与 DHA 各自目标值。
- 确认后写入两个目标：`fattyAcids.epa`、`fattyAcids.dha`。

### 阶段 3：切断旧字段计算

1. 所有计算路径停止读取 `properties.active_nutrients`。
2. 订单快照写入 `supplement_targets` 和 `nutrition_profile_snapshot`。
3. DIY 制作单、采购单、生产单、打印任务全部改用新版目标结构。
4. 测试覆盖“只有新版营养数据、没有旧字段”的补剂用量计算。

### 阶段 4：清理旧字段

1. 删除后台旧字段录入入口。
2. 删除旧字段解析工具。
3. 清理旧字段测试。
4. 数据库中可保留历史 JSON 但不再使用；确认无依赖后再做物理清理。

## 测试计划

### 单元测试

- 从 `nutrition_profile` 用 `fieldPath` 读取浓度。
- 单目标补剂用量计算。
- 多目标补剂按最大需求量计算。
- EPA、DHA 分开录入后不再支持 `EPA+DHA`。
- 旧字段缺失时仍能完成新版计算。
- 旧字段存在但新版字段缺失时计算失败并给出明确错误。

### 后端集成测试

- 创建/更新食谱时保存 `supplement_targets`。
- 食谱目标字段不存在时拒绝保存。
- 订单快照保存补剂目标和营养档案快照。
- 采购需求使用补剂损耗。
- 生产任务不使用补剂损耗。

### 小程序测试

- DIY 制作单按新版目标展示补剂用量。
- 生产详情页按锅次投料总重展示补剂实际添加量。
- 打印任务与生产详情页一致。
- 食谱详情页展示“每 kg 添加 x 单位营养素”。

## 风险与处理

### 1. 历史食谱缺新版营养数据

处理：

- 迁移前生成缺失清单。
- 缺失新版营养数据的补剂不能进入新版食谱保存。
- 已有历史订单继续按原快照展示，不强制重算。

### 2. 单位不一致

处理：

- 标准字段字典定义默认单位。
- 录入页按字段固定单位展示。
- 计算模块第一版不做跨单位自动换算，发现单位不一致直接报错。

### 3. 前后端短期字段并存

处理：

- 迁移期只允许新版字段参与计算。
- 旧字段只为旧页面展示兼容保留。
- 完成小程序和后台切换后删除兼容层。

## 验收标准

1. 新建补剂原料只填写 `nutrition_profile`，不写 `properties.active_nutrients`。
2. 新建或编辑食谱补剂项时，目标从新版营养字段选择器中选择。
3. 鱼油类补剂使用 EPA、DHA 两个独立目标，不再出现 `EPA+DHA`。
4. 同一补剂多个目标时，用量取最大需求量。
5. DIY、采购、生产、打印四条链路补剂用量口径一致。
6. 只有旧字段、没有新版营养数据的补剂不能通过新版食谱目标校验。
7. 现有生产单和历史订单不因原料营养数据修改而漂移。

## 实施建议

本改造应单独开分支实施，不与当前生产单补剂用量修复混在同一提交中。

建议实施顺序：

1. 补齐新版营养字段字典。
2. 新增食谱补剂目标 JSON 字段与 DTO。
3. 实现后端新版补剂计算模块。
4. 迁移普通单目标补剂。
5. 生成 `EPA+DHA` 人工确认清单。
6. 切换后台食谱编辑页。
7. 切换订单、采购、生产、DIY、打印链路。
8. 删除旧字段计算依赖。
