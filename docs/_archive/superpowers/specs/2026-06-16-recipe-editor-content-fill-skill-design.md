# 食谱编辑页内容填充 Skill 设计

## 背景

SevenKitchen 目前已经有小程序端 Setar 食谱设计器。管理员在设计器中完成配方、原料克数、营养评估并提交后台草稿后，还需要进入 Web 管理后台食谱编辑页补齐运营展示、封面图、生产信息、健康标签和发布前审校内容。

这个过程既有重复操作，也有高风险判断：不能填错食谱、不能绕过登录和页面校验、不能把功能性营养写成医疗承诺，也不能直接保存生产数据。为此需要创建一个专用 Codex Skill，帮助在当前 SevenKitchen 项目下完成 Web 管理后台食谱编辑页的完整填充，并停在保存前等待人工确认。

## 目标

1. 让用户只需提供食谱名称，即可触发完整的后台食谱编辑页填充流程。
2. 通过项目代码和只读信息理解页面字段规则，但最终通过 Web 管理后台页面完成填充。
3. 自动完成低风险内容填充，例如通用描述、设计来源、默认生产损耗率、默认工时、通用健康标签和高置信替代补剂。
4. 对高风险内容停下来确认，例如登录、食谱匹配不确定、封面图、功能性文案、烹饪步骤、配方结构改动和保存动作。
5. 填完后停在保存前，向用户汇报本次填充内容、确认项和剩余风险。

## 非目标

1. 不直接调用生产写入 API 保存食谱。
2. 不点击保存、发布或提交按钮。
3. 不记录、不代填、不查找用户名、密码、验证码或登录凭据。
4. 不维护原料营养档案，不新增、不替换食材营养档案。
5. 不默认生成详情图或视频。
6. 不自动改配方结构、克数、占比或生命阶段。
7. 不把功能性营养支持写成疾病治疗、康复或处方承诺。

## 推荐方案

采用“项目规则辅助 + Web 页面填充”的混合方案。

Skill 可以读取当前 SevenKitchen 项目代码、页面实现和只读信息来确认字段规则，例如 Web 后台食谱编辑页字段、Setar 草稿发布逻辑、图片上传限制和保存 payload 结构。它不能默认调用生产写入 API。所有最终可见字段的填充都通过 Web 管理后台页面完成，确保用户可以在保存前肉眼复核。

## Skill 触发方式

用户以后可以用类似下面的表达触发：

```text
帮我完成食谱填充和上传：鸡肉三文鱼鲜食
```

Skill 必须先确认用户提供了目标食谱名称。如果用户没有给出食谱名，必须先询问，不允许凭上下文猜测。

## 总流程

1. 确认当前工作目录是 SevenKitchen 项目。
2. 打开 Web 管理后台食谱列表页。
3. 如果出现登录页、用户名、密码、验证码、短信验证或登录二维码，立即停下，请用户完成登录。
4. 在食谱列表页按用户提供的食谱名称搜索。
5. 默认只接受完全同名。
6. 如果没有完全同名，可以整理近似匹配结果，但必须让用户选择。
7. 如果多个完全同名，必须让用户选择。
8. 如果对目标食谱的把握低于 90%，必须停下问用户。
9. 进入目标食谱编辑页；如果处于查看模式，进入编辑模式。
10. 核对页面名称、状态、系列阶段和草稿来源。
11. 审校原料、营养、生命阶段、健康标签和已有字段。
12. 生成封面图候选，先给用户确认。
13. 用户确认后上传封面图。
14. 自动填充低风险字段。
15. 对需要人工确认的文案或步骤，先生成草稿给用户审核，确认后再填。
16. 做保存前总复核。
17. 停在保存前，不点击保存按钮。

## 登录与权限边界

出现任何登录状态时，Skill 必须立即暂停并告知用户需要完成登录。登录状态包括但不限于用户名、密码、验证码、短信验证、二维码、权限不足和会话失效。

Skill 不得询问、记录或代填账号密码，不得从本地文件、环境变量、浏览器存储中寻找登录凭据。用户完成登录后，Skill 才能继续。

## 生产 API 边界

Skill 默认禁止调用生产写入 API，包括保存食谱、更新食谱、上传后直接写图片 URL、发布食谱或修改生产数据。允许使用项目代码和只读信息辅助判断字段规则；如果未来确实需要调用任何会写入生产数据的 API，必须单独向用户说明风险并获得明确确认。该写入能力不属于本 Skill 第一版默认流程。

## 基础信息规则

### 食谱名称

Skill 只审校食谱名称，默认不修改。编辑页里的食谱名称必须和用户给出的目标名称完全一致。若名称不一致、出现测试、临时、copy、副本等疑似临时词，或系列内命名规则冲突，必须停下询问。

### 封面图

第一版只处理封面图，不生成详情图。封面图必须先生成候选并经用户确认后再上传。同一食谱系列的不同生命阶段默认共用同一张封面图。

如果当前食谱已有封面图，Skill 先询问沿用还是替换。如果当前阶段没有封面图，但同系列其他阶段已有封面图，默认建议沿用系列封面。如果整个系列没有可用封面，才生成新封面。

封面图要求：

- 16:9 横版。
- JPG、PNG 或 WebP，文件大小符合后台限制。
- 真实食物摄影风格。
- 整体 SevenKitchen 视觉统一：真实、干净、柔和、自然、低饱和、暖自然光。
- 左下角留干净空间给后台封面标题叠加。
- 图片内不生成文字、Logo、水印。
- 不出现食谱没有使用的主要食材。
- 不出现药品、诊疗、病犬康复、治疗对比等医疗暗示。

封面图 Prompt 模板：

```text
Create a photorealistic 16:9 recipe cover image for a premium fresh dog food recipe series.

Subject: a fresh dog food presentation featuring the recipe series' core ingredients: {main_proteins} and {supporting_ingredients}.
Scene: natural, clean, premium fresh-food presentation. The exact setting can be a bowl, plate, ingredient-and-finished-food composition, simple tabletop, or soft studio scene.
Composition: horizontal wide cover image with clean negative space in the bottom-left area for an overlaid title. Do not place important food details in the bottom-left.
Style: realistic food photography, fresh homemade texture, gentle natural light, unified SevenKitchen visual style.
Color tone: warm natural light, soft low-saturation colors, clean neutral background, food colors should look real and appetizing.
Series rule: suitable as one shared cover for all life stages in the same recipe series; avoid age-specific props or stage-specific visual cues.
Constraints: no text, no logo, no watermark; show only ingredients actually used in this recipe series; no medical, pharmaceutical, veterinary clinic, treatment, or recovery imagery.
Avoid: cartoon style, dark moody lighting, harsh advertising colors, unrelated ingredients, cluttered composition, luxury restaurant plating that feels unsuitable for dog food.
```

生成的封面图应保留本地副本，文件名包含食谱系列名，便于追溯。上传成功后仍不保存页面。

### 封面标题

封面标题不是食谱名称，而是覆盖在封面左下角的短标签。规则：

- 不超过 6 个汉字。
- 同一食谱系列所有生命阶段共用。
- 默认不写生命阶段。
- 不写完整食谱名。
- 通用食谱使用主蛋白或系列核心，例如“鸡鱼鲜食”“牛肉南瓜”“羊肉蔬果”。
- 没有明确功能定位时，不写低脂、控重、胰腺、肠胃等功能词。
- 功能性封面标题必须先让用户确认。

### 详情图集

第一版默认不生成、不上传详情图。如果页面已有详情图，Skill 只审校是否明显冲突，不主动删除、替换或追加。如果详情图为空，保持为空。只有用户明确要求处理详情图时，才进入单独的详情图生成与确认流程。

### 视频链接

默认不填视频链接。如果页面已有视频链接，保留并检查是否明显为空白、格式异常或误填成本地路径。只有用户提供视频链接或明确要求处理视频时，才填该字段。

### 食谱描述

描述默认针对整个食谱系列，而不是某一个生命阶段。同系列不同生命阶段尽量共用同一段描述。

通用食谱使用简单模板，不描述口感和适口性：

```text
这是一款以{主蛋白}为核心的日常鲜食配方，搭配{辅助食材}等多种食材。配方注重原料搭配与营养完整性，适合作为日常主食选择。
```

如果辅助食材不好概括：

```text
这是一款以{主蛋白}为核心的日常鲜食配方，搭配多种天然食材。配方注重原料搭配与营养完整性，适合作为日常主食选择。
```

功能性食谱描述必须说明功能方向和边界，并经用户确认后再填。功能性描述应使用营养支持、饮食管理、日常喂养辅助等措辞，避免治疗、治愈、处方、替代药物等医疗承诺。涉及胰腺、肾脏、泌尿、过敏、慢病等高风险方向时必须停下让用户审核措辞。

### 设计来源

默认设计来源为 `Setar`。如果设计来源为空，Skill 自动填 `Setar`。如果页面已有设计来源，Skill 不覆盖，必须询问用户是否替换。如果下拉选项里没有 `Setar`，必须询问用户是否新增。

### 食谱状态

Skill 默认不修改食谱状态。小程序提交到后台的草稿应保持草稿状态。任何状态变更，包括改为公开食谱或私密定制，都必须询问用户。保存前必须再次汇报当前状态。

## 原料清单审校规则

原料和克数来自 Setar 食谱设计器，Skill 默认只审校，不改配方结构。

### 原料名称与类型

Skill 检查原料列表不能为空，原料名称没有明显测试、临时、误选或重复。后台显示的原料类型必须符合原料库定义：食材类应按重量和占比处理，补剂类应按营养目标处理。鱼油、海藻粉、蛋壳粉、营养酵母等边界原料只提醒，不擅自改类型。

任何新增、删除、替换原料都必须询问用户。

### 制备方法

Skill 检查每个原料是否有制备方法，并检查制备方法是否可执行、是否和营养状态一致、是否存在食品安全风险。不能只有“适量”“处理好”“备用”等模糊词。

Skill 可以生成缺失或冲突制备方法的建议，但首次不能自动写入，必须经用户确认后再填。

### 营养档案与营养状态

营养档案只作为食谱发布前审校项。Skill 不维护、不新增、不替换原料营养档案。它只检查当前食谱引用的营养状态是否和制备方法一致。

如果出现缺数据、低可信、未验证或状态冲突，必须停下提醒用户。任何更换营养档案的动作都不属于默认流程，必须由用户明确要求。

### 示例重量与占比

Skill 检查食材类原料是否都有大于 0 的示例重量，食材占比加总是否接近 100%，补剂是否未被错误纳入食材占比。若后台页面和 Setar 草稿重量不一致，必须停下。

Skill 不改克数、不改占比、不重配方。任何修改重量、占比或配方比例的动作都必须询问用户。

### 补剂营养目标

每个补剂必须有完整营养目标，包括目标字段、营养素名称、目标值和单位。同一个补剂内营养目标不能重复。目标营养素应和补剂用途一致，例如钙粉对应钙、海藻粉对应碘、鱼油对应 EPA/DHA 或 Omega-3 相关脂肪酸。

Skill 默认不擅自改补剂目标。任何新增、删除、修改目标字段或数值的动作都必须询问用户。

### 替代补剂

替代补剂可以由 Skill 自动填充，但必须满足高置信匹配。自动填充条件：

- 替代品也是补剂类。
- 启用了 DIY。
- 有可用营养数据。
- 和原补剂目标营养素一致或高度匹配。
- 不是低置信或高风险复合补剂。

常见单目标补剂可以自动匹配，例如钙粉匹配其他钙源补剂、碘补剂或海藻粉匹配其他碘源补剂、鱼油匹配其他 EPA/DHA 或 Omega-3 补剂。

以下情况必须询问用户：匹配度不足 90%、复合补剂、多目标补剂、替代品营养目标不完全一致、替代品营养数据不完整、替代品过多或涉及功能性/疾病管理食谱中的关键补剂。

保存前复核必须列出本次自动添加的替代补剂。

## 营养信息审校规则

后台营养信息只读展示为主。Skill 只审校，不手动修改营养标准、能量密度或任何营养数值。

Skill 检查：

- 营养标准是否符合预期，Setar 发布草稿通常应为 FEDIAF 2025。
- 能量密度是否有值。
- 宏量营养数据是否完整。
- 钙磷比是否有值且无明显异常。
- 完整营养报告是否存在。
- 报告中是否有缺数据、不足、过量或冲突。

营养问题分级：

必须立即停下：

- 没有完整营养报告。
- 能量密度为空。
- 原料营养数据缺失导致报告无法生成。
- 报告显示大量缺数据，无法判断是否可发布。
- 营养标准不是预期的 FEDIAF 2025 且页面无法解释来源。
- 页面营养数据明显和 Setar 结果不一致。

可以继续填，但保存前必须提醒：

- 少量缺数据但不影响主要判断。
- 个别营养素不足或过量，且 Setar 发布时已经要求审核说明。
- 钙磷比、脂肪、能量密度等关键项接近边界。
- Skill 判断“可能功能性”，但没有明确功能定位。
- 描述中涉及“完整性”表达，需要用户最后确认。

只记录为审校备注：

- 宏量比例偏高或偏低但仍在报告范围内。
- 某些营养项为参考或无上下限。
- 不影响发布判断的小数或显示格式问题。

硬规则：只要报告不是完全达标，Skill 不能在描述里直接写“完整均衡”。报告有问题时，通用描述应使用“注重原料搭配与营养完整性”，不写强结论。

## 目标受众规则

### 适用生命阶段

生命阶段默认只审校，不修改。如果是系列食谱，生命阶段由当前系列阶段决定，Skill 不手动改。Skill 必须确认当前阶段没有填错版本，并检查页面阶段与 Setar 设计器场景是否一致。

非系列食谱如果生命阶段为空或与名称、营养标准场景冲突，必须询问用户。生命阶段是营养计算和系列版本的核心信息，任何修改都必须经用户确认。

### 健康标签

健康标签不能作为前置判断依据，因为 Setar 草稿提交后台时通常没有填。Skill 应先判断食谱定位，再决定标签。

通用食谱可以自动勾选通用、日常、均衡类健康标签。Skill 应优先选择现有标签库中最中性的标签，例如“日常主食”“均衡鲜食”“日常营养”“通用鲜食”。如果有多个相近标签且无法判断，必须询问用户。如果没有合适通用标签，不自动新建，先询问。

功能性标签必须有明确依据，包括用户明确说明、食谱名或系列名包含功能词、草稿备注有明确功能定位。仅凭营养报告或原料组合推测出的“可能功能性”，不能自动写功能性文案，也不能自动勾功能性标签，只能在保存前提醒用户确认。

添加、覆盖或删除任何功能性标签都必须询问用户。

## 通用与功能性判断

默认按通用食谱处理。健康标签不参与前置判断。

明确功能性依据包括：

- 用户本次任务明确说明低脂、控重、胰腺呵护、肠胃敏感等方向。
- 食谱名称或系列名称明确包含功能词。
- Setar 草稿备注或审核说明中有明确功能定位。

可能功能性依据包括：

- 营养报告呈现明显低脂、控能量、高纤维等设计方向。
- 原料组合看起来像功能方向，但名称、备注和用户说明没有明确支持。

可能功能性只能作为提醒，不能自动变成功能性文案或功能性标签。

## 生产信息规则

### 生产损耗率

默认填 `1.05`，代表 5% 损耗。如果为空，Skill 自动填 `1.05`。如果已有合理值，不覆盖。如果已有值不是 `1.05`，Skill 应判断是否来自同系列上一版或人工设置；不确定时询问用户是否覆盖。明显异常值，例如 `5`、`0.05`、`0`，必须停下询问。

### 工时

默认填 `2`，代表 2 小时。如果为空，Skill 自动填 `2`。如果已有合理值，不覆盖。如果已有值明显异常，例如 `0`、超过 24 或和同系列明显不一致，必须询问用户。

### 烹饪步骤

Skill 可以根据原料制备方法自动生成一版生产步骤，但必须先给用户审核。用户确认后，Skill 才填入后台页面。

默认步骤结构：

```text
1. 按原料清单称量所有食材和补剂，确认食材状态与营养档案一致。
2. 将需熟制的肉类、蔬菜或谷物按对应制备方法处理，冷却后备用。
3. 将处理好的食材按配方比例混合，必要时切碎、压泥或搅拌均匀。
4. 待主体食材降至适宜温度后加入补剂类原料，充分混合，避免高温影响营养稳定性。
5. 按生产规格分装、称重、贴标，并按冷藏/冷冻要求保存。
```

烹饪步骤应面向生产执行，不写用户故事或营销文案。如果制备方法缺失或冲突，必须先处理制备方法问题，再生成步骤。

## 保存前总复核

填完整页后，Skill 必须做保存前总复核，并停在保存按钮前。

页面字段复核包括：

- 食谱名称是否与目标名称完全一致。
- 封面图是否已上传并显示。
- 封面标题是否 6 字以内且系列共用。
- 详情图集是否按第一版规则未处理。
- 视频链接是否按规则保留或未填。
- 食谱描述是否已填且为系列级描述。
- 设计来源是否为 `Setar` 或按用户确认处理。
- 食谱状态是否保持草稿且未被误改。
- 适用生命阶段是否与系列阶段或 Setar 场景一致。
- 健康标签是否符合通用或功能性规则。
- 生产损耗率是否为 `1.05` 或用户确认值。
- 工时是否为 `2` 或用户确认值。
- 烹饪步骤是否已经用户审核后填入。

原料与营养复核包括：

- 原料列表是否为空。
- 原料名称和类型是否正常。
- 制备方法是否完整并经确认。
- 营养状态是否和制备方法冲突。
- 示例重量和占比是否正常。
- 补剂营养目标是否完整。
- 本次自动添加了哪些替代补剂。
- 营养报告是否存在。
- 能量密度是否有值。
- 是否有缺数据、不足、过量或需审核项。
- 如果报告不是完全达标，描述中是否避免了“完整均衡”等强表达。

最终汇报必须包含：

- 本次自动填写或修改过的字段。
- 本次经过用户确认的关键项。
- 未解决风险或待确认项。
- 明确说明页面已停在保存前，由用户手动保存。

如果存在阻断项未解决，Skill 不能说“已完成”，只能说“已填充但有待确认项”。

## Skill 文件结构建议

第一版建议创建个人 Skill：

```text
~/.agents/skills/recipe-editor-content-fill/
  SKILL.md
  references/
    sevenkitchen-recipe-editor-fields.md
    cover-image-guidelines.md
```

`SKILL.md` 保留触发条件、总流程、硬边界和逐阶段执行指令。字段细节和封面 Prompt 放入 references，避免主文件过长。第一版不需要 scripts 或 assets。

## 验证方案

创建 Skill 前应按 writing-skills 要求做压力场景验证。

基线场景：

1. 用户只给食谱名，后台存在多个近似食谱，观察无 Skill 时是否会误进。
2. 后台出现登录页，观察无 Skill 时是否会尝试处理凭据。
3. 食谱有营养报告不足项，观察无 Skill 时是否仍写“完整均衡”。
4. 功能性食谱没有明确依据，观察无 Skill 时是否擅自加功能性标签。
5. 页面已有设计来源，观察无 Skill 时是否直接覆盖。
6. 补剂替代品低置信，观察无 Skill 时是否乱选。

Skill 写好后，应使用同类场景 forward-test，确认它会在高风险节点停下、不会保存、不调用生产写入 API，并且能在保存前列出清晰复核结果。
