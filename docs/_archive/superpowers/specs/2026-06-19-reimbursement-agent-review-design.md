# 报销智能审核 Agent 设计

## 背景

SevenKitchen 现有报销流程已经支持员工在小程序提交报销申请、上传支付凭证、关联已完成采购清单，并由管理员在后台审核。报销详情中已经展示采购记录、折算单价、上次单价、库存、平台费用、其它费用和支付凭证，适合引入智能审核能力来降低人工看单成本。

本设计采用“规则校验 + 支付凭证 OCR + Agent 风险总结”的方案。Agent 不直接通过、驳回或打款，只生成员工提交前提醒和管理员审核风险摘要。最终审核决定仍由管理员人工完成。

## 目标

- 员工提交前获得智能自查结果，明确哪些问题必须修正、哪些风险只需确认。
- 管理员打开报销单时看到同一份智能审核结果，快速定位金额、时间、价格和资料风险。
- 高风险问题拦截提交，普通风险不拦截但保留提醒和审核记录。
- 支持 OCR 识别支付凭证中的金额和支付时间；收款方可识别但不作为硬性要求。
- 保留每次智能审核记录，支持员工重新提交后的追溯。

## 非目标

- 第一版不做自动审批、自动驳回或自动付款。
- 第一版不要求收款方必须识别或必须匹配。
- 第一版不把采购价格上涨作为提交拦截条件。
- 第一版不替代管理员的最终审核责任。

## 已确认业务规则

### 高风险拦截

以下问题会阻止员工提交，并要求员工补充或修正：

- 未上传任何支付凭证。
- 报销总金额与费用明细合计不一致。
- OCR 可用但无法从支付凭证中识别出金额。
- OCR 识别出的支付金额合计与报销金额明显不一致。
- 支付时间明显异常，例如支付时间晚于提交时间较多，或早于关联采购发生时间过多。
- 关联采购清单不是已完成状态。
- 关联采购清单已经被其它报销单使用。
- 其它费用既没有分类，也没有说明。

### 普通风险提醒

以下问题不拦截提交，但员工端和管理员端都要提示：

- 采购记录折算单价较历史单价明显上涨。
- OCR 未识别到支付时间，但识别到了金额。
- 支付凭证张数较多且金额拆分复杂，需要人工复核。
- 其它费用说明较简略，但已满足最低提交要求。
- OCR 服务失败导致没有完成智能识别，此时不阻断流程，但管理员端必须显示“需人工复核凭证”。
- Agent 总结失败，此时保留规则校验和 OCR 结果，不影响提交。

## 员工端流程

1. 员工在“提交报销申请”页面选择采购清单、填写平台运费、平台打包费和其它费用，并上传支付凭证。
2. 员工点击提交时，小程序先请求后端执行智能审核。
3. 后端执行基础规则校验、OCR 识别和 Agent 风险总结。
4. 如果审核结果包含高风险拦截项，小程序不提交报销单，并展示需要修正的问题。
5. 如果只有普通风险，小程序展示提醒，例如“鸡胸肉折算单价较上次上涨 42%，请确认品牌、规格或渠道是否变化”，员工确认后可以继续提交。
6. 报销提交成功后，本次智能审核结果与报销单关联，供管理员审核时查看。

员工端文案以行动建议为主，不展示技术细节。员工需要知道“哪里不对、怎么补”，不需要知道模型、接口或内部字段。

## 管理员端流程

管理员打开报销单详情时，在费用明细上方显示“智能审核结果”卡片：

- 总体风险：低 / 中 / 高。
- 基础校验：金额、凭证、支付时间、资料完整性。
- OCR 结果：每张支付凭证识别到的金额、支付时间和可选收款方。
- 风险提醒：例如单价上涨、支付时间缺失、凭证金额不匹配。
- Agent 摘要：一句话说明本单最需要人工关注的点。
- 审核辅助建议：只显示“建议复核金额”“建议补充说明”“未发现明显异常”等提醒，不自动做最终结论。

管理员仍然手动选择通过、驳回或要求重提。管理员的人工审核意见与 Agent 审核摘要分开保存和展示，避免混淆责任。

## 后台设计

### 智能审核记录

新增一份独立的智能审核记录，与报销单关联。建议记录内容包括：

- 报销单 ID。
- 触发场景：提交前自查、提交入库、重新提交。
- 风险等级：LOW / MEDIUM / HIGH。
- 是否拦截。
- 高风险原因列表。
- 普通风险提醒列表。
- 员工端提示文案。
- 管理员端摘要文案。
- OCR 识别结果，包括图片 URL、金额、支付时间、可选收款方、识别置信度和失败原因。
- 规则校验结果，包括金额一致性、时间合理性、资料完整性、采购清单状态、价格异常。
- Agent 元信息，包括 provider、model、promptVersion、生成时间和失败原因。

实现时遵循项目现有 Prisma 命名规则：TypeScript 和 Prisma 使用驼峰命名，数据库实际列名通过 `@map` 映射为蛇形命名。具体字段需在实现阶段根据 `schema.prisma` 和 migration 确认，不能凭空写原生 SQL 字段名。

### 触发方式

第一版采用同步自查接口和提交接口联动：

- 员工点击提交时，先执行智能审核。
- 高风险时返回拦截结果，不创建或不更新报销单。
- 非高风险时允许提交，并将审核结果保存到报销单。
- 员工重新提交时重新运行智能审核，旧审核结果保留为历史。

如果 OCR 或 Agent 响应变慢，后端应有超时保护。OCR 服务失败不阻断提交，但必须在结果中标记“未完成智能识别”；Agent 总结失败不阻断提交，保留规则校验和 OCR 原始结果。

### 审核职责边界

系统规则负责确定性判断，例如金额是否相等、采购清单状态是否正确、是否缺少凭证。

OCR 负责从支付截图中提取金额和时间。金额是核心核对项，时间是风险判断项，收款方只作为补充信息。

Agent 负责把规则和 OCR 结果整理成自然语言提醒，不作为唯一判断依据。高风险拦截必须来自规则或 OCR 的确定性结果，不能只因为 Agent 主观判断而拦截。

## 风险等级

### 低风险

资料完整，金额匹配，支付时间正常，没有明显采购价格异常。

### 中风险

存在需要人工关注的问题，但不影响员工提交，例如价格上涨、支付时间未识别、说明较简略、OCR 服务失败。

### 高风险

存在确定性问题，员工必须先修正，例如无凭证、金额不匹配、OCR 有效但金额不可识别、采购清单状态不合法、其它费用缺少分类和说明。

## 异常处理

- OCR 识别不到金额：高风险拦截，提示员工补充清晰凭证或重新上传。
- OCR 识别不到时间：中风险提醒，允许提交，管理员端提示人工复核。
- OCR 服务失败：中风险提醒，允许提交，管理员端提示“智能识别未完成”。
- Agent 总结失败：不影响提交，展示规则校验结果。
- 员工重新提交：重新审核，旧记录保留，管理员默认查看最新结果。
- 管理员审核后员工再改凭证：需要重新进入重新提交流程，避免审核结果和材料不一致。

## 与现有系统的关系

报销单状态流转保持不变。智能审核结果只作为辅助信息，不改变现有 `PENDING_REVIEW`、`REIMBURSED`、`REJECTED`、`REQUIRES_RESUBMIT` 的业务含义。

现有工作台待处理数量仍以报销单状态为准。后续如果需要，可以给管理员增加“高风险报销待审”筛选，但第一版不改变工作台统计口径。

现有 Agent Provider 配置和营养审核 Agent 的模式可作为实现参考：配置 provider、保存结构化结果、失败时降级、人工最终确认。

## 测试范围

- 没有支付凭证时，员工提交被拦截。
- 报销总额与明细金额不一致时，员工提交被拦截。
- OCR 金额与报销金额不一致时，员工提交被拦截。
- OCR 识别不到时间时，员工可以提交，但员工端和管理员端都有提醒。
- 采购价格上涨时，员工可以提交，但员工端和管理员端都有风险提醒。
- OCR 服务失败时，员工可以提交，管理员端显示需人工复核。
- Agent 总结失败时，规则校验和 OCR 结果仍可展示。
- 重新提交后生成新的智能审核结果，管理员默认看到最新结果。
- 管理员最终审核动作不被 Agent 自动触发。

## 上线建议

第一阶段只启用“辅助审核”模式，观察报销单风险提醒是否准确。上线后重点看三类反馈：员工是否能理解拦截原因、管理员是否能更快定位风险、OCR 对实际支付截图的金额和时间识别是否稳定。

稳定后再考虑增强为轻量 C 方案，例如生成“建议补充说明”的审核意见草稿，但仍不自动代替管理员点击通过或驳回。
