# 食谱编辑器性能优化设计

## 目标

在不改变配方数据和营养计算规则的前提下，消除原料用量编辑、添加原料和拖动排序中的可感知卡顿；将排序网络请求收敛为一次，并避免连续编辑时重复执行完整营养评估。

## 已确认决策

1. 原料保存与营养评估解耦。原料写入成功后立即显示已保存；营养评估在最后一次会影响营养的编辑后 400ms 执行。
2. 评估尚未完成时，界面明确显示“评估更新中”；发布和进入营养详情前会强制等待最新评估完成。
3. 拖动过程中只更新插入位置，不改写原料数组、不重复读取每行布局；松手时才重排一次。
4. 排序使用单个批量接口，服务端只校验一次草稿权限，并在一个事务中保存顺序。排序不触发营养评估。
5. FEDIAF 目标按场景缓存于后端进程内。营养计算与持久化结果保持服务端为唯一来源。
6. 为按草稿读取并排序原料新增 `(design_recipe_id, sort_order)` 数据库索引。

## 设计

### 前端编辑状态

每个原料行维护局部字符串输入草稿。输入过程不改变 `items` 的已保存重量，因此不会连带重算总重、占比和全部行展示；失焦或确认时将合法数值写入 `items` 并调用单项保存。保存成功后通过共享的评估调度器安排一次延后评估。调度器只保留最后一个版本，旧响应不会覆盖较新的界面状态。

### 拖动排序

拖动开始时记录原始顺序与行位置。`touchmove` 最多每动画帧更新一个目标索引，并限频触觉反馈；列表保持原始顺序，只显示插入标记。松手时根据原始被拖动项和目标索引构建最终顺序，立即更新本地显示，再调用批量排序接口。失败时重新加载草稿恢复服务端状态。

### 后端接口与数据

新增 `PUT /api/v1/recipe-designer/drafts/:id/item-order`，请求体为 `{ itemIds: string[] }`。服务端验证数组不重复、长度和成员与草稿原料完全相同，再在事务中更新 `sortOrder`。接口返回按新顺序的原料轻量数据。

评估接口保持兼容。前端仅在编辑停顿后调用；服务端缓存每个 FEDIAF 场景的标准目标，减少重复查询。新增索引由 Prisma migration 创建，不使用手工生产库写入。

## 一致性与错误处理

- 保存失败仅回滚对应原料输入；评估失败保留已保存原料并显示可重试状态。
- 在评估请求进行期间又发生新的营养相关编辑时，旧响应被丢弃，调度器再次运行。
- 排序接口拒绝缺失、重复或跨草稿的原料 ID；前端重新加载草稿而不保留不可信本地顺序。
- 评估刷新不参与排序操作，避免无意义计算和状态竞争。

## 验收标准

1. 连续编辑同一或多个原料时，最后一次编辑后最多触发一次评估请求。
2. 拖动移动阶段不重排 `items`，松手后仅发起一次排序请求。
3. 30 个原料排序从 30 次请求降为 1 次。
4. 批量排序的授权、输入校验、持久化和失败恢复均有自动化测试。
5. 相关后端与小程序测试、后端构建和小程序发布构建通过。
