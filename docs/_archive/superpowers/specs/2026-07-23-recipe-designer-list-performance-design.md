# 食谱设计器列表首屏加载优化设计

## 背景与问题

生产端打开食谱设计器时，列表接口会读取所有可见食谱系列，并为每个系列附带全部关联草稿、草稿原料明细和关联食谱。列表界面只使用系列名称、业务状态、各生命阶段状态及最近更新时间；多余明细使响应体、数据库关联读取和小程序渲染时间随历史食谱量增长。

## 目标与范围

- 首次打开优先显示最新 20 个食谱系列卡片。
- 用户滑动至底部时继续加载下一页，不要求首次取得全部记录。
- 保持现有排序（最近更新优先）、状态筛选、卡片内容和进入编辑页行为不变。
- 不在本次变更中改变食谱编辑、发布、复制或删除业务规则。

## 方案

### 轻量列表接口

`GET /api/v1/recipe-designer/series` 增加可选查询参数：

- `page`：从 1 开始，默认 1。
- `pageSize`：默认 20，最大 50。

返回格式改为 `{ items, page, pageSize, hasMore }`。未传分页参数的调用也使用默认分页，避免旧调用再次取得全量记录。状态筛选直接下推到系列的 `businessStatus` 查询条件，仍按 `updatedAt desc` 排序。

每个系列仅选择构建卡片所需字段。草稿选择阶段、状态、发布时间、更新时间、场景、客户狗 ID、合规标志和原料数量；不读取每一条原料、营养数据或评估 JSON。关联已发布食谱选择阶段、状态、更新时间及卡片所需标识；不读取原料与营养详情。阶段是否“已修改”用草稿原料数量替代原料数组长度，修订草稿的有效性判断保留其需要的摘要字段。

### 小程序渐进加载

列表页首次显示时重置页码并请求第 1 页；在 `onReachBottom` 中加载下一页并追加。加载期间不发起重复请求；`hasMore` 为否后不再请求。切换状态筛选、从新建／编辑／删除等流程返回列表时，重新从第 1 页加载，确保状态最新。

首次加载沿用当前“加载中”占位；加载下一页不遮挡已显示卡片，可在列表末尾显示简短的加载提示。客户模式的狗狗数据保持并行加载，不阻塞食谱系列首屏请求。

### 数据库索引

新增 Prisma migration，为活跃系列按创建人／业务状态／更新时间读取提供复合索引。索引以 `created_by, status, business_status, updated_at DESC` 为主，并保留现有单列索引；客户系列使用同一可见性规则。

## 错误处理与兼容性

- 页码或页大小非法时由 DTO 校验拒绝；页大小上限固定为 50，防止误用恢复全量查询。
- 接口请求失败时，首屏保留现有错误提示；追加页失败时保留已加载数据并允许再次触底重试。
- API 客户端和页面同时适配分页响应；列表中已有的数组响应兜底保留，避免渐进部署期间空白。

## 测试与验收

- 后端单元测试：默认分页、页码偏移、`hasMore`、状态筛选下推、轻量选择字段和卡片阶段状态保持正确。
- 小程序测试：默认携带第 1 页与页大小、追加下一页、无更多数据不再请求、筛选后重置列表。
- 执行后端相关测试和小程序 Vitest 回归；执行小程序微信构建，确保可在微信开发者工具中打开构建目录验证。

## 取舍

仅做客户端缓存无法减轻首次接口的数据库和传输负担；仅精简字段不能控制列表持续增长后的响应时长。轻量查询、数据库分页和前端追加加载共同保证首屏速度，并维持完整历史列表的可访问性。
