# AI 食谱设计 · 重置设计（2026-10-31）

> 状态：待老板确认后实施
> 范围：产品线（CATALOG）与订单定制（ORDER）共用的 Agent 内核，本次先落产品线
> 前置：[重置基线](2026-10-31-ai-recipe-design-reset-baseline.md)

---

## 1. 一句话原则

> **目标是唯一的约束，评估是唯一的裁判，只有不可逆的动作才需要人。**

对应 Codex / DSH 这类 Agent 的做法：约束"不能乱来"，不约束"怎么做"；
靠**快的反馈回路**自我纠正，而不是靠在每个岔路口设卡。

---

## 2. 为什么改（有数据）

| 现状 | 数值 |
|---|---|
| 平均每次设计工具调用 | 59 步（7 个会话 ≥ 90 步） |
| 平均每步输入 token | 21,958（输出仅 169） |
| 输入/输出比 | 161 : 1 |
| 单次 `get_ingredient` 最大返回 | 190,711 字符 |
| 平均每份配方问人 | 3 次 |
| 现有卡点 | 12 个 |

结论：**约束已经很多，效果反而差。** 成本主要花在"预取 + 重读"，不是"想"。

---

## 3. 六个环节：现在 vs 改成

| 环节 | 现在的做法 | 改成 | 卡点处置 | 工具变化 |
|---|---|---|---|---|
| ① 目的 | 不问目的直接搜料；或强制走 9 项简报 | 说一句就记下、开工；没说只问一句"这份是为什么做的" | 删：简报 9 项、阶段确认、参考犬确认 | `set_copy` 增加 `designPurpose` |
| ② 选料 | 铺满 11 类候选 → 强制确认 → 才允许写 | 按目的推主蛋白 → 只查这一步要用的料 → 直接写 | 删：11 类铺满、逐类说明、候选确认 | `get_ingredient` 瘦身；`search_ingredients` 默认精简 |
| ③ 配方 | 写骨架 → 评估 → 调，但被"必须覆盖 11 类"绑架 | 写 → 评估 → 改，循环到通过 | 删：缺类解释、缺类例外 | `run_assessment` 只回缺口 + 覆盖度 |
| ④ 文案 | 单独一轮，写完等人判断好坏 | 配方定了顺手写，合规扫描当裁判 | 删：文案必须人判 | `set_copy` 保留，合规结果并入评估 |
| ⑤ 自检 | `check_ready` 单独跑，20 条门槛，AI 说"可以了" | 评估通过 = 可以交；上架门槛只在人点发布时算 | 删：AI 侧 20 条门槛、`check_ready` 工具 | 合并进 `run_assessment` |
| ⑥ 交付 | AI 不发布，人点；封面另走一条 | 不变：发布 / 改价 / 例外，三个人工口 | **留 3 个** | 删除 `finish_draft` |

---

## 4. 删掉的 9 个卡点

1. 9 项设计简报
2. 阶段 / 参考犬二次确认
3. 11 类候选铺满
4. 逐类"缺口说明"
5. 候选清单强制确认
6. 缺类申请例外
7. 成本 / 价格带确认
8. 文案必须人判
9. AI 侧 20 条发布门槛 + `check_ready`

## 5. 保留的 3 个（全部不可逆）

| 动作 | 为什么必须人 |
|---|---|
| 发布 / 上架 | 顾客能看见，撤不回 |
| 改价 / 定价 | 碰到钱 |
| 达标例外 | 让不合规配方过关，责任在人 |

---

## 6. 工具清单：22 → 20

| 处置 | 工具 | 说明 |
|---|---|---|
| 删 | `finish_draft` | 旧版遗留，2026-10-27 已下线，仅历史数据有 6 次调用 |
| 合并 | `check_ready` | 并入 `run_assessment`：一个裁判，一个入口 |
| 瘦身 | `get_ingredient` | 默认只回：名称、分类、关键营养（蛋白/脂肪/钙/磷）、过敏原、单价。**详情按需展开** |
| 瘦身 | `search_ingredients` | 默认每条只回：名称、分类、关键 3 项营养、单价；不返回全部营养档案 |
| 瘦身 | `run_assessment` | 默认只回：通过/不通过、缺口列表（营养素 + 差多少）、覆盖度。不再回全量 100 条明细 |
| 瘦身 | `get_draft` | 默认回摘要（目的、阶段、原料条数、上次评估结论），原料明细按需 |
| 保留 | 其余 16 个 | 不改语义 |

**新增字段**：`design_recipe.design_purpose`（varchar 200）。
作用等同 Codex 的 TODO 文件——不是卡点，是把话记在纸上，换人接手也看得懂。

## 7. 上下文治理（治"30 步就忘"）

| 问题 | 处置 |
|---|---|
| 单条工具结果最大 19 万字符 | 瘦身后单条目标 ≤ 4,000 字符 |
| 一次运行工具预算 200 次 | 降到 60 次（评估循环足够跑完；现在平均 59 步，大部分消耗在预取） |
| 历史只留 10 万字符且从最旧丢 | 瘦身后很少触顶；先把上限提到 20 万字符，观察一周 |
| 单次请求超时 180 秒 | 降到 90 秒 |

---

## 8. 新提示词目标

从 **3,706 字** 压到 **1,000 字以内**，只留四段：

1. 你的目标（把目的变成一份能过评估的配方）
2. 工具怎么用（一句话一个：取数的先摘要、要细节再展开）
3. 评估是唯一裁判（改完就跑，跑到通过或确实做不到为止）
4. 三件事必须问人（发布、改价、例外）

删掉：11 类清单、候选确认流程、缺类说明、补剂换算细则（移入工具返回）、时令与联网规则（保留一句"需要时查，注明来源"）。

---

## 9. 验收标准

1. 拿 3 份真实草稿（含 1 份订单定制）跑完整流程；
2. 工具调用步数 ≤ 35，问人次数 ≤ 1；
3. 评估结论与现在一致或更好（同一份草稿，缺口数量不增加）；
4. 单会话输入 token 从百万级降到十万级；
5. 发布 / 改价 / 例外三个人工口仍然拦得住。

---

## 10. 不做的事（本次明确排除）

- 不做配置平台 / 资产层（提示词、工具仍随代码发布）；
- 不动封面、文案、命名、健康、原料各模块的配置；
- 不删历史会话与草稿；
- 不改评估引擎的算法与 FEDIAF 数值。
