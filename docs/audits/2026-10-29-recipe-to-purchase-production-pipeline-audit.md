# 从配方到采购、生产、车间展示：全链路审计

- 日期：2026-10-29
- 范围：配方编辑器 → 食谱保存 → 下单定价 → 采购 → 排产 → 每锅用料 → 小程序采购/生产板块 → 打印
- 方法：读实现 + 用真实单据反推（SK20261028-002 等三单）+ 两条链路数字交叉对账
- 结论标注：✅ 一致 / ⚠️ 有风险 / ❌ 已确认有问题

---

## 0. 一页纸

### 链路

```
设计稿(克数)                      ← 编辑器逐项保存
   │ 发布（三条路径，算法不同）
   ▼
食谱(百分比 + 每kg补剂浓度)        ← 冻结
   │ 下单
   ├──► 价格快照（净/毛/采购三种用量 + 金额）
   └──► 配方快照（每样克数 + 百分比 + 补剂浓度）
          │
          ├──► 采购单：从「价格快照」取数，按缺口采购
          └──► 排产：从「配方快照」复制，按总重分锅
                 │
                 ├──► 制作单（小程序前端算：投料重量 × 百分比）
                 └──► 完工记账（后端另算一遍）→ 扣库存
```

### 五个结构性问题

| # | 问题 | 后果 |
|---|---|---|
| 1 | 派生值被存多份（总重、配比、补剂浓度、净/毛用量），刷新时机各不相同 | 数据漂移（10-28 事故） |
| 2 | 同一条算法多处实现（配比 5 处、用量 3 处） | 口径分叉，改一处漏四处 |
| 3 | 三条发布路径规则不一致（产品线归一、定制不归一、后台表单无护栏） | 同类事故会从不同入口复发 |
| 4 | 前端算展示、后端算记账，互不校验 | 错了也"一致地错"，只有采购是对的 |
| 5 | 没有"快照已落后于当前配方"的状态与校验 | 误以为改食谱会改订单 |

### 修复优先级（详见第 9 节）

- **P0（止血）**：定制快照改用克数/评估总重；制作单统一从克数推导；打印 PDF 不再吃前端数字
- **P1（内核）**：一个"配方用量"计算模块，定价/采购/制作/扣库存共用；总量改为派生；**锅快照改为引用**；重做单走内核
- **P2（护栏）**：发布与排产前校验、快照落后标记、采购只认 PAID 的边界

## 1. 配方保存

### 1.1 三种载体

| 载体 | 表 | 何时产生 | 存什么 | 可变性 |
|---|---|---|---|---|
| 设计稿 | `design_recipe` / `design_recipe_item` | 编辑器建草稿 | **克数**（唯一真源）、预处理、补剂目标、制作步骤、文案；另有评估缓存（总重/能量/评估版本号） | 可改，每次修改 `contentRevision +1` |
| 正式食谱 | `recipe` / `recipe_item` | 发布时 | `ratio_percent`、`example_weight`、`supplement_targets`、营养报告 | 不可改，改动走新版本 |
| 订单快照 | `order_item.recipe_snapshot` | 下单时 | 该单所用食谱的完整副本（含每样克数与百分比） | 不可改 |
| 锅快照 | `packaging_unit.recipe_snapshot` | 排产时 | 从订单快照再复制一份 | 不可改 |

### 1.2 编辑器保存机制

| 动作 | 写入 | 副作用 |
|---|---|---|
| 加原料 / 改克数 / 换原料 / 改预处理 / 调顺序 | 仅原料行 | `contentRevision +1` |
| 改文案、展示图 | 草稿行 | `contentRevision +1` |
| 营养评估（面板） | **不写库** | 只把结果算给页面看 |
| 跑评估（后台/助手） | 草稿行的评估缓存 | 更新总重、能量密度、营养数据、`assessmentContentRevision` |

结论：**草稿的"总重"是上一次评估时的快照，不是实时合计**；配比在设计稿里根本不存（`ratio_percent` 通常为空）。

### 1.3 三条发布路径（算法不同）

| 路径 | 入口 | 食材配比 | 补剂浓度 | 结论 |
|---|---|---|---|---|
| 产品线发布 | 配方设计器「发布」 | 有效克数 ÷ 食材有效克数合计（自动归一 100%） | 营养量 ÷ **本次评估总重** | ✅ |
| 定制快照 | 订单「加入待提交」/ 生成私密食谱 | 克数 ÷ **草稿缓存总重** | 营养量 ÷ **草稿缓存总重** | ❌ 10-28 事故 |
| 后台食谱表单 | 后台新建/编辑食谱 | 直接保存录入的百分比，不归一 | 直接保存 | ⚠️ 无护栏 |

三条路径共用同一张 `recipe` 表，仅 `status` 不同（PUBLIC / PRIVATE_CUSTOM / DRAFT），因此口径差异不易暴露。

### 1.4 状态与版本

- 草稿：`DRAFT → COMPLIANT / NEEDS_REVIEW → PUBLISHED`，记住 `published_recipe_id + version`
- 正式食谱：发布先落 `DRAFT`，系列「上线」时转 `PUBLIC`
- 定制快照：直接 `PRIVATE_CUSTOM`，固定 `version 1`（recipe_id = 草稿 id）
- 产品线：`recipe_id + version` 多版本；定制快照按草稿 id 生成

## 2. 下单与定价快照

### 2.1 输入与输出

- 输入：食谱（含 items）、总净重（`quantityG`）、包装方案、狗狗餐数、全局配置
- 输出：`order.pricing_breakdown_snapshot`（一份，含 `ingredientDetails`）
- 代码：`PricingService.calculateOrderPrice` / `calculateRecipeCost`

### 2.2 计算步骤

1. **起订量校验**：净重 < `minOrderWeightG` 直接拒绝
2. **物理量**：`投料毛重 = 净重/1000 × 配方损耗率`
3. **食材**（逐样）：
   - 归一配比 `r' = r ÷ Σ食材配比 × 100`（仅定价内部做）
   - 净需求 `N = 净重 × r'`
   - **成本用量（毛需求）** `G = N ÷ 出成率 × 损耗率` ← 采购单用的就是它
   - 采购用量（只含损耗，不含出成率） `P = N × 损耗率` ← **FOOD 实际不用**
   - 成本 `= G × 单价`
4. **补剂**：`剂量 = (目标值/kg × 净重kg) ÷ 浓度 × 补剂自身损耗`；`amount = purchaseAmount = 剂量`
5. **包材**：按包装方案（袋/标签/冰袋/箱）逐项计价
6. **人工**：`投料毛重 × (时薪 × 单批工时 ÷ 标准批次产量)`
7. **制造费**：`投料毛重 × 每kg间接成本`
8. **售价**：`总成本 ÷ (1 − 目标毛利率)`；运费单独算
9. **冻结**：金额 + `ingredientDetails`（`netAmount` / `amount` / `purchaseAmount`）

### 2.3 已知问题

| 级别 | 问题 |
|---|---|
| ⚠️ | 订单只支持单条（购物车已移除），价格快照只覆盖第一条；未来多品单需要重做 |
| ⚠️ | 同一原料存了三个用量口径，下游各取所需，容易取错 |
| ⚠️ | 归一化只在定价内部发生，不回写食谱；谁绕过定价谁就拿到没归一的数 |
| ℹ️ | 价格快照不引用配方快照，两份各冻各的——这是"采购对、制作单错"的结构性原因 |

## 3. 采购

### 3.1 触发与取数

- 触发：小程序/后台「生成采购单」（可先预览）
- 取数：`target_production_date` 在范围内、状态 = `PAID` 的订单 → `pricing_breakdown_snapshot.ingredientDetails`
- 前置校验：同一天已有待采购清单则必须续用（防重复采购）；已有已完成清单则生成**增量**清单

### 3.2 算法

1. 按 `(ingredientId, procurementSkuId)` 聚合
2. 取量：FOOD → `amount`（毛，含出成率+损耗）；其他 → `purchaseAmount`
3. 库存抵扣：按原料可用量依次抵扣；抵扣部分成本归零
4. 缺口：`gross − 抵扣`，换算成单据单位
5. 预估成本：`单价 × 缺口`
6. 落单：单头（制作日期中午 12 点、来源订单、订单日期快照）+ 明细
7. 联动：订单 `PAID → PURCHASING`；写库存预留（`ACTIVE`）

### 3.3 实际采购

- 车间按包装录入（件数 × 规格 → 基础量），写 `purchase_record` 与库存流水
- 可标记"不需采购"、可完成/重开、可删除

### 3.4 已知问题

| 级别 | 问题 |
|---|---|
| ⚠️ | 只查 `PAID`；当天已转 `PURCHASING` 的订单要靠"追加订单"接口补 |
| ⚠️ | 实际采购量不回写需求侧，计划与实采两套数 |
| ⚠️ | **重做单（0 元单）没有价格快照**，采购计算会跳过它，但它照样会被排产——原料需求会漏（目前线上还没有重做单，属潜在风险） |
| ℹ️ | 采购对"总重过期"免疫，因为它内部归一到 100%（\(r/Σr\) 把过期分母约掉了） |

## 4. 排产

### 4.1 触发与前置

- 触发：小程序「自动排单」（后台亦可创建批次）
- 前置：当天采购清单存在且**已完成**
- 取数：状态 `PURCHASING`、当天制作日期、条目未分配批次（`production_batch_id = null`）、有 `dailyIntakeG`

### 4.2 算法

1. **分组**：按（配方快照 id + 采购来源方案 + 配方明细签名）分组；版本号不在键里，但明细签名不同会自然分开
2. **生重**：`订单条目净重 × 配方损耗率`
3. **分锅**：单锅容量 = `defaultBatchCapacityG`，允许 5% 溢出；FIFO 装填，**订单条目可拆分**到多口锅（同一批次内）
4. **锅净重** = `min(容量 × 1.05, 剩余生重 ÷ 损耗率)`
5. **最小锅重优化**：最后一锅 < `minPotWeightG`（默认 2000g）时，从前锅匀重
6. **完整性校验**：每锅分配生重之和 = 净重 × 损耗率（±1g），否则报错
7. **落库**：批次 + 锅（复制配方快照、记录来源条目）+ 条目挂批次；订单 → `IN_PRODUCTION`

### 4.3 已知问题

| 级别 | 问题 |
|---|---|
| ⚠️ | 分锅只看总重，不看原料粒度（不影响正确性，影响凑锅效率） |
| ⚠️ | 锅快照是复制；上游修了食谱不会同步到已排产的锅（必须重排） |
| ℹ️ | 一个条目被拆到多口锅时，`source_order_item_ids` 会同时出现在多口锅 |

## 5. 每锅用料

### 5.1 展示（小程序前端）

```
投料毛重 = 锅净重 × 配方损耗率
食材用量 = 投料毛重 × 配比%
补剂用量 = (目标值/kg × 投料毛重kg) ÷ 浓度 × 补剂损耗
```

实现位置：车间详情、打印页、批量打印、顾客订单详情（各写一遍）。

### 5.2 记账（后端，完工时）

- 同一公式（`calculateProductionUsage`）
- 生成 `ingredients_usage_snapshot`（`required_g = actual_g`，只记理论量）
- 由开关 `autoDeductInventoryOnProduction` 决定是否扣库存（默认关）

### 5.3 已知问题

| 级别 | 问题 |
|---|---|
| ❌ | 展示与记账是两套实现，都直接乘存着的配比 → 不归一时一致地错 |
| ❌ | 打印 PDF 的用量由前端算好后传给后端，后端只负责渲染 |
| ⚠️ | 补剂剂量口径：前端把"配方损耗率"乘进了基准重量，后端与成本用"补剂自身损耗率"，两者差 0–3% |
| ⚠️ | 完工只报"正常/超出/短缺"，不采集逐样实际用量，账实差异只能靠锅级 surplus/shortage |

## 10. 目标形态（第 2 阶段设计）

### 10.1 一句话原则

**一份含量表，各处只存差额。**

### 10.2 四层数据：现在 vs 目标

| 层 | 现在 | 目标 |
|---|---|---|
| 配方 | 设计稿（克数）→ 食谱（百分比，分母可能过期） | 不变；发布时百分比由克数推导，并把"克数合计"一起存下 |
| 订单 | 配方快照 + 价格快照，两份各冻各的 | 订单只存**一份含量表**（每样克数 + 归一分比 + 补剂目标）；价格快照引用它，只加"钱"的部分 |
| 采购 | 从价格快照取毛用量 | 仍取毛用量，但毛用量来自含量表，不从定价内部另算 |
| 锅 | 复制整份配方 | 只存三样：引用哪张订单、锅净重、分到哪些条目/各多少克 |

### 10.3 含量表包含什么（业务描述）

- 每样食材：克数、食材内占比、每 kg 成品用量、下锅毛重
- 每样补剂：每 kg 目标、单锅剂量
- 一行合计：食材合计、锅净重、投料毛重（用于校验）

### 10.4 各环节从含量表里取什么

| 环节 | 取 | 再加 |
|---|---|---|
| 定价 | 净用量 | 出成率、单价、人工、制造费、毛利 |
| 采购 | 净用量 | 出成率、损耗、库存抵扣 |
| 车间/打印 | 下锅毛重、补剂剂量 | 无 |
| 完工记账 | 下锅毛重 | 无（与展示同源） |

### 10.5 锅为什么改成引用

- 昨天已经证明：修了订单快照，锅不跟，只能重排；
- 一口锅的配方内容 = 订单快照，重复存一份没有新增信息；
- 锅真正独有的只有三样：净重、分到哪些订单条目、每个条目分多少克。

### 10.6 重做单怎么办

- 重做单是 0 元单，没有价格快照，但有配方快照；
- 内核可以直接从配方快照算出含量表，采购与排产都能用；
- 这样重做单不再挂在"价格"这一层上，也顺手补掉"采购漏算重做单"的坑。

### 10.7 迁移与灰度

1. 内核先以纯函数落地，先给制作单与扣库存用（不动表结构）
2. 订单快照增加"归一分比"（旧单不动，新单写入）
3. 锅新增"引用哪张订单快照"的标记，同时保留旧字段；读取优先引用、回退旧字段
4. 价格快照增加"含量表指纹"，用于核对
5. 灰度两周后，删除旧字段与前端公式

### 10.8 验收标准（可量化）

- 同一锅：车间显示 = 完工记账 = 扣库存，误差 < 0.1g
- 同一原料：采购量 ÷ 出成率 ≈ 制作单用量（差 ≤ 5%，且只剩出成率一个原因）
- 任取一份"配比合计 ≠ 100%"的食谱走全链路，三个数仍一致
- 打印 PDF 与车间页面逐行一致
