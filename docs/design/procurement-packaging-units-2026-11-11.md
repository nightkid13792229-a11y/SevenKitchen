# 采购商品「包装层级 ↔ 单位」口径统一 方案

> 2026-11-11 · 起因：小程序「新增采购商品」里选了「份」看不出选中；AI 读出字典外的单位会被静默丢掉。
> 结论先写在最前：这不是两个小 bug，是**四份单位清单 + 一个被折叠掉的包装结构**，必须收成一份才能根治。

---

## 0. 一句话结论

采购单位、包装层级、换算倍数现在是**三个各说各话的字段**，而真正进库存的只有折叠后的一个数字。
本方案把它们收成**一个结构（包装层级）+ 一份字典（单位）**：

- 采购单位 = 包装层级的第一层，只能从字典里选；
- 换算倍数 = 层级的连乘，**服务端算，任何人不手填**；
- 单位字典只有一份（后台可维护），小程序、后台、AI 识别都读它。

---

## 1. 你看到的现象，直接原因是什么

### 1.1 「份」看不出选中

「我买的是」默认只显示 **5 个**，第 6 个起收进「更多」。这道原料（白萝卜，按克记账）能选的是 7 个，顺序是：

> 袋 箱 包 瓶 盒 **桶 份**

前 5 个正好是截图上的「袋 箱 包 瓶 盒」，「桶」和「份」都在折叠区里。AI 识别成「份」时，表单里**其实已经选中了**，只是那一格看不见 —— 员工以为没填，随手点「袋」，正确的单位就被覆盖了。

**同样的坑在渠道那一行早就修过**（2026-11-07）：渠道被折叠时会把它提到第一个，保证“选了什么一定看得见”。单位这一行漏了同样的处理。

### 1.2 更隐蔽的一种：单位看不见，却能保存

后台白名单里还有「斤、两、公斤、克」这些**计量单位**，但前端只显示“包装单位”，把它们藏了起来。
如果 AI 读出「斤」（农贸市场按斤买白萝卜太常见了），会发生：

1. 表单校验拿的是**完整白名单**，不是“看得见的 5 个” → 校验通过；
2. 屏幕上没有任何一个选项是亮的 → 员工以为没选；
3. 保存成功，账里记的是“3 斤”。

这种情况比报错危险：**数字是对的，单位是员工没看见、也没机会选的。**

### 1.3 字典外的单位：静默丢失

AI 读出「提」「组」「捆」这类字典里没有的单位时，前端会把整个单位**丢掉**，不留任何痕迹。
于是员工看到的是：商品名填好了、规格填好了、单位空着，只弹一句“还有必填项没填”——而**这一行根本没有红框**（全表单只有商品名和净含量会标红）。

### 1.4 为什么“包装层级”帮不上忙

11 月 9 日上线的「规格链」确实解决了“30 枚 1.59 千克被当成每枚 1590 克”的问题，但它和「我买的是」是**两套逻辑**：

- 规格链：层数和层单位**自由填**，什么词都行（枚、张、捆、提）；
- 我买的是：从**白名单**里选，而且只显示 5 个。

两者之间没有任何校验。于是可以出现“上面选袋、下面写‘一箱 = 10 捆’”这样自相矛盾的组合。

## 2. 根因：四份清单 + 一个被折叠的结构

把代码里所有“单位从哪来”列出来，一共**四份完整清单**（另有两处“展示子集”），互不同步：

| # | 位置 | 内容 | 谁在用 |
|---|---|---|---|
| 1 | 后端常量（`ALLOWED_PURCHASE_UNITS_BY_BASE_UNIT`） | 按克/毫升/个分三组，共 20/9/14 项 | 保存校验、表单选项接口、成本折算 |
| 2 | 后台页面常量（`procurementPurchaseUnits.ts`） | 同一份内容**抄了一遍** | 后台「编辑采购商品」的下拉 |
| 3 | 后台原料表单内联（`IngredientForm.vue:1868-1911`） | **又抄了一遍** | 后台「原料档案里加/改采购商品」的弹窗 |
| 4 | 小程序识别结果页（`UNIT_OPTIONS`） | `袋 盒 份 包 瓶 个 组 罐` + 斤/公斤/克/两 | 采购记录的数量单位 |

两处展示子集：小程序新建页只显示“包装单位”（`CLERK_UNIT_PRIORITY`，含白名单里没有的「提」「件」），以及“整件”判断表（`MULTIPACK_UNITS`）。

第 4 份最危险：它里面有「组」（四份清单都没有）、有「份」（按个记账的原料没有），而**换算永远用商品的倍数**，不看这行写的什么单位。于是“3 份”会被按“3 盒”乘一遍。

再看“结构”：

- 采购商品表里**没有**层数字段，只有 `purchase_unit` + `purchase_to_base_ratio` + 一段规格文本；
- 规格链只活在页面上，保存时被**折叠成一个倍数**，中间层（10 捆）从此消失；
- 后台编辑又能**直接改这个倍数**，和单位、和规格文本三者互不校验；
- 采购商品有 **5 个写入点**，其中 2 个（AI 原料建档、标准原料导入）绕过服务层直接写库。

一句话：**上游有四份清单和一个会被折叠的结构，下游只有一个数字。任何一处对不上，库存、成本、补货、食谱成本都会按倍数错，而且不报错。**

## 3. 目标模型

### 3.1 唯一事实：一条包装层级

采购商品上存一个结构化字段 `packaging`（JSON），形如：

```json
{
  "links": [{ "count": 10, "unit": "捆" }],
  "amount": 2500,
  "amountUnit": "G",
  "amountLabel": "克",
  "printedText": "10捆×500g"
}
```

- `links`：中间层，**可以为空**；每层是“数量 + 单位”，只用于展示和录入，**不参与换算**以外的任何判断；
- `amount`：最后一层，**永远用原料的基准单位**（克 / 毫升 / 个）表示；
- `printedText`：包装原文，订单截图匹配用（保留现状，不参与换算）。

派生规则（唯一实现，服务端）：

```
换算倍数 ratio = links 连乘 × amount
采购单位 purchaseUnit = 单独一列（字典里的一项），编辑时和 links/amount 一起提交、一起校验
```

为什么采购单位不塞进 JSON：它要参与查询、要去重、要进历史快照，放列里更稳；但它**不再是可单独编辑的字段**——保存时和层级一起校验，不能出现“单位是盒、层级是袋”的组合。

### 3.2 单位字典（一份，后台可维护）

复用现有的「选项字典」设施（`platform_option_set` + `platform_option_item`，和采购渠道一模一样）：

- 新选项集：`purchase_unit`（名称「采购单位」）；
- 每一项的 `extra` 带上四个信息：
  - `baseUnits`：这道单位适用于哪些基准单位（`G` / `ML` / `PCS`）；
  - `aliases`：别名（`公斤`、`千克` → `kg`；`升` → `L`；`个`/`只` 互认）；
  - `kind`：`PACKAGING`（袋/盒/箱…，员工默认看到的）或 `MEASUREMENT`（g/kg/斤/两/吨/ml/L，收在「更多」里的第二组）；
  - `multipack`：这个单位是不是“整件”（箱/桶/提/件/组），决定要不要逼员工补一层。

`kind` 解决的是 P0-3：计量单位不再“后台允许、前端消失”，而是**明确作为第二组出现在「更多」里**；AI 或老数据选中了「斤」，它会被提到第一位显示出来，员工看得见、改得掉。

好处：

1. 四份硬编码变成一份数据，**后台加一个单位不用发版**；
2. “整件”的判断也跟着字典走（现在前后端各写死一份 `['箱','桶','提','件']`，而「提」「件」根本不在白名单里，等于这两条规则永远不会触发）；
3. AI 识别可以把这份清单直接喂给模型，从源头减少“字典外单位”。

### 3.3 三端一致

| 场景 | 现在 | 之后 |
|---|---|---|
| 小程序「我买的是」 | 前端白名单 ∩ 前 5 个 | 字典（按原料基准单位过滤）：包装单位在前，计量单位收在「更多」第二组；**选中项永远可见**；有红框和提示 |
| 小程序「一份的规格」 | 自由文本层单位 + 基准数量 | 层单位从小词典选（可手填），最后一层单位**锁定**为基准单位，倍数实时算 |
| 后台编辑 | 单位下拉 + 倍数手填 + 规格自由文本 | 和员工端**同一套层级编辑器**；倍数只读；改层级自动带出倍数 |
| AI 识别 | 单位随便给，前端静默丢 | 提示词带字典清单；给出字典外单位时**保留原文作提示**，让员工明确选一个 |
| 采购记录 | 数量单位自由，永远按商品倍数折算 | 有商品时数量单位**锁定为商品单位**；不一致直接拦住并说明原因 |

## 5. 修复策略（按能独立上线切四段）

### 阶段 0 —— 止血（半天到一天，只改小程序前端 + 两条服务端校验）

1. 选中的单位**永远可见**（复用渠道那个“提到第一位”的做法）；
2. 「我买的是」补红框 + 一句人话提示；单位行补「AI 识别」标记；清单加载失败时明说原因；
3. **去掉“进页面就默认选袋”**：AI 没读出单位就留空并提示，而不是悄悄按袋记 10 倍；
4. 字典外单位不再静默丢：保留原文，在该行下面显示“AI 读到「X」，请选一个最接近的”；
5. 服务端加一条校验：保存时 `purchaseUnit` 必须属于字典（防止看不见的单位被存进去）；
6. 采购记录/补货行加一条“单位必须与商品单位一致”的拦截（服务端为主，前端同步提示）。

> 阶段 0 不需要改数据库，当天可上线，先把“看不见 / 找不到 / 被默认值顶替”消掉。

### 阶段 1 —— 一份字典（后端 + 后台，2~3 天）

1. 建选项集 `purchase_unit`（迁移 + 种子，内容 = 现有三组白名单 + 补齐 提/件/组）；
2. 后端加 `PurchaseUnitCatalog`（读字典、带缓存、带别名归一），白名单常量降级为“字典为空时的兜底”；
3. 后台编辑页改用字典接口，删掉 `procurementPurchaseUnits.ts`；
4. AI 提示词带上“这道原料允许的单位清单”。

### 阶段 2 —— 一条层级（后端 + 三端 UI，4~5 天，核心）

1. `procurement_sku.packaging` 字段 + 迁移回填（老数据 = `links:[]`、`amount: 原倍数`，无损）；
2. 纯函数 `derivePackaging()` / `validatePackaging()`（连乘、末层必须是基准单位、层单位长度、整件必须有层）；
3. 新建/编辑/员工新增三个入口**都收层级**，服务端统一派生倍数与单位；老的 `packCount + netContentPerPack` 继续兼容一年；
4. 员工端与后台共用同一套层级编辑器（后台只读倍数）；
5. 列表/详情/单据的规格文案一律由层级渲染，`productModel` 只做“包装原文”。

### 阶段 3 —— 全链路对账（3~4 天）

1. 采购记录：有商品时数量单位锁定为商品单位，不一致前端拦住 + 服务端 400；
2. 识别结果页的单位清单换成“商品单位 + 计量单位”两类，删掉第四份硬编码；
3. 补货/采购清单去掉“兜底成基准单位”的写法；
4. 改倍数时重算原料成本（或明确提示“成本未变，需重新结算”）；
5. 加一个巡检脚本：倍数与层级不符、单位不在字典、`productModel` 与层级明显矛盾 —— 输出清单给管理员，不做自动改。

## 6. 数据迁移与兼容

- **回填规则**：`packaging = { links: [], amount: purchase_to_base_ratio, amountUnit: <原料基准单位>, printedText: product_model }`。老数据的倍数原样保留，回填**不改变任何金额和库存**。
- **字典必须先覆盖历史值**：现有单位校验对“字典外的值”是**直接 400**（编辑即报错）。所以迁移顺序必须是「先统计库里出现过的所有采购单位 → 全部灌进字典（停用的历史项也留着）→ 再打开校验」，否则一批老商品会突然变成不可编辑。这一步照抄渠道字典当时的三段迁移（建集 / 回填 / 停用项保留）。
- **兼容期**：接口同时接受旧字段（`packCount` + `netContentPerPack`）和新字段（`packaging`），服务端折叠成同一份；旧版小程序不强制升级。
- **不做物理删除**：停用的单位、停用的商品都保留，历史单据继续能打开。
- **可回滚**：新字段为可空；回滚只需不使用它，不改动既有列。

## 7. 验收标准（业务可验收，逐条对应上面的问题）

1. 新建「箱 = 10 捆 × 500 克」，保存后后台看到的也是「1 箱 = 10 捆 × 500 克」，不是 5000 克一个数字。
2. 采购 3 箱 → 库存增加 15000 克，单价折算正确。
3. 选「份」（排第 9 个）时，芯片行**一定**能看到它亮着，不点「更多」也能看见。
4. AI 读出「提」时，页面显示“AI 读到「提」，请选一个”，而不是一片空白。
5. 后台把单位从「盒」改成「箱」但倍数不改 → 保存被拒，并说明原因。
6. 识别结果页把单位偷偷改成「份」（商品是盒）→ 生成前就被拦住，说明“这行写的是份，商品是按盒买的”。
7. 管理员在后台新增一个单位（例如「挂」），小程序和 AI 立刻能选到，不用发版。
8. 进「新增采购商品」页时**不默认选中「袋」**；AI 没读出单位就留空并提示，员工必须自己选一次。
9. 补货记录里把单位写成「克」→ 不会再按“1 件 = 1 克”入账，商品倍数照旧生效。
10. 后台用 AI 建档的原料，采购商品有规格文本、单位在字典里，且进后台能正常编辑（不再一改就 400）。
11. 巡检脚本在测试库上跑出 0 条“倍数与层级不符”、0 条“单位不在字典”。

## 8. 取舍（为什么这样设计）

| 选择 | 理由 | 什么时候要改 |
|---|---|---|
| 层级存 JSON，不建子表 | 层级永远整体编辑、没有独立生命周期；JSON 避免多 3 个文件和一次联表 | 将来要做“拆箱/分装、按层记库存”时再拆表 |
| 倍数仍然落库 | 库存、成本、补货几十处都在读它，实时连乘会把风险扩散到每条查询 | 保持“落库 + 服务端唯一写入 + 巡检” |
| `productModel` 保留 | 订单截图匹配靠它（“1.59kg(30枚)”这种写法） | 匹配逻辑改用结构化字段后再评估 |
| 采购单位单独一列 | 要参与查询、判重、历史快照 | 不变 |
| 不删除停用单位/商品 | 历史单据要能打开 | 不变 |

---

## 9. 明确不做（本期范围外）

- 不做“多单位库存”（同一原料同时按箱和按克记两本账）；
- 不做拆箱/分装业务（买一箱、拆成小袋入库）；
- 不改补货算法本身，只统一它的单位口径；
- 不动生产投料的“克”口径（只要倍数对，生产侧天然一致）。
