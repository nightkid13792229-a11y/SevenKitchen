# 库存管理改版 Implementation Plan（v2 · 按独立审核修订）

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 让「采购入库 − 生产扣料 = 账面库存」成立，且每笔变动有来源、有经手人、可复核；本次修订先修掉 5 处会把账记错的设计，再按批次上线。

**Architecture:** 四个批次，每批独立可上线。A 批只动记账口径与期初；B 批补留痕、门禁与开关；C 批做盘点状态机、复核与员工端；D 批做包材与在途净额。批次内任务按依赖排序，任务之间不共享未定义的类型。

**Tech Stack:** NestJS + Prisma(PostgreSQL) + Jest；uni-app(Vue3 小程序) + Vitest；admin-web(Vue3)。

## 这一版改了什么

| 审核结论 | 本版落在 | 怎么解决 |
|---|---|---|
| 撤回后再完成，库存永久少记 | A1 + A2 | 入库按「第几次」版本化；完成/撤回改成单事务；冲红只冲当前版本，再完成写新版本 |
| 「完工」改错入口、扣料失败被吞 | B2 | 改真实入口；扣料结果写进返回值和锅次；失败可补扣、可查 |
| 盘点「没数」表达不了 | C1 + C2 + C5 | 实盘数量可空 + 计数时刻；未盘不生成流水；结果页分开统计 |
| 驳回后重盘沿用旧账面 | C2 + C6 | 驳回即终态，只读；重盘 = 新建一张单，重新取账面 |
| 在途公式方向反了 | D4 | 在途只减「要买」，不减「可用」；先影子模式再开 |
| 复核两个后门 | C3 + C4 | 删掉「立即入账」参数和旧入账路由；后台补复核页 |
| 包材数量不在价格快照里 | D1 | 改读发货明细的「规格 + 袋数」，袋型复用现有选袋逻辑 |
| 采购这条没有操作人 | B1 | 采购单记「完成人 / 撤回人」；台账回查得到 |
| 首页按钮没落点、字段没排任务 | C8 | 新增 staff 专用首页接口；补货/流水做成一个抽屉，不再跳空页 |
| 一期默认值漏一处 | B4 | 三处兜底 + 默认配置 + 数据库列默认，一起改 |
| 手工排产门禁更松 | B3 | 和自动排单共用一段判断；没有清单也拦；force 只给管理员 |

## Global Constraints

- **一个任务一个工位**：`bash scripts/session.sh start "库存-A1-入库版本"`，分支 `task/日期-短名`；合并走 `session.sh merge`。主工作区只读。
- **结构变更只走 Prisma migration**：`cd backend && npx prisma migrate dev --name <snake_case>`；禁止手改库。
- **台账只增不删**：任何「撤回/作废」写负数行；禁止 `deleteMany` 台账。
- **数量一律落基准单位**（g / ml / pcs）；展示走 `miniapp/src/utils/staff-quantity.ts`，不在页面里自己拼单位。
- **不改订单成本口径**：`ProductionBatchCostSettlement.inventoryCost` 保持 0。
- **后端验证**：`cd backend && npx jest <path> --runInBand`；提交前 `npx tsc --noEmit`。
- **小程序验证**：`cd miniapp && npm run build:mp-weixin`（联调用 `npm run preview`）；**不上传正式版**，只走 `bash scripts/upload-trial.sh`。
- **员工端 UI**：深绿 `#1E3A2F` 导航、页面内不写大标题、最小 24rpx、选中态深绿底米白字（`docs/员工端UI规范.md`）。
- **每个任务一个提交**，提交信息 `feat(inventory): ...` / `fix(inventory): ...`；一个提交只含本任务的文件。
- **测试先红后绿**：测试必须因为「行为不对」而红，不能因为「测试环境没搭好」而红（见 A1 的说明）。

## Review Focus

这五类输入/场景没有任何一个任务的默认测试会覆盖，但最可能在上线后咬人。每条都已经挂到具体任务的测试里。

1. **撤回到再完成之间改了采购数量**：重入必须按新数量，账面不能被旧值卡住（A2）。
2. **盘点两小时里有人点了完工/发货**：账面基准必须是开单那一刻；未盘项不能当 0（C2/C5）。
3. **同一张盘点单被重复提交/复核**（双击、两个人同时点）：只能入账一次（C2）。
4. **发货时箱型对应的保温袋/冰袋不存在**：整票回滚，不能扣一半（D2）。
5. **在途量里混进已撤回的采购单**：不能算在途，否则少买（D4）。

## 分批上线

| 批次 | 内容 | 上线后能验收什么 | 窗口 |
|---|---|---|---|
| **A** | A1–A4 | 采购进出账、期初基线正确；扣料开关仍关 | 某天发货结束后，冻结 2 小时 |
| **B** | B1–B4 | 每笔能查到人；完工扣料可见；开关可安全打开 | 随 A 一起部署，开关在期初后手动开 |
| **C** | C1–C9 | 盘点可盲盘、可复核、可追责；首页可用 | 体验版先走一周，再发正式版 |
| **D** | D1–D5 | 包材自动扣；补货不重复下单 | 包材期初单独一次；净额先影子一周 |

**A+B 的上线窗口（写死）**：

1. 当天发货全部结束（约 17:30）后开始，群里说一声「开始盘点，别点完工/发货/完成采购」。
2. 部署后端（`bash backend/scripts/remote_deploy_v2.sh`），确认健康检查通过。
3. 跑 `npm run backfill:opening-stocktake -- --csv <文件>`（dry-run），人工核对：原料数 = 在用的全部原料数、总额与纸质盘点表一致、前 10 行抽查。
4. 加 `--apply` 写入；脚本打印「写入 N 行、期初单号 X」。
5. 后台打开「完工自动扣料」；用一张测试单走一遍「完工 → 流水里出现负数」。
6. 次日恢复采购/生产；一周内每天看一眼「负库存」和「未扣料锅次」。

> 这一版**不把「部署」和「期初」拆到两天**。部署后到开盘前，账只进不出，补货建议会归零；拆开就会少买。

- [ ] **Step 4: 改 `completePurchase`**

一个 `$transaction` 内按顺序：

1. `updateMany({ where: { id, status: 'PENDING' }, data: { status: 'COMPLETED', completedAt: now } })`；`count === 0` 直接抛「采购清单已完成或状态不允许」。
2. 读该单的 `purchaseRecords`（`inboundVersion`）。
3. 每条：`version = inboundVersion + 1`；写正数流水（`sourceVersion = version`）；`update inboundVersion = version`。
4. 数量 ≤ 0 的记录跳过（不写、不加版本）。

不要在事务外先 `purchaseList.complete()` 再写流水——现在的顺序就是「先入账、后校验」，双击时会先写后抛。

- [ ] **Step 5: 改 `reopenPurchaseList`**

一个 `$transaction` 内：

1. `updateMany({ where: { id, status: 'COMPLETED' }, data: { status: 'PENDING' } })`；`count === 0` 抛错。
2. 每条 `inboundVersion > 0` 的记录：**读该版本原来的入库流水**，按原金额取负写冲红（不能用采购记录上的当前数量——撤回后可能被改过）；`skipDuplicates` 防重。
3. `inboundVersion` **不变**（它是「第几次入库」的计数器，不是状态）。

**Interfaces:**
- Produces:
  - `startStocktake({ userId, note? }): Promise<InventoryStocktakeDto>` —— 建 DRAFT，按范围生成行，`countedQuantityG = null`，返回**盲盘 DTO**（无 expected/delta）；排序用 `lastCountedAt = 该原料历史盘点行的 max(countedAt)`，没有则分类 + 名称
  - `getDraft(userId): Promise<InventoryStocktakeDto | null>` —— 返回当前 DRAFT；别人的 DRAFT 不返回
  - `cancelDraft(id, userId): Promise<void>` —— 删除自己的 DRAFT（表头+行；此时还没有流水，删了不违反只增不删）；管理员可删任何人的
  - `saveStocktakeLines(id, lines: Array<{ ingredientId; countedQuantityG: number | null }>, userId)`
  - `previewStocktake(id, userId, opts?: { confirmPartial?: boolean }): Promise<InventoryStocktakePreviewDto>` —— **只算不写**：返回已盘/未盘、逐行 expected/counted/delta、容差内外；只允许 DRAFT；有未盘行且没传 `confirmPartial` → 400
  - `submitStocktake(id, userId, note?): Promise<InventoryStocktakeDto>`
  - `reviewStocktake(id, { approve: boolean; note?: string }, reviewerId): Promise<InventoryStocktakeDto>`
  - `isWithinTolerance(delta: number, expected: number, baseUnit: 'G'|'ML'|'PCS'): boolean` —— `Math.abs(delta) <= Math.max(Math.abs(expected) * 0.02, floor)`；floor：G/ML 50，PCS 2
- 规则：
  - **全局只允许一张 DRAFT**：自己已有 → 直接返回该单；别人有 → 409「已有未完成的盘点（提交人 / 时间）」。
  - 只有 DRAFT 可保存/提交；SUBMITTED 锁定；APPLIED/REJECTED 终态，再改返回 409。
  - 预览只允许 DRAFT；预览不写任何表；有未盘行时必须显式 `confirmPartial`（防止录到一半偷看账面）。
  - 提交时只处理 `countedQuantityG !== null` 的行；一行都没盘 → 400。
  - 全部在容差内 → APPLIED，并在本次事务里写流水；只要有一行超容差 → SUBMITTED，但**容差内的行照常入账**（这是设计，不是 bug；结果页要写清楚）。
  - 复核通过 → 把超容差行入账，APPLIED；驳回 → REJECTED，不写流水，必须填 note。
  - 入账沿用 `line.deltaG`，不重算。
  - 来源类型：`ROUTINE → STOCKTAKE`，`OPENING → OPENING_BALANCE`。

```sql
SELECT source_type, count(*)
FROM inventory_ledger_entry e
WHERE NOT EXISTS (
  SELECT 1 FROM purchase_record p WHERE e.source_type IN ('PURCHASE_RECORD','PURCHASE_RECORD_REVERSAL') AND p.id=e.source_id
  UNION ALL SELECT 1 FROM packaging_unit u WHERE e.source_type='KITCHEN_TASK' AND u.id=e.source_id
  UNION ALL SELECT 1 FROM inventory_stocktake s WHERE e.source_type IN ('STOCKTAKE','OPENING_BALANCE') AND s.id=e.source_id
  UNION ALL SELECT 1 FROM inventory_adjustment a WHERE e.source_type='MANUAL_ADJUSTMENT' AND a.id=e.source_id
)
GROUP BY source_type;
```

结果应为空。`PACKAGING_CONSUMPTION` 的 source 是 `${shipmentId}:${orderId}`，单独按前缀校验。

## 回滚预案

| 出了什么问题 | 怎么退 | 会不会脏账 |
|---|---|---|
| 期初数量错了 | 再跑一次期初（新单，会写新的 `OPENING_BALANCE`），旧的保留 | 不脏；新单覆盖余额 |
| 自动扣料把账扣花了 | 后台关开关；用「未扣料」列表补扣 | 不脏；只是少扣或多扣，下次盘点修 |
| 冲红/重入有问题 | 回滚代码；已写的正负行成对保留 | 不脏；余额仍对 |
| 新盘点页有 bug | 体验版回退；后台仍可用旧列表看 | 不脏 |
| 包材扣多了 | 关 `packagingDeductionEnabled`；下次包材盘点修 | 不脏 |
| 净额导致少买 | 关 `dailyNetOrderingEnabled`，立刻回旧逻辑 | 不脏 |
