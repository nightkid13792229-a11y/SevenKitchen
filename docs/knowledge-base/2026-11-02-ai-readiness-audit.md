# 知识库 · AI 就绪度审计与升级方案

**日期**：2026-11-02
**审计对象**：
- 治理层：`docs/knowledge-base/`（来源登记、证据政策、入库/复核 SOP、原文层产物）
- 运行时：`backend/src/domain/recipe-designer/knowledge-base/`（387 条结论）
- 原文层：Postgres 6 张表 + 11 个只读接口
- 调用链路：健康分析（标签注入）、配方 Agent（`read_knowledge` 工具）

**一句话结论**：

> 这是一间**整理得很好、出处记得很认真**的档案室，
> 但还不是一套**AI 能在需要时自己查、查得准、引用得住**的知识服务。
> 内容底子值 8 分，AI 可调用性只有 4 分。

---

## 0. 一页纸结论

| 项 | 结论 |
|---|---|
| **现有资产** | 387 条结论、28 个领域、803 处结构化出处、160 份文档（含 1 份误入的 README）、27,911 段、499 张表、592 张图、788 个出处锚点 |
| **最大优点** | 出处纪律强：387 条 100% 有结构化来源和复核日期；原文有稳定 ID、页码；健康分析输出层有“无出处不作答”的护栏 |
| **最大问题** | **检索仍靠“标签精确匹配 + 固定规则”**，不是理解问题；配方每次最多 24 条，健康分析每项 6 条，大量无关内容占位，真正相关的条目反而进不来 |
| **第二个问题** | **结论层、原文层、数字层是三座孤岛**：结论在代码里，原文在数据库里，营养标准/原料数据在另一个系统里；模型只能看到结论，看不到证据，也看不到数字 |
| **第三个问题** | **没有评测、没有检索日志、没有版本**：改了不知道好不好，错了不知道错在哪，回答无法回放到“哪条知识、哪段原文、哪个版本” |
| **推荐方案** | **方案 B：重构为“断言 + 事实 + 混合检索”的知识服务**；先用 1–2 周做方案 A 的止血项，再用 12–14 周完成主体 |
| **投入** | 约 52–81 人日；1 人约 3 个月，2 人约 6–8 周（不含内容专家审阅时间） |
| **预期收益** | 健康分析知识上下文从 2.3–2.6 万 tokens 降到 8 千以内；检索召回从“未测/估 40–50%”提到 90%；引用语义准确率提到 95%；配方 AI 第一次能“看到数字” |

```
387 条结论  ×  24 条上限  ×  2.3–2.6 万 tokens
27,911 段原文  →  模型可见 0 段
499 张表      →  与条目建立映射 18 张

```

## 1. 审计范围与方法

### 1.1 范围

本报告只审“知识库”本身，不审配方算法、营养计算引擎、订单/生产等业务模块。相邻的 `NutritionStandard`、`NutritionFood`、`Ingredient.nutritionProfile` 只在“模型能不能拿到数字”这一节被引用，不作为审计对象。

### 1.2 方法

| 方法 | 做了什么 |
|---|---|
| 读结构 | 读类型定义、标签词表、来源登记、校验逻辑、检索实现、提示词拼装 |
| 读数据 | 读 387 条条目的实际字段；统计领域、标签、来源、关键词、复核日期 |
| 读原文层 | 统计 160 份文档、27,911 段、499 表、592 图、788 锚点；对照导入脚本与数据库表 |
| 离线复现 | 用同一套检索函数复算典型犬只的命中结果、提示词长度、重复占位 |
| 抽样验证 | 抽 788 个锚点中的低相似度样本，人工核对“引用的文档对不对” |
| 对照文档 | 把治理文档的承诺与代码实际行为逐条对照，找“说的和做的不一样” |

### 1.3 口径说明

- **token 估算**：中文按 1.5 字/token 估算；用于比较相对大小，不作为账单依据。
- **相似度**：锚点文件里的 `score`，是“条目关键词与原文段落的匹配分”，不是语义相似度；低分不一定错，但低分集中出现的地方要人工看。
- **“模型可见”**：指进入提示词或工具返回，不是“数据库里有”。
- **“AI 可调用”**：模型能否在需要时主动取到、取准、并引用得住。

**名词表（后文反复出现）**

| 词 | 在这里是什么意思 |
|---|---|
| **token** | 模型读写文字的单位；中文大约 1.5 个字 = 1 token，也是计费单位 |
| **主题（topic）** | 现在的一条知识条目，例如 `renal-002`，给人读的完整说明 |
| **断言（claim）** | 从主题里拆出来的一句可独立引用的话，例如“犬 CKD 2–4 期应限磷” |
| **事实（fact）** | 带单位、口径、物种、阶段的数值，例如“磷 0.2–0.5% 干物质” |
| **混合检索** | 标签过滤 + 关键词打分 + 语义向量三路一起用，再合并排序 |
| **语义向量** | 把一句话变成一串数字（“意思指纹”），意思相近的句子距离近 |
| **MCP** | 一种让模型调用外部工具的通用接口；本文只作为交付方式之一 |

## 2. 当前架构长什么样

### 2.1 三层结构

```
原始资料（归档 169 份 / 已解析 160 份 / 约 668 MB，仓库外）
   │ 解析
   ▼
原文层（Postgres 6 张表）
  160 文档 / 27,911 段 / 499 表 / 592 图
   │ 人工写结论 + 自动锚定
   ▼
结论层（387 条，写在 TypeScript 代码里）
   │ 标签命中 / 关键词模糊匹配
   ▼
提示词（最多 24 条；健康分析 7 项 × 6 条）
   │
   ▼
模型（只允许引用上下文里的条目）
```

这个“原文 → 结论 → 输出”的三层方向是**对的**：原文只做证据，结论才允许对顾客说，输出层写死免责声明和分诊口径。问题不在分层，而在**层与层之间没有服务化**。

### 2.2 两条调用路径

| 路径 | 谁在用 | 怎么取知识 | 模型看到什么 |
|---|---|---|---|
| 健康分析 | 营养师侧（顾客侧开关默认关） | 固定 7 个方面，每项用固定标签 + 犬只标签，取前 6 条 | 42 个位置，但大量重复；知识上下文 2.3–2.6 万 tokens |
| 配方 Agent | 食谱设计 | 一个 `read_knowledge` 工具，按主题字符串模糊匹配前 8 条 | 标题、建议、前 3 条要点、前 2 条注意、出处名；**不给条目 ID** |
| 原文层 | 目前没有模型在用 | 11 个 HTTP 只读接口 | 只有人/外部系统能调；Agent 没有对应工具 |

### 2.3 一个关键事实

**结论层在代码里，不在数据库里。**

387 条结论是 32 个 TypeScript 文件，启动时由 `KnowledgeBaseService` 加载并校验。好处是类型安全、改错启动就报错；代价是：

- 模型不能按字段查询、过滤、排序；
- 改一个字要发版；
- 不能做“草稿/已审/已废弃”的状态机；
- 不能给每条结论单独编版本；
- 不能把结论和原文段落做数据库级联查。

原文层反而在数据库里，有稳定 ID、页码、章节。**结果就是：需要被查的结论在代码里，适合被查的原文在库里，两边靠 `entryId` 软关联。**

## 3. 做得好的地方（要保留）

1. **出处纪律**：387 条全部有结构化 `sources`，803 处引用，30 个来源；没有“无出处结论”。
2. **三层边界**：原文只做佐证，结论才允许对顾客说；输出层写死免责声明。这个边界比多数团队清楚。
3. **治理意识**：A–E 证据分级、入库 SOP、复核 SOP、来源登记、启动校验，一套齐全。
4. **原文层基础**：160 份文档、27,911 段、稳定段落 ID、页码、章节；这是做 RAG 的好底子。
5. **输出护栏**：健康分析只允许引用上下文里出现过的条目；越界措辞会降级；没出处就写“现有记录不足”。
6. **表格/图片存量**：499 张表、592 张图已经数字化/导出，虽然还没被用起来，但资产在。

这些优点说明：**不是内容不行，是“内容 → 模型”的这段路没修好。**

## 4. 以“AI 调用”为唯一标准：八个断层

> 判断标准只有一句：**模型在需要的时候，能不能拿到正确的、够小的、可引用的知识。**
> 人类读起来顺不顺、档案全不全、流程写得漂不漂亮，都只是手段。

### 4.1 断层一：找不准——检索是“标签匹配 + 固定规则”，不是理解问题

**现状**

- 检索靠 68 个“系统会产出的标签”做精确匹配；疾病识别靠 16 类关键词正则（肾、胰腺、肠、皮肤、结石、糖尿、甲状腺、肝、心、关节、肿瘤、认知、牙、繁殖、贫血、危重）。
- 健康分析给每一项配了**固定标签**。例如“记录解读”这一项，无论狗有没有病，永远带上 `ckd / renal / hepatic / cardio / gi`。
- 按现有代码离线复算：
  - **健康成犬**的“记录解读”，前 6 条是：验尿、UPC、肾病早期筛查、尿比重、肌酐尿素、IRIS 分期——**6/6 都是尿检/肾病内容，与“这只狗当前没有化验记录”不匹配**。
  - **呕吐犬**的“记录解读”，前 6 条里仍有 5 条是尿检/肾病。
  - **老年 CKD 犬**的 7 项共 42 个位置，只出现 **15 条不同知识**，27 个位置是重复（64%）。
- 提示词长度：健康分析知识部分 **2.3–2.6 万 tokens**；配方设计 **0.95–1.3 万 tokens**。

**后果**

模型不是“没知识”，而是“被无关知识包围”。它会：

- 用肾病知识回答呕吐问题；
- 反复看到同一条，挤掉真正相关的条目；
- 因为上下文太长，忽略中间的内容；
- 每次多花 2–3 万 tokens 的钱。

**应该怎样**

先把“这只狗是什么情况”变成结构化查询条件（物种、生命阶段、疾病、问题类型、语言），再做三路召回（标签/关键词/语义），最后按 token 预算组装。**不是把 24 条换成 240 条，而是把“对的那 6 条”找出来。**

---

### 4.2 断层二：粒度粗——一条 = 一篇小百科，不能精确引用

**现状**

- 387 条，平均 **729 字**、5.4 条要点、2.4 条注意；最长 2,363 字。
- 一条里常常同时装着：定义、分期、什么时候干预、营养怎么做、注意事项。
- 只有条目级 ID（`renal-001`），没有“句子级 ID”。
- 有 9 对条目关键词重合度 ≥0.5（如 `lab-003` 与 `lab-026`、`general-012` 与 `weight-007`），内容有重叠。
- `conflicts` 字段 0 条——不是没有分歧，是没人登记。

**后果**

- 模型说“引自 renal-001”，读者仍不知道是哪一句；
- 一条里既有“可观察”又有“立即就医”，无法按句标紧急程度；
- 命中一条就塞 729 字，其中 80% 与本次问题无关；
- 改一句话要重审整条，改错一个字段可能让整条失效。

**应该怎样**

把“主题（给人读的整条）”与“断言（给模型引用的一句话）”分开：

- **主题**：保留现在的 387 条，作为人类阅读和审核的单位；
- **断言**：从主题里拆出“一句结论 + 适用范围 + 出处 + 数值 + 禁忌”，作为检索和引用的单位；
- 断言的 ID 可以写成 `renal-002#d3`（第 3 条要点），不破坏现有条目。

这不需要重写 387 条，只需要**拆**，并给每一段一个稳定 ID。

---

### 4.3 断层三：两层脱节——结论在代码里，原文在库里，模型只看到一半

**现状**

- 387 条结论在 TypeScript 代码里；27,911 段原文在 Postgres 里。
- 原文层有 11 个只读接口，但**没有接进 Agent**；配方 Agent 有 8 个工具，其中知识工具只有 1 个模糊搜索。
- 499 张表里，只有 **18 张**与条目建立映射（涉及 46 个条目）；592 张图**没有一条结构化的图—条目关联**。
- 6 份文档没有来源 ID（AAHA 2018 糖尿病、AAHA 2022 疼痛、AAHA 2010 营养、WSAVA 微芯片、WSAVA OneHealth、README）。
- 知识库自己的 `README.md` 被当成一份“原文”解析进了原文层（9 段），会污染检索。

**后果**

- 模型只能“背结论”，不能“查证据”；
- 遇到结论没覆盖的问题，只能拒答或编；
- 表格里最有价值的数字（营养需求、原料成分、补充剂构成）模型看不到；
- 图片里的评分表、流程图、皮损图，模型也看不到。

**应该怎样**

给模型三个“查”的能力，而不是把整库塞进提示词：

1. **查断言**：按问题取最相关的几句话；
2. **看证据**：给定断言 ID，返回原文段落 + 文档 + 页码；
3. **取数值**：给定营养素/原料/物种/阶段，返回带单位与口径的数值。

原文层已经是数据库表，接这三个工具是“接线”，不是“重建”。

---

### 4.4 断层四：数字缺失——配方 AI 只能看到“达标/不达标”

**现状**

- 系统里其实有结构化营养数据：`NutritionStandard`（FEDIAF/NRC 标准）、`NutritionFood`、`Ingredient.nutritionProfile`。
- 但配方 Agent 的 `assess` 工具只返回：过没过、缺几项/超几项、缺口名称、过敏原。**不返回任何数值。**
- 499 张数字化表里，33.7% 的单元格是数字，但都是字符串；没有单位、没有“干物质/代谢能”口径、没有物种/阶段字段。
- **NRC 2006 的 62 张表，一张都没有进数字化表**。NRC 的 EPUB 里每张表是独立 HTML 文件（`chapter14_tb01.xhtml` 这类），本来是最好抽的；但当前 499 张表里 NRC 为 0。
- 499 张表里 486 张的表题是英文，中文查询按表题搜不到。

**后果**

配方 AI 的真实工作流是：

```
模型：把鸡肉加到 300g
工具：已执行
模型：评估一下
工具：未达标，缺 3 项，主要缺口：钙磷比、维生素D、锌
模型：……（它不知道现在钙磷比是多少，也不知道该加多少碳酸钙）
```

它只能“猜一个方向”，不能“算一个数”。对一个卖鲜食的公司，这是最危险的缺口：**知识库讲得头头是道，但配方最需要的数字不在模型手里。**

**应该怎样**

建一层“事实（fact）”：

- 营养需求：物种、生命阶段、营养素、最低量/推荐量/上限、单位、口径（DM/ME）；
- 原料成分：原料、常规成分、矿物、氨基酸、脂肪酸、维生素、来源、年份；
- 补充剂构成：碳酸钙含钙 40%、磷酸氢钙含钙/磷多少；
- 加工损失：水煮/蒸/冻干后的保留率；
- 每条事实带来源、页码、版本。

断言里如果出现数字，必须链接到事实 ID，而不是把数字写死在句子里。

---

### 4.5 断层五：引用“看起来 100%，实际一半不精确”

**现状**

- 788 个锚点，覆盖 387 条，账面 100%。
- 但：**401 个到段落（51%），387 个只到小节（49%）**；相似度 <0.2 的 104 个（13%），<0.3 的 251 个（32%）。
- 抽样发现**引错文档**：
  - `behav-002` 引 WSAVA 疼痛指南，锚到 `Pregnant-or-lactating-patients.pdf`（相似度 0.143）；
  - `breed-004` 引 ACVIM 肺动脉高压共识，锚到 `ACVIM-2024-免疫性血小板减少症-治疗`（0.143）；
  - `clinical-050` 引 WSAVA 疼痛指南表 5，锚到 `Cancer-Pain.pdf`（0.143）。
- 根因之一：导入脚本按“来源大类”映射 `sourceId`，25 份 ACVIM 全映射成 `ACVIM-CONSENSUS`、6 份 WSAVA 疼痛资料全映射成 `WSAVA-PAIN-2022`，**文档级没有区分**，锚定只能在同来源的多份文档之间做匹配，很容易挑错。
- 152 条条目没有英文关键词；它们的段落级锚定比例 **23.3%**，有英文关键词的是 **73.0%**；平均分 0.303 对 0.585。
- 592 张图里 **340 张图注是 AI 描述且未核对**（57.6%），42 张标为装饰图。

**后果**

对 AI 来说，**错误的出处比没有出处更糟**：模型会理直气壮地把一段不支持结论的原文当证据。对内部营养师来说，点开出处发现对不上，会直接摧毁对知识库的信任。

**应该怎样**

- 文档级来源 ID（每份文档一个 ID，不再按“大类”合并）；
- 锚定加“文档内一致性”校验：引用的来源名、文档标题、章节标题必须能对上；
- 低置信锚点不隐藏，但标成“仅到小节/待核”，不让模型当强证据；
- 152 条补英文关键词（这是投入产出比最高的一项）；
- 340 条 AI 图注在核对前不进入模型上下文。

---

### 4.6 断层六：没有评测、没有反馈——改了不知道好不好

**现状**

- 没有“标准问题集”（golden set），没有召回率/引用准确率/无依据拒答率的测量。
- 现有测试是**结构测试**：id 唯一、标签合法、出处已登记、接口形状正确；不测“这条知识该不该被检索到”。
- 没有检索日志：不知道每次回答了哪些条目、模型引用了哪些、用户点没点赞。
- 内置审计脚本只能查“标题重复、猫的内容、复核过期”，查不了“该命中的没命中”。
- 目前只报出 2 条待人工判断：`clinical-049` 出处名对不上登记表、`renal-006` 引了猫的资料。

**后果**

- 任何优化都无法证明有效，只能“感觉好像好一点”；
- 改坏了自己不知道；
- 用户反复问的问题，不会变成新条目；
- 这套资产无法回答“到底哪一块最拖后腿”。

**应该怎样**

先冻结 150 道“标准题”（覆盖配方、指标解读、分诊、复查、顾客 FAQ），每题给出“应该命中的断言/条目 + 应该引用的原文”。之后每次改知识库、改检索、换模型，都跑同一套题。

指标不求多，6 个就够：

1. 召回率（该出现的知识有没有出现）；
2. 上下文精度（出现的内容有多少是相关的）；
3. 引用准确率（引用的原文是否支持这句话）；
4. 无依据拒答率（没证据时有没有老实说不知道）；
5. 知识 tokens（每次塞多少）；
6. 延迟。

### 4.7 断层七：治理与工程脱节——文档说的和代码做的不一样

这是最容易被忽略、但对“AI 可审计”最致命的一条。

| 表面状态 | 实际情况 |
|---|---|
| 入库 SOP 要求填“紧急程度”“审核状态” | 2026-11-01 已删掉这两个字段，SOP 没改 |
| 审核包 README 说“没人审过就不给顾客看” | 字段已删，代码里没有“已审/待审”过滤；顾客侧开关一开，387 条都可能进入，代码里没有已审/未审过滤 |
| 原文方案说“原文不进数据库” | 已经建了 6 张表、灌了 27,911 段 |
| 最终报告说 27,911 段 / 499 表 / 788 锚点 | 另一份报告说 27,909 段 / 484 表 / 1,235 锚点；早期报告说数字化表 384 张 / 锚点 1,250 个 |
| 来源登记说 169 份 | 归档清单 157 份；原文层 160 份（含 README） |
| 来源登记说 `WSAVA-RENAL` 本地已有 | 归档清单里没有这份文件 |
| 所有条目 `reviewBy = 2027-04-01` | 387 条同一天到期，等于没有分批复核 |
| `conflicts` 用来记录来源分歧 | 0 条，尽管 30 个来源、803 处引用 |

**后果**

- 治理层不能当作“机器可读的合同”，只能当“人看的说明”；
- 发版时无法回答“这一版比上一版多了什么、少了什么”；
- 出问题时无法回放“当时用的是哪版知识、哪条断言、哪段原文”；
- 新人接手时，不知道哪份文档是真的。

**应该怎样**

一份 `manifest`（清单）管全部：条目数、断言数、来源数、文档数、表数、图数、锚点数、校验和、版本号、生成时间。所有文档引用这一份数字，不再各写各的。每次发布一个版本号，回答里记录版本号。

### 4.8 断层八：安全红线——接口无鉴权，原文和图片对外

**现状**

- `KnowledgeSourceController` 的 11 个接口**没有挂鉴权守卫**；同项目其他控制器普遍有 `@UseGuards(AuthGuard)`。
- `/kb-figures/` 是公开静态目录，任何人知道图 ID 就能取图。
- 原文层包含受版权保护的指南全文、表格、图片；方案里明确写过“版权风险要保守”。
- 没有看到速率限制、访问审计。

**后果**

- 受版权保护的全文可能被公开抓取；
- 内部知识（包括未核对的 AI 图注）对外可见；
- 将来接外部模型/合作方时，这是第一道过不去的门。

**应该怎样**

- 所有知识接口默认要求登录，按角色（营养师/管理员/内部服务）授权；
- 图片走签名 URL 或受保护代理，不直接公开目录；
- 原文全文只对内部角色开放；对外只给“短引用 + 出处”，不给全文；
- 加访问日志和速率限制。

## 7. 目标架构：从“档案室”到“知识服务”

### 7.1 五条设计原则

1. **结论仍是唯一可引用来源，原文只做证据。**
   不把 27,911 段原文丢给模型自由读；只让模型“按需取证据”。
2. **检索单位从“条目”降到“断言”。**
   一条结论拆成几句可独立引用的话；主题保留给人和审核。
3. **数字进结构化事实层，不进散文。**
   能用数值表达的知识，不要写成“适量”“注意补充”。
4. **一次只给“够用的最小上下文”。**
   按 token 预算组装，不按“命中多少塞多少”。
5. **每次回答可回放到“哪条断言、哪段原文、哪个版本”。**
   没有版本号的回答，不算可审计。

### 7.2 五层结构

```
L0 源与登记
   原始文件 + manifest（来源、版本、哈希、许可、可见性）
        │
L1 事实层（facts）
   营养需求 / 原料成分 / 补充剂构成 / 加工损失
   带单位、口径、物种、阶段、来源、页码
        │
L2 断言层（claims）
   一句结论 + 适用范围 + 证据段落 + 证据等级 + 复核状态
        │
L3 主题层（topics）
   现在的 387 条，作为人类阅读与审核的完整说明
        │
L4 服务层
   查询理解 → 三路召回 → 重排 → 预算组装 → 引用校验
        │
L5 应用层
   健康分析 / 配方 Agent / 营养师后台 / MCP 或外部工具
```

横切四件事：**版本发布、评测、观测、权限**。这四件事不做好，上面五层就是“又一个文档库”。

### 7.3 一条知识的新形态

**主题**（人读，保留现在的 387 条）：

> 犬 CKD 的磷限制：为什么限、限到多少、什么时候需要兽医介入。

**断言**（模型检索/引用，新增）：

```
断言 ID：renal-002#d2
一句话：犬 CKD 2–4 期应限制膳食磷；治疗粮范围约 0.2–0.5% 干物质。
适用：犬 / CKD 2–4 期 / 成年
不适用：幼犬、妊娠哺乳、未确诊的高磷血症
证据：SACN5 第37章 慢性肾病（具体页码由锚点给出）；FEDIAF 2025 相关表格
数值：磷 0.2–0.5% DM（事实 ID：fact-phos-ckd-01）
禁忌：限磷不得导致蛋白/能量不足；磷结合剂需兽医决定
复核：2027-04 / 版本 v2026.11
```

**事实**（数字，新增）：

```
fact-phos-ckd-01
营养素：磷
物种：犬
阶段：CKD 2–4 期
范围：0.2–0.5
单位：% DM
来源：SACN5 表 37-9
```

模型看到的是“断言 + 证据 + 数值引用”，不是一整篇小百科。

### 7.4 模型侧只需要四个工具

| 工具 | 输入 | 输出 | 用途 |
|---|---|---|---|
| `search_knowledge` | 问题、物种/阶段/疾病/问题类型、token 预算 | 最相关的断言（含 ID、原文短引、置信度） | 找知识 |
| `get_evidence` | 断言 ID | 原文段落、文档、章节、页码、引用 | 看证据 |
| `get_facts` | 实体（营养素/原料/补充剂）、物种、阶段 | 数值、单位、口径、来源 | 算数字 |
| `validate_citations` | 回答里的引用列表 | 每条引用有效/无效/只到小节 | 防编造 |

关键：**不给模型“整库”，给“按需取用”的四个动作。**

### 7.5 检索与上下文组装

```
问题 + 犬只档案
   │
   ├─ 查询理解：物种 / 生命阶段 / 疾病 / 问题类型 / 语言
   │
   ├─ 三路召回
   │    ① 标签/结构化过滤（精确）
   │    ② 关键词/BM25（中英文，含同义词）
   │    ③ 语义向量（把句子变成“意思指纹”）
   │
   ├─ 合并去重（断言 ID、近重复）
   ├─ 重排（相关性 + 证据等级 + 新鲜度 + 多样性）
   ├─ 预算组装（总 token 上限、每主题最多 N 条、安全断言必带）
   └─ 返回：断言 + 引用 + 版本
```

为什么必须三路：

- 只有标签：像现在，问“呕吐”给“尿检”；
- 只有向量：数字、否定、禁忌容易错；
- 三路合起来，才能既“懂意思”又“守精确”。

跨语言是硬需求：原文 95% 是英文，中文查询直接搜只能命中 4.9% 的段落。要么用多语言向量，要么在检索前把中文问题翻成英文关键词；最好两者都做。

### 7.6 版本、评测、反馈

**版本**

- 每次发布一个知识版本（如 `kb-2026.11.0`），带 manifest、校验和、变更说明；
- 生产用“整版切换”，出问题可回滚到上一版；
- 每条回答记录版本号，事后可回放。

**评测**

- 150 道标准题，覆盖配方、指标解读、分诊、复查、顾客 FAQ；
- 6 个指标：召回、上下文精度、引用准确、无依据拒答、tokens、延迟；
- 进 CI：知识库改动不跑评测，不许发布。

**反馈**

- 记录：问题、召回候选、最终选中、模型引用、用户反馈；
- 每周看三张表：零结果问题、低置信引用、被反复问但没条目的问题；
- 这三张表直接变成下一批入库任务。

### 7.7 安全与权限

| 层 | 做法 |
|---|---|
| 接口 | 默认登录；营养师/管理员/内部服务分角色 |
| 原文 | 全文只对内部角色；对外只给短引用 + 出处 |
| 图片 | 签名 URL 或受保护代理，不公开目录 |
| 顾客侧 | 断言级 `visibility` + `reviewStatus`；未审断言不进入顾客回答 |
| 审计 | 记录谁在什么时候取了哪条原文/哪张图 |
| 版权 | 全文不出内网；对外引用长度受限；上线前法务确认 |

## 8. 三个方案对比

| | **A. 优化** | **B. 重构（推荐）** | **C. 重建** |
|---|---|---|---|
| **做什么** | 修检索排序、补英文关键词、修锚点、加鉴权、建评测 | 断言层 + 事实层 + 混合检索 + 四工具 + 版本 + 评测 | 知识图谱/本体、全自动抽取、多模态、全量 admin |
| **周期** | 3–4 周 | 12–14 周 | 6 个月以上 |
| **风险** | 低 | 中 | 高 |
| **收益** | 约 60% | 约 90% | 100%，但边际收益低 |
| **适合** | 只想先稳一稳 | 要把知识库变成 AI 基础设施 | 有长期大团队、且 B 已跑通 |
| **不改什么** | 387 条仍在代码里 | 主题仍可保留在代码/仓库，断言进库 | 全部重做 |

**推荐：B，先用 A 做第 0 阶段。**

理由：

- 只做 A，检索还是“标签 + 固定规则”，碰到“库欣/巨食管/气管塌陷”这类没标签的问题仍然抓瞎；
- 直接做 C，投入大、周期长，而当前最痛的不是“知识不够多”，是“知识取不出来、引用不住”；
- B 是在现有资产上“加一层”，不推翻 387 条、不推翻原文层、不推翻治理层，风险可控。

## 11. 风险与边界

| 风险 | 等级 | 说明 | 缓解 |
|---|---|---|---|
| 版权/知识产权 | 高 | 原文全文、图片受版权保护 | 全文只在内网；对外只短引用；上线前法务确认 |
| 医疗安全 | 高 | 拆断言后可能丢“注意/禁忌” | 断言必须带 caveat；高风险断言人工全审；保留“无依据不作答” |
| 审核工作量 | 中 | 约 1,500–2,000 条断言，审不过来 | 先做高风险/高频 100 条；其余抽样审；断言继承主题的审核结论 |
| 检索错误 | 中 | 语义检索可能召回“像但不相关”的内容 | 混合检索 + 重排 + 引用校验 + 低置信拒答 |
| 数据质量 | 中 | 340 条 AI 图注、49% 小节级锚点 | 核对前不进上下文；低置信标黄；抽样复核 |
| 成本/延迟 | 低–中 | 向量化、重排会增加成本 | 语料小（2.7 万段/2 千断言），可缓存、批量；P95 目标 300ms |
| 变更管理 | 中 | 营养师/运营要学新后台 | 先做只读查询，再做编辑；培训和双轨期 |
| 过度工程 | 中 | 一开始就做知识图谱/本体 | 先断言+事实，跑通评测再谈图谱 |

**三条不做的事**：

1. **不把 27,911 段原文直接塞给模型**——上下文爆炸，且违反“结论只能来自已审条目”的边界。
2. **不在没有评测的情况下换检索/换模型**——改了不知道好坏，等于赌博。
3. **不为了“全”而保留错误引用**——错的出处比没有出处更伤信任。

## 12. 结论

这套知识库的**内容底子和治理意识，明显高于行业平均**：387 条结论、803 处出处、27,911 段原文、499 张表，不是一朝一夕能做出来的。

但它现在的形态，是“**给人查的档案室**”，不是“**给 AI 用的知识服务**”：

- 配方每次最多 24 条、健康分析每项 6 条，而这些位置是按标签和固定规则挑的；
- 原文层 2.7 万段、499 张表、592 张图，模型一段也看不到；
- 配方最需要的数字，在另一个系统里，模型只能看到“达标/不达标”；
- 788 个锚点账面 100%，但一半只到小节，抽样还能看到引错文档；
- 没有评测、没有日志、没有版本，改了不知道好不好。

**建议的路径不是“再补 200 条知识”，而是“把已有知识变成可检索、可引用、可计算、可回放的服务”。**

先做两周止血（鉴权、锚点、基线、导出、NRC 表），再用 12–14 周完成断言层、事实层、混合检索、四个工具和评测闭环。做完之后，这套知识库才真正配得上“供 AI 模型调用”这六个字。
