# 是否扩展全库：决策建议（2026-11-09）

## 结论

**暂不扩全库。**  
先把 CKD 章节目录和检索路由验证稳定，再按病种/来源分批扩，不做一次性全库铺开。

## 现状

- CKD 试点：5 份文档 / 78 个章节 / 857 段；
- 全库：159 份文档 / 6,090 个章节 / 27,902 段；
- 章节数约 78 倍，段落数约 32 倍。

## 为什么现在不扩

1. **目录质量还没验收**：CKD 目录刚建好，需要先用固定问题验证 top-k 是否命中正确章节；没验证就扩，错误会放大 78 倍。
2. **元数据歧义需要人审**：物种/分期/主题可以自动生成，但跨物种、跨分期、附录、表格章节会有歧义；全库需要明确谁负责审核。
3. **CKD 还有来源缺口**：覆盖地图显示碘在 5 份 CKD 文档中没有出现；这是来源缺口，不是扩库能解决的，应先补来源或明确不覆盖。
4. **维护成本**：全库目录一旦生成，文档更新/新增都要重跑和抽查；没有 owner 时会迅速过期。

## 扩库前必须满足

1. CKD 目录用 10–15 个固定问题验收：top-3 章节命中、引用可回源、无跨物种/分期串台；
2. 碘等已发现的来源缺口有结论（补文档，或明确不由知识库覆盖）；
3. 明确目录元数据的审核 owner（谁确认物种/分期/主题标签）；
4. 确定扩库顺序：按病种/来源分批，不按“全库一次性”。

## 建议的扩库方式（如果后续批准）

- 第一批：CKD 相关的其余来源（肾脏、老年、心血管交叉）；
- 第二批：高频病种（消化、皮肤、肝胆、体重管理）；
- 每批只做：目录生成 → 固定问题验收 → 再进入下一批；
- 不引入向量库/reranker，先把章节路由和来源元数据做稳。

## 判断

CKD 试点已经证明结构方向可行；现在扩全库的收益不明确、维护成本高。  
**先收口 CKD，再决定是否值得为全库投入。**
