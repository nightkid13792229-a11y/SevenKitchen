# 知识库结构审查（健壮性 · 交叉验证）

**日期**：2026-10-01
**审查问题**（老板原话）：
1. 这些资料来源结构**健不健壮**？
2. 你说的**交叉验证到底是怎样子的**？
3. 先不考虑能不能镜像、能不能下载——**先审知识结构本身**。

---

## 一、现在是什么结构

### 1.1 一条知识长什么样

```
知识条目（共 202 条）
├── id            如 renal-001
├── domain        20 个领域（RENAL / GI / SKIN / CARDIO / SENIOR …）
├── title         中文标题
├── keywords      检索关键词（平均 4.7 个）
├── applicableTo  触发标签（受控词表）
├── summary       结论（一段话）
├── details       要点明细（平均 5.4 条，最多 10 条）
├── caveats       注意事项（平均 2.2 条）
├── citations     出处（**自由文本**，实测 65% 只有 1 个来源）
└── priority      引用优先级 HIGH / MEDIUM / LOW
```

### 1.2 一条知识怎么被用上

```
狗狗档案 → 关键词猜出标签（16 类疾病领域）
        → 标签命中知识条目
        → 命中的条目【全部】塞进提示词
        → AI 只能引用这些条目，并标注条目编号
```

### 1.3 实测的体量

| 指标 | 数值 |
|---|---|
| 条目数 | 202 |
| 全部正文 | 约 240 KB ≈ 12.3 万 tokens |
| 单条平均 | **1,219 字符**（中位 1,187，最大 2,933） |
| **只有 1 个来源的条目** | **133 条（65%）** |
| **有 ≥2 个不同来源的条目** | **69 条（34%）** |

## 二、六个结构性问题

### 🔴 S1 · 领域是"一维疾病分类"，但健康管理要按"问题类型"回答

现有的 20 个领域（RENAL、GI、SKIN、CARDIO…）**全是疾病或器官**。

但健康管理真正要回答的是**五类问题**：

| 问题类型 | 家长/医生会问 |
|---|---|
| **解读** | 这个数值意味着什么？ |
| **分诊** | 要不要去医院？多急？ |
| **复查** | 多久再查一次？查什么？ |
| **营养** | 该吃什么、不该吃什么？ |
| **预防** | 平时怎么防？该做什么检查？ |

同一个疾病下，这五类问题的答案**完全不一样**，现在全挤在一个领域里。

**更麻烦的**：本次要新增的 3 个领域里，「**检查指标解读**」和「**常见病表现与就医时机**」是**按问题类型**分的，而旧的 20 个是**按疾病**分的——**两种分类混在一起了**。

> 具体后果：一条"肾病该多久复查一次"的知识，应该放在 `RENAL` 还是 `检查指标解读`？
> 现在没有答案，怎么放都能说得通。

**建议：改成两维坐标**——领域（疾病/系统）× 问题类型（解读/分诊/复查/营养/预防/免疫）。

---

### 🔴 S2 · 条目粒度太粗：一条 = 一篇小百科

平均一条 **1,219 字符、5.4 条要点、2.2 条注意事项**。

比如 `renal-001` 一条里同时装着：
- CKD 的 IRIS 四期定义
- 什么时候该开始营养管理
- 蛋白尿意味着什么
- 老年犬发病率

**三个后果：**

| 后果 | 说明 |
|---|---|
| **没法精确引用** | AI 说"引自 renal-001"，但读者不知道是哪一句 |
| **没法标紧急程度** | 一条里既有"1 期难以发现"（可观察），又有"肌酐 >2 必须干预"（需就医），标不了 |
| **检索颗粒度不对** | 命中一条就塞 1,200 字，其中可能 80% 跟这次问题无关 |

**建议：一个条目 = 一个"问题—答案"对。**

判断标准（可以直接拿去用）：
> **如果一句话可能被单独引用，而且它的紧急程度可能和其他句子不一样，就应该独立成条。**

---

### 🔴 S3 · 出处是自由文本 → 交叉验证在结构上根本做不到

这是老板问的核心。现在出处长这样：

```
citations: [
  { source: '小动物临床营养学（第5版）', chapter: '第37章 慢性肾病' },
  { source: '肝肾低脂注意事项笔记' },
]
```

**四个问题：**

| 问题 | 后果 |
|---|---|
| 来源是**字符串**，不是 ID | 同一份指南有 2–3 种写法（AAHA 2021 有 2 种、NRC 有 3 种），统计不了 |
| **不区分主来源和佐证来源** | 看不出哪份是主要依据 |
| **不记录来源之间是一致还是冲突** | 冲突被悄悄糊在一起 |
| 无法查询"有几个独立来源支持" | **交叉验证完全靠人肉，系统一无所知** |

---

### 🔴 S4 · 没有"证据强度"字段

`priority`（HIGH/MEDIUM/LOW）是**引用优先级**——决定喂给 AI 时先给哪条，**不是证据强度**。

结果：**一条只靠本地笔记撑着的结论，和一条被三个独立指南印证的结论，在系统里长得一模一样。**

实测的严重程度：
- **65% 的条目只有 1 个来源**
- **HEMO（血液）领域 6 条里 5 条的出处是"本知识库 X 领域"——自己引自己**

---

### 🟡 S5 · 没有"紧急程度"字段

已在前面讨论过：一条里混合了不同紧急程度的结论，AI 只能自己猜，猜的结果每次可能不一样。

---

### 🟡 S6 · 没有版本与时效字段

没有生效日期、没有复核日期。无法回答"哪些条目引用了已被取代的 AAHA 2014 体重指南"。

---

## 三、重点回答：交叉验证到底是怎么做的

"交叉验证"其实有**三种不同的东西**，混为一谈就会做错。

### ① 多来源印证 —— 同一结论，多个独立权威都这么说

这是最常见的理解。**关键在于"独立"两个字：**

| 情形 | 算不算独立 |
|---|---|
| SACN5 和 WSAVA 都引用了同一篇原始研究 | ❌ **不算**——它们同源 |
| WSAVA 指南和 AAHA 指南各自独立制定、结论一致 | ✅ **算** |
| SACN5（教科书）和 ACVIM（专科共识）互相印证 | ✅ **算** |

**落地方式**：出处分成两栏——`primary`（主来源）+ `corroborating`（印证来源），
并强制要求：**印证来源必须来自不同机构**。

### ② 条件交叉 —— 不同来源针对不同对象，结论不同但并不冲突

举例（这在免疫领域马上会遇到）：

| 来源 | 说法 |
|---|---|
| WSAVA 2024 疫苗指南 | 幼犬 6–8 周起可以开始首免 |
| 国内养犬登记规定 | 狂犬疫苗通常要求 3 月龄以上才能登记 |

**这不叫冲突，叫适用条件不同。**

**落地方式**：条目必须有**适用条件**字段，而不是把两个结论揉成一句话。

### ③ 真冲突 —— 来源之间结论确实不一致

举例：AAHA 2014 与 AAHA 2021 的体重管理结论。

**落地方式**：显式记录：

```
conflicts: [{
  甲: 'AAHA 2014 体重管理指南',
  乙: 'AAHA 2021 营养与体重管理指南',
  差异点: '……',
  我们取哪个: '……',
  理由: '……'
}]
```

> **这一条必须由人定，不能让 AI 自己挑一个。** 这是整个结构里最需要人的地方。

---

### ⚠️ 我要修正自己上一轮的判断

我上一轮说"96% 引同一本书，缺交叉验证"——**说得太笼统了**。实际上交叉验证应该**按风险分级**，不该一刀切：

| 结论类型 | 交叉验证要求 | 理由 |
|---|---|---|
| **高风险**：紧急程度、数值、禁忌、用药边界 | **必须 ≥2 个独立来源** | **说错了会伤到狗** |
| **中风险**：疾病定义、机制、复查节奏 | **1 个 A/B 级来源**即可，有第二个更好 | 定义就是那个定义，多引一本不增加信息 |
| **低风险**：背景知识、常识 | 1 个来源 | — |

**所以真正该先做的，不是"每条都补第二个来源"，而是先把「来源等级」和「风险等级」这两个字段建起来。**
有了它们，"哪条需要补第二个来源"就变成一张**可以查出来的清单**，而不是靠感觉。

## 四、建议的新结构

```
知识条目
├── id
├── domain            领域（疾病 / 系统）：RENAL · GI · IMMUNE · …
├── questionType   ★  问题类型：定义 / 解读 / 分诊 / 复查 / 营养 / 预防 / 免疫
├── riskLevel      ★  风险等级：高 / 中 / 低      ← 决定是否需要交叉验证
├── urgency        ★  紧急程度：立即就医 / 尽快就医 / 可观察（分诊类必填）
├── applicableTo      触发标签（受控词表，已有）
├── keywords          检索关键词（已有）
├── statement      ★  一句话结论（单一断言，可独立引用）
├── details           要点（每条尽量也能独立成立）
├── caveats           注意事项 / 禁忌 / 需兽医确认（已有）
├── citations      ★  结构化出处：
│                       primary        { sourceId, locator }     主来源，必须是登记表里的 ID
│                       corroborating  [{ sourceId, locator }]   印证来源，必须不同机构
│                       conflicts      [{ 甲, 乙, 差异, 取舍, 理由 }]
├── evidenceStrength ★ 证据强度（可由出处自动推导）：单源 / 双源印证 / 多源一致 / 存在冲突
└── reviewBy       ★  下次复核日期（配合复核 SOP）
```

**这套结构怎么保证健壮：**

| 原先的问题 | 新结构怎么解决 |
|---|---|
| 领域分类打架 | 两维坐标，疾病和问题类型各归各位 |
| 粒度太粗 | 一条一个断言，可独立引用、可独立标紧急程度 |
| 出处是字符串 | 改成来源 ID，**登记表里没有的 ID 直接报错**（校验已经建好了） |
| 交叉验证靠人肉 | `primary` / `corroborating` / `conflicts` 三栏写清楚，**能查、能统计** |
| 证据强度看不出 | 由出处自动推导，高风险结论单源时**校验器直接报警** |
| 紧急程度靠猜 | 写死在条目里，AI 只能照用 |
| 时效查不到 | `reviewBy` + 复核 SOP |

## 五、迁移成本与建议路径

改成新结构，**202 条几乎每条都要动**：补 4 个字段、出处结构化、粒度粗的要拆。
这是**重写**，不是打补丁。全量迁移代价很大。

**但有一条捷径，建议走这条：**

| 做法 | 说明 |
|---|---|
| **现有 202 条先不动** | 继续服务食谱设计器（它现在跑得没问题，且**只给营养师看，不直接面向顾客**） |
| **新领域（免疫 / 指标解读 / 常见病）直接用新结构建** | 这三块是**面向顾客**的，才是高风险场景 |
| 等新结构在真实场景验证有效，再回头迁旧的 202 条 | 迁移时还能顺带修正告一段落的问题 |

**理由**：现有 202 条的使用场景是"给营养师做设计参考"，风险可控；
**面向顾客的才是高风险场景**——新结构应该先用在高风险的地方。
