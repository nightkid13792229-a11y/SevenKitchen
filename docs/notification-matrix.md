# 通知矩阵：订阅消息 × 站内消息

> 2026-10-31 起草。用途：把"客户在哪个节点、收哪条通知、走哪条通道"定死，作为后续开发与文案的依据。
> 相关背景：客服会话受微信 48 小时 / 5 条限制（见文末附录），所以**该自动发的通知必须自动发出去**，不能靠客服去敲客户。

---

## 0. 五句话摘要

1. **订阅消息是"打断"**：弹在微信聊天列表，一次授权只能发一条，所以只用在客户正在等、或必须行动的事上。
2. **站内消息是"留痕"**：不打扰、成本近乎为零，只要客户以后可能回来查，就该写一条。
3. 大部分关键节点应该**两个都发**，但不是所有节点都值得打断。
4. 真正的稀缺资源是**订阅额度**：一次弹窗最多申请 3 个模板，所以每个订单要设计"把额度花在哪三条"。
5. 现状缺得最狠的是：**定制单付款成功**、**售后被驳回**、**普通订单完全没有站内消息**、**疫苗提醒从未启用**。

---

## 1. 判断标准

站在顾客角度，只问三个问题：

| 判断 | 结论 |
|---|---|
| 客户此刻是不是**在等这个结果**？ | 是 → 订阅消息 |
| 客户是不是**必须做点什么**（补资料、确认地址）？ | 是 → 订阅消息 |
| 是不是**钱或健康**的事？ | 是 → 订阅消息 |
| 三条都不占，但客户**以后可能回来查**？ | 只发站内消息 |
| 三条都不占，也不会回来查？ | **不发** |

一句话：**订阅消息只用来解决问题，不用来刷存在感。**

## 2. 通道能力边界

| | 小程序订阅消息 | 站内消息 | 客服会话（微信客服） |
|---|---|---|---|
| 客户在哪看到 | 微信「服务通知」 | 小程序「我的 → 消息」 | 微信聊天列表里的客服会话 |
| 需不需要客户同意 | **要**，点「允许」 | 不用 | 客户先开口 |
| 一次授权能发几条 | **一条** | 不限 | 客户开口后 48 小时内最多 5 条 |
| 一次弹窗最多申请几个模板 | **3 个** | — | — |
| 发送失败会怎样 | 静默失败（43101 = 未订阅） | 不会失败 | 超时直接发不出去 |
| 能不能发营销内容 | **不能**（会被拒/审核风险） | 不建议 | 不建议 |
| 正文长度 | 字段有硬限制（见 §5.3） | 标题 120 字 / 正文 500 字 | 单条约 680 汉字 |

> 结论：**订阅消息负责"把人拉回来"，站内消息负责"回来时一定看得到"，客服负责"要来回聊的事"。三者不能互相替代。**

## 4. 订阅额度怎么分配（关键设计）

微信规则：**客户点一次「允许」= 我们只能发一条**；一次弹窗最多带 **3 个模板**。

建议统一用 **"2 + 1"** 模式：下单时一次弹窗申请 2 个（覆盖主流程），后续关键动作再补申请 1 个。

| 订单类型 | 下单/付款时一次申请 | 后续补申请 | 说明 |
|---|---|---|---|
| 普通商品订单 | ① 发货 ② 延迟/缺货 | 签收可选 | 只有 2 条主线，够用 |
| 定制食谱订单 | ① 付款成功 ② 食谱交付 | 提交售后时申请「售后结果」 | **不增加弹窗次数**：现在是 1 个模板，改成 2 个还是同一次弹窗 |
| 补剂订单 | ① 排期 ② 发货 | 提交售后时申请「售后结果」 | 延迟/补发复用"发货"模板或"售后结果"模板 |
| 健康提醒 | 在档案页单独申请 | — | 需要一个明确的"开启提醒"按钮，客户不点就只发站内 |

> ⚠️ 不要为了多推一条就把额度全花在营销上。额度是客户的信任，花完就没了。

| `character_string` | 32 位以内数字/字母 | 订单号、运单号 |

| `time` | 24 小时制，如 `2026年10月31日 15:01` | |
| `date` | 年月日 | |
| `name` | 10 个以内汉字 | 宠物名 |
| 每个模板 | 最多 5 个字段，类型由模板固定 | |

## 6. 文案建议

### 6.1 站内消息

规则：**只写"发生了什么 + 点进去看什么"，不写会变的内容**（食谱名、日期这类细节点进去现查，避免消息和实际打架）。标题 ≤ 120 字，正文 ≤ 500 字，实际都控制在 30 字内。

| 节点 | 标题 | 正文 |
|---|---|---|
| 付款成功（定制） | 定制订单已付款 | 我们已收到你的付款，营养师开始设计后会通知你。 |
| 付款成功（普通） | 订单已支付 | 订单 {订单号} 已支付成功，发货后会通知你。 |
| 待补资料 | 还差一点资料 | 订单 {订单号} 需要补充{缺什么}，补齐后我们马上开始设计。 |
| 已排期 | 营养师已接单 | 你的定制食谱已进入设计，预计 {日期} 前后交付。 |
| 发货 | 你的订单已发货 | {快递公司}，运单号 {运单号}，点开看加热和保存说明。 |
| 延迟发货 | 发货时间有调整 | 订单 {订单号} 预计改为 {日期} 发货，给你添麻烦了。 |
| 签收 | 订单已签收 | 收到后请尽快冷冻保存，有问题随时找我们。 |
| 食谱交付 | 你的专属食谱已交付 | {食谱名} 已交付，点开看完整食谱。 |
| 重新交付 | 食谱已更新 | 你的专属食谱已重新交付（第 {n} 版），以这一版为准。 |
| 售后受理 | 售后申请已收到 | 我们会在 {n} 个工作日内处理，结果出来会通知你。 |
| 售后完成 | 售后已处理完成 | {一句话结论}，点开看详情。 |
| 售后驳回 | 售后申请未通过 | 原因：{驳回原因}。如有疑问可以直接在订单里联系我们。 |
| 退款到账 | 退款已原路退回 | ¥{金额} 已退回原支付账户，到账时间以微信为准。 |
| 退款失败 | 退款暂未成功 | 订单 {订单号} 的退款没有成功，我们会尽快联系你处理。 |
| 疫苗到期 | {狗狗名} 该打疫苗了 | {疫苗名} 的接种时间 {日期} 快到了，提前安排更稳妥。 |
| 驱虫到期 | {狗狗名} 该驱虫了 | 距离上次驱虫已 {n} 天，建议今天安排。 |

### 6.2 订阅消息

订阅消息的"文案"主要是字段值，尽量短、且不要带营销语。

| 模板 | 字段示例 |
|---|---|
| 订单支付成功 | 订单编号 `SK20261031001`；金额 `¥299.00`；商品 `定制鲜食食谱`；时间 `2026年10月31日 15:01` |
| 发货通知 | 订单编号；快递公司 `顺丰速运`；运单号 `SF1234567890`；发货时间；提示 `点开看加热说明` |
| 售后结果 | 订单编号；结果 `已完成`；说明 `已按你的要求调整` |
| 疫苗提醒 | 宠物名 `豆豆`；疫苗 `狂犬疫苗`；时间 `2026年11月05日`；提示 `提前预约更稳妥` |

> 注意 `thing` 只有 20 字，写不下"你的专属定制食谱已经由营养师完成设计并交付"，一句话说完就够。

## 7. 现状差距与优先级

### P0（先补，直接影响"客户失联"）

1. **定制订单付款成功**：订阅 + 站内，两个都没有。
2. **定制售后被驳回**：订阅 + 站内，两个都没有。
3. **普通订单站内消息**：发货、延迟、签收全靠订阅一条腿，客户没点"开启发货提醒"就彻底收不到。

### P1（两周内）

4. 普通订单「付款成功」站内 + 「缺货/延迟」订阅。
5. 定制「待补资料」「已排期」站内（排期可加订阅）。
6. 疫苗/驱虫提醒启用（代码里目前是 TODO）。
7. **订阅授权与发送结果落库** + 后台看板（现在只有发货通知记了成败，其余静默失败）。

### P2（有余力再做）

8. 消息中心按「订单 / 售后 / 物流」分类；进小程序时提示未读（现在红点只在「我的」）。
9. 退款到账订阅消息。
10. 复购提醒（站内 / 企业微信，不进订阅消息）。
11. 接物流轨迹查询（快递100 等），才能做"派送中/签收/物流异常"三条。

## 8. 可观测性：怎么知道"到底发出去了没有"

现在最大的盲区：**不知道多少客户其实收不到**。

建议加一张通知记录表（Prisma migration，字段 camelCase，落库 snake_case）：

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `customerId` | 收件客户 |
| `channel` | `SUBSCRIBE` / `INBOX` |
| `scene` | `ORDER_PAID` / `SHIPPED` / `DELIVERED` / `AFTERSALE_RESOLVED` … |
| `templateId` | 订阅消息模板（站内为空） |
| `bizType` / `bizId` | 业务指针（订单/交付/售后），**不存正文** |
| `status` | `AUTHORIZED` / `REJECTED` / `SENT` / `FAILED` / `SKIPPED` |
| `errorCode` / `errorMessage` | 微信返回码（43101 = 未订阅） |
| `createdAt` / `sentAt` | 时间 |

后台看板最少要有三个数：**今日应发 / 实际发出 / 因未订阅被跳过**。有了这三个数，才知道该不该上短信兜底。

配套要改的：所有业务统一走一个通知入口（现在补剂是绕过 `CustomerMessageService` 直接写库的，`linkType` 还不在类型里，加通道时容易漏）。

## 10. 附录：不该发通知的节点

避免过度打扰，这几类明确不发：

- 客户**刚在页面上完成**的操作结果（下单成功、提交售后、提交退款申请）。
- **微信已经在推**的（派送中）。
- 纯**营销**（活动、优惠、复购）——不进订阅消息；站内可发，但别塞进"订单"分类。
- **内部进度**（采购、分装、排产）——客户不关心，关心的是"什么时候到我手上"。

> 反过来说：**如果一条通知只能带来"哦"，那就别发。** 通知额度要留给"客户正在等的那件事"。

## 11. 附录：微信的两条硬规则（给运营/客服看）

1. **客服会话**：客户发消息后 48 小时内可回复，这一轮最多 5 条；客户再发一条，重新计时。超过就只能等客户开口。
2. **订阅消息**：客户点一次「允许」只能收到一条；没点「允许」就发不出去，而且客户那边没有任何提示。

所以：**通知是产品的事，不是客服的事。** 该自动发的，必须写进系统里。
