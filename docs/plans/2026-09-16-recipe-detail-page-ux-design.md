## 二、逐项说明

### 2.1 参考价优化评估

**现状（代码实现）**
- 位置：底部固定操作栏内、按钮行上方
- 主文案：`约¥xx.xx/100g`（无匹配生命阶段版本时追加"起"）
- 副文案：`已含冷链配送`
- 取值逻辑：优先取当前生命阶段版本价 → 否则取全阶段最低价 + "起" → 接口无数据则整条不展示
- 样式：金色浅底、右对齐、小字

**做对的地方（建议保持）**
1. 计价口径与真实下单一致，不会"页面一个价、结算另一个价"
2. "已含冷链配送"直击隐藏运费焦虑，是强信任加分
3. 用"起"字保守表达，不越界承诺
4. 按生命阶段版本取价，避免张冠李戴
5. 接口异常时不展示假数据

**待优化（5 处）**

| 编号 | 问题 | 建议 |
|------|------|------|
| PR-1 | `/100g` 不是家长的心算单位 | 有狗狗档案时主数字改「**约¥X/天**」，副行「折合¥Y/100g · 已含冷链配送」；无档案时保持 `/100g` |
| PR-2 | 位置靠后、权重偏低，首屏无价格 | 在「标题与卖点区」增加**价格锚点**（首屏可见），底部价格条保留做临门一脚 |
| PR-3 | 显示"起"时与真实价有落差 | 显示"起"时补一句「按狗狗体重精确计算最终价格」，管理预期 |
| PR-4 | 接口失败 → 页面完全无价格（信息真空） | 失败/无数据时降级为静态说明条：「价格按狗狗体重计算，进入订购可见」 |
| PR-5 | 描边用砖红系 `rgba(180,85,63,.14)`，价格被渲染成警示色 | 改金色系描边（价格是价值锚点，不是警示） |

### 2.2 健康标签的合规审核（重点）

**法规依据（原文）**

1. 《宠物饲料标签规定》（农业农村部公告第 20 号）
   - **第二十条第（一）项**：「**禁止对宠物饲料作具有预防或者治疗宠物疾病的说明或者宣传。**」
   - **第二十条第（五）项**：允许**功能声称**，但严格限定为「维持、增强宠物生长、发育、生理功能或者机体健康的作用」，且必须：
     ① 声称涉及的原料/添加剂须在配方中列示并标注添加量；
     ② **应当具备证明材料**（公开发表的出版物、教科书、配方组成、检测数据或试验报告）；
     ③ 不得涉及疾病。
     示例（官方）："含钙促进骨骼发育"、"含菊苣根粉促进肠道有益菌增殖"。
   - **第十二条 + 附录 5**：「改善**关节炎症**」「改善**慢性肾功能不全**状态」等表述属于**处方粮**（通用名称标"处方"）的标示范畴，且必须醒目标示「**请在执业兽医指导下使用**」。
2. 《中华人民共和国广告法》
   - **第十七条**：除医疗、药品、医疗器械广告外，**禁止其他任何广告涉及疾病治疗功能**，并不得使用医疗用语或易使推销商品与药品、医疗器械相混淆的用语。
   - **第二十八条**：与实际情况不符且影响购买行为的，构成虚假广告。
   - 说明：标签规定管包装，**产品页面同样受广告法约束**，页面上写"肾脏友好"一样有风险。

**判定结论**

| 表述 | 判定 | 理由 |
|------|------|------|
| 肾脏友好 | ❌ 不可用 | 直接指向肾脏，对应处方粮的"慢性肾功能不全"范畴 |
| 关节养护 | ❌ 不可用（如暗示改善/预防） | "改善关节炎症"属处方粮标示范畴；暗示预防则触及疾病预防 |
| 含 Omega-3，有助于维持关节正常功能 | ⚠️ 有条件可用 | 属功能声称，须有证明材料 + 配方标注添加量 |
| 符合 FEDIAF 2021 犬营养标准 | ✅ 可用 | 符合国际标准声称，须能提供证明材料 |
| 含三文鱼油 24% | ✅ 可用 | 成分声称，须在原料组成标注添加量 |
| 适合成犬维持期 | ✅ 可用 | 生命阶段标示，标签规定明确允许 |

→ **你隐藏健康标签的决定是正确的。**

**核心卖点问题的解决框架：四层卖点**

| 层级 | 安全性 | 示例 | 依据 |
|------|--------|------|------|
| ① 原料事实层 | 最安全（主力） | 含三文鱼油 24%、单一动物蛋白、无谷物、鲜肉现制、低温蒸煮、0 防腐剂 | 成分与特性声称规则 |
| ② 标准规范层 | 安全 | 符合 FEDIAF 2021 犬营养标准、全价犬粮 | 第二十条第（四）项第 7 点 |
| ③ 生命阶段层 | 安全 | 幼犬期、成犬维持、老年犬、妊娠/哺乳期 | 第五条允许的生命阶段标示 |
| ④ 功能声称层 | 需证据 + 审核 | 含膳食纤维，有助于维持肠道正常功能 | 第二十条第（五）项，须举证且标添加量 |

**落地三件事**
1. 建立**卖点词库**：
   - 白名单（可直接用）：成分类、工艺类、生命阶段类、标准类
   - 灰名单（需证据 + 人工审核）：功能声称类（维持/有助于/促进）
   - 黑名单（禁止）：肾、肝、关节、心脏、皮肤、结石、糖尿病、炎症、治疗、改善、预防、处方、药、抗炎、消炎、护肝、护肾
2. 把食谱卖点做成**结构化多选标签字段**（而非自由文本），从源头杜绝越界文案
3. 上架前**按词库过一道审核**

> 一句话：把"功效承诺"换成"**成分事实 + 适用对象 + 标准背书**"，既合规又不失高级感。

### 2.3 适用生命阶段（更正我的表述）

- 页面**已经展示**"当前生效的生命阶段"，并支持切换 —— 我此前表述不准确，更正。
- 真正缺的是 `applicableLifeStages`（**该食谱支持的全部阶段清单**）：家长必须点"切换"才知道有哪些可选。
- 且卡片文案「低运动量成犬或老年犬」是行业分级，家长看不懂；「已匹配 / 当前展示」两种前缀的差异也不直观。
- **建议**：卡片直接露出可选摘要（如「可选：幼犬 · 成犬 · 老年犬」）；标签改说人话（见 §3.2）。

### 2.4 状态 / 系列字段展示的目的

- **状态（公开/未公开）**：对普通顾客无正向价值，反而引发困惑。唯一有价值的场景是**员工预览**或**分享链接查看未公开食谱**时，给低调提示「内部预览版本，尚未对外发布」，防止内部误判已上线。
  → **建议：仅当食谱非公开时显示提示；公开时完全不显示。**
- **系列**：目的是**关联浏览与复购**（让家长理解"这是一套方案"并看到其他阶段版本）。若系列内无可跳转目标，展示系列名无意义。
  → **建议：不展示字段本身，只在有内容时做成"同系列其他食谱"推荐位。**
- 结论：两个字段都不作为"信息展示"上页面。

### 2.5 设计软件 / 营养标准

- **设计软件**：去掉（顾客视角无价值，且暴露内部工具名）。
- **营养标准**：由裸术语改为结论式表达 + 可展开解释。
  - 展示：`符合 FEDIAF 2021 犬营养标准 ▸`
  - 展开：`欧洲宠物食品工业联合会（FEDIAF）制定的犬营养标准，规定各生命阶段必需营养素的最低/最高限量。`
  - 位置：从"两格小卡"移到营养区顶部作为信任背书。
  - 前提：法规要求"符合国际标准声称"须能提供检测报告或配方等证明材料 —— 我们有营养计算引擎，具备举证基础，需确认可导出。

### 2.6 8 个营养素怎么"说人话"

> 关联提示：这与 P2-2「专业术语」条目相关，该条目此前**已撤销**（决定保持现状）。本节按"重新考虑要做"来设计，需你确认是否改变原决定。

**三层解读法**

1. **第一层｜分组**（把 8 项归为 3 组人话标题）
   - 「吃得好不好」：蛋白质、脂肪
   - 「消化顺不顺」：膳食纤维、矿物质（原"粗灰分"）
   - 「能量与骨骼」：热量水平（原"能量密度"）、碳水、含水量、钙磷搭配（原"钙磷比"）
2. **第二层｜给状态而非只给数字**：每项显示「达标 / 偏低 / 偏高」（沿用已统一的语义色），数字缩小为次要信息
3. **第三层｜顶部一句话总结**：如「高蛋白、适中脂肪，适合成犬日常维持」

**术语替换建议**

| 原术语 | 建议文案 |
|--------|----------|
| 粗灰分 | 矿物质 |
| 粗纤维 | 膳食纤维 |
| 钙磷比 | 钙磷搭配 |
| 能量密度 kcal/kg | 热量水平（并换算为"每 100g 含 X 千卡"） |
| 含水量 | 水分 |

**前提依赖**：状态判断需要参考区间。
- 首选：**后端补营养参考区间接口**（与营养引擎同源，最权威）
- 过渡：前端内置 FEDIAF 区间，并在页面标注"参考 FEDIAF"，后续切换为后端

#### 已确认决定（D1 · 2026-09-16）：保持现状 + 补「干物质（DM）」口径说明

**事实核验**（后端 `recipes.controller.ts → mapNutritionDetailedData`）：

| 页面指标 | 后端字段 | 实际口径 |
|----------|----------|----------|
| 蛋白质 | `protein_dm_pct` | 干物质（DM） |
| 脂肪 | `fat_dm_pct` | 干物质（DM） |
| 粗灰分 | `ash_dm_pct` | 干物质（DM） |
| 膳食纤维 | `fiber_dm_pct` | 干物质（DM） |
| 碳水 | `carbs_dm_pct` | 干物质（DM） |
| 含水量 | `moisture_pct` | 湿物质（全量基准） |
| 钙磷比 | `ca_p_ratio` | 比值，无口径 |

**关键结论**：这 5 项为**干物质口径但页面未标注**。鲜食含水量通常 60~75%，家长若与膨化粮包装上的湿物质数值直接对比，会严重低估本品营养水平（例：干物质蛋白 28% 可能显示为 8% 的湿物质观感）。
→ 补口径说明**不仅是严谨性要求，本身也是转化优化点**（当前展示把产品"说便宜了"）。

**展示方案**（待视觉确认）：
1. 每项数值后加紧凑后缀：`28.5%（DM）`
2. 区块底部补一句说明：`以上营养指标按干物质（DM）计，即去除水分后的占比；含水量为实际含水率。`
3. 含水量、钙磷比不加后缀

### 2.7 喂食量是否在详情页展示

**同意你的判断：不在详情页展示。** 理由：
1. 精确喂食量取决于体重 + 活动量 + 生命阶段，本质是**配置阶段的产物**；详情页只能给估算。
2. 一旦与订购页数字不一致，会引发"你们自己都对不上"的信任损伤。
3. 详情页真正缺的不是喂食量，而是**花费量级** —— 这一角色由参考价承担。

**建议替代方案**：
- 详情页明确给出**下一步预期**：「进入订购后，将按体重精确计算份量与价格」，用确定性替代留白。
- 已建档家长可显示「约 ¥X/天」（由价格推算的花费预估）—— 这不是喂食量，不冲突。

### 2.8 占比 / 用量列怎么展示

问题本质：食材按「占比 %」，补剂按「每 kg 添加量」，同一列承载两种口径。

| 方案 | 做法 | 评价 |
|------|------|------|
| **A（推荐）** | 拆成两张表：「主料」（原料/制备方法/占比）+「营养补充剂」（补充剂/每 kg 添加量） | 列头语义单一，符合两类物料的业务差异，也为后续"按体重换算克数"打底 |
| B | 仍一张表，一列两口径 + 单位前缀（`占比 12%` / `每 kg 加 3g`），列头写「占比 / 添加量」 | 改动最小，可接受 |
| C | 后端输出可读文案，前端只渲染 | 灵活但依赖后端 |

### 2.9 用「食谱说明」承载一句话卖点

- **位置合适**：说明区在标题下方，是天然卖点位。
- **建议做成两层**：
  1. **一句话定位**（醒目）：由结构化卖点标签组合生成，合规表述
  2. **详细说明**（常规字号）：保留现有 description 内容
- **关键约束**：卖点内容必须来自 §2.2 的白名单/结构化枚举，不得自由发挥，否则说明区会变成违规文案的温床。
- **落地**：给食谱增加「卖点标签」多选枚举字段，页面据此渲染一句话定位。

### 2.10 合规卖点的生产方案（D3 采纳：AI Agent + 标签框架）

**思路**：不建硬编码词库，把合规管控**前移到内容生产环节**（食谱编辑页），复用现有 AI 与标签基础设施。

**现有可复用资产**
| 资产 | 位置 | 说明 |
|------|------|------|
| AI 用途注册表 | `admin-web/src/constants/agentPurposes.ts` | 已有 DEFAULT / RECIPE_DESIGN / NUTRITION_REVIEW / SUPPLEMENT_LABEL，各用途可独立配模型 |
| DeepSeek 接入 | `backend/src/application/recipe-designer/deepseek-chat.ts` | 现成对话能力 |
| AI 服务范式 | `backend/src/application/recipe-designer/ai-design-suggestion.service.ts` | 可参照的既有实现 |
| 健康标签主数据 | `backend/prisma/schema.prisma → RecipeHealthTag`（含层级/排序/颜色）+ `RecipeHealthTagAssignment` | **标签是数据不是代码**，后台可维护 |
| 标签管理 API | `admin-web/src/api/recipeHealthTags.ts` | 已有管理入口 |

**四层架构**

| 层 | 内容 | 是否硬编码 |
|----|------|------------|
| ① 标签字典层 | 按合规四维重组：**原料事实 / 工艺特性 / 适用对象 / 标准背书**；旧的不合规标签**停用不删**（保留历史关联） | 否（主数据） |
| ② AI 生成层 | 新增 AI 用途（建议 `RECIPE_COPYWRITING`），提示词内置合规边界；输入=食谱结构化数据（原料/标签/生命阶段/营养标准），输出=**一句话卖点 + 食谱说明** | 否（配置化提示词） |
| ③ 规则兜底层 | AI 输出**必须过一道敏感词 / 疾病词拦截**（服务端配置表） | **是**（唯一兜底，做成可配置而非写死） |
| ④ 人工确认层 | 编辑页「生成 → 预览 → 修改 → 保存」，不自动发布，保留留痕 | 否（流程） |

**为什么保留第③层**：AI 不是合规责任主体，平台才是；此层是"保险丝"，不作为主要手段，但不可省略。

**集成入口（实测确定）**：`admin-web/src/views/Recipes/RecipeForm.vue`
- 该表单是**唯一**同时包含「食谱说明（`form.description`）、健康标签、营养标准、设计来源」的编辑面
- 小程序端 `pages/recipe-designer/editor.vue` 只编辑配方/原料/营养评估，**不含营销字段**
- → AI 卖点生成功能应集成在**后台 PC 端食谱编辑表单**，紧邻「食谱说明」与「健康标签」字段

**关键前置**：必须先完成标签字典合规审计（见 D8）。否则 AI 会把违规标签扩写为更完整的违规文案，等于把风险自动化、规模化。

#### 现有标签字典合规审计（实测，2026-09-16）

数据来源：本地后端公开接口 `GET /api/v1/recipes/filter-options`（开发库实际数据）。

| 标签 | 关联食谱 | 判定 | 依据 / 建议 |
|------|----------|------|-------------|
| **抗炎** | 5 | ❌ **不可用** | "抗炎"属医疗用语 / 疾病（炎症）相关表述，触及《广告法》第十七条；附录 5 第十九条"改善关节炎症"属处方粮范畴 → **建议停用** |
| **低敏** | 3 | ❌ **不可用** | 暗示降低过敏风险，过敏属病理状态；附录 5 第八条"降低原料和营养素不耐受"属处方粮范畴 → **建议停用** |
| 肠胃友好 | 5 | ⚠️ 需改造 | 隐含对肠胃的功效承诺；附录 5 第七/九条"降低急性肠道吸收障碍""改善消化不良"属处方粮 → 建议改 **易消化**（原料/工艺特性，可举证） |
| 抗氧化 | 2 | ⚠️ 需改造 | 偏向功效表述 → 建议改成分声称，如 **含维生素E** |
| 增重 | 0 | ⚠️ 需改造 | 效果型表述；附录 5 第十六条"改善超重状态"属处方粮 → 建议改为适用对象描述 |
| 护肤 | 0 | ⚠️ 需改造 | 隐含改善皮肤功效；附录 5 第十八条"改善皮肤炎症和过度脱毛"属处方粮 → 建议改 **含Omega-3** |
| 低脂 | 7 | ✅ 可用（须核验） | 法规第二十条第（四）项第 4 点**规定了"低脂肪"的数值门槛**（犬：水分 >65% 时脂肪 ≤4%）→ **须逐食谱核验数值**，不达标即违规 |
| 低钠 | 2 | ✅ 可用（须核验） | 属比较性声称，须以本企业产品为参照并明示，降低 ≥15% |
| 健康犬 | 7 | ✅ 可用（建议微调） | 不涉疾病；建议改为 **日常维持** 更具体 |
| 挑食 | 0 | ✅ 可用 | 描述适用场景，风险低 |

**结论**：10 个标签中，**2 个明确不可用**（抗炎、低敏，涉及 8 条食谱关联），**4 个需改造**，**2 个须逐食谱核验数值**，2 个基本可用。
→ 这印证了"必须先做字典合规化、再交给 AI"的判断。

**生命阶段字典（实测）**：幼犬、成犬、老年犬、低运动量成犬或老年犬、妊娠期、哺乳期 —— 均为法规允许的生命阶段标示；「低运动量成犬或老年犬」术语偏专业，建议保留字典原值但展示层说人话（见 §3.2）。

## 六、验收标准

- 家长视角首屏 10 秒内能说出：这是给什么狗吃的、大致多少钱、下一步做什么
- 页面上不出现：疾病相关表述、内部工具名（Setar）、裸术语（FEDIAF 无解释）
- 加载失败可重试；切换狗狗不丢失滚动位置
- 价格在所有状态下都有确定性表达（有价显示价，无价说明如何获得）
- 未登录点击任一操作：统一引导，登录后回到原食谱并接续任务
