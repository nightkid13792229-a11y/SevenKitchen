## 二、技术前提核实结论

调查覆盖后端 schema、服务层、接口层与小程序侧，结论如下。

### 2.1 可比预期更省力的部分

| 能力 | 现状 | 结论 |
|------|------|------|
| 一句话卖点 | 公开详情接口**已返回** `sellingPoint` | 数据已在页面上流通，只是没用 |
| 「这一单能吃几天」 | `estimatedFeedDays` **已算好**，且已传给结算页 | 只差显示 |
| 营养数据 | 接口**已返回** `nutritionDetailedData`（蛋白 / 脂肪 / 钙磷比等） | 只差显示 |
| 推荐引擎 | `GET /recipes/recommendations/:dogId` **完整存在**，含 `matchScore`、exclusive/general 分区、按 `allergyFoods`/`pickyFoods` 过滤 | 前端目前无人调用 |
| 推荐内容量 | 线上 **92 个公开食谱、29 个系列** | 内容充足 |
| 评论来源区分 | `RecipeReview.source` 区分 `PURCHASED` / `DIY`；`ReviewList` 组件**已内置**「已购买 / DIY制作」标签 | 只需加过滤参数 |
| 试吃装结构 | `OrderItem` 为 `recipeSnapshot` + `orderId`，**一单天然可装多个食谱** | 结构可行 |
| 最低起订量 | 前端常量 `MIN_ORDER_WEIGHT_G = 1000`；后端 `minOrderWeightG` 是**全局配置**（后台可调），非硬编码 | 试吃装可走独立起订规则 |
| 交付时效 | 结算页已有「制作日期 + 急冻 24h + 顺丰特快 1–2 日 + 预计发货 / 收货日期」 | 订购页只需给「节奏」，不必给日期 |
| 订阅消息通道 | `shipping-notification.service` 已在发微信订阅消息 | 复购提醒可复用 |

### 2.2 需要从零建的部分

| 能力 | 现状 | 结论 |
|------|------|------|
| 优惠券体系 | **不存在**（无 coupon / voucher / promotion） | 见 3.4，建议不做券系统 |
| 折扣钩子 | `pricing.service.ts` 有 `discountRate` 参数，但全链路**写死 1.0** | 可复用为「新客首单立减」 |
| 定期配送 / 自动续订 | **不存在**（`subscription` 全部是微信订阅消息，非配送订阅） | 见 3.5，涉及支付签约，跨版本 |
| 一键复购 | **不存在**（无「再来一单」） | 见 3.5 |
| 试吃装商品形态 | **不存在**（无 trial / sample 概念） | 需新产品定义 |

### 2.3 关键风险发现

**① 购买评价为 0 条 —— 比「评论放哪」更严重**

| 指标 | 线上实际值 |
|------|-----------|
| 完成订单 | **204 个** |
| 已支付订单 | **229 个**（`payment_status='SUCCESS'`） |
| 总评论 | **3 条** |
| └ DIY 来源 | 3 条 |
| └ **购买来源** | **0 条** |

204 个完成订单 → 0 条购买评价。**评价生产闭环是断的**。
若现在就把「购买评论」搬到订购成品页，搬过去是个**空板块**。

**② 推荐位曾被有意下线，原因未记录**

- 提交 `64627ce3`（2026-06-14）`fix: remove home personalized recommendations`，从首页删除 286 行。
- 后端引擎保留、前端 API 封装保留，但首页回归测试**明确断言不得使用** `recipeRecommendationApi`。
- 该提交**无原因说明**，文档中也无记录。
- **风险**：推荐质量或展示口径可能存在问题。重新启用前必须先查明原因。

## 三、实施方案

按「投入产出比」排序，分五个阶段。

### 3.1 阶段一：零成本速赢（数据已在手边）

全部为 🟢 成本，建议本轮先做。

| 项 | 做法 | 说明 |
|----|------|------|
| **卖点上移** | 食谱名下方展示 `sellingPoint`（沿用详情页样式） | 接口已返回，页面未用 |
| **显示「约可吃 N 天」** | 分装摘要行补一句「约可吃 N 天」 | `estimatedFeedDays` 已算好 |
| **每日 / 每餐成本** | 底部价格区或摘要区展示「约 ¥X/天」 | 纯计算，对标进口粮的关键锚点 |
| **回详情页入口** | 页面内加「查看完整介绍 / 营养与评价」入口 | 纯跳转，解决最后一步无法回看 |
| **交付节奏说明** | 物流卡补「预约制作 → 急冻 24h → 顺丰特快 1–2 日达」 | 见下方决策说明 |

**关于交付时效（决策 3）的判断：要展示，但内容与结算页不同。**

- 结算页回答「**哪一天到**」——需要地址与预约制作日期，只有结算页才知道。
- 订购页回答「**这个商品多久能到、我能不能等**」——这是**买不买的决策输入**。
- 若不展示，用户配置完一整页走到结算页才发现要等数天，属于**把流失点后移，而非消除流失**。
- 因此：订购页给**节奏**（文案，无具体日期），结算页给**具体日期**，互补不冲突。

> ⚠️ 需要你确认：实际制作 + 发货周期是几天？周期较长时会劝退部分用户，
> 但考虑到客单价高、冷链且已有「破损全额仅退款」，透明化的收益大于损失。

### 3.2 阶段二：信任与风险逆转

| 项 | 做法 | 前置条件 |
|----|------|----------|
| **售后保障板块** | 独立板块，突出三条：<br>① 破损 / 变质：**无理由仅退款，不退货，全额退款**<br>② 冷链履约承诺（顺丰生鲜 + 冷冻包材 + 冰袋）<br>③ 营养标准背书（已有，并入该板块作为起点） | 需你确认对外文案口径与赔付流程 |
| **挑食顾虑引导** | 不承诺「不爱吃退款」，改为引导试吃装（见 3.6） | 依赖试吃装上线 |
| **致敏原提示** | 结合狗狗档案的 `allergyFoods`，提示本单含有的相关食材 | 数据已存在，需确认展示口径 |
| **溯源 / 质检背书** | 检测报告、资质、中央厨房素材 | 需素材 |

### 3.3 阶段三：连带推荐

引擎现成，重点是**先查明下线原因**再启用。

| 阶段 | 做法 | 成本 |
|------|------|------|
| **3.3.1 同系列推荐** | 接口已返回 `availableLifeStageVersions`。看幼犬版时提示「同款还有 成犬版 / 老年版」 | 🟢 纯前端 |
| **3.3.2 相似食谱推荐位** | 订购页底部「可能也适合 {狗狗名}」，调用已有推荐引擎（需排除当前食谱） | 🟡 需确认下线原因 |
| **3.3.3 试吃装推荐位** | 见 3.6，最强的连带载体 | 🔴 新产品 |

> ⚠️ **启用前必做**：查明 `64627ce3` 的下线原因，并确认推荐结果**不暴露未合规的健康标签**
> （这是与标签合规清理相关的敏感点）。

### 3.4 阶段四：优惠 —— 建议只做「新客首单立减」，不做券系统

**不建议本轮做券系统**：券模板 + 领取记录 + 订单核销 + 取消退还 + 后台管理是一整个子系统，
本轮做不完且容易出错。

**建议做法**：规则型「新客首单立减」，复用已有 `discountRate` 钩子。

- 全局配置增加「新客首单立减 X% / 立减 ¥X」
- 下单时判断该用户无已支付订单 → 标记为新客
- 价格预览链路带上折扣，订购页展示「新客首单立减 ¥XX」

**需要你决策**：
1. 折扣力度（百分比还是固定金额）
2. 是否与其他优惠叠加
3. 退款 / 取消时折扣如何处理
4. 是否需要防刷（同人多账号）

### 3.5 阶段五：复购 —— 建议只做「复购提醒 + 一键沿用」，不做定期配送

**定期配送不现实**：涉及微信支付**委托代扣签约**（需单独申请）、排期、自动下单、失败重试，
是跨版本的大工程。

**建议做法**：吃完提醒 + 一键复购，全部基于现有数据与现有消息通道。

| 项 | 做法 | 依赖 |
|----|------|------|
| **吃完提醒** | `estimatedFeedDays` + 收货日期 → 推算「约 X 月 X 日吃完」→ 到点发微信订阅消息 | 复用 `shipping-notification.service` |
| **提醒落地页** | 点开直接回到该食谱、该配置的订购页 | 需支持带配置参数进入 |
| **一键沿用上次配置** | 若该用户买过此食谱，订购页顶部显示「你上次买的是 150g×3袋，一键沿用」 | 需查历史订单 |

> 定期配送（委托代扣）建议列入**下一轮**独立评估。

### 3.6 阶段六：试吃装（新产品，非页面改动）

这是解决「挑食顾虑」的正确方向：把不敢承诺的「不爱吃退款」，
换成**小额试吃降低试错成本**，风险可控且能带连带销售。

**已核实**：一单可装多个食谱（`OrderItem` 结构支持）；最低起订量是全局配置，可走独立规则。

**需要先定义的产品问题**：
1. 装几个食谱？每个多少克？
2. 定价逻辑：单价高于还是低于常规装？（试吃通常允许略高单价）
3. 能否自选食谱，还是固定搭配？
4. 是否计入「新客首单立减」？
5. 是否受 1000g 起订量约束？（建议豁免）
6. 试吃装的售后是否同样适用「破损全额仅退款」？

### 3.7 关于评论拆分（决策 5）—— 建议调整顺序

**方向认同，但建议先修「评价生产」，再做「评价展示」。**

| 步骤 | 做法 | 说明 |
|------|------|------|
| **第 1 步** | 修评价生产闭环：订单完成后引导评价（订阅消息提醒 + 订单详情醒目入口 + 可选激励） | **这是当前真正的断点** |
| **第 2 步** | 后端评论列表接口加 `source` 过滤参数；`ReviewList` 组件加 `source` prop | 小改动 |
| **第 3 步** | 订购成品页放「买过的人怎么说」（`source=PURCHASED`） | 需有内容 |
| **第 4 步** | **务必做空态兜底**：0 条时显示「成为第一个评价的人」或直接隐藏 | 避免空板块伤害信任 |

## 四、依赖与风险

| 风险 | 说明 | 应对 |
|------|------|------|
| 推荐位下线原因未知 | 可能是推荐质量或展示口径问题 | 启用前查明 `64627ce3` |
| 购买评价为 0 | 展示板块会空 | 先修评价生产，并做空态兜底 |
| 交付周期透明化的劝退效应 | 周期长时会流失部分用户 | 属正确劝退，售后成本更低 |
| 优惠防刷 | 新客判定可能被多账号绕过 | 需产品确认风控口径 |
| 试吃装是新产品 | 涉及定价、起订规则、售后口径 | 需独立产品定义 |
| 定期配送工程量大 | 涉及支付签约 | 列入下一轮 |

## 五、建议的推进顺序

1. **阶段一（零成本速赢）** —— 立刻可做，全部数据已就绪
2. **阶段二（信任与风险逆转）** —— 需先定售后文案口径
3. **阶段三 3.3.1（同系列推荐）** —— 零后端改动，可并入阶段一
4. **3.7 第 1 步（修评价生产）** —— 越早做越早积累评论资产
5. **阶段四（新客首单立减）** —— 需定折扣规则
6. **阶段五（复购提醒）** —— 依赖订单积累
7. **阶段六（试吃装）** —— 需产品定义，建议独立立项
