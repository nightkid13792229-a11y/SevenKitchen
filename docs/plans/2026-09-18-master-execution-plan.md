## 二、板块 A · 首单路径修剪

### A0 现状（实测 14 步）

```
首页 → 卡片 → 详情页 → 点「买成品」→ 登录弹窗 → 登录页 → ★强制绑手机
  → ★强制完善头像昵称 → 回到【详情页】(不是订购页) → 再点一次「买成品」
  → 订购页 → ★创建狗狗档案(12 项) → 选周期/分装 → 出价
  → 确认订单 → 结算页 → ★新增地址 → 选日期 → 提交 → 支付
```

★ = 纯填表。

### A1 改什么

| # | 改动 | 现状 | 改为 | 涉及文件 |
|---|------|------|------|----------|
| **A1** | 点「买成品」需登录时，登录后**直达订购页** | 回到食谱详情页，需再点一次 | 直达 `/pages/recipe-order/index?recipeId=&dogId=&lifeStage=` | `pages/recipe-detail/index.vue`（`goToOrder` / `promptLoginAndRedirect`） |
| **A2** | 「自己做」同理，登录后**直达 DIY 配置页** | 回到食谱详情页 | 直达 `/pages/recipe-diy/index?...` | 同上 |
| **A3** | 登录后**不再强制绑手机** | 登录成功即跳绑定页 | 删除该跳转 | `pages/login/index.vue` |
| **A4** | 登录后**不再强制完善头像昵称** | 登录成功即跳完善资料 | 购买链路直接进目标页 | `pages/login/index.vue` |
| **A5** | 登录按钮文案改回真实动作 | 「手机号快捷登录」（实际只做微信登录） | **「微信一键登录」** | `pages/login/index.vue` |
| **A6** | 游客点「暂不登录，先逛逛」时**记住订单意图** | 意图丢失 | 记 pending 意图，下次登录后自动续上（复用客服那套机制） | `pages/login/index.vue` + `App.vue` |

### A2 为什么可以安全地不做登录时绑手机（已核实）

- **结算页本来就会强制绑手机**：`pages/checkout/index.vue:883` 调 `ensurePhoneBound()`，未绑定会带返回路径跳到绑定页；
- 绑定完成后能正确回到原页面：`utils/account.ts:99-101` 用 `getCurrentPagePathWithQuery()` 作 redirect。

→ **登录时那次是重复的，删掉不会漏。**

### A3 预期结果

**14 步 → 10 步**；填表从 4 次降到 3 次，且**全部发生在顾客已经决定要买之后**：
手机号（结算页，本来就要）、狗狗档案（按体重精算的唯一输入，属核心价值不是摩擦）、地址（结算页必需）。

### A4 不做

- ❌ **不改「必须建档」**。档案是精算的唯一输入。但**建档的体验改造**（先只要名字+体重就出价，其余字段后补）列入**二期**，因为它涉及建档页结构，风险高于收益。
- ❌ 不动地址收集。

## 三、板块 B · 订购页价值补完

### B1 现状

订购页从第 1 屏到最后一屏是**纯配置**：生命阶段 → 封面 → 菜名 → 标准卡 → 选狗 → 六项参数 → 天数 → 分装 → 原料明细 → 说明 → 底栏。
**全页没有一句"为什么值得买"。**

### B2 补什么（全部零后端改动）

| # | 补什么 | 数据来源 | 放哪里 |
|---|--------|----------|--------|
| **B2.1** | **一句话卖点** | 详情接口已返回 `sellingPoint`，订购页已在调同一接口，只是 `Recipe` 接口没定义该字段 | 菜名正下方，沿用详情页样式 |
| **B2.2** | **售后保障板块** | 政策已确认 | 原料明细之后、说明之前 |
| **B2.3** | **交付节奏** | 文案（结算页已有同样说明） | 说明区物流卡：`预约制作 → 急冻 24h → 顺丰特快 1–2 日达` |
| **B2.4** | **回详情页入口** | 纯跳转 | 页内一行小字「查看完整介绍 / 营养与评价」  ~~已撤销（2026-09-19）：与「自洽≠重复」原则冲突，订购页不放把用户送走的出口~~ |

### B3 ⚠️ 已按你的意见修订：不做「可吃 N 天」，不做「每天成本」

**理由（已核实）**：

顾客在订购页选的就是「7 天 / 15 天 / 30 天」，而默认分装算法是
`每袋 = 每日饭量 ÷ 餐次`、`袋数 = 餐次 × 天数`。
所以**总量天然等于"顾客选的天数"**，`estimatedFeedDays` 算出来就是他刚选的那个数字——**是回声，不是信息**。

**改为：让"天数"这件事说清楚 + 强化已有的每袋价**

| 动作 | 现状 | 改为 |
|------|------|------|
| 区块标题 | 「饭量设置」 | **「一次准备几天的量」** |
| 天数选项 | `7天 / 15天 / 30天`（保持） | 保持 |
| 分装摘要 | `每袋 150g / 共3袋 / 总净重 450g` | **保持**（清晰，不动） |
| 底栏副价 | `¥23.00/袋` | **`每餐约 ¥23.00`**（默认分装时 1 袋 = 1 餐）+ 辅助说明「每袋 = 一顿」 |
| 自定义分装时 | `均价 ¥23.00/袋` | **保持**（自定义时袋 ≠ 餐，不能叫"每餐"） |

> **为什么「每餐」比「每天」更直接**：顾客能立刻对标"一顿进口粮多少钱""一顿外卖多少钱"，
> 而"每天成本"是个需要二次换算的数字，且鲜食按天算天然比干粮贵 2–3 倍，**单摆日成本会主动招来比价**。
> 「每餐」既是从首页 `¥X/100g` 到整单总价之间的换算桥梁，又不制造新的比较焦虑。

> **仅保留一处例外**：当顾客使用**自定义分装**时（此时总重与"整数天"不对齐），
> 分装摘要行补一句「约可吃 N 天」——**只有在这种情况下它才是新信息**。

### B4 暂不做（需要素材或规则）

| 项 | 为什么等 |
|----|----------|
| **配餐实拍**展示在订购页 | 素材有（订单原料照片），但"展示哪一张"需要定规则（最近一单？随机？），且涉及他人订单图片的授权口径 |

## 四、板块 C · 售后承诺上线

### C1 政策口径（已按你的意见定稿）

> **收到后如有破损、变质等品质问题：全额退款，或免费重做。**

| 项 | 决策 |
|----|------|
| 是否写「无理由」 | ❌ **不写** |
| 承诺范围 | 破损、变质等**品质问题** |
| 处理方式 | **全额退款 或 免费重做**（与系统现有 REFUND / REMAKE 两档完全对应） |
| **人工审核** | ✅ **保留**，暂不放开直退；后续观察无问题再逐步放开权限 |

### C2 上线位置（说一次、复述一次）

| 位置 | 作用 | 文案方向 |
|------|------|----------|
| **订购页**（原料明细之后） | 建立信任 | 「收到后如有破损、变质等品质问题，可申请全额退款或免费重做」+ 冷链承诺 |
| **确认订单页**（价格区下方） | 支付前最后一次安心 | 一句话复述 |
| **订单详情页**（已有售后区） | 履约期兜底 | 沿用现有入口，补一句政策说明 |

### C3 系统无需改动

已核实：退款金额本来 = 整单金额，模型里**没有任何"是否需要寄回"的字段**，即**系统现在就是这个模式**——只是没告诉顾客。

## 五、板块 D · 首页分区 + 简化版个性化推荐

### D1 分区（解决"货架气质是病号饭"）

| 动作 | 内容 |
|------|------|
| 首页默认货架 | 只放**日常主食**（正向角标：食材 / 口味 / 生命阶段） |

| 用词规范 | 见 `2026-09-18-special-needs-wording-compliance.md` 的 A/B/C/D 四类词表 |

> ⚠️ 前置：**P1（清理违规内容）必须先完成**，否则专区里放的就是违规内容。

### D2 简化版个性化推荐（可重启，下线原因是"太复杂"）

## 六、板块 E · 漏斗埋点

**现状：小程序只有狗狗档案的事件埋点，成品链路上一个都没有。**

| 漏斗 | 事件序列 |
|------|----------|
| **成品** | 首页曝光 → 详情页浏览 → 点「买成品」→ 登录完成 → 建档完成 → 订购页出价成功 → 进结算页 → 支付成功 |

| **DIY（对照）** | 详情页 → 生成制作单 |

**关键指标**：每步流失率、「点买成品 → 支付成功」整体转化率、次日 / 7 日复购率。

> 一期**只做采集**，不做看板。
