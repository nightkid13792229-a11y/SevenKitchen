# 一期落地方案 · 止血与度量

> 版本：v1（2026-09-18）
> 上游：`2026-09-18-finished-fresh-food-top-level-design.md`（顶层设计 v4）
> 范围：**成品鲜食链路**。补剂线（补剂商城）由另一任务会话负责，本文不涉及。
> 一期目标：**让现有链路不再漏人 + 让已有价值看得见 + 让效果可度量**。不新增后端功能。

## 零、一期为什么是这四件事

顶层设计里三条产品线中，补剂线已在别处推进；定制线和试吃装都需要新的下单能力。
**一期只做「不需要新后端能力、但能立刻减少流失」的部分。**

| 一期做 | 为什么现在做 |
|--------|-------------|
| ① 首单路径修剪 | 首次购买实测 14 步，其中 4 步是纯填表；改动极小、流失最大 |
| ② 订购页价值补完 | 数据**全都在前端已经拿到了**（卖点/可吃天数/每天成本），只是没展示 |
| ③ 售后承诺上线 | 政策已确认可对外；系统本来就支持整单退不退货 |
| ④ 漏斗埋点 | 现在只有狗狗档案埋点，**所有优化都在猜** |

## 一、首单路径修剪

### 1.1 实测的 14 步（现状）

```
首页 → 卡片 → 详情页 → 点「买成品」→ 登录弹窗 → 登录页 → ★强制绑手机
   → ★强制完善头像昵称 → 回到【详情页】(不是订购页) → 再点一次「买成品」
   → 订购页 → ★创建狗狗档案(12 项) → 选周期/分装 → 出价
   → 确认订单 → 结算页 → ★新增地址 → 选日期 → 提交 → 支付
```

★ = 纯填表，不给顾客任何价值。

### 1.2 三个关键事实（本次核实，决定能砍到什么程度）

| # | 事实 | 证据 | 结论 |
|---|------|------|------|
| 1 | **结算页已经强制绑手机** | `pages/checkout/index.vue:883` 调 `ensurePhoneBound()`，未绑定会带返回路径跳到绑定页 | **登录时那次绑手机是重复的，可以直接去掉** |
| 2 | 绑手机后能正确回到原页面 | `utils/account.ts:99-101` 用 `getCurrentPagePathWithQuery()` 作 redirect | 体验不会断 |
| 3 | 登录页的按钮叫「手机号快捷登录」，但实际只做微信登录 | `pages/login/index.vue:36-42` + `handleWechatLogin` 调 `/auth/wechat-login` | 文案与实际不符，也放大了"必须绑手机"的错觉 |

### 1.3 改造清单

| # | 改什么 | 位置 | 改为 |
|---|--------|------|------|
| **A1** | 点「买成品」需登录时，登录后**直达订购页**，不停在详情页 | `pages/recipe-detail/index.vue` `goToOrder` / `promptLoginAndRedirect`（1165-1215） | redirect 目标由 `/pages/recipe-detail/index?...` 改为 `/pages/recipe-order/index?recipeId=&dogId=&lifeStage=` |
| **A2** | 「自己做」同理，登录后直达 DIY 配置页 | 同上 `generateDiySheet` | redirect 目标改为 `/pages/recipe-diy/index?...` |
| **A3** | 登录后**不再强制绑手机** | `pages/login/index.vue:224-232` | 删除这段跳转；改由结算页兜底（已存在） |
| **A4** | 登录后**不再强制完善头像昵称** | `pages/login/index.vue:236+` `needsProfileSetup` 分支 | 购买链路直接进目标页；头像昵称引导移到「我的」页可选 |
| **A5** | 登录页去掉"必须绑手机"的错觉 | `pages/login/index.vue:36` | 按钮文案改回「微信一键登录」 |
| **A6** | 游客点「暂不登录，先逛逛」时**不丢订单意图** | `pages/login/index.vue` `skipLogin` | 记一个 pending 意图；下次登录后自动续上（复用客服那套 pending target 机制 `App.vue:14-68`） |

**预期效果**：14 步 → **10 步**，其中填表从 4 次降到 3 次（手机号、档案、地址），且**全部发生在顾客已经确定要买之后**。

### 1.4 不做的事

- ❌ **不动"必须建档"**。狗狗档案是按体重精算的唯一输入，是我们的核心价值，不是摩擦。
  但要改**它出现的位置和语气**——见 1.5。
- ❌ 不动地址收集（结算页本来就该收）。

### 1.5 建档的体验改造（二期候选，一期先记）

现在：订购页 → 整页空态「请先创建狗狗档案」→ 跳走 → 填 12 项 → 才回来。
建议方向（**二期**）：先只要"名字 + 体重"就出方案与价格，其余字段（体况/活动量/零食）在出结果后以"让方案更准"的名义逐步补。
> 一期不动，因为它涉及建档页结构，风险高于收益。

## 二、订购页价值补完（数据都在手上）

### 2.1 现状

订购页从第 1 屏到最后一屏是**纯配置**：生命阶段 → 封面 → 菜名 → 标准卡 → 选狗 → 参数 → 天数 → 分装 → 原料明细 → 说明 → 底栏。
**全页没有一句"为什么值得买"。**

### 2.2 可以立刻补上的（零后端改动）

| # | 补什么 | 数据来源 | 放哪里 |
|---|--------|----------|--------|
| **B1** | **一句话卖点** | 详情接口**已返回** `sellingPoint`，订购页已在调同一接口，只是没存进本地结构（`recipe-order/index.vue:500-515` 的 `Recipe` 接口无此字段） | 菜名正下方，沿用详情页样式 |
| **B2** | **约可吃 N 天** | `estimatedFeedDays` **已算好**（`index.vue:827`） | 分装摘要行 `每袋 150g / 共3袋 / 总净重 450g` 后面补一句 |
| **B3** | **每天成本** | `amountTotal ÷ estimatedFeedDays`，纯计算 | 底栏价格下方小字 |
| **B4** | **售后保障板块**（见第三节） | 政策已确认 | 原料明细之后、说明之前 |
| **B5** | **交付节奏** | 文案（结算页已有同样的说明可复用） | 说明区的物流卡：`预约制作 → 急冻 24h → 顺丰特快 1–2 日达` |
| **B6** | **回详情页入口** | 纯跳转 | 页内一行小字「查看完整介绍 / 营养与评价」  ~~已撤销（2026-09-19）：与「自洽≠重复」原则冲突，订购页不放把用户送走的出口~~ |

### 2.3 ⚠️ 一个需要你拍板的点：价格怎么讲

首页展示的是 **¥X/100g 起**（小单位，听起来便宜），订购页出的是**整单总价**（¥345–976）。
中间缺一次换算，用户会有"怎么这么贵"的落差。

三种讲法：

| 方案 | 文案示例 | 优点 | 风险 |
|------|----------|------|------|
| **① 讲天数**（推荐为主） | 「这一单 = 你家狗 **7 天**的口粮」 | 把总价翻译成"逛一次超市"，最不吓人 | 需要用户理解"一次买一周" |
| **② 讲每天成本** | 「约 **¥83/天**」 | 便于与进口粮/处方粮对比 | **单价高时反而显贵**（鲜食按天算天然比干粮贵 2–3 倍） |
| ③ 都讲 | 主「7 天」+ 副「约 ¥83/天」 | 信息完整 | 版面变挤 |

> **我的建议：主讲①、副讲②，且②必须带对比语境**（例如"含冷链配送与按体重精算"），
> 否则单摆一个 ¥83/天 会主动招来"比某某粮贵"的联想。

### 2.4 暂不做（需要素材或接口）

| 项 | 为什么等 |
|----|----------|
| **配餐实拍** | 素材有（订单原料照片），但"订购页该展示哪张"需要定规则（最近一单？随机好评单？），且涉及他人订单图片的授权口径 |

## 三、售后承诺上线

### 3.1 政策（已确认可对外）

> **破损 / 变质：无理由仅退款，不退货，全额退款。**
> **不爱吃：不作承诺**（改为试吃装承接，五期）。

**系统现状**：流程本来就是这个模式——退款金额 = 整单金额，模型里**没有任何"是否需要寄回"的字段**。
换句话说：**我们已经在这么做了，只是没告诉顾客。**

### 3.2 上线位置（三处，只说一次、复述一次）

| 位置 | 作用 | 文案方向 |
|------|------|----------|
| **订购页**（原料明细之后） | 建立信任 | 「收到后如有破损或变质，**无理由全额退款，不用寄回**」+ 冷链承诺 |
| **确认订单页**（价格区下方） | 支付前最后一次安心 | 一句话复述 |
| **订单详情页**（已有售后区） | 履约期兜底 | 沿用现有入口，补一句政策说明 |

### 3.3 需要你给的

- **对外文案的最终口径**（是否写"无理由"三个字；是否需要写"24 小时内拍照"之类的流程条件）
- 赔付流程是否与现有 `aftersale-apply`（退款/重做/投诉三档）一致

> ⚠️ 注意：一旦对外承诺"全额退款"，`aftersale` 的**审核环节**（目前 REFUND 仅 ADMIN 可审）会成为体验瓶颈。
> 建议明确：这类退款是否**免审核直退**。这属于运营决策。

## 四、首页分区 + 简化版个性化推荐

### 4.1 分区（解决"货架气质是病号饭"）

现在 24 道菜的封面角标里有 5 道是疾病/症状名（IBD、草酸钙结石、胆泥淤积…），**和日常主食混在同一个货架**。

| 动作 | 内容 |
|------|------|
| 首页默认货架 | 只放**日常主食**（正向角标：食材/口味/生命阶段） |
| 新增专区入口 | **「特殊需求」**独立入口，疾病/症状类食谱收进去 |
| 专区口径 | 配比依据 + **适用边界** + **不替代兽医诊疗**；**禁用「处方粮」一词**；对外用「专属定制 / 专项营养定制」 |
| 最终用词 | ⚠️ 需过一次合规确认 |

### 4.2 简化版个性化推荐（已确认可重启，下线原因是"太复杂"）

| 做 | 不做 |
|----|------|
| 有档案时，首页顶部「给 {狗名} 的推荐」**横向 3 张卡** | ❌ 「专属优先 / 通用也适合」双分组（"复杂"的来源） |
| 每张卡一行理由（"成犬 · 12kg · 已避开鸡肉"） | ❌ 狗狗切换器 / 星级 / 匹配分 |
| 一个主动作「按推荐配一周」 | ❌ 无档案时铺满整屏 |
| 无档案时只留「30 秒告诉我你家狗」 | — |

⚠️ **两处工程注意**：
1. 现有回归测试**明确断言首页不得使用 `recipeRecommendationApi`**（`home.regression.spec.ts:288-303`），重启必须同步更新该测试。
2. 后端推荐接口**还在**（`GET /recipes/recommendations/:dogId`，含过敏原 −40 / 挑食 −12 的打分），属"孤儿接口"，可直接复用。

## 六、漏斗埋点

**现状：小程序只有狗狗档案的事件埋点，成品链路上一个埋点都没有。**

### 6.1 要装的漏斗

| 漏斗 | 事件序列 |
|------|----------|
| **成品** | 首页曝光 → 详情页浏览 → 点「买成品」→ 登录完成 → 建档完成 → 订购页出价成功 → 进结算页 → 支付成功 |
| **首单专线** | 「买成品」触发登录 → 登录耗时 → 是否被绑手机拦截 → 是否被建档拦截 |
| **DIY**（对照） | 详情页 → 生成制作单 → 补剂点击 |

### 6.2 关键指标

- **每一步的流失率**（尤其是登录、绑手机、建档三个已知卡点）
- **从「点买成品」到「支付成功」的整体转化率**
- **次日/7 日复购率**

> 一期只做采集，不做分析看板；看板可以后置。

## 八、一期需要你拍板的 5 件事

1. **价格怎么讲**：主「这一单 = 你家狗 N 天的口粮」、副「约 ¥X/天」（推荐），还是只讲其中一个？
2. **售后文案口径**：对外写不写"无理由"？是否需要流程条件（如 24 小时内拍照）？
3. **退款是否免审核**：承诺全额退款后，`aftersale` 的人工审核环节是否放开直退？
4. **安全区/敏感区**：特殊需求专区的用词，由谁做合规确认？
5. **是否授权我开始改小程序代码**（改完我会跑 `npm run preview` 或 `build:mp-weixin` 并告知你微信开发者工具该打开哪个目录）？
