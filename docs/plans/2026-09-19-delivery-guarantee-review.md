## 一、现状

位于「原料明细」之后、「说明」之前。一张白底卡片里平铺三条：

```
交付与保障
────────────────────────────────────────
①  交付节奏
   预约制作 → 制作完成后急冻 24 小时 → 顺丰特快 1–2 日送达

```

编号是圆形浅绿底徽章；标题 27rpx 加粗；描述 24rpx 灰字。

## 二、信息结构的问题

### A1. ⚠️ 用 1/2/3 编号是语义误导

这三项是**并列关系**（我们怎么送 / 怎么保温 / 坏了怎么办），不是步骤。
而第 ① 条**内部本身就有箭头序列**（预约制作 → 急冻 24h → 发货）——
外层再套一层数字编号，等于**两套"顺序语言"打架**，读者会下意识以为"要先干1再干2"。

### A2. ⚠️ 两类不同性质的内容被平铺，核心价值被埋在最后

| 条目 | 性质 |
|------|------|
| ① 交付节奏、② 冷链履约 | **过程说明**（信息） |
| ③ 破损变质全额退款 | **风险逆转**（承诺） |

按转化逻辑，**「全额退款」才是这个板块真正的价值所在**——
食物类目最大的下单阻力就是"坏了怎么办"，而我们现在把它放在**第 3 条**，
用户要读完两行物流说明才看到它。

### A3. 标题把两个决策问题绑在一起

「交付」（多久能到）和「保障」（出问题怎么办）是两个独立问题。
绑在一起不是不行，但排序上**应该让「保障」先行**，因为它是消除顾虑的那一个。

## 三、内容完整性的问题（我认为最需要补的）

### B1. 🔴 缺「多久之内能申请」——这是真实的风险点

我核实了系统里的真实规则（`miniapp/src/utils/order-aftersale.ts`）：

```
已完成订单：收货后 7 天内可申请退款 / 重做（投诉不受限）
const COMPLETED_AFTERSALE_WINDOW_MS = 7 * 24 * 60 * 60 * 1000
```

**订购页一个字都没提这个时效。**

后果很具体：顾客看到"破损变质可全额退款"，会理解成"随时可退"；
收货两周后想起来要退，被系统拒绝 → **纠纷 + 差评**，而且他会认为我们"说话不算话"。

### B2. 🔴 缺「去哪申请」

用户读懂了"可以退"，但**不知道从哪里进**。
实际路径是：「我的订单 → 订单详情 → 售后服务」或订单列表卡片的「申请售后」。
这句必须写，否则"可以退"就只是一句空话。

### B3. 🟡 「不爱吃」完全没有回应

这是鲜食**第一大顾虑**（挑食），当前板块里一个字都没有。

你之前定的口径是「不爱吃：不作承诺，用试吃装承接」——
但**试吃装还没做**，所以目前这块是**纯空白**，顾客的顾虑没有任何落点。

### B4. 🟡 「不用寄回」没说出口（对我们有利）

我核对过数据模型：**根本没有"是否需要寄回"的字段**，
退款金额恒为整单金额（`orders.controller.ts`），也就是**系统本来就是仅退款、不退货**。

而"不用寄回"对顾客是**明确的好处**（省事、不用跑快递），我们却没说。

## 四、UI 交互的问题

### C1. 三行纯静态文本，读完没有出口

**我的判断：这里不该加交互。** 理由：

1. 按我们刚立的准则——**订购页不给"离开这一页"的理由**；
2. 此时**订单还不存在**，所以不可能有"申请售后"这个动作；
3. 唯一可能的动作是"联系客服"，而底栏**已经有常驻客服入口**。

→ 结论：靠文案说清楚即可，不加按钮、不加跳转。

### C2. 编号徽章只是装饰，不传递信息

现在 ①②③ 两个作用都没有：既没表达顺序（本来就不是步骤），也没帮助扫读。
建议让「全额退款」那一条**视觉突出**，另外两条降为普通说明。

### C3. 「顺丰生鲜」在同一段里出现两次

第 ① 条说"顺丰特快"，第 ② 条说"顺丰生鲜配送"，读起来有重复感。

## 五、小问题

### D1. 死模板残留

物流卡（`card.mediaKind === 'logistics'`）的模板与样式**还在代码里**，
但 `productExplanationCards` 只产出 `storage` 和 `cooking` 两种，**没有任何卡片会命中它**。

风险：以后有人"修复"这个卡片，就会和「交付与保障」的物流信息**重复**。
建议清掉（模板 + 样式）。

### D2. 不建议重复的一点

「收到后请立即冷冻」在下方「说明」板块**已经有了**（"收到后请尽快放入冷冻或冷藏环境"）。
**不建议在保障板块再写一遍**——这正是我们刚反对过的"同一信息在两处重复"。
