## 零、已确认的六条业务决策

| # | 决策 |
|---|------|
| 1 | 售价**由系统按原料等成本自动算出**，核心定价参数解耦到 Web 后台可调 |
| 2 | 单次限购 **5 套**，参数后台可调 |
| 3 | 运费走**现有按重量的运费模板** |
| 4 | 库存**低于 10 套**时后台提醒补货，并提供**一键备货/排产** |
| 5 | **不计入**新客首单立减 |
| 6 | **一期就要把备货生产做进系统** |

补充确认：

| 项 | 定稿 |
|---|---|
| 生产方式 | 提前做好一批，急冻后入库，**现货发售** |
| 组合方式 | **后台预设固定组合**，顾客不挑菜 |

## 三、定价

### 3.1 参数解耦（后台「试吃装设置」）

| 参数 | 默认 | 说明 |
|---|---|---|
| 试吃倍率 | 1.25 | 成本 → 实收 |
| 价格圆整 | 进位到 1 元 | 可选：不圆整 / 0.1 元 / 1 元 |
| 单次限购套数 | 5 | |
| 补货预警阈值 | 10 套 | |
| 一键备货默认套数 | 20 套 | |
| 保质期（月） | 6 | |
| 允许强制排产（跳过采购完成检查） | 开 | 记操作日志 |

复用现有「全局配置」，**不重复造**：人工时薪、间接成本（元/kg）、批次产能、批次利用率、补充剂损耗率、目标利润率、运费模板。

### 3.2 合并定价公式

```
单套成本 = Σ(5 道菜的原料成本)            ← 含出肉率、损耗率、补剂
         + Σ(各菜毛重 × 人工单价_i)        ← 人工单价按各菜 batchLaborHours 算
         + 总毛重 × 间接成本费率
         + 包材成本（5 道菜袋规格合并后一次计算，泡沫箱/冰袋按总净重算一次）

实收（试吃价）  = 单套成本 × 试吃倍率 → 圆整
划线价          = 单套成本 ÷ (1 − 目标利润率) → 圆整
立省            = 划线价 − 实收
```

### 3.3 实现方式：抽取，不复制

把 `PricingService.calculateOrderPrice` 内「算一道菜的原料成本 + 毛重」的循环
（`pricing.service.ts:332-593`）抽成可复用方法，供两处调用：

1. 现有 `calculateOrderPrice`（**行为必须完全不变**）
2. 新增 `calculateTastingPackPrice`（多菜合并）

**硬约束**：抽取前后，用真实食谱 + 固定输入跑价格一致性对比，**误差必须为 0**。
新增特征化（golden snapshot）回归测试锁死。

## 四、现货下单链路

```
顾客点链接 → 试吃装详情页
  → 服务端实时算价（成本 × 试吃倍率）+ 运费（现有模板）
  → 生成价格快照（15 分钟有效，防篡改）
  → 下单：原子扣库存（先到期先出），库存不足直接拦
  → 支付 → 已付款
  → 后台直接发货（不走采购/生产/急冻）
  → 超时未付款 / 取消 → 自动释放库存
```

- 关键点：`OrderType.TASTING_PACK` 的订单**必须显式排除**在采购清单生成与排产查询之外
  （不依赖"碰巧查不到"）。
- 现货订单 `target_production_date` 置空。

## 五、备货生产链路

```
后台库存低于阈值 → 提醒 → 一键备货（填套数，默认 20）
  → 系统按各菜配方算出原料需求 → 生成采购清单（原料库存抵扣沿用现有逻辑）
  → 采购完成 → 一键排产（复用现有 auto-schedule，放宽为备货单）
  → 生成生产批次（source=STOCK）：每道菜一个分装单元，分装计划 = 套数 × 2 袋 × 80g
  → 员工端生产/分装/拍照/完工（沿用现有流程，展示「试吃装备货」标识）
  → 完工：系统按实际产出建议入库套数 → 运营确认 → 生成库存批次
```

## 七、风险与底线

| 风险 | 处理 |
|---|---|
| 改定价算法可能算错所有订单的钱 | 只抽取复用、不改算法；前后价格一致性快照测试，误差为 0；现有定价测试全绿 |
| 备货生产接入采购/排产/分装/标签 | 顺现有 `STOCK_REPLENISHMENT` 与 `auto-schedule` 接，不另造；每接一处加回归测试 |
| 试吃装订单被误拉去排产 | 用订单类型显式隔离，采购/排产查询显式排除 |
| 超卖 | 下单即原子扣库存（数据库层保证）+ 30 分钟自动释放 |
| 现货价格浮动 vs 客服报价 | 下单瞬间锁价（现有快照机制）；提供手动定价覆盖开关 |

**不做**：

- ❌ 不给试吃装另建独立订单体系
- ❌ 不做顾客自选组合（技术上一单多菜可行，留待后续）
- ❌ 不动现有鲜食定价结果、排产算法、售后规则、补剂链路

## 八、验收标准

1. 后台能建一个 5 道菜的试吃装并上架，能复制购买链接。
2. 登记 20 套入库后，链接打开显示"现货、剩余 20"。
3. 顾客下单付款后库存变 19，订单在「我的订单」显示为试吃装。
4. **两个顾客同时抢最后 1 套，只有一人付成功**。
5. 未付款超时 → 订单关闭且库存回到 20。
6. 后台能直接发货；顾客能申请退款；有货时可补发。
7. 后台能看到每批库存的生产日期、到期日、剩余套数。
8. 库存低于阈值 → 提醒 → 一键备货 → 采购 → 排产 → 完工入库，全流程在系统内完成。
9. **现有鲜食订单价格与改动前完全一致。**

#### 一个留给第 3 批的口径决策

现货的售价应该按**哪个成本**算？两个候选：

- **A. 实时原料价**：每次报价按今天的原料价重算 → 原料涨价立刻反映在售价上
- **B. 入库批次成本**（推荐）：按当前可用库存的加权平均单套成本算 → 卖的是早先做好的货，按实际成本定价；原料价波动不会让毛利凭空蒸发

**第 2 批已按 B 实现**（无库存时自动回退 A，用于上架前预览）。
下单瞬间仍会价格快照锁价，手动定价覆盖始终可用。
如需改回 A，只需在下单链路不传 `stockUnitCost`。

#### 第 2 批发现并修掉的一个真问题：草稿修订版会漏进商品

`recipeRepository.findById()` 取的是**最新版本**，而最新版本可能是**尚未发布的草稿修订版**。

实测：食谱「萝卜绿豆鸭胸猪里脊」v1 是 PUBLIC，v2/v3 是 DRAFT，
`findById` 返回 v3，名字叫 **「萝卜绿豆鸭胸猪里脊 修订 修订」**。
如果直接用它组货，顾客会看到这个还没发布的名字；配方也可能没定稿。

**修法**：给食谱仓储新增 `findLatestPublicById()`（取已公开的最新版本），
试吃装的**组货快照**与**成本测算**都改用它。
副作用：试吃装这条线与鲜食订单链路（仍用 `findById` 取最新版本）口径不同 ——

#### 三处刻意的"不统一"

| 项 | 现货 | 鲜食 | 为什么 |
|---|---|---|---|
| 发货前状态 | 已付款即可发货 | 必须走完采购→生产→急冻 | 现货是早做好的存货，没有生产这一步 |
| 售后类型 | 只退款 / 补发 | 退款 / 重做 | 现货"重做"没有意义 |
| 制作日期 | 订单不存（null） | 必填 | 现货不排产；采购与排产按制作日期捞单，天然不会捞到现货，另有显式排除兜底 |

#### 已知取舍

- 现货订单的**支付超时沿用「支付配置」的共享值**（与鲜食同一套自动关单任务），
  没有像补剂那样单独配一个超时。补剂之所以独立是因为结算页与订单体系完全不同；
  现货走的是同一张 `order` 表、同一个关单任务，拆开反而容易漏关单。
- **补发**目前由客服手工处理（现货订单不支持"重做"）。
  若后续要一键补发，可以在现货单上做"0 元补发单"，仍需扣库存。

#### 本批修的三个坑

| # | 坑 | 后果 | 修法 |
|---|---|---|---|
| 1 | 建议入库套数用了「整单用量」当「一套用量」 | 做 10 套只建议入库 1 套 | 除以计划套数还原每套用量；专门加了 4 条单测钉死 |
| 2 | `PurchaseList` 强制要求至少一个来源订单 | 备货采购单创建直接失败 | 放宽为「来源订单 **或** 备货单至少有其一」，两者都空仍然拦住 |
| 3 | `PackagingUnit` 强制要求至少一个来源订单明细 | 备货锅创建不出来 | 改为「来源订单 **或** 分装计划至少有其一」，订单锅的约束没有放松 |

#### 一处刻意的依赖解耦

`TastingPackProductionService` **不直接 import `PurchasingService`**，而是通过
`TASTING_PACK_PURCHASING_PORT` 令牌注入一个窄接口。

原因不是架构洁癖：采购域的依赖链会牵进只发 ESM 的 `uuid` 包，
一旦在本模块顶层 import，**整个单测文件连解析都过不去**（CJS 运行时）。
用令牌既保留运行时的真实实现，也让这个服务对采购域只依赖一个接口。

#### 一个发现但不属于本次范围的问题

配方快照里，**按营养素目标定量的补剂 `ratio` 为 0**（它们不是按比例加的）。
车间「录入实际用量」是按 `ratio` 反算应投量的，所以这类补剂在车间会显示应投 0。
这是**订单链路一直以来就有的行为**（本次是原样复用同一份构建器，没有改动），
不在试吃装范围内，但如果要修，应该订单与备货一起修。

### 10.2 定价成本基数解耦成后台可切换

现货的两难：货是前几天按当时的价格做好的，售价可以按**今天的原料价**算，
也可以按**这批货实际花了多少钱**算。两种都说得通，所以做成后台可切换，
而不是写死在代码里。

| 口径 | 含义 | 特点 |
|---|---|---|
| **`LIVE`（默认）** | 每次报价按**今天的原料价**重算成本 | 成本永远跟得上行情；原料涨跌会带动售价 |
| `STOCK_BATCH` | 按**库存加权批次成本**算（入库时记下的单套成本） | 毛利更稳；原料涨价时早先低价做的货会卖得偏便宜 |

位置：后台「试吃装设置 → 定价 → 成本基数」，改完即时生效。

**顺带收紧了一处信息外泄**：顾客端报价原本会回传 `unitCost` 与 `costBasis`。
顾客不需要知道我们的成本，也不需要知道我们按哪个口径定价 ——
现已从顾客端报价与货架接口移除，后台仍可在「试吃装商品」列表看到这两个数字。
（加了一条验收项专门守着这件事。）

**实测（真实 HTTP，17/17 通过）**

```
✅ 口径=按今天原料价：后台看到成本 ¥55.99（实时），不是库存的 ¥40
✅ 顾客端报价不泄露成本与口径：只返回 snapshotId/价格/可售量/限购
✅ 口径=按库存批次成本：后台成本改为 ¥40
```
