## 三、重大发现：为什么"先体检档案"是对的

### 3.1 现状：很多"必填"其实是系统替顾客填的默认值

建档向导里，下面这些项页面**预先就填好了默认值**：

| 项目 | 表单默认值 | 问题 |
|---|---|---|
| 体况评分 | 默认 **5 分** | 顾客没选，档案里也会是 5 分 |
| 活动量 | 默认 **低活动** | 顾客没选，档案里也会是"低活动" |
| 每日餐数 | 默认 **2 餐/天** | 顾客没选，档案里也会是 2 餐 |

**后果**：档案里"有值"不等于"顾客真的填过"。

- 如果按决策 1 直接做门槛校验，会发现**门槛永远拦不住人**——因为这几项永远非空，全是默认值顶上的。
- 更严重的是：营养师拿到的是一份**看起来完整、实际是编的数据**，而定制食谱恰恰要吃体重、体况、活动量来算量。
- 决策 1 把"活动量、每日餐数、体况评分、是否绝育"都列进了门槛，**这四项目前正好都是默认值或未真正询问的**。

### 3.2 结论

**必须先解决"怎么知道顾客真的填过、而不是被默认值顶上"**，否则：

- 决策 1 的门槛形同虚设；
- 决策 3/4（带出与存回）会把编造的数据在两边来回搬；
- 决策 11（排产前重算）会拿默认值重算，等于白算。

这是"先体检档案"最硬的理由：**不是流程好不好看的问题，是门槛和数据可信度的问题。**

## 四、老板建议：用 AI 简化档案填写 —— 现成能力盘点与判断

老板建议：顾客只上传狗狗最近的过敏原检测报告，系统自动提炼出对哪些食物过敏，顾客确认一下即可。
并要求判断：**哪些简化方案需要 AI，哪些不需要。**

### 4.1 盘点结论：这条流水线你们已经跑着了，只是没用在健康档案上

系统里**已有一套完整的"上传图片 → 自动提炼 → 人工确认后保存"的实现**，目前用在**补剂包装识别**上：

| 环节 | 现成能力 | 状态 |
|---|---|---|
| 1. 上传图片/PDF | `POST /api/v1/health/upload-image`（本就挂在 health 路径下） | ✅ 已可用，支持图片与 PDF |
| 2. 文件存储 | 腾讯云 COS | ✅ 生产已配置密钥 |
| 3. 图片文字识别（OCR） | 腾讯云 OCR（复用 COS 密钥，无需新增密钥） | ✅ 已实现 |
| 4. 文字 → 结构化字段 | DeepSeek（生产**已启用并已配密钥**，用于配方设计与文案） | ✅ 已启用 |
| 5. 人工确认后保存 | "AI 生成 + 人工确认"的既有约定 | ✅ 已是既定模式 |

**结论**：老板举的例子**不需要从零新建能力**，属于把既有流水线换一个用途（换提示词 + 换目标字段 + 加确认界面）。
这是一个**成本可控、风险已知**的复用，而不是一次探索。

⚠️ 注意：这条流水线原本是为**印刷清晰的包装袋**设计的；医疗检测报告有表格、印章、手写，识别准确率会更低。
因此**"顾客确认"这一步是必须的安全网，不能让 AI 直接写进档案**。

### 4.2 判断一：不需要 AI 的简化（便宜、稳定、可立刻做）

| # | 简化做法 | 为什么不需要 AI |
|---|---|---|
| 1 | **把预填的默认值改成"未填写"** | 纯交互问题。**这是最重要的一条**：现状体况评分默认 5 分、活动量默认"低"、餐数默认 2，顾客没选也被顶上了，门槛因此失效 |
| 2 | 体重支持斤 / 公斤 / 磅输入 | 单位换算，算术即可 |
| 3 | 品种 → 自动带出成年体型、常见遗传病提示 | 查品种库，不需要 AI |
| 4 | 生日 → 自动算月龄与生命阶段 | 已有能力 |
| 5 | 体重 → 自动带出最近一次记录 | 已有体重记录表 |
| 6 | 能推算的就不再问（有生日就别再问生命阶段） | 减少必填项，纯逻辑 |
| 7 | 体况评分 → 用图文对照（摸肋骨、看腰线）自评 | 这是国际通用的标准评分法，靠图示即可，**不必让 AI 估** |
| 8 | 饮食偏好 → 改成标签选择 + 从历史订单带出 | 已有"口味分析"能力（接口已就绪但前端没接） |
| 9 | 疫苗/驱虫 → 按上次日期与周期提醒下次 | 日期计算 |
| 10 | 建档进度明确提示"还差哪几项、为什么必须填" | 纯文案与校验 |

### 4.3 判断二：值得用 AI 的（因为输入是"非结构化"的）

| # | 场景 | 价值 |
|---|---|---|
| 1 | **过敏原检测报告 → 过敏食物清单**（老板举的例子） | 最高。报告格式五花八门，只有 AI 能通吃 |
| 2 | 化验单 / 体检报告 → 体检记录（指标与异常项） | 高。顾客看不懂，我们却需要 |
| 3 | 疫苗本照片 → 疫苗记录（名称 + 日期） | 高。顾客普遍有本子、懒得手打 |
| 4 | 处方 / 病历照片 → 疾病记录（诊断、用药、就诊日期） | 高 |
| 5 | 顾客自由文字 → 拆成结构化项 | 高。"对鸡肉牛肉过敏，去年得过胰腺炎"一句话拆成 2 类记录 |
| 6 | 口语化偏好 → 对应到你们的食材库 | 中高。"不吃鸡胸" → 鸡肉 |
| 7 | 狗狗照片 → 建议品种 | 中。准确率有限，**只作为建议值让顾客确认** |

### 4.4 判断三：建议先不要用 AI 的

| # | 做法 | 为什么不建议 |
|---|---|---|
| 1 | **用照片估算体况评分（BCS）** | 看着诱人，但这个数字要用来算喂食量，**AI 估错了没人能发现**；且顾客拍照角度、光线差异极大。先做"图文对照自评" |
| 2 | AI 提炼后**直接写入档案、不经顾客确认** | 医疗信息必须"AI 提取 → 顾客确认 → 才写入"。与决策 5（不臆断疾病状态）、决策 9（必须知情同意）一致 |
| 3 | AI 判断疾病名称或严重程度 | 越界，属于诊断行为 |

### 4.5 需要老板决定的取舍

| # | 问题 | 说明 |
|---|---|---|
| **A1** | AI 简化先做哪几个？ | 建议**先只做第 1 个**（过敏原报告 → 过敏清单）。跑通一条再铺开，避免一次做 7 个都半成品 |
| **A2** | 识别失败/不确定时怎么办？ | 建议**降级为手工填写**，不能卡住顾客 |
| **A3** | 是否接受每次调用有微小成本？ | OCR + AI 每次调用都有成本（单次很低，但随用量增长） |

## 五、提案：狗狗档案全面体检（待审核）

### 5.1 体检范围

| 块 | 要看清什么 |
|---|---|
| ① 首次建档 | 分几步、每步问什么、哪些是默认值顶上的、能不能跳过、中途退出会怎样 |
| ② 档案详情页 | 能看到什么、能改什么、改的入口好不好找、改完有没有反馈 |
| ③ 健康档案 | 过敏、疾病、体检、体重、疫苗 五类：怎么录、怎么展示、哪些"记了却没人用" |
| ④ 与其它业务的衔接 | 定制食谱、鲜食下单、推荐、客服 —— 谁在读档案、读哪些项 |
| ⑤ 数据可信度 | 哪些值可能是默认值冒充的；哪些项两处并存（如过敏既有正式记录又有老文本框） |
| ⑥ 缺失与冗余 | 该有却没有的项；有却没人用的项；必填/选填设置是否合理 |
| ⑦ 简化机会 | 逐项标注：**哪些可以去掉、哪些可以自动带出、哪些可以靠规则简化、哪些值得用 AI 从报告/照片提炼** |

### 5.2 产出

一份**问题清单 + 改动建议 + 优先级**，逐条用业务语言说明"现在什么样、会出什么问题、建议怎么改、改了影响谁"，供老板审核。**审核通过前不动代码。**

### 5.3 与定制功能的关系

体检结论会直接影响：
- 决策 1 的门槛怎么做才有效（对应 3.1 的发现）
- 决策 3/4 的带出与存回清单
- 决策 7 要给档案新增的"喜好 / 不吃食材"位置
- 决策 8 的体重有效期怎么展示与提醒
- 决策 9 的知情同意文案放在哪一步
- **第四节判断出的 AI / 非 AI 简化方案，哪些纳入本次改造**
