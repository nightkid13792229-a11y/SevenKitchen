# 狗狗档案 ↔ 食谱定制 · 字段对齐梳理

> 版本：v1（2026-09-27）
> 目的：**只做决策前的现状核对与方案对比，不含任何代码改动**
> 背景：食谱定制页涉及「健康管理目标」「喜好的食材」等信息，而这些信息在狗狗档案里也有一份。
> 需要先确认：两边怎么对齐？顾客在定制页填的内容，要不要、能不能同步回档案？
> 顺带回答：未登录 / 无档案 / 档案不完善时，定制页当前会怎样。

---

## 零、先说一个实测发现的阻断性缺陷（已修，待部署）

**只要顾客填了至少一个「过敏信息」，定制单就提交不了**（HTTP 500）。

- 原因：同步代码往 `allergy_record` 写入了 4 个**数据库里不存在的列**
  （`allergenType` / `severity` / `discoveryDate` / `confirmedBy`），
  Prisma 抛 `Unknown argument` → **整个下单事务回滚**。
- 影响面：小程序端 `syncToHealthProfile` **恒为 true 且无开关**，
  所以这不是边缘路径，而是**填了过敏就必然失败**。
  对一个"按过敏与病症定制"的产品来说，这是主路径。
- 已修：只写模型里真实存在的字段（`allergen` + `notes` 留来源），
  并补了 7 项回归测试把"不得写入不存在的字段"锁死。
- ⚠️ **生产仍在跑坏代码**，需要一次后端部署才生效。

> 这个缺陷本身就是本次梳理要解决的问题的注脚：**回写方向从来没有被真正验证过。**

## 一、Q1：定制页当前的门槛行为

| 情况 | 现在的行为 | 结论 |
|---|---|---|
| **未登录** | 页面内**没有任何登录校验**；直接进入时拉狗狗列表会 401，页面弹「网络错误，请检查后端服务」（**误导**，其实是没登录），随后落到"还没有狗狗档案"空态 | ❌ 有缺口 |
| **无狗狗档案** | 明确的空态 +「创建狗狗档案」按钮；建档返回后 `onShow` 会自动刷新出刚建的狗 | ✅ 已处理 |
| **档案不完善** | **完全不检查**。只要"选中狗狗 + 选了目标"即可提交；体重/体况/生命阶段为空也照样下单 | ❌ 有缺口 |

**为什么"档案不完善"是硬问题**：定制食谱的核心是**按体重、体况、生命阶段算量与配比**。
这三项缺失时，营养师拿到的是一张**算不出量**的单子，最终还得回头找顾客补。

## 二、两边现有字段盘点

### 2.1 狗狗档案（`dog` 表 + 4 张记录表）

**主表字段**

| 分组 | 字段 | 是否必填 | 前端可编辑处 |
|---|---|---|---|
| 基础 | `name` 名字 | 必填 | 建档向导 / 档案页 |
| | `breedId` + `customBreedName` 品种 | 必填 | 同上 |
| | `birthday` 生日 | 必填 | 同上 |
| | `gender` 性别 | 必填 | 同上 |
| | `isNeutered` 是否绝育 | 必填 | 同上 |
| | `avatarUrl` 头像 | 选填 | 同上 |
| 体况 | `currentWeightKg` 当前体重 | 必填 | 同上 |
| | `bcsScore` 体况评分 | 必填 | 同上 |
| | `sizeClassOverride` 体型覆盖 | 选填 | 同上 |
| | `lifeStageOverride` 生命阶段覆盖 | 必填 | 同上 |
| 喂养 | `mealsPerDay` 每日餐数 | 默认 2 | 同上 |
| | `treatInputMode` / `treatLevel` / `manualTreatKcal` 零食口径 | 有默认 | 同上 |
| **旧文本字段** | `allergyFoods` 过敏食材 | 选填 | ⚠️ **档案页表单里没有它** |
| | `pickyFoods` 挑食/不爱吃 | 选填 | 档案页「饮食提醒」有 |
| | `preferredFoods` 喜欢的食物 | 选填 | ⚠️ **未见前端使用** |
| | `medicalHistory` 既往病史 | 选填 | ⚠️ **未见前端使用** |
| 缓存 | `cachedTargetFoodKcal` | — | 系统写 |

**结构化记录表**

| 表 | 业务字段 | 谁在写 |
|---|---|---|
| `allergy_record` 过敏 | 只有 `allergen` + `notes` + `attachments` | 档案页；定制单同步 |
| `medical_record` 疾病 | `visitDate` / `chiefComplaint` / `diagnosis` / `treatment` / `medications` / `status` / `followUpDate` / `veterinarian` / `notes` | 档案页；定制单同步 |
| `checkup_record` 体检 | `checkupType` / `checkupDate` / `findings` / `recommendations` / `veterinarian` | 档案页 |
| `weight_record` 体重 | `recordDate` / `weightKg` / `note` / `syncedToProfile` | 档案页 |
| `vaccine_record` 疫苗 | — | 档案页 |

> ⚠️ **同一件事存在两处**：过敏既有结构化 `allergy_record`，主表上还有个旧文本字段 `allergyFoods`；
> 而档案页表单里**并没有** `allergyFoods`。**以哪个为准需要先定**，否则定制单同步写哪边都会出现"两处不一致"。

### 2.2 食谱定制单（`custom_recipe_order` 表）

| 字段 | 含义 | 档案里有对应吗 |
|---|---|---|
| `dogId` | 选中的狗狗 | — |
| `targetGoal` | 定制目标（减重/维持/增重/健康管理） | ❌ 档案里**没有**"目标"概念（档案算的是"维持"所需热量） |
| `allergies[]` | 过敏信息 | ✅ 对应 `allergy_record`（结构化） |
| `medicalConditions[]` | 疾病史 | ✅ 对应 `medical_record` |
| `preferredIngredients[]` | 喜欢的食材 | ⚠️ 只有旧文本 `preferredFoods`，且前端未见使用 |
| `dislikedIngredients[]` | 不吃的食材 | ⚠️ 只有旧文本 `pickyFoods` |
| `additionalNotes` | 其它需求 | ❌ 无对应 |
| `attachmentUrls[]` | 附件（化验单等） | ❌ 无对应（档案的附件挂在各记录下） |
| `syncToHealthProfile` | 是否回写档案 | — |

## 三、同步现状：一个方向已通、另一个方向**根本没接**

### 3.1 定制单 → 档案（**已存在，但刚从"必崩"修好**）

提交定制单时，若 `syncToHealthProfile = true`：

| 来源 | 写入目标 | 规则 | 问题 |
|---|---|---|---|
| `allergies[]` | `allergy_record` | 按 `allergen` 去重，**只加不删** | 已修（原先写不存在的列必崩） |
| `medicalConditions[]` | `medical_record` | 按 `diagnosis` 去重，**只加不删**，`status` 一律 **CHRONIC**、`chiefComplaint` 一律「定制食谱时提供」 | ⚠️ **系统替顾客判定了"慢性病"** |
| `preferredIngredients[]` | —— | **不写** | 喜好无处安放 |
| `dislikedIngredients[]` | —— | **不写** | 不吃无处安放 |

### 3.2 档案 → 定制页（**接口已就绪，但前端一个都没调**）

后端其实**已经写好两个现成接口**：

| 接口 | 返回 | 小程序是否调用 |
|---|---|---|
| `GET /custom-recipe/dogs/:dogId/health-summary` | 过敏、疾病（近 5 条）、体检（近 3 条）、体重趋势（近 5 条） | ❌ **完全没有调用** |
| `GET /custom-recipe/dogs/:dogId/preference-analysis` | 按历史订单分析口味偏好 | ❌ **完全没有调用** |

**结论：顾客在档案里已经写了「对鸡肉过敏」，进定制页仍要重新手打一遍。**
这不是"要不要新增同步"的问题，而是**现成的同步能力根本没有接上**。

## 四、由此产生的 6 个待决策点

| # | 问题 | 可选项 |
|---|---|---|
| 1 | **"能定制"的最低档案要求是什么？** | 建议：当前体重 + （生日或生命阶段）+ 体况评分 + 是否绝育。这四项直接决定算量与配比 |
| 2 | 不满足时怎么办？ | ①在定制页**就地补齐**（体验最好）②引导去档案页补 ③允许提交但提示"营养师会联系你补信息" |
| 3 | **定制页要不要带出档案已有信息？** | 建议要：选中狗狗后自动带出过敏/疾病，顾客可增删 |
| 4 | 定制页**新增**的内容要不要回写档案？ | 建议要（但需先定第 5、6 点） |
| 5 | 回写时**疾病状态**怎么定？ | 系统不再臆断 `CHRONIC`；或改为"待确认"，由客服/顾客在档案里补 |
| 6 | 顾客在定制页**删掉**某项，档案怎么办？ | 建议**只加不删**（避免误删正式医疗记录），并在页面上写明"档案里的记录不会被删除" |
| 7 | 喜好/不吃食材放哪？ | ①给档案加结构化位置（迁移）②约定"只进定制单、不进档案"③继续用旧文本字段 |

## 五、三种整体方向

| 方案 | 做法 | 好处 | 代价 |
|---|---|---|---|
| **A（推荐）** | 定制页 = 档案的**第二个填写入口**：带出已有信息 + 回写新增内容 | 顾客只填一次；客服在档案里看到全貌 | 要把上面 7 个决策点定清楚 |
| B | 定制页**独立**，不回写档案 | 改动最小 | 两处重复填；客服看不到定制诉求 |
| C | 定制页**只读档案**，必须先完善档案 | 数据最干净 | 门槛最高，流失最大 |

## 六、建议的推进顺序

1. **先定第 1 项**（"能定制"的最低档案要求）—— 这一项定了，Q1 的"档案不完善"才**有可执行的判据**
2. 再定第 3、4 项（带出 / 回写）
3. 最后定第 5、6、7 项（回写细则）
4. 期间**先修未登录的误导提示**（弹"网络错误"其实是没登录）—— 这个不依赖任何决策，可以先做
