# 狗狗档案 UX 审视与重构方案

> 版本：v1.1（2026-09-27，U1–U5 已由老板确认；U4 标注文案按老板定稿修改）
> 视角：**站在顾客的角度走一遍**，回答四个问题——哪些信息必须问？哪些步骤能简化？哪些交互能优化？整个流程要不要重构？
> 方法：四路代码调查 + 生产库真实行为数据 + 亲自走一遍现有流程
> 配套文件：`2026-09-27-dog-profile-review.md`（技术缺陷体检）、`2026-09-27-custom-recipe-decisions-and-profile-review.md`（12 项业务决策）
> 状态：**方案已确认，可开工**；前置修复中 H2 仍待 D6 决策

## 一、先看事实：顾客实际上是怎么用档案的

不讲感受，先看真实数据（生产库 4544 只狗、3631 位顾客）。

### 1.1 健康档案的使用率：低到接近"没这个功能"

| 健康档案里的内容 | 有多少只狗填过 | 使用率 |
|---|---|---|
| 疫苗 | **0 只** | **0%**（因为顾客端根本没有入口） |
| 过敏 | **24 只** | **0.5%** |
| 体检 | 74 只 | 1.6% |
| 病史 | 257 只 | 5.7% |
| 体重记录 | 1449 只 | 31.9% —— 但见下 |

**93.6% 的狗狗档案里，完全没有健康信息**（过敏 / 病史 / 体检一项都没有）。

### 1.2 更扎心的一点：那 32% 的体重记录，绝大多数不是顾客记的

体重记录一共约 1774 条，按来源拆开：

| 来源 | 条数 | 占比 |
|---|---|---|
| 「建档初始体重」——**系统自动补的** | 1091 | 61.5% |
| 「档案体重更新」——**改档案时系统自动补的** | 383 | 21.6% |
| 顾客自己填的（含手写备注） | 316 | 17.8% |

而**真正在长期追踪体重的狗只有 46 只（占全部 4544 只的 1%）**（有 3 条以上记录）。

**结论**：健康档案在顾客手里**几乎是空的**。看起来"有 32% 在记体重"，其实是系统自己写进去的。

### 1.3 病史功能曾经有人用，但已经停了

病史记录按月分布：

| 月份 | 新增病史记录 |
|---|---|
| 2026-03 | 206 |
| 2026-04 | 105 |
| 2026-05 | 11 |
| 2026-06 | 8 |
| 2026-07 | 1 |
| 2026-09 | 1 |

**332 条里有 311 条（94%）集中在 3–4 月**，之后基本停摆。同期也是建档量最高的两个月（3 月 2318 只、4 月 997 只），之后回落到每月 100–160 只。

### 1.4 我们目前**看不到**顾客在哪一步流失

建档漏斗埋点**生产库里只有 1 条数据**（还是 9 月 24 日内部测试留下的）。对比：成品食谱链路的埋点有 242 条真实数据。

原因是建档埋点是 **9 月 21 日才写的代码，还没随小程序发布**。

**所以本次 UX 审视没有"数据支撑的流失点"可用**，只能靠"亲自走一遍 + 已有数据分布"来判断。这是诚实的边界。

## 二、诊断：三个根本问题

### 问题 1：健康档案"填了没用"——所以没人填

顾客填过敏是为了让推荐避开。**但现在推荐食谱根本读不到顾客填的过敏**（读的是那个顾客端连输入框都没有的旧字段）。

> 一个顾客花两分钟填完"对鸡肉过敏 → 保存"，然后首页照样给他推含鸡肉的食谱。
> **他填第二次吗？不会。**

**这是 93.6% 空白的根本原因之一**——不是顾客懒，是这件事对他没有回报。

### 问题 2：最好的收集时机被浪费了

**建档向导 3 步里，完全没有健康信息。** 而建档是顾客注意力最集中、最有耐心的时刻。

之后想看健康档案要：
`爱犬列表 → 概览页 → 点"编辑基础信息" → 在"体重"标签旁找到一个小小的"健康管理"链接 → 才进得去`

**入口藏在"编辑基础信息"里**——顾客在概览页看到"体重 6.5kg"，根本想不到记体重变化的地方藏在"编辑"按钮里。

### 问题 3："必填"是假的，顾客做了一堆无意识的选择

建档页有 **9 项预填默认值，界面上还渲染成"已选中"高亮**，顾客分不清自己选没选过：

- **活动量**默认"低活动" → 成年犬热量算出来**偏低约 14%**
- **每日餐数**默认 2 餐 → **直接决定每包克重与总包数 → 影响报价**
- 体况评分默认 5 分、性别默认"弟弟"、绝育默认"未绝育"、零食默认"较少"

**整个「第 2 步 喂食信息」可以一步不动就直接通过**——那两个 `*` 号是装饰。

生产佐证：**4544 只狗里，体况评分等于默认值 5 的有 3466 只（76.3%）**。

## 三、逐项审计：这 20 项信息，哪些真的需要问？

我把档案里所有要顾客提供的信息过了一遍，按"能不能省"分成四级。

### A 级：必须问，而且必须顾客**主动确认**（不给默认值）

| 项目 | 谁真正在用 | 为什么不能省 |
|---|---|---|
| **名字** | 展示、订单、营养师、AI | 没有它没法称呼这只狗 |
| **当前体重** | 算热量 → 算份量 → **算价格** | 缺了算不出来；单位必须写清（见交互优化 1） |
| **品种 或 体型** | 体型 → 热量；遗传病提示 | 缺了算不出体型基准 |
| **生日**（或年龄段） | → 生命阶段 → 热量 | 幼犬/成犬/老犬配比完全不同 |
| **体况评分** | 热量系数（×1.0 ~ ×0.6） | 直接决定"减重建议"，且**是你要的门槛项** |
| **活动量** | 热量系数（两档差 13.6%） | 影响最大的一项，**绝不能用默认值** |
| **每日餐数** | **每包克重 + 总包数 → 报价与排产** | 错了就是**报错价**，必须顾客亲选 |
| **过敏** | 本该是推荐与配方的**安全底线** | 定制产品的命门；但**必须先让它产生价值**（见问题 1） |

### B 级：可以推算，不必问

| 项目 | 现在怎么问 | 建议 |
|---|---|---|
| **生命阶段** | 建档时有一个"手动选择"弹层（**而且是死 UI，没有入口**）；默认"自动" | **完全不问，一律自动推算**；只在"妊娠 / 哺乳"这类生日算不出来的特殊阶段，才显式问一次 |
| **月龄 / 年龄** | 不问（好） | 保持不问，从生日算 |
| **体型** | 只在混血/手填品种时才问（好） | 保持；纯种犬从品种库带出 |

### C 级：可以延后到"以后再说"

| 项目 | 现在的位置 | 建议 |
|---|---|---|
| **头像** | **建档第 1 步就问** | 挪到建档完成页（"给它挑个头像吧"，纯可选）。建档第一步问头像，是在顾客最想快点看到结果的时候增加了负担 |
| **零食档位** | 第 2 步，默认"较少" | 收进"更多设置"，默认值明确标注"估的不准也没关系" |
| **病史 / 体检** | 健康管理页（找不到） | 挪到建档第 3 步，**可跳过**，并优先用"上传报告自动识别" |
| **体重记录** | 健康管理页 | 建档时自动补一条即可；之后在概览页给显眼入口 |
| **喜欢的食材 / 不吃的食材** | 顾客端**完全没有入口**（只有员工工具在读） | 建档第 3 步顺带问（标签选择，不用打字） |
| **疫苗** | **顾客端零入口，后端全做好了** | 单独排期做，优先度低于上面几项 |

### D 级：建议降级为"选填"或砍掉

| 项目 | 现状 | 建议 | 理由 |
|---|---|---|---|
| **性别** | 必填，默认"弟弟" | **降为选填**，收进"更多信息" | 实测**对喂食计算零影响**，唯一用途是一个妊娠警告——而妊娠阶段顾客根本选不到 |
| **是否绝育** | 必填，默认"未绝育"，界面写"会影响热量评估" | **降为选填**，并**修正那句说明** | 实测只有"成犬 + 工作犬"才用得到；其余情况写进去了也完全不参与计算。**话术与算法不符** |
| **零食输入方式** | 默认"按档位估算" | 保留，但不给顾客看 | 精确 kcal 模式**没有入口**，是死代码 |
| **既往病史（旧文本字段）** | 顾客端已废弃，只原样回传 | 清理时一并处理 | 只有后台 AI 在读 |

### 一句话总结这张审计表

**真正必须顾客回答的只有 8 项**（名字、体重、品种/体型、生日、体况评分、活动量、餐数、过敏）。
其余的：**2 项能推算、6 项能延后、2 项该降级**。而现在系统让顾客面对的是 20 多项。

## 四、步骤简化

### 现在的 3 步

| 步骤 | 问了什么 | 问题 |
|---|---|---|
| ① 基础信息 | 头像、名字、性别、生日、体重、品种+体型、绝育 | **7 项**，其中头像可以后置、性别/绝育几乎不影响结果 → 负担最重的一步 |
| ② 喂食信息 | 体况评分、活动量、餐数、零食 | **整步可跳过**（全默认值）→ 形同虚设 |
| ③ 喂食建议 | 只读结果 | **这不是一个"步骤"**，是结果页 |

### 三个结构性问题

1. **负担分配反了**：最重的一步（①）放在最前面，顾客最容易在这里放弃。
2. **第②步是假的**：既能整步跳过，又承担着最影响计算的活动量与餐数。
3. **健康信息无处安放**：3 步里一个字都没提，而这是定制业务的命门。

## 五、交互优化清单（12 项）

| # | 问题 | 优化建议 | 优先级 |
|---|---|---|---|
| **1** | **体重输入框不写单位**，国内顾客按"斤"填 → 热量翻倍或严重不足 | 输入框旁加 `公斤 / 斤` 切换，默认公斤并**显示"公斤(kg)"** | 🔴 高 |
| **2** | 体况评分**默认 5 分**，界面显示成"已选中" | 默认**不选中**，必须顾客亲自点；未选不能进入下一步 | 🔴 高 |
| **3** | 活动量**默认"低活动"**，且**只有文字、没有配图** | ①默认不选中 ②**加图示 + 生活场景描述**（"每天遛 2 次、每次 30 分钟以上"这种），让顾客对得上号 | 🔴 高 |
| **4** | 每日餐数默认 2 餐，**却直接影响制作单的生成** | **默认高亮"2 餐"**，旁注「**影响制作单的生成，请确认**」（老板定稿文案，不说"价格"） | 🔴 高 |
| **5** | 概览页的健康记录**保存/删除是坏的** | 修好（或按 D6 决策只保留一个入口） | 🔴 高 |
| **6** | 顾客填的过敏**推荐读不到** | 把推荐与 AI 的过敏依据切到结构化记录，并让"填完立刻在首页生效" | 🔴 高 |
| **7** | 过敏/疾病**要顾客手打文字** | 常见过敏原做成**标签一点即选**；手打只作补充；主推**上传报告自动识别** | 🔴 高 |
| **8** | 健康管理入口**藏在"编辑基础信息"里** | 概览页给一个显眼的"健康档案"卡片入口 | 🟠 中 |
| **9** | 概览页只显示"过敏 2 条"，**看不到具体内容** | 只读态直接列出过敏原与诊断（现成接口已能返回，只是没人调） | 🟠 中 |
| **10** | **生命阶段顾客完全改不了**（狗狗长大、怀孕、进入老年都没法改） | 概览页加"生命阶段"编辑，或至少提供"妊娠/哺乳/老年"的快捷选项 | 🟠 中 |
| **10-附** | 体重过期提醒（60 天口径）**不做全站提醒** | 只在**需要用到体重的场景**提醒（定制页 / 下单页 / 打开档案时）。生产数据预演显示回填后 **93% 的狗都超过 60 天**，全站提醒等于没有提醒（见 U6） | 🟠 中 |
| **11** | 中途退出**全丢**（草稿功能因一个从未写入的标记而失效） | 修好草稿；离开前拦截并提示 | 🟠 中 |
| **12** | 建档完成**没有任何"完整度"提示**，顾客不知道还差什么 | 完成页给出"已完善 X/Y"，并说明"补上过敏信息，推荐会更准" | 🟡 低 |

## 六、重构方案：新的建档流程

**设计原则三条**：
1. **能推算的不问**，能延后的不前置
2. **影响钱和安全的，必须顾客亲口确认**（不给默认值）
3. **健康信息在最合适的时机、用最省力的方式收集**，并且**立刻产生回报**

### 新流程

#### 第 1 步：它是谁（4 项，都容易答）

| 项目 | 做法 |
|---|---|
| 名字 | 文字输入 |
| 品种 / 体型 | 搜索选择；**混血或不知道品种时，直接选体型（小型/中型/大型）**，不强迫顾客纠结品种 |
| 生日 | 日期选择；**另提供"大概几个月大"的快捷选项**，避免顾客为了建档去翻疫苗本 |
| 当前体重 | 数字输入 + **公斤/斤切换** |

> 头像、性别、绝育**不在这一步**。

#### 第 2 步：怎么喂（3 项必须亲选 + 1 项可折叠）

| 项目 | 做法 |
|---|---|
| 体况评分 | 9 张卡片**默认全不选中**，配现有参考图；顾客必须选 |
| 活动量 | 5 张卡片**默认全不选中**，**配生活场景描述和图示**；顾客必须选 |
| 每日餐数 | **默认高亮"2 餐"**，旁注「**影响制作单的生成，请确认**」（其余两项仍必须亲选，不预选） |
| 零食（可折叠） | 放"更多设置"里，明确写"按大概选就行" |

#### 第 3 步：有什么要注意的吗（**可跳过**，这是新增的）

页面文案（一句话讲清好处）：
> **告诉我们它不能吃什么，我们会在推荐食谱时自动避开。**

三个入口，**从最省力到最费力**排：

| 顺序 | 方式 | 说明 |
|---|---|---|
| ① | **上传检测报告 / 病历** | AI 自动识别 → **顾客确认后**才写入（你说过要先做这一个） |
| ② | **点选常见项** | 过敏原、常见病史做成标签，一点即选，不用打字 |
| ③ | **暂时跳过** | 明确写"跳过也能用，以后随时可以补" |

> ⚠️ **AI 识别失败必须自动降级为手工填写**，绝不能卡住顾客（对应你定的 A2）。

#### 完成页：立刻给回报

| 内容 | 说明 |
|---|---|
| 每日热量需求 + **建议喂食量（克）** | 现在总览页只有热量、没有克数，顾客其实最想知道"每天喂多少克" |
| 健康信息若未填 | 一句轻引导："补上过敏信息，推荐会更准"，**但不拦路** |
| 头像 | 这里才问"给它挑个头像吧"（纯可选） |

### 最关键的一条：让填写**立刻有回报**

顾客填了"对鸡肉过敏"之后，**首页推荐必须马上不再出现含鸡肉的食谱**。

这是让顾客愿意填健康信息的**唯一真正动力**。这也是为什么"修推荐的过敏依据"（体检报告 H1）**不是技术债，而是这次 UX 改造的前提**。

## 七、改造前后对比

| 环节 | 现在 | 重构后 |
|---|---|---|
| 必须回答的问题 | 20+ 项，其中 9 项被默认值代答 | **8 项必须亲选**，其余可推算/可延后 |
| 步骤 | 3 步，第 2 步是假的，第 3 步是结果页 | 3 步，**每一步都真的在收集**，第 3 步可跳过 |
| 健康信息 | 3 步里一个字没提；入口藏在"编辑基础信息"里 | **建档里不问**（U7 推翻了原方案），全部归「健康管理」页；"一点即选 + 上传报告自动识别"搬进该页过敏区 |
| 填了过敏 | **推荐读不到**（填了没用） | 首页推荐**立刻避开** |
| 体重单位 | 不写，顾客可能按斤填 | 公斤/斤切换 |
| 体况评分 / 活动量 | 系统预先选好，顾客无意识跳过 | 顾客必须亲选，配图示 |
| 日均餐数 | 默认 2 餐（影响报价） | **默认高亮 2 餐**，并标注「影响制作单的生成，请确认」 |
| 中途退出 | 全丢 | 草稿保留 + 离开拦截 |
| 生命阶段 | 完全改不了 | 可改，特殊阶段有快捷选项 |
| 数据可信度 | 76% 的体况评分是默认值 | 每一项都"顾客真的选过" |

## 八、和已定决策、技术体检的衔接

| 已定内容 | 本方案的对应 |
|---|---|
| 决策 1：门槛 10 项 | 全部落在「A 级必须亲选」；**门槛判据应为"顾客确认过"，不是"字段非空"** |
| 决策 2：不满足就地补齐 | 即新流程的"默认不选中 + 未选不能下一步" |
| 决策 3：定制页带出档案信息 | 但**93.6% 的档案没有健康信息**，所以定制页**仍必须问**——只是要用"带出 + 补问"而不是"依赖档案" |
