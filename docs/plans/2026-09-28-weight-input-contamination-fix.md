# 体重输入污染修复方案（「斤」当「公斤」）

- 日期：2026-09-28
- 背景：`docs/audits/2026-09-28-dog-calorie-algorithm-full-audit.md` 文首「重大补充」与第九节
- 性质：**输入质量修复**，与后续「按 FEDIAF 重构热量算法」是两件独立的事
- 优先级建议：**排在算法重构之前**——体重错 2 倍，算法再准也会多喂 68%

---

## 一、问题一句话

顾客按「斤」报了体重，系统当成「公斤」存了下来。
后果：热量按 `2^0.75` 计算 = **多给 68% 的食物**。这比审计里任何一项系数问题（最大 +34%）都严重，也最能解释「按系统给的热量买、狗还是变胖」。

而且它形成闭环：**体重填错 → 多喂 68% → 狗真变胖 → 再称重又按更大的体重算 → 继续放大。**

---

## 二、根因

| 事实 | 说明 |
|---|---|
| 小程序已有「斤 / 公斤」选择器 | 内部一律按公斤存储，换算逻辑本身是**正确**的 |
| **但默认停在「公斤」** | 国内顾客习惯按斤报体重 |
| **没有任何合理性校验** | 现有校验只有「>0 且 ≤200 公斤」，一只 43 kg 的柯基、120 kg 的德国牧羊犬都能直接存进去 |
| 三个入口都缺校验 | 建档、体重记录、档案编辑 |

即：**单位选择器和顾客的表达习惯不匹配，且没有任何护栏。**

## 五、修复方案（五层）

### 层 1｜输入时拦截（前端，三个入口都做）——**先止血**

**入口**：建档、体重记录、档案编辑。

**规则**（`a` = 品种常见成年体重；混血/无品种时用体型档兜底）：

| 判定 | 条件 | 动作 |
|---|---|---|
| **强提示（疑似填了斤）** | w > a×1.9 **且** w/2 落在 [0.5a, 1.6a] | 弹提示：「这个体重对<品种>偏大，**是不是填了斤？**」+ **一键按斤换算**按钮 |
| 偏大 | w > a×1.6 | 轻提示：「<品种>常见约 X kg，请确认」 |
| 偏小 | w < a×0.5 | 轻提示：「<品种>常见约 X kg，请确认；也可能选错了品种」 |
| 正常 | 其他 | 不提示 |

**外加一条零成本但很有效的改动：双向实时回显。**
输入框下方实时显示换算结果，例如输入 43、单位选公斤 → 显示「= 86 斤」。顾客自己就会反应过来「我家狗哪有 86 斤」，在保存前自己改对。

**为什么不做硬拦**：确实有超胖的狗，硬拦会把真实数据挡在外面，也会流失顾客。**提示 + 一键换算**足够。

### 层 2｜后端同样校验（前端可被绕过）

- 后端按 `dog_breed.average_adult_weight_kg` 或体型档做**同一套**判断；
- **极端不可能的值直接拒绝**（任何犬种都不可能）；
- 其余情况**接受但记 warning 日志**（便于后续统计）；
- **收紧现有上限**：`MAX_WEIGHT_KG` 目前是 **200 kg**，建议降到 **130 kg**（前后端一致）。200 kg 这个值本身形同虚设——历史上最重的狗约 155 kg。

### 层 3｜存量清理

**第 1 步只读导出**（符合仓库约定：数据脚本默认 dry-run，`--apply` 才写入），产出 A/B/C/X 分级清单（含品种、体重、比值、记录历史），**先给你看，不改正**。

**A 级处置方式三选一**（见第六节请你定）。

### 层 4｜防复发监控

| 指标 | 频率 |
|---|---|
| A 级占比（≥品种均值 1.9 倍） | 每月 |
| 「斤 / 公斤」选择器的使用率 | 每月（若大量顾客用斤，说明默认值该调整） |
| 同日重复体重记录数 | 每月 |

### 层 5｜顺带修的相邻问题

| # | 问题 | 建议 |
|---|---|---|
| 1 | 同一只狗同一天会写入两条体重记录（144 组） | 改为同一天**覆盖更新**，而不是新增（需确认是否影响历史记录展示） |
| 2 | 建档初始体重记录与档案体重值的一致性 | 加断言 + 单元测试（两者必须相等） |
| 3 | `MAX_WEIGHT_KG = 200` | 收紧到 130 |

## 六、老板决定（2026-09-28）

| # | 事项 | 决定 |
|---|---|---|
| 1 | **A 级 217 只怎么处置** | **不动**。原话：**「我们没有办法去判断顾客是真的填错了，还是说他养了一只串串体重就有这么大，或者他是一只茶杯犬体重就有这么小，我们也没有权力去改顾客的数据。」** |
| 2 | `MAX_WEIGHT_KG` 200 → 130 | **改**（前后端一致） |
| 3 | 同日体重记录改为覆盖更新 | 缓办 |
| 4 | **提示的范围** | **只保留「公斤 ⇄ 斤」换算回显，其他提醒全部撤掉**。原话：**「我觉得不要给错误的提醒。只在填写体重的地方给出公斤和斤的换算提醒就可以了。」** |

### 这条决定落实为一条产品原则

> **不替顾客改数据。** 系统只做两件事：**判断** 和 **提示**；最终改不改由顾客自己决定。

因此存量 217 只**不做任何后台修正**，改为通过「层 1 输入时提示」自然覆盖：
- 顾客下次**编辑档案**或**记录体重**时，同一个提示会自动出现；
- 提示用的是「请确认」，不是「你填错了」——因为串串、茶杯犬确实存在；
- 提示里带**一键按斤换算**，顾客觉得对就点，觉得不对就不点。

**代价（要认）**：主动修正覆盖不到「再也不打开档案」的顾客，那部分狗会继续被多喂。
**这是老板明确接受的取舍**——比起擅自动顾客的数据，宁可慢。

---

### 第 4 条决定带来的最终形态（2026-09-28 二次修订）

**保留的**（唯一一处体重提示）：
> 输入框下方显示**单位换算回显**，例如输入 43、单位选公斤 → 「= 86 斤」。
> 这是**客观事实**，永远不会错——顾客自己就能发现单位选错。

**撤销的**（原方案里的「合理性提示」，全部删除）：
| 已删除的提示 | 撤销原因 |
|---|---|
| 「这个体重对博美偏大，是不是填了斤？」 | 顾客可能养的就是体型大的**串串**，系统会误伤 |
| 「柯基常见约 11.3 公斤，这个体重偏小」 | 顾客可能养的就是**茶杯犬** |
| 「这次填的和档案里相差很大，请确认单位」 | 幼犬生长期、减重期体重本来就会大幅变化 |
| 一键「按斤算」按钮 | 等同于系统在暗示顾客填错了 |

**保留下来的硬约束只有一条**：超过 **130 公斤**直接拒绝（生物学上不可能）。
它不针对任何具体品种，因此不会误伤。

**这次修订的原则**：**误报比不报更伤信任。** 系统无法区分「填错了」和「本来就长这样」，
所以只把客观事实（单位换算）摆出来，判断交给顾客。

### 第 5 步：月度监控指标（待做）

每月跑一次以下只读统计即可，**不需要改代码**：

```sql
-- 体重明显偏大的狗（疑似单位错值）占成年犬比例
WITH t AS (
  SELECT d.current_weight_kg / NULLIF(b.average_adult_weight_kg, 0) AS r
  FROM dog d JOIN dog_breed b ON d.breed_id = b.id
  WHERE b.average_adult_weight_kg > 0
    AND d.birthday < NOW() - INTERVAL '24 months'
)
SELECT
  COUNT(*) FILTER (WHERE r >= 1.9) AS suspect,
  COUNT(*) AS total,
  ROUND(100.0 * COUNT(*) FILTER (WHERE r >= 1.9) / COUNT(*), 2) AS pct
FROM t;
```

判读：**占比在涨 → 提示没起作用；占比归零 → 修好了。**

## 八、这件事与算法重构的关系

- 两者**独立**，但**顺序不能颠倒**：体重是算法的输入，输入错了，重构也白搭。
- 修完之后，第 2 组遗留的两件事才能落地：
  1. **用曲线反推「生长速率」**（判断幼犬长得太快/太慢）需要真实体重；
  2. **体重趋势预警**（体况 5 分但体重在涨）需要干净的体重历史。
- 本方案的层 1（输入拦截）与算法重构**没有代码冲突**，可以并行推进。
