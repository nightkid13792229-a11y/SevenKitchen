# 健康管理 · 需求与能力审计 + 优化重构方案

**日期**：2026-09-30
**审计范围**：小程序「健康管理」页的六个板块（病史 / 体检 / 过敏 / 疫苗 / 饮食 / 体重），
以及它们在后端与其它能力（食谱定制、首页推荐、管理后台）之间的连接。
**视角**：以**狗狗家长**为主，**管理员 / 营养师**为辅。

---

## 一、一句话结论

> **"为定制食谱服务"这一条（需求点 2）其实已经做得很深了，不需要重建；**
> **真正缺的是另外三条：分享（0%）、AI 的深度学习与建议（只做了过敏识别）、
> 疫苗的"计划"（只有记录和提醒）。饮食偏好则是最薄的一块 —— 只是两个文本框。**

所以这不是"推倒重来"，而是**补齐三条腿 + 加厚最薄的那块 + 统一六个板块的外壳**。

---

## 二、现状盘点：六板块 × 五个需求点

图例：✅ 已具备 ｜ ⚠️ 部分具备 ｜ ❌ 缺失

| | 记录 | 回溯 | **分享** | **服务其它能力** | **AI** |
|---|---|---|---|---|---|
| **病史** | ✅ 完整增删改查 | ⚠️ 只有平铺列表 | ❌ | ✅ **已接入食谱设计器** | ⚠️ 识别接口能读病历，界面只开放了过敏 |
| **体检** | ✅ 含报告附件上传 | ⚠️ 同上（附件可预览） | ❌ | ✅ 同上 | ⚠️ 同上 |
| **过敏** | ✅ +「一点即选」快速添加 | ⚠️ 同上 | ❌ | ✅ **已接入（安全底线）** | ✅ **唯一真正落地的 AI**：拍照识别报告 |
| **疫苗** | ✅ 含"下次接种日" | ⚠️ 有「即将到期」 | ❌ | ❌（本不需要） | ❌ |
| **饮食** | ❌ **只是两个文本框** | ❌ 无历史 | ❌ | ✅ 合并进 AI 提示词 | ❌ |
| **体重** | ✅ 完整 | ✅ **含趋势图** | ❌ | ✅ 已接入增减重计划 | ❌ |

### 2.1 已经做得好的（不用重建）

**① "服务其它能力"这条腿，后端已经打通三层：**

| 数据 | 用在哪 | 怎么用 |
|---|---|---|
| **过敏原** | 定制食谱 | 结构化记录 + 旧文本备注**合并后交给 AI**，避免"顾客写了过敏、配方照样用" |
| **病史 / 体检** | 定制食谱 | 关键词匹配出健康标签（肾病 `ckd`、胰腺炎 `pancreatitis`、高血脂…），**驱动配方设计** |
| **饮食偏好** | 定制食谱 | 档案里的 + 顾客下单时单独填的**合并**（下单时填的不写回档案——知情同意范围只有过敏与疾病） |
| **体重** | 增减重计划 | 完整的计划、校正、安全边界 |

> 这一点很重要：**老板需求点 2 的"定制食谱"部分，已经是完成态。**

**② 过敏 AI 识别是全站唯一落地的 AI**，而且做法很克制：
三步（选图 → 上传 COS → 调识别接口）、**识别结果必须先经顾客确认才落库**、
任何一步失败都降级为手工填写。识别接口实际还能读出病历（`medicalConditions`），
只是界面按当时的决定**只开放了过敏**。

**③ 安全边界守得对**：AI 的提示词里明确禁止"判断疾病名称、严重程度、过敏类型、
是否需要治疗"——这些不属于它的任务。

### 2.2 关键缺口

| # | 缺口 | 严重度 | 说明 |
|---|---|---|---|
| **G1** | **分享能力完全缺失** | 🔴 高 | 需求点 1 明确要"下一次就诊时方便看到、甚至分享"。六个板块**都没有任何分享入口**。这是三个作用里唯一 0% 的一个。 |
| **G2** | **饮食偏好太薄** | 🔴 高 | 只有 `preferredFoods` / `pickyFoods` 两个自由文本框。**无结构、无历史、无法回看"偏好什么时候变的"**。而它既要驱动食谱，又要支撑需求点 1 的"饮食偏好变化"回溯。 |
| **G3** | **AI 只做了录入辅助，没做健康分析** | 🟡 中 | 需求点 3 要两件事：① 填写时辅助录入（✅ 过敏做了）② **健康分析与建议（❌ 完全没有）**。而且识别只开放了过敏，体检报告 / 疫苗本 / 病历都还不能拍。 |
| **G4** | **疫苗只有"记录 + 提醒"，没有"计划"** | 🟡 中 | 需求点 4 要的是**可执行的接种计划**。现状：记录里有"下次接种日" + 到期提醒 + 订阅消息。**没有**：按免疫程序生成的接种时间表、缺哪一针、逾期多久。 |
| **G5** | **板块之间没有联动视图** | 🟡 中 | 六个板块各自独立，**没有一个"一眼看全"的健康总览，也没有时间线**。就诊时医生最需要的恰恰是"这只狗过去一年发生过什么"。 |
| **G6** | **六个板块的"外壳"不统一** | 🟡 中 | 记录类（病史/体检/过敏）是同一套组件，疫苗和体重各是各的 —— 列表样式、空态、按钮位置、日期格式都不一致。这是"重构视觉"最实际的收益点。 |
| **G7** | **后台没有独立查看狗健康档案的入口** | ⚠️ 部分 | 营养师在**食谱设计界面里确实能看到**这只狗的过敏/病史/体检（设计器会加载它们当输入），但**没有一个"查看某只狗健康档案"的独立页面**；顾客上传的报告原件也只有顾客自己能看。 |

## 三、需求重整

把老板的 5 点整理成可执行的需求，并按"谁是主角"分层。

### 3.1 狗狗家长（第一优先）

**R1 · 记录**
- R1.1 六类信息都能记：就诊记录、检查/体检报告、过敏报告、疫苗接种、饮食偏好、体重
- R1.2 **拍照/上传即录入**（不只过敏，扩展到体检报告、疫苗本、病历）——AI 辅助 + 顾客确认
- R1.3 记录要有"当时发生了什么"的结构，不只是自由文本

**R2 · 回溯**
- R2.1 **健康时间线**：把六类记录按时间排成一条线，一眼看全"这只狗过去经历了什么"
- R2.2 **就诊前一分钟能看全**：最近一次体检是什么时候、正在吃什么药、对什么过敏
- R2.3 饮食偏好的**变化历史**（什么时候从"爱吃鸡肉"变成"不吃鸡肉"）

**R3 · 分享**
- R3.1 生成一份**可分享的健康摘要**（给兽医看 / 给家人看 / 换医院时带上）
- R3.2 分享内容可控：哪些信息给出去由顾客决定（医疗信息敏感）
- R3.3 形式：小程序内分享卡片 / 长图 / 可打开的链接

**R4 · 疫苗计划**
- R4.1 按免疫程序（幼犬首免、成年加强、狂犬年针）**生成接种时间表**
- R4.2 明确"下一针是什么、什么时候、逾期了没有"
- R4.3 到期提醒（已有订阅消息能力，可复用）

**R5 · AI 健康建议**
- R5.1 在**专业知识库框架下**给出健康分析与建议
- R5.2 边界要清楚：AI 不做诊断，只做"你可能需要留意…""建议咨询兽医"
- R5.3 建议要能落到食谱上（与 R2 的定制能力衔接）

### 3.2 管理员 / 营养师（第二优先）

- R6.1 后台能看到某只狗的健康全貌，用于设计食谱
- R6.2 顾客上传的报告，营养师可以查看原件（现在只有顾客自己能看）
- R6.3 健康标签（肾病/胰腺炎等）在后台可见、可人工修正

### 3.3 老板原话里需要澄清的两处

| 原话 | 需要澄清 |
|---|---|
| "甚至是**分享**之前的记录" | 分享给谁？兽医（专业视图）还是家人（通俗视图）？是否包含报告原件？ |
| "在**专业知识库**的框架下" | 这个知识库现在存在吗？是指已有的 FEDIAF/WSAVA 资料，还是要新建？建议在 R5 开工前先定这一条。 |

## 四、重构方案

### 4.1 分三层，不要混在一起做

```
第一层：外壳统一（视觉）        ← 收益立刻可见，风险最低
第二层：补齐三条缺失的腿        ← 分享 / 疫苗计划 / 时间线
第三层：加厚饮食偏好 + AI 扩展  ← 数据模型要动，收益最大
```

### 4.2 第一层：统一六个板块的外壳

**问题**：记录类共用一套组件，疫苗和体重各写各的 —— 列表、空态、按钮位置、
日期格式、卡片间距都不一致。老板已经指出过"视觉有割裂感"。

**做法**：
1. 抽出一套**健康板块通用外壳**（标题 / 说明 / 空态 / 列表行 / 主操作按钮 / 卡片间距），
   六个板块都用它 —— 与 2026-09-30 已建立的"色系 + 书签"衔接
2. 统一日期/单位/状态文案的显示格式
3. 把各板块的"主操作"位置统一（现在有的在顶部、有的在底部、有的在行内）

**产出**：六个板块长得像一家人；后续加板块（比如"用药"）不用再写一套壳。

### 4.3 第二层：补齐三条腿

**① 分享（G1）**

| 步骤 | 内容 |
|---|---|
| 1 | 健康摘要页：选择要分享的内容（默认全选，医疗信息可取消勾选） |
| 2 | 生成形式：小程序内分享卡片 + 长图（兽医最常要的是能存下来的图） |
| 3 | **只读、带有效期**：分享出去的是快照，不是实时档案；过期自动失效 |

> 医疗信息分享要格外克制：**默认不包含报告原件**，只给结构化摘要。

**② 疫苗计划（G4）**

| 步骤 | 内容 |
|---|---|
| 1 | 建一份"免疫程序"参考表（幼犬首免三针 + 狂犬、成年加强周期） |
| 2 | 按狗的出生日期 / 已有接种记录，**算出还缺哪几针、什么时候该打** |
| 3 | 在疫苗板块顶部显示"下一步：X 月 X 日 打 XX 疫苗"，逾期标红 |
| 4 | 复用已有的订阅消息能力做提醒 |

**③ 健康时间线（G5、R2.1）**

| 步骤 | 内容 |
|---|---|
| 1 | 后端加一个聚合接口：一次取回六类记录，按时间倒序 |
| 2 | 前端加"时间线"视图（可作为第七个书签，或放在最前面作为默认） |
| 3 | 就诊模式：一键生成"最近 3 个月发生了什么"的摘要 |

### 4.4 第三层：加厚饮食偏好 + 扩展 AI

**① 饮食偏好结构化（G2）**

现状是两个文本框。建议改成**结构化的三条信息**：

| 字段 | 形式 | 用途 |
|---|---|---|
| 爱吃的 | 结构化标签（可自由输入） | 提高适口性 |
| 不吃的 / 挑食 | 结构化标签 | 避开 |
| **真过敏** | **不在本板块**，走过敏板块 | 安全底线，必须分开 |

> ⚠️ 现有实现**已经正确区分了"过敏 ≠ 不爱吃"**（代码注释写明），这点要保持。

再加**变更历史**：每次修改记一条，支持"什么时候改的、改前是什么"。

**② AI 扩展（G3、R5）**

| 优先级 | 内容 | 说明 |
|---|---|---|
| P0 | **把已有的识别能力开放到体检报告 / 疫苗本 / 病历** | 识别服务已经能读病历，只差界面开放 + 各板块的确认界面 |
| P1 | 健康摘要与建议 | 基于已有记录 + 专业知识库；**明确不做诊断** |
| P2 | 录入时的智能补全 | 例如疫苗本识别后自动匹配免疫程序、提示还缺哪一针 |

### 4.5 建议的推进顺序

| 期 | 内容 | 依赖 |
|---|---|---|
| **1** | 六个板块外壳统一（第一层） | 无 |
| **2** | 分享（G1） | 无 |
| **3** | 健康时间线（G5） | 需要一个聚合接口 |
| **4** | 疫苗计划（G4） | 需要免疫程序表 |
| **5** | 饮食偏好结构化 + 变更历史（G2） | **要动数据模型**（新增表 + 迁移） |
| **6** | AI 扩展（G3） | 需要先定"专业知识库"是什么 |

> 第 5、6 期会动数据库与 AI 口径，建议单独立项、单独验收。

## 五、需要老板决定的四件事

| # | 事项 | 为什么现在要定 |
|---|---|---|
| 1 | **分享给谁、包含什么** | 决定 R3 的形态（兽医专业视图 vs 家人通俗视图 vs 两者都要） |
| 2 | **"专业知识库"是什么** | R5 的全部前提。是复用已有的 FEDIAF/WSAVA 资料，还是要新建？ |
| 3 | **营养师在后台到底怎么用健康数据** | 决定要不要做后台健康视图（G7）。目前后台只有狗档案分析，没有健康视图 |
| 4 | **是否接受第 5 期动数据库** | 饮食偏好结构化 + 变更历史需要新表；这是本方案里唯一改数据模型的地方 |
