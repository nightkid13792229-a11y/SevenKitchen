# 食谱定制 · 现状体检与优化方案

> 版本：v1（2026-10-04）
> 范围：小程序「食谱定制」顾客流程 + 后端定制单接口 + Web 后台定制单处理流程
> 状态：**体检完成，方案待拍板，尚未改动任何代码**
> 工作区：独立目录 `SevenKitchen-custom-recipe-optimize`（与其它会话物理隔离）
> 方法：三个模块各做一遍只读通读（顾客端页面、后端服务与控制器、后台页面），逐条核对到「文件:行号」

---

## 零、三句话结论

1. **流程是通的，但后台有个大坑**：顾客能下单付款、后台能确认收款→制作→交付；但**在食谱设计器里做好的食谱挂不到订单上**，员工必须回到订单页把数值、食材、步骤**手工重抄一遍**，而且两处表单的字段结构还不一样。这是当前最大的效率与出错点。
2. **后端有 4 处会真实漏钱或锁死产能的隐患**：付款成功与超时关单抢状态、并发提交冲破每日单量上限、退款结果回调断链（退款状态永远停在"处理中"）、后台取消已付款单不退钱。这类问题平时不发作，一发作就是钱和客诉。
3. **顾客侧有一批"说了却没做到"的地方**：预约日期其实是假的（恒为当天）、约满时让顾客"选其他日期"但页面根本没有日期可选、30 分钟付款时限从不告知、已取消的订单显示英文、连点两次会生成两张待付款单。

## 一、现在的流程长什么样

### 1.1 顾客侧（6 步）

| 步 | 顾客做什么 | 系统做什么 |
|---|---|---|
| 1 | 从首页常驻「食谱定制」卡，或「我的 → 我的定制订单」进入 | 两个入口都不带狗；页面内再选 |
| 2 | 选一只狗 | 老档案第一次进要**补确认**：4 道体况动作题 + 活动量 + 餐数，确认后**写回档案** |
| 3 | 填定制需求 | 目标（减重/维持/增重，必填）；可选「需要健康管理」→ 疾病史 + 过敏（点选标签，或拍报告让 AI 识别）；饮食偏好；备注 + 附件 |
| 4 | 勾知情同意（选了健康管理则必须勾） | 按钮才可点 |
| 5 | 提交 | 金额取自后台配置（当前定制费 ¥300、可抵扣 ¥150）；**预约日期恒为当天** |
| 6 | 成功页立即微信支付 | 30 分钟不付自动关单（**顾客不知道有时限**）；付款后可在订单页看进度，**未开始制作可自助取消并原路退款** |

### 1.2 后台侧（5 步）

| 步 | 员工做什么 | 结果 |
|---|---|---|
| 1 | 打开「定制食谱订单」列表 | 可按 5 档状态/日期/关键字筛选；4 张统计卡（待付款/制作中/已交付/收入，**无"已付款"**） |
| 2 | 点「确认付款」（微信回调已自动置"已付款"，人工确认是兜底） | 转「已付款」并给顾客发微信通知 |
| 3 | 点「开始制作」 | 转「制作中」 |
| 4 | 点「在设计器中设计」（新标签打开） | 设计器按 dogId 关联，侧栏能看到该狗最近定制单的需求 |
| 5 | **回到订单页**，在「创建定制食谱」表单里手工填写名称/描述/封面/营养标准/蛋白脂肪碳水/能量密度/食材+制备法+占比/制作步骤，点「提交食谱并交付」 | 生成"只有这位顾客可见"的定制食谱，订单转「已交付」，给顾客发微信通知 |

### 1.3 状态口径对照（三处不齐）

| 后端状态 | 中文含义 | 后台列表 | 后台详情 | 小程序 |
|---|---|---|---|---|
| PENDING_PAYMENT | 待付款 | 有 | 有 | 有 |
| PAID | 已付款 | 有 | 有 | 有（文案写成"已付款 · 等待制作"） |
| IN_PROGRESS | 制作中 | 有 | 有 | 有 |
| DELIVERED | 已交付 | 有 | 有 | 有 |

### 甲级 · 会漏钱 / 会锁死产能（4 条，最高优先）

|---|---|---|---|
| 1 | **钱付了、单却被关掉**：顾客付款成功与"超时自动关单"几乎同时发生时，系统可能把已付款的单改写成"已取消"，而且不退款 | 顾客付了 ¥300，订单显示已取消，钱也不退 | `custom-recipe.service.ts:551-573`、`:604-651`（先读状态、再按 id 无条件更新） |

## 三、建议方案（四档）

### 档一 · 资金与产能止血（后端为主，改动小、收益确定）

1. 付款与关单抢状态：改成"带状态条件的原子更新"，谁先到谁生效；关单前先查一次真实支付结果
2. 下单占名额：改成事务内条件扣减，扣不到就明确拒绝并提示顾客
3. 退款回调补上定制单分支，退款状态能闭环；后台与顾客都能看到结果
4. 后台取消已付款单：按拍板口径处理（禁止 / 自动退款）
5. 附件上传加归属校验；订单号不存在返回业务错误而不是 500
6. 配置定制费为 0 时不允许发起支付（或禁止保存 0）
7. 顺手补接口参数校验（月份、状态枚举），消掉 500

### 档二 · 员工处理链路打通（后端 + 后台，业务收益最大）

1. **设计器 → 订单通路**：设计器发布时带上定制单号，或加一个「交付到订单」按钮，取消手工重抄
2. 交付表单加必填校验；二次确认写清狗名、单号、金额
3. 后台订单详情显示**档案最新**过敏/疾病，并标出"下单后档案有更新"
4. 显示退款状态/支付流水号/取消原因/交付倒计时；列表加"待处理"默认视图与超期标记
5. 后台详情补「已取消」文案
6. 权限：按拍板口径决定客服能否操作

### 档三 · 顾客体验修补（小程序）

1. 首屏加载态
2. 预约日期：**要么让顾客真选**（用排期接口显示可约/约满/节假日），**要么明确改成"下单后我们安排"**并统一三处文案
3. 提交前讲清"下一步付款"；按钮改「下一步：支付 ¥300」；付款页与订单页提示剩余支付时间
4. 防重复：进页面先查未付款单 + 按钮加锁
5. 换狗清空/隔离医疗数据
6. 接上「已取消」文案；把状态文案统一到一处公共工具
7. 附件要么真支持 PDF、要么改文案；登录过期提示改"请重新登录"；首页登录后回跳定制页

### 档四 · 结构性减负（建议单独排期，不混在本轮）

1. 拆分三个超大文件
2. 抽小程序 `custom-recipe` 的 API 层
3. 把字符串断言测试换成真实行为测试

## 六、已拍板的决策（2026-10-04）与分批安排

| # | 问题 | 决定 |
|---|---|---|
| 1 | 预约日期 | **顾客不选**；系统自动排最近可用工作日（当天满则顺延），并明确告知预计交付日 |
| 2 | 后台权限 | **客服/员工可做日常**（确认收款、开始制作、查看订单）；**交付食谱与取消订单仅管理员** |
| 3 | 后台取消已付款单 | **取消时自动原路退款**，并告知顾客 |
| 4 | 交付之后 | **允许「重新交付」**（替换原食谱并再次通知顾客） |
| 5 | 重复下单 | **不限制张数**；只修"连点两次生成两张单"与新增"待付款单提醒" |
| 6 | 退款进展 | **小程序显示**「退款中 / 已退款（含金额）」 |

### 分批安排

- **第一批** ＝ 档一（后端止血）+ 档三（顾客体验）。两块互相咬合（防连点、付款时限、排期、退款状态都要后端先给口子），一起交付、一起验收。
- **第二批** ＝ 档二（后台员工链路），重点是把"设计器做好的食谱一键交付到订单"打通，取消员工手工重抄。

### 第一批的接口契约（后端给小程序的新增/变化）

| 接口 | 变化 |
|---|---|
| `GET /api/v1/custom-recipe-config`（公开） | 新增 `paymentTimeoutMinutes`（0 = 不自动关单） |
| `POST /api/v1/custom-recipe/orders` | `scheduledDate` 改为**系统自动排的最近可用工作日**；返回体新增 `paymentDeadlineAt` |
| `GET /api/v1/custom-recipe/orders/:id`、`GET /my-orders` | 新增 `paymentDeadlineAt`、`refundStatus`、`refundAmount`、`refundedAt` |
| `POST /api/v1/custom-recipe/upload-attachment` | 增加订单归属校验；订单非法/非本人返回业务错误而非 500 |

## 七、第一批执行记录

### 7.1 后端（档一）· 已完成并提交 `e1fa8225`

| 事项 | 落地方式 |
|---|---|
| 钱付了单被关掉 | 关单改 **CAS**：`updateMany({ where: { id, status: PENDING_PAYMENT } })`，抢不过回调就放弃关单 |
| 同上 · 最后一道防线 | 支付回调遇到"订单已关闭但钱到账"：补记流水 → **自动原路退回**，并打 error 日志 |
| 同上 · 事前预防 | 定时关单**前先向微信核查支付结果**，查到已付就确认收款；核查失败本轮跳过（宁可晚关，不可错关） |
| 排期超卖 | 占位改事务内 CAS（按读到的 `bookedCount` 原值条件更新），抢不到换下一天重试，最多 5 次 |
| 口径 1 · 自动排期 | 服务端从今天起找最近可接单工作日，节假日/满员顺延；`scheduledDate` 不再采信顾客传值 |
| 退款断链 | 微信退款回调补 **CRR 分支**，写入 `refundStatus` / `refundedAt` / `refundId` |
| 口径 3 · 后台取消退款 | 取消已付款单先原路退款，退款失败就不取消 |
| 越权上传 | 新增 `assertOrderOwnership`，订单不存在返回业务错误 |

## 十、上线顺序建议

1. **先上后端**（两批的后端改动都在里面）：老小程序、老后台都不受影响（新增字段是追加，权限是放宽）。
2. **再上小程序**：小程序不再传 `scheduledDate`，必须在后端之后发布，否则老后端的必填校验会拦下来。
3. **最后上后台前端**：后台要用到新的「一键交付」接口，必须在后端之后。
4. 本地联调要换后端：小程序默认指向 `http://127.0.0.1:3011/api/v1`，
   而带本轮改动的后端在本工作区（`SevenKitchen-custom-recipe-optimize/backend`）。
   按项目规则，切换 worktree 的后端前要**先停掉原来的后端进程**，再在本工作区执行
   `cd backend && npm run start:dev`。
