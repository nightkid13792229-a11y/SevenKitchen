## 〇、怎么用这份文档

### 0.1 任务编号

`批次.序号`，例如 `1.3` = 批次 1 的第 3 个任务。

- **档位**：`S` = 半天内 / `M` = 1~2 天 / `L` = 3~5 天 / `XL` = 5 天以上
- **依赖**：写清"必须先完成什么"，避免乱序施工
- **验收**：写清"怎么证明这件事真的做完了" —— 不接受"我觉得好了"

### 0.2 状态标记

| 标记 | 含义 |
|---|---|
| ⬜ | 未开始 |
| 🟦 | 进行中 |
| ✅ | 已完成（有验证证据） |
| ⏸️ | **被口径卡住**（等老板拍板） |

### 0.3 一个任务的"做完"包含什么

**任何任务都不算做完，除非同时满足**：

1. 代码写完，**生产代码**类型检查干净：`npx tsc -p tsconfig.build.json --noEmit` **0 错**（见 1.1.1）；
2. 相关测试通过（新增能力必须补测试）；后端全量 ≥ 3158 项、admin-web ≥ 252 项、小程序 ≥ 1642 项，**且 0 失败**；
3. **本模块相关的手工走查做过一遍**（不是只看测试绿）；
4. 在本文的进度表里改了状态，并写下**验证证据**（跑了什么命令、看到什么结果）；
5. 涉及三端契约变化的，同步更新 `docs/05_API_Specs.md`。
6. 动了 `miniapp/` 的，跑过 `npm run preview` 或 `npm run build:mp-weixin`，并明确告诉老板微信开发者工具打开哪个目录。

#### ⚠️ 1.1.1 一个**必须知道**的坑：`tsc --noEmit` 不能当验收标准

实测发现：

| 命令 | 结果 |
|---|---|
| `npx tsc --noEmit`（根 tsconfig，**含测试文件**） | **262 个错误，分布在约 62 个测试文件里** —— 都是**既存**的，与本次重构无关 |
| `npx tsc -p tsconfig.build.json --noEmit`（排除 `**/*spec.ts`） | **0 错** |
| `npx nest build`（同上排除逻辑） | **通过** |

**结论：项目的真实约定是"生产代码干净，测试文件的类型错误长期没人修"。**

所以本计划的验收标准定为：

- **生产代码**：`npx tsc -p tsconfig.build.json --noEmit` 必须 **0 错**；
- **测试文件**：基线是 **262 个既存错误**，要求是**不得新增**（不是"归零"）；
  新增测试文件如果自己引入类型错误，要自己修掉。

> 如果按最初设想的"`tsc --noEmit` 无错"去验收，**每个任务都会被这 262 个历史错误卡住**。

#### 1.1.2 与"联调期间不要跑 build"的关系

`CLAUDE.md` 规定联调期间只跑 `npx tsc --noEmit`（因为 `nest build` 会删掉 `dist/`，把正在跑的后端弄死）。

**修正后的做法**：联调期间用 **`npx tsc -p tsconfig.build.json --noEmit`** ——
它既排除了测试文件的噪音，**又不产出、不删除任何东西**，比原命令更适合当自检。

>
> ⚠️ **联调期间**（有 `start:dev` 后端在跑）**不要跑 `npx nest build`** ——
> 它会删掉 `dist/` 重建，正在跑的后端会当场死掉且 watch 救不回来。
> 这种情况改用 `npx tsc -p tsconfig.build.json --noEmit`（不产出、不删东西）。
