### E1 的两页分工（这是本版最重要的定义）

**第 1 页「专属食谱」= 快速告诉你：这份食谱有哪些食材、长什么样。**
目的是让顾客**确认**"这是不是我要的那份"。确认了，才进入第 2 页解决问题。

要包含：食谱封面、食谱名、卖点、一句话营养结论、食材配比。
**不包含每日喂食量**（那个放第 2 页）。

**第 2 页「采购与制作」= 解决"接下来怎么做"。**
要包含：狗狗每天该吃多少、这一次总共做多少、每种食材用多少（**净用量**）、
补剂用多少 / 什么规格 / 从哪买、生产制作的 SOP。

> 标题**不改**（仍叫「采购与制作」）—— 你的原话："他看着用量清单也可以去采购啊，
> 只不过那个损耗是要他自己来估而已"。

## 一、这个板块到底卖什么

### 1.1 三句话

1. 家长为**"我家狗狗的特殊情况"**付 ¥300，我们出一份**只属于它**的食谱。
2. 这份食谱拿去喂，家长可以选择**自己做**（看我们的制作步骤），也可以**让我们做成品**（¥300 全额抵扣货款）。
3. 卖的不是一份文档，是**一次服务** —— 有交付、有答疑、有售后。

### 1.2 它和另外两条产品线的关系

| | 鲜食成品线 | 补剂线 | **定制线（本板块）** |
|---|---|---|---|
| 卖什么 | 做好的饭 | 预分装补剂 | **一份专属食谱 + 服务** |
| 顾客付什么 | 货款 + 运费 | 货款 | **定制费 ¥300**（买成品可全额抵扣） |
| 我们赚什么 | 货款毛利 | 佣金 | **定制费**；抵扣后靠成品回收 |
| 交付物 | 实物 | 实物 | **食谱 + 报告 + 步骤（数字交付）** |

> **关键区别**：另外两条线交付的是"东西"，这一条交付的是"方案 + 人"。
> 所以它的**交付环节和售后环节**必须比另外两条线更正式 —— 这正是现在最缺的部分。

### 1.3 现状的四个断层（为什么必须重构）

| # | 断层 | 后果 |
|---|---|---|
| 1 | **交付只是一次"写字段"**：把食谱编号写进订单、状态改成"已交付"、发条通知，就完事了 | 没有交付记录、没有交付内容留档、交付后改食谱顾客看到的会**跟着变**且无法回溯 |
| 2 | **售后根本没有**：定制单没有售后状态、没有工单、没有修改/重做/补发通道 | 顾客交付后不满意，只能找客服，客服只能人工微信沟通，系统里查不到任何痕迹 |
| 3 | **设计器和订单是两套东西**：营养师在设计器里做完，要回到食谱管理页手工设置"私密定制 + 客户 + 狗狗"，才能出现在订单的候选列表里 | 员工多绕一步，容易设错归属；设计器本身也不知道自己在为哪张单做事 |
| 4 | **业务规则散落在三个端**：状态文案小程序写了一遍、后台写了一遍、统计口径又一遍；改一个枚举要改 6 处 | 上一次加「已取消」状态时，漏了两处半，顾客看到英文枚举 |

> 第 4 条正是老板说的**"字段、算法解耦"**要解决的问题。它在本文第十、十一节展开。

## 二、我们面对的是哪几类顾客

| 类型 | 典型故事 | 他要什么 | 板块要满足什么 |
|---|---|---|---|
| **A 对症型** | 狗有肠胃敏感 / 结石史 / 过敏，现成食谱都不合适 | 一份能安心喂的食谱 | 症状、过敏、忌口能被准确收集，并在设计时自动拦截 |
| **B 减增重型** | 狗偏胖或偏瘦，兽医说要控制体重 | 一份控量、能长期坚持的食谱 | 体重管理计划与定制需求要能串起来，交付后能看到喂多少 |
| **C 只要方案型** | 想自己做饭，但不知道怎么配比 | 食谱 + 制作方法 | 交付物要包含**能照着做**的步骤与采购清单 |
| **D 看完再买型** | 先定制，满意了再让我们做成品 | 方案满意 → 转成品单 | 抵扣额度要清楚可见，交付后要有顺畅的"去买成品"引导 |
| **E 售后型** | 按食谱喂了两周，狗软便 / 家长觉得量不对 | 有人管、能改 | **必须有售后通道**，且能改食谱、能重新交付 |

> **E 类是这次新补的。** 前面四类都只管"交付之前"，交付完就没有下文了 ——
> 而定制是高价服务，**交付后那段时间**才是真正决定口碑和复购的窗口。
>
> ⚠️ 第二版修正：这个窗口原来是 **30 天**，2026-10-17 老板定为 **7 天**。
> 时间短了，但"交付后必须有人管"这个判断不变 —— 只是管的方式变成
> "窗口内走小程序售后，窗口过后走企业微信"（见第八节）。

## 三、板块要解决的四个问题

| 域 | 谁的心声 | 我们要交付的 |
|---|---|---|
| **A 下单**（小程序） | "我想给我家狗定制一份食谱" | 一条**问得准、问得少**的下单路径：选中狗狗 → 确认体况 → 填需求 → 付款 |

## 六、状态机：主状态少而稳，其余用子状态

> **第二版整体重写。** 第一版是 6 档 + 6 个子阶段，且在等顾客"确认收货"；
> 老板 2026-10-17 定：**5 档**、**交付即完成**、**取消确认收货与自动完成**。
> 原表保留在 6.0 供对照，不静默删除。

### 6.0 第一版是什么样（仅供对照）

| 码 | 顾客看到 | 第二版处理后 |
|---|---|---|
| `PENDING_PAYMENT` | 待付款 | ✅ 保留 |
| `PAID` | 已付款 · 待接单 | ✅ 保留（标签改为「已付款」） |
| `IN_PROGRESS` | 制作中 | ✅ 保留（标签改为「已付款 · 制作中」） |
| `DELIVERED` | 已交付 | ✅ 保留，但含义变了：**售后窗口未过** |
| `COMPLETED` | 已完成 | ✅ 保留，含义变了：**售后窗口已过、彻底结束** |
| `CANCELLED` | 已取消 | ✅ 保留 |

> 第一版说"6 档"。第二版仍然是这 6 个**状态码**，但老板视角只看到 **4 个不同的标签**
> （已付款与制作中在顾客侧合成一档），所以对外称为「**5 档**」：待付款 / 已付款 / 已交付 / 已完成 / 已取消。
> `IN_PROGRESS` 仍然存在，但**顾客侧不再单独展示为一个阶段** —— 他看到的还是「已付款」。

### 6.1 顾客看到的 5 档（2026-10-17 老板定）

| 顾客看到 | 对应状态码 | 含义 | 顾客能做什么 |
|---|---|---|---|
| **待付款** | `PENDING_PAYMENT` | 已下单未付款 | 去支付 / 取消订单 |
| **已付款** | `PAID`、`IN_PROGRESS` | 钱到账，我们在做 | 联系客服（企业微信）；**不能自助取消** |
| **已交付** | `DELIVERED` | 食谱已给你，**售后窗口还没过** | 查看食谱 / 提售后 / 联系客服 |
| **已完成** | `COMPLETED` | **售后窗口也过了**，这单彻底结束 | 查看食谱（历史）/ 联系客服 |
| **已取消** | `CANCELLED` | 超时关单 / 顾客取消 / 后台取消 | 查看退款进展 |

**关键规则：**

1. **交付即进入「已交付」**，顾客**不需要点任何确认**。
2. **「已完成」由系统在售后窗口到期时自动变** —— 顾客无需操作，
   老板也无需操作。窗口天数 = 售后窗口（见 8.4，当前 **7 天**）。
3. **没有"自动完成"了**：第一版的"交付后 3 天未确认自动完成"整条作废。
   现在的"N 天后变已完成"**不是等确认**，而是**等售后窗口关闭** —— 两件事不一样。
4. **售后不影响主状态**：售后是独立的单（见第八节），提售后不会把订单改回"处理中"。
5. 窗口过后**后台仍可重新交付**（F3），此时订单从「已完成」回到「已交付」，
   并且**新的售后窗口重新起算**（否则改完之后顾客没法再提）。

### 6.2 内部子阶段（后台可见，顾客不逐条看）

**第二版大幅精简。** 第一版有 6 个（待接 / 已接 / 等资料 / 设计中 / 审核中 / 待交付）；
老板 2026-10-17 定：现阶段只有他一个人接单、设计、交付，
**工作台待办只保留两档**。

| 子阶段 | 含义 | 进待办吗 |
|---|---|---|
| `PENDING_DELIVERY` | 已付款，**还没交付**（含"正在设计"） | ✅ **待交付** |
| `AFTERSALE_OPEN` | **有未处理完的售后** | ✅ **待售后** |

> 第一版那 6 个子阶段**全部作废**。理由很实在：一个人干，把"已接/审核中"这些
> 拆出来只是给自己增加点击次数，没有任何人需要看这一层。
>
> 如果将来真的雇人了，再从这里加回来 —— 加子阶段只影响后台，顾客侧不受影响，
> 所以现在精简是安全的。

### 6.3 状态与"售后窗口"的联动（第二版新增）

```
待付款 ──付款──> 已付款 ──交付──> 已交付 ──窗口到期──> 已完成
   │                │                │
   └──取消──────────┴────────────────┴──> 已取消
                     （交付前可退，交付后只能调整食谱）
```

| 时刻 | 发生什么 |
|---|---|
| 交付那一刻 | 订单变「已交付」，**售后窗口开始计时**（7 天） |
| 窗口内提售后 | 订单**仍是「已交付」**；售后单据独立推进 |
| 窗口到期（无未结售后） | 订单**自动变「已完成」** |
| 窗口到期（还有未结售后） | **等售后处理完**再变「已完成」 |
| 窗口过后老板主动重交 | 订单回到「已交付」，**窗口重新起算 7 天** |

> 最后一行是第二版想清楚的一处边界：如果不重算窗口，
> 老板好心帮顾客又改了一版，顾客反而没法再提意见了。

### 6.4 状态不是给人看的字符串，而是"能做什么"

> 这一条**第一版就定了，第二版沿用并加强** —— 它是"前端只渲染"的落点。

后端返回订单时，除了状态码，还要一并返回：

| 字段 | 作用 | 前端怎么用 |
|---|---|---|
| `status.code` / `status.label` / `status.tone` | 状态码、中文标签、色彩档位 | 直接渲染徽章 |
| `status.customerHint` | 一句给顾客的说明（"我们正在设计，预计 X 月 X 日前给你"） | 直接渲染 |
| `progress.current` / `progress.timeline[]` | 进度节点 | 直接渲染时间轴 |
| `actions[]` | 当前可做的动作：`{code,label,enabled,disabledReason}` | **遍历渲染按钮**，不做任何判断 |

**第二版的变化**：交付后**不再出现「确认收到」这个动作**；
窗口过后**不再出现「提售后」**（顾客只能看到「联系客服」）。

## 七、交付：一次交付 = 一份"交付单"

### 7.1 现状的问题（具体到会发生什么）

1. 交付只写两个字段：`recipe_id` + `delivered_at`，**没有交付记录**。
2. 交付的食谱是**就地覆盖**的同一行记录（版本号恒为 1）——
   营养师交付后又改了设计器里的配方，顾客下次打开**看到的是新内容**，而且没有任何提示。
3. 顾客交付后**看不到交付物清单**，只能点进食谱详情自己找。
4. 顾客**无法表达"我收到了"或"有问题"**。
5. 后台**看不到顾客有没有看过**，只能靠微信问。

### 7.2 新设计：交付单

**一次交付 = 一条交付记录**，包含：

| 内容 | 说明 |
|---|---|
| 交付编号与版本 | 第几次交付（第 1 版、第 2 版…） |
| 交付物清单 | 见 7.3，每项可配开关 |
| 内容快照 | 交付那一刻的食谱内容被**冻结留档**，之后改食谱不影响这一版 |
| 交付人 / 交付时间 | 谁交的、什么时候交的 |
| 通知状态 | 发没发、什么时候发的 |
| 顾客查看 / 确认 | 什么时候看的、什么时候确认的、有没有说有问题 |
| 替换关系 | 第 2 版替换了第 1 版，但第 1 版仍然可查 |

**同一张订单可以有多条交付记录**（重新交付、售后修改后再次交付）。

### 7.3 交付物清单（**第二版重新定义**）

#### 7.3.0 第一版是什么样（仅供对照，不静默删除）

第一版把 5 项内容（专属食谱 / 营养报告 / 制作 SOP / 采购清单 / 补剂清单 / 喂食建议）
合并成**两页 + 1 张长图 + 1 个营养报告入口**，并规定：

| 第一版规定 | 第二版处理 |
|---|---|
| 第 1 页放**每日喂食量** | ❌ **移到第 2 页**（老板 2026-10-17 纠正） |
| 顾客看得到**采购量**（含损耗余量） | ❌ **整个删掉**，只给净用量（E2） |
| 交付清单含**复诊建议、调整建议** | ❌ **删掉**（E3） |
| 封面与文案人工录入 | ✅ 保留录入，但**改由 AI 生成 + 老板审核**（E5） |

#### 7.3.1 第二版的两页结构

**第 1 页「专属食谱」—— 回答"这是不是我要的那份"**

| 块 | 内容 | 来自哪 |
|---|---|---|
| 封面 | **食谱照片**（AI 生成，老板审核） | 新增 |
| 基础信息 | **食谱名**、**卖点**（一句话）、适用狗狗 | 已有字段，覆盖 AI 生成 |
| 营养背书 | 「✓ 符合 FEDIAF 犬营养标准」 | 已有 |
| **一句话营养结论** | 白话，不是专业表格（AI 生成，老板审核） | 已有 `plainConclusion` |
| 核心营养 | 蛋白·脂肪·灰分·水分·纤维·碳水、能量密度、钙磷比 | 已有 |
| **食材配比** | 食材 + 制备方法 + **占比** | 已有 |
| 详细营养报告 | 点进去看完整报告 | 已有独立页 |

> **这一页不含每日喂食量。** 老板原话把这一页的定位说透了：
> "第一页就是快速的告诉用户，你的食谱有哪些食材，长什么样子。
> 这个也是让用户能够快速确认，这个食谱是不是他自己想要的。"

**第 2 页「采购与制作」—— 回答"接下来怎么做"**

| 块 | 内容 | 说明 |
|---|---|---|
| **每天怎么喂** | 每天多少克、分几餐、每餐多少克 | **营养师给参考值，顾客可改**（E6） |
| **这次做多少** | 做几天、总净重 | 顾客改喂食量后**跟着重算** |
| **每种食材净用量** | 按本次总净重算出每种食材要**用**多少 | ⚠️ **只有净用量，没有采购量** |
| 补剂用量与购买 | 每 kg 食材加多少、什么规格、从哪买 | 见 7.3.3 |
| 制作 SOP | 步骤、火候、注意事项 | 已有 |
| 储存方式 | 冷藏/冷冻多久 | 已有 |
| **喂食建议提醒** | 换粮过渡提醒等 | ⚠️ **只保留这一类提醒** |

> **这一页也没有"采购量"。** 老板原话："我们给净用量，损耗量让用户自己去判断。"
> 理由他说得很清楚：**付费交付要严谨，不能拿一个经验估算的损耗率当严格信息给顾客**。
> （DIY 那边的损耗率是给普通用户的善意参考，不适用于付费交付。）

#### 7.3.2 为什么去掉采购量（记录理由，避免以后又加回来）

| 第一版 | 第二版 |
|---|---|
| 采购量 = 净用量 × (1 + 损耗率)，损耗率默认 1.07 | **不计算** |
| 好处：顾客照着买就行，不用自己想 | 风险：**损耗率是估算的**，不同食材差很多（肉几乎不损耗，叶菜损耗大） |
| — | 顾客看到"买 2723g"以为是精算结果，**实际上只是净用量乘了 7%** |

> 老板的判断：**"付费的用户，我不能靠估算的一个损耗率，作为严格交付的信息。"**
>
> 如果将来要重新提供采购量，前提是**按食材分别设损耗率**（而不是全局一个数），
> 并且**明确标注"这是建议量，不是精确值"**。在此之前不给。

#### 7.3.3 补剂购买：复用 DIY，不另做一套

交付第 2 页的补剂，顾客可以**直接买**。两类商品走两条路：

| 类型 | 是什么 | 怎么买 |
|---|---|---|
| **推广联盟商品** | 第三方（京东 / 淘宝）的商品，我们有推广链接 | **跳转**到对应平台下单，我们赚佣金 |
| **自产预分装补剂** | 我们自己分装的 | **一键买齐**本次所需全部补剂 |

> 老板原话："你可以完全参考一下 DIY 制作单那条路径。"
>
> **实现上直接接 DIY 现有做法**（把本次所需的补剂清单交给补剂下单页）。
> 知道它那边「还没完全收工」，但我们**跟着它走** —— 它收工后这边自动跟着好，
> 不用改两遍。这是老板明确选的方案。
>
> **食材暂时不卖**（老板原话："食材我暂时不卖"），所以食材那几行只是**文字用量**，
> 不带商品链接。

#### 7.3.4 长图（第二版加二维码）

| 项 | 第二版 |
|---|---|
| 用途 | **老板自己用**：买菜时给摊主看 / 打印贴冰箱 |
| 内容 | 第 2 页的内容（净用量、补剂、SOP） |
| **新增** | **嵌入小程序二维码**，别人在微信里扫可以直接进小程序 |
| 扫码落地 | **小程序首页**（不是这张食谱 —— 交付内容是私密的，陌生人看不到） |

> 老板原话："长图就是给自己看的，买菜或者是打印。只是顺手找个地方放个二维码。"
> 所以二维码是**顺带加的传播入口**，不改变长图的主要用途。

#### 7.3.5 AI 生成封面与文案（第二版新增）

**接智谱 AI。** 生成两样东西：

| 生成什么 | 用哪个模型 | 实测速度 |
|---|---|---|
| **文案**：食谱名 / 卖点 / 一句话营养结论 | `glm-4-flash`（文本） | 很快（不到 1 秒） |
| **封面图** | `glm-image`（图像） | 约 **28 秒**/张 |

> 实测对比：`cogview-4` 只要 8 秒，但**食材画得不准**（说鸡胸肉+南瓜+糙米，出来像炒饭）；
> `glm-image` 慢 20 秒，但三样食材分得清、像正经食物摄影。
> **食谱封面必须和内容对得上** —— 对不上，顾客第一眼就会觉得不靠谱。所以选慢的那个。
> （两张都实测过，**没有可见水印**。）

**交互方式（老板选的 A 方案）：**

```
在后台的输入框旁边有个「AI 生成」按钮
   ↓ 点击
生成一版内容，填进输入框（老板可以先改）
   ↓ 不满意
旁边有个输入框：「告诉它怎么改」（比如"再简短点""突出低脂"）
   ↓
重新生成一版
```

**放在哪：** 后台的**食谱设计器** + **食谱编辑页**（两处都加）。
> 老板纠正过我一次：这不是给顾客看的交付页上的按钮，
> 而是**老板自己录食谱信息时用的工具**，只在 Web 后台。

**生成后必须老板确认才录入** —— AI 不直接写库。

**Key 存哪：** 与现有 DeepSeek 一样，**存数据库、加密、后台可配**（不写进代码或配置文件）。

**图片存哪：** AI 给的链接是**临时的会过期**，必须**下载后转存到我们自己的对象存储**，
否则过几天封面就变裂图。

#### 7.3.6 喂食参数：营养师给参考值，顾客可改（第二版新增）

| 项 | 规则 |
|---|---|
| 默认值 | 营养师（老板）在交付时给一个**参考值** |
| 顾客能不能改 | ✅ **能**，在第 2 页直接改 |
| 改了会怎样 | **用量清单跟着重算**（净用量是按喂食量算的） |
| 要不要通知营养师 | ❌ **不通知**（老板明确说不需要） |
| 谁算 | **后端算** —— 顾客改了喂食量，前端不重算，重新调后端拿新清单 |

> 老板原话："用户改喂食量，用量清单肯定要跟着重算呀，因为制作量都不一样了吧。"

### 7.4 顾客侧的交付体验（**第二版重写**）

交付发生时：

1. 顾客收到**微信订阅消息**（如果他点过"允许"）；同时进**小程序消息中心**（第二版新增）；
2. 订单状态变「**已交付**」；
3. 交付卡片显示：交付时间、交付人、交付物清单；
4. 卡片底部动作（**由后端下发**）：
   - 「**查看专属食谱**」→ 第 1 页
   - 「**采购与制作**」→ 第 2 页
   - 「**有问题**」→ 进入售后（第八节）
   - 「**联系客服**」→ 企业微信
5. **没有「确认收到」了**（第二版删除）；
6. **没有"若 N 天未确认将自动完成"的提示了**（第二版删除）；
7. 7 天后自动变「已完成」，顾客不需要做任何事。

> 第一版这里是「确认收到 / 有问题」两个按钮 + "3 天内未确认自动完成"的提示。
> 第二版全删 —— 因为**交付即完成**，顾客没有"确认"这个动作。

### 7.5 重新交付与修改（第二版补充窗口规则）

| 场景 | 行为 |
|---|---|
| 员工主动优化 | 可再次交付，生成新版本；顾客收到通知，旧版本仍可查 |
| 顾客要求修改（窗口内） | 走售后流程；修改完成后**再次交付**，售后单与交付单关联 |
| 顾客要求修改（**窗口过后**） | 顾客只能走**企业微信**；老板**后台仍可改**，改完仍是新版本 |
| **任何一次重新交付** | ⚠️ **售后窗口重新起算 7 天**（第二版新增） |
| 交付后发现错了 | 允许撤回本次交付（回到待交付），并留痕说明原因 |

> **为什么窗口要重算**：如果不重算，老板好心帮顾客又改了一版，
> 结果顾客拿到新版本时窗口已经过了 —— **反而没法再提意见**。
> 这是第二版想清楚的一处边界。

## 八、售后：服务售后与成品售后必须分开

> **第二版整体重写。** 老板 2026-10-17 说这是"多个周期要捋一下"——
> 原来确实有三个不同的周期（30 天售后 / 7 天无理由退款 / 7 天改一次食谱），
> 互相打架。本版统一成**一个时间轴**。

### 8.1 两条线不能混（不变）

| | **服务售后**（本板块） | **成品售后**（现有订单售后） |
|---|---|---|
| 针对什么 | 定制这份**服务**：食谱不合适、要调整 | 收到手的**东西**：坏了、少了、不新鲜 |
| 挂在哪 | 定制单 | 成品订单 |
| 现有能力 | **没有** | 已有（退款 / 重做 / 投诉 / 补发） |
| 本次要做 | **从零建** | 不动，但要在交付卡片里给出入口引导 |

### 8.2 ★ 三个周期统一成一条时间轴（第二版核心）

第一版存在三个互相打架的周期：

| 第一版的三个周期 | 问题 |
|---|---|
| 交付后 **30 天**可提售后 | 太长，数字产品交付 30 天后还能提，说不清 |
| **7 天**内无理由退款 | 与"交付后原则上不退款"（N5）直接矛盾 |
| **7 天**内可免费改 **1 次** | 与"30 天售后窗口"矛盾 —— 到底哪个窗口说了算？ |

**第二版统一成一句话：**

```
交付前 ────────────────── 交付 ────────────────── 交付后 7 天 ──────> 之后
   │                        │                          │
   │                        │                          │
无理由全额退            不能再退款                免费改 2 次          后台仍可改
（7 天内）              （服务已提供）           （超出可申请人工）    但顾客只能走企业微信
```

| 时间段 | 能退款吗 | 能改食谱吗 | 谁发起 |
|---|---|---|---|
| **下单 ~ 交付前** | ✅ 无理由**全额**退 | —（还没交付） | 顾客自助 / 后台 |
| **交付后 7 天内** | ❌ 不能退款 | ✅ **免费 2 次** | 顾客在小程序提售后 |
| **交付 7 天后** | ❌ 不能退款 | ⚠️ 后台**仍可改**，但不走小程序售后 | 顾客只能走**企业微信**找老板 |

> **"7 天免费改 2 次"里的"2 次"是免费额度**。用完 2 次后如果还要改，
> 顾客仍可在**窗口内**提，但变成"人工审核"（老板决定改不改）。
> 窗口过了就是**只能走企业微信**，系统里不再有入口。

### 8.3 售后类型：4 种 → 2 种（第二版）

| 第一版 | 第二版 | 去哪 |
|---|---|---|
| 答疑 | **不建单** | 直接跳**企业微信** |
| 调整食谱 | ✅ **建单**（唯一保留的类型） | 小程序内提交 → 后台处理 |
| 退款 | **去掉**（交付后不退款，见 8.2） | — |
| ~~投诉~~ | **去掉** | 以**聊天记录**形式留在企业微信里 |

> 老板原话："投诉不单做类型，以聊天记录的形式留在企业微信里"。
>
> **为什么这么砍**：现在只有老板一个人，售后单据的价值是"要跟踪、要留痕"。
> 答疑是一问一答，没有"跟进中"这个状态；投诉是个情绪，走人工沟通比走工单合适。
> 只有**调整食谱**需要"提交 → 处理 → 重新交付 → 关闭"这条轨迹。

### 8.4 售后单的生命周期（简化后）

```
提交（描述 + 传图，类型固定为「调整食谱」）
   ↓
待受理 ──> 处理中 ──> 已解决（关联一版新的交付）
                └──> 已不受理（说明原因）
```

- 每一步都有时间点与操作人，**全程留痕**；
- 「已解决」时必须关联到**新的交付记录**（这是它和"答疑"最大的区别）；
- 顾客端能看到售后进度，与订单进度并列展示；
- **顾客可以撤回**（还没受理时）—— 第一版就有，保留。

### 8.5 具体数值（全部后台可配）

| 项 | 定值 | 可配置 | 说明 |
|---|---|---|---|
| 无理由全额退窗口 | 下单后 **7 天**（且未交付） | ✅ | 交付后立刻失效 |
| 售后受理窗口 | 交付后 **7 天** | ✅ | ~~第一版 30 天~~ |
| 免费调整次数 | **2 次** | ✅ | ~~第一版 1 次~~ |
| 窗口后的处理方式 | **后台仍可改**，顾客走企业微信 | 规则固定 | 第二版新增 |
| 交付后主动退款 | **不受理**；确有质量问题由**管理员特批**并留痕 | 规则固定 | 沿用 N5 |

> ⚠️ **第一版的"交付后 3 天自动完成"整条作废** —— 那是配合"确认收货"的，
> 现在不需要确认了。取而代之的是「售后窗口到期自动变已完成」（见 6.3）。
> 这两个数字**不要混**：一个是"等确认"（已删），一个是"等窗口"（7 天）。

### 8.6 与现有客服模块的关系（第二版更新）

**客服会话继续用现有的企业微信客服，不重复造。**

第二版明确两点：

1. **答疑类售后不建单**，直接跳企业微信（8.3）。
2. **入口的位置和形式**：
   - **定制页**（还没下单）：用"不带订单"的模式，只带"从定制页进来"这个来源
   - **订单详情 / 交付页 / 售后台**：带订单号（发一张小程序卡片，客服点开能进那个订单）
   - **窗口过后的顾客**：小程序里不再有"提售后"入口，只剩"联系客服"

> 关于"企业微信能不能**主动**找已下单的顾客"：这是平台能力，不是我们的代码能决定的，
> 需要单独确认企业微信开通了什么。**本文不假设它一定能做到**；
> 现有实现走的是"**顾客发起**→带卡片进会话"这条路，第二版沿用。

## 九、后台管理需求

### 9.1 工作台（新增）

**按待办驱动，不是按列表驱动**。

**第二版：从 5 档精简到 2 档**（老板 2026-10-17 定）。

| 队列 | 说明 |
|---|---|
| **待交付** | 已付款、还没交付（含"正在设计"） |
| **待售后** | 有未处理完的售后单 |

~~待接单~~ / ~~待设计~~ / ~~超期~~ —— **第二版删除**：

> 本次把其余枚举按同一范式补齐。

### L3 · 表单元数据化（问顾客什么，后台可配）

**只对"定制需求问卷"做**（不做通用低代码引擎）：

| 能力 | 说明 |
|---|---|
| 字段定义 | 码 / 标签 / 类型 / 是否必填 / 帮助文案 / 排序 / 分组 |
| 受控类型 | 单选、多选（从词表取）、是-否、文本、长文本、日期、附件、只读推导值 |
| 条件显示 | `visibleWhen`：例如"选了'有过敏'才显示过敏原选择" |
| 校验 | 必填、长度、数值范围、张数 —— **由后端下发规则并最终校验** |

**收益**：老板已经连着改了 6 批定制页文案与结构（见 10-05 的 6 篇文档），
每次都要改小程序并发版。做元数据化后，**改字段不用发版**。

**边界（重要）**：
- 只做**字段级配置**，不做"拖拽建表单"；
- 字段类型**白名单**，不能自定义控件；
- 结构化字段（如过敏原）必须绑定词表，**不允许退化成自由文本** ——
  否则营养师侧的结构化拦截（"配方命中确诊过敏原"报警）会失效。

### L4 · 规则集中化（什么情况下能做什么）

| 规则 | 现状 | 本次 |
|---|---|---|
| 状态流转合法性 | ⚠️ 硬编码在服务里，且有 3 条路径绕过它 | 收敛为**唯一入口**，所有路径都过 |
| 谁能做什么动作 | ❌ 前端 + 后端各判断一次 | 后端统一下发 `actions[].allowed` |
| 什么时候自动流转 | ⚠️ 分散在定时任务与支付回调 | 集中登记 |
| 退款/额度规则 | ⚠️ 与服务代码混写 | 抽成独立策略，参数走 L1 |

## 十五、产能与自动排单系统（老板 2026-10-16 新增要求）

> **老板原话**："整套系统现在只有我一个人可以来接定制单和设计食谱和交付。
> 我需要在 Web 端管理后台和小程序的工作台，有一个地方能够调整我每天可以接单的单量。
> 也可以手动的调整节假日是否接单。也就是说我需要一个自动的排单系统，
> 能够考虑到我每天的食谱设计的生产供给量，以及节假日是否接单的可选开关。"

### 15.1 这个系统要回答的三个问题

| # | 问题 | 谁在问 |
|---|---|---|
| 1 | **今天/这周我接了几单、还能接几单？** | 老板 |
| 2 | **这张单我承诺什么时候交付？系统凭什么这么算？** | 顾客 + 老板 |
| 3 | **明天放假，怎么让系统别接单？** | 老板 |

### 15.2 现有基础（已经有，但要补）

| 已有 | 位置 | 说明 |
|---|---|---|
| 每日接单上限 | `CustomRecipeConfig.dailyCapacity`（默认 4） | 只有一个数字，且**入口只在 Web 后台** |
| 按天的日历表 | `CustomRecipeSchedule`（容量 / 已占 / 是否可接 / 是否公众假期 / 备注） | 结构是对的，但缺"批量按星期设置"和可视化 |
| 自动排期 | 服务端从今天起找最近可接单的工作日，跳过假期与满员，CAS 防超卖 | **算法已有且已修过竞态**，本次不改算法，只改"参数从哪来、怎么看" |
| 交付日推算 | 接单日 + 配置的工作日数（跳过周末与公众假期） | 已有 |

> **结论：排单的"引擎"已经在了，缺的是"驾驶舱"。**
> 本次主要做：① 产能模型补一个维度；② 日历可视化与批量设置；③ 小程序工作台补入口。

### 15.3 产能模型（**第二版简化：只保留一个上限**）

**第一版是两套上限**（每日接单上限 + 每日交付上限），理由是
"接单是收钱那一刻，交付是交出食谱那一天，两者不是同一件事"。

**老板 2026-10-17 否掉了这个设计**：

> "顾客的付款没有上限，因为他可以排单一直往后排嘛。
> 只是我每天交付量，也就是我每天设计食谱的上限需要设置。"

也就是说：**接单不设上限**（顾客可以一直下单，日期往后排），
**只有"每天能交付几份"需要设** —— 因为它等于你一天能设计几张食谱。

| 参数 | 含义 | 第二版 |
|---|---|---|
| ~~每日接单上限~~（`dailyCapacity`） | 一天最多收几张单 | ❌ **删除**（接单不限量） |
| **每日交付上限** | 一天最多交出几份（= 一天能设计几张） | ✅ **保留，且是唯一的上限** |
| **交付工作日数** | 下单后第几个工作日交付（`deliveryWorkDays`） | ✅ 保留，当前 3 |
| ~~排期最多往后看 45 天~~ | 排期范围 | ❌ **删除**（老板："这个不设限"） |

**排单规则（第二版）**：

```
顾客下单
  → 从今天起往后找第一个「未关闭 且 交付量 < 每日交付上限」的工作日  = 承诺交付日
  → 把这个**确定的日期**告诉顾客
  → 占用该日的交付位
```

**举例（老板原话）**：每天只能设计 5 张，那么第 6 个人下单时，
他会被排到**下一个工作日**。

**两条补充规则：**

1. **日期后台可改**：老板可以手动把某张单挪到别的日子（比如临时有事）。
   改完**系统不发通知**，由老板走**企业微信**告诉顾客。
2. **工作日历仍然有效**：哪几天不接单、哪一天单独关掉，仍然按 15.4 那三种方式配。

**验收**：把「每日交付上限」改成 1，连下 3 单，
三张单的承诺交付日应当是**连续三个工作日**，而不是同一天。

> **给老板的一句话解释**：现在只有**一个数字**要管 —— "我一天能做几份"。
> 其余的（哪天休息、某天临时关闭）还是照旧在日历里点。

### 15.3.1 一个务实的提醒

老板现在的单量如果还不到"每天排满"的程度，这套排单系统**不会立刻发挥作用**。
它的价值在两处：
1. **忙起来的那天不会翻车** —— 系统不会在已经排满的日子里继续承诺交付；
2. **顾客看到的日期是可信的** —— 今天已经是"系统自动排 + 有人能改"，
   而不是"永远显示 3 天后"。

### 15.4 工作日历：三种关闭方式

| 方式 | 用途 | 现状 |
|---|---|---|
| **单日关闭** | 明天临时有事 | ⚠️ 表里有，缺便捷入口 |
| **按星期规则**（新增） | 每周日固定休息 | ❌ 没有 |
| **一段日期关闭**（新增） | 国庆放假 7 天 | ⚠️ 有批量接口但入口不清晰 |

**一条硬口径**：关闭某一天时，**已经排在那天的订单不能被静默改期** ——
必须提示"这天已有 N 张单，要不要一并顺延？"，由老板决定。

### 15.5 两个入口（老板要求 Web + 小程序都要有）

#### 入口一 · Web 后台「食谱定制设置 → 产能与日历」

| 区块 | 内容 |
|---|---|
| 产能参数 | 每日接单上限 / 每日交付上限 / 交付工作日数 |
| **未来 30 天日历视图** | 每天显示：星期、是否关闭、已接几单/上限、已排几份交付/上限；可点单日切换开关 |
| 批量设置 | 按星期（周一~周日 各一个开关）+ 选一段日期一键关闭 |
| 占用查询 | 点某一天看这天排了哪些单 |

#### 入口二 · 小程序「工作台 → 今日排单」

老板在外面也要能改，所以小程序要有：

| 区块 | 内容 |
|---|---|
| 今日概览 | 今天接了几单 / 上限；今天要交付几份 / 上限；还剩几个位 |
| 待办 | 待接单 / 待设计 / 待交付 三个数字，点进去是列表 |
| 快捷操作 | **今天不再接单**（一键关闭当天）、明天休息、未来 7 天日历（点选开关） |
| 产能调整 | 直接改"每天能做几份"（改的是配置） |

> **注意**：小程序工作台是**员工/管理员视图**，不是顾客视图。
> 现阶段只有老板一个人用，因此复用现有的员工工作台入口即可，不需要新建权限体系。

### 15.6 产能见底时怎么对待顾客

| 场景 | 顾客看到 |
|---|---|
| 今天已满 | 自动排到下一个可接单日，并写明"最近可接单：X 月 X 日" |
| 未来 7 天全满 | 明确告知"当前排期较满，最早可约 X 月 X 日"，**不隐藏、不欺骗** |
| 全部关闭（长时间放假） | 定制页顶部提示"暂停接单，X 月 X 日恢复"，**按钮置灰**（由后端下发，前端不判断） |

| 2 | 改"每日交付上限"为 1，连下 3 单 | 三张单承诺交付日连续三个工作日，不撞车 |

## 十六、订单入口合并（第二版新增 · 跨模块）

> 老板 2026-10-17 提出：把**成品订单、食谱定制订单、预分装补剂订单**
> 三种合并到**一个入口、一个页面**里。

### 16.1 为什么合并

现在顾客要查订单，得知道去哪一页找：

| 订单类型 | 现在在哪 |
|---|---|
| 成品订单 | 「我的订单」 |
| 定制订单 | 「我的定制订单」（另一个入口） |
| 补剂订单 | 「补剂订单」（又一个入口） |

对顾客来说这是**同一个问题**："我买的东西到哪了？" —— 让顾客先分类再查，
是我们把自己内部的系统边界甩给了他。

### 16.2 合并后的样子（老板定的）

| 项 | 规则 |
|---|---|
| 入口 | **一个**（我的页面里的「我的订单」） |
| 页面 | **一个列表**，三种订单**混排** |
| 怎么区分 | **角标**（标明是哪一种）或**底色**区分 |
| 排序 | 按时间倒序（与现在一致） |
| 筛选 | 需要保留按类型的筛选（混排之后没有筛选会很难找） |

> 老板原话："合并后三种订单混在一个列表页里，只不过用角标或者底色来进行区分嘛。"

### 16.3 先做哪一端（老板定的顺序）

| 顺序 | 端 | 说明 |
|---|---|---|
| **1** | **小程序 · 顾客端** | 老板原话："可以先做小程序客户端" |
| 2 | 小程序 · 员工工作台 | 随后 |
| 3 | Web 后台管理 | 随后 |

> 先做顾客端，是因为**顾客感受最直接**，而且现在三张订单页各自独立、维护成本高。

### 16.4 这件事的难点（提前说清楚，不是技术细节）

**它不是"把三张列表拼在一起"这么简单。** 三种订单的：

| 差异点 | 情况 |
|---|---|
| 状态体系 | 三种订单各自有状态码与文案，**不能简单拉平** |
| 能做的动作 | 成品能"申请售后/确认收货"，定制能"提售后/查看食谱"，补剂又不同 |
| 金额构成 | 成品有货款+运费+抵扣，定制是定制费，补剂有服务费+运费 |
| 售后归属 | 成品售后、定制售后是**两条不同的线**（见 8.1） |

所以合并的正确做法是：**后端给一个统一的"订单条目"渲染契约**
（类型、状态标签、金额摘要、能做什么），前端只负责画。
**这与本文第十一节"前端只渲染"是同一条原则。**

> ⚠️ 这也意味着：**这件事不能只改前端**。后端要先有一个"合并订单列表"的接口，
> 把三种订单归一化成同一个形状。这是本次重构里工作量最大的一项。

### 16.5 验收

| 场景 | 验什么 |
|---|---|
| 顾客同时有 3 种订单 | 一个列表里都看得到，角标/底色能区分，排序正确 |
| 点进去 | 跳到各自的详情页，**不串**（点定制单不能跳进成品详情） |
| 筛选 | 能只看某一种 |
| 总数角标 | 我的页面上的"订单(N笔)"要数三种之和（现在只数成品+定制） |
