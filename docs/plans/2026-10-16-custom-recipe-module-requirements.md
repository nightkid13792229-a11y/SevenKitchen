## 一、这个板块到底卖什么

### 1.1 三句话

1. 家长为**"我家狗狗的特殊情况"**付 ¥300，我们出一份**只属于它**的食谱。
2. 这份食谱拿去喂，家长可以选择**自己做**（看我们的制作步骤），也可以**让我们做成品**（¥300 全额抵扣货款）。
3. 卖的不是一份文档，是**一次服务** —— 有交付、有答疑、有售后。

### 1.2 它和另外两条产品线的关系

| | 鲜食成品线 | 补剂线 | **定制线（本板块）** |
|---|---|---|---|
| 卖什么 | 做好的饭 | 预分装补剂 | **一份专属食谱 + 服务** |
| 顾客付什么 | 货款 + 运费 | 货款 | **定制费 ¥300**（买成品可全额抵扣） |
| 我们赚什么 | 货款毛利 | 佣金 | **定制费**；抵扣后靠成品回收 |
| 交付物 | 实物 | 实物 | **食谱 + 报告 + 步骤（数字交付）** |

> **关键区别**：另外两条线交付的是"东西"，这一条交付的是"方案 + 人"。
> 所以它的**交付环节和售后环节**必须比另外两条线更正式 —— 这正是现在最缺的部分。

### 1.3 现状的四个断层（为什么必须重构）

| # | 断层 | 后果 |
|---|---|---|
| 1 | **交付只是一次"写字段"**：把食谱编号写进订单、状态改成"已交付"、发条通知，就完事了 | 没有交付记录、没有交付内容留档、交付后改食谱顾客看到的会**跟着变**且无法回溯 |
| 2 | **售后根本没有**：定制单没有售后状态、没有工单、没有修改/重做/补发通道 | 顾客交付后不满意，只能找客服，客服只能人工微信沟通，系统里查不到任何痕迹 |
| 3 | **设计器和订单是两套东西**：营养师在设计器里做完，要回到食谱管理页手工设置"私密定制 + 客户 + 狗狗"，才能出现在订单的候选列表里 | 员工多绕一步，容易设错归属；设计器本身也不知道自己在为哪张单做事 |
| 4 | **业务规则散落在三个端**：状态文案小程序写了一遍、后台写了一遍、统计口径又一遍；改一个枚举要改 6 处 | 上一次加「已取消」状态时，漏了两处半，顾客看到英文枚举 |

> 第 4 条正是老板说的**"字段、算法解耦"**要解决的问题。它在本文第十、十一节展开。

## 二、我们面对的是哪几类顾客

| 类型 | 典型故事 | 他要什么 | 板块要满足什么 |
|---|---|---|---|
| **A 对症型** | 狗有肠胃敏感 / 结石史 / 过敏，现成食谱都不合适 | 一份能安心喂的食谱 | 症状、过敏、忌口能被准确收集，并在设计时自动拦截 |
| **B 减增重型** | 狗偏胖或偏瘦，兽医说要控制体重 | 一份控量、能长期坚持的食谱 | 体重管理计划与定制需求要能串起来，交付后能看到喂多少 |
| **C 只要方案型** | 想自己做饭，但不知道怎么配比 | 食谱 + 制作方法 | 交付物要包含**能照着做**的步骤与采购清单 |
| **D 看完再买型** | 先定制，满意了再让我们做成品 | 方案满意 → 转成品单 | 抵扣额度要清楚可见，交付后要有顺畅的"去买成品"引导 |
| **E 售后型** | 按食谱喂了两周，狗软便 / 家长觉得量不对 | 有人管、能改 | **必须有售后通道**，且能改食谱、能重新交付 |

> **E 类是这次新补的。** 前面四类都只管"交付之前"，交付完就没有下文了 ——
> 而定制是高价服务，交付后的 30 天才是真正决定口碑和复购的窗口。

## 三、板块要解决的四个问题

| 域 | 谁的心声 | 我们要交付的 |
|---|---|---|
| **A 下单**（小程序） | "我想给我家狗定制一份食谱" | 一条**问得准、问得少**的下单路径：选中狗狗 → 确认体况 → 填需求 → 付款 |
| **B 交付**（小程序 + 后台） | 顾客："我的食谱好了吗？"<br>我们："做完了，给你" | 一份**版本化、有留档、能追溯**的交付：交付物清单 + 通知 + 顾客确认 |
| **C 售后**（小程序 + 后台） | "这份食谱我喂着不对劲" | 一条**有窗口、有分类、有闭环**的售后通道：答疑 / 修改 / 退款，全程留痕 |
| **D 管理**（Web 后台） | "这些单子谁在做？做到哪了？" | 一个**按待办驱动**的工作台 + 和订单绑定的食谱编辑器 |

**四个域的关系**：A 产生订单 → D 支撑生产 → B 是交付动作 → C 是交付之后的兜底。
本次重构的主战场是 **B、C、D**；A 已经比较完整，只做"去硬编码"的改造。

## 四、顾客视角的完整流程

```
① 进定制页（首页入口卡 / 我的-我的定制订单）
        ↓
② 选一只狗  → 系统给出体况评分与建议方向
        ↓
③ 填定制需求（目标 / 过敏 / 饮食偏好 / 备注 / 上传资料）
        ↓
④ 提交 → 系统自动排期，给出「预计交付日」与「付款时限」
        ↓
⑤ 付款 ¥300（微信支付；30 分钟不付自动关单）
        ↓
⑥ 等待：订单页能看到**进度时间轴**（已接单 → 设计中 → 待交付）
        ↓
⑦ 交付：收到通知 → 订单页出现「你的专属食谱已完成」，可查看交付物
        ↓
⑧ 确认：点「确认收到」；或直接点「有问题」进入售后
        ↓
⑨ 交付后：引导去买成品（¥300 抵扣）／ 30 天内可提售后
```

**现有流程缺 ⑥⑦⑧⑨ 四段**。本次要补的就是这四段。

### 4.1 每一步的验收口径

| 步 | 验收 |
|---|---|
| ② | 体况评分与建议方向由**后端算**，前端只展示；改档案后重进页面，数字跟着变 |
| ③ | 顾客要填的字段由**后端下发**（见第十节 L3）；小程序不再写死任何选项 |
| ④ | 预计交付日、付款截止时间、金额**全部由后端返回**，前端不做日期推算、不做减法 |
| ⑤ | 金额与后端配置一致；配置改了，新单立刻生效，老单不变 |
| ⑥ | 时间轴的每个节点文案、是否完成、时间点都由后端给（见 6.4） |
| ⑦ | 交付物清单由后端给；点开能看；**交付时的内容被冻结留档**，之后改食谱不影响已交付那一版 |
| ⑧ | 「确认收到」与「有问题」两个动作都由后端下发（能不能点、点了会发生什么） |
| ⑨ | 抵扣余额、可用范围由后端算；售后入口按窗口与状态由后端决定是否出现 |

## 五、后台视角的完整流程

```
① 工作台首页：待办队列（待接单 / 待设计 / 待交付 / 超期 / 待受理售后）
        ↓
② 认领订单 / 指派营养师
        ↓
③ 看订单详情：顾客需求 + 档案最新对比 + 资料附件 + 历史沟通
        ↓
④ 点「去设计食谱」→ 打开编辑器（**带着这张订单进去**）
        ↓
⑤ 编辑器里做完 → 发布 → 回到订单 → 一键交付
        ↓
⑥ 交付：选交付物 → 预览顾客会看到什么 → 确认交付 → 系统通知顾客
        ↓
⑦ 等顾客确认；顾客提售后 → 售后工作台处理（答疑 / 修改重交付 / 退款）
```

**现在缺 ①②④⑤⑦**：
- 没有工作台与待办队列（只有一张平铺列表 + 4 张统计卡）

- 编辑器不带订单进去（员工要手工把归属设到食谱管理页）

## 六、状态机：主状态少而稳，其余用子状态

### 6.1 顾客看到的主状态（6 档）

| 码 | 顾客看到 | 含义 | 能否取消 |
|---|---|---|---|
| `PENDING_PAYMENT` | 待付款 | 已下单未付款 | 可自助取消 |
| `PAID` | 已付款 · 待接单 | 钱到账，等我们接 | 可自助取消并全额退款 |
| `IN_PROGRESS` | 制作中 | 营养师在做（内部细分不显示） | 不可自助取消 |
| `DELIVERED` | 已交付 | 食谱已给你，等你确认 | — |
| `COMPLETED` | 已完成 | 你已确认 / 超期自动完成 | — |
| `CANCELLED` | 已取消 | 超时关单 / 顾客取消 / 后台取消 | — |

> **相对现状的两处变化**：① 新增 `COMPLETED`；② `DELIVERED` 不再是终态。
> 理由：交付完还得有"确认"和"售后"两个阶段，现在的 `DELIVERED` 是死胡同
> （代码里它的可流转列表是空数组），导致交付之后再没有任何系统动作。

### 6.2 内部子阶段（后台可见，顾客不逐条看）

给"制作中"这一档配一个**子阶段**字段，与主状态解耦：

| 子阶段 | 员工在做什么 |
|---|---|
| `PENDING_ACCEPT` | 已付款，还没人接 |
| `ACCEPTED` | 已接单 / 已指派营养师 |
| `NEED_INFO` | 资料不足，等顾客补充 |
| `DESIGNING` | 营养师设计中 |
| `IN_REVIEW` | 内部审核中 |
| `READY_TO_DELIVER` | 设计完成，待交付 |

> **为什么不做成主状态**：主状态每加一档，三个端都要改文案与展示。
> 子阶段只影响后台工作台，顾客侧仍是"制作中"。

### 6.3 售后是独立的单，不改主状态

售后不能做成主状态 —— 否则"已交付"和"售后中"会互相覆盖，跟现状 `DELIVERED`
是终态一样僵。**售后是一张独立的单**（见第八节），挂在订单下，可以有多次。

### 6.4 状态不是给人看的字符串，而是"能做什么"

后端返回订单时，除了状态码，还要一并返回：

| 字段 | 作用 | 前端怎么用 |
|---|---|---|
| `status.code` / `status.label` / `status.tone` | 状态码、中文标签、色彩档位 | 直接渲染徽章 |
| `status.customerHint` | 一句给顾客的说明（"我们正在设计，预计 X 月 X 日前给你"） | 直接渲染 |
| `progress.current` / `progress.timeline[]` | 进度节点：`{code,label,done,at,note}` | 直接渲染时间轴 |
| `actions[]` | 当前可做的动作：`{code,label,enabled,disabledReason,confirmText,danger}` | **遍历渲染按钮**，不做任何判断 |
| `actions[].allowed` | 当前登录者有没有权限 | 后端已算好，前端据此显示/隐藏 |

> **这是"前端只渲染"最关键的一条机制**：前端不知道"已付款才能取消"这条规则，
> 它只是把后端给的按钮画出来。规则变了，前端不用发版。

## 七、交付：一次交付 = 一份"交付单"

### 7.1 现状的问题（具体到会发生什么）

1. 交付只写两个字段：`recipe_id` + `delivered_at`，**没有交付记录**。
2. 交付的食谱是**就地覆盖**的同一行记录（版本号恒为 1）——
   营养师交付后又改了设计器里的配方，顾客下次打开**看到的是新内容**，而且没有任何提示。
3. 顾客交付后**看不到交付物清单**，只能点进食谱详情自己找。
4. 顾客**无法表达"我收到了"或"有问题"**。
5. 后台**看不到顾客有没有看过**，只能靠微信问。

### 7.2 新设计：交付单

**一次交付 = 一条交付记录**，包含：

| 内容 | 说明 |
|---|---|
| 交付编号与版本 | 第几次交付（第 1 版、第 2 版…） |
| 交付物清单 | 见 7.3，每项可配开关 |
| 内容快照 | 交付那一刻的食谱内容被**冻结留档**，之后改食谱不影响这一版 |
| 交付人 / 交付时间 | 谁交的、什么时候交的 |
| 通知状态 | 发没发、什么时候发的 |
| 顾客查看 / 确认 | 什么时候看的、什么时候确认的、有没有说有问题 |

#### 7.3.1 现有页面的内容地图（2026-10-16 勘察完成）

**页面一 · 食谱详情页**（`miniapp/src/pages/recipe-detail/index.vue`）
回答的是"**这是什么、为什么适合我家狗**"：

| 顺序 | 块 | 内容 |
|---|---|---|
| 1 | 封面 | 封面图 + 角标 |
| 2 | 基础信息 | 食谱名、卖点、适用狗狗、生命阶段版本 |

| 顺序 | 块 | 内容 |
|---|---|---|
| 1 | 制作清单 · 狗狗信息 | 名字 / 体重 / 餐次 |

| 4 | **营养补充剂表** | 补剂 / 推荐品牌 / 最佳添加时机 / **添加总量** + 一键购买 |

#### 7.3.2 合并方案（✅ 2026-10-16 老板已确认）

**结论：不做 6 个独立交付物，做「2 页 + 1 张长图 + 1 个报告入口」。**

```
交付单
├── 第 1 页「专属食谱」   ← 是什么、为什么适合它（一屏读完，全静态）
│     封面 + 食谱名 + 卖点
│     ✓ 营养标准背书卡
│     食材表（占比口径）
│     补剂表（每 kg 添加量口径）
│     【新增】每日喂食建议（吃多少、分几餐、怎么过渡）
│     【新增】一句话白话营养结论
│     └→ 入口：查看完整营养评估报告
│
├── 第 2 页「采购与制作」（核心页）← 照着做、照着买
│     狗狗信息 + 制作信息
│     食材表（建议采购量，含损耗余量）+ 采购合计
│     营养补充剂表（添加总量 + 推荐品牌 + 一键购买）
│     制作步骤 SOP
│     【新增】储存与复热提示
│
├── 长图导出（复用现有出图能力，可保存到相册、发给家人）
│
└── 第 3 页「营养评估报告」（第 1 页的入口进去）
      现有报告 + 【补】一句白话结论 + 【补】图例（不足/达标/超标）
```

**合并的判断依据**：

| 原有内容 | 现在在哪 | 决定 | 理由 |
|---|---|---|---|
| 专属食谱（食材/占比） | 详情页 | **成为第 1 页主体** | 这是"方案"，必须先看到 |
| 核心营养成分 | 详情页 | **并入第 1 页** | 不必单独一页，跟在食材后面更自然 |
| 营养评估报告 | 独立页 | **降为入口 + 补白话结论与图例** | 专业表格有价值，但顾客需要先看懂结论 |
| 制作步骤 | DIY 制作单 | **留在第 2 页** | 和采购量放在一起才是"照着做" |
| 采购清单 | DIY 制作单（一列） | **不独立成页**，保持"食材表 + 建议采购量" | 采购量天然跟着用量走，拆开反而要来回对 |
| 补剂用量清单 | 详情页 + DIY 制作单 | **两页各留一份，口径不同** | 第 1 页答"加多少比例"，第 2 页答"这一批加多少克 + 买哪个" |
| 喂食建议 | **现在没有**（只在成品订购页有，且绑下单语境） | **新增，放第 1 页尾部** | 顾客最先想知道的就是"每天喂多少" |
| 复诊/调整建议 | 没有 | **暂不做**，放进售后答疑 | 避免交付物过长 |
| 评价 | 详情页 | **不进交付单** | 交付单是我们给的方案，不是商品页 |

**三个必须遵守的设计约束**：
1. **一页一件事**：第 1 页回答"是什么"，第 2 页回答"怎么做"。不要把采购塞进第 1 页。
2. **能出图**：交付物必须能保存成一张长图 —— 家长在厨房里看的是手机相册，不是小程序。
   现有出图能力（A4 基准、2 倍输出、自适应高度）**直接复用**，不要重写。
3. **数据全部由后端组装**：采购量、损耗余量、喂食克数、营养结论 —— 后端算好，小程序只渲染
   （现状：采购量算法在小程序里，见第十一节第 2 项）。

**这次要新做的东西（不多）**：
- 把散在 4 个页面的块**拼成一份带顺序的交付物**（后端给结构，前端按结构渲染）；
- 「每日喂食建议」块（把成品订购页那段**去掉下单语境**后搬过来）；
- 「一句话白话营养结论」（后端根据评估结果生成）+ 报告页补图例；
- 营养师为这张交付单**给定喂食参数**（几餐、每餐多少、吃多少天）——
  现在这个参数是**顾客在 DIY 页自己选的**，定制交付里必须由营养师定。

### 7.4 顾客侧的交付体验

交付发生时：
1. 顾客收到订阅消息；
2. 订单页状态变「已交付」，出现一张**交付卡片**：交付时间、交付人（营养师昵称）、交付物清单；
3. 每项交付物可点开查看；
4. 卡片底部两个动作（**由后端下发**）：
   - 「确认收到」→ 订单转 `COMPLETED`
   - 「有问题」→ 进入售后（第八节）
5. **`COMPLETED` 前一直显示**，不会因为顾客没点就消失；
   超过配置天数（**老板定：3 天**）自动完成，并在订单页写明"若 3 天内未确认，系统将自动完成"。

### 7.5 重新交付与修改

| 场景 | 行为 |
|---|---|
| 员工主动优化 | 可再次交付，生成新版本；顾客收到通知，旧版本仍可查 |
| 顾客要求修改 | 走售后流程；修改完成后**再次交付**，售后单与交付单关联 |
| 交付后发现错了 | 允许撤回本次交付（回到待交付），并留痕说明原因 |

> 口径沿用 10-04 已拍的"允许重新交付"，本次补上**版本与留痕**。

## 八、售后：服务售后与成品售后必须分开

### 8.1 两条线不能混

| | **服务售后**（本板块） | **成品售后**（现有订单售后） |
|---|---|---|
| 针对什么 | 定制这份**服务**：食谱不合适、看不懂、要调整 | 收到手的**东西**：坏了、少了、不新鲜 |
| 挂在哪 | 定制单 | 成品订单 |
| 现有能力 | **没有** | 已有（退款 / 重做 / 投诉 / 补发） |
| 本次要做 | **从零建** | 不动，但要在交付卡片里给出入口引导 |

### 8.2 服务售后能做什么（类型做成可配置字典）

| 类型 | 顾客的意思 | 我们的处理 |
|---|---|---|
| **答疑** | "这个食材买不到 / 怎么换" | 客服或营养师回复，不改食谱 |
| **调整食谱** | "喂了两周，便便不好" | 营养师修改 → 重新交付 |
| **退款** | "我不要了" | 按规则退款（人工审核） |
| **投诉** | "交付太慢 / 沟通不畅" | 记录并跟进 |

### 8.3 售后单的生命周期

```
提交（选类型 + 描述 + 传图）
   ↓
待受理 → 已受理（指派处理人）→ 处理中 → 已解决 / 已拒绝
```

- 每一步都有时间点与操作人，**全程留痕**；
- 「已解决」时如果是"调整食谱"，必须关联到**新的交付记录**；
- 顾客端能看到售后进度，与订单进度并列展示。

### 8.4 窗口与次数（2026-10-16 老板已定）

| 项 | 定值 | 可配置 |
|---|---|---|
| 售后受理窗口 | 交付后 **30 天** | ✅ |
| 交付后自动完成 | **3 天** | ✅ |
| 免费调整次数 | 7 天内 **1 次**（待确认 N2），超出走人工 | ✅ |
| 交付后主动退款 | **原则上不受理**，改为「调整食谱」；确有质量问题由**管理员特批** | 规则固定，特批需留痕 |

### 8.5 与现有客服模块的关系

- **客服会话继续用现有的企微客服**，不重复造；
- 但要从定制单/交付卡片点进去时**带上订单号与来源**，
  让客服一进来就知道是哪张单（现状：小程序点客服**没带订单号**，
  而且客服卡会把定制单错误地解析成"成品订单详情"页面 —— 这是个已发现的缺陷，本次一并修）。

## 十、配置化清单（"字段解耦"的落地清单）

> 老板的要求原话：**"尽量把所有的字段、算法等解耦出来。所有的计算交给后端，前端只负责渲染和呈现。"**
>
> 下面把它拆成**四层**。这是本文最需要工程落地的一节。

### L1 · 参数字典化（数值与开关，后台可改，不用发版）

| 分组 | 参数 | 现状 |
|---|---|---|
| 价格 | 定制费、可抵扣额 | ✅ 已有 |
| 产能 | 交付工作日、每日接单上限、支付超时 | ✅ 已有 |
| 售后 | 售后窗口天数、免费调整次数、自动完成天数 | ❌ 新增 |
| 交付 | 交付物清单开关（7 项）、是否要求顾客确认 | ❌ 新增 |
| 附件 | 张数上限、单文件大小、允许类型 | ❌ 现在写死 9 张 / 10MB |
| 设计默认值 | 默认营养标准、默认能量密度、**生产损耗率**、工时 | ❌ 现在写死，且**两处不一致（1.05 vs 1.07）** |
| 排期 | 防呆天数、占位重试次数、订单号前缀 | ❌ 现在写死 45 天 / 5 次 |
| 通知 | 订阅消息模板 | ⚠️ 走环境变量，可保留 |

### L2 · 选项字典化（枚举变成数据，前端不再写死中文）

必须能在后台维护"码 / 中文名 / 排序 / 颜色 / 图标 / 是否启用"的清单：

| 字典 | 现状 |
|---|---|

## 十五、产能与自动排单系统（老板 2026-10-16 新增要求）

> **老板原话**："整套系统现在只有我一个人可以来接定制单和设计食谱和交付。
> 我需要在 Web 端管理后台和小程序的工作台，有一个地方能够调整我每天可以接单的单量。
> 也可以手动的调整节假日是否接单。也就是说我需要一个自动的排单系统，
> 能够考虑到我每天的食谱设计的生产供给量，以及节假日是否接单的可选开关。"

### 15.1 这个系统要回答的三个问题

| # | 问题 | 谁在问 |
|---|---|---|
| 1 | **今天/这周我接了几单、还能接几单？** | 老板 |
| 2 | **这张单我承诺什么时候交付？系统凭什么这么算？** | 顾客 + 老板 |
| 3 | **明天放假，怎么让系统别接单？** | 老板 |

### 15.2 现有基础（已经有，但要补）

| 已有 | 位置 | 说明 |
|---|---|---|
| 每日接单上限 | `CustomRecipeConfig.dailyCapacity`（默认 4） | 只有一个数字，且**入口只在 Web 后台** |
| 按天的日历表 | `CustomRecipeSchedule`（容量 / 已占 / 是否可接 / 是否公众假期 / 备注） | 结构是对的，但缺"批量按星期设置"和可视化 |
| 自动排期 | 服务端从今天起找最近可接单的工作日，跳过假期与满员，CAS 防超卖 | **算法已有且已修过竞态**，本次不改算法，只改"参数从哪来、怎么看" |
| 交付日推算 | 接单日 + 配置的工作日数（跳过周末与公众假期） | 已有 |

> **结论：排单的"引擎"已经在了，缺的是"驾驶舱"。**
> 本次主要做：① 产能模型补一个维度；② 日历可视化与批量设置；③ 小程序工作台补入口。

### 15.3 产能模型：把"接单量"和"交付量"分开

现状只有一个"每日接单上限"。对一个人来说这是不够的 ——
**接单**是收钱那一刻，**交付**是交出食谱那一天，两者不是同一件事。

| 参数 | 含义 | 谁受影响 | 默认 |
|---|---|---|---|
| **每日接单上限** | 一天最多收几张单（`dailyCapacity`，已有） | 顾客下单时能不能排到这天 | 4 |
| **每日交付上限**（新增） | 一天最多交出几份食谱 | 承诺的交付日往后排 | 4 |
| **交付工作日数** | 接单后第几个工作日交付（`deliveryWorkDays`，已有） | 交付日 | 3 |

**排单规则（按顺序执行）**：

```
顾客下单
  → 从今天起往后找第一个「未关闭 且 接单量 < 每日接单上限」的日子  = 接单日
  → 从接单日往后数「交付工作日数」个工作日（跳过周末与关闭日）      = 候选交付日
  → 若候选交付日当天交付量已满，继续往后顺延到第一个有空位的日子   = 承诺交付日
  → 占用该日的交付位；把承诺交付日告诉顾客
```

**验收**：把「每日交付上限」改成 1，连下 3 单，三张单的承诺交付日应当是**连续三个工作日**，而不是同一天。

> **给老板的一句话解释**：这两个数字**默认一样**（都是 4）。如果懒得分开想，
> 只改「每日接单上限」，系统会自动跟着用同一个数。
> 什么时候需要分开？——例如"周末不接单，但周末可以交付"，或者
> "先收下订单（让顾客安心），交付日往后排一点"。

### 15.3.1 一个务实的提醒

老板现在的单量如果还不到"每天排满"的程度，这套排单系统**不会立刻发挥作用**。
它的价值在两处：
1. **忙起来的那天不会翻车** —— 系统不会在已经排满的日子里继续承诺交付；
2. **顾客看到的日期是可信的** —— 今天已经是"系统自动排 + 有人能改"，
   而不是"永远显示 3 天后"。

### 15.4 工作日历：三种关闭方式

| 方式 | 用途 | 现状 |
|---|---|---|
| **单日关闭** | 明天临时有事 | ⚠️ 表里有，缺便捷入口 |
| **按星期规则**（新增） | 每周日固定休息 | ❌ 没有 |
| **一段日期关闭**（新增） | 国庆放假 7 天 | ⚠️ 有批量接口但入口不清晰 |

**一条硬口径**：关闭某一天时，**已经排在那天的订单不能被静默改期** ——
必须提示"这天已有 N 张单，要不要一并顺延？"，由老板决定。

### 15.5 两个入口（老板要求 Web + 小程序都要有）

#### 入口一 · Web 后台「食谱定制设置 → 产能与日历」

| 区块 | 内容 |

#### 入口二 · 小程序「工作台 → 今日排单」

老板在外面也要能改，所以小程序要有：

| 区块 | 内容 |
|---|---|
| 今日概览 | 今天接了几单 / 上限；今天要交付几份 / 上限；还剩几个位 |
