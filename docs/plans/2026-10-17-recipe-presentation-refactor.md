# 食谱展示层重构需求（2026-10-17）

> **这是跨模块的重构需求，不是定制板块的需求。**
>
> 涉及四条产品线的页面：成品食谱详情、DIY 配置、DIY 制作单、定制交付。
>
> **老板 2026-10-17 的原话**：
> "我最大的担心其实就是定制食谱页面与 DIY 和食谱详情页相关的页面，有太多重复的字段。
> 我担心两边各有一套字段，以后如果想改，如果忘记改另外一边的话，就很麻烦。"
>
> **老板选了范围 B**："连评价、收藏、分享、分装这些也一起整理。"

---

## 一、为什么要做（三个具体代价）

### 代价 1：同一个东西，三个页面三个名字

| 概念 | 详情页 | DIY 制作单 | 交付第 2 页 |
|---|---|---|---|
| 净用量 | `amount` | `theoreticalAmount` / `netAmount` | `netG` |
| 制备方法 | `preparationMethod` | `preparationMethod` | `preparation`（接口层改过名） |
| 占比 | `ratio`（0.4） | — | `ratioPercent`（40） |

**最危险的是 `amount`**：详情页里它是**金额**，制作单里它是**用量**。
同一个名字，一个是钱一个是重量 —— **不会报错，只会算错**。

### 代价 2：一个页面干后端的活

```js
// diy-sheet/index.vue:1975
const actualAmount = theoreticalAmount * (1 + lossRate)
```

采购量在前端算。而且损耗率取的是**全局一个数**，
跟老板定的"不同食材损耗差很多"是矛盾的。

### 代价 3：每页各写一套样式

| 页面 | 总行 | template | **script** | style |
|---|---|---|---|---|
| 食谱详情页 | 2494 | 439 | **965** | 1080 |
| DIY 配置页 | 2092 | 271 | **908** | 907 |
| DIY 制作单 | 3367 | 526 | **1603** | 1232 |
| 交付第 1 页 | 515 | 136 | **118** | 255 |
| 交付第 2 页 | 549 | 156 | **187** | 200 |

**三个旧页合计 7953 行**，交付两页合计 1064 行。
样式部分：详情页 140 条规则、DIY 配置 123 条、DIY 制作单 170 条、合计 **433 条**，
其中大量重复（表格、卡片、按钮）。

**所以"改一个字段要改 3~5 处"不是感觉，是结构决定的。**

## 三、目标：三层结构

> 一句话：**页面只做编排，展示共用组件，计算全在后端。**

```
┌─ 页面层（薄）────────────────────────────┐
│  只负责：取数据 → 组装 → 编排组件顺序        │
│  目标：每页 script < 250 行                │
└───────────────┬──────────────────────────┘
                │
┌─ 展示层（共享组件）───────────────────────┐
│  · 食谱封面块（图 + 名 + 为谁 + 狗信息）     │
│  · 一句话块                                │
│  · 核心营养成分块（含标准背书 + 报告入口）     │
│  · 食材表块（名称 + 占比）                  │
│  · 营养素表块（名称 + 浓度）                 │
│  · 用量表块（名称 + 净用量）                 │
│  · 制作步骤块                              │
│  · 储存块                                  │
│  → 四个页面共用这一套，**一套样式**           │
└───────────────┬──────────────────────────┘
                │
┌─ 逻辑层（后端 + composables）──────────────┐
│  后端算：分组、占比、净用量、补剂量、饭量       │
│  composables：收藏 / 分享 / 评价 /          │
│               生命周期版本匹配               │
│  → 页面不再自己算、不再自己拼状态             │
└──────────────────────────────────────────┘
```

## 五、验收标准（可量化，不靠感觉）

| # | 验收 | 怎么量 |
|---|---|---|
| 1 | 全站搜 `purchaseG` / `totalPurchaseG` / `actualAmount` / `lossRate` | **0 处** |
| 2 | 全站搜 `ratioPercent` 与 `ratio` 混用 | **只剩 `ratioPercent`** |
| 3 | 交付接口层搜 `preparation:`（不带 Method） | **0 处** |
| 4 | **详情页 script 行数** | 965 → **< 250** |
| 5 | **DIY 制作单 script 行数** | 1603 → **< 300** |
| 6 | **DIY 配置页 script 行数** | 908 → **< 300** |
| 7 | **四个页面的 `<style>` 规则总数** | 433 → **一套共享组件内的规则** |
| 8 | **改一次"净用量"的字段名** | **只需改 1 个文件** |

**第 8 条是真正的验收** —— 它直接回答老板担心的那件事。
**做法**：随便挑一个字段（比如净用量），改它的名字，然后看要改几个地方。
**能只改 1 处，这次重构才算成功。**

## 六、不做什么

| # | 不做 | 原因 |
|---|---|---|
| 1 | 不改页面的**视觉设计**（颜色、字号、间距） | 这次只动结构和数据流 |
| 2 | 不动**评价表单本身的字段** | 那是评价模块自己的事 |
| 3 | **不合并成一个页面** | 字段统一之后合并才有可能，但那是下一步 |
| 4 | 不动后台（admin-web）的字段名 | 后台本来就跟数据库一致 |
| 5 | 不改长图（`PrintCanvasBuilder`）的绘制逻辑 | 只改它吃的数据 |

## 七、执行顺序（每步可单独验收）

| 阶段 | 做什么 | 风险 |
|---|---|---|
| **一** | 后端补齐 6 项（补传 + 搬计算） | 低 —— 只加不倒 |
| **二** | 前端改字段名（4 项） | 低 —— 机械替换 + 测试 |
| **三** | 抽 7 个展示组件 | 中 —— 要保证四个页面视觉不变 |
| **四** | 抽 5 个 composables | 中 —— 涉及交互 |
| **五** | 删采购量整条线 | **低 —— 净减少代码** |

> **建议把"删采购量"放到最后做**：前面几步都不改行为，
> 只有这一步会改变顾客看到的内容（少了一列），
> 放在最后，出问题容易定位。

## 八、风险

| 风险 | 说明 | 对策 |
|---|---|---|
| **详情页是在跑的页面** | 成品食谱详情，顾客每天都在看 | 每步都跑回归测试 + 手工过一遍四个页面 |
| **改动跨四条产品线** | 第一次这么大的横向改动 | 按上面五个阶段分步，每步单独上线 |
| **交付页还没真实交付过** | 生产上已交付 0 单 | 反而说明现在改成本最低 |
| **生命周期版本逻辑复杂** | 133 行 / 10 个 computed | **单独做成一个 composable，先抽不改逻辑** |
