### 第 8 条的实测结果（这是最重要的一条）

拿 **`netG`（净用量）** 试：改它的名字要动 **6 个文件**（不含测试）：

| # | 文件 | 角色 | 能不能省 |
|---|---|---|---|
| ① | `custom-recipe.shopping.ts` | 算出来（源头） | ❌ 不能 |
| ② | `custom-recipe.delivery.ts` | 快照类型 + 拷进快照 | ❌ 不能 |
| ③ | `api/custom-recipe.ts` | 前端接口类型声明 | ❌ 不能（类型得跟后端一致） |
| ④ | `RecipeIngredientUsageTable.vue` | **屏幕渲染** | ❌ 不能 |
| ⑤ | `utils/delivery-print.ts` | **长图渲染** | ❌ 不能（另一种媒介） |
| ⑥ | `pages/custom-recipe/delivery-shopping.vue` | **页面适配层** | ⚠️ **理论上能省** |

**⑥ 是什么**：页面要把快照的 `shopping.lines`（只有 `name` + `netG`）
和 `recipe.items`（有制备方法）按名字合并，再喂给组件 —— 因为组件需要三列，而快照分成两处。

**结论：6 个，不是 1 个。** 但要说清楚原因：

- ②③ 是"数据契约"，**任何字段改名都要动**（不是重构能消除的）
- ④⑤ 是**两种媒介**（屏幕 / 长图），需求文档要求长图独立渲染，所以必然是两处
- ⑥ 是唯一能优化的（组件直接吃快照形状）

**所以 `<1 个文件` 这个目标本身也不现实** —— 它至少是 **5 个**（数据源头 + 契约 + 前端类型 + 两种媒介的渲染）。

真正能量的是：**从"每个页面各画一遍"变成"两个渲染器各画一遍"**。
改名前，占比/用量在**四个页面**各画了一遍；现在只有**两个组件 + 一个长图渲染器**。

## 九、那条端到端链路的验证思路（以及我为什么没有造数据）

有人会问：为什么不直接造一条测试消息、或者跑一遍交付？

### 生产环境：不造数据

造测试单会往生产库写真实订单 / 交付记录 / 退款链路。
**验证一个功能不该以污染生产数据为代价。**

### 本地环境：我没有动它

查下来本地库是**真落后 8 个 migration**（已应用 176 / 共 184），
`customer_message`、`custom_recipe_delivery`、`custom_recipe_aftersale` **本地从来没建过**。

跑 `prisma migrate deploy` 能补齐，但**那是老板的开发环境，改它超出这次任务范围**。

### 那这条链路到底靠什么可信？

| 证据 | 说明 |
|---|---|
| **表结构逐列核对** | 生产库 9 列，类型与长度与代码**完全一致** |
| **索引被实际使用** | `EXPLAIN` 显示走了 `customer_message_customer_id_created_at_idx` |
| **Prisma 模型可加载** | 路由返回 401（不是 500），说明 `CustomerMessageService` 注入成功、<br />Prisma client 认识 `customerMessage` 模型 —— **否则模块初始化就会炸** |
| **service 单测 6 个** | 含"写失败不抛错""超长截断""防越权""limit 夹取" |
| **模块注册无误** | `app.module.ts` 的 controller + provider 都注册了，启动无报错 |

> **唯一没被直接观测到的**：`deliver()` 里那一行 `customerMessages.send(...)`
> 在真实交付时会不会被执行到。
>
> 这需要**一次真实交付**才能看到。建议第一次交付后去库里数一下
> `SELECT count(*) FROM customer_message` —— 从 0 变 1 就是通了。

### 为什么接受这个缺口

因为补它的代价（造生产测试数据）**大于**风险本身：
`send()` 外面包了 `?.` 和 `.catch()` —— **就算它完全不执行，交付流程也不受影响**。
所以这条链路的失效模式是"顾客收不到通知"，**不是"交付失败"**。

**影响可控，所以不为此造数据。**

### 为什么会错

> ⚠️ **只改 default 不够** —— 现有行的值不会跟着变，顾客还是按 30 天算。
> UPDATE 带了 `WHERE ... AND aftersale_window_days = 30 AND free_revision_count = 1` 双重保险：
> 只有"还是旧默认值"时才改，将来别人改过就不会被覆盖。

|---|---|---|
| `CoverImageService.renderTitleOnCover` | 在**已有**封面图上叠标题文字 | **不会生图** |
| `AgentProviderConfigService.getEnabledDeepSeekRuntimeConfig` | 取 DeepSeek 的 baseUrl / model / apiKey | **写死 `provider: 'deepseek'`**、走 `findDeepSeekConfig`；取不到智谱的配置 |

### 要接上还差 5 步

| # | 要做 | 说明 |
|---|---|---|
| 1 | 加**通用的** provider 配置读取 | 现在只有 DeepSeek 版。要么加 `findProviderConfig(purpose, provider)`，要么把现有方法泛化 |
| 2 | 写**智谱 glm-image 的客户端** | 跟 DeepSeek 的 chat 接口形状完全不同（生图是另一套请求/响应） |
| 3 | 图生成后**上传 COS** | 与现有 `CoverImageService` 的上传逻辑复用即可 |
| 4 | 加后端接口 | 例如 `POST /admin/recipes/:id/generate-cover` |
| 5 | 加后台按钮 + 加载态 + 失败重试 | 最后一步，也是最简单的 |

**前 4 步都是后端，第 5 步才是"按钮"。**

### 为什么没有勉强做完

这条链路涉及**外部付费接口**（智谱生图约 0.1 元/张）与**新的 provider 集成**，
做一半比不做更糟 —— 会出现"按钮在、点了报错"的状态，比"没有按钮"更让人困惑。

**建议单独排一轮**，且先在本地验证一次真实生图请求，再上线。

## 十五、补剂列表「购买入口」为什么没做 —— 差一层数据

### 需求（2.8.4 ④）

每个补剂卡片要有：产品名+规格 / 需要多少 / 每单位含量 /
**换一个** / **去买** / **一键买齐**。

### 已经有的

- ✅ 需要多少（`totalG`，后端算）
- ✅ 每单位含量（`targets`）
- ✅ 补剂名（`name`）

### 差什么：`ingredientId`

「去买」「一键买齐」都要跳补剂下单页，而下单页建行**必须有 `ingredientId`**：

```ts
saveSupplementPurchaseDraft({
  lines: [{ ingredientId, amount, name, unit }],   // ← 没有 id 建不了行
  ...
})
```

而交付快照里的 `SnapshotSupplement` **只有 `name`**，没有 id。

### 为什么不在这一轮硬加

查了链路，要动 **4 个地方**：

| # | 文件 | 改什么 |
|---|---|---|
| 1 | 交付服务的**输入类型** | `ingredient: { name, type }` → 加 `id` |
| 2 | 交付服务的**调用方查询** | Prisma select 要带上 `ingredient.id` |
| 3 | 域层 `SnapshotSupplement` / `SnapshotRecipeItem` | 加快照字段 |
| 4 | 前端第 2 页 | 加「一键买齐」按钮 |

**做到一半会出现"按钮在、点了报错"** —— 比没有按钮更让人困惑。

### 已经试过并回退

这一轮我试着改第 2、3 步，改完**编译报错**（`ingredient.id` 在输入类型里不存在）——
说明第 1、2 步必须一起改。**已全部回退，仓库回到干净状态**（tsc 仍是基线 273）。

### 建议

单独一轮做，顺序：**① 输入类型 → ② 查询 → ③ 域类型 → ④ 前端按钮**，
每步跑 `tsc --noEmit` 确认错误数仍是 273。

> ⚠️ **快照是老数据**：已经交付过的单子里没有 `ingredientId`。
> 所以前端必须做"拿不到 id 就不显示购买入口"的降级 —— 不能假设字段一定在。
