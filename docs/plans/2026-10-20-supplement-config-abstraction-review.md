# 补剂配置 · 抽象度与解耦性审查

日期：2026-10-20  
审查对象：运费、包邮门槛、服务费、起送、支付超时、排期/售后、标签等配置；后台 Web 配置页；报价/下单/支付链路。  
结论：**不是“全部硬编码”**。这些字段已经进了 `SupplementShopConfig`、后台 Web 配置页和报价服务；但只做到了“字段可配”，还没做到“单一事实源 + 业务语义可配 + 上线值可控”。生产出现 8 元运费/49 元包邮，主要是老配置行没有被迁移到首发目标值，加上默认值分散在多个地方。

## 一、已经解耦的部分

| 配置 | Web 配置页 | 后端消费 |
|---|---|---|
| 加价倍率 | 有 | `supplement-pricing.service.ts` |
| 服务费方式/金额 | 有 | 报价服务 |
| 包材费/袋 | 有 | 报价服务 |
| 圆整规则/用量进位 | 有 | 报价服务 |
| 最低起送 | 有 | 报价 + 下单校验 |
| 最大份数/总天数 | 有 | 报价/下单 |
| 支付超时 | 有 | 补剂微信支付 |
| 截单/产能/自动排期 | 有 | 排期服务 |
| 售后窗口/自动完成 | 有 | 售后/定时任务 |
| 免服务费门槛 | 有 | 报价服务 |
| 运费策略/一口价/模板 | 有 | 报价服务 + `ShippingService` |
| 包邮门槛 | 有 | 报价服务 |
| 分装效期/最短剩余效期 | 有 | 分装/标签 |
| 标签品牌/干燥剂提示 | 有 | 标签服务 |

结论：**这些不是硬编码在报价函数里的数字**；`flatShippingFee`、`freeShippingThreshold` 等都从配置对象读取。生产问题是数据，不是“代码里写死 8/49”。

## 二、真正的问题：字段解耦了，但“默认值/规则/文案”没有单一事实源

### 1. 默认值有三套，且都不是首发目标值

- Prisma schema 默认：倍率 2.0、服务费 9.9、一口价运费 8、包邮门槛 null、总天数 90（`backend/prisma/schema.prisma:3922-3961`）。
- admin-web 表单初始值：同样 2 / 9.9 / 8 / null / 90（`admin-web/src/views/SupplementShop/Config.vue:527-548`）。
- 生产实际行：倍率 2.5、服务费 10、运费 8、包邮门槛 49、总天数 365。
- 需求目标：倍率 2.5、服务费 10、运费 6、包邮 129、总天数按首发口径。

影响：
- 新建环境（配置行不存在）会自动落成旧默认值，不是首发目标值；
- 老环境不会因为加字段而更新旧字段，必须人工保存一次；
- 后台表单默认值、schema 默认值、首发目标值三处，谁也不是权威。

建议：
- 建立**唯一的配置默认值/首发目标常量**（后端一个模块），schema 默认值和后台表单默认值都跟它对齐；
- 增加一个 `apply-supplement-launch-config` 脚本：默认 dry-run，只对“仍等于旧默认值”的字段更新，支持 `--force`；
- 后台配置页顶部显示“当前值与首发目标不一致”的检查项，而不是要求人肉记 6/129。

### 2. 业务规则仍然写死在代码里，配置只给了数字

- 包邮门槛只按 `goodsAmount` 判断（`backend/src/application/supplement-shop/supplement-pricing.service.ts:454-456`）。
- 免服务费门槛只按 `supplementPrice` 判断（同文件 415-419）。
- 后台文案却写“补剂费 + 服务费 + 包材费”达到包邮门槛（`admin-web/src/views/SupplementShop/Config.vue:274`）。
- 小程序注释也还写“商品金额（补剂费 + 分装服务费）”（`miniapp/src/pages/supplement-order/index.vue:370`），和实际纯商品口径不一致。

影响：运营以为自己在配“含服务费的金额”，实际系统按纯商品算；这类规则换口径必须改代码，不能只改后台。

建议：
- 配置增加显式的 `freeShippingBasis` / `freeServiceBasis`（如 `GOODS` / `GOODS_PLUS_SERVICE` / `PAID_TOTAL`），报价按枚举计算；
- 至少把规则说明和计算函数放在同一模块，后台文案从后端返回或引用同一常量，不再手写。

### 3. “最低起送”文案和行为相反

- 后台写“低于此金额只提示，不阻止下单”（`Config.vue:216`）。
- 下单服务实际直接抛错（`supplement-order.service.ts:266-273`）。

影响：运营以为只是提示，顾客却下不了单；这是配置语义冲突，不是显示问题。

建议：明确二选一——要么下单拦截并改文案，要么只警告并删除后端抛错；首发目标为 0，建议先统一成“0 = 不限制；大于 0 则拦截”。

### 4. 运费模板模式依赖隐藏的重量估算

- 一口价模式直接读 `flatShippingFee`，没问题。
- 模板模式用 `estimateWeightG`：袋重固定 100g、平勺按 0.1g/勺、片/粒按 1.2g/单位（`supplement-order.service.ts:1540-1554`）。
- 需求 3.5.3 明确“不要猜密度”，库存按 PCS 记；这里为了模板运费又猜了一次，而且后台没有任何提示。

影响：如果运营选了“按重量模板”，运费可能和真实重量不一致；补剂本来建议一口价，这个模式容易被误用。

建议：
- 补剂首发只开放 `FLAT_RATE`，模板模式隐藏或标记“实验性”；
- 若保留模板，把重量估算规则做成配置/明示，不要藏在代码里。

### 5. 配置接口没有管理员权限

- `AdminSupplementShopController` 类上只有 `AuthGuard + StaffGuard`（`backend/src/interfaces/controllers/admin-supplement-shop.controller.ts:60`）。
- `PUT config`（125-130）、`PATCH catalog/:id`（86-95）、`enable-all-producible`（97-105）都没有 `AdminGuard`。
- 需求 3.11：配置截单/产能/包材/日历 = 管理员；员工不能调管理员动作。

影响：员工可以直接改价格/运费/门槛/上架状态。即使后台页面不展示，接口仍然可调。

建议：配置、上架、批量上架全部加 `AdminGuard`；读配置可保留员工只读或直接也限管理员。

### 6. 配置没有变更审计

- 只有 `updatedAt`，没有 `updatedBy`/旧值/新值/变更来源。
- 订单有 `pricingSnapshot`（好），但“谁把 129 改成 49”查不到。

建议：增加配置变更审计（操作人、时间、字段、旧值、新值）；至少记录 `updatedBy` 和一条变更日志。

### 7. 字段重复定义，容易再次漂移

- `SupplementShopConfigDto`（后端接口）、`admin-web/src/api/supplementShop.ts` 的 `SupplementShopConfig`、`Config.vue` 的表单初始值、Prisma schema 四处各写一份。
- 这次 `maxTotalDays` 已经出现 90/365 不一致；包邮门槛出现 null/49/129 三个值。

建议：
- 以后端 OpenAPI/JSON Schema 为契约生成 admin 类型，或至少加一个“字段清单契约测试”；
- 表单初始值不要手写，加载前用 `null` 占位，加载后用服务端值；失败态不允许直接保存默认值。

### 8. `aftersalePolicy` 是“死配置”

- schema、DTO、后台表单都有 `aftersalePolicy`（`schema.prisma:3971`、`Config.vue:635`）。
- 但售后申请/详情/消息没有任何地方消费它。

影响：运营以为写了售后政策，顾客看不到，属于假配置。

建议：要么在顾客售后页/详情展示，要么从配置页删除，避免“配了没生效”。

## 三、结论与建议顺序

**回答你的问题：**
- 运费、包邮门槛不是硬编码，已经在 Web 配置页里，报价也从配置读；
- 但“默认值、首发目标值、包邮口径、文案、权限”没有统一抽象，生产又沿用了老配置行，所以看起来像硬编码；
- 需要从“字段可配”升级到“规则可配 + 单一事实源 + 上线值有检查”。

建议顺序：
1. 生产后台先把运费改 6、包邮改 129（并确认 `maxTotalDays` 是否要 90）。
2. 配置/上架接口加 `AdminGuard`。
3. 建单一默认值/首发目标常量 + dry-run/apply 脚本 + 配置页差异提示。
4. 修正三处文案（包邮口径、最低起送、小程序注释/说明）。
5. 再决定是否引入 `freeShippingBasis`/模板重量策略；如果首发只用一口价，先把模板模式隐藏。
