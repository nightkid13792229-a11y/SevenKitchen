## 一、定制售后：员工代客发起调整（新增能力）

**问题**：顾客不满意但不会/不方便在小程序提单时，后台没有任何入口能把改好的食谱交回去 ——
「改稿 → 重交」整条链只挂在顾客提交的售后单上。

**做法**：
- `custom_recipe_aftersale.source`（`CUSTOMER` / `STAFF`，默认 CUSTOMER，历史数据零回填）；
- 订单详情（已交付/已完成）新增「代客发起调整」：建单即 `ACCEPTED`、处理人=发起人，
  紧接着 reopen 设计槽位并打开设计器；
- 员工发起**不占顾客免费次数、不受售后窗口限制**；
- 重复点击不报错，复用同一条进行中的调整（`resumed: true`）；
- 建单前校验「这份交付后面有可回改的设计草稿」，老订单直接指路订单页「重新交付」。

**踩到并修掉的**：`reopenForAftersale` 无条件开修订草稿，而「订单设计」流程交付后草稿仍是
`NEEDS_REVIEW` → 400「只有已发布食谱可以创建修订草稿」。现在只有已发布时才开修订，否则复用。

## 二、历史订单食谱：只认「真正用过」的

**问题**：交付过 ≠ 吃过。顾客不认可、正在调整的那份也会出现在历史里。

**口径（老板拍板）**：定制食谱只有**订单已完成**（顾客确认收到 / 交付满 7 天无异议自动确认）
才进历史；有未处理完调整的单不会被自动完成，因此天然排除。

**配套**：历史读**交付快照**（名字/原料/宏量），不再读会被改名、重生成快照就地覆盖的活行；
新交付的快照补写 `nutrition.reportRows`，让以后能原样回看「交付当时那张表」。
`renameSeries` 不再改已交付私密食谱的名字（重交时会按最新草稿重写）。

## 三、配方编辑器

| 问题 | 根因 | 修法 |
|---|---|---|
| 撤销删除后，仪表/宏量/评估全空 | 撤销 = 删除 + 重建，原料 id 变了；营养档案按 id 缓存，空窗期把「没有档案」的原料发去评估 | 发请求前校验档案齐备：先补拉一次，仍缺就保留上一次结果、不发 |
| 撤销后补剂目标被放大几十~几百倍 | 重建时只带回目标定义、丢了原值，服务端按草稿上一次评估回写的总重重算（实测总重 1.24–1.55 g，正常 249.5 g） | 前端带回落库口径的 `targetValue`，服务端全量带值时直接沿用；客户端自算的浓度仍忽略 |
| 镁的每项贡献显示 0.0 | 明细一律「1 位小数 + 克」，镁单项只有 0.005–0.03 g | 统一格式化：≥1 保留 1 位、<1 保留 2 位有效数字 |
