# 疫苗领域审计（B0.6 · 2026-10-29）

> **目的**：在继续修“某一天算错”之前，先把**字段、分类、决定、状态**的“唯一真相”理清楚。
>
> **看不懂技术版？** 看 [大白话版](2026-10-29-vaccine-audit-plain-language.md) —— 不用任何术语，只讲“发生了什么、像什么、会怎样、怎么改”。
>
> **边界**：本文只审计 + 给建议，**不改代码**；Q1/Q2（26 周口径、20 周两个选择）先不拍板。
> **结论先行**：找到 **12 个字段/模型层面的问题**，其中 3 个是“双真相/不稳定主键”，比单个日期 bug 更根本；
> 这些问题不解决，B1–B4 修完仍会在别的组合上冒出来。

---

## 0. 一句话

**疫苗排期的风险，主要不在“日期加减”，而在“同一个事实有几个来源、一条决定挂在什么主键上、一个字段到底表示什么”。**
这轮审计就是把这三件事定死。

## 2. 数据模型总览

```
Dog (birthday 必填)
 ├─ VaccineRecord      (疫苗本上的一针：名称/日期/病种/类别/核对)
 ├─ AntibodyTestRecord (一份抗体报告：日期/项目/结论/下次评估)
 └─ VaccineDecision    (对某个 stepKey 的决定：SKIP/NOT_NOW/STOPPED…)

产品库：不是表，是代码里的 products.ts（名称/别名/厂商/病种/minWeeks/…）
```

**没有独立的“计划表”**：计划是每次用“生日 + 记录 + 抗体 + 决定”实时算出来的纯函数结果。
这是优点（可测试、无状态漂移），也是要求（**输入字段必须无歧义**）。

## 3. 字段字典（只列会进排期的字段）

### 3.1 Dog

| 字段 | 类型 | 谁写 | 谁读 | 含义 | 风险 |
|---|---|---|---|---|---|
| `birthday` | `DateTime`（**必填**） | 建档/编辑 | 排期、年龄 | 狗狗生日 | schema 必填，所以“没有生日”在库里其实不可达；UI 的“缺生日”是**防御性死路径**（P3） |

### 3.2 VaccineRecord

| 字段 | 类型 | 谁写 | 谁读 | 含义 | 风险 |
|---|---|---|---|---|---|
| `vaccineName` | String | 顾客/识别 | 归类、展示 | 本子上的名字 | 自由文本；同名不同苗、别名都能进来 |
| `vaccinationDate` | `@db.Date` | 顾客/识别 | 排期 | 接种日 | DTO 用**上海时区**转字符串，引擎用**本地时区**；服务器不在东八区就会差一天（P2） |
| `components` | String[] | 顾客勾/产品库 | 归类、展示 | 这一针含哪些病种（cdv/cpv/cav/…） | 闭集过滤在服务端；空数组 = 未登记 |
| `kinds` | String[] | **服务端算** | 排期 | 归到哪几类（core/rabies/lepto/core_early/other） | **和 components 双真相**（见 A2）；schema 注释还停在“core/rabies/lepto/other”，漏了 `core_early`（P2） |
| `productVerified` | Boolean 默认 true | 识别/顾客核对 | 排期 | **名字**有没有被人工核对过 | 名字核对 ≠ 医学覆盖；单病种也会被当成核心（见 A3） |
| `attachments` | String[] | 顾客/识别 | 展示 | 原件 URL | 同一张图会挂在多条记录上；删除时有引用检查（已做，P3） |
| `notes` | String? | 顾客 | 展示 | 备注 | 不进排期 |
| 唯一性 | — | — | — | 服务端按“同一天 + 同名”查重 | 不同别名/不同写法可绕过；无 DB 唯一约束（P3） |

### 3.3 AntibodyTestRecord

| 字段 | 类型 | 谁写 | 谁读 | 含义 | 风险 |
|---|---|---|---|---|---|
| `testedAt` | `@db.Date` | 顾客/识别 | 排期 | 检测日 | 时区同 A1（P2） |
| `targets` | String[] | 顾客/识别 | 排期、展示 | CORE / RABIES，可多值 | 服务端过滤闭集；UI 单选；多值时计划只看 CORE |
| `result` | enum | 顾客/识别 | 排期、展示 | PASS/FAIL/UNKNOWN | 不设阈值，照抄报告（正确） |
| `nextReviewAt` | `@db.Date?` | **服务端算 3 年**；DTO 也允许显式传 | 记录区展示 | “下次评估” | **和引擎的 1 年双真相**（见 A1，最严重） |
| `value`/`unit` | String? | 顾客/识别 | 展示 | 原始数值/单位 | 不进排期；不设阈值 |
| 同日多份 | — | — | — | 可存多份 | 引擎只看日期排序；同一天两份不同结论时**没有稳定 tie-breaker**（P2） |

### 3.4 VaccineDecision

| 字段 | 类型 | 谁写 | 谁读 | 含义 | 风险 |
|---|---|---|---|---|---|
| `stepKey` | String | 前端（来自 plan） | 排期 | 对哪一步做决定 | **不稳定主键**：记录一变，stepKey 的含义/存在性会变（见 A4） |
| `decision` | String | 前端 | 排期 | ACCEPT/DEFER/SKIP | 实际只用 SKIP；ACCEPT/DEFER 没有语义（P2） |
| `reason` | String? | 前端 | 展示 | NOT_NOW/STOPPED | NOT_NOW 没有推迟日期，实际是永久跳过（P1） |
| `createdAt`/`updatedAt` | DateTime | DB | — | 时间 | `updatedAt` 可做“推迟 30 天”的基础，但现在没用 |

### 3.5 产品库（代码，不是表）

| 字段 | 含义 | 风险 |
|---|---|---|
| `components` | 这支苗含哪些病种 | 是“能不能顶核心”的真正依据；但引擎认领记录时**没有用它做覆盖校验**（A3） |
| `kinds` | 由 components 推导 | 和记录的 `kinds` 是两套推导 |
| `minWeeks` / `KIND_START_WEEKS` | 起始周龄 | **两套常量**，一个在产品、一个在推荐逻辑；可能不一致（P2） |
| `booster` | 免疫程序（自由文本） | **没有结构化 DOI**；狂犬 36 个月只写在文字里，没法按产品算（P2） |
| 版本 | 无 | 产品库一改，老记录“按名字重算”的规则不一致（A2） |

### 3.6 前端契约

| 字段 | 现状 | 风险 |
|---|---|---|
| `VaccineStep.titer` | 有 | 计划行/下一针都用它；复查过期后仍显示“已完成”（B1） |
| `VaccineStep` 无 `matchedRecordDate` | 无 | “已完成”只能显示计划日，不是实际接种日（V13） |
| `VaccineStep` 无 `options` | 无 | 20 周后“接种/测抗体”两个选择没有数据出口（Q7） |
| `VaccinePlanResponse` 无 `history`/`superseded` | 无 | 旧的首免步骤只能整条隐藏，补记入口没有数据（V5） |

## 4. 高风险发现（按严重度）

### 🔴 A1 `nextReviewAt` 双真相：记录区写 3 年，计划写 1 年

| 项 | 内容 |
|---|---|
| 现象 | 抗体合格后，**记录区**显示“下次评估 2029-xx”（服务端按 3 年算并存进 `nextReviewAt`）；**免疫计划**显示“下次复查 2027-xx”（引擎按 1 年算，且**完全不读**这个字段） |
| 根因 | 2026-10-17 把引擎从 3 年改成 1 年，但服务端 `computeAntibodyNextReviewAt` 仍写 3 年；DTO 仍允许客户端传 `nextReviewAt`；记录区读字段、计划读引擎 |
| 影响 | 同一页两个日期，家长必然问“到底哪个”；也是“边界没考虑全”的典型 |
| 建议 | **唯一真相 = 引擎算**：服务端不再写 3 年；DTO 去掉/限制 `nextReviewAt`；API 返回“引擎算出的复查日”；记录区与计划区用同一个数 |
| 归属 | B1（必须在做 20 周两个选择之前） |

### 🔴 A2 `kinds` 与 `components` 双真相，读路径还有三套分类

| 项 | 内容 |
|---|---|
| 现象 | 一条记录同时存 `components`（病种）和 `kinds`（类别）。写入时由 components 推 kinds；读取时 `classifyRecordKinds` 又可能按产品库/名字重算；产品库变化时，只有 `components` 为空的记录会“跟着变准”，有 components 的记录仍用旧 kinds |
| 根因 | 2026-10-05 存 kinds、2026-10-06 加 components；两者都保留，读路径做兼容 |
| 影响 | 同一条记录在不同时间/不同入口可能被算成不同类别；V4（单病种算核心）就是这条链上的一个口子 |
| 建议 | **components 是唯一事实，kinds 是派生值**：写入只存 components；读取一律用同一函数重算；或存 kinds 但只作为缓存并标注版本。不要再让读路径“看情况选一个” |
| 归属 | B0.6/B3（V4） |

### 🔴 A3 `productVerified` 语义混用：名字核对 ≠ 医学覆盖

| 项 | 内容 |
|---|---|
| 现象 | 字段本意是“产品名有没有被人工核对过”，但计划把它当“这一针算不算数”；一只只打了“细小单苗”的狗，名字核对通过 → 被算成完整核心一针（V4） |
| 根因 | 安全默认值只防“识别错名字”，没防“名字对、覆盖不够” |
| 影响 | 该算没算（狗漏打），比多提醒严重 |
| 建议 | 拆成两个概念：`nameVerified`（名字核对）与 `coverageConfirmed`（病种覆盖够不够）；引擎认领 core 时必须校验 `coversCoreSeries`，不能只看 kinds |
| 归属 | B3（V4） |

### 🟠 A4 `VaccineDecision.stepKey` 不稳定：决定会“漂移”或变孤儿

| 项 | 内容 |
|---|---|
| 现象 | 决定按 `stepKey`（如 `core-puppy-2`、`lepto-restart-1`）存；记录一加/一删，步骤序列重排，同一个 key 可能指向**另一针**；某个 key 可能**消失**（如重启步骤），决定留在库里但没人读 |
| 根因 | 用“materialize 后的步骤标识”当业务主键 |
| 影响 | 家长点“这次先不打”，过几天补了一条记录，这个决定可能落到另一针上；或者永远不生效/不显示 |
| 建议 | 决定不要挂 stepKey，改挂**稳定目标**：`kind + episode`（如“第 2 次核心首免”），或挂“规则”（如“这一类暂不提醒”），或每次读计划时按当前步骤重新匹配并清理孤儿 |
| 归属 | B6（V7）前必须先定 |

### 🟠 A5 `NOT_NOW` 没有“推迟”语义

| 项 | 内容 |
|---|---|
| 现象 | NOT_NOW = 永久跳过这一步；对年苗就是跳过一年；没有“推迟到某天”的字段 |
| 根因 | 决策模型只有 `decision` + `reason`，没有时间 |
| 影响 | 临时不方便（生病/出差）会变成长期漏打（V7） |
| 建议 | 加 `snoozeUntil`（或用 `updatedAt + N 天`）；NOT_NOW 只隐藏到该日期；STOPPED 才是长期 |
| 归属 | B6（Q5） |

### 🟠 A6 `materializeSteps` 与 `matchRecords` 两套认领

| 项 | 内容 |
|---|---|
| 现象 | 窗口/锚点在一次认领里算；状态/DONE 在另一次认领里算；两次的 `Claimer` 独立 |
| 根因 | 历史演进：先有 materialize，后有 match |
| 影响 | 可能出现“窗口按 A 针算、状态按 B 针算”的不一致；V11 的重复行也是这类“两处各算一遍”的后遗症 |
| 建议 | 一次认领，同时产出“窗口 + 状态 + 命中记录”；或用差分测试证明两套永远一致 |
| 归属 | B0.7（差分测试）/ B1–B4 视结果 |

### 🟡 A7 日期/时区三套口径

| 项 | 内容 |
|---|---|
| 现象 | DTO 用 `TimezoneUtil.toShanghaiDateString`；引擎 `toDateText` 用本地 `getFullYear/getMonth/getDate`；服务端查重 `toDayText` 也用本地 |
| 根因 | 历史演进，没有统一入口 |
| 影响 | 服务器在东八区时看不出来；换时区/云函数环境会差一天（疫苗日期差一天不是小事） |
| 建议 | 统一用 `TimezoneUtil` 的“上海日历日”；`@db.Date` 的读写在 service 边界一次转好，引擎只收 `YYYY-MM-DD` 字符串（它已经是） |
| 归属 | B0.6 / 所有批次 |

### 🟡 A8 分类有三套函数、一套死代码

| 项 | 内容 |
|---|---|
| 现象 | `classifyVaccineKinds`（按名字）、`kindsOfComponents`（按病种覆盖）、`classifyRecordKinds`（读记录时选一个）；`productCoversKind` 没有调用方 |
| 根因 | 逐步补出来的分类规则 |
| 影响 | V4 的“单苗算核心”就出在“按名字”这条路上；同一支苗在不同入口可能归成不同类 |
| 建议 | 只保留一条主链路：**components → kinds**；名字只用于“查产品库/提示补勾”，不再直接产出 core；删除或收编死代码 |
| 归属 | B3（V4） |

### 🟡 A9 同日多份抗体没有稳定 tie-breaker

| 项 | 内容 |
|---|---|
| 现象 | `findCoreTiterCover` 只按 `testedAt` 排序；同一天两份（一份 PASS、一份 FAIL）时，取哪份取决于数组顺序 |
| 根因 | 没有 `createdAt`/`id` 的次级排序 |
| 影响 | 同一天复测的家长可能看到不确定的结果 |
| 建议 | 明确规则：同日取**最新创建**的一份（`createdAt`/`id`），并在文档里写死 |
| 归属 | B1 |

### 🟡 A10 DTO 仍允许客户端传 `nextReviewAt`

| 项 | 内容 |
|---|---|
| 现象 | `CreateAntibodyTestDto.nextReviewAt` / `Update…` 可传；服务端会用它覆盖自动计算 |
| 根因 | 早期设计允许“兽医填复查日” |
| 影响 | 家长/前端可写出第三个复查日；与引擎的 1 年冲突（A1） |
| 建议 | 要么删除这个入参（复查日只由引擎算），要么明确“只有兽医/后台可传”，并提供审计 |
| 归属 | B1 |

### 🟡 A11 `VaccinePlanResponse` 缺 `options` / `matchedRecordDate` / `history`

| 项 | 内容 |
|---|---|
| 现象 | 20 周两个选择、已完成行的实际接种日、旧首免补记，都没有数据出口 |
| 根因 | 契约是 2026-10-15 冻结的，后续需求（Q7/V13/V5）没进契约 |
| 影响 | UI 只能“藏”或“猜”，V13/V5/Q7 做不干净 |
| 建议 | B0.6 定字段：`options`（VACCINATE/TITER）、`matchedRecordDate`、`history`（被让开的步骤 + 补记入口） |
| 归属 | B1/B4/F |

### ⚪ A12 低风险但要知道

| 项 | 内容 |
|---|---|
| “缺生日”死路径 | `Dog.birthday` 必填；UI 的“缺生日”状态在库里不可达；要么删，要么让 birthday 可空（产品决定） |
| `kindOfStepKey` | `core_early` 分支永远不命中（key 是 `core-early-1`），会落到 `core`；目前不可达，但别留 |
| `pickNext` 与计划排序 | 计划排序同时间按“必打优先”，`pickNext` 只按窗口；同一时刻可能“下一针”和计划第一行不是同一条 |
| 重复记录 | 服务端按“同名+同日”查重；不同别名可绕过；无 DB 唯一约束 |
| 长寿命上限 | 狂犬 20 格 / 钩端 20 格；20 岁以上的狗会排完，属边界 |

## 5. 这 12 条与 7+1 个案例的关系

| 案例 | 直接被哪条字段/模型问题放大 |
|---|---|
| V1 抗体过期 | A1（两个复查日）+ 引擎把 titer 当 DONE |
| V2 26 周补强消失 | 状态机缺 `CORE_PRIMARY_DONE → 26W` 的“错过”分支 |

| V4 单苗算核心 | A2 + A3 + A8（分类三套） |
| V5 钩端旧第 2 针 | A4（stepKey 漂移）+ 状态机缺 restart 的当前步选择 |

| V11 两行评估 | A6（两套认领）+ titer 替换所有核心步骤 |
| V17 25 周晚起步 | 16/26 周边界 + 状态机缺 `CORE_LATE_START` |

## 6. 对 Q1 / Q2 的影响（为什么先不拍板是对的）

- **Q1（26 周口径）**：它不是一个“日期选择”，而是**状态定义**——`CORE_PRIMARY_DONE`（16 周完成）和 `CORE_LATE_START`（没完成）必须分开。
  字段审计会决定：用哪个字段判定“完成”（`lastCoreDose >= birthday+16w`），以及 `lastDose` 是否包含组合苗里的核心成分。
  这些定清楚后，Q1 就不再是“要不要打”，而是“这两类狗分别怎么排”。
- **Q2（20 周两个选择）**：它依赖 A1（复查日唯一）、A11（`options` 字段）和 R9（是否主动提示）。
  字段审计会决定：`titerEligible` 是“步骤属性”还是“计划选项”，复查日由谁算。
  这些定清楚后，Q2 只是“给不给两个按钮”，不是“要不要改模型”。
- **结论**：先做 B0.6/B0.7，Q1/Q2 很可能会变成“模型里已定”的事情，而不是拍脑袋的选择。

## 7. 不变量清单（B0.7 用，先 12 条）

1. 一个类别最多一个“当前步”；计划里不出现重复行（同 kind+label+date）。
2. 被替代/被让开的步骤，绝不作为“当前步”。
3. 一条记录最多认领一步；组合苗不能算成多针。
4. `productVerified === false` 的记录不认领任何步骤，且 `pendingReview` 计数正确。
5. 未来日期、早于起始周龄、认不出类别的记录不认领任何步骤，且必须有冲突提示。
6. 有 ≥16 周一针、且没有 26 周针/合格抗体的狗，必须出现 26 周补强或“补一针”（1% 兜底）。
7. 晚起步（没有 ≥16 周一针、现在 ≥16 周）必须出现“补一针”，不能出现“6~8 周第 1 针”。
8. 抗体 PASS 不得出现核心疫苗行；只出现一个“抗体复查”；复查日 = 唯一真相。
9. 抗体 FAIL 必须出现“补一针”或明确提示（Q2 定案后）。
10. 钩端上一针 ≥18 个月 → 必须出现重启（第 1 或第 2 针），不能只排年度。
11. 决定只能影响它当初指向的那一步；步骤变了不能漂移到别的针，孤儿决定必须可清理。
12. `next` 必须在 `plan` 里（或明确为空）；`next` 与计划第一行的排序口径一致。

## 10. B0.7 首轮结果（2026-10-29）

> 500 个随机历史（固定 seed 20261029），6 条不变量，跑现有引擎。
> 报告：[2026-10-29-vaccine-invariant-audit.md](2026-10-29-vaccine-invariant-audit.md)

| 不变量 | 违反数 | 说明 |
|---|---|---|
| I4 钩端 ≥18 个月空档必须重启 | **46** | 最大的一类：旧的“第 2 针”把重启步骤挡住了 |
| I2 16 周完成首免 → 26 周补强/补一针不能漏 | 6 | 1% 兜底被漏 |
| I3 ≥16 周晚起步 → 不能套 6~8 周第 N 针 | 6 | 25 周/17 周的边界 |
| I1 计划里不出现完全相同的两行 | 1 | 抗体替代的多行 |
| I6 抗体替代只该有一个核心行 | 1 | 同上 |
| I5 下一针必须在计划里 | 0 | 首轮没撞到 |

**怎么读这组数：**

- 这不是“bug 数”，是“规则被破坏的次数”；同一个根因（比如“旧首免步骤还是当前步”）会在很多随机历史里重复出现。I4 的 46 次，大部分是同一个根因。
- 示例里的 `[cpv,ccov,lepto]` 是随机生成器**故意**制造的“名字与病种不一致”组合，用来压字段冲突；真实数据不会这么多，但能逼出“到底谁说了算”。
- 这 6 条只是第一版；下一轮会补“决定不漂移、字段唯一真相、同日多份抗体”等不变量，并加一份“参考状态机”做对照。

**结论：** 不变量测试确实能撞出“7 个案例之外”的问题（比如 I4 的 46 次），比继续穷举例子更接近“考虑全”。
