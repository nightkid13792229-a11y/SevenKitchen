## 1. #1 复查日唯一来源

### 规则

- 抗体合格后的“建议复查日”由**排期程序**算一次：`检测日 + 1 年`。
- 记录区、免疫计划、以后可能的提醒，都读这一个结果。
- 存储里不再写一个独立的“3 年后”日期；旧值只作审计，不再展示。
- 页面上写“**建议复查**”，不写“抗体到期/保护期到了”。

### 改前 / 改后

| | 2026-10-01 抗体合格 |
|---|---|
| **改前** | 记录区：下次评估 **2029-10-01**；计划区：下次复查 **2027-10-01** |
| **改后** | 记录区 + 计划区：**建议复查 2027-10-01** |

### 改动

| 层 | 改什么 |
|---|---|
| 服务端 | 保存抗体报告时不再写“检测日 + 3 年”；读取时按 1 年算（或写 1 年，旧数据读时覆盖） |
| 接口 | `nextReviewAt` 返回 1 年；客户端传的 `nextReviewAt` 先忽略/限制（兽医改期后续再做） |
| 页面 | 记录区显示同一个 1 年日期；文案改为“建议复查” |
| 老数据 | 已存 3 年的记录：**读时按 1 年算**，不批量改库；字段留作审计，后续可清理 |

### 测试

1. 存了 3 年 → 接口返回 1 年；计划也是 1 年。
2. 不合格/未判读 → 没有复查日。
3. 记录区与计划区的日期**完全相同**（新增一条“同一事实”测试）。
4. 老数据（字段=2029）读出来仍是 2027。

### 风险

低。唯一影响：以前显示 2029 的记录会变成 2027（这正是要修的）。兽医改期是后续增强，不在这一版。

### 不做

不改 20 周/4 周门槛；不改 PASS/FAIL 判定；不改 1 年这个产品口径（Q6 已定）。

## 2. #3 成分唯一

### 规则

- 一支苗算不算“完整核心一针”：**只看成分**，必须同时含 **犬瘟（CDV）+ 腺病毒（CAV）+ 细小（CPV）**。
- 只防一种、只防两种（如二联）→ **只算记录，不能顶完整核心一针**。
- 名字只用于：查产品库、预填“含哪些疫苗”、提示家长补勾；**不再用名字直接判 core**。
- 两个问题分开：
  - **名字核对过吗？**（识别/人工核对）
  - **这一针覆盖够吗？**（成分）
- 扫描识别：名字不在产品库、或成分不明 → 要求家长补勾“含哪些疫苗”，勾完才参与计划；手工录入已经这样做。

### 改前 / 改后

| | 记录“细小单苗”2026-06-26 |
|---|---|
| **改前** | 被算成核心第 1 针；计划从第 2 针（2026-07-10）开始 |
| **改后** | 记录保留，标“只防细小一种，不能顶核心一针”；核心第 1 针仍待接种（原建议 6 月，已过） |

### 改动

| 层 | 改什么 |
|---|---|
| 分类 | 只保留一条主链路：成分 → 类别；名字分类不再产出 core |
| 认领 | 引擎认领 core 时校验“三病齐全”，不能只看类别 |
| 页面 | 单苗/二联记录下加一句“只防一种，不能顶核心一针；建议补打/咨询兽医” |
| 扫描 | 未知名字 / 成分不明 → 要求补勾；不再“核对名字就算数” |

### 实现（2026-10-30 · commit `9a9051a0`）

- 名字不再直接判 `core` / `core_early`；产品库按**真实成分**（`kindsOfComponents`）算。
- 读取记录时顺序：`components` → 产品库 → 名字（只保留狂犬/钩端/可选苗）；
  存下来的 `kinds` 只当缓存，**不再作为事实**。
- 单病种名字只推断**一个成分**：细小→cpv、犬瘟→cdv、腺病毒→cav、
  副流感→cpi、狂犬→rabies、钩端→lepto；联苗（二/四/六联）不猜，要求补勾。
- 组合苗修正：二联+钩端不再被“早期苗”吞掉；二联+狂犬仍只算 rabies（汪倍护）。
- 识别草稿同一套：单病种推断成分；联名 → `kinds` 空、`productVerified=false`，
  界面请顾客补勾。
- 页面“只防一种”的提示按原顺序留到 **F 阶段（UI 最后）**；后端已保证单苗不顶核心。

### 老数据 / 预检

- **只读统计**：名字像“单苗/犬瘟/细小/腺病毒”、但没有成分、没有产品库匹配的记录，有多少条？影响多少只狗？
- 预检结果小 → 直接改；结果大 → 先给家长一句解释（“我们补上了以前漏掉的一针”），再改。
- 这些记录会从“已完成”变回“未完成”，提醒会变多——方向安全。

### 测试

1. 名字矩阵：犬瘟单苗 / 细小单苗 / 腺病毒单苗 / 犬二联 / 四联 / 六联 / 卫佳细 / 犬特威 / 猫三联。
2. 不变量：单病种记录永远不能认领 core。
3. 基线：`C-SINGLE`、V4 对照。

### 风险

中。数据影响面需要预检；提醒变多是预期方向。

### 不做

不改产品库；不改“认不出必须勾病种”；“六联是否含钩端”交给成分，不再猜名字。

## 3. #2 决定贴类别

### 规则

- **“这次先不打”** = **这一类推迟 30 天**；30 天后重新出现。
- **“不再接种了”** = **这一类都不再提醒**；随时可恢复。
- 决定记在**类别**（核心/狂犬/钩端）上，不记在“第 2 针”这种会变的位置上。
- **事实优先**：这一类真的有记录 → 就是完成，不叫“忽略”。

### 改前 / 改后

| | 狂犬 2025-10-01 打的，2026-10 点“这次先不打” |
|---|---|
| **改前** | 直接跳到 2027-10（两针空两年） |
| **改后** | 30 天后再提醒；30 天内不再催；到期后重新出现 |

| | 补了一条记录之后 |
|---|---|
| **改前** | 便签跟着“第 2 针”的位置走，可能贴到别的针 |
| **改后** | 便签贴在“这一类”上，记录怎么增删都不漂移 |

### 改动

| 层 | 改什么 |
|---|---|
| 决策模型 | 增加 `kind` + `snoozeUntil`；唯一键 `(dogId, kind)`；不再用 stepKey 当业务主键 |
| 迁移 | 旧 stepKey 决策 → 按前缀归到类别；NOT_NOW → 从 `updatedAt` 起推迟 30 天；孤儿决定清理 |
| 计划 | `pickNext`/`selectPlanSteps`/`buildIgnored` 按类别决定处理；`ignored` 一个类别一行 |
| 页面 | “这次先不打”后写“30 天后再提醒”；“不再接种”仍整类停；留 F 阶段 |

### 实现（2026-10-30 · commit `1b13f2d2`）

- `VaccineDecision` 增加 `kind` 与 `snoozeUntil`；唯一键 `(dogId, kind)`。
- `NOT_NOW` = 从今天起 30 天；`STOPPED` = 长期；`ACCEPT`/`DEFER` 不再接受。
- `ignored` 按类别计数（一个类别一行），带 `snoozeUntil` 供前端显示。
- API 仍用 `stepKey` 调用，后端映射到类别；旧 `(dogId, stepKey)` 唯一键保留，
  切换/回滚期间旧代码仍能工作；再用 BEFORE 触发器从 `step_key` 自动补 `kind`，
  旧写入不会撞 `kind NOT NULL`（commit `da0ba759`）。
- 迁移把旧 `stepKey` 回填类别；旧 NOT_NOW 从 `updatedAt` 起算 30 天；孤儿清理；
  **生产 0 条决定**，所以生产迁移是空操作。
- 页面文案（`IgnoreSheet` 里“两个选项行为一致”已过时）留 F 阶段。

### 迁移规则（2026-10-30 老板确认）

- 旧 **“这次先不打”（NOT_NOW）**：从**当时决定的时间**（`updatedAt`/`createdAt`）算 30 天；
  已经超过 30 天的，直接视为过期、重新出现。
- 旧 **“不再接种了”（STOPPED）**：按 `stepKey` 前缀归到类别，整类停。
- 找不到对应针的旧决定：清理（留日志），**不硬套**到别的针。
- **生产只读预检：`VaccineDecision` 0 条** → 生产迁移是空操作；
  仍用 fixture/副本演练，不直接改库。

### 测试

1. NOT_NOW 后补一条记录：决定仍在这一类，不漂移。
2. 30 天后重新出现；30 天内不出现。
3. STOPPED 整类隐藏；恢复后回来。
4. 有记录时，决定不覆盖事实（DONE 就是 DONE）。

### 风险

中。需要数据迁移；老决定要归档/清理；家长可能预期“跳过一整年”，文案要解释。

### 不做

第一版不做“按单针推迟”；不做 ACCEPT/DEFER（没有语义）；不做无期限的 NOT_NOW。

## 4. #4 两套算法：先测的结果

### 已经做了什么

- 1000 个随机历史，1195 个“已完成”步骤。
- 检查：每个“已完成”的命中日，是否落在它自己的窗口内（允许第一步很晚 / 宽限 4 周）。
- 结果：**0 个窗口不一致**。
- 报告：[2026-10-30-vaccine-differential-audit.md](2026-10-30-vaccine-differential-audit.md)。

### 结论

- **目前没有证据表明两套算法会给出互相矛盾的窗口/状态**。
- 因此：**不重构**。把这条检查留作守门员；以后字段/模型改了再跑。
- 这符合“先测不盲改”：不为了“看起来整齐”去动核心。

### 以后什么时候再考虑重构

- 如果这条检查出现 >0 的不一致；
- 或者 #1/#3/#2 的改动让窗口/状态的来源发生变化；
- 或者真实数据抽查发现“日期和状态说的不是同一针”。
