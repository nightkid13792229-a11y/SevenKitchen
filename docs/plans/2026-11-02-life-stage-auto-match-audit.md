# 生命阶段自动匹配：页面盘点、交互评审与优化方案

> 日期：2026-11-02
> 范围：小程序顾客端全部页面（含员工端需要"版本"的履约页）
> 方法：代码通读 + 生产库只读统计 + 生产接口实测
> 状态：**已出设计稿** → [优化设计方案](../superpowers/specs/2026-11-02-life-stage-auto-match-design.md)（2026-11-02）

---

## 一、先把"自动匹配"拆成三件事

顾客说的"自动匹配"，在系统里其实是三层不同的能力。混在一起谈，就会得出"四页都做了"这种看似完整、实际体验断层的结论。

| 层 | 是什么 | 谁在做 | 出错时的后果 |
|---|---|---|---|
| **① 阶段判定** | 根据生日、品种/体型、活动量、人工覆盖，判断这只狗现在处于哪个阶段 | 后端权威实现（`resolveDogProfileStage`） | 热量算错、推荐错 |
| **② 版本选择** | 一道菜有多个生命阶段版本时，选出该给这只狗的那一版 | 详情页**已自动**；订购/DIY **靠上层传入 + 人工点"切换"** | 做错配方（幼犬吃成犬粮） |
| **③ 告知与留痕** | 不匹配时说清楚、让顾客确认、把确认记下来 | 四页都有卡片，但触发条件、文案、确认方式各不相同 | 该提醒没提醒 / 提醒了但没记 |

**本次评审的重点是 ② 和 ③。** ① 已经收口到后端，质量可以，不需要重做。

| 只有 1 个版本的菜 | 6 / 29 | |

**三个直接结论：**

1. **不是边缘场景。** 近八成在售的菜有多个版本，版本选择是主路径上的事。
2. **提醒几乎没被触发过。** 三个月只有 3 次确认——要么大家都没选错，要么**该提醒的场景根本没走到提醒**（下面会看到，确实有）。
3. **这 3 条里有 2 条是"误判"。** 见第四节场景 2。

## 三、页面盘点：谁需要，谁不需要

### 3.1 必须"自动匹配"的页面（决策页）

| 页面 | 现在做了什么 | 应该做什么 | 差距 |
|---|---|---|---|
| **食谱详情** | 后端按狗自动选版；有"已匹配：X"卡；可打开版本列表切换 | 保持自动选版；匹配态轻量展示；**没选狗时不谈匹配** | 🔴 未选狗/游客也会看到红色"没有完全匹配版本" |
| **成品订购** | 版本下拉在**页面最顶部**；换狗**不换版**，弹红卡让顾客点"切换到X"；卡片"我已知晓"后结算**再弹一次** | 版本跟着狗走；一页一个"版本条"；确认只做一次 | 🔴 版本与狗分离；双确认；手动切换多一步 |
| **DIY 配置** | 只在"不匹配"时出现卡片；**没有换版入口**；匹配时完全看不到是哪一版 | 和订购页同一套版本条；可换版 | 🔴 顾客做的是哪一版，页面上没有 |
| **DIY 制作单** | 不匹配时静态展示 | 任何情况下都记明"版本"，打印件上也有 | 🟡 正常单看不出是哪版 |
| **再次购买** | 沿用上次买的版本；狗阶段变了才弹红卡 | 沿用上次版本，但**主动提示并按新阶段切换** | 🟡 不会自动跟新阶段；看不出"上次是哪版" |
| 订单确认 / 订单详情 | 无任何版本信息 | 显示"旺财 · 普通成年犬版" | 🟡 顾客无法核对买的是哪版 |
| 员工端 订单中心 / 生产 | 打印标签里有适用阶段，订单中心没有 | 订单中心也显示版本 | 🟢 影响小，但履约核对靠标签 |

### 3.2 需要"阶段"、但不需要"版本匹配"的页面

| 页面 | 现状 | 判断 |
|---|---|---|
| **首页筛选** | 手动多选，**10 个术语混着两套口径**（见下） | 🟡 该帮顾客预选，而不是让他自己猜 |
| **收藏** | 无任何阶段信息 | 🟡 可加"适合旺财"标记 |
| **狗狗档案** | 有"生命阶段"展示 + 人工覆盖 | 🟢 基本够，缺"为什么是这个阶段" |
| 饭量计算 / 体重管理计划 | 自动用阶段算热量 | 🟢 正常，可把依据说清楚 |
| 定制食谱 | 自动用阶段；顶部已按 2026-10-18 决定隐藏 | 🟢 不动 |
| 补剂订购 | 继承制作单 | 🟢 不需要匹配，可带一句"来自哪份制作单" |
| 试吃装 | 多道菜组合，不绑定单只狗 | ⚪ 不需要 |

首页那 10 个筛选项（生产接口实测）：

> 小于14周幼犬、大于等于14周幼犬、幼犬、成犬、普通或高运动量成犬、老年犬、低运动量成犬或老年犬、妊娠期、哺乳期、繁殖期

**"幼犬"和"小于14周幼犬"有什么区别？"老年犬"和"低运动量成犬或老年犬"呢？** 顾客答不上来，我们自己的两套命名（档案层 / 食谱层）也没统一。

### 3.3 明确不需要的页面

售后、地址、消息、客服、登录、协议、订单列表（除"再次购买"入口外）——它们不参与"这只狗该吃哪一版"的决策，不要为了"统一"硬加提示。

## 四、站在顾客角度：7 个真实场景

> 下面的"心里话"是按现有代码路径推出来的，不是虚构的情绪。

### 场景 1｜朋友分享来一条食谱链接（未登录、没填狗）

页面先出现红色卡片：**"当前狗狗档案没有完全匹配版本，已展示可用替代版本。"**

心里话：*"我还没填狗呢，哪来的'不匹配'？"*

**这是全站性问题，不是个别菜。** 生产接口实测：不带狗请求任何一道菜，返回的都是 `FALLBACK_ADULT`；一道只有一个版本的菜也一样。也就是说，**每一个游客打开每一道菜，都会看到一条红色警示**。

### 场景 2｜狗是幼犬，但这道菜没有幼犬版

顾客在订购页看到红卡，写的是：**"「旺财」的档案对应大于等于14周幼犬，当前手动展示低能量成年犬 / 老年犬版本，请确认是否适合。"**

心里话：*"我没手动选啊，是你们给我的。"*

**这是文案把系统行为说成了顾客行为。** 生产库 3 条确认记录里，有 2 条就是这种情况：那两道菜**根本没有幼犬版**（一道只有成犬版，一道只有低活动/老年版），系统回退展示，却把结论记成了"顾客手动换版"。

### 场景 3｜换一只狗，版本不跟着换

订购页最上面是版本下拉，往下翻才是"选哪只狗"。换狗之后，版本不变，页面变红，要求顾客再点一次**"切换到普通成年犬版"**。

心里话：*"系统不是知道我家狗的年龄吗？为什么还要我点？"*

详情页其实已经做到了"换狗自动换版"——**同一件事，两个页面两种做法**。

### 场景 4｜点了"我已知晓"，结算又弹一次

订购页卡片上的"我已知晓"只是把卡片藏起来，**不留痕**；点"立即购买"时又弹一个内容几乎一样的窗，这次才留痕。

心里话：*"我刚点过啊，是不是没点上？"*

DIY 页反而是对的：卡片确认即留痕，生成制作单时不再问。

### 场景 5｜在 DIY 页想知道自己做的是哪一版

页面从头到尾没有版本信息；只有出问题时才冒出一张红卡。想换一版，得退回详情页、切换、再重新进来。

心里话：*"我这份到底是幼犬版还是成犬版？"*

### 场景 6｜复购时狗已经长大了

订单里看不出上次买的是哪一版；点"再次购买"，还是老版本，然后弹红卡让顾客自己切。

心里话：*"它都一岁多了，你们还给我幼犬版？"*

（这恰好是产品规划里最重要的"幼犬→成犬过渡"时刻，现在处理得最粗糙。）

### 场景 7｜首页想按"我家狗能吃"筛

顾客面对 10 个术语，不知道自家狗算"幼犬"还是"小于14周幼犬"，也不知道"低运动量成犬或老年犬"包不包括自家 8 岁的狗。

心里话：*"你直接按我家狗筛不行吗？"*

## 五、五条设计原则

1. **默认即正确。** 系统先替顾客选对，顾客只需要确认；不要把选择题丢给顾客。
2. **版本跟着狗走。** 狗变了，版本必须跟着变；手动选择只对当前这只狗、当前这次有效。
3. **一页一个版本条。** 详情、订购、DIY、制作单用同一个组件、同一套文案，不再四页四说法。
4. **只在"选错有后果"时拦。** 幼犬/繁殖期选错是安全问题，必须确认；成犬与老年/活动量档位之间是偏好问题，提示即可，不必拦。
5. **说过的话要算数。** 同一次下单只确认一次；确认即留痕；订单、制作单、复购页都能查到"是哪一版"。

## 六、方案

### 6.1 一个组件：版本条（Version Bar）

放在"当前爱犬"卡片正下方，跟着狗走，不放在页顶。

```
┌──────────────────────────────────────────────┐
│ 旺财 · 2岁 · 普通成年犬                        │
│ 这道菜做「普通成年犬」版 · 按档案匹配   换一版 › │
└──────────────────────────────────────────────┘
```

- 匹配时是**中性色**，不是绿色大块，也不喊"已匹配"（"匹配"是系统词，顾客不关心）。
- 点右侧打开底部版本列表：每版一行，标注"适合谁"，自动匹配那版打勾，当前版标"当前"。
- 不匹配时才整条变色（黄/红），且**必须给出出路**（恢复匹配版 / 看适合的菜）。

### 6.2 六种状态，六套文案

| 状态 | 触发条件 | 文案 | 动作 |
|---|---|---|---|
| **已选对** | 系统自动选中匹配版本 | 这道菜做「普通成年犬」版 · 按档案匹配 | 换一版 |
| **手动换过（低风险）** | 顾客主动换到成犬/老年/活动量另一档 | 当前：低能量成年犬/老年犬版 · 不是按旺财档案匹配的 | 恢复为普通成年犬版 |
| **没有这一版** | 这道菜没有该阶段的版本（回退） | 这道菜没有适合旺财（幼犬）的版本，现展示「普通成年犬」版 | 看看幼犬能吃的菜 |
| **高风险不匹配** | 幼犬/繁殖期 ↔ 其他 | 红色 + 一句后果说明（钙磷、能量密度） | 换合适版 / 仍要继续 |
| **无法确认** | 结论接口失败 | 暂时无法确认这份食谱是否适合旺财 | 重试 |
| **还没选狗** | 未登录 / 没档案 | 添加爱犬，自动匹配版本 | 去添加 |

**关键：没选狗时，绝不出现"不匹配""没有完全匹配版本"这类字样。** 顾客这时连对象都没有。

### 6.3 换狗 / 换版规则（一张规则表，四页共用）

| 动作 | 结果 |
|---|---|
| 进入页面 | 按当前狗自动选版 |
| 换一只狗 | **自动重选**；顶部轻提示"已按旺财切到普通成年犬版"（不弹窗、不红卡） |
| 顾客手动换版 | 仅对这只狗生效；显示"手动选择"状态；换狗后重置为自动 |
| 再次购买 | 沿用上次版本；若狗的阶段变了，**自动切到新版并说明**："上次是幼犬版；旺财现在 14 个月，已换成成犬版" |
| 下单 / 生成制作单 | 高风险且未确认 → 确认一次并留痕；同一单不再问第二次 |

### 6.4 确认与留痕：分级，而不是一刀切

| 组合 | 提醒强度 | 是否拦 | 是否留痕 |
|---|---|---|---|
| 幼犬 ↔ 成犬/老年；繁殖期 ↔ 其他 | 红色 + 说明后果 | 下单前确认一次 | ✅ 每次下单 |
| 成犬 ↔ 老年 / 活动量档位 | 黄色提示 | 不拦 | 可选 |
| 这道菜没有该阶段版本（回退） | 中性说明 + 出路 | 不拦 | — |
| 无法确认 | 灰色 + 重试 | 不拦 | — |
| 没选狗 | 不提示 | — | — |

> ⚠️ 这一条会**修改 2026-09-19 定下的"每次不匹配都确认"**。它不是技术选择，是合规口径，需要老板拍板（见第十节）。若维持原口径，则退化为"所有不匹配都确认，但只确认一次、文案按真实原因写"。

### 6.5 让版本"看得见"：三处必须补

1. **订单确认页**：在狗信息旁加"普通成年犬版"。
2. **订单详情 / 制作单**：同上；制作单的打印件也加一行。
3. **复购页**：显示"上次版本 → 本次版本"。

数据上，订单快照和制作单快照都建议补存 `seriesLifeStage` 与中文名，避免以后食谱改名/改版导致历史单说不清。

### 6.6 首页与收藏：帮顾客选，而不是让他猜

- 筛选抽屉顶部加一行："旺财 · 2 岁 · 普通成年犬　[按它筛选]"。点一下预选，顾客仍可改。
- 筛选词表收敛：同一概念只留一个说法（幼犬/成犬/老年/繁殖），不要同时出现"幼犬"和"小于14周幼犬"。
- 收藏卡片加"适合旺财"角标（需要后端批量返回适配结论，避免逐条请求）。

### 6.7 跨时间：阶段跨越提醒（这是最值得做的新能力）

狗会从幼犬长成成犬，版本必须跟着换。现在系统只在"顾客自己走到某个页面"时才可能发现。

建议在生日跨过 14 周 / 成犬阈值 / 老年阈值时，在首页或"我的"出现一条：

> 旺财已经 10 个月，幼犬版该换成成犬版了。　[看成犬版食谱]　[怎么换粮]

产品规划里已经写明：**幼犬→成犬的过渡是整个生意的枢纽**。这条提醒是把这个判断真正落到产品里的动作。

## 八、后端与接口（给开发看的）

1. **接口语义要拆开**
   现在 `/recipes/:id?dogId=&lifeStage=` 里的 `lifeStage` 同时承担"系统当前展示"和"顾客手动选择"两种含义，导致误判。
   建议：`lifeStage` 只在顾客手动点时传；另加 `selectedLifeStage` 回传"实际展示的版本"；`matchType` 增加 `NO_DOG`。
2. **详情 / 匹配结论接口**
   无 `dogId` 且无手动版本时，不返回 `FALLBACK_ADULT`，返回 `NO_DOG`（不带警示文案）。
3. **批量适配**
   `GET /recipes?dogId=` 或独立批量接口返回每道菜的适配结论，供首页/收藏打标，避免逐条请求。
4. **快照**
   订单快照与制作单快照补 `seriesLifeStage` + 中文名；历史单按 `recipeId` 回查兜底。
5. **阶段跨越**
   优先"读时计算"（首页/我的打开时判断阈值），不做定时任务，避免消息骚扰与运维成本。
6. **指标**
   现有 `life_stage_acknowledgement` 只有"确认"记录，缺"看到但放弃"。建议补一个轻量事件（展示/切换/放弃），否则无法评估这次改造的效果。

## 十、需要老板拍板的三件事

| # | 问题 | 我的建议 | 影响 |

| 1 | 提醒是否按风险分级？（幼犬/繁殖期强制确认；成犬↔老年只提示） | **分级**。幼犬吃成犬粮是安全问题，成犬吃老年版不是 | 修改 2026-09-19 "每次都确认"的口径，需你同意 |
