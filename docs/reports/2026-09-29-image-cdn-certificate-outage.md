**事故等级**：P0（生产环境全部图片无法加载，影响所有小程序用户）
**影响时间**：2026-09-29 07:59 起，至 2026-09-29 20:41 修复，约 **12.7 小时**
**影响范围**：`img.sevenkitchen.cloud` 下所有图片 —— 食谱封面、商品图、分享图、狗狗头像等

## 一、结论

不是小程序代码问题，也不是图片丢失。**是图片 CDN 域名的 HTTPS 证书过期了**，微信小程序拒绝加载证书无效域名下的任何图片。

图片文件本身完好（绕开证书校验可正常下载，返回 200）。

---

## 二、根因：一个 API 参数层级错误，静默失败一个月

### 真正的问题

服务器上 `/root/.acme.sh/deploy_to_tencent_cdn.sh` 是 acme.sh 续期后的自动部署钩子，它本身**写了完整的两步**：上传证书 + 绑定到 CDN。但第二步的参数结构错了：

| | 脚本实际发送 | 腾讯云 API 要求 |
|---|---|---|
| 证书 ID 位置 | `Https.CertId` ❌ | `Https.`**`CertInfo`**`.CertId` ✅ |

腾讯云 API 对**未知字段静默忽略**，因此：

1. 证书上传成功 → 控制台里多了一张新证书
2. 绑定 CDN 的请求**返回成功**（有 RequestId）
3. 脚本据此打印 `✓ Certificate successfully deployed to CDN!`
4. **但 CDN 上的证书一次都没换过**
5. 一个月后旧证书到期，图片全站不可用

### 为什么整整一个月没人发现（更值得警惕）

- acme.sh 在**非 debug 模式**下会丢弃 reload 钩子的全部输出（`>/dev/null 2>&1`），服务器 `acme.sh.log` 里**一条部署记录都没有**
- 脚本最后一条命令成功，整体退出码仍为 **0**
- 结论：**脚本在"假装成功"**，故障完全不可见

### 时间线证据

| 时间 | 事件 |
|---|---|
| 2026-06-30 | 旧证书签发（`YqXtfQ9m`，到期 09-29 07:59） |
| 2026-08-31 00:36 | acme.sh 自动续期，新证书上传成功（`aPqJgdOU`，到期 11-29） |
| 2026-08-31 00:36 | **绑定 CDN 步骤静默失败**，CDN 继续使用旧证书 |
| 2026-09-29 07:59 | 旧证书过期，图片全站不可用 |
| 2026-09-29 20:41 | 手动在控制台完成部署，服务恢复 |

## 五、遗留问题（已确认，**暂不处理**）

### `www.sevenkitchen.cloud` 是空壳

| 检查项 | 发现 |
|---|---|
| DNS | 解析到 1.14.3.2（同服务器） |
| 内容 | 空 —— 仅 nginx 默认欢迎页 |
| HTTPS | **无配置**（只有 80 端口 server 块，且该块唯一用途是 Certbot ACME 验证） |
| 访问量 | 全部访问日志仅 **1 条**（360 爬虫，403） |
| 代码引用 | 仅 1 处：`backend/src/utils/cors.util.ts` 的 CORS 白名单 |

**现象**：访问 `https://www.sevenkitchen.cloud` 时，nginx 回落到默认 443 服务块，使用
`api.sevenkitchen.cloud` 的证书 → 浏览器报证书域名不匹配：

```
curl: (60) SSL: no alternative certificate subject name matches target host name 'www.sevenkitchen.cloud'
```

绕过证书后返回 404，走 HTTP 返回 403。

**性质**：与本次事故**同一类病根** —— 证书签发了（Certbot 还在正常续期），却从未部署到真正需要它的地方。

**决策**：2026-09-29 与负责人确认，**保持现状不动**。后续二选一：

1. 补上 HTTPS 并 301 跳转到 `sevenkitchen.cloud`（改动最小，消除证书警告）
2. 彻底删除（nginx server 块 + Certbot 证书，需**同时**删除，否则 Certbot 续期会失败）

## 六、告警：已有，但抓不住这类故障

腾讯云 **SSL 证书到期告警早已开启**，渠道为站内信/邮件/短信/微信/企业微信，
过去 30 天已发送 **6 条**「腾讯云SSL证书即将过期通知」。

**但它没能阻止本次事故**，原因有两层：

1. 告警只说"您账户里有证书快过期了"，不会指出**哪一张是正在给生产 CDN 供证的**
2. 更致命：8-31 新证书**上传成功**，从控制台看该域名有有效证书，**告警视角里没有任何异常**——异常发生在"有没有真正装到 CDN 上"，而这不在控制台监控范围内

**结论：控制台告警天然无法覆盖"部署失败"这类故障。**

### 建议

增加一个**独立自检**（非控制台视角）：每日主动连接 CDN，读取**真实生效证书**的剩余天数，
低于阈值即告警（可走企业微信机器人，零成本）。这与修复脚本里的"回读校验"是同一思路：
**检查用户实际看到的那个证书。**

## 七、经验教训

1. **API 返回成功 ≠ 操作生效。** 关键写操作必须**回读校验**，尤其面对会静默忽略非法字段的 API
2. **自动化的输出必须可见。** 被 `>/dev/null` 吞掉的日志等于没有日志；本次故障静默了一个月纯属此因
3. **告警要盯"结果"，不要盯"过程"。** 控制台知道"证书已上传"，用户需要的是"证书已生效"
4. **证书类自动化必须端到端实测。** 只测"脚本能跑通"是不够的——旧脚本也"跑通了"
