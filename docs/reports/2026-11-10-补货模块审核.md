# 小程序「采购管理 → 补货」审核报告

> 日期：2026-11-10
> 范围：员工工作台 → 采购管理 → 补货（补货建议、创建补货单、补货清单详情、执行、完成入库、撤回、报销）及库存管理里的补货相关入口；含会影响补货数据的后台（admin-web）操作
> 方式：逐行读前端页面与后端服务/接口/表结构；跑现有测试；**未改任何代码、未连生产库、未跑 migration、未部署**
> 性质：独立审核，与 `docs/inventory-review-2026-11/` 既有材料无依附；重叠处会标注「已知」

---

## 给老板的三句话

1. **不要在小程序清单列表里删「待采购」的补货单**——如果员工已经录过采购记录，记录和金额会一起被删掉，且找不回来。
2. **补货单建好以后不能再加原料、也不能改计划数量**；漏买了一样东西，只能把整张单删掉重来——而删除又有上面的风险。
3. **补货单录采购时，弹窗里的「还需 / 共需 / 多 / 差」是按克算的**，按「袋 / 箱 / 瓶」买的补货品会显示成「还需 5g」，别照着它判断买没买够（明细卡片上的「仍需 5 袋」是对的）。

---

## 一、结论

**链路是通的**：建单 → 开始采购 → 记录采购 → 完成入库 → 报销，每一步都能走完，状态机和后端校验基本一致，入库幂等也做对了。

**但「补货」现在只是「日采清单换了个来源」**：数量口径、单位、可编辑性、列表筛选都还是日采的思路。共发现 **4 个 P0、10 个 P1、19 个 P2**；其中 3 个会直接让钱或记录出错，1 个会让现场无路可走。

建议先修 P0（约 1.5～2 天），再处理 P1（约 2～3 天），P2 排期。

### 覆盖到的

### 没覆盖到的（结论边界）

1. **没有真机/模拟器操作**：没有登录态，UI 结论来自模板与交互逻辑，不是点出来的；视觉细节（间距、颜色、动效）未逐屏核。
2. **没有查生产数据分布**：有多少原料配了阈值、有多少原料没有启用采购商品、有多少历史补货单带记录——这些会直接影响「未设阈值」比例和「无 SKU 价格口径」的影响面。相关结论已标注前提。
3. 后台（admin-web）只做了与补货数据相关的对照检查，未做完整审核。

## 三、补货现在到底怎么跑

```
员工工作台
  └─ 采购管理
       ├─ 补货（快捷入口）──────────────┐
       └─ 采购清单列表（日采 + 补货混排） │
                                        ▼
                     创建补货单（选日期 → 补货建议 → 选原料 → 填计划量/渠道/型号）
                                        │
                                        ▼
                     补货清单详情（待采购 / 未开始）
                        ├─ 开始采购（写 startedAt）
                        ├─ 记录采购（选 SKU → 买了几件 → 花了多少钱）
                        ├─ 标记无需采购 / 删除明细（仅未开始时）
                        ├─ 完成采购 ──► 写入库存流水（只认补货/混合策略）
                        └─ 撤回完成 ──► 删除这批入库流水
                                        │
                                        ▼
                     报销（工作台 → 报销管理 → 新建 → 选已完成的清单）
```

关键事实：

1. **建单只落一张清单**：计划日期 + 若干原料（按采购单位填计划量），金额按「档案价 × 计划量」估。
2. **同一天只允许一张「待处理」补货单**（全局校验，不分人）。
3. **计划量建单后不能再改，也不能再加原料**——后端有「加一项」接口，小程序没有入口。
4. **采购记录必须挂采购商品（SKU）**，带渠道和换算规格；金额是员工实付金额。
5. **完成采购时才写库存**，且只写「补货 / 混合」策略的原料；日采原料即使出现在补货单里也不入库。
6. **撤回完成 = 删掉这批入库流水**，清单回到待采购。
7. **报销只认「已完成且未报销」的清单**；补货/包材清单不能填运费和包装费。

## 四、问题清单

> P0 = 会丢钱/丢记录/算错数，必须马上修；P1 = 会买错、走不下去、前后端口径不一致；P2 = 明显体验/健壮性/性能；P3 = 代码与文案。

### P0

#### P0-1 删除「待处理」清单会把已录入的采购记录一起删掉

- **现象**：列表里任何「待采购」且未关联报销的清单都显示「删除」。员工已经跑完菜市场、逐条录了采购记录（每笔都有金额），只要还没点「确认采购完成」，删除入口就一直在。确认弹窗写的是「删除后所有关联订单将回退到已付款状态」——补货单没有关联订单，这句话既解释不了风险，也没提采购记录会没。
- **机制**：后端删除只校验「已报销不能删」「已完成不能删」，**不检查有没有采购记录**；清单一删，明细和采购记录级联删除（数据库外键 Cascade），已花的钱和报销依据一起消失，没有回收站。
- **证据**：列表删除入口 `miniapp/src/pages/staff-purchasing/index.vue:157-163`；确认文案 `同文件:936-940`；后端 `backend/src/application/purchasing/purchasing.service.ts:3600-3625`；级联 `backend/prisma/schema.prisma:2510`。
- **影响**：一次误点 = 一笔真实支出在系统里不存在；报销少报；这批货也不会入库（因为没完成）。
- **建议**（择一或组合）：
  1. 后端：存在采购记录就禁止删除，提示「请先处理采购记录，或先完成再撤回」；
  2. 前端：有记录时隐藏删除；确要删，文案写明「将同时删除 N 笔采购记录（¥X）」并二次确认；
  3. 长期：删除改「作废」软删除，可追溯。

#### P0-2 补货单记录采购时，「还需 / 共需 / 多 / 差」的数量单位算错，能差几百上千倍

- **现象**：计划买 5 袋（1 袋 = 2.5kg）的补货单，打开「记录采购」，顶部显示「还需 **5g** · 共需 **5g**」；买 1 袋后显示「多 **2495g**」。真实应该是「还需 12.5kg / 多 0」或「还差 4 袋」。
- **机制**：弹窗把「计划量 5」当成基准单位直接换算，而「袋 / 箱 / 瓶 / 盒 / 平勺」这些单位在换算函数里没有对应分支，原样返回；展示时又按基准单位拼标签（g）。采购记录本身保存的数量和金额是**对的**（按「件数 × 规格」另算），错的只是引导判断的进度数字。
- **证据**：`detail.vue:1331-1337`（取 `quantityUnit` 去换算）、`:1206-1227`（非 g/kg/ml 单位原样返回）、`:1377`（按基准单位拼标签）；补货单明细单位来自 SKU 采购单位 `purchasing.service.ts:2368`。
- **影响**：采购员据此判断「买够了没有」，补货品几乎全是按袋/箱/瓶买，所以**几乎每张补货单都会命中**；可能少买（以为多买了）或反复补买。数据本身不脏，但人会做错决定。
- **建议**：补货单的「还需/已买/共需」直接按**采购单位**展示（几袋）；若要用基准单位，必须按 SKU 换算比先折算。加一条单测覆盖「单位=袋 + 基准单位=G」。

#### P0-3 后台可以对补货单「追加订单」，把 kg 和「袋」直接相加

- **现象**：后台采购单详情页的「追加订单 / 剔除订单」按钮只按状态（待采购）置灰，补货单也能点。追加后，订单的原料需求会被合并进补货明细：数量相加、单位保留补货单的（袋），金额相加。等于「2.5kg + 2 袋 = 4.5 袋」。
- **附带影响**：追加订单还会给这些订单**创建库存占用**、把订单状态改成「采购中」、把订单挂到补货单的关联订单里——补货单变成了「订单 + 补货」混合单。
- **证据**：`backend/src/application/purchasing/purchasing.service.ts:2962-2998`（只校验 PENDING，无 kind 校验）；合并求和 `同文件:421-470`；后台按钮 `admin-web/src/views/Purchasing/PurchaseLists.vue:217-235`；库存占用与订单状态 `purchasing.service.ts:3075-3130`。
- **影响**：补货单的数量、金额、库存占用全错；后续完成入库建立在错数上；删除该单还会把订单退回「已付款」。
- **建议**：服务端对补货单直接拒绝订单类操作（追加/剔除/重算）；后台按钮按 `kind` 隐藏或置灰。

#### P0-4 补货单建好后不能加原料、不能改计划量；同日又只允许一张待处理单 → 漏买只能删单重建

- **现象**：创建页是唯一能编辑计划量和原料的地方。进入详情后，未开始只能「删除明细」，不能「加一项」，也不能改数量；一旦开始采购，连删除入口也没了。
- **死路怎么形成**：漏了一个原料 → 详情页无法加 → 想再建一张补货单 → 后端以「同一天已有待处理补货单」拒绝 → 只能把整张单删掉重建 → 而删除会丢记录（P0-1）。
- **证据**：详情页无新增/改量入口；后端其实有 `POST lists/:id/items`（`staff-purchasing.controller.ts:798`）和删除明细（`:858`），小程序 API 层也封装了 `addManualItemToList`（`api/purchasing.ts:307`），但**没有任何页面调用**；同日唯一校验 `purchasing.service.ts:2283-2297`。
- **影响**：现场补项/改量无路可走；这是本次审核里最容易被员工感知到的流程缺陷。
- **建议**：
  1. 未开始状态提供「添加原料」「修改计划数量」（复用已有接口）；
  2. 或把计划量编辑下放到每个原料卡；
  3. 同日唯一放宽为「同一创建人 + 同一天」，并支持合并到已有清单。

### P1

#### P1-1 明细卡的「仍需 X」永远不减少，容易重复采购

- 卡片固定显示「仍需 计划量」。已录 2 箱（计划 3 箱），仍显示「仍需 3 箱」，只多一个「已采购」小标签。
- 证据：`detail.vue:166-171` 用 `formatQuantity(item)`；`formatQuantity` 直接取 `item.quantityNeeded`（`:2571-2579`），采购记录不回写这个字段。
- 影响：采购员照着卡片买，会按计划量再买一遍；分次采购时最危险。
- 建议：改成「还需 = max(0, 计划 - 已记录折算量)」，买齐显示「已买齐」；或把标签从「仍需」改成「计划」。

#### P1-2 补货单明细仍显示「订单 X · 现有 Y · 抵扣 Z」，数字对补货没有意义

- 每个原料下面一行「订单 26 袋 · 现有 0 · 抵扣 0」；补货单没有订单，「订单 26」其实是计划量（空字段回退成了 `quantityNeeded`）。
- 证据：`detail.vue:176-182`；回退逻辑 `api/purchasing.ts:217-227`；补货建单只写 `quantityNeeded`（`purchasing.service.ts:2383-2402`）。
- 建议：补货单隐藏这一行，换成「计划 / 已买 / 还需」或「当前库存 / 补货点」。

#### P1-3 别人的补货单会把你挡住，但你根本看不到那张单

- 员工 B 当天建补货单，提示「日期 X 已存在待处理的补货采购单，请继续编辑该清单」；可 B 的列表只显示自己创建的，B 找不到那张单，也进不去。
- 证据：同日校验全局（`purchasing.service.ts:2283-2297`，`prisma-purchase-list.repository.ts:321-338` 不带创建人过滤）；列表对员工按创建人过滤（`staff-purchasing.controller.ts:686`）。
- 影响：多员工（或老板在后台建过单）时，B 当天无法建补货单，也无从「继续编辑」。
- 建议：冲突提示带上创建人/清单入口；或把校验限定为「同一创建人」。

#### P1-4 加进补货单的日采原料，采购完不入库存，界面却在鼓励这么做

- 创建页副标题写「日采原料也可以临时加入补货单」。员工加了、买了、完成了，这批货**不进库存**——入库只处理「补货 / 混合」，日采被静默跳过（只写日志）。
- 证据：文案 `stock-create.vue:64`；过滤 `backend/src/application/inventory/inventory.service.ts:278-324`。这也是 `docs/inventory-review-2026-11/04-独立审核意见.md` 认定的既有结构问题（「日采原料完全不进账」），**已知**。
- 影响：以为补了库存，实际账面为 0，下次补货建议继续报警；生产领料会对不上。
- 建议：短期在完成时提示「其中 N 项为日采原料，不会入库」；中期按库存改版方案让日采也入库，或禁止日采原料进补货单。

#### P1-5 撤回完成会删掉入库流水；这批货已被用掉时，库存会变负

- 完成后入库 10kg → 生产领走 5kg → 点「撤回完成」→ +10kg 的流水整行删除 → 账面 -5kg。
- 证据：撤回 `purchasing.service.ts:3971-3999` 只校验「已完成」「未关联报销」；回滚是 `deleteMany`（`inventory.service.ts:363-386`）；前端提示「已入库的采购记录会先回滚」，没有「已被消耗」的拦截或警告（`detail.vue:2372`）。
- 影响：库存变负、补货建议失真、盘点记成盘亏。
- 建议：撤回前检查这批入库是否已被后续流水消耗；有消耗则禁止撤回，或改为差额冲销（注意既有审核意见 3.1 已指出「冲红后重做会被防重逻辑跳过」的坑，改方案时要一起处理）。

#### P1-6 权限与接口边界：员工可查看/操作别人的清单；改删采购记录时清单 ID 被忽略

- **现象 A**：列表按创建人过滤，但详情、开始、记录、完成、撤回、删除等单据级接口只校验「清单存在」，不校验「是不是你的」；若干方法（加项/删项/删单）签名收了 `operatorId`，函数体里一次都没用。
- **现象 B**：`PUT /lists/:id/records/:recordId` 和 `DELETE /lists/:id/records/:recordId` 只读 `recordId`，路径里的 `:id` 完全没读——接口文档写着「这张单里的这条记录」，实际是「全库任意记录」。
- **证据**：`staff-purchasing.controller.ts:709-724、986-995、1101-1107、1181-1190、1314-1344`；`purchasing.service.ts:3771-3787、3816-3820、4005-4010、4030-4035、4130-4138`；`operatorId` 未使用 `3332-3661`。
- **影响**：正常单人操作碰不到；但员工之间、以及任何拿到 ID 的调用方可以改别人的单和金额。和「员工只看自己的」这条规则不一致。
- **建议**：服务层统一加归属校验（管理员放行）；记录接口补 `purchaseListId` 并断言记录属于该单。

#### P1-7 没有启用采购商品的原料，补货金额和库存单价按错口径算（可能放大 N 倍）

- **前提**：原料没有启用中的采购商品，但档案仍有「元 / 采购单位」的价格和 ≠1 的换算比（补剂、包材更可能）。
- **机制**：没有商品时，系统把采购单位当成基准单位、换算比写死 1，却仍用「元/采购单位」的价格 → 建议量按「粒/克」算，金额按「元/瓶」乘 → 放大换算比那么多倍；库存单位成本同样错。
- **证据**：`purchasing.service.ts:666-687`（ratio 写死 1、价仍取档案）、`:1937-1952`（建议量与单位成本）、`:2367-2372`（建单金额）；价格口径见 `backend/src/domain/ingredient/unit-price.ts:1-14`。
- **影响**：只影响**预估/展示金额**，采购记录的实付金额不受影响（记录侧用档案真实换算比）。但员工会照着一个离谱的预估去判断「这单要花几千」。
- **建议**：没有商品时不要算建议金额（显示「待补采购商品」），或统一用档案的真实换算比；先按待确认第 4 条查数据确认影响面。

#### P1-8 完成后没有常驻的「去报销 / 看报销单」入口

- 完成成功只弹一次「是否现在提交报销」；点「稍后」后，已完成详情页只有「撤回完成」，没有「去报销」，也不显示「已关联报销单」。
- 现有绕法：工作台 → 报销管理 → 新建 → 选清单，步骤多、容易漏报。

## 五、待确认（需要老板/产品拍板，不属于「代码写错」）

1. **补货单是否允许同一天多张？** 现在不允许。若要按渠道拆（线上/菜市场），需要放开并解决合并/对比。
2. **补货单是否应该可编辑？** 如果不允许改量/加项，就要明确「删单重建」是唯一流程，并把删除做安全。
3. **日采原料进补货单，到底该不该入库？** 现在的行为和界面文案是矛盾的。
4. **没有启用采购商品、但档案有价格的原料有多少？** 决定 P1-7 是「潜在」还是「已发生」。可用只读 SQL 先看：
   `select i.id,i.name,i.type,i.purchase_to_base_ratio,i.current_price_per_purchase_unit from ingredient i where i.purchase_to_base_ratio <> 1 and not exists (select 1 from procurement_sku s where s.ingredient_id=i.id and s.is_active);`
5. **安全库存/补货点/目标库存的业务单位**是基准单位还是采购单位？代码按基准单位比较，后台表单没有单位提示——有人按「袋」填 2，系统当 2 克。
6. **建议量的小数件**：按整件向上取整，还是允许散装按重量买？
7. **AI 识别订单截图是否对补货单开放？** 现在开放，且消耗识别配额。对电商囤货可能是有用的，但需要确认。
8. **删除「未完成但有记录」的清单**：禁止，还是带强提示允许？

## 六、做得好的地方（不建议动）

1. **补货建议的信息密度合适**：当前库存、补货点、目标库存、建议量、预估金额、推荐商品一次说清。

6. **删单前显式释放库存占用、撤回时把完成时间落 null**，这些细节都处理过。
7. **回归测试守住了文案和可读性**（补货/日采用词、对比度、底栏安全区），值得保留。
