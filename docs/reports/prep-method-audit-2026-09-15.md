对象：正式食谱（每条食谱的最新版本）+ 设计器草稿 的原料「制备方法」文案

## 一、审核范围与方法

| 项目 | 数量 |

方法：
1. **规则筛查**：把「营养档案状态」与文案中的称重口径/熟制步骤交叉比对，并检查结构性问题（空文案、机器码、自由文本、标点、商品属性混入）。
2. **AI 独立复核（两个独立代理）**：抽取 58 条问题样本 + 5 条"规则判为正常"的对照样本，逐条复核"判定是否正确 / 严重度 / 修法"，并专门找**误报与漏报**。复核共提出 **17 条误报、9 条漏报**，本报告已全部并入（见第四节）。

## 二、总体结论

- 有问题的原料项：**4,045 项**（正式食谱 **1,835 项 / 涉及 135 个食谱**；设计器草稿 2,210 项）
- 严重度（项次）：**高 1,975 / 中 1,099 / 低 1,049**
- 正式食谱的问题分布：私密定制 715 项 / 98 个食谱、公开食谱 325 项 / 28 个、草稿 65 项 / 11 个
- **口径规则已于 2026-09-15 由业务确认**：「设计器里选了『水煮沥干（熟）』这类档案时，厨房就是按煮完之后的重量称」→ 即 **口径跟随营养档案**（生档案→生重/干重，熟档案→熟重）。据此 A1/A2/A3 可以按规则批量改文案，**不需要逐条人工判断**。

## 四、AI 独立复核结论（含纠正我的误判）

### 1. 最关键的发现：系统本身是"双口径"设计 —— A 类不能批量改

每个原料同时挂 **RAW（生）** 和 **COOKED（熟）** 两套营养档案，而且档案备注里**明确写了称量口径**，例如黑米：

| 档案 | 备注（生产库原文摘录） |
| --- | --- |
| 黑米（生/干） | 主档案；**食谱设计器按生重称量** |
| 黑米（熟/米饭） | 同源熟制档案；**食谱设计器按熟后重量称量** |

也就是说，系统的既有约定确实是"**熟档案 ↔ 按熟重称量**"，这支持"熟档案却写生重 = 文案错"的判断方向。

**但是**：文案里写的口径 ≠ 实际称量口径。复核实测有些食谱的文案同时出现「生重」和「煮熟后称重」，说明"称生重、用生数据"在部分食谱里可能是**有意为之**。因此：
- 若按熟重称量 → 应改文案；
- 若确实按生重称量 → 该改的是档案（回到"生"）。

**这两种情况在数据里长得一模一样**，所以 A1/A2 必须先由业务确认规则，**绝不能批量替换**，否则会把本来正确的食谱改坏。A4（跨食谱混用）只是同一根因的聚合表现，建议**按"原料"而不是按"条目"**出修复清单，并补一条"**同一食谱内同一原料口径唯一性**"校验。

### 2. 复核纠正的误报（我的判定偏重）

- **B1 机器码**：原判"前台显示乱码"**不准确**——接口会把字典 ID 解析成中文（实测 148 条中 147 条可确定性还原，仅 `76b12041…` 已查不到）。真实风险是**存储形式脆弱 + 掩盖了"整条食谱没有营养档案"**，已从「高」降为「中」。
- **B3 空文案**：一律判「高」偏重。补剂/油/粉无生熟概念、按剂量称取即可，已拆出 **B3b（低，215 项）**；只有真实食材（紫薯、金针菇、鳕鱼颈背肉等）才值「高」。
- **C1 系列（油/粉/补剂写"生重"）**：**不是营养口径冲突**（油和粉不因加热改变重量，按实际重量投料与档案口径本来就一致），已全部从「中」降为「低」，并按"可安全删除的冗余词"处理；同时修掉了 C1 与 C1c 对同一句文案**重复计数**的问题。
- **A2b**：含"焯水"又已写"生重"的条目（猪肝、鸡心）不构成矛盾，判定偏严，已保留但归入"待人工确认"。

### 3. 复核发现的漏报（已修正）

| 漏报 | 影响 | 修正 |
| --- | --- | --- |
| 状态枚举大小写敏感（`raw`/`cooked` 小写被静默跳过） | 52 项（正式 22 项）漏检，如黑米"煮熟后打碎" | 已改为大小写不敏感，并新增 **D1** |
| A3 因文案含熟制词被跳过 | 花椰菜「焯水后称重」、紫甘蓝「煮熟后沥水」等漏判 | 已放宽，A3 从 26 项增至 **474 项** |
| "整条食谱无营养档案"未报 | 59 个食谱 / 912 项（多为外部工具 Animal Diet Formulator 导入） | 新增 **E1（高）** |
| 商品属性写进步骤（"无添加即食燕麦"） | 顾客会在制作说明里看到商品名 | 新增 **B6** |
| 补剂被归到「乳类及制品」、分类为空 | 影响前台分类展示 | 新增 **E2**，并在报告中记录 2,303 项补剂分类错误 |

**E1（912 项无营养档案）与 D1（52 项状态枚举）建议优先处理**，否则口径类问题无法判定。

### 根因修复（代码，与文案修复配套）

1. 制备方法字典补「熟重」「干重」；
2. 生成默认文案时**按所选营养档案状态决定「生重/熟重/干重」**，不再照抄该原料上一次的文案；
3. Web 食谱设计器补制备方法入口，并在切换营养档案时提示口径不一致。

否则：只修历史数据不改生成逻辑，下次发布会重新写回「生重」。


## 六、附带发现（超出"制备方法"范围，但同源）

1. **59 个正式食谱（912 项原料）没有营养档案**，设计来源绝大多数是外部工具 **Animal Diet Formulator**（1 个是 Setar）——不是从咱们的设计器发布的，所以上一轮"发布丢档案"的修复没有覆盖到它们。
2. **营养档案状态标注不统一**：`raw`/`cooked` 小写、状态 `RAW` 却标注"干/原样/生重"、`AIR_DRIED` 与 `DRIED` 都叫"干"。
3. **补剂分类错误**：2,303 项补剂被归为「乳类及制品」，另 156 项分类为空。

## 七、防复发（根因）

1. 制备方法字典**补上「熟重」（和「干重」）**——现在只有「生重」，所以默认值永远写生重；
2. 生成默认文案时**按所选营养档案状态决定「生重/熟重」**，不再照抄该原料上一次的文案；
3. Web 食谱设计器**补上制备方法的选择入口**（现在完全没有），并在切换营养档案时提示口径不一致；
4. 长期建议把制备方法从自由文本改为**受控词表词组**（结构化），从根上消除口径矛盾；
5. 增加校验：同一食谱内口径唯一性、状态枚举规范化、分类与原料类型一致性。
