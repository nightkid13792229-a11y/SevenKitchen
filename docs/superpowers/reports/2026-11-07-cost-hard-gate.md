# 食材成本「硬门禁」改造记录（2026-11-07 晚）

在「成本口径归位」上线之后，老板提出把兜底机制从根上去掉：
成本的写入者只能有两个，其余一律不许。

## 一、目标模型（老板拍板）

1. **建档即定价**：新增食材原料时，必须同时新增一条采购商品，
   填「这一件多少钱」和「一件多少克」。这条商品的价格换算成每克成本，作为初始值。
2. **报销覆盖**：之后唯一的改价渠道是采购报销——实付金额 ÷ 实际克数，覆盖每克成本。
3. 除此之外，**没有第三个写入者，也没有兜底/回退**。

## 二、这次改了什么

### 1. 建档与采购商品合成一次提交
- 后端：授权写入的入参增加「采购商品」；原料、营养档案、采购商品、初始成本
  在**同一个事务**里落库，要么全成、要么一条都没有。
- 前端：AI 建档的「采购商品」卡片从“写入之后”挪到“写入之前”，
  随授权按钮一起提交；删掉「保存采购商品」「稍后补」两个按钮。
- 结果：库里不会再出现「有原料、没价」的中间态。

### 2. 砍掉第三个写入者
- 库存页的「改成本」入口整个删除。
- 后端接口对**食材**直接拒绝手工改价（补剂/包材不受影响，它们没有采购商品层）。

### 3. 换算变成数据库约束
- `procurement_sku.purchase_to_base_ratio` 改为 NOT NULL + CHECK > 0。
- 迁移先体检再改表：有不满足的数据就整条回滚并报出条数。
- 生产库实测 303 条采购商品、0 条不满足，可直接上。

## 三、验证

- 后端全量：**6007 通过、8 失败**（8 条是补剂商城既有红，主工作区同样红）
- 后台：1137 条测试全绿，`npm run build` 通过，`vue-tsc` 无本次文件报错
- 新增测试：建档必带采购商品（3 条）、换算约束迁移（2 条）、食材禁止手工改价（1 条）

## 四、行为变化（需要通知运营）

- **以后不能“先建档、后补价”**：没填商品和价，这条食材就建不出来。
- 草稿里原来的「当前采购价」不再决定成本，成本一律由随提交的采购商品折算。
- 库存页不再能直接改成本；要调价只能走采购报销。

## 五、上线时的迁移

`20261107220000_sku_ratio_required`：先体检，再给采购商品加「换算不能为空且大于 0」的约束。
生产数据已满足，不需要修数据。
