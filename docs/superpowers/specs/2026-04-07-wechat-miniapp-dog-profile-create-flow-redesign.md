# 微信小程序端狗狗档案创建流程重构设计

## 背景

当前已有狗狗的“爱犬概览页”与局部编辑交互已经完成一轮重构：

- 页面采用卡片化分区
- 同页分区编辑替代了旧的二级页主编辑链路
- 基础信息、喂养参数、健康记录、热量建议已经形成较统一的表达方式

但首次建档入口 [miniapp/src/pages/dog-create/index.vue](/Users/zhaochen/Documents/SevenKitchen/.worktrees/codex-dog-profile-flow/miniapp/src/pages/dog-create/index.vue) 仍然保留旧的 UI 和交互语言，主要问题包括：

- 四步流已经存在，但每一步仍然更像旧式表单分页，而不像“逐步搭建档案”
- 信息组织与爱犬概览页不一致，用户在“建档”和“后续查看/编辑档案”之间会感受到明显割裂
- 第 1 步、第 2 步的字段边界不够符合用户心智，基础档案信息与热量计算参数混在一起
- 第 3 步“喂食建议”仍然带有偏工具页的感觉，而不是一个结果确认页
- 第 4 步健康记录虽然是增强信息，但在表达上仍然容易让用户误以为必须一次性填满

现阶段我们不需要推翻已经跑通的四步创建流，也不需要重新定义狗狗档案的领域模型。真正需要重构的是“创建体验”本身：保留四步的整体漏斗，把每一步的视觉语言、信息密度和交互方式，统一到爱犬概览页已经验证过的方向。

## 目标

1. 保留现有四步创建流，不推翻已验证的流程骨架
2. 让首次建档页与爱犬概览页共享同一套视觉语言与交互心智
3. 把创建页从“旧表单分页”重构为“逐步搭建档案”的体验
4. 降低首次建档的理解成本与操作成本，提升完成率
5. 明确每一步的职责边界，避免基础信息、热量参数、结果确认、健康补充相互混杂
6. 保持后续档案查看与编辑的一致性，减少用户在建档成功后的认知切换

## 非目标

- 本次不改变“创建页仍为四步流”这一主流程结构
- 本次不把首次建档改造成与概览页完全同页同形态的单页编辑器
- 本次不要求在创建阶段开放完整的狗狗头像上传能力
- 本次不重新设计后端核心档案接口或计算规则
- 本次不在创建阶段开放体重历史管理工具

## 设计原则

1. 创建页像“逐步建立档案”，不像“切片的大表单”
2. 每一步只解决一种核心任务，不让用户在同一页里做多种判断
3. 能复用爱犬概览页成熟交互的地方，尽量复用而不是重新发明
4. 热量建议页是“结果确认页”，不是“参数计算工具页”
5. 健康记录是增强项，不阻塞完成建档
6. 创建时只录当前值，不提前引入历史管理工具

## 与现有方案的关系

本设计是对 [2026-04-03-wechat-miniapp-dog-profile-edit-interaction-design.md](/Users/zhaochen/Documents/SevenKitchen/.worktrees/codex-dog-profile-flow/docs/superpowers/specs/2026-04-03-wechat-miniapp-dog-profile-edit-interaction-design.md) 中“首次建档四步流”的进一步细化与重构。

保持不变的部分：

- 仍然是四步流
- 第 3 步仍然承担热量建议确认
- 第 4 步仍然是可跳过的健康信息补充
- 健康记录仍然使用逐条记录保存的思路

本次新增或调整的重点：

- 第 1 步与第 2 步的字段边界重新划分
- 创建页整体视觉和交互语言对齐爱犬概览页
- 第 3 步改造成更明确的“结果确认页”
- 第 4 步进一步弱化阻塞感

## 总体方案

保留四步创建流，但把每一步重构成“卡片化模块 + 清晰动作 + 统一解释方式”的体验。

四步分别为：

1. 基础信息
2. 喂养参数
3. 热量建议
4. 健康记录

整体上，创建页应与爱犬概览页形成如下关系：

- 爱犬概览页负责“查看当前档案状态并局部编辑”
- 创建页负责“从零开始搭建档案”
- 两者共享相同的基础组件和表达方式：
  - 性别选择胶囊
  - 品种搜索与手动填写逻辑
  - BCS 评分选择与评分图
  - 活动水平说明卡
  - 零食等级选择
  - 三张能量卡
  - 健康记录逐条新增与附件上传能力

## Step 1：基础信息

### 页面目标

让用户快速建立一张基础档案卡，并录入首次热量估算必须依赖的基础事实。

### 包含字段

- 狗狗名字
- 性别
- 生日
- 当前体重
- 品种
- 体型（自动匹配 / 手动兜底）
- 是否绝育

### 布局

第一张卡：狗狗身份

- 左侧为头像占位区
- 右侧为名字输入与性别选择
- 性别文案使用 `弟弟 / 妹妹`

第二张卡：基础事实

- 生日
- 当前体重（kg）

第三张卡：品种

- 搜索框带搜索图标
- 搜索结果卡直接展示“品种名 + 体型”
- 标准品种被选中后，显示“已自动匹配体型：X型犬”
- 提供弱化兜底入口：`手动调整`
- 无搜索结果时，才出现 `去手动填写`
- 进入手动填写模式后，隐藏搜索框，只保留名称输入和体型选择

第四张卡：是否绝育

- 使用与概览页一致的二选一交互

### 关键交互

1. 创建阶段不出现 `体重管理` 入口  
   首次建档只录当前体重，不进入历史体重工具。

2. 建档成功后，系统自动生成首条历史体重记录  
   该记录为 `建档初始体重`，而不是要求用户在创建时手动进入体重管理记录。

3. 标准品种默认自动匹配体型  
   不默认暴露体型手动调整；只有通过弱化入口才可覆盖。

### 设计理由

- 对用户而言，体重和绝育更像基础档案事实，而不是喂养参数
- 把体重提前到第 1 步，有助于让第 2 步只聚焦真正的热量估算参数
- 建档阶段不开放体重管理，可避免把“录当前体重”和“管理历史体重”混淆

## Step 2：喂养参数

### 页面目标

只保留真正影响热量估算的喂养参数，让用户清楚自己正在决定“怎么计算”，而不是继续填写基础档案。

### 包含字段

- BCS 体态评分
- 活动水平
- 每日餐数
- 零食评估

### 不再包含

- 体重
- 品种
- 是否绝育

这些信息已在第 1 步完成。

### 布局

第一张卡：BCS 体态评分

- 直接单选评分，不再使用底部 picker
- 选项显示 `分数 + 状态`
- BCS 评分图默认展示
- 提供 `热量影响` 弱入口

第二张卡：活动水平

- 用描述卡片表达，不只显示抽象等级名
- 提供 `热量影响` 弱入口

第三张卡：每日餐数

- 保留简单选择器
- 不提供“热量影响”说明入口

第四张卡：零食评估

- 直接使用 4 档等级选择
- 不再要求选择零食输入方式
- 不再向大多数用户暴露“精确零食热量”输入
- 提供 `热量影响` 弱入口

### 关键交互

1. BCS 图默认展示  
   用户可以边看图边选分数，不再跳新页面。

2. `热量影响` 说明详细展开  
   不是泛泛解释，而是明确说明该项如何进入热量估算：
   - `BCS` 通过体况系数调整总能量需求
   - `活动水平` 通过活动系数影响总能量需求
   - `零食评估` 从总热量中预留部分热量，减少主食热量

3. 零食等级统一回归“等级心智”  
   即使历史上存在精确零食热量输入，也不再把创建阶段暴露为主交互。

### 设计理由

- 第 2 步应该只承担“喂养参数输入”这一件事
- 用户更容易理解“这些参数在影响热量”，而不是继续填基础档案
- 简化零食输入可明显降低理解成本

## Step 3：热量建议

### 页面目标

把这一页定义为“结果确认页”，而不是“继续操作的工具页”。

### 布局

第一张卡：狗狗摘要

- 姓名
- 年龄 / 月龄
- 生命阶段
- 当前体重

不再重复展示活动水平。

第二张卡：三张能量卡

- 总能量需求
- 零食能量
- 每日主食热量

其中 `每日主食热量` 作为主结果卡，做更强的视觉强化。

第三张卡：喂食建议说明

- 明确这是首次喂养参考值
- 提示用户结合体重和体态变化动态调整
- 给出更可执行的一句提醒：
  - 体重升高可适当下调
  - 体重下降可适当上调

### 页面动作

- `返回上一步`
- `保存档案`
- `继续填写健康记录`

### 不再出现

- `更新推荐结果`
- `返回喂食信息`
- `每日饭量`

### 关键交互

1. 前面参数变化后自动重算  
   第 3 步不再承担“手动触发更新”的职责。

2. 结果卡的心智与爱犬概览页保持一致  
   避免用户建档成功后又看到另一套能量结果表达。

### 设计理由

- 这一页最重要的工作是让用户确认“我该先按多少主食热量喂”
- 手动更新和重复信息会冲淡这个目标

## Step 4：健康记录

### 页面目标

让用户在不被阻塞的前提下，补充健康信息；并明确告诉用户这一步可以跳过。

### 页面表达

顶部说明卡：

- `健康记录可稍后再补充，不影响先完成建档`

### 页面结构

病史 / 体检 / 过敏三块：

- 默认展示摘要
- 新增记录时，该条自动展开
- 其他记录保持折叠
- 每条记录逐条保存
- 支持上传图片或 PDF 作为附件

挑食 / 不爱吃的食物：

- 独立成“饮食提醒”输入区
- 只有改动时才显示：
  - `撤销修改`
  - `保存挑食提醒`

### 页面动作

- `返回上一步`
- `跳过并创建`
- `完成建档`

### 不再出现

- `统一保存健康信息`
- 旧的 `过敏食物` 输入

### 设计理由

- 健康记录是增强信息，不应像整页大表单那样要求一次性填满
- 逐条保存和折叠结构更适合真实使用习惯
- `过敏食物` 与逐条过敏记录存在语义重叠，应从 UI 中正式移除

## 跨步骤统一交互

### 1. 步骤顶部

继续保留四步进度条，但视觉语言对齐爱犬概览页：

- 更卡片化的承载
- 更清晰的当前步骤高亮
- 更轻的辅助说明

### 2. 底部动作

每一步的按钮文案都应体现当前任务，而不是长期复用单一的“保存/下一步”：

- Step 1：`返回 / 下一步`
- Step 2：`返回上一步 / 生成喂食建议`
- Step 3：`返回上一步 / 保存档案 / 继续填写健康记录`
- Step 4：`返回上一步 / 跳过并创建 / 完成建档`

### 3. 页面滚动

步骤切换时自动回到页面顶部，避免延续上一页的滚动位置。

### 4. 创建页与概览页的边界

- 创建页负责从零搭建档案
- 概览页负责查看与后续局部编辑
- 两者共享组件，不共享页面职责

## 组件与复用策略

本次重构优先复用现有概览页成熟组件与工具，而不是在创建页再维护一套新逻辑。

优先复用的能力：

- 基础信息区的性别、品种、体型逻辑
- 喂养参数区的 BCS / 活动 / 零食交互
- 热量建议区的三张能量卡与说明文案结构
- 健康记录区的逐条保存、折叠、附件上传结构

创建页只应保留必要的“步骤流”壳层和创建态特有逻辑：

- 本地草稿
- 创建成功后的首条体重历史写入
- 跳过健康信息后的最终创建动作

## 错误处理与完成率保护

1. 第 1 步和第 2 步仍保留创建态草稿恢复能力  
   本次不移除现有草稿机制。

2. 第 3 步试算失败时，不阻塞创建档案  
   允许用户先保存档案，再稍后重新查看建议。

3. 第 4 步附件上传失败不应阻塞当前记录保存  
   用户仍可先保存文字记录。

4. 跳过健康步骤时，明确告诉用户后续仍可从概览页补充  
   避免用户误以为“现在不填以后就没地方填了”。

## 测试与验证重点

### 设计验收

1. 创建页 4 步视觉和交互语言与爱犬概览页一致
2. 第 1 步不再出现体重管理入口
3. 第 2 步不再出现体重和零食输入方式
4. 第 3 步不再出现手动更新推荐按钮
5. 第 4 步明确可跳过，且健康记录采用逐条保存结构

### 功能验收

1. 首次建档成功后，自动生成首条历史体重记录
2. 标准品种自动匹配体型，手动填写品种可自行选择体型
3. 前序步骤改动能正确驱动第 3 步热量结果更新
4. 健康记录附件上传与逐条保存可正常工作
5. 跳过健康步骤后仍可顺利完成建档

## 结论

本次重构不改变“创建页仍是四步流”这一主骨架，而是把每一步从旧式表单分页，升级成与爱犬概览页统一的卡片化建档体验。

核心收益在于：

- 用户对“基础档案 / 喂养参数 / 热量建议 / 健康补充”的边界更清楚
- 建档页与建档后的档案页不再像两套产品
- 创建成功后的认知迁移成本降低
- 完成率优化方向更稳定，不需要重新冒险推翻整个建档漏斗
