# 食材多层 / 补剂与包材单层 / 食谱补剂替代选项设计

## 背景

当前原料域在 2026-04-11 到 2026-04-14 已完成第一轮 `标准原料 / DIY 推荐 SKU / 采购 SKU` 解耦，并已经部署到生产。

现状里：

- `食材` 已经基本符合预期：
  - 食谱绑定标准原料
  - 小程序端通过 `recommended_product` 展示家庭 DIY 推荐商品
  - 采购、库存、生产执行通过 `procurement_sku` 落到具体采购商品
- `补剂` 和 `包材` 仍然沿用了与食材相同的多层模型
- `补剂` 的实际计算链路仍然严重依赖旧字段 `ingredient.properties.active_nutrients`
- `nutrition_profile` 与 `recommended_product.active_nutrients` 并没有真正成为补剂计算的唯一数据来源

这带来了三个根本问题：

1. `补剂` 的不同 SKU 往往代表不同产品、不同规格、不同有效成分浓度，并不只是“同一种东西的不同购买渠道”，因此并不适合继续套用食材的多层模型。
2. `包材` 没有营养意义，也没有用户侧推荐商品语义，同样不适合继续拆成 `DIY 推荐 SKU / 采购 SKU` 两层。
3. 由于旧字段仍在暗中生效，管理后台看到“空”的营养数据，并不代表系统真的没有浓度；后台认知与实际业务计算已经分裂。

用户已经明确新的业务方向：

- `食材` 继续保留多层模型
- `补剂` 改成单层模型，一条标准原料就是一个具体补剂产品
- `包材` 改成单层模型，一条标准原料就是一个具体包材产品
- `补剂` 相关计算统一改由 `nutrition_profile` 推导，不再长期依赖历史 `active_nutrients`
- 由于补剂改单层后不再依赖 SKU 承接“多产品推荐”，需要新增 `食谱补剂替代选项`
- `食谱替代选项` 本次只支持 `补剂`，不支持 `食材`

## 目标

1. 保持 `食材` 现有多层模型不变：
   - `标准原料 -> DIY 推荐 SKU -> 采购 SKU`
2. 将 `补剂` 改为单层模型：
   - 一条标准原料 = 一个具体补剂产品
3. 将 `包材` 改为单层模型：
   - 一条标准原料 = 一个具体包材产品
4. 将 `nutrition_profile` 确立为补剂营养与浓度的唯一真源
5. 将 `ingredient.properties.active_nutrients` 降级为兼容缓存，不再手工维护
6. 新增 `食谱补剂替代选项`，承接“同一补剂位可给用户推荐多个具体补剂产品”的需求
7. 为后续生产数据治理提供清晰迁移路径，避免继续在补剂和包材上新增或扩张 SKU 层

## 非目标

- 不在本次重构里改变食材的三层模型
- 不在本次重构里支持食材替代选项
- 不在本次重构里一次性删除所有历史 `active_nutrients` 字段
- 不在本次重构里同时重做全部营养素单位标准体系
- 不在本次重构里展开订单页用户交互改造

## 现状分析

### 1. 食材链路已经基本符合业务模型

当前 `食材` 已经具备：

- 标准原料承接逻辑食材与营养数据
- `recommended_product` 面向小程序端 DIY 推荐
- `procurement_sku` 面向采购、库存和生产执行

这条链路已经在线上运行，且与业务认知基本一致，因此本次不再推倒重来。

### 2. 补剂链路存在三套并存来源

当前线上补剂实际存在三套来源：

- `ingredient.nutrition_profile`
- `recommended_product.active_nutrients`
- `ingredient.properties.active_nutrients`

但当前真正参与补剂计算的主要仍是：

- `ingredient.properties.active_nutrients`

具体依赖链路包括：

- 管理后台食谱编辑页补剂营养目标下拉与单位显示
- 后端 `PricingService` 补剂理论用量与成本计算
- 小程序 DIY 制作单补剂用量展示
- 小程序配方详情页补剂单位展示
- 小程序生产打印/生产详情中的补剂显示

因此当前最大的问题不是“历史字段还存在”，而是：

`历史字段仍在默默生效，而新的营养数据录入入口并没有明确接管这些计算链路。`

### 3. 补剂 SKU 与包材 SKU 的业务语义并不成立

#### 补剂

对补剂来说，不同 SKU 往往代表：

- 不同浓度
- 不同品牌
- 不同剂型
- 不同展示单位（粒、片、平勺、毫升）
- 甚至不同产品本体

这意味着它们更适合作为不同的“补剂产品”，而不是“同一逻辑补剂下的若干 SKU”。

#### 包材

对包材来说，业务关注的是：

- 规格
- 供应商/渠道
- 采购价
- 库存策略
- 是否消耗品

它不需要 DIY 推荐层，也没有营养层，因此继续沿用 SKU 拆分只会增加维护成本。

### 4. 补剂改单层后，必须补上食谱替代选项

当前如果想在同一食谱中给用户推荐多个补剂产品，是通过：

- 同一标准原料下挂多个 `recommended_product`

一旦补剂改单层，这种方式不再成立。此时要表达：

- “这个食谱补碘位默认用海藻粉，但也可以让用户选海带粉胶囊或海带粉片”

必须引入正式的 `食谱补剂替代选项`。

## 总体方案

本次采用“两种模型并存”的方案：

- `食材` 保持多层模型不动
- `补剂` 与 `包材` 改为单层模型
- `食谱补剂替代选项` 只为补剂提供多产品候选能力

最终对象模型如下：

### 食材

```text
标准原料（逻辑食材）
  ├─ 营养数据
  ├─ 家庭 DIY 推荐 SKU（小程序推荐）
  └─ 采购 SKU（采购 / 库存 / 生产执行）
```

### 补剂

```text
标准原料（具体补剂产品）
  ├─ 营养数据（唯一真源）
  ├─ 产品与展示信息
  ├─ 采购与价格信息
  ├─ DIY 启用开关
  └─ 采购/生产启用开关
```

### 包材

```text
标准原料（具体包材产品）
  ├─ 产品与规格信息
  ├─ 采购与库存信息
  └─ 采购/生产启用开关
```

### 食谱补剂替代选项

```text
食谱补剂位（默认补剂原料）
  └─ 0..N 个候选补剂原料
```

## 目标数据模型

## 一、食材保持多层模型

`FOOD` 类型保持现状：

- 保留 `recommended_product`
- 保留 `procurement_sku`
- 保留管理后台“家庭 DIY 推荐商品”和“生产采购 SKU”两个区块
- 保持采购、库存、生产、小程序 DIY 制作单现有食材逻辑

本次只做兼容性调整：

- 让列表、状态、过滤与迁移逻辑明确区分 `FOOD` 与非 `FOOD`
- 防止新的单层逻辑误伤食材链路

## 二、补剂改单层模型

### 1. 标准原料语义

对 `SUPPLEMENT` 类型：

- 一条标准原料就是一个具体补剂产品
- 不再衍生 `recommended_product`
- 不再衍生 `procurement_sku`

例如未来应建模为三条不同标准原料：

- `海带粉胶囊 325μg/粒`
- `海藻粉 450μg/平勺`
- `海带粉片 150μg/片`

而不再是“同一个海藻粉标准原料下的三个 SKU”。

### 2. 标准原料承担的信息

补剂标准原料需要直接承担：

- 名称
- 类型
- 标签
- 营养分类
- 添加时机
- 生产损耗率
- 基准单位 / 标准单位展示名 / 单个重量
- 品牌
- 规格
- 展示单位
- 购买链接
- 图片
- 采购渠道 / 供应商
- 采购单位 / 换算 / 当前价 / 参考价
- 启用 DIY 推荐
- 启用采购 / 生产
- 营养数据

其中：

- `nutrition_profile` 是补剂营养与浓度的唯一真源
- `properties.active_nutrients` 不再人工编辑，只允许系统派生

### 3. 开关规则

补剂新增两个明确的产品级开关：

- `diyEnabled`
- `procurementEnabled`

语义如下：

- `diyEnabled = true`
  - 该补剂产品可出现在 DIY 制作单推荐/替代候选中
- `procurementEnabled = true`
  - 该补剂产品可进入采购、库存、生产执行链路

二者可以独立：

- 只用于 DIY 推荐的补剂产品
- 只用于生产采购的补剂产品
- 两者都启用的补剂产品

### 4. 计算真源

补剂相关计算一律以：

- `nutrition_profile`

推导出的标准化营养浓度为准。

需要被统一改造的链路包括：

- 食谱编辑页补剂营养目标候选
- 食谱详情页单位显示
- 后端定价 / 补剂理论用量计算
- 小程序 DIY 制作单补剂用量计算
- 小程序生产详情 / 打印 / 标签渲染中的补剂显示

### 5. 历史兼容

在过渡阶段：

- 系统仍允许保留 `properties.active_nutrients`
- 但它只能由 `nutrition_profile` 派生
- 不再作为独立录入源

这样可以保证旧链路暂时继续可读，同时逐步把所有下游消费迁到新的派生服务/标准化 helper。

## 三、包材改单层模型

### 1. 标准原料语义

对 `PACKAGING` 类型：

- 一条标准原料就是一个具体包材产品
- 不再衍生 `recommended_product`
- 不再衍生 `procurement_sku`

例如：

- `4号泡沫箱`
- `4号真空袋`
- `铝箔保温袋 32cm`

都应各自是单独标准原料。

### 2. 标准原料承担的信息

包材标准原料直接承担：

- 名称
- 类型
- 标签
- 基准单位 / 单个重量 / 最大容量
- 是否消耗品
- 关联配件
- 品牌
- 规格
- 渠道 / 供应商
- 采购单位 / 换算 / 当前价 / 参考价
- 安全库存 / 补货点 / 目标库存
- 启用采购 / 生产

包材没有：

- 营养数据
- DIY 推荐开关
- 食谱替代选项

### 3. 与食材的区别

包材虽也进入采购和库存链路，但它不是“逻辑对象 + 多个 SKU”的关系，而是“一个产品就是一个包材原料”。因此应与补剂一样使用单层产品模型。

## 四、食谱补剂替代选项

## 1. 设计目标

补剂改单层后，食谱需要一种正式能力来表达：

- 当前食谱默认使用哪一个补剂产品
- 同一补剂位还允许用户改选哪些候选补剂产品

本次只支持 `SUPPLEMENT` 类型，不支持 `FOOD` 或 `PACKAGING`。

## 2. 建模方式

采用“默认补剂 RecipeItem + 若干候选替代项”的方式：

- 保留现有 `RecipeItem` 作为默认补剂位
- 新增 `RecipeSupplementAlternative`

建议字段：

- `id`
- `recipeItemId`
- `alternativeIngredientId`
- `sortOrder`
- `isActive`
- `createdAt`
- `updatedAt`

约束：

- 仅允许 `recipeItem` 对应的原料类型为 `SUPPLEMENT`
- `alternativeIngredient` 也必须为 `SUPPLEMENT`
- 同一 `recipeItem` 下不能重复挂同一候选补剂

### 3. 行为规则

- `RecipeItem` 本身代表默认补剂产品
- 替代项只记录“候选补剂原料”，不再引入 SKU
- DIY 制作单默认使用 `RecipeItem.ingredientId`
- 用户切换候选补剂后：
  - 使用被选补剂原料的营养数据重新计算添加总量
  - 展示该补剂原料自己的品牌、规格、购买信息、展示单位

### 4. 后台编辑规则

食谱编辑页中的补剂项需要新增一个“替代补剂”配置区：

- 默认补剂原料
- 候选补剂原料列表
- 排序
- 启停

后台在添加候选项时，只能筛出：

- `SUPPLEMENT`
- `diyEnabled = true`
- 且未被当前补剂位重复挂载的原料

### 5. 小程序展示规则

DIY 制作单中：

- 不再针对补剂读取 `recommended_product`
- 而是读取“当前补剂位的默认补剂 + 候选补剂原料列表”
- 用户切换时，切换的是“补剂原料”，不是“补剂 SKU”

这样可以自然承接：

- 不同产品
- 不同剂型
- 不同有效成分浓度
- 不同展示单位

## 五、计算与派生规则

### 1. `nutrition_profile` 是唯一真源

补剂相关的营养与浓度一律从 `nutrition_profile` 推导。

统一规则：

- 食谱的补剂营养目标候选来自 `nutrition_profile` 可解析出的字段
- 补剂默认单位来自 `nutrition_profile` 的标准化单位
- DIY 制作单和定价服务使用同一套浓度解析 helper

### 2. `active_nutrients` 降级为兼容缓存

在过渡期：

- 允许系统从 `nutrition_profile` 派生：
  - `properties.active_nutrients`
- 旧页面和旧接口如果暂时仍依赖它，可以继续读

但原则是：

- 不再手工维护
- 不再独立录入
- 不再作为产品模型设计的主入口

### 3. 食材继续维持现有模式

对 `FOOD`：

- `nutrition_profile` 仍然维护食材营养数据
- DIY 制作单食材部分仍按当前食材逻辑运作
- 不把补剂和包材的单层逻辑错误扩散到食材

## 六、管理后台交互调整

## 1. 原料列表

列表层明确按类型分治：

- `FOOD`
  - 显示 `营养数据`
  - 显示 DIY / 采购 SKU 计数
- `SUPPLEMENT`
  - 显示 `营养数据`
  - 不再显示 DIY / 采购 SKU 计数
  - 改为显示：
    - DIY 启用状态
    - 采购启用状态
- `PACKAGING`
  - 不显示 `营养数据`
  - 不显示 DIY SKU 计数
  - 改为显示采购启用状态

## 2. 原料编辑弹窗

### FOOD

保持现状：

- 标准原料基础信息
- 类型特定属性
- 家庭 DIY 推荐商品
- 生产采购 SKU

### SUPPLEMENT

改成单层产品编辑：

- 标准原料基础信息
- 标准口径
- 补剂属性
- 产品信息
- DIY / 采购启用开关
- 不再显示家庭 DIY 推荐商品区块
- 不再显示采购 SKU 区块

### PACKAGING

改成单层产品编辑：

- 标准原料基础信息
- 标准口径
- 包材属性
- 产品信息
- 采购启用开关
- 不再显示营养数据入口
- 不再显示家庭 DIY 推荐商品区块
- 不再显示采购 SKU 区块

## 3. 营养数据弹窗

营养数据弹窗的适用类型改为：

- `FOOD`
- `SUPPLEMENT`

对 `PACKAGING`：

- 继续不提供入口

对 `SUPPLEMENT`：

- 保存时继续派生兼容缓存
- 但界面说明文案要明确：
  - 营养数据将直接影响补剂默认浓度与替代补剂计算

## 七、数据迁移策略

本次重构不能直接“一把切”，需要分阶段进行。

### 阶段 A：冻结扩张

- 暂停继续为 `SUPPLEMENT` 与 `PACKAGING` 新增 `recommended_product`
- 暂停继续为 `SUPPLEMENT` 与 `PACKAGING` 新增 `procurement_sku`
- 数据治理与运营录入全部改按新单层思路进行

### 阶段 B：补剂与包材数据审计

对现有 `SUPPLEMENT` 与 `PACKAGING` 做盘点：

- 哪些只有 1 个推荐商品 / 1 个采购 SKU，可直接扁平迁移
- 哪些存在多个不同产品，需要拆成多条标准原料
- 哪些食谱需要建立补剂替代候选关系

### 阶段 C：模型落地与兼容迁移

- 先落表结构与后台编辑页
- 先让补剂与包材可以按单层方式新建和编辑
- 同时保留旧字段兼容读取

### 阶段 D：历史数据迁移

#### 补剂

迁移原则：

- 如果旧标准原料下只有一个有效产品，则扁平到该标准原料本体
- 如果旧标准原料下有多个本质不同的产品，则拆为多条补剂标准原料
- 原食谱默认补剂位保留默认项
- 其他产品转成该补剂位的替代候选

#### 包材

迁移原则：

- 一条旧包材原料下如有多个本质不同的采购 SKU，应拆成多个包材标准原料
- 包材不建立替代选项

### 阶段 E：切断旧主依赖

等补剂相关消费链路都完成后：

- `RecipeForm`
- `PricingService`
- DIY 制作单
- 生产页/打印页
- 配方详情页

统一切到新 helper / 新模型，再逐步清退对 `properties.active_nutrients` 的直接读取。

## 八、兼容与风险控制

### 1. 最大风险

最大风险不是 schema 变化，而是：

- 某些链路仍在读旧 `active_nutrients`
- 某些链路已开始写 `nutrition_profile`
- 两边如果不统一，会出现“后台看到 A，实际计算用 B”

### 2. 风险控制原则

- 永远只保留一个真源：`nutrition_profile`
- 兼容缓存只能由真源派生
- 补剂和包材的新单层模型先支持新增，再迁历史
- 食谱替代选项先补后端模型和后台编辑，再补小程序交互

### 3. 线上过渡期保护

在过渡期，管理后台必须能明确区分：

- 当前字段是“产品级正式字段”
- 当前字段是“历史兼容字段”

避免运营继续把数据录到即将退场的入口里。

## 九、测试与验收标准

### 1. 食材回归

- 食材原料编辑不受影响
- DIY 推荐 SKU / 采购 SKU 链路不受影响
- 小程序食材推荐与采购库存链路继续正常

### 2. 补剂单层验收

- 新建一个补剂产品无需再新增 DIY SKU / 采购 SKU
- `nutrition_profile` 保存后可直接参与食谱补剂计算
- 关闭 `diyEnabled` 后，该补剂不会出现在 DIY 替代候选里
- 关闭 `procurementEnabled` 后，该补剂不会出现在采购/生产执行里

### 3. 包材单层验收

- 新建一个包材产品无需采购 SKU
- 可直接参与采购、库存、生产执行
- 不显示营养数据入口

### 4. 食谱补剂替代验收

- 一个补剂位可以挂多个候选补剂原料
- DIY 制作单可切换候选补剂
- 切换后添加总量会按所选补剂营养数据重算
- 切换后展示的品牌、规格、链接、单位与所选补剂一致

## 十、推荐实施顺序

1. 先冻结补剂与包材继续扩张 SKU
2. 先完成补剂 / 包材单层模型与后台编辑页
3. 再完成食谱补剂替代选项模型与后台配置
4. 再切 DIY 制作单、定价、食谱详情、生产打印等消费链路
5. 最后再做补剂 / 包材历史数据迁移与旧字段清理
