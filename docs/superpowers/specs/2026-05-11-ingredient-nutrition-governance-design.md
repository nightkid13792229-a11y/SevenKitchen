# 原料营养治理设计

## 背景

SevenKitchen 希望逐步建设类似 ADF（Animal Diet Formulator）和 PDD（Pet Diet Designer）的犬配方设计能力。完整配方设计器、Agent 自动设计、小程序食谱同步都依赖一个前提：后台现有食材和补剂必须拥有可信、可追溯、可计算的营养档案。

当前项目已经具备一些基础：

- Web 管理端、微信小程序、NestJS 后端和 PostgreSQL 数据库
- 现有后台原料库 `Ingredient`
- 原料营养档案字段 `Ingredient.nutritionProfile`
- 独立营养原料库 `NutritionFood`
- 营养原料与后台原料映射 `NutritionFoodMapping`
- USDA 搜索/导入接口雏形
- FEDIAF 营养标准 seed
- 标准原料统一营养数据模板

本阶段从“原料库优先”开始，不先做完整配方设计器。目标是先把后台已有食材和补剂补成可供后续配方计算使用的数据底座。

## 目标

1. 覆盖当前 Web 管理端后台原料库里的所有食材和补剂。
2. 食材数据源优先级为 USDA 优先，其次是本地中国食物成分表。
3. 中国食物成分表不使用线上查询网站，改用用户本地 PDF 解析出的私有中间库。
4. 补剂优先使用产品标签；标签图片经 OCR/AI 识别后只生成待确认草稿。
5. 只有人工确认后的营养档案才能写入现有后台原料并参与未来配方计算。
6. 保留数据来源、匹配理由、确认人、确认时间、可信度和版本记录。
7. 为后续 ADF/PDD 风格配方设计器、Agent 自动设计和小程序同步打基础。

## 非目标

- 不在本阶段开放给普通小程序用户。
- 不在本阶段实现完整食谱自动平衡算法。
- 不在本阶段允许 Agent 直接发布食谱或直接写入正式营养档案。
- 不把中国食物成分表 PDF 解析数据作为公开分发的数据源。
- 不处理包材营养数据；包材不进入本阶段覆盖统计。
- 不替代营养师/人工审核。

## 参考软件

本项目后续配方设计方向参考：

- ADF：Animal Diet Formulator
- PDD：Pet Diet Designer

本设计阶段只吸收它们的核心产品方向：原料营养库、营养标准对照、配方计算、报告输出和专业审核流程。不照搬其界面、数据结构或商业规则。

## 数据源策略

### 食材

食材候选来源优先级：

1. USDA FoodData Central
2. 本地中国食物成分表结构化中间库
3. 人工创建候选

USDA 作为第一来源，因为它有正式 API 和批量数据集，字段结构稳定，适合机器处理。中国食物成分表作为第二来源，主要用于中文食材、国内常见部位或 USDA 匹配不准的原料。

用户本地已有两本 PDF：

- `/Users/zhaochen/Documents/Seven/宠物学习资料/书籍/杨月欣 - 中国食物成分表 标准版 第6版 第1册 (2018, 北京大学医学出版社) - libgen.li.pdf`
- `/Users/zhaochen/Documents/Seven/宠物学习资料/书籍/杨月欣 - 中国食物成分表 标准版 第6版 第2册 (2019, 北京大学医学出版社) - libgen.li.pdf`

这两本 PDF 会解析成 SevenKitchen 本地私有结构化中间库。该中间库只服务用户自己的本地项目匹配和回溯，不作为公开产品资产。

### 补剂

补剂优先来源为产品标签。

流程为：

```text
上传标签图片
  -> OCR 识别文字
  -> AI 提取成分、单位和原始口径
  -> 系统尝试换算
  -> 生成待确认草稿
  -> 人工确认后写入正式营养档案
```

补剂图片识别结果在人工确认前不参与任何配方计算。

## 总体方案

采用“治理型原料库”方案，保留三层数据：

1. 来源层
2. 候选/草稿层
3. 确认层

### 来源层

来源层保存原始数据和证据：

- USDA 原始 food record、FDC ID、数据类型、原始 nutrient 列表
- 中国食物成分表解析记录、册数、页码或表格位置、食物名、原始字段
- 补剂标签图片、OCR 原文、AI 识别结构、识别模型版本

来源层回答“数据从哪里来”。

### 候选/草稿层

候选/草稿层保存系统建议，但不直接进入计算：

- 食材：后台原料和外部来源记录的匹配候选
- 补剂：标签图片识别和换算后的草稿

候选需要记录：

- 匹配分数
- 匹配理由
- 来源优先级
- 高/中/低把握分级
- 是否需要人工补充参数
- 当前状态

候选/草稿层回答“系统为什么建议这样填”。

### 确认层

确认层是唯一可参与未来配方计算的数据：

- 写入 `Ingredient.nutritionProfile`
- 同步或映射到 `NutritionFood`
- 保存确认人、确认时间、可信度、来源引用和版本备注

确认层回答“当前业务系统正式采用哪份营养档案”。

## Web 管理端流程

新增 Web 管理端入口：`原料营养治理`。

该入口只面向管理员或内部使用者。小程序第一阶段不提供治理入口。

### 总览

展示覆盖率：

- 后台食材总数
- 后台补剂总数
- 已确认营养档案数量
- 有候选待确认数量
- 缺数据数量
- 不完整档案数量

包材不纳入覆盖率统计。

### 食材匹配

按高/中/低把握分组展示候选：

- 后台原料名
- 候选来源
- 候选食物名
- 部位/状态
- 主要营养字段对比
- 匹配理由
- 系统把握

高把握候选允许批量确认。中低把握候选必须进入详情页确认。

### 补剂识别

每个补剂可以上传一张或多张标签图。系统生成待确认草稿，详情页展示：

- 原图
- OCR 文本
- AI 提取的成分列表
- 原始标签口径
- 换算后口径
- 缺失参数
- 单位或字段疑点

所有补剂草稿都必须人工确认后才能写入正式营养档案。

### 已确认档案

展示已写入的营养档案：

- 当前营养数据
- 来源记录
- 确认记录
- 版本备注
- 历史版本

后续修正不静默覆盖旧记录，而是生成新的版本说明。

## 匹配规则

食材匹配不只看名称，还要综合：

- 原料类型
- 中文名
- 英文名
- 别名
- 部位
- 生熟状态
- 样品状态
- 是否可食部口径
- 现有标签分类

匹配分级：

- 高把握：名称、部位、状态都接近，允许批量确认
- 中把握：大类一致，但部位或状态不完全确定，需要详情确认
- 低把握：只做参考，不允许批量写入

USDA 候选优先于中国食物成分表候选。只有 USDA 缺失、匹配不准或不适合中文食材时，才优先看中国食物成分表候选。

## 换算规则

系统保留两类口径：

- 原始口径：来源真实写法
- 标准化口径：系统计算使用的结构

允许的原始口径包括：

- 每 100g
- 每 100ml
- 每 1g
- 每 1ml
- 每粒、每片、每勺、每份

食材通常按每 100g。油脂可能是每 100ml 或每 100g。补剂常见为每粒、每片、每勺或每份。

缺少换算必需参数时，系统可以保存草稿或不完整档案，但不能静默进入完整计算。例如：

- 标签写“每份含钙 300mg”，但没写每份重量
- 标签写“每勺含 EPA 200mg”，但没写每勺多少克或多少毫升
- 油类数据按 ml 给出，但没有密度

这种情况需要人工补充参数后才能确认完整档案。

## 与现有数据模型的衔接

### `Ingredient.nutritionProfile`

这是现有业务使用的营养档案字段。确认后的营养数据写入这里，供后续食谱、DIY、配方设计器和 Agent 读取。

### `NutritionFood`

继续作为独立营养原料库，用于保存更专业、可复用的营养对象。

食材确认后，可以生成或更新对应的 `NutritionFood` 记录，再通过 `NutritionFoodMapping` 关联到后台原料。

### `NutritionFoodMapping`

保留后台原料和独立营养原料的映射关系。

这让现有业务可以先通过 `Ingredient.nutritionProfile` 直接可用，同时保留未来迁移到更专业营养库的空间。

## 配方设计器衔接

后续 ADF/PDD 风格配方设计器只读取确认后的营养数据。

如果某个原料缺关键营养数据：

- 允许被选入配方
- 页面必须提示缺失项
- 达标判断必须标记“不完整”
- 不允许把缺失数据当成 0 或自动推断为达标

## Agent 衔接

后续 OpenClaw、OpenAI Agent 或其他智能 Agent 只能访问确认后的数据和受控接口：

- 可用原料列表
- 已确认营养档案
- 原料标签和限制
- 营养标准
- 创建配方草稿接口
- 计算差距报告接口

Agent 不能：

- 把 OCR 草稿直接写入正式营养档案
- 直接发布食谱
- 绕过人工确认
- 使用低把握候选当作已确认数据

## 小程序衔接

小程序第一阶段只消费结果：

- 展示已发布食谱
- 生成 DIY 制作单
- 打开营养报告
- 未来展示更完整的营养分析

小程序不承担原料营养治理、批量匹配或补剂标签审核。

## 质量控制

1. USDA 和中国食物成分表候选必须保留来源记录。
2. 食材自动匹配必须有高/中/低把握分级。
3. 只有高把握食材候选允许批量确认。
4. 补剂图片识别只生成草稿，人工确认前不参与计算。
5. 单位换算必须展示原始口径和换算后口径。
6. 缺少换算参数时不得静默生成完整档案。
7. 每次确认都要保存确认人、确认时间和版本备注。
8. 未来配方设计器和 Agent 只读取确认层数据。

## 错误处理

### USDA 请求失败

系统保留失败原因，并允许稍后重试。失败不会影响已有候选和已确认档案。

### 中国食物成分表解析失败

解析失败记录到导入报告中，标明文件、页码或表格片段。失败部分不进入候选库。

### OCR/AI 识别失败

补剂标签识别失败时保留原图，并提示重新上传更清晰图片或人工录入。

### 单位无法识别

候选进入“需人工处理”状态，不允许确认成完整档案。

### 重复来源

如果同一个 USDA FDC ID 或同一条中国食物成分表记录已存在，系统复用来源记录，不重复创建。

## 实施顺序建议

1. 建立来源记录和候选/草稿数据模型。
2. 解析本地中国食物成分表 PDF，生成私有中间库。
3. 完善 USDA 导入和标准字段映射。
4. 建立食材候选匹配与分级。
5. 建立 Web 管理端原料营养治理总览和食材匹配页。
6. 建立补剂标签图片上传、OCR/AI 草稿和人工确认流程。
7. 将确认后的数据写入 `Ingredient.nutritionProfile` 并同步 `NutritionFood`。
8. 为后续配方设计器和 Agent 暴露只读确认层接口。

## 已确认决策

- 从原料库优先开始，不先做完整配方设计器。
- 第一版覆盖现有后台所有食材和补剂。
- 食材优先 USDA，其次本地中国食物成分表。
- 不使用线上食物营养成分查询平台作为第一版数据源。
- 中国食物成分表 PDF 解析成仅本地项目使用的私有结构化中间库。
- 补剂优先产品标签。
- 补剂标签图片识别结果必须先生成待确认草稿。
- 用户确认后才写入正式营养档案。
- 采用来源库、候选/草稿、确认档案三层结构。
- 管理入口在 Web 管理端，不在小程序工作台。
- 后续参考软件为 ADF 和 PDD，不是 PPP。
