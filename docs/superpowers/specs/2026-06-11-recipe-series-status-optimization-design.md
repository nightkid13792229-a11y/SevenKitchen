# 食谱系列状态优化设计

## 背景

当前食谱相关状态分散在三类对象上：

- `RecipeSeries.status` 只表示系列是否可用，目前是 `ACTIVE / DELETED`。
- `Recipe.status` 表示正式食谱版本状态，目前是 `DRAFT / PUBLIC / PRIVATE_CUSTOM`。
- `DesignRecipe.status` 表示设计草稿评估和发布状态，目前包含 `DRAFT / COMPLIANT / NEEDS_REVIEW / PUBLISHED / ARCHIVED`。

这些状态各自有合理来源，但在业务展示中承担了混合语义。管理后台和小程序设计器都需要同时表达“整个系列是草稿、公开还是私密定制”和“五个生命阶段分别设计到哪一步”。如果继续用单个正式食谱版本的 `Recipe.status` 推导系列和阶段状态，会出现以下问题：

1. 新建系列后即使某个生命阶段没有原料，也可能因为存在空设计草稿而显示为已修改。
2. 小程序点击“提交后台草稿”后，阶段仍显示为草稿，缺少“已提交”的业务状态。
3. 一个系列下多个生命阶段或多个版本状态不一致时，系列整体状态会被临时推导，展示不稳定。
4. 小程序编辑器的“撤回”目前只是撤销最近一次编辑操作，不是回到最新正式版本。

本设计把状态重新拆成两层业务状态：食谱系列整体状态和系列下生命阶段状态。

## 已确认决策

1. `DRAFT / PUBLIC / PRIVATE_CUSTOM` 应作为食谱系列的整体业务状态，而不是主要挂在某个正式食谱版本上。
2. 五个生命阶段仍然需要各自独立状态，不能被系列整体状态替代。
3. 正式食谱版本仍然存在，但它的状态不再作为系列业务状态的唯一来源。
4. 小程序设计器列表需要同时展示系列整体状态和五个生命阶段状态。
5. 小程序编辑器需要支持一键撤回当前修改，回到最新正式版本。

## 目标

1. 明确区分“系列整体业务归属”和“生命阶段设计进度”。
2. 让管理后台和小程序列表状态口径一致。
3. 支持系列草稿、公开发布、私密定制三种整体业务状态。
4. 支持五个生命阶段分别显示未设计、已修改、已提交、已发布、私密定制。
5. 支持已发布或私密定制阶段的修订草稿一键回到最新正式版本。
6. 通过迁移兼容现有 `Recipe`、`RecipeSeries`、`DesignRecipe` 数据。

## 非目标

1. 不重做食谱设计器的营养计算和评估规则。
2. 不改变五个生命阶段定义。
3. 不改变小程序公开食谱详情页的生命周期匹配逻辑，除非它依赖旧状态口径。
4. 不在本次设计中引入完整定制订单权限模型；私密定制的具体用户授权可在后续设计中细化。
5. 不删除历史正式食谱版本。

## 状态模型

### 系列整体状态

系列整体状态描述“这个系列食谱准备面向谁”。

建议在 `RecipeSeries` 上新增业务状态字段：

```text
businessStatus: DRAFT | PUBLIC | PRIVATE_CUSTOM
```

状态含义：

| 状态 | 展示文案 | 含义 |
| --- | --- | --- |
| `DRAFT` | 草稿 | 该系列仍在后台检查、补充信息或等待决策，未面向公开用户或定制用户生效 |
| `PUBLIC` | 已发布 | 该系列作为公开食谱面向所有用户展示 |
| `PRIVATE_CUSTOM` | 私密定制 | 该系列作为私密定制食谱，用于特定用户、宠物或定制订单 |

`RecipeSeries.status` 可以继续保留为生命周期字段，用于 `ACTIVE / DELETED`。这两个状态不表达业务可见性。

### 生命阶段状态

生命阶段状态描述“这个系列下某个生命阶段做到哪一步了”。

建议对小程序和管理后台统一输出以下状态：

| 状态 | 展示文案 | 含义 |
| --- | --- | --- |
| `NOT_DESIGNED` | 未设计 | 该阶段没有原料，或不存在可编辑设计内容 |
| `MODIFIED` | 已修改 | 该阶段已有原料和设计内容，但还没有提交后台草稿 |
| `SUBMITTED` | 已提交 | 该阶段已提交为后台草稿，等待后台完善、发布或设为私密定制 |
| `PUBLISHED` | 已发布 | 该阶段已经有当前公开正式版本 |
| `PRIVATE_CUSTOM` | 私密定制 | 该阶段属于私密定制系列，或该阶段当前正式版本被确认为私密定制 |

阶段状态可以先由现有 `DesignRecipe` 和 `Recipe` 数据推导，也可以在后续新增显式阶段表。无论内部实现如何，接口输出必须稳定。

### 正式食谱版本状态

`Recipe` 仍然表示正式食谱版本。它可以继续保留状态字段，但语义需要收窄为版本级状态，不再承担系列整体业务状态。

建议过渡期保持现有 `Recipe.status`，用于兼容已有接口：

- `DRAFT`：后台草稿版本，通常对应阶段 `SUBMITTED`。
- `PUBLIC`：公开正式版本，通常对应阶段 `PUBLISHED`。
- `PRIVATE_CUSTOM`：私密正式版本，通常对应阶段 `PRIVATE_CUSTOM`。

长期可以考虑把 `Recipe.status` 重命名或替换为更清晰的版本状态，例如 `versionStatus`，但这不是第一阶段必须完成的内容。

## 核心流程

### 新建系列

1. 小程序设计器点击“新建食谱”。
2. 后端创建 `RecipeSeries`，`businessStatus = DRAFT`。
3. 后端可以创建默认生命阶段的 `DesignRecipe`，但如果没有原料，该阶段必须显示 `NOT_DESIGNED`。
4. 其他未创建设计草稿的阶段也显示 `NOT_DESIGNED`。

### 编辑生命阶段

1. 用户进入某个生命阶段编辑页。
2. 如果该阶段没有原料，列表显示 `NOT_DESIGNED`。
3. 用户添加至少一个有效原料后，该阶段显示 `MODIFIED`。
4. 修改名称、生命阶段或备注但没有原料时，不应单独让阶段进入 `MODIFIED`，除非后续明确把这些视为可提交设计内容。

### 提交后台草稿

1. 用户在营养报告页点击“提交后台草稿”。
2. 后端基于当前设计草稿创建或更新对应阶段的后台正式食谱草稿。
3. 该阶段显示 `SUBMITTED`。
4. 系列整体仍保持 `DRAFT`，直到 Web 管理后台明确选择公开发布或私密定制。

### Web 后台发布公开食谱

1. 管理员在 Web 管理后台检查系列标题、封面、详情图、描述等信息。
2. 管理员确认该系列面向所有用户发布。
3. 系列 `businessStatus` 改为 `PUBLIC`。
4. 被发布的生命阶段显示 `PUBLISHED`。
5. 小程序公开橱窗只展示 `businessStatus = PUBLIC` 且至少一个阶段为 `PUBLISHED` 的系列。

### Web 后台设为私密定制

1. 管理员确认该系列是为特定用户、宠物或订单定制。
2. 系列 `businessStatus` 改为 `PRIVATE_CUSTOM`。
3. 已提交或已确认的相关生命阶段显示 `PRIVATE_CUSTOM`。
4. 小程序公开橱窗不展示该系列。
5. 私密定制入口和订单流程可以通过后续授权规则读取该系列。

### 一键撤回到最新正式版本

1. 用户在小程序编辑器中打开已发布或私密定制阶段后，系统可以创建修订草稿。
2. 用户点击“一键撤回”。
3. 后端找到该系列、该生命阶段下最新正式版本：
   - 优先 `PRIVATE_CUSTOM`，如果系列是私密定制；
   - 否则优先 `PUBLIC`。
4. 后端删除、归档或重置当前未提交修订草稿。
5. 小程序重新加载最新正式版本内容。
6. 如果撤回后没有新的修改，阶段状态回到 `PUBLISHED` 或 `PRIVATE_CUSTOM`。

## 页面表现

### 小程序食谱设计器列表

系列卡片需要显示：

- 系列名称。
- 系列整体状态：草稿、已发布、私密定制。
- 最近更新时间。
- 五个生命阶段状态。

生命阶段状态文案：

- `NOT_DESIGNED`：未设计
- `MODIFIED`：已修改
- `SUBMITTED`：已提交
- `PUBLISHED`：已发布
- `PRIVATE_CUSTOM`：私密定制

现有“私密食谱”建议统一为“私密定制”，与 Web 后台一致。

### 小程序食谱编辑页

编辑页需要区分两个撤回能力：

- 撤销最近一次编辑：继续保留为编辑历史 undo，可以用图标表达。
- 回到最新正式版本：新增明确按钮或菜单项，文案建议为“回到正式版本”或“撤回修改”。

“撤回修改”只在存在已发布或私密定制基线版本且当前有修订草稿时展示。

### Web 管理后台食谱列表

列表以系列为主行展示：

- 系列名称。
- 系列整体状态。
- 封面。
- 五个生命阶段标签。
- 是否存在待提交、待发布或待完善阶段。

生命阶段标签点击后进入对应阶段版本详情。

### Web 管理后台食谱详情

详情页需要允许管理员处理系列整体状态：

- 保存为草稿。
- 发布为公开食谱。
- 设为私密定制。

发布或设为私密定制时，应明确作用范围：

- 当前生命阶段。
- 当前系列所有已提交生命阶段。

第一阶段可以先支持当前生命阶段，后续再补批量发布。

## 接口调整

### 设计器系列列表接口

`GET /api/v1/recipe-designer/series` 返回值建议增加：

```text
businessStatus: DRAFT | PUBLIC | PRIVATE_CUSTOM
businessStatusLabel: string
```

每个阶段返回：

```text
status: NOT_DESIGNED | MODIFIED | SUBMITTED | PUBLISHED | PRIVATE_CUSTOM
```

原有 `recipeStatusCategory` 可以作为过渡字段保留，但前端应逐步改用 `businessStatus` 和阶段 `status`。

### 管理后台食谱接口

`GET /api/v1/admin/recipes` 和 `GET /api/v1/admin/recipes/:id` 需要返回系列整体业务状态。

发布和私密定制操作建议收口成显式动作：

```text
POST /api/v1/admin/recipe-series/:seriesId/publish
POST /api/v1/admin/recipe-series/:seriesId/private-custom
POST /api/v1/admin/recipe-series/:seriesId/revert-to-draft
```

如果第一阶段不新增系列接口，也可以先通过现有 `admin/recipes/:id` 更新当前阶段，同时同步更新 `RecipeSeries.businessStatus`。但最终应收口到系列维度，避免页面误把单阶段状态当成系列状态。

### 撤回接口

小程序编辑器需要新增接口：

```text
POST /api/v1/recipe-designer/drafts/:id/revert-to-latest-official
```

返回新的可编辑草稿或正式版本快照，前端据此刷新编辑器。

## 迁移策略

### 数据库迁移

1. 新增 `RecipeSeriesBusinessStatus` 枚举。
2. 在 `recipe_series` 新增 `business_status` 字段，默认 `DRAFT`。
3. 保留 `RecipeSeries.status` 的 `ACTIVE / DELETED` 语义。

### 现有数据回填

按系列下已有正式食谱版本回填：

1. 如果任一版本为 `PRIVATE_CUSTOM`，系列 `business_status = PRIVATE_CUSTOM`。
2. 否则如果任一版本为 `PUBLIC`，系列 `business_status = PUBLIC`。
3. 否则系列 `business_status = DRAFT`。

阶段状态回填和接口推导：

1. 没有设计草稿、没有正式食谱版本：`NOT_DESIGNED`。
2. 有设计草稿但有效原料数为 0：`NOT_DESIGNED`。
3. 有设计草稿且有效原料数大于 0，但没有后台正式食谱草稿：`MODIFIED`。
4. 有 `Recipe.status = DRAFT` 的对应阶段正式食谱：`SUBMITTED`。
5. 有 `Recipe.status = PUBLIC` 的对应阶段正式食谱：`PUBLISHED`。
6. 系列 `business_status = PRIVATE_CUSTOM` 或阶段有 `Recipe.status = PRIVATE_CUSTOM`：`PRIVATE_CUSTOM`。

如果同一阶段同时命中多个状态，优先级为：

```text
PRIVATE_CUSTOM > PUBLISHED > SUBMITTED > MODIFIED > NOT_DESIGNED
```

## 风险与处理

### 旧接口兼容

现有小程序、管理后台和公开食谱接口可能仍依赖 `Recipe.status`。第一阶段不删除旧字段，先新增系列业务状态并调整列表推导。

### 状态优先级变化

以前有后台草稿时阶段显示“草稿”，新方案显示“已提交”。需要同步前端文案和测试，避免运营误解。

### 私密定制授权

本设计只定义系列状态，不完整定义“哪个用户能看到私密定制”。实施时需要保证私密定制不会进入公开橱窗。用户级授权可以作为后续专项。

### 一键撤回破坏数据

撤回不应删除历史正式版本。对于未提交修订草稿，优先归档或重置；如果要删除，也必须只删除当前用户当前阶段的未提交修订草稿。

## 验收标准

1. 新建系列后，未添加原料的生命阶段显示“未设计”。
2. 添加原料后，该生命阶段显示“已修改”。
3. 提交后台草稿成功后，该生命阶段显示“已提交”。
4. Web 后台发布后，系列显示“已发布”，对应生命阶段显示“已发布”。
5. Web 后台设为私密定制后，系列显示“私密定制”，对应生命阶段显示“私密定制”。
6. 小程序公开橱窗只展示系列整体状态为“已发布”的食谱。
7. 私密定制系列不出现在公开橱窗。
8. 对已发布或私密定制阶段做修改后，编辑器显示可撤回修改。
9. 点击撤回修改后，内容回到最新正式版本，阶段状态不再显示“已修改”。
10. 同一系列多个生命阶段可以显示不同阶段状态，但系列整体状态只有一个。

## 实施拆分建议

第一阶段：后端状态模型和接口口径。

- 新增 `RecipeSeries.businessStatus`。
- 回填历史系列状态。
- 修正设计器系列列表阶段状态推导。
- 管理后台接口返回系列业务状态。

第二阶段：小程序展示和撤回。

- 小程序设计器列表展示系列整体状态和阶段状态。
- 文案统一为“已提交”“私密定制”。
- 新增回到最新正式版本能力。

第三阶段：Web 管理后台发布动作收口。

- 管理后台列表以系列状态为主。
- 发布、私密定制、回到草稿以系列维度表达。
- 保留单生命阶段处理能力，避免批量误操作。

第四阶段：清理旧状态语义。

- 梳理仍依赖 `Recipe.status` 表达系列状态的接口。
- 将 `Recipe.status` 逐步收窄为版本级状态。
- 补充私密定制授权模型。
