# 新增标准原料 Skill 设计

## 背景

SevenKitchen 的标准原料新增不是单表写入。一个可用于业务的原料可能同时涉及标准原料、营养档案、主营养档案映射、食材采购 SKU、标签绑定、补剂单层产品字段、营养单位换算和生产迁移包。

项目中曾经尝试过小程序侧 AI 原料创建能力，后续已移除相关页面和表。新的能力不恢复那个面向小程序的创建入口，而是在项目内创建一个 Codex Skill，让 Codex 在本项目中以受控方式新增标准原料。

## 目标

1. 创建项目内 Skill：`skills/adding-standard-ingredients/`。
2. 支持自动新增 `FOOD` 食材和 `SUPPLEMENT` 补剂。
3. 写入本地开发库前，必须确认本地库和生产库处于可安全部署的一致状态。
4. 本地写入必须先 dry-run，再人工确认。
5. 本地写入后生成本次新增对象清单、营养审计报告和生产迁移包。
6. 生产迁移只允许迁移本次新增原料相关数据，禁止整库迁移或本地库覆盖生产库。
7. 食材营养数据必须从可追溯来源寻找和录入，不能凭模型记忆补全。
8. 补剂优先通过包装照片识别标签和有效成分；没有照片时必须提示用户补充照片或文字/链接依据。

## 非目标

1. 第一版不支持 `PACKAGING` 包材新增。
2. 第一版不恢复小程序 AI 原料创建页面。
3. 第一版不允许无确认写入生产库。
4. 第一版不自动更新生产已有原料；更新已有记录必须作为单独变更处理。
5. 第一版不使用普通网页或模型记忆作为食材主档案营养来源。
6. 第一版不把本地数据库整体同步到生产数据库。

## 已确认决策

1. 第一版直接做半自动新增能力，而不是只做人工 SOP。
2. 第一版覆盖食材和补剂，但两条流程分开。
3. 本地开发库允许写入，但写入前必须通过本地和生产一致性检查。
4. 生产侧只接收本次新增对象的定向迁移包。
5. 食材营养来源不优先 CFCT；CFCT 是其他更完整来源找不到合适匹配时的兜底来源。
6. MEXT、AUSNUT/AFCD、Canadian Nutrient File、UK CoFID、Ciqual 等官方数据库纳入白名单。
7. 营养来源匹配、完整性、单位审计和犬用口径标准化都是硬闸门。
8. 跨来源补字段允许，但必须通过口径一致、父子营养素一致、能量和宏量 sanity check。
9. 维生素 A、D、E 必须按项目和 FEDIAF 犬用口径标准化后再进入可计算主字段。

## 整体架构

Skill 名称建议为 `adding-standard-ingredients`。它是一个项目内受控导入工作流，指导 Codex 使用项目内脚本、Prisma schema、营养档案规则和迁移包规则完成新增原料。

核心流程：

```text
用户输入
  -> 本地/生产一致性检查
  -> 原料类型分流
  -> 资料和来源收集
  -> dry-run manifest
  -> 用户确认
  -> 写入本地开发库
  -> 本地回读和营养审计
  -> 生成定向生产迁移包
  -> 生产预演检查
  -> 等待用户确认生产执行
```

Skill 的边界：

- 支持新增 `FOOD` 和 `SUPPLEMENT`。
- 不支持 `PACKAGING`。
- 不允许跳过 dry-run。
- 不允许跳过用户确认。
- 不允许整库导入。
- 不允许生产无预演执行。
- 不允许用本地库覆盖生产库。

## 本地和生产一致性检查

一致性不要求两边业务数据逐行完全相同，而是要求本次新增结果可以安全变成生产迁移包。

### 结构闸门

检查本地和生产：

- Prisma migration 历史一致。
- 本地没有未应用 migration。
- 生产没有本地缺失 migration。
- 关键表结构一致。

关键表至少包括：

- `ingredient`
- `ingredient_tag`
- `ingredient_tag_assignment`
- `nutrition_food`
- `nutrition_food_mapping`
- `procurement_sku`
- `procurement_sku_price_history`

### 引用闸门

检查本次新增会引用的对象：

- 标签在本地和生产都存在，且名称和层级可对齐。
- 已有营养来源或营养档案在生产也存在。
- 如果本地新建营养档案，迁移包必须把它一起带上。
- 不能依赖只存在本地、生产缺失的配置。

### 冲突闸门

检查生产当前状态：

- 不存在同名、同品牌、同规格的标准原料。
- 不存在冲突的 `nutrition_food(name, data_source, version)`。
- 不存在同一原料下等价采购 SKU。
- 补剂不能把同一具体产品重复建成多个标准原料。
- 食材不能把采购 SKU 信息写回标准原料主字段作为主要真源。

任意闸门失败时，Skill 只能生成草稿和问题清单，不能进入本地可迁移写入状态。

## 食材新增流程

食材的标准原料是逻辑食材，不是采购商品。

输入示例：

```text
新增去皮鸡腿肉，生重，优先找官方完整营养数据，采购 SKU 先用本地市场。
```

流程：

1. 判断原料类型为 `FOOD`。
2. 生成标准原料草稿：名称、基准单位、标签、可食率、密度、备注。
3. 从官方来源白名单寻找营养数据。
4. 对候选来源做语义、状态、完整性和单位检查。
5. 如果同一来源词条已经生成完全匹配的 `NutritionFood`，可复用；否则新建 `NutritionFood`。
6. 创建 `NutritionFoodMapping`，并经确认设为主档案。
7. 需要采购时创建 `procurement_sku`。
8. 回读校验食谱设计器可见主营养档案，采购/库存链路可见采购 SKU。

食材硬规则：

- 不因名称相似复用营养档案。
- 生/熟、去皮/带皮、鲜/干、粉末/油脂状态不能混用。
- 品牌、渠道、规格、采购价必须落到采购 SKU，而不是作为食材标准原料本体。
- 无可追溯营养来源时不能创建高可信主档案。

## 补剂新增流程

补剂为单层模型，一条标准原料就是一个具体补剂产品。

输入示例：

```text
新增 NOW 鱼油 180 粒，每粒 EPA 500mg DHA 250mg，iHerb 采购。
```

流程：

1. 判断原料类型为 `SUPPLEMENT`。
2. 要求用户优先提供包装照片，包括正面、成分表、营养表、规格和净含量。
3. 如果没有照片，必须提示用户补充照片；如暂时没有照片，可改用文字、商品链接、检测报告或供应商规格书，但不能凭空补浓度。
4. 从照片或资料识别品牌、商品名、规格、每份/每粒/每勺重量、有效成分、单位、建议用量、净含量、渠道。
5. 生成补剂标准原料草稿，名称应包含产品和浓度差异，避免把多个具体产品混成一个泛化原料。
6. 写入单层产品字段：品牌、规格、渠道、采购单位、换算、价格、展示单位、图片/链接。
7. 写入营养浓度档案，并保留字段级来源。
8. 判断 `diyEnabled` 和 `procurementEnabled`。
9. 校验补剂计算能从营养档案解析到目标营养素浓度。

补剂硬规则：

- 不挂 `procurement_sku`。
- `properties.active_nutrients` 只能作为兼容派生或缓存，不作为人工真源。
- 标签写“碳酸钙 1000mg”不等于“钙 1000mg”；必须确认元素量。
- 无来源形态的 A/D/E 不自动换算。

## 食材营养来源政策

### 官方来源白名单

可优先评估的官方数据库包括：

- USDA FoodData Central
- NZFCD / FOODfiles
- NEVO
- MEXT / 日本食品标准成分表
- Australian Food Composition Database / AUSNUT
- Canadian Nutrient File
- UK CoFID
- 法国 Ciqual

其他可接受来源：

- 检测报告
- 供应商规格书
- 产品标签
- 项目已导入并可审计的 `nutrition_source_record`

CFCT 作为兜底来源：

- 只有当其他更完整来源找不到合适匹配时才考虑。
- 如果中国本土食材只有 CFCT 有明确匹配，可以使用。
- 使用 CFCT 时必须标记缺失字段和置信度，不能伪装成完整档案。

不可接受来源：

- 普通网页摘录。
- 无版本、无编号、无来源的表格。
- 模型记忆。
- 不能追溯原始单位或状态的数据。

### 来源匹配规则

候选来源必须通过：

1. 来源资格检查。
2. 原料本体匹配。
3. 生/熟、去皮/带皮、鲜/干、粉末/油脂等状态匹配。
4. 可食部口径检查。
5. 单位和基准口径检查。
6. 完整性评分。

选择主档案时优先级：

```text
语义和状态精确匹配
  > FEDIAF 必需营养素覆盖率高
  > 同一数据来源含生熟两种状态档案
  > 来源权威且可追溯
  > 字段级单位可靠
```

## 营养完整性检查

完整性由两部分组成。

### 状态完整性

检查同一数据来源是否同时存在同一原料的生档案和熟档案。

- 同源含生熟档案，评分更高。
- 只有生或只有熟，不直接淘汰，但标记适用边界。
- 标准原料默认状态必须和主档案一致。
- 生重设计不能拿熟制档案冒充。

### FEDIAF 必需营养素覆盖率

覆盖率基于项目中的 FEDIAF 2025 犬营养标准数据和字段映射，不在 Skill 中手写固定清单。

计算规则：

```text
覆盖率 = 有有效数值的 FEDIAF 2025 必需营养素数量 / FEDIAF 2025 需要评估的必需营养素总数
```

无效数值包括：

- 缺字段。
- `null`。
- 空字符串。
- 非数字。
- 数值为 `0`。

例外：只有当来源明确标注该营养素检测值为 0，且该营养素允许 0 时，才可作为有效值。默认情况下 0 按无数据处理。

审计报告必须输出：

- 覆盖率百分比。
- 缺失营养素清单。
- 生/熟档案是否齐全。
- 候选来源排序原因。

## 跨来源补字段一致性

允许多来源补字段，但补入前必须通过一致性校验。

### 口径统一

补充字段必须先统一到同一基准：

- 每 100g。
- 每 100ml。
- 每 1g。
- 每 1ml。
- 每份、每粒、每勺。

生熟状态、干湿基准、可食部口径不一致时，不能直接补入。

### 父子营养素一致

必须检查：

- 亚油酸不能大于总脂肪。
- EPA + DHA + DPA 不能大于总脂肪。
- 各脂肪酸合计不能明显超过总脂肪。
- 单个氨基酸不能大于粗蛋白。
- 氨基酸总和不能明显超过粗蛋白。
- 可溶性纤维 + 不溶性纤维不能大于总纤维。
- 矿物质合计不能出现明显不可能的数量级。

### 宏量和能量 sanity check

必须检查：

- 蛋白、脂肪、碳水推导热量不能和来源能量严重冲突。
- 水分 + 蛋白 + 脂肪 + 灰分 + 碳水/纤维不能明显超过 100g。
- 干物质换算后不能出现负值或不合理比例。

冲突处理：

- 默认不补入冲突字段。
- 生成冲突报告。
- 可进入数据修复或优化候选。
- 修复后必须重新通过一致性校验。
- 不允许静默覆盖主档案或硬塞异常值。

## 犬用营养口径标准化

人用食品数据库的营养字段不能直接等同于犬用 FEDIAF 计算字段。新增原料时必须做犬用口径标准化。

### 维生素 A

强制重算。

- 优先使用视黄醇和犬用 beta-carotene 活性。
- 仅有 RAE/RE 时只能作为 fallback。
- 必须记录原值、原单位、来源形态、换算系数和是否 fallback。
- 项目实现真源为 `backend/src/domain/ingredient/vitamin-a-conversion.ts`。

### 维生素 E

强制重算。

- 需要区分 d-alpha-tocopherol、dl-alpha-tocopherol、tocopheryl acetate 等形态。
- 无 FEDIAF/NRC 确认换算依据的形态先保留为 review-only。
- tocotrienol 不自动计入维生素 E 达标值。
- 项目实现真源为 `backend/src/domain/ingredient/vitamin-e-conversion.ts`。

### 维生素 D

强制单位标准化。

- 普通 D2 + D3 总量可按 `1 microgram = 40 IU` 换算。
- D2、D3 和 25-hydroxy 等形态必须保留来源形态。
- 特殊代谢物不自动按普通 D3 处理。

### 其他需要 review 的营养素

- B3：不要把 niacin equivalents 直接当犬用烟酸。
- B9：DFE、folate、folic acid 必须记录形态，不清楚时降级。
- 矿物质补剂：必须区分化合物量和元素量。
- 能量：来源能量可保留，犬配方评估应经过项目的能量审计路径。

只有项目已有明确换算规则的字段才自动重算。否则保留原始来源项并要求人工确认。

## 单位审计

单位审计分两次。

### 入库前单位审计

检查：

- 原始单位。
- 原始基准。
- 每 100g、每份、每粒、每 ml 口径。
- mg、microgram、IU、g、kcal、kJ 换算。
- 干物质、湿基、可食部、生熟状态。
- A/D/E 活性单位换算。

不通过时不能设为主档案。

### 本地写入后单位审计

回读本地数据并检查：

- `nutrition_food.nutrition_data` 未丢字段。
- `ingredient.nutrition_profile` 与主档案一致。
- 字段级来源和换算说明仍存在。
- 父子营养素、宏量、能量 sanity check 通过。

通过后才允许生成生产迁移包。

## 迁移包设计

本地写入成功后生成迁移包。迁移包只包含本次新增或本次必须随带的对象。

### 对象清单

可能包含：

- `ingredient`
- `nutrition_food`
- `nutrition_food_mapping`
- `procurement_sku`
- `procurement_sku_price_history`
- `ingredient_tag_assignment`
- 必要来源记录或附件引用

### 审计报告

必须包含：

- 本地/生产一致性检查结果。
- 原料类型判断。
- 营养来源匹配报告。
- FEDIAF 必需营养素覆盖率。
- 生/熟档案完整性。
- 单位审计。
- 犬用口径标准化记录。
- 跨来源补字段一致性报告。
- 本地写入后回读校验。

### 生产预演

执行生产前必须 dry-run：

- 检查同名、同品牌、同规格冲突。
- 检查营养档案唯一键冲突。
- 检查标签、来源、枚举引用。
- 输出将新增、将跳过、将失败清单。
- 确认不会修改无关生产数据。

### 执行形态

迁移包以 JSON manifest 为真源。执行脚本应优先使用 Prisma Client 读取 manifest 并执行数据写入。SQL 只可作为审计预览或人工检查辅助，不作为默认执行路径。

生产执行必须是独立命令，默认 dry-run。真实执行需要用户明确确认。

## Skill 文件结构

建议结构：

```text
skills/adding-standard-ingredients/
  SKILL.md
  references/
    source-policy.md
    nutrition-audit.md
  scripts/
    check-db-alignment.ts
    prepare-ingredient-import.ts
    apply-local-ingredient-import.ts
    audit-ingredient-import.ts
    build-production-migration-package.ts
  assets/
    manifest-template.json
```

### SKILL.md

包含：

- 触发条件。
- 硬规则。
- 食材/补剂分流。
- 人工确认点。
- 禁止事项。
- 常见错误。
- 需要读取的 reference 文件说明。

### source-policy.md

包含：

- 官方来源白名单。
- CFCT 兜底规则。
- 来源匹配评分。
- 生/熟状态完整性。
- FEDIAF 覆盖率计算要求。

### nutrition-audit.md

包含：

- 单位审计。
- 跨来源补字段一致性。
- 犬用口径标准化。
- A/D/E 处理。
- 父子营养素和能量 sanity check。

### scripts

脚本职责：

- `check-db-alignment.ts`：检查本地/生产结构、migration 和关键引用。
- `prepare-ingredient-import.ts`：根据输入草稿生成 dry-run manifest。
- `apply-local-ingredient-import.ts`：只允许写入本地开发库。
- `audit-ingredient-import.ts`：回读本地数据并生成审计报告。
- `build-production-migration-package.ts`：生成生产迁移包和预演报告。

生产真实执行脚本不作为第一版默认入口。若后续加入，也必须默认 dry-run 且要求显式确认。

## 测试和验证

创建 Skill 时使用文档 TDD 思路，先设计失败场景，再写 Skill 和脚本。

必须覆盖的失败场景：

1. 跳过本地/生产一致性检查就写入本地。
2. 生成整库迁移或试图覆盖生产库。
3. 食材把品牌规格写进标准原料，而不是采购 SKU。
4. 补剂没有照片或文字来源，却继续凭空创建浓度。
5. CFCT 被错误设为优先来源。
6. 名称相似但状态不一致的营养档案被复用。
7. 亚油酸大于总脂肪仍被补入。
8. 氨基酸大于粗蛋白仍被补入。
9. 维生素 A/E 没做犬用口径换算。
10. 维生素 D 特殊形态被当普通 D3 自动换算。
11. FEDIAF 必需营养素覆盖率没有输出。
12. 本地写入后未回读校验就生成生产迁移包。

脚本测试应优先放在 `backend/tests` 或 Skill 自带脚本测试中，执行时不连接生产写库。生产相关测试只允许 dry-run 或使用 mock 数据库连接。

## 风险和防护

### 风险：误写生产

防护：

- 生产命令默认 dry-run。
- 真实执行要求显式确认。
- manifest 只允许本次对象。
- 禁止整库导入。

### 风险：营养数据看似完整但口径错误

防护：

- 来源匹配评分。
- 单位审计。
- 犬用口径标准化。
- 字段级来源。
- 完整性和一致性报告。

### 风险：多来源补字段制造不合理档案

防护：

- 先统一基准。
- 父子营养素检查。
- 能量和宏量 sanity check。
- 冲突字段默认不补入。

### 风险：本地可用但生产不可部署

防护：

- 写本地前做生产一致性检查。
- 本地写入后生成定向迁移包。
- 生产预演检查冲突和引用。

## 成功标准

1. 使用 Skill 新增食材时，能生成来源可追溯、单位审计通过、可迁移的本地新增结果。
2. 使用 Skill 新增补剂时，能从照片或用户提供资料识别有效信息，并在缺照片时主动提示。
3. 本地写入前必须有本地/生产一致性报告。
4. 本地写入后必须有审计报告。
5. 生产迁移包只包含本次新增对象。
6. 生产预演能清楚说明将新增、将跳过、将失败的内容。
7. Skill 验证能拦住失败场景中的危险行为。
