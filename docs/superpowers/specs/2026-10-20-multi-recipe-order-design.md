# 食谱定制多份购买设计

- 日期：2026-10-20
- 状态：已定稿（V3 原型已确认；成品抵扣取消）
- 适用模块：小程序、后端、admin-web、设计器

## 1. 为什么做

现有定制订单一份订单只交付一份食谱。顾客实际存在另一种需求：

- 不想狗狗在一段时间内只吃一种配方；
- 希望一次买几份不同配方的完整主食，轮换着吃；
- 常见做法是每个口味做 7–15 天的量，做成鲜食后冷藏/冷冻，今天吃一种、明天吃另一种。

顾客通常不具备营养知识，也不一定说得出自己想要什么肉。因此产品不能把“设计多份方案”完全交给顾客自由填写，需要在确认订单页提供受控的份数和主蛋白选择。

## 2. 产品定义

### 2.1 一份是什么

一份 = 一份独立、完整、可长期作为主食的食谱方案。

- 每份都有独立的主蛋白、主碳水和蔬菜搭配；
- 每份都能单独生成自己的 DIY 制作单；
- 每份做几天、做多少量，由顾客之后在 DIY 制作单里配置，不在定制订单里选择；
- 多份之间不是同一份食谱复制多份。

### 2.2 一次买多份是什么

同一只狗，一个订单，最多 5 份不同配方的完整食谱。

- 一个订单号；
- 一次支付；
- 共享同一套狗狗档案、过敏信息、肠胃信息和备注；
- 不提供每份单独备注；
- 全部 N 份一次性交付；
- 每份可独立进入 DIY 制作单。

### 2.3 已确认的核心规则

| 项目 | 规则 |
|---|---|
| 单笔最少份数 | 1 |
| 单笔最多份数 | 5 |
| 是否同一只狗 | 是 |
| 是否不同配方 | 是 |
| 备注 | 一份共享备注，不按份拆分 |
| 主蛋白选择 | 默认营养师搭配；顾客可选择想轮换的肉类 |
| 主碳水/蔬菜 | 由营养师搭配，必须与其它份明显不同 |
| 交付 | 一次性交付全部 |
| 退款/售后 | 第一版整单处理，不按单份拆分 |
| 每份制作量 | 顾客在 DIY 制作单自行配置 |
| 成品抵扣 | 全面取消，不再发放或使用 |

## 3. 目标与非目标

### 3.1 目标

- 顾客能在一个订单里购买 1–5 份不同配方的完整食谱；
- 顾客不需要懂营养，也能选择“想轮换哪几种肉”或交给营养师；
- 价格、优惠、交付日期在确认页清晰展示；
- 营养师能在一个订单里设计并一次性交付 N 份食谱；
- 顾客能分别使用每一份食谱生成 DIY 制作单；
- 后台可以配置优惠规则和交付节奏，不需要每次改代码。

### 3.2 非目标

- 不做每份单独备注；
- 不做同一配方复制多份；
- 不做按份分批交付；
- 不做单份退款；售后受理仍以整单为对象；
- 不做固定套餐价；
- 不做超过 5 份的订单；
- 不在定制订单里询问顾客总共做多少天、冰箱容量或每份制作量。

### 3.3 失败条件

以下情况即使系统能下单，也视为产品失败：

- 顾客付了 N 份的钱，最终只收到少于 N 份；
- 多份的主蛋白、主碳水或蔬菜几乎相同，顾客觉得“只是换了点配料”；
- 系统仍按一份的交期承诺 3 个工作日，但实际有 5 份设计；
- 多份折扣由前端计算，导致支付金额与订单金额不一致；
- 顾客选中的肉类与明确过敏信息冲突，系统仍直接生成订单；
- 取消/退款时无法按整单算清折扣。

## 4. 顾客流程

### 4.1 定制页

保持现有定制流程：

- 选择狗狗；
- 健康档案；
- 过敏信息；
- 当前主食；
- 定制原因；
- 肠胃；
- 共享备注；
- 上传报告和附件。

本页不增加份数和肉类选择。

### 4.2 确认订单页

在「定制信息」之后增加「多份方案」：

1. 需要几份不同配方的食谱？
   - 1–5；
   - 默认 1；
   - 使用步进器，不允许直接输入超过 5。
2. 希望哪几种肉轮换？
   - 默认收起，显示“让营养师帮我搭配”；
   - 顾客主动展开后，可多选肉类；
   - 选中数量必须等于份数；
   - 同一种肉不能重复选；
   - 有明确过敏记录的肉类必须过滤或禁用；
   - 顾客不选时，由营养师决定 N 种不同主蛋白。

选择变化时：

- 价格明细即时更新；
- 折扣即时更新；
- 预计交付日期即时更新。

### 4.3 价格明细

展示：

- 原价 = 每份定制费 × 份数；
- 多份优惠；
- 应付金额；
- 每份均价；

金额必须以后端报价为准；前端展示不能作为最终支付依据。

### 4.4 交付

显示后端按份数计算出的交付日期：

> 预计 X 月 X 日（含）之前交付

全部 N 份在同一交付批次内交付。

### 4.5 订单详情

交付后展示 N 份食谱：

- 每份独立卡片；
- 每份显示食谱名称和已有食材信息，方便顾客区分；
- 每份有独立的“生成 DIY 制作单”入口；
- 显示“本次共交付 N 份”；
- 不出现“第 1 份已交付、第 2 份未交付”的分批状态。

## 5. 价格与优惠

### 5.1 基础价格

- 每份定制费：沿用后台「食谱定制费」；
- 默认 300 元/份；

### 5.2 默认阶梯优惠

后台可配置；建议默认值：

| 份数 | 折扣 | 原价 | 应付 | 每份均价 |
|---:|---:|---:|---:|---:|
| 1 | 原价 | 300 | 300 | 300 |
| 2 | 5% | 600 | 570 | 285 |
| 3 | 8% | 900 | 828 | 276 |
| 4 | 10% | 1200 | 1080 | 270 |
| 5 | 12% | 1500 | 1320 | 264 |

规则：

- 按达到的最高档计算整单折扣；
- 最高折扣默认 12%，后台配置上限 20%；
- 金额四舍五入到分，展示到元或两位小数；
- 订单保存价格快照，后续后台调价不影响老订单。

### 5.3 后端权威报价

新增报价能力，输入：

- 份数；
- 当前配置。

输出：

- 单价；
- 原价；
- 折扣率；
- 优惠金额；
- 应付金额；
- 预计交付日期。

下单时必须重新计算，不接受前端传金额。

### 5.4 全面取消成品抵扣

确认取消食谱定制金额可抵扣成品鲜食的功能。

- 新订单不再记录、展示或发放可抵扣额度；
- 确认页不出现「可抵扣」；
- 订单详情不出现「成品抵扣额度」；
- 后台不出现「可抵扣金额」配置；
- 成品订单不再使用定制抵扣；
- 取消订单不再恢复抵扣额度；
- 相关接口、字段、测试和文案一并清理。

目前没有真实老订单，唯一已支付订单是测试订单，因此不需要为历史顾客保留抵扣余额。测试订单也不保留抵扣权益。

## 6. Web 后台配置

### 6.1 多份购买开关

- 是否启用多份购买；
- 默认关闭，完成设计/交付能力后开启。

### 6.2 份数

- 最少 1；
- 业务硬上限固定为 5，不允许配置超过 5；
- 后台可以在 1–5 之间调低当前上限，但不能调高到 6。

### 6.3 多份优惠

配置表：

| 份数 | 折扣率 | 展示文案 |
|---:|---:|---|
| 2 | 可配 | 可配 |
| 3 | 可配 | 可配 |
| 4 | 可配 | 可配 |
| 5 | 可配 | 可配 |

校验：

- 只能配置 2–5；
- 1 份不允许折扣；
- 折扣率不能为负；
- 份数越高，折扣不能降低；
- 最高折扣不超过 20%；
- 修改只影响新订单。

### 6.4 交付配置

- 每日设计工时：可配置，默认 8 小时；
- 每份食谱默认设计工时：可配置，默认 1.6 小时（0.2 个工作日）；
- 特殊食谱可按份单独覆盖设计工时；
- 每日设计产能 = 每日设计工时 ÷ 实际每份工时，默认 8 ÷ 1.6 = 5 份/天；
- 基础交付工作日：默认 1 天（包含第一份）；
- 第 2 份起，每多一份增加 0.2 个工作日；
- 5 份订单预计 2 个工作日交付；
- 周末和公众假期跳过。

## 7. 交付与设计流程

### 7.1 设计器

一个订单可关联 N 份食谱：

- 后台订单显示“共 N 份，已设计 X 份，还差 N-X 份”；
- 营养师可逐份创建/编辑；
- 营养师人工把关每份主蛋白、主碳水和蔬菜的差异；系统不新增结构化验收字段，也不做交付拦截；
- 全部 N 份完成后才能一次性交付；
- 不允许只交付其中一部分。

### 7.2 交付

- 一次交付批次包含全部 N 份；
- 每份保留独立的内容快照；
- 订单状态在整批交付完成后变为已交付；
- 只发送一次交付通知；
- 顾客确认收到按整单处理。

### 7.3 DIY 制作单

- 每份食谱独立生成 DIY 制作单；
- 制作天数、制作量由顾客自行配置；
- 多份之间互不影响；
- 定制订单本身不记录每份制作天数。

## 7.4 多份差异：人工设计规范

多份之间的差异由营养师人工判断，不做系统级验收。

原因：

- “明显不同”包含食材差异、营养结构、适口性和顾客偏好，很难用几个字段可靠判断；
- 强行做系统校验会把复杂判断变成误拦截；
- 营养师本来就会看狗狗档案、过敏、肠胃和备注，由人来设计更合适。

内部设计规范（不是系统硬校验）：

- 每两份之间尽量做到主蛋白、主碳水、主蔬菜有明显区别；
- 顾客指定了肉类时，优先按顾客选择设计；
- 因过敏、供应或营养原因需要替换时，营养师在交付说明里写清原因；
- 设计完成后由营养师自查，必要时由负责人抽检。

系统仍然保留的校验只有：

- 份数 1–5；
- 顾客选肉数量与份数一致、不重复（这是选择器规则，不是食谱质量验收）；
- 全部 N 份完成后才能一次性交付；
- 不允许只交付其中一部分。

## 8. 产能与排期

当前系统按订单数占排期；多份后必须按“设计工时”占产能。

规则：

- 每日设计工时和每份设计工时都来自后台配置；
- 默认每份 1.6 小时（0.2 个工作日），每日 8 小时 = 5 份；
- 一个订单占用 `N × 每份实际工时`；
- 当天剩余工时不足时顺延到下一个工作日；
- 允许一个订单跨工作日占用产能，但交付仍按整单一次完成；
- 预计交付日期 = 最早可开工日 + 基础 1 个工作日 + 第 2 份起的额外工时，向上取整到工作日。

示例：

| 份数 | 设计工时 | 预计交付 |
|---:|---:|---:|
| 1 | 1.6 小时 | 1 个工作日 |
| 2 | 3.2 小时 | 2 个工作日 |
| 3 | 4.8 小时 | 2 个工作日 |
| 4 | 6.4 小时 | 2 个工作日 |
| 5 | 8 小时 | 2 个工作日 |

## 9. 数据与兼容

### 9.1 订单

新增概念字段：

- 份数；
- 顾客选择的肉类偏好（可为空，表示营养师搭配）；
- 单价；
- 原价；
- 折扣率；
- 优惠金额；
- 应付金额；
- 价格快照。

老订单：

- 份数视为 1；
- 原有金额和单份交付不受影响。

### 9.2 多份与交付

产品要求：

- 一个订单可关联多份食谱；
- 一次交付批次包含多份食谱；
- 每份食谱有独立快照和 DIY 入口；
- 第一版整单退款、整单售后。

具体表结构由实现阶段设计，但不得用“复制订单”来模拟多份，否则优惠、支付、交付和售后都会分裂。

## 10. 肉类选择与过敏

- 肉类选项来自后台可维护的字典，不在前端写死；
- 顾客选择是偏好，不是绕过过敏检查的授权；
- 选中的肉类数量必须等于份数且不重复；
- 顾客不选时，由营养师决定；
- 过敏和肠胃安全由营养师结合档案人工判断；
- 因过敏、供应或营养原因需要替换肉类时，营养师在交付说明里写清原因，不静默替换。

## 11. 退款、售后与调整

第一版：

- 未交付整单退款；
- 已交付后按整单受理售后，一个订单只有一个售后工单；
- 如果问题只涉及其中一份，可以只重交受影响的那一份，其他份不变；
- 不按单份退款；
- 免费调整沿用现有订单级次数和时间窗，不按份数叠加；
- 多份折扣在整单退款时按实付金额退回。

### 顾客如何指定食谱提售后

订单详情里每份已交付食谱都有自己的卡片，卡片上提供：

> 对这份食谱申请售后

点击后打开售后表单，自动带上：

- 订单号；
- 这份食谱的名称；
- 这份食谱的交付记录 ID。

表单只允许针对这一份提交，顾客不需要再手选订单或输入食谱名称。

如果问题涉及多份：

- 顾客可以在调整表单的“涉及食谱”选择器里勾选一份或多份；
- 默认选中刚点击的那一份，也可以追加其他份；
- 一次提交共用一个诉求说明；
- 如果几份的问题完全不同，建议分开提交；
- 后台按订单汇总查看。

免费调整次数：

- 一次提交算 1 次整单免费调整，不管这次涉及几份；
- 不按份数累加；
- 顾客提交时页面要明确显示“本次将使用 1 次免费调整”。

后台售后详情必须显示“涉及哪几份食谱”，处理人点击重新交付时只重交被选中的份，其他份不动。

## 12. 上线策略

### 第一阶段：价格与配置

- 后端报价；
- 后台优惠配置；
- 订单价格快照；
- 确认页份数与价格；
- 单元测试覆盖 1–5 份。

### 第二阶段：设计与交付

- 订单关联多份食谱；
- 设计器多份设计；
- 一次性交付；
- 订单详情多份展示；
- 每份 DIY 制作单；
- 产能按份数扣减；
- 交期按份数计算。

### 第三阶段：售后与运营

- 整单退款/售后；
- 交付通知真机闭环；
- 运营数据与异常监控。

**多份购买开关在第二阶段完成前必须保持关闭。**

## 13. 验收标准

- 1–5 份均可下单，6 份被拒绝；
- 价格、折扣全部由后端计算；
- 默认优惠档位正确，后台修改后新订单生效；
- 顾客可选 N 种不同肉，也可交给营养师；
- 过敏肉类被过滤/禁用；
- 5 份订单交期按设计工时计算，默认 2 个工作日；
- 一个订单交付 N 份，不能少交；
- 每份食谱可独立生成 DIY 制作单；
- 营养师人工自查多份之间的主蛋白、主碳水、主蔬菜差异；系统不做强制校验；
- 整单退款金额正确；
- 老订单不受影响；
- 多份开关关闭时，顾客只能买 1 份。

## 14. 实现阶段需要自行决定的事项

- 多份食谱与交付批次的表结构；
- 现有 `recipeId` 单份关系如何兼容；
- 设计器界面如何呈现多份进度；
- 现有订单详情如何兼容老订单；
- 肉类字典如何与现有食材/过敏数据衔接；
- 免费调整在订单级的具体计数方式；
- 多份交付通知的聚合方式。

## 15. 已做出的实现层判断

1. 免费调整次数仍按整单计算，不按份数叠加。
2. 有结构化过敏记录的肉类硬禁用；自由文本过敏信息提示顾客和营养师复核。
3. 若营养师发现顾客选的肉与安全冲突，必须在交付前联系顾客确认替换，不能静默替换。
4. 每日设计工时和每份设计工时均可配置；默认每份 1.6 小时，每日 5 份。
5. 售后是一个整单工单，但调整可以只重交受影响的一份或多份。
6. 顾客从每份食谱卡片进入售后，可追加选择其他份。
