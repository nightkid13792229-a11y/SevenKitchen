# 订单绑定食谱设计与待提交仓库

- 日期：2026-10-22
- 状态：业务方向已确认；数据模型与交互细节待评审
- 适用模块：admin-web 食谱设计器、后端定制订单/设计器、顾客交付链路

## 1. 为什么做

现在的定制食谱设计流程存在两个断点：

1. 从订单进入设计器后，只能新建一个空系列；如果想复用已发布食谱，需要回列表复制系列、再改参考爱犬、再发布，订单上下文容易丢失。
2. 一份或多份食谱设计完成后，仍要回订单页重新找候选、再交付；设计过程被切成多个页面。

同时，设计器现在实际承担了两类完全不同的工作：

- **产品线设计**：完善橱窗，不绑定某只狗、不绑定某个订单；
- **订单定制设计**：为某张订单、某只狗设计，最终必须交付给该订单。

这两类工作如果继续混在同一个“无上下文新建系列”流程里，后续界面和规则会越来越难维护。

目标是把订单定制设计变成一条完整闭环：

> 从订单进入 → 选择已有食谱作为模板 → 在编辑器内调整 → 加入本单待提交仓库 → N 份齐全后最终提交并交付 → 不离开编辑器完成主流程。

## 2. 目标

1. 从订单进入设计器时，参考爱犬和订单从创建开始就绑定，不依赖“复制后再换狗”。
2. 可以在配方编辑页内选择已有食谱作为模板：
   - 已上架橱窗的食谱；
   - 其他狗狗的定制食谱；
   - 当前设计器内的其它可复用食谱（后续可选）。
3. 模板只作为起点，复制为本单专属草稿，不修改原食谱。
4. 模板生命阶段与订单狗狗不匹配时，只提示，不阻止。
5. 每完成一份食谱，可以加入「本单待提交仓库」；未齐前订单不交付。
6. 第 N 份就绪后，在编辑器内完成最终提交，一次性交付并通知顾客。
7. 产品线设计与订单定制设计有明确的设计上下文，不靠 URL 临时推断。
8. 后续两种模式的界面可以分化，但共用原料编辑、营养评估、保存队列等核心能力。

## 3. 非目标

- 不做按份分批交付；仍然一次交付 N 份。
- 不做顾客在小程序里自行选择模板。
- 不做模板市场、付费模板、跨门店共享。
- 不自动修改模板的生命阶段。
- 不根据生命阶段不匹配自动阻止设计。
- 不在本设计中重做营养评估算法、原料库或 AI 建议。
- 不把定制食谱发布到公共橱窗。
- 不做历史订单的批量回填。

### 3.4 存量订单兼容

不做自动历史回填，也不把已交付历史重新挂进待提交仓库。

存量**进行中**订单分两类处理：

1. 新流程上线后新建的订单：默认使用订单设计工作台；
2. 上线前已在设计中的订单：保留旧订单页交付入口；如要继续使用新工作台，可把该订单已生成、且确认属于该狗的私密定制食谱**手工纳入**待提交仓库，不自动按候选列表计数。

这样不会因为候选列表里存在其他订单的食谱而误算已就绪份数，也不会让进行中的订单被卡死。

## 4. 两种设计上下文

### 4.1 产品线设计（CATALOG）

入口：食谱管理 → 食谱设计 → 新建设计系列。

特征：

- 不绑定订单；
- 不强制绑定狗狗；
- 可选设置一只参考爱犬，仅作设计参考，不产生订单归属；
- 发布目标为橱窗产品线；
- 没有「本单 N 份」「待提交仓库」「交付顾客」；
- 右侧面板不显示顾客定制订单信息；
- 允许更换参考爱犬；
- 发布后进入公共/内部食谱体系，遵守现有发布规则。

### 4.2 订单定制设计（ORDER）

入口：订单中心 → 定制订单 → 开始设计 / 继续设计。

特征：

- 必须绑定 `orderId`；
- 必须绑定该订单的 `dogId`；
- 参考爱犬锁定，不允许更换；
- 有本单份数、已就绪份数、待提交仓库；
- 发布目标为该订单的私密定制食谱；
- 最终由本单最后一份触发批量交付；
- 顾客只能看到最终交付的食谱，不能看到待提交仓库中的中间版本。

### 4.3 上下文必须持久化

不能只用路由参数判断模式。设计草稿/系列自身要记录：

- `designMode: CATALOG | ORDER`
- `orderId?`
- `customerDogId?`（订单模式必填）
- `orderQuantity?`（订单模式）

路由负责打开正确草稿，服务和页面根据草稿上下文做权限、锁定和操作差异。

已有历史系列迁移为 `CATALOG`，不自动挂到任何订单。

## 5. 订单设计主流程

### 5.1 从订单进入

1. 订单详情点「开始设计」/「继续设计」；
2. 打开订单绑定的设计页；
3. 顶部显示：
   - 订单号；
   - 狗狗名；
   - 本单 N 份；
   - 已就绪 X / N；
4. 参考爱犬显示为锁定状态：
   - 文案：本单已绑定 Foxy，不能更换；
   - 不显示更换入口。

### 5.1.1 订单设计工作台

「继续设计」不直接打开某个最近草稿，而是打开**订单设计工作台**。

工作台显示 N 个槽位：

- 已就绪：显示食谱名称、版本、更新时间；
- 编辑中：显示草稿名称、最后保存时间；
- 空白：显示「从已有食谱开始」/「新建空草稿」。

每个槽位打开一个独立的订单绑定设计草稿。每个草稿有自己的系列，保证 N 份可以各自命名，不会全部叫同一个系列名。

工作台内可以：

- 新增一份；
- 选择模板；
- 打开某一份继续编辑；
- 移除一份未最终提交的草稿；
- 查看 N 份进度；
- 最终提交（仅管理员，见 5.6）。

从设计器主列表进入时，订单绑定系列默认不显示，避免 Foxy 的 N 个中间系列把产品线列表铺满；需要时应从订单工作台进入。

### 5.2 选择模板

编辑器内提供「从已有食谱开始」入口，打开模板选择抽屉/弹窗，不离开页面。

模板范围：

- 已上架橱窗食谱；
- 其他狗狗的定制食谱（仅内部可见）；
- 当前订单已经就绪的食谱可以查看，但不重复复制同一个已就绪版本。

同一模板可以在同一订单里使用多次。多份订单经常需要“复制同一基础模板，分别更换主蛋白”；系统只要求最终 N 份的食谱 ID 不同，不要求模板来源不同。

模板列表显示：

- 食谱名称；
- 来源：橱窗 / 定制；
- 适用生命阶段；
- 主蛋白；
- 原料数量；
- 宏量营养摘要；
- 更新时间。

选择模板后先显示确认信息：

- 模板名称；
- 模板阶段；
- 当前狗狗阶段；
- 如不一致，显示提示，不阻止继续；
- 说明：将复制为新草稿，原食谱不会被修改。

### 5.3 生命阶段不匹配

比较：

- 模板的 `seriesLifeStage` / `scenario`；
- 订单狗狗当前有效生命阶段。

不一致时：

- 只显示黄色提示；
- 不改变模板阶段；
- 不阻止创建；
- 不阻止编辑、保存、加入待提交或最终交付；
- 提示文案说明“原料比例可能需要按当前阶段重新评估”。

如果模板没有阶段信息：

- 提示“模板未标注阶段，请自行核对”；
- 仍允许继续。

### 5.4 复制为订单草稿

确认模板后：

1. 创建一个新的订单绑定设计系列/草稿；
2. 复制模板的原料、比例、用量、烹饪/制备方式和阶段信息；
3. 记录模板来源：
   - `sourceRecipeId`
   - `sourceRecipeVersion`
   - `sourceKind: CATALOG | CUSTOM`
4. 原食谱不变；
5. 新草稿的参考爱犬固定为订单狗狗；
6. 新草稿不继承原食谱的顾客、狗狗、订单或交付关系；
7. 新草稿的默认名称为：
   - `{狗名}定制 · {模板名}`
   - 发布前可改名。

### 5.5 编辑与加入待提交

编辑现有配方明细。

完成后点：

> 加入本单待提交仓库

动作：

1. 校验配方至少有一个原料；
2. 执行现有的“发布私密定制食谱”流程，生成该订单专属的食谱版本；
3. 写入待提交记录，状态为 `READY`；
4. 订单状态保持 `IN_PROGRESS`；
5. 顾客不可见、不发送交付通知；
6. 顶部进度更新为 `已就绪 X / N`。

权限：

- 营养师/员工可以设计、编辑、加入待提交；
- 「最终提交并交付」沿用现有治理口径，仅管理员可操作；
- 员工把 N 份做到就绪后，页面显示「N/N 已就绪，等待管理员提交」，管理员在同一编辑页完成最后一步。

待提交食谱在最终提交前仍可：

- 打开继续修改；
- 修改后重新生成版本并更新待提交记录；
- 从待提交仓库移除。

### 5.6 最终提交

当 `READY` 数量等于订单份数 N 时，且当前登录人是管理员，编辑器内出现：

> 提交本单并交付

点击后：

1. 再次校验 N 份齐全且属于同一订单/同一狗狗；
2. 校验操作人是管理员；
3. 调用现有批量交付服务；
4. 一次性建立交付记录；
5. 订单转为已交付；
6. 给顾客发送一条交付通知；
7. 待提交记录转为 `DELIVERED`；
8. 页面显示交付成功状态。

最终提交必须是原子操作：

- 不允许只交付其中一部分；
- 失败时订单保持原状态，待提交仓库保留；
- 重试必须幂等，不重复发通知、不重复交付。

### 5.7 订单只有 1 份

同样走待提交仓库：

- 加入第 1 份即满足数量；
- 可直接最终提交；
- 不跳过待提交状态，保证交互一致。

### 5.8 订单页交付入口与售后

- 新流程订单：订单详情显示「去设计工作台」和 N 份进度，不再显示旧的「一次性交付」按钮；最终交付只能在编辑工作台完成。
- 旧流程/存量进行中订单：保留订单页原有交付入口，直到订单完成或手工纳入新工作台。
- 售后改稿/重新交付：仍从订单页进入，不强制走待提交仓库；重新交付不是首次 N 份交付。
- 服务端必须校验：新流程的最终提交只能消费本单待提交仓库中的 READY 食谱，不能拿同狗候选列表里的任意食谱拼单。

### 5.9 权限

- 设计、编辑、加入待提交：内部设计角色（营养师/管理员）。
- 最终提交并交付：管理员，沿用现有「交付仅管理员」规则。
- 员工完成 N 份后可以停在「等待管理员提交」；管理员可从订单或工作台完成最终提交。

## 6. 数据模型建议

### 6.1 设计系列/草稿增加上下文

在现有设计系列或草稿上增加：

- `designMode: CATALOG | ORDER`，默认 `CATALOG`
- `orderId?`
- `customerDogId?`
- `orderQuantity?`

约束：

- `ORDER` 模式必须同时有 `orderId`、`customerDogId`、`orderQuantity`；
- `CATALOG` 模式不得有 `orderId`；
- 订单模式参考爱犬必须等于 `customerDogId`。

具体放在系列还是草稿上，由实现时结合现有模型决定；原则是**草稿自身可恢复上下文**，不能只靠页面参数。

### 6.2 一份一个系列

订单绑定设计中，**一份 = 一个独立设计系列/草稿**，而不是一个系列里塞 N 个草稿。

原因：

- 私密食谱发布名当前优先取系列名；一个系列多个草稿会让顾客收到多个同名食谱；
- 产品线系列列表不应被订单中间稿淹没；
- 每份可以独立从不同模板开始、独立命名、独立移除；
- 订单工作台通过 `OrderRecipeDesign` 聚合 N 个槽位。

订单绑定系列在食谱设计主列表中默认过滤掉，只通过订单工作台访问。

### 6.3 待提交记录

新增订单待提交表，例如 `OrderRecipeDesign`：

- `id`
- `orderId`
- `dogId`
- `designDraftId`（唯一）
- `recipeId`（就绪后的私密食谱版本，唯一）
- `sourceRecipeId?`
- `sourceRecipeVersion?`
- `sourceKind?`
- `status: DRAFT | READY | DELIVERED | REMOVED`
- `stageMismatchWarning?`
- `createdBy`
- `createdAt`
- `updatedAt`

约束：

- 同一订单同一草稿只有一条有效记录；
- 同一订单不能超过订单份数；
- 最终提交只处理 `READY`；
- `DELIVERED` 只能在批量交付成功后写入。

### 6.4 模板来源

模板来源只做审计和追溯，不建立“原食谱被本单修改”的关系。

原食谱删除/下架后：

- 已复制的草稿仍可继续；
- 来源字段可保留 ID，不要求可打开；
- 页面显示“来源食谱已不可用”即可。

## 7. API 建议

### 7.1 模板搜索

`GET /recipe-designer/recipe-templates?keyword=&kind=ALL|CATALOG|CUSTOM`

返回：

- 食谱身份；
- 名称；
- 来源类型；
- 阶段；
- 主蛋白；
- 原料数；
- 宏量摘要；
- 更新时间。

只允许内部设计角色。

### 7.2 从模板创建订单草稿

`POST /recipe-designer/orders/:orderId/designs/from-template`

body:

- `sourceRecipeId`
- `sourceKind`
- `name?`

返回：

- 新设计系列 ID；
- 新草稿 ID；
- 阶段不匹配提示。

服务端必须：

- 校验订单状态允许设计；
- 校验狗狗归属；
- 校验模板可见性；
- 复制内容；
- 锁定参考爱犬；
- 不修改原食谱。

### 7.3 待提交

- `POST /recipe-designer/drafts/:draftId/order-ready`
- `POST /recipe-designer/orders/:orderId/designs/:designId/remove`
- `GET /recipe-designer/orders/:orderId/design-progress`

### 7.4 最终提交

`POST /api/v1/admin/custom-recipe/orders/:orderId/submit-designs`

管理端路由，`AdminGuard`。

服务端：

- 校验 READY 数量 = 份数；
- 校验所有 READY 记录属于本订单、本狗；
- 调用现有批量交付；
- 幂等；
- 返回交付结果。

## 8. 页面与交互

### 8.1 共用部分

- 原料库；
- 配方明细；
- 关键比例仪表；
- 宏量构成；
- 营养评估；
- 保存队列/撤销重做；
- 爱犬信息面板（按模式显示不同内容）。

### 8.2 按模式切换

| 区域 | 产品线设计 | 订单定制设计 |
|---|---|---|
| 入口 | 食谱设计主列表 | 订单设计工作台 → 某一槽位 |
| 顶部标题 | 产品线系列名 | 订单号 + 狗名 + 本单 X/N |
| 参考爱犬 | 可选、可更换 | 必选、锁定 |
| 模板入口 | 可选（后续） | 必须有 |
| 右侧面板 | 爱犬信息，无订单需求 | 爱犬信息 + 本单需求 + 交付进度 |
| 主按钮 | 发布到橱窗 | 加入待提交 / 等待管理员提交 / 提交并交付（管理员） |
| 待提交仓库 | 无 | 有 |
| 系列列表可见 | 是 | 否（通过订单工作台） |
| 交付通知 | 无 | 仅最终提交发一次 |

### 8.3 不离开页面

以下操作都应在编辑器内以抽屉/弹窗完成：

- 选择模板；
- 查看模板原料与宏量营养；
- 查看待提交仓库；
- 查看本单进度；
- 最终提交确认。

只有“返回订单/返回列表”才离开页面。

## 9. 安全与边界

1. **不自动阻止**
   - 生命阶段不匹配只提示；
   - 过敏/健康信息只展示事实，不自动阻止；
   - 由营养师判断。

2. **模板不修改原食谱**
   - 所有调整作用在复制出的订单草稿上；
   - 发布只生成该订单的私密食谱。

3. **隐私**
   - 其他狗狗的定制食谱只对内部设计角色可见；
   - 模板列表不展示原顾客手机号、微信、订单备注等隐私字段。

4. **交付边界**
   - 待提交仓库对顾客不可见；
   - 顾客只能看到最终交付的 N 份；
   - 未齐 N 份不得交付。

5. **订单取消/退款**
   - 订单取消后，待提交仓库停止可编辑；
   - 已生成但未交付的私密食谱不向顾客展示；
   - 具体清理策略由实现计划决定，但不能留下可交付状态。

## 10. 验收标准

1. 从 Foxy 订单进入订单设计工作台，看到 N 个槽位，参考爱犬锁定为 Foxy。
2. 在编辑器内可以搜索并选择「十字花科全谷物三文鱼鸡肉」。
3. 选择后生成新的订单草稿，原食谱不变；同一模板可以在两份里各用一次。
4. 如果模板阶段与 Foxy 不一致，只出现提示，仍可继续。
5. 修改后可「加入本单待提交仓库」，进度变为 1/2。
6. 此时订单未交付，顾客看不到第一份。
7. 设计第二份并加入后，进度为 2/2。
8. 点「提交本单并交付」后一次性交付 2 份，顾客收到一条通知。
9. 员工做到 N/N 时显示等待管理员提交；管理员可在同一页完成提交。
10. 从产品线设计入口新建系列时，不要求订单、不要求狗狗，界面不出现待提交仓库。
11. 订单绑定系列不出现在产品线主列表里。
12. 刷新页面后仍能恢复订单上下文、工作台槽位和待提交进度。

## 11. 失败条件

以下情况视为失败：

- 选模板后又要求用户回列表复制系列；
- 复制模板后订单上下文丢失；
- 模板阶段不匹配被硬阻止；
- 待提交仓库中的食谱提前出现在顾客端；
- N 份未齐却允许交付；
- 最终提交只交付部分食谱；
- 最终提交重复发通知；
- 产品线设计被强制绑定狗狗或订单；
- 员工可以绕过管理员直接触发首次交付；
- 同一模板被系统误判为重复而禁止使用；
- 订单工作台把同一狗的候选食谱自动算成已就绪，导致份数虚高。

## 13. 实施时由构建者决定的事项

- 上下文放在系列还是草稿；
- 待提交表的具体命名；
- 订单工作台的路由形态（独立页还是编辑器内抽屉）；
- 存量进行中订单「手工纳入已有食谱」的入口优先级；
- 模板搜索复用现有接口还是新增接口；
- 订单取消后的暂存清理策略。

已由本设计确定、不再留给实现猜测的：

- 一份一个系列；
- 同一模板可重复使用；
- 待提交时生成私密食谱；
- 最终提交仅管理员；
- 新流程订单不再走订单页首次交付；
- 存量进行中订单不自动回填。

这些不改变上述业务规则。

## 14. 已确认的实现口径

以下问题已在设计评审中定稿，实施计划不再重新猜测：

1. **权限**
   - 设计与加入待提交：内部设计角色（营养师/员工/管理员）；
   - 最终提交并交付：仅管理员，沿用现有交付治理口径；
   - 员工完成 N/N 后显示「等待管理员提交」。

2. **存量进行中订单**
   - 不做自动回填；
   - 保留旧订单页交付入口；
   - 如要切换新工作台，需手工把已确认属于该狗的私密食谱纳入待提交仓库。

3. **订单页交付入口**
   - 新流程订单不再显示旧的首次批量交付按钮；
   - 旧订单和售后重新交付保留原入口；
   - 新流程最终提交只能消费本单待提交仓库中的 READY 食谱。

4. **同一模板复用**
   - 同一模板可以在同一订单的两份里重复使用；
   - 只要求最终 N 份的食谱 ID 不同。

5. **工作台与系列**
   - 一份 = 一个独立设计系列/草稿；
   - 订单工作台用 N 个槽位聚合；
   - 订单绑定系列不出现在产品线主列表；
   - 每份可以独立命名，避免同名交付。

6. **待提交生成时机**
   - 加入待提交时生成私密定制食谱版本；
   - 最终提交只建立交付关系并发通知，不重新生成食谱。
