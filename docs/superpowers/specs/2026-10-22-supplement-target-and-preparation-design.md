# 补剂添加浓度与原料预处理设计

- 日期：2026-10-22
- 状态：业务口径已确认；待实施计划
- 范围：补剂目标营养素、添加浓度、原料预处理、制作步骤
- 暂不包含：共用上线闸门、营养报告触发、产品线/订单分支闸门、页面合并实施

## 1. 背景

现在补剂添加浓度依赖“移除补剂后是否出现营养缺口”的反向推断：

1. 评估完整配方；
2. 移除某个补剂再评估；
3. 如果某营养素从达标变成不足，或不足恶化，就认为该补剂是这个营养素的来源；
4. 用补剂实际贡献量反推每 kg 添加浓度。

这个算法无法处理纤维素粉这类功能性补剂：

- 加或不加都不会造成 FEDIAF 营养缺口；
- 宏量营养又被兜底逻辑排除；
- 因此没有目标营养素，也没有添加浓度。

手工回填 19.67g/kg 只是补数据，不是修复算法。

同时，设计器中的制备方法目前只能自动展示，不能编辑；制作步骤也不在设计器中维护，导致上线/交付时资料不完整。

## 2. 目标

1. 补剂添加时，由营养师明确选择目标营养素，不再依赖缺口推断。
2. 补剂添加浓度由当前配方和用量直接计算，作为本配方的实际添加浓度。
3. 补剂营养档案可以保存默认目标营养素，减少重复选择。
4. 原料预处理和制作步骤职责分开，均可设计器中编辑。
5. 现有补剂和食谱数据有明确兼容/迁移规则。

## 3. 非目标

- 不恢复“建议目标浓度”字段；当前配方实际添加浓度就是营养师希望达到的浓度。
- 不按缺口自动推断补剂目标。
- 不自动从历史食谱复制制备方法。
- 本期不实现共用上线闸门和报告触发；后续单独设计。
- 本期不合并食谱列表、版本管理、下架、复制等全部食谱管理能力。

## 4. 术语

### 4.1 目标营养素

补剂在本次配方中要提供的营养素，可以是一个或多个，也可以是同单位组合。

例：

- 纤维素粉 → 膳食纤维；
- 鱼肝油 → 维生素 A、维生素 D；
- 鱼油 → EPA + DHA（组合求和）。

### 4.2 添加浓度

按当前配方计算出的实际浓度：

```text
添加浓度（每 kg 配方） =
  补剂提供的目标营养素总量
  ÷ 配方总重量（g）
  × 1000
```

显示单位沿用目标营养素单位。

计算口径固定为：

- 分母使用 `assessment.totalWeightG`，即**计入评估的有效原料重量（g）**；
- 不按补剂的粒/片/平勺数量直接相加；
- 不叠加生产损耗；
- 关闭某个原料的“计入评估”，会改变分母并重新计算所有补剂浓度；界面需要提示这一影响；
- `PER_SERVING` 补剂必须能解析出有效克重；解析不出时是阻断错误，不能按 0 静默处理。

**添加浓度就是营养师在当前配方中希望达到的浓度**，不再另设“建议目标浓度”。

### 4.3 原料预处理

单个原料进入制作前的处理信息：

- 部位/规格；
- 生/熟/干/鲜状态；
- 去皮、去骨、去油、切块、打碎等；
- 称重口径。

### 4.4 制作步骤

整份食谱从原料到成品的顺序流程：

- 步骤顺序；
- 操作说明；
- 可选时间、温度、设备。

## 5. 补剂目标营养素

### 5.1 营养档案默认目标

在补剂营养档案（`NutritionFood`）上增加默认目标营养素配置。

因为补剂营养档案不会与多个采购原料共用，默认配置放在营养档案上，不放在原料—档案映射上。

结构建议：

```json
{
  "defaultSupplementTargets": [
    {
      "fieldPath": "macros.fiber",
      "label": "膳食纤维",
      "unit": "g"
    },
    {
      "fieldPath": "derived.epaDha",
      "label": "EPA+DHA",
      "unit": "mg"
    }
  ]
}
```

规则：

- 只能选择该档案中非空、数值大于 0 的字段；
- 组合不采用多个 `fieldPaths` 数组，而是复用/扩展现有**派生营养字段**：
  - `derived.epaDha = SUM(EPA, DHA)`；
  - 其它组合（如 Ca:P）同样作为派生字段；
- 一个目标始终对应一个可被现有计价、生产、交付链路消费的 `fieldPath`；
- 组合的求和、单位、标签由派生字段目录统一维护；
- 默认配置只是添加时的初始值，不锁定食谱中的选择；
- 修改食谱中的目标不反写营养档案。

### 5.2 添加补剂时的交互

#### 从食材库添加

1. 选择补剂原料；
2. 如果营养档案有默认目标，自动带出；
3. 如果没有默认目标，必须先选择目标营养素，才能完成添加；
4. 可以临时增加/删除目标，或修改组合；
5. 添加后立即显示目标营养素和当前添加浓度。

#### 从营养素贡献弹窗智能添加

1. 当前查看的营养素自动成为目标；
2. 允许追加其他目标或组合；
3. 确认添加后，补剂项保存目标定义；
4. 添加浓度按新配方总重量重新计算。

### 5.3 食谱内修改

在配方明细中，每个补剂显示：

- 目标营养素标签；
- 当前添加浓度；
- 修改目标入口；
- 用量输入。

修改用量、配方总重量或目标营养素后，添加浓度自动重算。

如果目标营养素在当前档案中为空：

- 不允许保存该目标；
- 给出明确提示；
- 不静默显示 `-`。

### 5.4 数据模型

#### 营养档案

`NutritionFood.nutritionData.meta.defaultSupplementTargets` 或独立字段，保存目标定义。

建议优先使用独立 JSON 字段，避免继续扩大 `nutritionData` 的隐式结构。

#### 设计补剂项

`DesignRecipeItem` 增加/使用：

- `supplementTargets`：目标定义数组；
- 每个目标包含：
  - `fieldPath`（单个，必须来自营养字段目录或派生字段目录）
  - `label`
  - `unit`
  - 当前计算值 `targetValuePerKg`

`targetValuePerKg` 是计算缓存，不是独立人工维护的目标。

#### 已发布食谱项

`RecipeItem.supplementTargets` 保存发布时的目标定义和计算值，供小程序/详情页显示。

### 5.5 兼容历史数据

历史补剂项可能有三种状态：

1. 有 `supplementTargets` 和 `targetValuePerKg`：保留，作为已有添加浓度；
2. 只有 `nutrientTargetKey/Value`：转换为单目标；
3. 完全没有目标：尝试使用营养档案默认目标；没有默认目标的标记为“待补目标”，由上线/交付闸门拦截。

不再用“移除后缺口”自动生成新目标。

阶段一发布行为先保持**硬阻断**：补剂没有明确目标就不允许发布/加入待提交；在共用闸门上线前，不使用“发布后再标待补”的宽松路径，避免补剂被静默丢弃、按 0 计价。

## 6. 原料预处理

### 6.1 命名

UI 统一改为：

- 单原料字段：**原料预处理**；
- 表格列：**预处理**；
- 整份食谱字段：**制作步骤**。

数据库字段可以继续使用 `preparationMethod`，避免大范围迁移；语义按新定义解释。

### 6.2 内容边界

原料预处理只回答：

- 用哪个部位/规格；
- 生/熟/干/鲜；
- 是否去皮、去骨、去油；
- 切成什么形态；
- 是否打碎/搅拌；
- 按什么状态称重。

不写入整道菜的火候、时间、顺序。

### 6.3 编辑方式

配方明细每一行增加预处理编辑：

- 默认从营养档案/原料默认值带出；
- 可从制备方法字典选择；
- 允许人工覆盖；
- 显示“自动带出/人工修改”状态；
- 修改后保存到设计草稿。

不再从历史食谱自动复制默认预处理，避免把上一道菜的工艺带错。

### 6.4 数据模型

- `DesignRecipeItem.preparationMethod`：保留，存预处理选项或文本；
- 新增 `preparationNote`：补充部位/规格等自由说明；
- 新增 `preparationSource: AUTO | MANUAL`：自动带出还是人工修改；
- 现有 `preparation_method` 长度限制需要评估并迁移（设计项 100、订单项 20），不能把长文本硬塞进原字段；
- 默认预处理来源改为**营养档案/原料档案的默认值**，不再从历史食谱复制。

## 7. 制作步骤

### 7.1 内容边界

制作步骤回答：

- 先做什么、后做什么；
- 混合/加热/冷却/分装；
- 时间、温度、设备；
- 从原料到成品的完整顺序。

### 7.2 编辑方式

设计器内增加「制作步骤」区域：

- 新增步骤；
- 编辑步骤；
- 上下移动；
- 删除步骤；
- 每步至少包含操作说明；
- 可选时间、温度、设备。

不再只在食谱管理详情页填写。

### 7.3 数据模型

建议使用结构化的步骤数组，而不是一段长文本：

```json
[
  {
    "sortOrder": 1,
    "instruction": "将所有食材按配方称重",
    "durationMinutes": null,
    "temperatureC": null,
    "equipment": null
  }
]
```

存储位置需保证：

- 设计阶段可编辑；
- 发布到正式食谱时随版本保存；
- 订单私密食谱也能带出；
- 历史 `Recipe.productionSteps` 文本可迁移为单步骤或保留只读兼容；
- 交付快照目前 `steps: string[]` 且实际写空，建议升级为 v2 结构化步骤，同时保留旧的字符串渲染兼容；已交付历史快照不自动回填。

## 8. 与后续闸门的衔接

本期只把字段和计算做对，不实现最终闸门。

后续共用闸门至少应检查：

- 每个补剂都有目标营养素；
- 补剂添加浓度 > 0；
- 每个原料都有预处理；
- 制作步骤至少一步；
- 预处理中的生熟状态与营养档案口径不矛盾。

## 9. 验收标准

1. 添加纤维素粉时，默认目标为膳食纤维；当前配方显示实际添加浓度 19.67g/kg。
2. 添加鱼肝油时，可选择维生素 A、维生素 D 或两者；两者均显示实际浓度。
3. 添加 EPA+DHA 组合时，按同单位求和显示一个组合浓度。
4. 修改补剂用量或配方总重，添加浓度自动变化。
5. 没有目标营养素的补剂不能静默保存为完整状态。
6. 营养档案可以保存默认目标，食谱内修改不反写档案。
7. 设计器中可以编辑每个原料的预处理。
8. 设计器中可以新增、排序、修改、删除制作步骤。
9. 历史有目标值的补剂继续显示；没有目标值的补剂在保存/发布/加入待提交时被明确拦截，不能静默通过。
10. 重新打开设计器、刷新、发布/交付后，目标定义和浓度保持一致。
11. 历史已发布食谱的补剂目标值按新公式完成重算，并有差异清单；已交付订单快照不被改写。

## 10. 实施边界

### 第一阶段

- 营养档案默认目标；
- 添加补剂时选择目标；
- 添加浓度计算；
- 历史已发布食谱补剂目标值的差异清单与重算迁移；
- 历史数据兼容；
- 原料预处理编辑。

### 第二阶段

- 制作步骤编辑与存储；
- 发布/私密食谱持久化；
- 共用闸门接入。

### 第三阶段

- 结构化步骤写入顾客交付页、DIY 卡片和交付快照 v2；
- 产品线/订单分支闸门；
- 页面合并；
- 报告触发交互。

## 11. 构建评审后的固定口径

1. **组合目标**
   - 一个目标只对应一个 `fieldPath`；
   - EPA+DHA 等组合用派生字段表达；
   - 不把多字段数组带进已发布 JSON，避免计价、生产、交付链路重写。

2. **添加浓度分母**
   - 使用 `assessment.totalWeightG`；
   - 关闭计入评估会改变分母，需提示；
   - 无法解析有效克重的按份补剂是阻断错误。

3. **发布行为**
   - 阶段一没有共用闸门时，补剂缺少目标仍在发布/加入待提交时硬阻断；
   - 不用“先发布、后补目标”，避免下游静默丢弃。

4. **默认目标**
   - 默认目标放在补剂营养档案；
   - 需要一次性人工确认/回填，不能假设已有档案自动有默认值。

5. **单位、校验与旧编辑器**
   - 组合使用派生字段定义的规范单位；
   - 可换算的同量纲单位统一换算后保存；
   - 无法解析的目标在保存时返回明确错误，不再静默丢弃；
   - 食谱管理详情页现有“手工填写目标值/kg”的编辑器，在设计器接管后改为只读/移除，避免两处口径并存。

6. **预处理**
   - 保留现有 `preparationMethod` 兼容，新增补充说明和来源；
   - 需要处理 100/20 字符长度限制；
   - 默认值改为营养档案/原料档案，不再从历史食谱自动复制。

7. **制作步骤**
   - 设计阶段可编辑；
   - 发布/交付沿用同一份步骤；
   - 食谱管理详情页的 productionSteps 编辑器改为只读或同步展示，避免与设计器双写；
   - 交付快照升级为结构化 v2，同时兼容旧字符串；
   - 已交付历史不回填。

## 12. 已确认的产品决策

1. **历史已发布食谱的补剂目标值：统一按新公式重算**
   - 以当前 `RecipeItem`、当前营养档案和 `assessment.totalWeightG` 重算；
   - 保留目标定义（`fieldPath` / 组合派生字段），只重算 `targetValuePerKg` 及兼容的单项值；
   - 重算影响后续订单计价和采购量，这是已接受的业务变化；
   - 已交付订单的交付快照不修改，历史顾客看到的版本保持原样；
   - 重算前产出差异清单（食谱、补剂、旧值、新值），重算后保留审计记录。

2. **制作步骤交付范围：本阶段只做设计器编辑与保存**
   - 本阶段完成结构化步骤的设计、保存、发布/私密食谱持久化；
   - 下一阶段再把结构化步骤写入顾客交付页、DIY 卡片和交付快照 v2；
   - 已交付历史快照不回填。

## 13. 留给实现的决定

- 默认目标使用独立 JSON 字段还是 `nutritionData.meta`；
- 制作步骤使用新表还是 JSON 字段；
- 历史数据迁移的批处理方式；
- 预处理字典的最终选项集合。

这些不改变本文定义的业务规则。
