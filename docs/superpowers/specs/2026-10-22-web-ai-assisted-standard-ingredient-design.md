# Web 端「AI 辅助添加标准原料」设计（阶段一：食材）

> 状态：方向已与老板确认（2026-10-22），待评审后转实施计划
> 范围：`admin-web/`（原料管理）＋ `backend/`（接口与服务）
> 前置阅读：`docs/superpowers/specs/2026-09-05-ingredient-adding-semi-auto-refactor-design.md`
> （本地营养库、匹配器、覆盖率审计、生产写入脚本的既有建设）

## 一、要解决的问题

现在新增一个食材，真实动作是这一串：找权威库词条 → 比覆盖度 → 不够就多源缝合 → 按字段规范和单位换算录进营养档案 → 建标准原料 → 找货补采购/推荐 → 建映射。全靠人把七件事在脑子里串起来。

最慢的是「从参考词条往营养档案里搬数字」，最容易错的是「单位」。老板的原话：数据要严格审查，不可以出错，特别是营养素含量和单位换算。

后台其实什么都不缺：本地营养库已有约 1.96 万条（USDA 8,263／CNF 5,993／NZFCD 2,857／MEXT 2,478／其他，截至 2026-09-05），匹配器、覆盖率审计、来源策略、AI 候选复核、营养档案与标准原料的数据结构都在。缺的是把这串能力做成**在浏览器里、一步一步、每一步都留证据**的新增流程。

## 二、目标 / 非目标 / 反目标

**目标**

1. 一个食材从输入名字到「可用于配方」，全程在一个向导里完成；AI 出方案，人做确认。
2. 每个进入营养档案的数字，都能追到：哪份来源、原始值、原始单位、换算公式、谁确认的。
3. 单位与量纲错误在入库前被确定性规则挡住；算得出来的错，不给绕过。
4. 从第一天起记录「AI 提了什么、人改了什么」，作为将来放权的依据。

**非目标**

- 不做阶段二（AI 全自动建原料），只预留。
- 不做补剂向导（第二期，同一骨架加分支）。
- 不重做营养档案编辑器、标准原料表单（复用现有组件）。
- 不改本地营养库的导入管线。

**反目标（做了就算失败）**

- 变成一个「AI 填完你闭眼点通过」的按钮。
- 为了省事，把单位换算交给大模型。
- 营养档案里留下无法追溯到来源的数字。

## 四、流程骨架

```
① 起手（口径卡 + 生熟清单）
      ↓
② 营养依据（候选 + 缝合方案）        ← 补剂在这里换成「商品标签」
      ↓
③ 档案成型（编辑器 + 证据账本）
      ↓
④ 终检（拦死 / 例外 / 提醒）
      ↓
⑤ 标准原料档案
      ↓
⑥ 收尾（一次性提交 + 主映射 + 待办）
```

食材与补剂共用 ③④⑤⑥ 的骨架，② 是唯一分叉点；分叉的是内容，不是动作。

## 五、每一站

### ① 起手

输入：原料名字（必填），可选类型、照片、备注。

AI 做：

- 出「检索口径卡」：中文规范名、英文名、可能的异名/学名、易混词（如兔肝 vs 兔肉）、默认状态（生/熟）、默认基准口径（每 100g 可食部）。
- 按类别预填「这份原料要几份档案」清单。

人做：确认或修改口径；勾选生熟清单；改类别。

规则：

- 口径卡不确认，不能进下一站。
- 类别判不准就留空让人选，不硬猜。
- 口径与清单存在向导草稿里，不落正式表。

### ② 营养依据

AI 做：按口径 + 别名 + 状态查本地库，给出排序候选；每个候选显示库、词条名、状态、必需营养素覆盖数、缺项、一句话理由。覆盖率不够时出「缝合方案」。

人做：选一个主来源；确认缝合方案（整案）。

规则：

- **只补缺，不覆盖**——主来源有的字段不许被别的来源改。
- 同一字段多源冲突（例如铁 5.5 与 12.0）**不自动裁决**，标红等人选。
- 缝合方案每一行都能点开：来源记录/原始页面、原始值、原始单位、换算公式、最终值、状态（直接采用／换算／补位／人工）。
- **熟档案不得由生档案推算**。水分一跑营养就浓缩，算出来的比没有更危险。找不到就标「待补」。
- 覆盖率不设硬门槛，但低于阈值要在 ③ 顶部持续显示「营养待补：覆盖率 xx%，缺 xx」。
- 生熟必需项缺失：页面顶部提示，可选「继续找」或「登记例外」；例外必须写理由，记录操作人。

### ③ 档案成型

复用现有营养档案编辑器，增加「证据」这一层。

- 每个字段显示：最终值、来源、状态；点开是账本（见第六节）。
- AI 只填有来源的字段；没来源就留空，不留「猜的」。
- 人可以改任何值，改动记入审计：原值 → 新值 → 谁 → 何时 →（可选）为什么。
- 营养档案的口径（每 100g / 每份）与原料的基准单位必须在这里就对齐，不留给终检兜底。

### ④ 终检

**在服务端执行**，前端只负责展示。不信任前端传来的「我检查过了」。

| 类别 | 例子 | 处理 |
|------|------|------|
| 拦死 | 单位不在该字段允许集合；来源/标签声明值与档案值不符；换算反算不闭合 | 没有绕过按钮，只能改数据 |
| 可例外 | 宏量之和 > 100g/100g；生熟必需项缺失；覆盖率过低仍要完成 | 必须写理由，记录人，事后可查 |
| 提醒 | 能量 4/9/4 反算偏差 > 10%；与同库同类词条量级差数倍；疑似填错列 | 可忽略，忽略也留痕 |

### ⑤ 标准原料档案

复用 `IngredientForm` 的字段，按类型显示。

- AI 预填有依据的字段：名称、类型、基准单位、单位展示名、CFCT 分类、可食部比例。
- 拿不准的留空并标「待补」，**不阻断保存**。
- 商品、采购、DIY 推荐不在这里（食材后置到 ⑥ 之后）。

### ⑥ 收尾

一次性提交，事务性：要么全成，要么全不成。

- 创建标准原料 + 营养档案 + 主映射（有生/熟两份时建次映射）。
- 提交后生成待办：补熟档案、补采购 SKU、评估是否进 DIY 推荐。**不自动创建商品**。
- 提交前再做一次查重（同名/同品牌同规格）。

## 六、证据与记账

两张东西，都随草稿走：

1. **字段账本**：`字段 / 最终值 / 单位 / 来源记录 / 原始值 / 原始单位 / 换算公式 / 状态 / 操作人 / 时间`。
2. **AI 提案快照**：每次 AI 出方案存一份；人改了什么另存 diff。

用途有两层：

- 审查时：任何一个数字能当场摊开给人看。
- 半年后：能算出每站的「提案被采纳率」和「改动率」，这才是决定要不要放权的数据，而不是拍脑袋。

## 七、与现有系统的关系

**复用（不重写）**

- 本地营养库与匹配能力：`backend/src/application/standard-ingredient-import/`（`source-policy`、`nutrition-audit`、状态映射与覆盖率）
- 数据模型：`NutritionFood`、`NutritionFoodMapping`、`NutritionSourceRecord`、`Ingredient`
- 前端组件：`IngredientForm.vue`、`IngredientNutritionEditor.vue`、`NutritionProfilePreview.vue`
- AI 调用与配置：`nutrition-governance` 的 provider 配置（已有候选排序与复核的提示词基础）

**新增**

- 入口：原料管理页「新增标准原料」旁加「AI 新建」→ 全屏向导页。
- 服务端草稿（一张表）：向导当前站点、口径卡、候选与缝合方案、字段账本、AI 提案快照。**草稿永远不进配方链路**。
- 接口：起手口径建议、候选与缝合方案、终检、提交。
- 提交服务：一次事务里建三样东西。

**边界**

现有「原料营养治理」工作台是给**已有原料**做候选复核的，面向批处理；新向导是**从零创建**。两者共用底层能力，但入口与交互不同。不要为了复用把工作台改造成向导。

## 八、阶段二：现在不做，留什么

- 草稿表与提案快照就是为它留的：将来「连跑」只是把每站的「等人确认」改成「自动通过 + 记录不确定项」。
- 现在不做：开关、无人值守、自动启用、批量跑。

## 九、成功标准（可验收）

1. 用「兔肝」走完一遍，全程不离开向导；营养档案里每个非空字段都能追到来源。
2. 故意把某个值改成错误单位，终检必须拦住，且页面上没有绕过按钮。
3. 故意制造宏量和 > 100，能登记例外并留下理由与操作人。
4. 中途关掉页面再打开，能回到上次的站点。
5. 提交后原料、营养档案、主映射三者齐全，且是一次性写入。
6. 记账可查：能看到这次 AI 提了什么、人改了什么。

## 十、风险

| 风险 | 应对 |
|------|------|
| 向导变成「闭眼点通过」 | 冲突不自动裁决；拦死项无绕过；证据默认展开 |
| 大模型编造数字或换算 | 换算只走确定性代码，且必须能反算；AI 只负责语义与理由 |
| 草稿污染正式数据 | 草稿独立表，永不进配方链路；提交前查重 |
| 营养待补的原料被误用 | 沿用现有 readiness 机制：待补/待验证档案在配方侧有明确提示 |
| 站点太多，人嫌烦 | ② 以下默认整案确认；只有冲突与例外才需要逐项动手 |

## 十一、留给 builder 的决定

以下我认为可以由实施者定，前提是不违反上面的硬规则：

- 向导页是新建路由还是复用现有弹窗容器。
- 草稿表的具体字段拆分（整块 JSON 还是拆列）。
- 候选与缝合方案的接口粒度（一个接口全给，还是分开）。
- 前端状态管理方式；是否用 localStorage 兜底刷新。
- 终检规则的代码组织（一个规则清单 + 执行器）。
- 组件复用程度：直接嵌 `IngredientForm` 还是抽一个只读版。
