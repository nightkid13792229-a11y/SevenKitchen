## 一、要解决的问题

### 1.1 现在的设计流程

一道产品线菜 = 一个系列（`RecipeSeries`），下面按生命阶段各有一份设计草稿（`DesignRecipe`）。编辑器的操作是：左边原料库点原料、中间配方明细调克数/预处理、右边看营养评估和爱犬信息，最后跑上线检查、发布。

现有 AI 是编辑器右上角的「AI 设计建议」四步向导（营养方案 → 食材推荐 → 审核 → 制作 SOP）。它的问题是：

- 每一步都是一次独立的模型调用，只输出 JSON 建议，人还要自己一条条搬进配方；
- 接口围着“某只狗”转（`/dogs/:dogId/...`），产品线这条不绑定狗的路走不通；
- 没有工具调用，也没有“做一步、看结果、再改”的循环；
- 它不知道整个目录里哪些原料用过了，只能凭当前草稿给建议。

所以它只能“建议”，干不了活。

### 1.2 老板提的四类耗时

1. **配原料**：要想主蛋白、内脏、碳水、蔬菜、菌藻、坚果种子怎么搭；还要判断“这套是不是跟别的菜撞了”。
2. **封面图**：要到别的模型网站生成、下载、去水印、再上传。本文不做，单独一条线。
3. **五个生命阶段**：同一道菜要出 5 个阶段版本，差异不大但都要调。本文先做“一个阶段”，五阶段以后作为独立 skill。
4. **文案**：命名、封面标题、卖点、详情、制作步骤、原料预处理。本文要做。

### 1.3 两条设计路径，先做产品线

设计器里本来就有两种来源：

- `CATALOG`：产品线食谱，进小程序橱窗，不绑定某只狗；
- `ORDER`：顾客定制食谱，按订单和狗档案设计。

本文只做 `CATALOG`。定制那条以后再做，能共用的工具/skill/会话直接抽出来复用；共用不了的部分到时候单独设计。

### 1.4 产品线货架先不做

现在系统里没有“产品线”这个字段，只有系列和健康标签。老板会另外手动划定产品线，本文不负责建货架、也不要求给现有 26 道菜分类。

在货架定下来之前，AI 的“跟谁比”一律对**全部已发布食谱**；货架定下来之后，`get_catalog_usage` 和 skill 里的差异化规则再收窄到本产品线。

## 二、目标 / 非目标 / 反目标

### 目标

1. 一句话（如“做一道低脂易消化的鸭肉成犬餐”）→ 一份可审的草稿：原料、克数、营养达标、文案齐全，一次运行内完成。
2. AI 通过工具干活；数字和门禁由代码算；人只做方向判断和签字。
3. 对话是唯一的控制面和审计记录；不新增一套与编辑器重复的仪表盘。
4. 边界可执行：不许编原料、编数字；不许发布、改价、动生产。
5. skills 和评测能沉淀经验，让 AI 越跑越准，而不是越写越长。

### 非目标

- 不做 `ORDER` 定制路径（以后复用）。
- 不做五阶段一键扩展（以后单独 skill）。
- 不做封面图生成（图片模型是另一条管线）。
- 不做产品线 CRUD / 货架定义（老板手动划）。
- 不让 AI 新建原料（缺原料就停下来问，走原料那条线）。
- 不让 AI 发布。
- 不重做营养评估、营养报告、上线检查这些现成界面。

### 反目标（做了就算失败）

- AI 自己宣布“达标”或“可以发布”。
- AI 编造原料、营养数值、引用。
- 为了“看起来完整”，在 AI 面板里再画一套达标/覆盖率/报告。
- 关掉页面就丢失对话记录。
- Agent 无步数/时长/成本上限地跑。
- 人闭眼点通过，审核变成形式。

## 三、产品形态：对话式 Agent 驱动设计器

### 3.1 一句话定位

**对话式 Agent 驱动设计器**：人用对话下指令、改方向；Agent 通过工具操作草稿；产出是一份可审的草稿，不是聊天记录。

### 3.2 抽屉

编辑器右侧一个抽屉，只有三样：

```
┌─────────────────────────────┐
│ ✳ AI 食谱助手   已完成 · 有 2 个问题   ⇥收起 ✕ │
├─────────────────────────────┤
│ 你：做一道低脂易消化的鸭肉成犬餐          │
│ ✳：先看了目录：26 道菜，鸭肉 2 道……        │
│   ├ 查原料库：菌藻类 12 个候选（工具行）    │
│   ├ 跑评估：3 项不达标（工具行）            │
│ ✳：换好了。                                 │
│   ┌ 鸭心 5% → 鸭胗 5% · 锌 −3%（改动卡） ┐ │
│   └ [撤销] [看差异]                      ┘ │
│ 你：卖点再口语一点                          │
│ ✳：「鲜鸭配南瓜，肠胃舒服，体态轻盈」 [采用] │
│ ✳：还有两件要你定：……                      │
├─────────────────────────────┤
│ [不介意，继续] [锌再加点] [换主蛋白]        │
│ 直接说，或者点上面的快捷话…            ↑   │
└─────────────────────────────┘
```

- **标题栏**：名称、状态（工作中/等你回答/已完成/中断）、停、收起。
- **对话**：助手文字、工具步骤行（一行一句人话，不展示 JSON）、改动卡、例外审批卡、交付确认卡。
- **输入框**：文字 + 少量快捷话；工作中禁用，只能按停。
- **没有**任务卡、结果卡、报告入口。目标、进度、结论都在对话里；需要看配方/评估/报告，回编辑器原有界面。

### 3.3 任务在对话里，会变

- 不设“任务卡”这种固定板块。任务就是对话里的意图，允许中途变。
- **目标一变，Agent 必须先复述再动手**：“目标改成低脂+护关节，主蛋白仍是鸭肉，我按这个重做。”复述放在对话里，不放进面板。
- Agent 内部仍要有任务状态（它自己得知道在干嘛），但那是它的事，不占界面。

### 3.4 入口

- 主入口：食谱列表「新建设计系列」→「让 AI 起草」→ 输入一句话 → 建系列 + 第一份草稿 → 进编辑器，抽屉打开，开始第一次运行。同一弹窗保留「默认阶段」选择（默认成犬 110ME）；草稿建立后 Agent 没有换阶段的工具，brief 里的阶段和草稿阶段对不上就停下来问。
- 次入口：编辑器里已有空草稿时，点「AI 助手」，抽屉提示“说一句话开始”。
- **只给营养师和管理员看**：其他角色不显示 AI 入口；后端接口同样按角色校验。
- 旧的四步向导从编辑器入口下线；代码先保留一个版本，确认无回归后再删。它的营养方案/食材推荐/SOP 提示词可以作为 skill 的素材复用。

### 3.5 运行期间的行为

- **运行中草稿只读**（前端禁用 + 后端写接口返回 409），避免 AI 和人互相覆盖。
- 要改就按「停」；停完草稿可编辑，改完再发一句话，Agent 重新读草稿后继续。
- Agent 停下来**问人**时（等待回答，不算运行中），草稿可编辑；人答完，Agent 重新读一遍再动。
- 同一份草稿同一时间只能有一个运行；运行中发新消息被拒绝。
- **撤销**：每次运行开始时给草稿拍一份快照，抽屉提供「撤销这次运行」；单条改动卡的「撤销」只在它是最后一次改动时可用，之后又改过就失效。

### 3.6 对话要落库

对话和每一步工具调用必须跟着草稿存进数据库，不能只放在浏览器内存里。它是唯一的任务记录和审计记录；关掉页面、换台电脑、服务重启后都要能接上。

关掉抽屉或刷新页面，后台运行继续；重新打开抽屉接着看。服务重启则标为中断，可以接着跑。

## 四、验收契约：什么叫做完

先划范围：本文的 Agent 只做**一个生命阶段的一份草稿**；“可发布”不在它的“完”里。产出是“可审的草稿”。

### A. 配方本身（代码逐条能查）

1. 每个原料都能落到真实、启用、营养档案已验证的原料上，编的一个都不许有。
2. 每个原料有克数，总重 > 0，参与评估的占比合计 100%。
3. **七类**：初选时按七类铺开，作为设计的起点；最终允许缺类，但缺哪类、为什么缺，必须写出来由人确认。产品线本身禁用某类的（如无谷线不要谷物），按禁用来，不算缺。
4. 评估跑在**当前内容版本**上，不是旧结果；结果跟着草稿。内容版本与报告版本对不上即视为过期，必须重跑。
5. **评估必须达标**；并且关键指标尽量离上下限留 **20%** 余量（工作标准，不是门禁）。余量不足的，交付前必须逐条列出来让人确认。
6. 补剂如果用了，必须是真实补剂；目标营养素由系统推断或人设，Agent 不自己编，缺了就用 `ask_user` 请人设。

### B. 基本信息（代码查非空，人判好坏）

系列名、封面标题、一句话卖点、详情描述、制作步骤、每个原料的预处理方式。健康标签只挂评估能支持的（代码校验）；卖点/描述里的功效只能来自评估结果或知识库条目，不许编。

字段落点：系列名/封面标题/卖点/健康标签挂在系列上；描述/制作步骤挂在草稿上；发布时复制到 `Recipe`。具体以现有 schema 为准。

### C. 必须在对话里说清楚

- 它替你做了哪些假设（如“不用乳制品、蛋”）；
- 哪些指标余量不足、哪些贴着限值；
- 哪件事它拿不准、要你定；
- 跟目录里哪道菜像、像在哪几类。

### D. 不许说“完了”、必须停下来问的情况

- 七类里有一类，库里根本没有可用原料；
- 评估怎么调都达不到，或和需求冲突（又要低脂又要高能量）；
- 需要新增原料，但库里没有；
- brief 提到的产品线/约束在系统里不存在或没定义；
- brief 里的阶段和草稿阶段不一致；
- brief 有歧义，且不同理解会做出不同的菜。

### E. 人的判断，AI 不碰

好不好吃、卖点顺不顺、品牌调性、这条线要不要、成本能不能接受。AI 可以提案、可以估、可以给理由，但最后拍板的是人。

### 4.1 “完”的三种结局

1. **达标完成**：`check_ready` PASS。
2. **带警告/例外完成**：`check_ready` PASS_WITH_WARNINGS，且人在「交付确认」卡上点了确认；或 BLOCKED，但管理员已批准例外，且留痕。
3. **没完成**：停下来问，明确说出现在草稿里有什么、卡在哪、人可以怎么接。

### 4.2 20% 余量怎么算

- 下限型（最小值 L）：值 ≥ L × 1.20。
- 上限型（最大值 U）：值 ≤ U × 0.80。
- 范围型（如钙磷比、能量密度）：先按“离最近一边的限值”算，具体规则在 P0 与营养师确认。
- 先对所有有上下限的指标计算并展示；哪些指标必须留余量，P0 与营养师定一份“关键指标清单”。
- 余量不足不是硬失败，但**不许静默通过**：`check_ready` 返回 PASS_WITH_WARNINGS，`finish_draft` 生成一张「交付确认」卡，逐条列出余量不足项；人点「确认交付」才算完。

### 4.3 例外与缺类确认

- **达标例外**（如急性胰腺炎发病期）：只有管理员能批；营养师可发起；理由必填；批准人、时间、理由写进草稿历史。Agent 只能 `request_exception`，不能自己开。
- **缺类确认**：设计者（营养师）确认即可，理由必填；不算达标例外。
- 两者的审批卡都出现在对话里，不另开页面。

### 4.4 差异化规则（已确认）

| 维度 | 规则 | 性质 |
|---|---|---|
| 主蛋白 | 同一产品线内必须不同；货架未定前，对全目录比较只作提醒，不硬拦 | 硬（有线时）/ 提醒（无线时） |
| 内脏、肌肉部位 | 尽量不同，撞了可接受 | 软 |
| 鱼类 | 尽量不同，撞了可接受 | 软 |
| 碳水、蔬菜、菌藻、坚果种子 | 最好不同，不严格卡死 | 软 |
| 水果、乳、蛋、豆 | 有差异更好，撞了不算错 | 软 |
| 食用盐、油脂 | 不比 | 不比 |
| 补剂 | 不比 | 不比 |

实现方式：`get_catalog_usage` 给证据；`check_catalog_conflicts` 按这张表标硬/软；skill 决定怎么处理——硬撞车要停下来问人，软撞车在交付说明里提一句。

## 五、工具与边界

### 5.1 边界（比清单更重要）

- **读**：整个食谱目录、标准原料库、营养库、历史使用情况。
- **写**：只有当前这一份草稿。
- **不碰**：正式食谱、发布、价格、生产、别的草稿、原料库。
- **不开“新增原料”**：库里没有就停下来问，不许编、不许自己建。
- **封面图**：不生成、不上传；只能写封面标题和卖点。已有的 `RecipeCoverImageService`（智谱生图 + COS 转存）v1 不接，后续可作为工具。
- 每一次工具调用都落日志（工具名、参数摘要、结果摘要、耗时），出问题能复盘。

### 5.2 工具清单（18 个）

#### 读（4）

| 工具 | 作用 | 关键约束 |
|---|---|---|
| `get_draft` | 当前草稿：原料、克数、占比、文案、内容版本、上次评估 | 只读 |
| `search_ingredients` | 按关键词/CFCT 分类/食材或补剂搜原料库 | 只返回真实、启用、有已验证营养档案的原料 |
| `get_ingredient` | 某个原料详情：营养、过敏原、预处理方式、价格 | 只读 |
| `get_catalog_usage` | 目录使用情况：某主蛋白/某套原料用过几次、跟哪几道重合、重合在哪几类 | 只给证据，不下结论 |

#### 写（7）

| 工具 | 作用 | 关键约束 |
|---|---|---|
| `add_ingredient` | 加一个真实原料 + 克数 | 原料 ID 真实、克数 > 0、不重复 |
| `replace_ingredient` | 换原料，保留或重算克数 | 同上 |
| `update_weight` | 改克数 | 克数 > 0 |
| `remove_ingredient` | 删原料 | 不能删到总重 ≤ 0 |
| `set_preparation` | 设预处理方式和备注 | 预处理方式必须在受控列表或可创建 |
| `set_copy` | 写系列名、封面标题、卖点、描述、健康标签 | 字段白名单、长度校验、健康标签必须是标签库里启用且合规的 |
| `set_production_steps` | 写结构化制作步骤 | 结构校验 |

每个写工具返回“改完后的状态 + 哪些结果过期了”（如“评估已过期”），让 Agent 立刻知道后果。参数不对当场报错，错误原样还给模型，它自己改。

#### 查（4）

| 工具 | 作用 | 关键约束 |
|---|---|---|
| `run_assessment` | 在当前版本上跑评估：达标/不足/超标/缺数据、离限值余量 | 由现有评估引擎算，Agent 不许自己算 |
| `check_coverage` | 七类覆盖情况 + 缺类原因 | 只读映射表，不改草稿 |
| `check_catalog_conflicts` | 跟目录比，按硬/软规则返回“跟谁像、像在哪” | 只给证据，不下结论 |
| `check_ready` | 把 A/B 合成一份“能不能交付”的检查单（含已批例外、缺类确认） | 返回 PASS / PASS_WITH_WARNINGS / BLOCKED + 逐条原因 |

#### 问 / 收尾（3）

| 工具 | 作用 | 关键约束 |
|---|---|---|
| `ask_user` | 停下来问，最多 2 个问题 + 选项 | 一次只问一件事；问完挂起等人 |
| `request_exception` | 申请例外（达标不了、要缺类），等人批 | 只能申请，不能自批；理由必填 |
| `finish_draft` | 交付：生成「交付确认」卡（有警告时逐条列出），人点确认才算完 | `check_ready` BLOCKED 且无已批例外时拒绝生成 |

### 5.3 设计原则

- **工具是动词，不是通用 CRUD。** 只给一个“改草稿”的万能工具，它什么都能改，校验也没法做；拆成动词，每个都能卡住。
- **工具清单就是权限清单。** 没列进来的，它做不到。
- **报错是数据，不是异常。** 校验失败要把原因原样还给模型，这是它能自纠的前提。
- **三个先不开**：新增原料、发布、改价。

### 5.4 七类判定映射（已确认）

一份原料只归一类；先判内脏，再按 CFCT 分类。

| 七类 | 判定 | 依据 |
|---|---|---|
| 内脏 | 营养库分类 = `ORGAN`，或名称命中内脏词表（肝/心/胗/肾/肚/肠/肺/脾/脑/胰/腺/腰）**且 CFCT 属于畜/禽/水产**；排除香肠/腊肠这类加工肉 | 营养库分类 + 词表；**优先于蛋白** |
| 肌肉蛋白 | CFCT = 畜肉类及制品 / 禽肉类及制品 / 水产类，且未被判成内脏 | `properties.cfct_class` |
| 碳水 | CFCT = 谷类及制品 / 薯类及制品 | 同上 |
| 蔬菜 | CFCT = 蔬菜类及制品（**南瓜算蔬菜**） | 同上 |
| 菌藻 | CFCT = 菌藻类 | 同上 |
| 坚果种子 | CFCT = 坚果种子类 | 同上 |
| 油脂 | CFCT = 油脂类 | 同上 |
| 可选 · 水果 | CFCT = 水果类及制品 | 同上 |
| 可选 · 乳 | CFCT = 乳类及制品 | 同上 |
| 可选 · 蛋 | CFCT = 蛋类及制品 | 同上 |
| 可选 · 豆 | CFCT = 干豆类及制品 | 同上 |
| 可选 · 调味 | CFCT = 调味品类 | 同上 |
| 补剂 | 原料类型 = `SUPPLEMENT`，不参与七类 | `Ingredient.type` |
| 未归类 | 以上都不命中 | 列出来，不静默放过 |

边界：

- 蛋、乳不算主蛋白（主蛋白只认畜/禽/水产）。
- 鱼油算油脂，不算蛋白；鱼/虾/贝算蛋白。
- 鸭胗算内脏（业务口径，不按解剖学）。
- 带骨/软骨现在会落到“蛋白”，严格说不是肌肉；先这样跑，遇到再补“钙源”可选类。
- 映射表是代码配置，不是 AI 提示词；`check_coverage` 只读它。

### 5.5 文案合规（v1 能落地的部分）

- **禁用词表**：沿用 `recipe-copywriting-compliance.ts` 的 `FORBIDDEN_CLAIM_PATTERNS`（已有，支持环境变量追加），`set_copy` 命中即拒绝。
- **健康标签**：v1 只允许有明确举证方式的三个标签——低脂按数值门槛、易消化需举证、单一动物蛋白按原料判定（已确认）；其余标签先不开放给 AI，人工挂。
- **“每句话可倒查”的完全体**留到 P4；v1 先挡住最危险的表述。

## 六、循环与失败处理

### 6.1 一次运行

1. 人发一句话（或点「开始起草」），后端开一次运行，状态 `RUNNING`。
2. 模型每一步做一个决定，调一个工具；工具执行完把结果还给模型；模型再决定下一步。
3. 每一步往对话里写一行给人看的话（“查了菌藻类，12 个候选”），不展示原始 JSON；需要时展开看细节。
4. 结束只有五种：交付、停下来问、卡住、超限、人按停。
5. 运行结束后草稿可编辑；人再发一句话就是新的一次运行，Agent 先 `get_draft` 重新读。

### 6.2 状态

`RUNNING`（干活中，草稿只读）/ `WAITING_USER`（等回答，草稿可编辑）/ `COMPLETED` / `STOPPED`（人按停）/ `FAILED` / `INTERRUPTED`（服务重启）。

### 6.3 上限（先这么定，跑一段再调）

- 最多 30 次工具调用；
- 最多 6 分钟；
- 同一个工具、同样的错，最多重试 2 次；
- 模型调用失败重试 1 次；
- 连续 3 次同一个错 → 停。

超限即停，保留草稿，告诉人卡在哪一步、为什么。

### 6.4 失败怎么处理

- 工具报错（原料不存在、克数非法）→ 原样还模型，它自己改。
- 模型调用失败（超时/5xx）→ 重试一次；还失败就停。
- 评估怎么调都达不到 → `request_exception` 问人，或停。
- 停下来时必须说清楚：草稿里现在有什么、卡在哪、人可以怎么接。
- 不许“假装完成”：没跑评估、没跑 `check_ready`，不能说交付。

### 6.5 技术前提

- **工具调用客户端**：现有 `deepseek-chat.ts` 只做“一次性出 JSON”（`response_format: json_object`），要新增支持 `tools` / 多轮 tool 消息的客户端。P0 先做一个 spike，确认当前配置的模型支持 function calling；不支持就换模型或换供应商。
- **工具调用兜底**：如果当前模型不支持 `tools`，用 JSON 动作协议兜底（模型输出 `{tool, args}`，后端执行，把结果作为文本回灌）；能力一样，只是多轮工具消息要靠文本模拟。
- **没有长连接**：项目现在没有 SSE/WebSocket。第一版用**轮询**（1.5 秒一次）拿新消息和状态，不上 WebSocket。
- **会话落库**：新增会话表和消息表，跟草稿绑；消息按序号增量拉取。
- **写锁**：运行中后端拒绝草稿写接口（409），不只靠前端禁用。
- **重启恢复**：服务重启时把 `RUNNING` 标记为 `INTERRUPTED`；人可以接着跑（新一次运行从现有草稿和对话继续）。
- **用量**：每次运行的 token 用量记在会话上；上限先不设死，用日志观察。

### 6.6 上下文怎么拼

- **系统提示**：角色与边界、当前 skill（含版本）、七类映射、差异化规则、验收契约、输出要求。
- **启动上下文**：草稿摘要（系列/阶段/现有原料/文案状态）、紧凑目录摘要（菜名/主蛋白/健康标签）。
- **每步**：完整对话 + 最近工具结果；工具结果只给摘要和 ID，不给整份营养 JSON。
- **长对话**：超过 N 轮时，把较早的工具结果折叠成摘要，控制 token。
- **留痕**：每次运行记下 skill 版本和 token 用量。

## 七、Skills 与评测

### 7.1 skill 是什么

工具是手柄，skill 是操作规程：先干什么、后干什么、什么情况停下来、遇到什么坑怎么处理。它不给 AI 加权限，也绕不过工具和闸门。它比提示词多三样东西：检查清单、工具顺序、可测试的例子。

### 7.2 第一版只装一个 skill：起草一道产品线食谱

内容至少包括：

- **适用**：`CATALOG` 新建草稿、一个生命阶段。
- **步骤**：解析 brief → 查目录定差异化 → 按七类定骨架 → 落草稿 → 跑评估、不达标就调 → 写文案 → 跑 `check_ready` → 交付或提问。
- **判断规则**：硬撞车/软撞车（见 4.4）、20% 余量、七类覆盖、什么时候申请例外。
- **停下来问的时机**：缺类没原料、目标冲突、需要例外、brief 有歧义且影响结果。
- **常见坑**：南瓜算蔬菜、鸭胗算内脏、鱼油算油脂、蛋乳不算主蛋白、补剂不进七类。
- **例子**：一好一坏两个完整例子。

“改一版”不单独做 skill，它就是这个循环本身。五阶段扩展以后另装一个 skill。

### 7.3 skill 怎么长出来

靠“人改了什么”。每次 AI 交付后，把它改的每一处记下来：换了哪个原料、改了哪个克数、动了哪句文案。定期看这些改动：

- 反复出现的同类改动 → 写成 skill 里的一条规则；
- 只出现一次的 → 不进 skill，留在对话里。

要三样东西：

1. 交付时给草稿拍快照（AI 版）；
2. 人改完、发布时，跟快照做 diff，存下来；
3. 每个 skill 有版本号，每次运行记下用的是哪版。

没有这份改动记录，skills 只会越写越长，不会越写越准。

### 7.4 评测

- **测试集**：12 条测试 brief + 1 个环境构造（某类没有可用原料）。见附录 A。
- **指标**：`check_ready` 一次通过率、人工改了几处（来自快照 diff）、问了几次、几次例外、端到端时长、token 用量、失败原因分类。
- **质量**：好不好吃、文案顺不顺，抽几条人工看，不做自动化评分。
- **跑法**：独立测试库（不碰生产），预置原料库和目录快照；批量跑，草稿、日志、指标都存下来。
- **频次**：每次改 skill 都跑；调参期每周跑一次。

### 7.5 把一次人工修改变成规则

1. 看 diff，把同类改动聚成一组；
2. 判断是工具问题、skill 规则问题、数据问题，还是一次性偏好；
3. 工具/数据问题 → 修工具或补数据；
4. 规则问题 → 改 skill，升版本；
5. 如果是新出现的模式 → 往测试集里加一条 brief；
6. 重跑评测，确认没变坏。

- 工具层：把现有 service 能力包装成 Agent 可调用的函数，带校验和日志。

- 评测脚本：批量跑 12 条 brief，出指标。
- 抽屉 UI：标题栏 + 对话 + 输入框，轮询刷新。

### 不碰

- 发布服务、定价、采购、生产、库存。
- 小程序。
- `ORDER` 定制路径（以后单独设计）。
- 现有营养评估/报告/上线检查的计算逻辑。

## 十、已确认的决定

2026-10-24 老板确认：

1. **健康标签白名单**：v1 只开放“低脂 / 易消化 / 单一动物蛋白”三个有明确举证方式的标签；其余人工挂。
2. **谁能用 AI 起草**：营养师 + 管理员；其他角色看不到入口。
3. **20% 范围型余量**：离最近一边的限值 20%；营养师后续可调。

“体重管理”“低敏”“抗炎”等已被合规删除，不许再用（见 `prisma/apply-health-tag-compliance.ts`）。

### 10.1 本设计已定下的判断（builder 可照此做）

1. 首次运行失败：保留系列和草稿，标“AI 未完成”，人可续跑或删除。
2. 会话/消息保留 180 天（可配）；发布后的快照长期保留。
3. 成本：先只记录 token，不设硬上限；配置项留好。
4. skill 存仓库，随代码评审、带版本号。
5. 例外被驳回：Agent 不重复申请同一个例外，改为调整配方或停下来问。
6. 评测：独立测试库 + 固定原料库/目录快照；不碰生产。
7. 并发：沿用现有 provider 配置的 `maxConcurrency`；同一草稿串行。
8. 交付确认卡、例外审批卡的“确认/批准”走 UI 端点，Agent 不能代签。
9. 人在等待回答时改了草稿：Agent 恢复时先 `get_draft`，在对话里说一句“我看到你改了 X”，再继续。
10. 模型工具调用：P0 spike 决定用 `tools` 还是 JSON 动作兜底；这是工程验证，不需要业务拍板。
