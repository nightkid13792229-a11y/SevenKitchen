# 定制食谱 · 食谱调整页需求与设计

- 日期：2026-10-24（2026-10-25 修订）
- 状态：待老板审阅（未开发）
- 范围：小程序顾客端「食谱调整」页；后台订单中心/食谱设计器衔接放第二阶段

---

## 1. 为什么做

现在的「售后与问题反馈」页混了四件事：问问题、调整食谱、其他意见、退款。实际顾客只有两类需求：

- **问问题 / 其他意见**：企业微信找 Seven爸爸更快，不需要系统表单；
- **调整食谱**：需要留痕、按次计数、能看结果、后台能处理并重新交付。

退款是订单级的钱的事，和“调整食谱”不是同一个对象。所以：

- 当前页收窄成**只做食谱调整**；
- 退款以后单独开页；
- 后台仍共用同一张售后单（`CustomRecipeAftersale`），不新建一套数据。

## 2. 目标

1. 顾客从交付卡片进入后，能一眼看到“还能不能调、还能调几次、之前调过什么、当前这条什么状态”。
2. 一次可以选多份食谱，但只算 1 次调整；一次只能有一条未处理完的调整。
3. 顾客提交调整需求（文字必填 + 照片/文档可选），后台订单中心能看到，并进入食谱设计器处理。
4. 撤销本次提交后，调整次数退回；商家驳回不消耗次数。
5. 页面不展示历史进度时间轴，只展示每次请求的提交时间、内容、状态和结果说明。

## 3. 非目标

- 本期不做退款申请页（另立需求）。
- 本期不做“补充提交”：提交后想补充，走企业微信。
- 本期不做状态变更历史/客服留言时间轴。
- 本期不做“问个问题 / 其他意见”类型；这两类走企业微信。
- 本期不做后台设计器里的需求面板（第二阶段）。

## 4. 已确认的规则

| 规则 | 结论 |
|---|---|
| 一次能提几条 | 一条。当前调整未处理完（待受理/已受理/处理中）时，不能提下一条，即使次数还有 |
| 一次能选几份 | 多份订单可以一次选多份；**一次提交只算 1 次调整**，不按份数叠加 |
| 补充提交 | 不做。想补充/修改，走企业微信找 Seven爸爸 |
| 撤销 | 只在“待受理”时可撤；撤销后这条不算次数，次数退回 |
| 商家驳回 | 不算一次调整；历史已驳回的也不占次数 |
| 撤销后的状态 | 显示“已撤销”，不是“未受理” |
| 进度展示 | 只显示提交时间、提交内容、当前状态；不展开历史 |
| 处理完成 | 状态显示“已交付”；显示后台填写的“调整总结”和最新食谱入口 |
| 提交门禁 | **只要求文字非空**；附件可选，不作门禁 |
| 退款 | 本期不处理退款页；入口先保留（见 §9） |

## 5. 页面结构（从上到下）

### 5.1 导航与标题

- 页面标题：**食谱调整**
- 不再出现“售后与问题反馈”字样。

### 5.2 额度条

固定在最上面，两个数字：

> 售后窗口期还剩 **N** 天　·　调整次数还剩 **N** 次

- 窗口按交付时间起算，后端 `windowDaysLeft`；向上取整。
- 次数按后端 `freeRevisionsLeft`；撤销和商家驳回都不计数。
- 窗口已过或次数为 0 时，数字照常显示，下面给一句原因，表单不出现。

### 5.3 食谱调整记录

- 标题：**食谱调整记录**
- 不写“最新一条在最上面”，顺序本身已经说明。
- 按提交时间**从近到远**排。
- 每条请求一张卡：
  1. **提交时间**：明确写“提交时间 2026-10-18 09:12”，不是裸日期。
  2. **涉及食谱**（多份订单时）：如“涉及 2 份：鸡肉南瓜、鸭肉西兰花”。
  3. **提交内容**：超过 4 行或 120 字自动折叠，底部“展开/收起”。
  4. **当前状态**：待受理 / 已受理 / 处理中 / 已交付 / 已撤销 / 未受理
  5. **结果说明**：
     - 未受理：显示后台的驳回原因；
     - 已交付：显示后台写的“调整总结”（`handleNote`），并给“查看最新食谱”入口；
     - 其他状态不额外写说明。
- 处理中的卡片只显示状态，不写“如需补充请找 Seven爸爸”。
- 已交付的卡片不写“已重新交付一版”这类通用提示，只显示调整总结 + 最新食谱入口。
- 不再显示时间轴、受理时间、处理时间、历史进度。
- 空态：`还没有提交过调整需求`。
- 卡片不提供“补充”“再次编辑”；已交付后要再调，用下面的表单重新提交一条（受次数和窗口限制）。

### 5.4 调整哪个食谱？（大容器）

把“选食谱 → 看摘要 → 写需求”装进**一个容器**，不再分成三个散落的板块。

```
┌─ 调整哪个食谱？ ─────────────────────┐
│  [鸡肉南瓜 ●] [鸭肉西兰花]  ← Tab     │
│  ─────────────────────────           │
│  食谱摘要（当前这份）                  │
│  ─────────────────────────           │
│  想怎么调整（当前这份的输入框 + 附件）  │
└──────────────────────────────────────┘
```

**多份订单**

- 大标题：**调整哪个食谱？**
- 标题下方一排 Tab，列当前批次的所有食谱；默认选中进入时那张卡对应的食谱；从消息/订单列表/客服进来、没有 `recipeId` 时默认第一份。
- 点 Tab 同时切换**食谱摘要**和**想怎么调整**；每份的输入框和附件各自独立，切回来不丢草稿。
- **没有单独的“调整份数”弹窗**：Tab 本身就是选择。哪几份写了文字，就提交哪几份；没写的 Tab 不提交。
- Tab 上有内容的打一个小圆点/勾；底部提交按钮显示“提交调整（N 份）”。
- 至少一份的文字非空才能提交；附件不作门禁。
- 只写一份就只提交一份；写多份也只算 **1 次**调整。
- 某份只传了附件、没写文字：这份不提交，提示顾客“写一句这份想怎么调，或删掉附件”。

**只有一份食谱**

- 不显示“调整哪个食谱？”和 Tab；直接显示这份的摘要 + 表单，避免一个 Tab 还要点。

**容器里的两块**

1. **食谱摘要**（当前 Tab）
   - 食材名 + 占比（不显示部位/预处理、制备方法、克数）。
   - 补剂：营养素名 + 每公斤食材添加量（不显示产品名）。
   - 宏量营养：蛋白质、脂肪、灰分、纤维、碳水，全部标注 **DM（干物质占比）**；不显示水分、钙磷比、能量。
   - DM 折算：`DM = 100 - 水分`；`某营养素 DM% = 该营养素 as-fed% ÷ DM × 100`；缺项显示“—”。
   - 只读。
2. **想怎么调整**（当前 Tab）
   - 大文本框，占位：`比如：鸡肉想换成鸭肉、某样食材减少一点、份量想调整……`
   - **每份独立的附件**：切到哪份，就显示哪份的照片/文档。
   - 只保留一个“**添加附件**”按钮，底部弹窗选“照片”或“文档”；照片缩略图，文档文件名/大小；可新增、可删除。
   - **删除必须同时删 COS 存储桶里的文件**，不能只删页面链接。
   - 底部不再写“支持照片和 PDF/Word”“提交后由 Seven爸爸看一下”这些提示；格式提示放弹窗选项里。

**视觉**

- 一个浅色大容器，圆角/边框；大标题、Tab、摘要、表单都在里面，用细分隔线分开。
- 摘要和表单不再各自套一张重卡片，避免“卡片里还有卡片”。
- “食谱调整记录”仍在大容器上方，是独立板块。

### 5.5 提交后的状态

| 情况 | 页面 | 底部固定栏 |
|---|---|---|
| 没有未处理完的调整，且窗口/次数可用 | 历史卡 + 大容器（Tab + 摘要 + 表单） | 企业微信 + **提交调整（N 份）** |
| 最新一条是“待受理” | 历史卡 + 大容器（Tab + 摘要，表单换成锁定说明） | 企业微信 + **撤销本次提交** |
| 最新一条是“已受理/处理中” | 历史卡 + 大容器（Tab + 摘要，表单换成锁定说明） | 企业微信 + 处理中（不可点） |
| 最新一条是“已交付” | 历史卡 + 大容器；窗口/次数可用则显示表单 | 企业微信 + **提交调整（N 份）** |
| 窗口已过 / 次数为 0 | 历史卡 + 大容器（只读摘要）；不显示表单，显示原因 | 企业微信 |
| 没有提交过 | 空态 + 大容器（Tab + 摘要 + 表单） | 企业微信 + **提交调整（N 份）** |

- 固定栏最多两颗：企业微信 + 当前主动作（提交或撤销）。不做四颗并排。
- “撤销本次提交”只在 `canCancel`（待受理）时出现；撤销成功后刷新，次数退回，表单重新出现。
- 待受理/处理中时，大容器仍可切换 Tab 看摘要；只是表单换成“当前有一条正在处理”。

## 6. 入口与按钮文案

入口位置不变：**定制订单详情 → 你的定制食谱交付卡片**。

按钮文案：

- 没有未处理完的调整 → **调整食谱**
- 有未处理完的调整 → **查看进展**

“已交付”的历史记录不影响按钮：只要窗口/次数允许，仍显示“调整食谱”，可再提一条。

## 7. 状态与数据映射

| 库状态 | 顾客端显示 |
|---|---|
| `PENDING` | 待受理 |
| `ACCEPTED` | 已受理 |
| `PROCESSING` | 处理中 |
| `RESOLVED` | **已交付**（仅本页；后台仍叫已解决） |
| `REJECTED` + `rejectReason` 含“撤回” | **已撤销** |
| `REJECTED` + 其他原因 | 未受理 |

现有字段已经够用：

- `status`、`description`、`photos`、`createdAt`、`canCancel`、`rejectReason`、`handleNote`；
- 额度：`windowDaysLeft`、`freeRevisionsLeft`、`hasOpen`、`canSubmit`、`reason`；
- 撤回后不计数：后端 `getQuota` 已排除 `rejectReason` 含“撤回”的行；
- 多份请求：`deliveryItemIds` / `recipeRequests` / `describeSelection` 已存在；
- 每份附件：`recipeRequests` 现在只有 `{deliveryItemId, description}`，需要扩展成 `{deliveryItemId, description, photos: string[]}`；这是 JSON 字段，不用建表。旧记录没有 `photos` 时回退到顶层 `photos`（整单共用）并标注“旧记录附件”。

需要改三处：

1. **顾客端状态中文**：`listForCustomer` 加 `customerStatusLabel`，把“顾客撤回”的 `REJECTED` 显示成“已撤销”，不显示成“未受理”。
2. **额度只统计调整类**：
   - `getQuota` 的 `usedCount` / `hasOpen` 只统计 `type = 'ADJUST_RECIPE'`；
   - `usedCount` 排除 `REJECTED`（顾客撤回 + 商家驳回都不算次数）；
   - `listForCustomer` 只返回 `type = 'ADJUST_RECIPE'`，否则旧的问题/退款单会混进历史。
3. **多份选择/每份附件**：Tab 切换即选择；提交时把有文字的食谱放进 `deliveryItemIds` 和 `recipeRequests`，每份带自己的 `photos`；顶层 `photos` 取并集，兼容后台和旧页面。一次提交仍算 1 次。

## 8. 接口与数据流

- 读额度：`GET /custom-recipe/orders/:orderId/aftersale/quota`（或现有 quota 接口）
- 读列表：`GET /custom-recipe/orders/:orderId/aftersales`
- 提交：`POST /custom-recipe/orders/:orderId/aftersale`
  - `type: 'ADJUST_RECIPE'`
  - `description`（必填，非空；传一段整单汇总，后台/顾客以 `recipeRequests` 里的每份说明为准）
  - `photos: string[]`（可选；所有份的附件并集，兼容旧展示）
  - `deliveryItemIds: string[]`（本次写了文字的份）
  - `recipeRequests: [{ deliveryItemId, description, photos: string[] }]`（每份的说明和附件）
- 撤销：现有 `POST /custom-recipe/aftersales/:id/cancel`
- 附件上传：现有 `POST /custom-recipe/upload-attachment`；**返回值增加附件 `id`**，供删除使用。上传时带上 `deliveryItemId`（当前 Tab），后台把附件记录挂到这一份的草稿；提交时按份写进 `recipeRequests[].photos`。
- 附件删除（新增）：`DELETE /custom-recipe/attachments/:id`
  - 校验附件属于当前顾客的订单；
  - 先删 COS 对象，再删 `CustomRecipeAttachment` 记录；
  - COS 删除失败则不删记录、返回失败，让顾客重试，避免“页面删了、桶里还在”；
  - 记录删除失败但 COS 已删：记录保留并写日志，后续清理。
  - 后台现有 `deleteAttachment` 也只删数据库记录、不删 COS；本次一并改成先删 COS，避免后台删了、桶里还在。
- 调整总结：后台 `resolve` 时 `handleNote` 已必填；顾客历史卡直接显示。
- 最新食谱入口：优先打开该订单最新的交付页（`/pages/custom-recipe/delivery?orderId=...&recipeId=...`）；多份订单可落到订单详情，让顾客自己选哪一份；没有可打开的交付时隐藏入口。
- 已交付关联：`CustomRecipeAftersale.linkedDeliveryId` 已存在，但本期不强制绑定，页面也不展示版本号。后台“处理完成”即 `RESOLVED`，顾客页显示“已交付”；如果要保证“已交付”一定对应一版新食谱，需要后台把“处理完成”和“重新交付”绑在一起，放第二阶段。

## 9. 退款入口

- 本期**不隐藏、不改**订单详情底栏的“退款申请”按钮（小程序还没上生产）。
- 但本期售后页会被改造成“食谱调整”，所以 `scene=refund` 进来时只显示一个临时占位：
  - 标题“退款申请”；
  - 一句“退款申请页正在制作中，请联系 Seven爸爸”；
  - 企业微信入口。
- 等退款页做好后，用独立页面替换这个占位。

## 10. 后台衔接

### 第一阶段（跟随本页）

- 订单中心 → 该订单 → 售后申请：能看到 `ADJUST_RECIPE` 的提交内容、**每份食谱各自的说明和附件**、提交时间、状态。
- 后台“处理完成”弹窗已经有必填的“给顾客的处理说明”（`handleNote`），顾客历史卡直接显示；文案在后台可改成“调整总结”。
- 商家驳回不消耗调整次数（后端额度统计调整）。

### 第二阶段（后续，已单独记录）

见 `docs/plans/2026-10-24-custom-recipe-adjustment-phase2-backlog.md`。核心三件：

- 售后申请详情加“进入食谱设计器”入口；
- 食谱设计器展示“顾客调整需求”和附件；
- 营养师改完后交付新版本，售后单写入 `linkedDeliveryId` 并置为 `RESOLVED`；
- 已交付卡的“调整总结”与“查看最新食谱”必须对应这次新交付，不能只把状态改成已交付。

> 已交付总结/最新食谱入口本期 UI 就做；后台把 `handleNote` 和 `linkedDeliveryId` 真正串起来放第二阶段。

## 11. 验收标准

1. 从交付卡片进入，按钮文案按“有/没有未处理完的调整”显示“查看进展/调整食谱”。
2. 页面只显示一个类型：食谱调整；没有“问个问题/其他意见/退款”选项。
3. 当前有一条未处理完的调整时，表单不出现，底部不能再次提交。
4. 多份订单能一次选多份，提交后只扣 1 次；历史卡显示“涉及 N 份”。
5. 提交后，历史卡显示“提交时间”、内容、状态“待受理”。
6. 待受理时可撤销；撤销后状态“已撤销”，次数恢复，表单重新出现。
7. 已受理/处理中不可撤销，卡片只显示状态。
8. 商家驳回的请求不占次数，显示“未受理”+驳回原因。
9. 已交付显示“已交付”+后台填写的“调整总结”+“查看最新食谱”入口。
10. 长内容自动折叠，可展开/收起。
11. 食谱摘要显示食材、补剂营养素、5 项 DM 宏量营养；不显示食材总数、部位/预处理、产品名、克数、钙磷比、能量。
12. “调整哪个食谱？”大容器把 Tab、摘要、表单装在一起；点 Tab 同时切换摘要和表单，切回来草稿还在。
13. 多份订单哪几份写了文字就提交哪几份；只写一份算 1 次，写多份也算 1 次；Tab 有内容标记；底部按钮显示“提交调整（N 份）”。
14. 每份附件独立：切到哪份显示哪份的照片/文档；删除附件会同时删 COS 文件；旧记录没有每份附件时回退到整单附件并标注。
15. 所有 Tab 都为空时不能提交；有任意一份文字非空即可提交；附件可选；附件可新增、预览、删除；删除会同时删 COS 文件。
16. 附件上传弹窗从底部出现，选项里写清照片/文档格式。
17. 只有一份食谱时不显示“调整哪个食谱？”和 Tab。
18. 退款入口本期不隐藏；`scene=refund` 只显示临时占位。
