# 定制食谱 · 食谱调整页需求与设计

- 日期：2026-10-24
- 状态：需求评审中（未开发）
- 范围：小程序顾客端「食谱调整」页；后台订单中心/食谱设计器的衔接列为第二阶段

---

## 1. 为什么做

现在的「售后与问题反馈」页混了四件事：问问题、调整食谱、其他意见、退款。实际顾客只有两类需求：

- **问问题 / 其他意见**：企业微信找 Seven爸爸更快，不需要系统表单；
- **调整食谱**：需要留痕、按次计数、能看进度、后台能处理并重新交付。

退款是订单级的钱的事，和“调整某一份食谱”不是同一个对象。所以：

- 把当前页收窄成**只做食谱调整**；
- 退款以后单独开页；
- 后台仍然共用同一张售后单（`CustomRecipeAftersale`），不新建一套数据。

## 2. 目标

1. 顾客从交付卡片进入后，能一眼看到“还能不能调、还能调几次、当前这条到哪一步了”。
2. 顾客提交调整需求（文字 + 照片/文档），后台在订单中心的售后申请里能看到，并进入食谱设计器处理。
3. 一次只允许一条未处理完的调整；处理完之前不能提下一条。
4. 撤销本次提交后，调整次数退回。
5. 页面不展示历史进度时间轴，只展示提交时间、提交内容、当前状态。

## 3. 非目标

- 本期不做退款申请页（另立需求）。
- 本期不做“补充提交”：提交后想补充，走企业微信。
- 本期不做状态变更历史/客服留言时间轴。
- 本期不做“问个问题 / 其他意见”类型；这两类走企业微信。
- 本期不做后台设计器里的需求面板（第二阶段）。

## 4. 已确认的规则

| 规则 | 结论 |
|---|---|
| 一次能提几条 | 一条。当前调整未处理完（待受理/已受理/处理中）时，不能提下一条，即使调整次数还有 |
| 补充提交 | 不做。想补充/修改，走企业微信找 Seven爸爸 |
| 撤销 | 只在“待受理”时可撤；撤销后这条不算次数，次数退回 |
| 撤销后的状态 | 显示“已撤销”，不是“未受理” |
| 进度展示 | 只显示提交时间、提交内容、当前状态；不展开历史 |
| 处理完成 | 状态显示“已交付” |
| 退款 | 独立页面，本期先不做；入口处理见 §9 |

## 5. 页面结构（从上到下）

### 5.1 导航与标题

- 页面标题：**食谱调整**
- 不再出现“售后与问题反馈”字样。

### 5.2 额度条

固定在最上面，两个数字：

> 售后窗口期还剩 **N** 天　·　调整次数还剩 **N** 次

- 窗口按交付时间起算，后端 `windowDaysLeft`；向上取整。
- 次数按后端 `freeRevisionsLeft`；撤销的请求不计数。
- 窗口已过或次数为 0 时，数字照常显示，下面给一句原因，表单不出现。

### 5.3 食谱调整进度

- 标题：**食谱调整进度**
- 按提交时间**从近到远**排；最新一条在最上面。
- 每条请求一张卡，只显示三样：
  1. **提交时间**（YYYY-MM-DD HH:mm）
  2. **提交内容**（超过 4 行或 120 字自动折叠，底部“展开/收起”）
  3. **当前状态**：待受理 / 已受理 / 处理中 / 已交付 / 已撤销 / 未受理
- 不再显示时间轴、受理时间、处理时间、历史进度。
- 空态：`还没有提交过调整需求`。
- 卡片不提供“补充”“再次编辑”；已交付后要再调，用页面底部/表单重新提交一条（受次数和窗口限制）。
- 状态下方补一行“当前结果”：`未受理` 显示驳回原因；`已交付` 有处理说明就显示。这不是历史进度，是这次请求的结果，避免顾客只看到一个状态却不知道为什么。

### 5.4 本次食谱（简化）

目的：让顾客写需求时不用来回翻交付页，又能看到这份食谱的基本信息。

- **食材**：食材名 + 占比（不再显示部位/预处理、制备方法、克数）。
- **补剂**：营养素名 + 每公斤食材添加量（不显示补剂产品名）。
- **宏量营养**：蛋白质、脂肪、灰分、水分、钙磷比、能量密度（6 项，控制在两行内）。
- **多份订单**（待确认是否保留多选）：如果保留“一次调整可选多份”，这里只展开第一份，其余折叠成“另有 N 份”，避免一屏放不下；如果改成一份一条，则只显示当前这份。

数据来自当前交付快照/订单详情；只读，不可编辑。

### 5.5 调整需求（表单）

- 大文本框，占位提示：
  > 比如：鸡肉想换成鸭肉、某样食材减少一点、份量想调整……
- 支持照片/文档上传：
  - 图片 + PDF/Word；
  - 可预览、可删除；
  - 复用现有售后附件上传通道（COS），交互参考健康档案的上传组件；
  - 上限与现有售后附件一致。
- 提交按钮在底部固定栏，不在表单里重复。
- **没有“问题类型”选择**：本页固定提交 `ADJUST_RECIPE`。
- 提交时带上本次要调整的交付份 `deliveryItemIds`：
  - 单份老交付没有批次：**不传** `deliveryItemIds`（后端会拒绝“单份订单指定具体食谱”）；
  - 多份订单：从进入页面的那张卡解析出 `deliveryItemId`；如果保留多选，允许顾客在页面里再勾选其他份。
- 从消息中心 / 订单列表 / 客服进入（没有 `recipeId`）时：单份订单直接进入；多份订单默认选中最新一批的第一份，页面顶部显示紧凑的份选择（如果保留多选），否则提示顾客从订单详情的食谱卡进入。

### 5.6 提交后的状态

| 情况 | 页面 | 底部固定栏 |
|---|---|---|
| 没有未处理完的调整，且窗口/次数可用 | 进度卡 + 简化食谱 + 表单 | 企业微信 + **提交调整** |
| 最新一条是“待受理” | 进度卡 + 简化食谱；不显示表单 | 企业微信 + **撤销本次提交** |
| 最新一条是“已受理/处理中” | 进度卡 + 简化食谱；不显示表单，给一句“已在处理，如需补充请找 Seven爸爸” | 企业微信 + 处理中（不可点） |
| 最新一条是“已交付” | 进度卡 + 简化食谱；窗口/次数可用则重新显示表单 | 企业微信 + **提交调整** |
| 窗口已过 / 次数为 0 | 进度卡 + 简化食谱；不显示表单，显示原因 | 企业微信 |
| 没有提交过 | 空态 + 简化食谱 + 表单 | 企业微信 + **提交调整** |

- 固定栏最多两颗：企业微信 + 当前主动作（提交或撤销）。不做四颗并排。
- “撤销本次提交”只在 `canCancel`（待受理）时出现；撤销成功后刷新，次数退回，表单重新出现。

## 6. 入口与按钮文案

入口位置不变：**定制订单详情 → 你的定制食谱交付卡片**。

按钮文案：

- 没有未处理完的调整 → **调整食谱**
- 有未处理完的调整 → **查看进展**

“已交付”的历史记录不影响按钮：只要窗口/次数允许，仍显示“调整食谱”，可再提一条。

## 7. 状态与数据映射

现有售后状态：

| 库状态 | 顾客端显示 |
|---|---|
| `PENDING` | 待受理 |
| `ACCEPTED` | 已受理 |
| `PROCESSING` | 处理中 |
| `RESOLVED` | **已交付**（仅本页；后台仍叫已解决） |
| `REJECTED` + `rejectReason` 含“撤回” | **已撤销** |
| `REJECTED` + 其他原因 | 未受理 |

现有字段已经够用：

- `status`、`description`、`photos`、`createdAt`、`canCancel`、`rejectReason`；
- 额度：`windowDaysLeft`、`freeRevisionsLeft`、`hasOpen`、`canSubmit`、`reason`；
- 撤回后不计数：后端 `getQuota` 已排除 `rejectReason` 含“撤回”的行。

需要补两处：

1. **顾客端状态中文**：现在 `statusLabel` 把 `REJECTED` 一律翻成“未受理”，撤销也显示“未受理”。建议后端在 `listForCustomer` 里加 `customerStatusLabel`（按上表生成），前端直接渲染，不在前端做字符串匹配。
2. **额度只统计“调整”类**：现在 `getQuota` 把该订单的**所有售后类型**都算进 `usedCount` 和 `hasOpen`。历史上如果提过“问个问题/其他意见/退款”，会占用调整次数，甚至挡住调整提交。必须改成只统计 `type = 'ADJUST_RECIPE'`；`listForCustomer` 也要过滤只返回调整类，否则进度区会混进旧的问题/退款单。

## 8. 接口与数据流

沿用现有接口，不新建表：

- 读额度：`GET /custom-recipe/orders/:orderId/aftersale/quota`（或现有 quota 接口）
- 读列表：`GET /custom-recipe/orders/:orderId/aftersales`
- 提交：`POST /custom-recipe/orders/:orderId/aftersale`
  - `type: 'ADJUST_RECIPE'`
  - `description`
  - `photos: string[]`
  - `deliveryItemIds: [当前交付份 id]`
  - 进入页面的参数：`orderId` + `recipeId`；页面拉订单详情，在 `deliveryBatch.items` 里按 `recipeId` 找到对应的 `deliveryItemId`；单份老交付没有批次时，按整单售后提交（不传 `deliveryItemIds`）。
- 撤销：现有 `POST /custom-recipe/aftersales/:id/cancel`
- 已交付关联：`CustomRecipeAftersale.linkedDeliveryId` 已存在，但本期不强制绑定，页面也不展示版本号。后台点“处理完成”即 `RESOLVED`，顾客页显示“已交付”；如果要保证“已交付”一定对应一版新食谱，需要后台把“处理完成”和“重新交付”绑在一起，放第二阶段。
- **类型过滤**：`listForCustomer` 只返回 `type = 'ADJUST_RECIPE'`；`getQuota` 的 `usedCount` 和 `hasOpen` 也只统计 `ADJUST_RECIPE`。否则历史“问个问题/其他意见/退款”会占调整次数、挡住提交、混进进度区。

## 9. 退款入口的处理（本期必须定）

当前订单详情底栏有“退款申请”，点进去是同一个售后页（`scene=refund`）。本期把售后页改成纯“食谱调整”后，这个入口不能继续指向它，否则顾客点退款会看到调整页。

本期建议二选一：

- **A（推荐）**：先隐藏“退款申请”按钮；退款走企业微信找 Seven爸爸。
- **B**：保留按钮，但点击直接打开企业微信客服，不进退款表单。

等退款页做好后，再恢复独立入口。

## 10. 后台衔接

### 第一阶段（跟随本页）

- 订单中心 → 该订单 → 售后申请：能看到 `ADJUST_RECIPE` 的提交内容、附件、提交时间、状态。
- 现有后台已经能看到售后类型/说明/照片；本阶段只需确认类型文案和筛选。

### 第二阶段（待确认是否本期一起做）

- 售后申请详情加“进入食谱设计器”入口；
- 食谱设计器展示“顾客调整需求”和附件；
- 营养师改完后交付新版本，售后单写入 `linkedDeliveryId` 并置为 `RESOLVED`；
- 顾客页显示“已交付”。

> 现状：后台“处理完成”只写 `RESOLVED + handleNote`，“重新交付”是另一个按钮，`linkedDeliveryId` 可能为空。本期页面接受这个现状（`RESOLVED` 即显示已交付）；如果要求“已交付”必须绑定新版，需要把后台两个动作合并，属于本期额外范围。

## 11. 验收标准

1. 从交付卡片进入，按钮文案按“有/没有未处理完的调整”显示“查看进展/调整食谱”。
2. 页面只显示一个类型：食谱调整；没有“问个问题/其他意见/退款”。
3. 当前有一条未处理完的调整时，表单不出现，底部不能再次提交。
4. 提交后，列表最新一条显示提交时间、内容、状态“待受理”。
5. 待受理时可撤销；撤销后状态“已撤销”，次数恢复，表单重新出现。
6. 已受理/处理中不可撤销；页面提示找企业微信补充。
7. 已交付显示“已交付”；窗口/次数允许时可以再提一条。
8. 长内容自动折叠，可展开/收起。
9. 简化食谱显示食材、补剂营养素、6 项宏量营养；不显示部位/预处理、产品名、克数。
10. 附件可上传、预览、删除；提交后后台订单中心能看到。
11. 退款按钮不再进入调整页（按 §9 的方案处理）。

## 12. 待确认（需要老板定）

1. **多份交付订单：一次调整能不能选多份？**
   - 现状：一条提交可以勾选多份，只算 1 次调整；后台可以按选中份重新交付。
   - 新页面目前按“进入时那一份”设计；3 份食谱 + 2 次免费额度时，如果一份一条，顾客无法一次改完。
   - 建议：保留“一次可选多份、只算 1 次”，但把选择器做小（一行 chip，默认选中进入时那份），不做旧版的大勾选卡片。需要老板确认。
2. **商家驳回的调整算不算一次？** 现状算；建议不算（没有实际调整）。需要确认，且要决定是否追溯修正历史计数。
3. **退款入口本期选 A 还是 B？** 推荐 A（先隐藏按钮）；B 是保留按钮但点击直接打开企业微信。退款页后续再做。
4. **后台“进入食谱设计器”是否本期一起做？** 建议第二阶段；如果本期要做，范围会增加后台订单中心 + 设计器两个模块。

> 已定（builder's call）：状态卡在“未受理/已交付”时，额外显示一行 `rejectReason` / `handleNote` 作为当前结果说明；这不是历史进度，不违背“只显示时间、内容、状态”的简化。
