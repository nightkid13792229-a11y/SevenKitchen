# 食谱需求分类（第一阶段）

- 日期：2026-10-26（v3，范围已收窄到后台整理）
- 状态：结构、分类、节点、定义规则均已定稿；进入实施
- 适用模块：admin-web「食谱列表&设计」、后端食谱/系列
- 节点词典：同目录 `2026-10-26-recipe-taxonomy-nodes.md`

## 1. 为什么做

三件事指向同一个缺口：**菜没有可归类的结构。**

1. 生产库 26 道已上架菜，26 个名字全部是食材清单，除食材外没有任何类别信息。
2. 原来画的 6 条产品线，逐条核对后只有 1 条是"卖什么菜"，其余 5 条都是"怎么筛菜"，所以这批菜无论如何分不进去。
3. 定制食谱的命名有四种写法混用（狗名、日期、`(副本)`、备注），因为系统里除了名字没有别的地方能承载这些信息。

结论：命名、合规门禁、货架展示都是下游问题。**先给菜一个能归类的结构，其余往后排。**

## 2. 第一阶段范围

**做：** 后台一个「需求分类」整理入口——能建分类节点、能把系列归进去、能按归类筛选、能随时调整结构。

**不做（明确推迟）：**
- 小程序按需求分类展示（暂不需要）
- 命名规则强制、发布门禁（推后）
- AI 起名接入（推后）
- 价格带 / 档次（已取消该分类）

## 3. 模型：三张表，与食谱解耦

| 表 | 是什么 | 关键字段 |
|---|---|---|
| `recipe_taxonomy_kind` | 需求分类（5 个，固定但可加） | code、name、是否可见、排序 |
| `recipe_taxonomy_node` | 节点 | kindId、parentId、name、**definition**、sort、状态（启用/停用） |
| `recipe_series_taxonomy` | 归属（多对多） | seriesId、nodeId、createdBy |

**食谱表一个字不改。** 以后加分类、改节点名、重排顺序，全在这三张表里动。

### 3.1 归属规则

1. **跨分类可以多挂**：一道三文鱼菜可以同时是「鱼 · 三文鱼」「健康需求 · 皮肤毛发 · 瘙痒」「季节 · 应季」。
2. **同一分类内最多一个归属**，且只能挂**叶子节点**。父节点只做汇总。
   - 例：「主蛋白」里只能选一个物种；不能既是三文鱼又是鸡。
3. **可以为空**：一道菜可以没有任何健康需求、任何场景。空不代表错，代表这是缺口——正是规划要看的东西。

### 3.2 节点定义（必填）

每个节点必须写一句「什么菜该放进来」。没有定义，同一个人隔一周、不同的人、AI，会把同一道菜归到不同地方；节点越多偏得越远。

定义的要求：**能用来做判断**，不是同义反复。

- ✅「适用于主人反馈软便、但未确诊疾病的狗」
- ❌「针对肠胃问题」

## 4. 五个需求分类与节点

节点全集见词典文件。此处只给规模与层级规则：

| 分类 | 层级 | 节点数 | 说明 |
|---|---|---|---|
| 主蛋白 | 二级（畜/禽/鱼 → 物种） | 3 + 17 | 只到物种，不含部位；非鱼类水产不进此分类 |
| 健康需求 | 二级（系统 → 症状或疾病） | 11 + 36 | 叶子只能是症状或疾病，不放"支持/期"这类干预词 |
| 场景 | 一级 | 4 | 日常主食、初次尝试、换粮过渡、出行 |
| 季节 | 一级 | 6 | 春夏秋冬、应季、换季敏感期 |
| 工艺形态 | 一级 | 5 | 只建"蒸煮鲜食"一支，其余空置 |

## 5. 界面

### 5.1 入口

**「食谱列表&设计」页**（`/recipe-designer`）。这是唯一入口，不新开页面。

### 5.2 布局

页面上方加一个切换：**「按系列」/「按需求分类」**。

**按需求分类**视图：

```
┌──────────────┬──────────────────────────────┐
│ 分类树        │ 该节点下的系列列表            │
│              │                              │
│ ▾ 主蛋白      │ [卡片] 三文鱼 · 南瓜糙米      │
│   ▾ 畜类     │ [卡片] 鸡肉 · 山药小米        │
│       猪      │                              │
│       牛      │  未归类：12 道                │
│   ▾ 禽类     │                              │
│   ▾ 鱼类     │                              │
│ ▾ 健康需求    │                              │
│ ▾ 场景        │                              │
└──────────────┴──────────────────────────────┘
```

- 左树只显示**启用**的节点；停用节点折叠在「已停用」里
- 点节点 → 右侧显示该节点下的系列
- 顶部固定一个「未归类」入口，随时能看还剩多少没分
- 每行显示已归属的标签（截断显示，悬停看全）

### 5.3 归类操作

- **单道**：行内「归类」按钮 → 弹出多选树（按分类分组，同分类单选、跨分类可多选）
- **批量**：列表多选行 → 顶部「批量归类」→ 同一个多选树，只对该分类生效
- **不改动食谱本身**：归类只写归属表，不触发版本、不触发发布

### 5.4 结构维护

- 分类树可增节点、改名、调顺序、停用
- 停用不删除：已归到该节点的菜保留归属，但在树里收起
- 节点删除只允许"无归属且无子节点"时执行

### 5.5 权限

与现有设计器一致：员工可归类，结构维护（增删节点、改定义）限管理员。

## 6. 落地顺序

1. **建三张表 + 节点词典导入**（后端）
2. **分类树 + 归类接口**（后端）
3. **「按需求分类」视图**（前端，只读）
4. **归类操作**（单道 + 批量）
5. **结构维护**（增删改、停用）
6. **把现有 26 道归一遍**（产品工作，验证结构够不够用）

第 6 步是验收标准：如果 26 道里有菜归不进去，说明分类还缺东西，回到第 5 步补节点。
