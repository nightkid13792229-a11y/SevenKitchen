# AI 添加原料 · 入口分线设计（食材 / 补剂）

- 日期：2026-10-29
- 状态：已实施（2026-10-29，commits `43466373`..`6a682e8c`；手工回归待老板点一遍）
- 范围：`admin-web/src/views/Ingredients/ai-agent`、`admin-web` 路由与原料创建 API 客户端、`backend` 原料创建（ingredient-creation）接口与守卫
- 不在本期：补剂线的字段与核验规则、补剂 Agent 的工具集、营养档案编辑入口、AI 判线（拿不准时让模型猜）

## 1. 结论先行

1. **只保留一个页面**：`/ingredients/ai-agent`（AI 添加原料）。另一个「先判断食材还是补剂」的半成品页 `/ingredients/ai-create` 删除，路由保留一条重定向，避免旧书签 404。
2. **一个页面、两副身体**：页面外壳共享；线路定了之后才挂上对应的身体（食材身体 = 现有 Agent 工作台；补剂身体 = 明确的「未开放」占位，不是假装能用）。
3. **线路不是 URL 参数，是决议结果**：真正决定线路的只有两个来源——已存在的草稿 / 已有原料（后者本期没有入口，留给未来），它们**锁定**；在此之外，**用户手选**说了算。URL 上的 `line` 只用来决定“进页面第一刻高亮哪一条”，用户一点就退场。
4. **本期只做「新建」和「手选」**：没有编辑入口、没有 AI 判线、没有补剂身体。
5. **后端四处必须硬拦**：没有草稿时必须显式带线路；草稿是补剂时拒绝起草；授权/提交只放行食材；创建草稿的类型不再写死 `FOOD`（改为显式传入，本期仍只放行 `FOOD`）。

## 2. 背景：为什么必须分线

这次线上跑「添加鸡蛋清」暴露的是同一类问题的两端：

- **今天整条 AI 链路只认食材**：草稿创建时类型写死 `FOOD`（`ingredient-creation-draft.service.ts` 的 `create({ type: 'FOOD' })`），`writeIngredient` 只接受 7 个食材字段（名称、英文名、类别、基本单位、单位展示名、CFCT 分类、可食部），`writeNutrition` 只能从 7 个公共营养库的来源记录里抄数值。
- **补剂线是另一套东西**：营养来自商品标签照片（OCR / 视觉模型抽取），口径是每粒 / 每勺，卡片要剂型、是否油性、是否零售、等价组；它现在没有草稿、没有核验、没有授权闸门，只有一个「新增补剂」弹窗一次调用直接写库。

两条线的**数据来源、计量口径、字段集、核验规则、产出物**全都不同。所以线路必须在很靠前的地方定下来，而且**一旦定了就不允许在页面里改**——字段集不同，混写会得到一份既不像食材也不像补剂的脏草稿。

## 3. 已定的三件事（老板 2026-10-29 决定）

1. 只保留 Agent 页面；「先判断食材还是补剂」的半成品页可以不要。
2. 接受「一个页面、两副身体」。
3. 营养档案入口（编辑已有原料）本期不管，未来再说。

## 4. 目标 / 非目标 / 反目标

**目标**

- 进页面第一件事就是定线路，线路没定之前不建草稿、不能开跑。
- 线路的判定规则只有一份，可单测，未来加入口时只需加一个输入。
- 后端不会因为前端漏传或手快而被写进错误的线。

**非目标**

- 不做补剂线（字段、核验、工具集）。
- 不做编辑入口（从营养档案 / 原料详情进来）。
- 不做「不确定就让 AI 判」。
- 不改草稿命名规则（草稿名仍是第一句话原文）、不做草稿续接入口、不改「终检」与「核验」的概念重叠——这些是相邻问题，单独立项。

**反目标（做了算失败）**

- 选「补剂」之后系统点头，AI 仍按食材建档，产出一份「补剂名字的食材档案」。
- 两条线各占一个路由，未来每加一个入口都要判断该跳哪。
- 补剂线没做，却在界面上留一个能点进去、能跑一半的入口。

## 5. 术语

| 写法 | 含义 |
|---|---|
| 线路（line） | `FOOD` 食材 / `SUPPLEMENT` 补剂。数据库里是原料类型字段，另有第三个值 `PACKAGING` 包装，**不属于本页面**，决议时显式拒绝 |
| 任务类型（mode） | `CREATE` 新建原料 / `EDIT` 编辑已有原料。本期只做 `CREATE`；`EDIT` 只占位，不实现 |
| 入口（entry） | 进入本页面的来源。每个入口声明自己能提供什么（草稿 id / 原料 id / 线路预选 / 什么都没有） |
| 身体（body） | 线路确定后挂上的那套界面与逻辑 |

## 6. 设计

### 6.1 页面结构

```
┌─ AI 添加原料 ─────────────────────────────────────────┐
│  [入口说明 + 当前线路标签]                             │
│                                                       │
│  线路未定：起手卡（两选一）                             │
│  线路已定：<FoodBody> 或 <SupplementBodyGate>          │
└───────────────────────────────────────────────────────┘
```

- 外壳：标题、入口说明、线路标签、以及「线路未定」时的起手卡。
- 食材身体：就是今天的 Agent 工作台（左侧对话 + 右侧草稿审核），不动。
- 补剂身体：本期是一个**闸门卡片**，写明「补剂线和食材的字段、计量口径、核验都不一样，正在单独做」，并给一个「改回食材」的出口（仅在线路还没锁定、还没跑过任何一轮时提供）。

### 6.2 线路从哪来（决议阶梯）

按顺序取第一个命中的：

| 优先级 | 来源 | 输入 | 锁定 |
|---|---|---|---|
| 1 | 已有草稿 | `draftId` → 读草稿的类型 | 🔒 锁定 |
| 2 | 已有原料 | `ingredientId` → 读原料的类型 | 🔒 锁定 |
| 3 | **用户手选** | 起手卡 / 换线路 | 可改（没建草稿之前） |
| 4 | **入口预选** | URL `line`，仅作初始预选 | 可改（用户点过之后失效） |
| 5 | 都没有 | 停在起手卡，不建草稿 | — |

补充规则：

- **用户的选择永远压过入口预选**（第 3 级在第 4 级之前）。`entryLine` 只在进入页面的第一刻起作用：决定起手卡先高亮哪一条，或在只有一条可行时直接进去；**用户点过任何一次之后，它就退出判定**。否则 `?line=supplement` 会让闸门卡上的「改回食材」变成死路。
- **有对象时 URL 的 `line` 一律忽略**。真实线路只从草稿 / 原料读，前端不拿 URL 决定线路。
- 对象与 URL 冲突时以对象为准，并显示一行「已按原料类型纠正」，不弹错误窗。
- 第 2 级本期没有入口会用到，但决议函数要支持，避免未来补入口时重写判定。
- `PACKAGING` 没有被任何一级支持 → 直接拒绝并提示「本页面不处理包装」。

决议逻辑做成**一个纯函数**放在前端（`resolveLineEntry`），输入是 `{ draftType, ingredientType, entryLine, userPick }`，输出 `{ line, source: 'DRAFT' | 'INGREDIENT' | 'USER' | 'ENTRY' | null, locked, notice }`。规则只有这一份，测试直接打这个函数，必须覆盖「预选补剂 → 用户改选食材 → 结果食材、source=USER」。

> 为什么不在后端单开一个「决议接口」：本期只有「新建 + 手选」一种情况，后端能裁决的只有「草稿存在与否」，单开接口属于空转。等编辑入口进来（那时才真正有「对象 vs 预选」的冲突要裁），再把它提到后端，前端只调一个接口。这是设计上的欠账，写在这里，别忘。

### 6.3 页面状态与文案

| 状态 | 触发 | 界面 | 输入框 |
|---|---|---|---|
| A 未定线 | 无草稿、无预选 | 起手卡：「这次添加的是：食材类原料 / 补剂类原料」+ 一行说明「食材按每 100g 从营养库取数；补剂按每粒从商品标签取数」 | 禁用 |
| B 食材 | 选了食材 / 草稿是食材 | 今天的界面 + 顶部标签「食材线」；**没建草稿之前**标签旁给一个「换线路」文字按钮，点了回起手卡 | 可用 |
| C 补剂（未开放） | 选了补剂 | 闸门卡 + 「改回食材」 | 禁用 |
| D 恢复草稿 | 带 `draftId` | 按草稿类型进 B 或 C | 按 B |
| E 被拒绝 | 草稿/原料是包装 | 错误卡 + 返回原料列表 | 禁用 |

> D 与 E 本期只体现在决议函数里，**页面不接入口**：今天的页面刷新即丢现场（不读 `draftId`、没有草稿列表），这一条属于相邻问题（草稿续接），单独立项。写进状态表是为了让决议函数一次做对，将来接入口时不用改判定。

规则：**线路没定之前不建草稿。** 今天的草稿是点「开始」时由后端顺手建的（草稿名直接取那句话原文），这次把「点开始」挡在线路之后——不再「先上车再决定去哪」。

### 6.4 入口契约（URL）

```
/ingredients/ai-agent                          ← 新建，线路待选
/ingredients/ai-agent?line=supplement          ← 新建，入口预选（可改）
/ingredients/ai-agent?draftId=…                ← 继续草稿，线路由草稿决定
```

本期只实现前两个；`draftId` 走决议阶梯第 1 级，但**页面的草稿续接入口不在本期**（没有草稿列表、没有刷新恢复），所以它暂时只是「未来预留」——不过决议逻辑要认它，免得将来加的时候又改一遍。

`ingredientId` 同理，本期不实现入口，但决议函数要认。

### 6.5 后端防线（前端拦不住的，这里必须拦）

先分清两种失败：**请求本身不成立**（没带线路、线路是不可用的那种）→ 应在控制器里、`flushHeaders()` 之前拦下，返回真正的 400；**草稿内容不成立**（草稿是补剂）→ 只能进服务层才知道，此时响应头已经发出去了，只能以 SSE `error` 事件结束。页面对两种都能显示（HTTP 错误走 `message` 字段，SSE 错误走气泡），但测试断言不同。

| 位置 | 现状 | 本期改成 |
|---|---|---|
| 建草稿 | 类型写死 `FOOD`，前端不传 | 类型改为**显式传入**（服务层仍只接受 `FOOD`，别的值直接抛错）；对外的非法取值由控制器入参校验挡在 400，不会走到建草稿 |
| AI 起草（`POST agent/stream`）· 入参 | 不看草稿类型 | ① 没有 `draftId` 又没带 `line` → **控制器 400**（flush 之前）；② `line=SUPPLEMENT` → **控制器 400**「补剂线还没开放」；③ 有 `draftId` 时忽略 `line` |
| AI 起草 · 草稿 | 完全不看草稿类型 | 草稿类型不是 `FOOD` → **服务层拦截，以 SSE `error` 事件返回**「补剂线还没开放」，且保证不新建草稿、不写任何字段 |
| 授权 / 提交 | 用草稿类型建原料，但没有限制 | 草稿类型不是 `FOOD` → 400（纵深防御，为补剂线开放那天留好位置） |

**上线过渡（一个版本）**：后端不认识 `line` 的旧页面仍可能被浏览器缓存着，为了不让它们的首轮全部报错，缺 `line` 时**按 `FOOD` 处理并记一条 warn 日志**；等新版 admin-web 铺开后的下一个版本，再把这个默认值删掉、改为严格必填。这样后端可以先上、前端随后，不必卡同一个发布窗口；回滚只需回前端（后端对旧请求是宽容的）。

错误必须是可直接展示的中文，不用英文错误码当文案（可以带 `reason` 字段给前端判断）。

## 8. 测试

- **决议函数单测**：无输入 → 未定；入口预选 → 可改；**预选补剂后用户改选食材 → 食材、`source=USER`**；草稿 / 原料压过用户选择；包装 → 拒绝；冲突 → `notice` 出现。
- **后端**（扩展现有 spec，不新起一套）：`tests/application/ingredient-creation/ingredient-draft-agent.service.spec.ts`、`ingredient-creation-authorize.service.spec.ts`、`ingredient-creation-draft.service.spec.ts`。覆盖：带 `draftId` 时忽略 `line`；**草稿类型非食材 → 以 SSE `error` 事件返回，且草稿未被新建、字段未被写**；授权/提交 400；过渡期内缺 `line` → 按 `FOOD` 走并落 warn 日志。
- **接口层**（控制器 / e2e 任选其一）：`line=SUPPLEMENT` → **HTTP 400**，且断言「没有产生新草稿」；过渡期内缺 `line` **不报错**（按 `FOOD` 走并落 warn），严格化留到下个版本——这条与 6.5 的兼容默认一致。
- **页面回归**（沿用仓库源码回归测试的写法）：入口按钮仍指向 `IngredientAiAgent`；`ai-create` 路由已下线且有重定向；页面含线路闸门与「换线路」。
- **自检**：后端只跑 `npx tsc --noEmit` 与相关测试（联调期间不要 `npm run build`，会删 `dist`）；admin-web 构建通过。

## 9. 落地顺序

1. 后端契约与守卫（+ 单测）。**带一个版本的兼容默认**（缺 `line` → `FOOD` + warn），所以后端可以先上线，不会打断现在这个页面。
2. 前端决议函数与线路闸门（+ 单测）——选补剂时看到的是明确的「未开放」，不是假确认；同时开始发 `line`。
3. 删除 `ai-create` 一整套，加重定向，改标题。
4. 下一个版本：删掉兼容默认，`line` 改为严格必填（此时新版 admin-web 已铺开）。
5. 全量自检，回归一次「添加鸡蛋清」那条路径。

## 10. 我的判断（builder 可按此执行，不用再问）

1. **保留一个路由**（`ai-agent`）而不是两条线各一个——避免两套代码漂移。
2. **写了第一个字段之后不允许改线路**，只给「另起一份」的出口——字段集不同，混写必脏。
3. **「补剂未开放」本期写在前端闸门里**，但文案与开关集中在一处；补剂线做完时改成读后端能力位。
4. **后端 `intake/classify` 暂留**（见 6.6）。
5. **不新增决议接口**（见 6.2 的欠账说明）。
6. **用户的选择压过入口预选**，入口预选只负责“进页面第一刻高亮哪一条”，用户一点就退场（见 6.2）。
7. **状态 B 给「换线路」**（没建草稿之前），避免只能刷新页面才能改主意（见 6.3）。
8. **入参错误走 400，草稿内容错误走 SSE `error`**：前者在控制器 flush 之前拦，后者在服务层拦（见 6.5）。
9. **过渡期一个版本允许缺 `line` 按 `FOOD` 处理**，让后端能先上线、不和前端卡同一发布窗口；下个版本收紧（见 6.5 / 9）。
