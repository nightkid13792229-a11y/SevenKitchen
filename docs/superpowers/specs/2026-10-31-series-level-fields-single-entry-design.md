# 系列级资料只有一个维护入口（发布 / 更新）

- 日期：2026-10-31
- 状态：老板确认 A 方案并执行
- 范围：admin-web 食谱设计器（上线检查抽屉、列表页发布 / 更新抽屉、编辑器跳转）、
  backend recipe-designer 阶段发布门槛
- 不在范围：旧「编辑食谱」页、订单定制交付流程、数据模型与历史数据迁移

## 1. 为什么改

2026-10-26 的系列发布设计定过一条原则：

> 谁共用，谁在系列；谁各写各的，谁在阶段。

并且把「阶段抽屉和系列抽屉出现两个都能编辑的同一字段」列为反目标。

2026-10-27 做 AI 命名和需求分类时，为了让门禁能在检查抽屉里当场补，
又把「食谱名称」和「快速归类」放进了上线检查。结果是：

- 名称在发布 / 更新和上线检查两处都能改；
- 归类只在检查抽屉里改，发布抽屉反而没有；
- 未归类卡的是阶段入库，但归类本身是系列级资料。

同一份资料两个入口，容易改漏、改错，也让「阶段」和「系列」两层职责重新混在一起。

## 2. 决定（A 方案）

系列级资料只在「发布 / 更新」里维护；上线检查只负责阶段门槛和只读摘要。

1. 上线检查不再编辑名称 / 归类。产品线只读展示名称和归类状态；
   订单定制没有发布抽屉，名称仍然在检查抽屉里改。
2. 快速归类搬进发布 / 更新的「发布设置」，保存后立即重算整系列门槛。
3. 阶段入库（保存到系列仓库）不再检查 `TAXONOMY_REQUIRED`；
   整系列发布继续检查（`series-release-readiness.ts` 已有这条门槛）。
4. 上线检查的「去发布 / 更新」带上系列 id / 名称跳到列表页，
   列表页打开后直接弹出对应系列的抽屉；参数消费一次后从地址栏清掉。

## 3. 五条资料的归属

| 资料 | 归属 | 在哪里改 | 上线检查里 |
|---|---|---|---|
| 食谱名称 | 系列 | 发布 / 更新（订单定制仍在上线检查） | 只读 |
| 快速归类 | 系列 | 发布 / 更新 | 只读状态 |
| 封面图 | 系列 | 发布 / 更新 | 只读状态 |
| 一句话卖点 | 系列 | 发布 / 更新 | 只读状态 |
| 封面角标 | 系列 | 发布 / 更新 | 只读状态 |

阶段自己的东西（原料、克数、营养、制作步骤、补剂目标）仍然在上线检查和编辑器里改。

## 4. 为什么不保留「就地补」

就地补的便利，换来的是同一条资料两个入口。归类被搬走后，如果阶段入库还卡归类，
就会出现「在这儿被拦、却要去别处修」；所以阶段门槛与编辑入口必须一起移动。

代价是从编辑器到发布抽屉要多一步。第 2 节第 4 条把这一步压缩成一次点击，
不再需要在一堆系列卡片里找。

## 5. 不做什么

- 不改数据库，不迁移历史草稿上的展示字段；
- 不动订单定制的展示资料流程（封面图 / 封面标题仍在上线检查里改）；
- 旧「编辑食谱」页仍能改封面 / 角标 / 卖点，属于同一类重复，另开任务收口；
- 不把「系列资料」拆成第三个抽屉：发布 / 更新已经是唯一入口。

## 6. 验收

1. 产品线上线检查里没有可编辑的名称和归类；只读区能看到名称、归类、封面、卖点、角标状态。
2. 发布 / 更新抽屉能改名、挂归类、传封面、填卖点、选角标。
3. 未归类不再阻断「保存到系列仓库」，但阻断「发布 / 更新」。
4. 从上线检查点「去发布 / 更新」，直接弹出对应系列的发布 / 更新抽屉。
5. 订单定制仍可在上线检查里改名、设封面。
