# 知识库上数据库 · Web 只读入口 · AI 检索升级（设计）

**日期**：2026-11-01
**老板决定**（2026-11-01）：知识库全部上数据库。Web 只给老板与管理员看。核对原文要能直接跳到对应页。

---

## 0. 一页纸

**要解决的三个真问题**

1. 知识条目写死在 32 个代码文件里，改一条要发版。
2. 条目与原文之间没有机器可读的线：出处是"第 40 章 草酸钙结石"这种自然语言，系统不知道它对应哪份文件、第几页，人也没法一键核对。
3. AI 查知识库只会"拿一串字撞标题"，中文不分词、不能筛、不能翻页，返回的还是拼好的字符串。

**做什么**（三步，每步都能独立验收）

| 步骤 | 内容 | 做完能看到什么 |
|---|---|---|
| **第一步 · 数据层**（4.5 天） | 6 张表建好；387 条 + 1249 处出处搬进库；出处从 76 种写法收敛到 31 个来源；接上归档文件路径；2572 页建页标题索引；补上传缺的 1 份 | 数据库成为唯一事实来源，**内容与现状逐字等价**；每条出处都能落到"文件 + 第几页" |
| **第二步 · 看得见**（3 天） | 后台「知识库」只读页面 + 7 个接口 + 原文文件服务（支持跳页） | 你能按分类浏览、全文搜索、**点出处直接跳到原文那一页** |
| **第三步 · AI 用得准**（3 天） | 检索升级（同义词/筛选/分页/结构化返回）+ 工具改造 + 提示词 | AI 问"草酸钙结石营养方向"能一次命中带出处页码的条目 |

合计约 **10.5 天**。

**不做什么**（这一轮）

- 不做全文入库（原文不进数据库，只留页标题索引）。
- 不做向量检索。
- 不做在线编辑（页面纯只读）。
- 不做 OCR（3 份扫描件标注"无法定位"）。
- 不搭回退/备份机制（生产当前是测试环境，见 D20）。
- 顾客侧行为一律不变。

**唯一保留的保险丝**：知识库真的没数据时，两条业务链路**不硬答**（健康分析回"暂不可用"，AI 工具回"暂无该主题，不要凭记忆编"）。这一行代码，符合"没有出处的结论一个字都不说"，不做额外机制。

## 2. 目标与非目标

### 目标

- **G1** 知识条目的唯一事实来源是数据库；改内容不需要改代码。
- **G2** 每条出处都能机器定位到「来源 → 归档文件 → 页码」；定位不到的显式标注。
- **G3** 后台有一个只读页面：按领域/问题类型/审核状态分类浏览、全文搜索、点出处直接打开原文对应页。
- **G4** AI 侧检索质量提升：主题查询能命中，可带筛选，返回结构化、带边界信息。
- **G5** 原有两条业务链路（食谱设计 Agent、顾客/营养师健康分析）**行为完全不变**。

### 非目标

- 不做面向顾客的知识库入口。
- 不把原文全文写进数据库。
- 不做向量检索（理由沿用 `source-archive-and-retrieval-plan.md` 第二章）。
- 不改变"结论只能来自已审核条目"这条边界。

### 失败的样子（anti-goals）

- 内容搬完发现某几条的措辞变了 → 失败（必须逐字等价）。
- 出处归一靠猜 → 出处张冠李戴，比现在更糟 → 失败。
- 原文文件通过接口暴露给公网或顾客 → 失败。
- 后台页面成为"又一个没人看的页面" → 用"点开就是原文对应页"作为它的存在理由。

## 4. 数据模型

新增 6 张表。命名遵循 `docs/DATABASE_NAMING_CONVENTIONS.md`：Prisma camelCase，`@@map` 到 snake_case。

### 4.1 `knowledge_source`（来源登记，31 行 = 26 个外部 + 5 个内部笔记）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | String @id | 沿用现有 ID，如 `SACN5`、`WSAVA-VACC-2024` |
| `name` / `version` | String | 展示名与版本 |
| `organization` | String | 机构前缀（WSAVA/AAHA/ACVIM/SACN/IRIS/MERCK/NRC/FEDIAF/CN/INTERNAL） |
| `tier` | String | A/B/C（证据分级，沿用 `evidence-policy.md`） |
| `role` | String | 用途说明 |
| `archivePath` | String? | **新增**：相对归档路径，如 `sacn5/chapters/SACN5_40.pdf`；内部笔记为空 |
| `pageCount` | Int? | 页数 |
| `hasTextLayer` | Boolean | 是否有文字层 |
| `kind` | Enum | `EXTERNAL` / `INTERNAL_NOTE` / `SECONDARY_REF` |
| `retired` | Boolean | 已废弃（如 AAHA-2014-WEIGHT），检索时降权不删除 |

### 4.2 `knowledge_entry`（条目，387 行）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | String @id | 沿用现有 ID（`urolith-001`） |
| `domain` | Enum | 28 个领域 |
| `questionType` | Enum? | 新结构有，旧结构为空 |
| `title` / `summary` | String | |
| `details` / `caveats` | String[] | |
| `keywords` / `applicableTo` | String[] | |
| `riskLevel` / `urgency` / `priority` | Enum | |
| `reviewStatus` | Enum | **默认 `PENDING_REVIEW`**（沿用"缺省即未审核"） |
| `reviewBy` | DateTime? | 下次复核日期 |
| `reviewerNote` | String? | |
| `version` | Int | 每次写入 +1 |
| `createdAt` / `updatedAt` | DateTime | |

> 不加 `audience` 列：营养师/顾客的可见性由 `domain` + `reviewStatus` 推导，保持现有逻辑单点。

### 4.3 `knowledge_entry_source`（出处，约 1,249 行）

| 字段 | 说明 |
|---|---|
| `entryId` / `sourceId` | 外键 |
| `locator` | 原样保留人类可读定位（"第 40 章 草酸钙结石"） |
| **`rawCitation`** | **原样留痕**：旧式出处那句自由文本一个字不改地存下来（如"小动物临床营养学（第 5 版），第 40 章 草酸钙结石"）；新式出处同 `locator + note` |
| **`normalizationRule`** | 归一用的是哪条规则（规则编号 / `MANUAL` / `NEW_FORMAT`），归一错了能整体回滚重跑 |
| `pageStart` / `pageEnd` | 解析出的页码，可空 |
| `locatorStatus` | `RESOLVED` / `UNRESOLVED` / `NO_PAGE`（扫描件）/ `NOT_APPLICABLE`（内部笔记） |
| `note` | 补充说明 |
| `sortOrder` | 展示顺序 |

> 有了 `rawCitation`，"出处归一"就是**可逆的**：映射错了不用回滚数据库，改规则重跑即可；也彻底解决"76 种写法里有 50 种在库里没地方存"的问题——它们就存在这一列。

### 4.4 `knowledge_page_index`（页标题索引，2,572 行）

`(archivePath, pageNo) → heading`，heading 为每页首行文本截断到 80 字符。
用途：①给"第 40 章/表 35-1/指南第 5 页"这类 locator 反查页码；②Web 侧展示文件目录。

### 4.5 `knowledge_alias`（同义词，初始 100–200 行）

`(alias, targetType: ENTRY|DOMAIN, targetId, weight)`。
初始由条目 `keywords` 自动生成，再人工补常用说法（草酸钙结石 / 膀胱结石 / 尿血 / 便血 / 胰腺炎康复期…）。

### 4.6 `knowledge_revision`（修订历史）

每次写入落一行：`entryId, version, snapshot(Json), action(IMPORT/CREATE/UPDATE/REVIEW), actorId, note, createdAt`。
第一版只有 `IMPORT`；将来开了在线编辑才会有人的操作。

## 5. 内容搬家与出处归一

### 5.1 搬家流程

```
32 个 .ts  ──[脚本 export]──▶  knowledge-entries.json（全量快照，进仓库）
                                    │
                                    ├─▶ 校验（现有 validateEntries 全部规则）
                                    └─▶ 导入数据库（幂等：按 id upsert）
```

- 导出脚本读现有 `DOMAIN_DATA`，输出**规范化 JSON**（字段顺序固定、空数组不省略），作为等价性基准。
- 导入脚本 `--apply` 才写库，默认 dry-run 并打印差异。
- 导入完成后再改 `KnowledgeBaseService` 读数据库；在此之前代码不动。

### 5.2 出处归一（最需要细心的一步）

目标：76 种写法 → 26 个外部来源 + 5 个内部笔记来源 + 3 条二手引用。

| 类型 | 处理 |
|---|---|
| 同一来源的多种写法（"小动物临床营养学（第5版）" / "（第 5 版）"；ACVIM 22 种；AAHA 2021 4 种） | 按"来源名规范化表"人工核定后合并 |
| 5 个"我们自己的笔记"（12 处） | 新建内部来源 `INTERNAL-NOTE-*`，`kind = INTERNAL_NOTE`，`archivePath = null`，UI 上明确标"内部整理，无原文" |
| 3 处未登记文献（GfE / Meyer & Zentek / Klein 等） | 标 `kind = SECONDARY_REF`，UI 提示"转引，需回溯原文"；是否补归档单列待办 |
| 新结构 449 处（已有 sourceId） | 只需补 `archivePath` 关联与页码，不动 sourceId |

**产出**：一张 `docs/knowledge-base/citation-normalization.csv`（原写法 → 来源 ID → 处理方式 → 人工签核列），**先给人过目再执行**。不自动拍板。

**实测可行性**（2026-11-01 用 26 条正则规则试跑）：800 处旧式出处里 **796 处（99.5%）能被规则唯一映射**到 26 个来源中的一个；只有 3 个名字、4 处（GfE / Meyer & Zentek / Klein 等）需要人工定夺。
也就是说这一步的实际工作量在"**抽检确认**"而不是"逐条判断"——规则跑完人工抽 10% 复核即可。

### 5.3 页码解析

对每条出处，按顺序尝试：

1. locator 里直接写了页码（"第 5 页""p.12"）→ 直接用。
2. 归档文件就是该章节的单文件（SACN5 的 72 章，文件=章节）→ `pageStart = 1`，`RESOLVED`。
3. 用 locator 里的章节名/表号在 `knowledge_page_index` 里对该文件做模糊匹配 → 命中则记页码，`RESOLVED`；不命中记 `UNRESOLVED`（不猜）。
4. 文件无文字层 → `NO_PAGE`。
5. 内部笔记 → `NOT_APPLICABLE`。

预期覆盖率：SACN5 相关（约 800 处中的 295+）可 100% 落到文件；其余按 1/3 规则尽力，未命中的在页面上显示"打开文件（未能定位页码）"。

## 6. 运行时架构

```
                    ┌──────────────────────────────┐
  食谱 Agent ──────▶│ KnowledgeBaseService（签名不变）│
  健康分析   ──────▶│  getAll / searchByTags /      │──▶ 内存缓存（387 条 + 别名 + 来源）
                    │  buildPromptContext           │        ▲
                    └──────────────────────────────┘        │ 30s TTL / 版本号变化
                                                            │
  Web 读接口 ──────▶ KnowledgeReadService ──────────────────┤
  Web 写接口(将来)──▶ KnowledgeWriteService ──▶ bump version ─┘
                                                            │
                                                    PostgreSQL（唯一事实来源）
```

**要点**

- 缓存对象 = 条目 + 来源 + 别名 + 页索引（页索引较大，按需查询，不进热缓存）。
- `GET /api/v1/admin/knowledge/health` 之外的写操作都会 `bump version`；另一个进程最迟 30 秒感知。

### 6.1 受影响的调用方（必须逐个过）

| 调用方 | 现在怎么用 | 改造后 |
|---|---|---|
| `recipe-agent.service.ts` + `knowledge-port.ts` | 同步 `getAll()` | 不动（走缓存） |
| `health-analysis.service.ts` | 同步 `buildPromptContext()` | 不动（走缓存） |

## 7. 原文接线

### 7.1 配置

| 环境变量 | 本地 | 生产 |
|---|---|---|
| `KNOWLEDGE_ARCHIVE_ROOT` | `/Users/zhaochen/Documents/SevenKitchen-knowledge-sources` | `/opt/sevenkitchen/knowledge-sources` |

未配置时：页面显示"本机未配置原文目录"，文件接口返回明确提示，其余功能不受影响。

### 7.2 文件服务

```
GET /api/v1/admin/knowledge/sources/:sourceId/file?exp=<unix>&sig=<hmac>
```

- `sig = HMAC-SHA256(sourceId + exp + userId, JWT_SECRET)`，有效期 5 分钟。
- **本接口只认签名，不叠加 Bearer**。因为 `window.open` 打开新标签页带不上 `Authorization` 头；签名由已过 `StaffGuard + @Roles('ADMIN')` 的接口签发，本身就是鉴权凭据（5 分钟、绑定 sourceId 与签发人）。
- 路径只从数据库取（`sourceId → archivePath`），**客户端永远不能传路径**；再校验 `realpath` 在 root 之下（防穿越）。
- 支持 `Range`，支持 `HEAD`；`Content-Disposition: inline`；按扩展名给 `Content-Type`。
- 每次访问写审计日志（谁、哪个来源、什么时候）。

### 7.3 跳页

Web 侧：`window.open(fileUrl + '#page=' + pageStart)`。
浏览器原生 PDF 阅读器认这个锚点；不支持的情况下停在首页，页面同时显示"目标：第 N 页"提示。

**非 PDF 文件**（23 份 ACVIM XML、5 份 Merck、5 份 TXT、1 份 EPUB，共 34 份）没有页码概念，处理方式：

| 格式 | 处理 |
|---|---|
| ACVIM XML（JATS 全文，已确认是 PMC 正文而非摘要） | 抽 `<sec>/<title>` 建"章节索引"，按 locator 里的章节名定位，页面内滚动并高亮 |
| Merck HTML + TXT | **服务端只给 TXT**（HTML 是 Next.js 页面，正文混杂）；按 locator 关键词在 TXT 里定位并高亮 |
| NRC EPUB | 按章节文件定位，当作"小节"处理 |
| FEDIAF / 中文法规 PDF | 同 PDF |

这些文件在库里 `pageCount = null`，UI 上显示"章节：xxx"而不是"第 N 页"。

### 7.4 对账脚本

`npm run audit:knowledge-archive`
比对三方：`manifest.csv`（本地清单）↔ 本地目录 ↔ 生产目录（通过 SSH 列文件 + sha256sum），输出缺件、多件、哈希不符。补上传缺的那 1 份后，一次跑到全绿。

## 8. AI 侧改造

### 8.1 工具形态

沿用现有工具名 `read_knowledge`（已在生产，改名要动提示词），改成三种用法：

| 调用 | 行为 | 返回 |
|---|---|---|
| 不带参数 | 列可用范围 | 领域清单 + 问题类型清单 + 各多少条 + 有多少条已审核 |
| 带 `topic` / 筛选 | 检索 | 最多 8 张卡：id、标题、一句话结论、紧急程度、风险、审核状态、出处数、首个出处（来源名 + 定位）。附命中总数 |
| 带 `ids` | 取全文 | 完整条目（结论 / 要点 / 注意 / 出处列表，带页码） |

新增可选参数：`domain`、`questionType`、`approvedOnly`、`limit`（默认 8，上限 20）。

### 8.2 打分规则（内存）

| 命中位置 | 分值 |
|---|---|
| 关键词完全等于查询 | 10 |
| 关键词包含 / 别名命中 | 6 |
| 标题包含 | 5 |
| 上下文标签 ∩ applicableTo（每个） | 4 |
| 领域名 / 问题类型名包含 | 3 |
| 摘要 / 要点包含 | 1 |

同分排序：风险等级 HIGH 优先 → priority HIGH → id。
**没有命中就不返回**（不做无意义的模糊兜底），并明确告诉模型"知识库没有这个话题，不要凭记忆回答"。

### 8.3 提示词上下文

`buildPromptContext` 输出格式微调：每条先给"结论"，再给"依据"，出处带页码；并显式写清"不得据此诊断/给药"。结构与现有 24 条上限不变。

### 8.4 旧条目的短板补法（数据层做完之后，分批）

- 第一批 4 个领域：泌尿结石 12、肾 11、胰腺炎 12、肠胃 14 = **49 条**，补齐 `questionType`（绝大多数为 `NUTRITION`）、`riskLevel`、`sources`、`reviewStatus`。
- 脚本先给建议值并标出置信度，人工确认后写入；不自动拍板。
- 目标：让"草酸钙结石的营养管理方向"这类问题，AI 拿到的是带风险等级、带出处页码、能判断"能不能说给顾客"的条目。

### 8.5 待老板确认的一件事

**"必须先查知识库、查不到就拒答"要不要做成硬约束？**

`read_knowledge` 是一个**可选**调用的工具，模型完全可能不查就直接设计配方。改工具描述和提示词只能提高它查的概率，不能保证。

| 方案 | 做法 | 代价 |
|---|---|---|
| 轻（本轮默认） | 改工具 + 改提示词，把"特殊需求配方要先查"写进流程约束文字 | 小，但只是"强烈建议" |
| 重 | 在 Agent 循环里加卡口：命中"特殊需求"关键词时，未调用过 `read_knowledge` 就不允许出配方 | 大，会动现有食谱链路，且要先定义"什么算特殊需求" |

这一条先按"轻"做，等你看到实际效果再决定要不要升级。
