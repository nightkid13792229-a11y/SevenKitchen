# 预分装补剂下单页重构 · 设计

- 日期：2026-11-01
- 涉及端：`miniapp/`（顾客端下单页）、`backend/`（补剂报价与下单）、`admin-web/`（补剂商城配置）
- 页面：`miniapp/src/pages/supplement-order/index.vue`（导航标题「一键购买补剂」，入口按钮叫「购买预分装补剂」）

---

## 1. 为什么做

这一页是"制作单 → 买补剂"的唯一出口。现在的状态是：

1. **金额可能和实际扣款不一致**。改套数/改勾选后，如果服务端重算失败，界面会保留旧金额但用新套数下单；算价还没回来时也能点提交。
2. **"全部补剂都不可买"会变成一个死页**。为用户准备的空态永远进不去，顾客看到的是可勾选的清单 + ¥0.00 + 灰按钮 + 一句看不懂的"价格获取失败"。
3. **买多少被卡死在 3 套**。这是产品上限，不是业务上限；老板要求把主动权交回顾客。
4. **顾客说不清"买的是什么量"**。清单右侧只有孤零零一个「114g」，选了 3 套还是 114g，全页没有"一共几袋"。

## 3. 目标（可验收）

1. **金额永远一致**：页面显示的合计 = 服务端接受的金额 = 实际扣款金额。任何时刻（含正在算价、算价失败、刚改完套数）都成立。
2. **顾客能说清买了什么**：几种、每种几袋、整单多少克、一共几袋。
3. **想买多少买多少**：1–99 套都能买，三张卡覆盖常见档位，自定义覆盖其余。
4. **任何异常都有出口**：报价失败、全部不可买、地址失效、份数越界，都有明确下一步，且提示说人话。

## 4. 非目标

- 不做独立的确认订单页。
- 不做页内改配方/改天数/改袋规（那是制作单的事）。
- 不改按单排期的算法（大单只提示）。
- 不做"只买部分天数"。
- 不改补剂价格的算法（定价、加价倍率、服务费、运费、包邮门槛都不动）。

## 5. 失败的定义（出现任何一条即视为没做完）

- 顾客看到的金额和扣款金额不一致，哪怕只差一分。
- 同一张制作单生成两笔内容相同的订单。
- 顾客必须退出页面重进才能继续操作。
- 同一个错误连续弹两个提示，且真实原因被后一个盖掉。

## 7. 目标形态

### 7.1 页面结构（从上到下）

1. **来源卡**：食谱名 + 狗名（无狗名时"按当前制作单配比"）；右上入口文案改为**「改制作单」**，只在有制作单时出现，点击退回制作单（见 T4）。
2. **预分装说明图**：首次访问展示；之后折叠成一行「为什么是预分装？」可展开。折叠状态记本地存储。
3. **补剂清单**
   - 标题「本次要买的补剂」+ 右侧「全选 / 全不选」。
   - 副标「按这张制作单的配比算：3 种，每种 1 袋」。
   - 每行：名称 / 品牌规格 / 右侧 `整单 114g`；套数 > 1 时显示 `114g × 5 袋`。
   - 买不了的灰掉 + 原因；买不了的不能被选中。
   - 清单下方一行汇总：**共 15 袋**（服务端 `bagCount`）。
   - 汇总下方一个 ⓘ：「这个量是按你制作单里的食物总量和营养目标算出来的，不是你自己填的。」
4. **收货地址**：已选 / 未选两态；未选时卡片内直接给"去添加"的引导。
5. **套数选择器**（详见 7.2）。
6. **费用明细**：补剂商品金额 / 分装服务费 / 运费 / 合计 / 预计发货；当包材费 > 0 时增加「包材费」行；服务费被门槛免掉时该行显示「已免」；下方小字「分装后建议 6 个月内吃完（袋上印有效期）」；大单提示（详见 7.6）。
7. **底部固定栏**：合计 + 「提交订单」按钮；算价中显示「更新中」且按钮不可点。
8. **客服入口**：沿用 `CustomerServiceInlineButton`，与「下单配置」「确认订单」两页同款，放在底部栏左侧。
9. **提交确认弹层**（详见 7.8）。

### 7.2 套数选择器

沿用现有三张卡，加第四张：

```
选择套数
1 套 = 这张制作单需要的全部补剂（每种 1 袋）
满 129 元包邮

[ 1 套 ]  [ 2 套 ]  [ 3 套 ]  [ 自定义 ]
 ¥41.50    ¥83.00    ¥124.50     5 套
                                  ¥207.50
```

规则：

- **三张卡固定 1/2/3，与后台配置无关**：金额与"已包邮"角标仍由服务端 `portionOptions` 提供，前端不做乘法。
- **后台的"最多份数"彻底失效**：数据库列保留（不动迁移），但不再参与卡片数量、也不再参与下单校验。若以后要"临时关闭加量"，另加一个显式开关，不要复用这个字段。
- **第四张「自定义」**：
  - 未选中时只显示「自定义」三个字。
  - 点击弹出底部弹层：`−  [ 5 ]  +`，可直接点数字输入；下方「取消 / 确定」。
  - 弹层打开时的默认值：当前套数（若 ≤ 3 则取 4）。
  - 取值范围 1–99。超出输入按边界收敛。
  - 确定后：第四张卡显示「5 套 / ¥207.50」并高亮，前三张取消高亮；选择 1–3 时反过来，三张卡接管，第四张回落成「自定义」。
- **控件始终展示**：只要有可选购的补剂就展示（现在 `maxPortionMultiplier > 1` 才显示的条件取消）。
- **每次变更都要等服务端确认**（见 7.3）。

### 7.3 结算规则（钱的一致性）

- **单一事实来源**：`summary` 只在一次完整的服务端报价成功后才替换。
- 任何本地状态变化（勾选、套数）之后、服务端确认之前，标记为「金额待确认」：
  - 底部合计显示「更新中」；
  - 提交按钮禁用。
- 报价失败 → **回滚到服务端最后一次确认的状态**（勾选与套数一起回滚），并给一次行内提示。
- 每次报价带递增序号，只接受最新一次的响应（旧的直接丢弃）。
- 首屏只发**一次**报价：全量报价返回后直接用它算合计，不再补发第二次。
- **不要再拿 `maxPortionMultiplier` 去夹套数**：现在页面在报价回来后会把超出的套数夹回上限，这条逻辑必须去掉（改成 1–99 的技术兜底），否则自定义 5 套会被悄悄改回 3 套。
- 提交时校验的顺序：金额已确认 → 有地址 → 有勾选 → 商城开放 → 建单。
- 建单成功后立即锁页（按钮变「处理中」，不可再点）；建单与支付分开 try/catch，**建单成功就一定有订单**：
  - 建单成功 → 调起支付 → 支付成功 / 取消 / 失败，**三种情况都跳订单详情**，结果用弹窗或 toast 说明；
  - 只有「建单」本身失败才提示"提交失败"。

### 7.4 错误与空态

- **全部不可买**：进入专门空态「这些补剂暂时无法购买」，逐条列出「哪种 + 为什么」，底部两个出口：「联系客服」「返回我的制作单」。
  - 需要后端配合：`available.length === 0` 时**不再抛错**，改为正常返回一条**零值报价**（`lines: []`、金额全 0、`portionOptions: []`）+ `unavailable` 清单。
  - 选零值报价而不是 `quote: null`：老版本小程序读的是 `res.data.quote.lines`，null 会让它直接抛错；零值报价能让**新旧客户端都进空态**。
- **单条不可买**：清单内灰显 + 原因（现状保留）。
- **网络层不再自动弹 toast**：由页面统一用行内横幅展示真实原因，长文案能换行。
- **报价失败**：费用区显示横幅「价格没拿到：<真实原因>」+「重试」；提交按钮禁用。

### 7.5 收货地址

- `onShow` 每次都重新拉地址列表。
- 收到 `address-selected` 事件时：
  - 兼容两种 payload：`{ addressId }` 与纯字符串 id（`address-edit` 发的是字符串）。
  - 本地没有这个地址 → 重新拉列表并回显。
  - 仍然找不到 → 地址卡显示「地址已失效，请重新选择」，并禁用提交。
- 提交校验用「地址对象是否存在」而不是「地址 id 是否非空」。

### 7.6 大单提示（方案 A）

- 报价返回 `bagCount`。`bagCount > 大单提示袋数`（后台可配，默认 60 袋）时，在费用区下方显示一行：
  「本单分装量较大（约 90 袋），实际发货会顺延，我们会联系你确认。」
- **不拦单**，**不改** `packingDate` 的计算逻辑，**不占**产能名额的判断。

### 7.7 文案与视觉

- 「份」全部改成「套」（含按钮、提示、错误文案）。
- 删除库存提示块（顾客拿它做不了任何决定；文案是账本口径；后端开关默认关闭，线上从未显示过）。
- 「改用量」→「改制作单」。
- 勾选框改方形；提交按钮、勾选框、地址链接统一品牌墨绿/金色，去掉 `#4a90d9`。
- 页面标题（`pages.json`）从「一键购买补剂」改成「购买预分装补剂」。
- 「全不选」「改制作单」「重试」等文字型按钮的热区补到 ≥ 44px。

### 7.8 提交确认弹层

点「提交订单」后不直接建单，先弹底部弹层：

- 收货地址（可改）
- 补剂摘要：3 种 / 共 15 袋
- **打开弹层时重新取一次价**，显示最终金额（商品 / 服务费 / 运费 / 合计）
- 预计发货日
- 售后一句 + 「未付款 30 分钟内自动取消」
- 主按钮「提交并支付」

弹层是**唯一**的建单入口。

**重新取价后金额和页面不一致时**（例如后台刚改过价）：弹层里用醒目提示标出「价格有更新」，显示新合计，并要求顾客再点一次确认才建单；不自动提交、不静默替换。

## 9. 我的判断（除非老板反对，按此执行）

1. **技术兜底 99 套**：顾客看不到，只为防误输入打挂后台。
2. **大单提示阈值默认 60 袋**：约等于两天产能；后台可改。
3. **自定义弹层默认值 4**：连续点"+"从 4 开始最顺手。
4. **网络层不再弹 toast**，由页面行内展示（涉及 `utils/api.ts` 的默认行为，只在下单链路内改）。
5. **"全部不可买"由后端返回零值报价 + 清单而不是抛错**：前端才有办法展示逐条原因，老客户端也不会崩。
6. **说明图只折叠、不删**：新顾客仍需要这个概念，老顾客不该每次划过。
7. **确认弹层用页面内自带的遮罩实现**：项目里没有通用弹层组件（各页都是自己写的 `spec-modal` 那套），不为这一页单独抽组件。

## 10. 验收

### 行为测试（现在的字符串断言不够，必须补）

1. 改套数后报价失败 → 套数与金额都回到上一次确认值，提交按钮禁用。
2. 报价未返回时点提交 → 不发请求。
3. 全部不可买 → 渲染专门空态，含每种补剂的原因。
4. 新增地址后返回 → 地址卡正确回显。
5. 自定义 5 套 → 提交请求里 `portionMultiplier = 5`，页面合计 = 服务端返回的 total。
6. 连续快速改勾选 → 最终金额对应最后一次选择。
7. 建单成功、支付异常 → 不提示"提交失败"，跳订单详情。
8. 同一页连续点击提交两次 → 只产生一笔订单。

- 后端 `npm test` 通过；`npx tsc --noEmit` 通过（联调期间不跑 `npm run build`）。

## 11. 风险与已知取舍

1. **取消上限后没有任何"吃不完"的兜底**：袋子同一天分装、同一天到期，买越多越可能过期。已用"6 个月内吃完"的提示缓解，风险由顾客承担（老板已确认）。
2. **产能只提示不排期**：一单 90 袋只占 1 个排期名额，运营需要自己盯大单。已知并接受。
3. **老客户端兼容**：`totalDays` / `perDayCost` 恒为 null，老版本读到不会崩，但也显示不出天。
4. **改单链路涉及三端**：小程序改动必须走体验版上传，不走正式发布。

## 12. 开工前定下的实现口径（builder check 的答复）

下面是写计划前必须定、现已定下的六件事。都标了依据；老板如果不同意任何一条，改这里即可。

### T1 行为测试的载体：抽 composable + node 单测

小程序侧没有组件测试环境（无 jsdom / @vue/test-utils），也不引入。做法：

- 把"报价状态机"抽成一个纯 TS 模块（`useSupplementQuote` 或独立 store）：负责发起报价、序号去重、失败回滚、`quoteStale` 标记、套数与勾选的服务端确认。
- 页面只做渲染与事件转发。
- 单测在 node 环境里 mock `request`，覆盖 §10 的 8 条行为。
- 现有字符串断言中，锁 UI 结构的那几条保留（防回归），但**不能替代**行为测试。

### T2 金额一致性的最后一公里：create 带期望金额

- `POST /supplement-orders` 增加 `expectedTotal`（**整数分**，避免浮点）。
- 服务端重算后与 `expectedTotal` 不一致 → 拒绝建单，返回新的报价口径（业务码 + 最新合计）。
- 页面收到后：把金额更新到弹层、提示"价格有更新，请再确认"，**不自动提交**。
- 依据：§5 把"差一分"定义为失败；只靠"以服务端为准"不满足这个定义。

### T3 防重复下单：幂等键，不按内容判重

- 前端：提交按钮 in-flight 锁 + 建单成功后锁页。
- 后端：新增可空列 `client_request_id`（唯一索引，按 userId 维度），由小程序在**一次提交流程开始时**生成、重试时复用。
- **不按 `diySheetId` 或订单内容判重**：同一张制作单以后还想再买是正常复购，不能被挡。
- 代价：一次 Prisma 迁移（新增列 + 唯一索引）。按项目规则走 migration 脚本，不手改库。

### T4 「改制作单」：改成"退回制作单"，不在栈上留旧页面

已核实的事实：`diySheetId` 对同一 user+recipe+dog 是**就地更新同一行**，旧页面手里的 id 仍有效、内容却已变；而制作单页是从 URL 参数重建的（`recipeId/dogId/perMealG/dailyIntakeG/packagePlan`），本页的草稿里没有这些参数，所以"在本页重建"要么多拉一次制作单、要么重建出错的清单。

因此把问题从根上去掉：

- **「改制作单」只在草稿带 `diySheetId` 时出现**（复购草稿没有制作单，不显示）。
- 点击行为改为：`getCurrentPages().length > 1` 时 `navigateBack()`，否则 `redirectTo` 制作单列表；并 toast 提示「改完再点『购买预分装补剂』」。
- 本页因此**被销毁**，不存在"返回后看到旧数据"的场景，也不再往页面栈上叠页面。
- 由此**不需要**新增"按最新制作单重建清单"的接口或逻辑。

### T5 `enabled` / `warnings` 的落点

- **商城关闭（`enabled=false`）**：整页提示"补剂商城暂未开放" + 返回制作单，不渲染清单与提交。
- **未达最低起送（`minOrderAmount`）**：提交前就禁用按钮，费用区行内说明"商品金额 ¥X，未达最低起送 ¥Y"。
- **其余 `warnings` 不进顾客页**。核对过：液体补剂已经被 `findUnavailableReason` 判为不可买，永远不会进入报价；"未配置分装有效期"属于内部配置问题（内部提示，不吓顾客）。

### T6 支付超时文案：读配置，不写死

- 报价响应增加 `paymentTimeoutMinutes`。
- 弹层按配置渲染"未付款 X 分钟内自动取消"；配置为 0（不自动关单）时**不显示这句**。
- 依据：custom-recipe 那条链已经是这么做的（`utils/custom-recipe-order.ts`），补剂链保持一致。
