# 采购-报销接入 AI：订单截图识别（第一期）设计

- 日期：2026-11-04
- 提出：老板
- 状态：待确认
- 范围：第一期（截图识别 → 人工核对 → 生成采购记录 → 报销预填）
- 原型：`mockups/procurement-ai/prototype.html`（同目录 `shots/` 为逐页截图）

---

## 0. 一页纸

员工在「采购清单详情」上传商超订单截图，AI 读出商品行、金额和费用，按**清单需求**逐项匹配，
员工核对后一键生成采购记录；报销页自动预填金额、费用和凭证，员工确认提交。
AI **不自动提交、不自动审批**。

用 10 张真实截图实测（DeepSeek 生产模型）：9 笔订单、67 行，单价与数量 67/67 正确，
商品额/运费/包装/实付 40 项全对，平均 2.6 秒/单。
已知缺陷：盒马订单号 3/10 读错、"是否截图完整"误判 1 次、"称重退差价"标签误报 2 次——均已在规则里处理。

---

## 1. 要解决的问题

1. 员工现在要对着订单一行一行手打：品名、数量、金额，一单十几行。
2. 商超订单常常公私混在一起（样本 9 单里 4 单含个人采购，个人金额占 21%），整单报销会多报。
3. 订单截图会被折叠（沃尔玛「共 18 件」只显示 3 行），AI 会安静地少记。
4. 员工改不了、退不了：一旦报销就不能动，退货退款没有出口。

## 3. 目标 / 非目标 / 反目标

**目标**

- 上传订单截图后，员工只需核对，不再逐行手打。
- 公私混单能拆清楚，报销金额与凭证差额可解释、可审计。
- 截图不完整、重复上传、规格读不出来时，系统拦住或提示，不产生错账。
  - 2026-11-05 修订：**「金额对不对」只提示、不拦截**。优惠/满减/特价/包装费/称重退差都会让
    商品小计与各行合计对不上，公式化判断只会误报（盒马特价单：小计按原价、商品行按实付价）。
    完整与否由模型判断；有提示时员工勾选「我已对照原图核对」即可生成，差额仍留档，
    报销审核页会作为中风险提示显示。真正会拦人的只剩「没匹配原料 / 缺数量 / 缺金额」。
- 失败可降级：AI 不可用时照常手填，不阻断采购。

**非目标（本期明确不做）**

- 不做称重退差的台账与追回。
- 不做自动提交、自动审批、自动打款。
- 不做商超 App 对接、不做订单同步。
- 不做供应商管理、比价、采购议价。
- 不做退货物流跟踪。
- 不改财务总账科目与报表口径（只在报销单上增加差额字段）。

**反目标（做到了也算失败）**

- 因为 AI 读错导致库存或成本数字错，且系统没提示。
- 员工为了省事把公账商品标成个人、或个人标成公账，且无人复核。
- 报销金额和凭证金额对不上，却没有任何说明。
- 为了接 AI 把现有手工流程弄坏（不能手填了、不能改了）。

## 4. 流程对比

**现在**

```
生成日采清单 → 开始采购 → 逐个原料「记录」→ 选商品、填数量金额
→ 确认完成（入库）→ 去报销 → 勾清单、填运费包装、传凭证 → 提交
```

**第一期之后**

```
生成日采清单 → 开始采购
  → 上传订单截图（1~5 张，可多单）
  → AI 识别 + 自检 + 按清单匹配（约 3 秒）
  → 核对页：逐行确认「算采购 / 算个人 / 未匹配」
  → 一键生成采购记录（可再改）
  → 确认完成（入库，不变）
  → 去报销：金额、运费、包装、凭证、差额说明已预填
  → 员工确认提交（不变）
```

管理端本期只做**只读展示**：报销详情增加「凭证金额 / 报销金额 / 差额 / 差额原因」四项，审批流程不变（仍是上传付款凭证即完成）。审核 Agent 与审核台属于第三期。

## 5. 页面与交互

原型见 `mockups/procurement-ai/prototype.html`，逐页截图见 `shots/`。

| 编号 | 页面 | 要点 |
|---|---|---|
| P0 | 采购管理（列表页） | 不改结构；清单卡片加一行「含截图识别 N 条」 |
| P1 | 采购清单详情（改造） | 「用订单截图快速录入」卡片常驻；未开始采购时点击先确认开始 |
| P2 | 上传订单截图 | **不选渠道**；1~5 张，每张算一笔订单；三条截图指引 |
| P3 | 识别中 | 按订单数显示进度；20 秒超时按失败处理 |
| P4 | 识别结果核对（核心） | 顶部按订单切换；渠道可改；行级四态；**每行可点开修改** |
| P4b | 修改一行 | 改数量/单价/匹配原料/标记个人；改动会与截图比对 |
| P5 | 选择原料 / 新建商品 | 只列清单内原料（20~30 项），**不做搜索**；分组 + 最近使用 |
| P6 | 采购记录（生成后） | 每条带「来自截图」徽标，可编辑、可删 |
| P7 | 报销提交（预填） | 清单、运费、包装、凭证已填；显示凭证/报销/差额 |
| P8 | 报销详情（员工） | 「撤回报销」+ 解锁说明；已报销时按钮消失 |
| P9 | 管理员审核台（第三期） | Agent 建议 + 凭证对比 + 通过/驳回/退回 |

**P4 行级四态的判定**

- **已匹配**：订单行 → 采购商品 → 原料，且该原料在本次清单里。绿色。
- **个人**：员工手动标记，或未匹配且员工确认不要。灰色。
- **未匹配**：订单行在清单里找不到对应原料。红色，必须处理（选原料或标个人）。
- **需新建商品**：原料匹配上了，但该原料下没有可用商品。黄色，给新建入口。

**多笔订单**

- 一次上传最多 5 笔订单，每张图算一笔；核对页按订单切换，底部合计跨单累加。
- 同一笔订单需要多页时，引导员工截长图，不做「多页合并」（容易把两笔单合成一笔）。

**生成规则**

- 每行都可以点开修改：数量、单价、匹配原料、标记个人；改动会标「已改动」。
- 只有「已匹配」的行会生成采购记录；「个人」和「未匹配」不生成。
- 同一订单行只能生成一条记录；同一原料多行可以合并（默认不合并，保留原始行）。
- 生成前校验：每行金额 × 数量必须与订单行小计一致（±0.01）。
- 生成后仍可在记录列表里改数量、金额、商品。

## 7. 接口

前缀 `/api/v1/staff/purchasing`，守卫沿用 `AuthGuard + StaffGuard`。

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/upload-order-screenshot` | 上传单张截图到 COS（`purchase-order-screenshots/`，私有 ACL） |
| POST | `/lists/:id/order-imports` | 传 imageUrls（1~5 张，每张一笔），同步识别，返回 imports[] |
| GET | `/lists/:id/order-imports` | 该清单的识别记录 |
| PATCH | `/order-imports/:id` | 改渠道/订单号/时间（识别错了手动修正） |
| PUT | `/order-imports/:id/lines/:lineId` | 改单行：数量/单价/匹配原料/标个人 |
| POST | `/order-imports/confirm` | 传 importIds[]，事务内批量生成采购记录 |
| DELETE | `/order-imports/:id` | 放弃本次识别（软删 status=DISCARDED） |

报销侧：

- `POST /reimbursements` 的 DTO 增加 `voucherAmount?`、`differenceNote?`；
- 校验：`voucherAmount ≥ totalActualCost`；差额 = `voucherAmount - totalActualCost`，自动算；
- 纯补货报销单：`platformShippingFee`、`platformPackagingFee` 必须为 0（R10）。

## 8. AI 识别与匹配

### 8.1 管线

```
手机选图（压缩，宽 ≤1080）
 → 上传 COS（私有目录）
 → 服务端切段：每段 ≤2200px，沿空白行切，最多 6 段
 → 一次调用送入全部段（OpenAI 兼容多图）
 → 输出 JSON（渠道、单号、时间、行、费用、实付、完整性）
 → 自检：Σ行小计 vs 商品金额；Σ数量 vs 件数
 → 按清单需求匹配
 → 落 import + lines（草稿，不生成采购记录）
```

### 8.2 提示词要点（版本号记入 `prompt_version`）

1. 三家字段名映射：盒马「商品小计/运费/环保包装费/实付合计」、山姆「商品总金额/配送费/包装费/实际支付」、沃尔玛「商品金额/运费/包装费/实际支付」。
2. 「¥29.00 ×2」中的 29.00 是单价，行小计 = 单价 × 数量；用合计校验。
3. 必须自己把行小计加一遍，与商品金额比对；不一致 → `incomplete=true` 并写差额。
4. 件数校验用 **Σ数量**，不是行数（实测误判过）。
5. 只有出现「补差退款 X 元」的数字才算退差；「称重退差价」标签不算。
6. 读不到的字段给 null，禁止编造；不输出姓名、电话、地址。
7. 输出必须是单个 JSON 对象。

### 8.3 匹配

**方向**：以清单里的原料为主线，去订单里找；不反过来给订单行硬找原料。

1. 订单行 → 采购商品：先去规格后比名称（品牌前缀可有可无），再按关键词（主料名）。
2. 采购商品 → 原料：`ProcurementSku.ingredientId`。
3. 原料不在本次清单 → 未匹配。
4. 原料在清单但无可用商品 → 需新建商品。
5. 置信度：名称完全一致且金额自洽 = HIGH；仅关键词命中 = MEDIUM；无 = LOW（默认人工）。

**为什么不做全量自动落库**：实测 67 行里只有 40 行能对上（59.7%），且 21% 是个人采购；强行自动会错账。

### 8.4 配额与降级

- 新用途 `PURCHASE_ORDER_IMPORT`，后台「AI 设置」可单独配模型；未配置回退全局默认。
- 配额沿用现有模式：每人每天 30 次、全系统每月 3000 次。
- 模型超时/失败 → 返回「识别失败，请手填」，不阻断；员工可重试。
- 重复图片（同 imageHash）→ 直接拒绝并提示「这张图已经导入过」。

### 8.5 识别结果如何落成采购记录

这是整个链路最容易出错的一步，规则先定死：

1. **数量**：订单行的「1 盒 / 2 袋」直接作为 `actualQuantity`，单位取该采购商品的 `purchaseUnit`。
2. **换算**：克数由 `ProcurementSku.purchaseToBaseRatio`（= 件数 × 单件净含量）算出，AI 不参与换算。
3. **规格不一致**：订单写 250g、商品却是 500g/袋时**不自动折算**，该行降级为「需新建商品」，
   由员工确认后新建一个 250g 的商品，或改用正确商品。绝不按比例硬算。
4. **金额**：`unitPrice × qty` 必须等于截图行小计（±0.01），否则不允许生成。
5. **一行一记录**：同一商品出现多行时**不合并**，保留原始行，方便与截图逐行对账；
   员工可在生成后手动合并。
6. **件数与规格**：`actualPackageCount / actualPackageSize / actualPackageUnit`
   由商品净含量预填，允许员工修改；改了以后按新值重算克数。

## 9. 边界与异常

| 场景 | 处理 |
|---|---|
| 截图折叠、行数不够 | 自检差额 → 提示「截图可能没展开，请点开『共 N 件』后重截」 |
| 订单号读错 | 不阻断；显示可编辑，去重靠图片指纹 |
| 称重退差 | 提示「本单有 N 元退差，按实付记账」，不扣减 |
| 混合订单 | 个人行不进采购；报销差额说明自动生成 |
| 一单覆盖多张清单 | 本期：一次只对一张清单识别；多清单需分开上传 |
| 同一订单多张图 | 一次导入内合并；重复图片拒绝 |
| 原料无商品 | 行内给「新建采购商品」，预填名称/规格/单价 |
| 员工改金额 | 允许，但记录页显示「与截图不一致」提示，供审核 Agent 核对 |
| 撤回 | 待审核可删；已报销不可删（R9） |

## 10. 权限、审计与隐私

- 上传、识别、生成：员工/管理员（`StaffGuard`）。
- 截图存 **私有** COS 目录，前端用短期签名 URL 展示（现有 `getSignedUrl` 能力）。
- 模型调用使用签名 URL，不把 bucket 公开。
- 识别记录保留 `rawResult`、模型、提示词版本、确认人，供追查。
- 采购记录保留来源截图 key；报销单保留凭证与差额说明。

## 11. 验收标准

1. 用现有 10 张截图回归：9 笔订单的行数、单价、数量、商品额、运费、包装费、实付 100% 一致。

4. 同一张图第二次上传被拒绝。
5. 零商品原料可现场新建商品并落记录。
6. 关掉 AI 配置后，员工仍可手填完成采购与报销。
7. 待审核报销单撤回后，清单解锁（需员工再点「撤回完成」，不自动），可改记录、可重新提交；已报销的单据无撤回入口。
8. 纯补货报销单不能填运费/包装费。

## 15. 评审答疑（2026-11-04 补，以此为准）

设计稿过了一轮独立评审，提出 5 个会改变实现的问题，逐条定夺如下。

### 15.1 撤回：保留两步，不做自动解锁

- 删除报销单**只解除清单关联**，不自动执行「撤回完成」；
- 员工仍需自己点「撤回完成」，并弹二次确认：*「撤回归还库存流水。如果这批货已经领用或投产，请不要撤回，联系管理员。」*
- 不新增「是否已领用」的自动判定——库存流水里没有这个字段，硬做会误伤；本期靠文案与人工判断。
- 一期做入口与文案（约 1 人日），不做自动链路。

### 15.2 差额：可以为空，不可以为负

- 差额 = 凭证金额 − 报销金额；**小于 0 直接拦下**，提示「报销金额超过凭证金额，请检查采购记录」。
- 称重退差不会产生负差：截图上的实付是退差前金额，仍然 ≥ 报销额（R7）。
- 一张报销单含多张订单时：`voucherAmount` = 各导入单实付之和，允许员工手工修正；每张订单分别登记。

### 15.3 凭证：订单截图私有，报销凭证存 key + 签名 URL

- 订单截图存私有目录，用于识别与审计；
- 报销单新增 `receiptKeys` 列（实体里已有该字段，但一直没落库），后台详情接口返回**短期签名 URL**；
- **不**把订单截图复制进公开的 `reimbursement-receipts` 目录；
- 影响面：admin-web 报销详情的图片展示改走签名 URL，重提时的凭证比对改比 key（约 2～3 人日，含在一期补里）。

### 15.4 识别：只做同步，不做轮询

- 单次请求 20 秒超时；实测平均 2.6 秒，够用；
- 失败**不落库、不扣当日配额**，前端提示重试；
- 去掉「稍后回来」，P3 就是等待页。

### 15.5 数量与规格：订单行给数量，商品给规格，员工在 P4 确认

- 识别行新增 `unit` 字段（盒/袋/份/瓶）；
- P4 每行显示「1 盒 × 500g/盒」，规格与单位可改；
- 若订单规格与商品规格不一致 → 降级为「需新建商品」，绝不按比例折算；
- 生成时复用现有 `addPurchaseRecord` 的归一化逻辑，不另写一套换算。

### 15.6 两个小口径

- **图片去重**：唯一键仍为 `[purchaseListId, imageHash]`，但 `DISCARDED` 的记录不参与去重，允许重新导入；跨清单允许重复（本就是不同采购）。
- **运费/包装费**：所有**非日采**清单（补货、包材）都不能填，不只是补货。

## 16. 第二轮评审答疑（2026-11-04 晚）

### 16.1 采购管理页要不要改

不改结构与交互，只在清单卡片上加一行「含截图识别 N 条」。
截图识别是清单详情的职责，列表页保持“选日期、生成、看清单、进详情”。
新增 P0 原型。

### 16.2 上传入口什么时候出现

卡片**常驻**，不藏在「开始采购」之后。
未开始采购时点它，弹一句「开始采购后才能录入，是否现在开始？」，确认后直接进入上传。
理由：入口藏起来员工会找不到；但没开始采购就生成记录会破坏现有状态机，所以用一次确认代替隐藏。

### 16.3 渠道不给用户选

上传页不选渠道；AI 识别（实测 10/10 正确），结果页顶部显示「渠道 盒马 ▾」可改。
用途正是你说的：识别失败或识别错时手动修正。

### 16.4 多笔不同渠道的订单

支持。一张图 = 一笔订单，一次最多 5 笔；核对页按订单切换，合计跨单累加。
同一笔订单的多页不做合并（容易把两笔合成一笔），引导员工直接截长图。

### 16.5 识别结果能不能改

能。每一行点开就是 P4b：改数量、单价、匹配原料、标记个人。
改动会标「已改动」，审核时与截图逐行对照；把金额改到合计对不上时，直接拦住不让生成。
另外允许「删除这一行」（AI 多读）和「添加一行」（AI 漏读）。

### 16.6 选原料要不要搜索

不要。清单只有 20~30 项，按类型分组、常用的排前面就够；搜索框反而占地方。
P5 已去掉搜索框。
