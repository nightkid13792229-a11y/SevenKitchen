# 食材成本口径归位 + AI 建档收尾（设计）

- 日期：2026-11-07
- 提出：老板
- 状态：待确认
- 范围：**食材（FOOD）** 的成本口径 + 后台「AI 添加原料」食材线的收尾
- 不动：补剂、包材、小程序、采购清单预估、推荐商品

---

## 0. 一页纸

**问题**：食材的采购口径（采购单位、换算倍数、单价）长在了标准原料档案上，
而食材本来就另有一层采购商品，同形字段各有一份。

- **算价**只读档案那一份；
- **采购**只读商品那一份；
- 档案那份在后台**没有任何编辑入口**，AI 建档时被强制写成 `g / 1 / 0`。

结果是：新建的食材原料价格恒为 0，一旦被选进食谱，成本按 0 算，售价跟着偏低，
而整条链路不报错、不提示。

**方案**：让档案只管一件事实——**每基准单位多少钱**（结算结果）；
采购口径整体归位到采购商品；新建食材必须落一条带价的采购商品，
它的价用来**初始化**档案成本。

**改动面**：一次数据折算 + 一张价格历史表 + 三个写入点 + **一处采购折算修正**
（评审发现：采购记录的实际数量一直按原料换算折，换算改成 1 之后会把「2 袋」记成 2 克，
必须改成按采购商品的换算折——这条本来就是个缺陷，见 §10.1）；后台三处界面；小程序不改。

## 1. 现状（为什么非改不可）

### 1.1 字段归属是反的

| 类型 | 能否挂采购商品 | 采购口径实际存在哪 | 后台能编辑吗 |
|---|---|---|---|
| 补剂 | **不能**（接口直接拒） | 原料档案 | 能，三格都有 |
| 包材 | **不能** | 原料档案 | 能，三格都有 |
| 食材 | **能，且可多条**（不同品牌/规格/渠道） | **两边各一份** | 档案那一份**没有入口** |

证据：`ProcurementSkuService.assertFoodIngredientCanOwnProcurementSkus()`
只允许 `FOOD` 挂采购商品。

也就是说：**只能挂单个商品的两类，口径挂在档案上是对的；
能挂多个商品的那一类，口径反而也挂在档案上**——这一条本身就不成立。

### 1.2 食材档案那一份是死数据

- **AI 建档**（`ingredient-creation-commit.service.ts`）：
  `purchaseToBaseRatio: 1`、`currentPricePerPurchaseUnit: 0`、`purchaseUnit = 基准单位名`。
- **后台表单**（`IngredientForm.vue`）：食材**不渲染**「采购单位 / 换算倍数 / 当前采购价」三格；
  保存前 `sanitizeTopLevelFieldsForFood()` 会把这三格**强制写回** `g / 1 / 0`。
- **唯一能手填的地方**是「库存」页的「改价格」，而它按**采购单位**填——
  AI 建的食材采购单位就是 `g`，在那儿填 39.9 会变成 **39.9 元/克**。

### 1.3 算价只认档案那一份

`PricingService.calculateRecipeCost()` →
`Ingredient.getUnitCost()` → `currentPricePerPurchaseUnit ÷ purchaseToBaseRatio`。

2026-11-06「单一来源」改造删掉了读时推导（当时的四档：最近采购价 → 创建价 →
商品价 → 当前价），并明确写死「算价一律读档案当前价」。所以
**采购商品上的价目前不参与任何食谱成本计算**。

### 1.4 后果：从建档到首采之间是空窗期

```
AI 建档（成本 0）
   ↓  食谱里已经能选到它
食谱 / 试吃装测算 / 订单定价（这一项成本 = 0）
   ↓  没人发现
售价偏低，毛利被吃掉
```

对照：补剂商城对 0 价是有硬拦截的（`NO_PRICE`：「进货价为 0，无法计价」）；
食谱与订单这条线**没有任何拦截或提示**。

## 2. 已锁定的决定（老板 2026-11-07）

| 编号 | 决定 |
|---|---|
| R1 | 食材成本只保留**一个数**：每基准单位成本（克 → 元/g；毫升类 → 元/ml） |
| R2 | 采购口径（采购单位 / 换算 / 单价）归采购商品；档案上那两格对食材**退休** |
| R3 | 新建食材**必须至少落一条采购商品**；允许先存草稿，但不算走完，列表要能刷出来 |
| R4 | 采购商品的价必须**接进成本**：建档时初始化，报销时覆盖 |
| R5 | 采购商品的价**不删**；采购清单预估、推荐、报销「预估 vs 实付」对照都不动 |
| R6 | 档案成本在原料页**只读展示**，并且**能查历史** |
| R7 | 硬拦只在**发布**这一关；下单不拦；编辑时行内标红 |
| R8 | 一次做完，**含存量折算**；折算前后已发布食谱成本必须一分不差 |

## 3. 目标模型

### 3.1 三个数，各归各位

| 数 | 存在哪 | 含义 | 谁写 |
|---|---|---|---|
| 商品价 | `procurement_sku.current_purchase_price` | **这个商品**多少钱（元/件） | 建档/员工新增时人填或截图识别；报销回写 |
| 商品换算 | `procurement_sku.purchase_to_base_ratio` | **这个商品**一件多少基准单位 | 同上（件数 × 每件净含量） |
| 原料成本 | `ingredient.current_price_per_purchase_unit` | **一克**多少钱（结算结果） | 建档初始化；报销覆盖；手工改价 |

### 3.2 一条公式

```
每基准单位成本 = ingredient.current_price_per_purchase_unit
                ÷ ingredient.purchase_to_base_ratio
```

**食材不变量**：`purchase_to_base_ratio ≡ 1`，`purchase_unit ≡ 基准单位展示名`。
因此对食材而言，`current_price_per_purchase_unit` **就是**「每克多少钱」，
不再需要一次除法，也不会再出现两套口径。

> 不新增列：这一列对补剂/包材仍是「元/采购单位」，语义没变；
> 只是食材把它固定成「元/基准单位」。一列一个含义，没有分叉。

### 3.3 三个写入点

1. **初始化**（R4）：创建采购商品时，若「原料成本 = 0」且「该商品有价」，
   写入 `成本 = 商品价 ÷ 商品换算`。
   **只补空，不覆盖**——已有价的一律不动。
2. **报销覆盖**：沿用现有链路。因为 `ratio = 1`，现有公式
   `baseUnitCost × ingredientRatio` 自动等于「元/g」，**回写代码不用改**。
3. **手工改价**（库存页）：保留，但必须写历史，否则历史会漏。

### 3.4 一个读点

`Ingredient.getUnitCost()`，没有第二套。下游（订单、试吃装、采购预估、调价防呆）
全部经由它。

### 3.5 为什么不让算价直接读采购商品的价

一条食材可以有多条采购商品，而**食谱明细不记录用的是哪一条**
（`recipe_item` 里没有 `procurement_sku_id`）。真去读，就必须替它挑一条。
2026-11-06 删掉的旧逻辑正是「自动挑一个 SKU」，结果是「专挑同档最贵的，
和实际付的钱脱节」。

商品价回答的是「这个商品多少钱」；原料成本回答的是「我一克花了多少钱」。
后者是把前者折平之后的结果，与品牌无关。两者不是二选一，是上下游。

## 4. 数据折算（存量归位）

### 4.1 规则

对 `type = FOOD` 且 `purchase_to_base_ratio ≠ 1` 的原料：

```
新成本 = 旧成本 ÷ 旧换算
新换算 = 1
新采购单位 = 基准单位展示名
```

数学上与原值等价（`旧成本 ÷ 旧换算` 与 `新成本 ÷ 1` 是同一个数），
所以已发布食谱的成本不变。

### 4.2 迁移要点

- **先备份整表**（照 11-06 那次的写法，建 `ingredient_food_cost_backup_20261107`），
  回滚可原样回填。
- 精度：`current_price_per_purchase_unit` 是 `numeric(14,6)`。
  折算用**numeric 除法**（不要先转 float），结果按 6 位小数四舍五入。
  绝对误差上限 `1e-6 元/g`，折到 1kg 净食约 `0.001 元`——显示到分不会变，
  但极少数正好卡在舍入边界的行可能差 1 分，需在双跑报告里逐条解释。
- `purchase_unit` 回填 `COALESCE(NULLIF(unit_display_label,''), lower(base_unit))`。
- 落一条历史记录并在 note 里写明「2026-11-07 口径归位折算」，便于日后解释。

### 4.3 对账（不通过不许上线）

1. **逐条对账**：`round(旧成本 ÷ 旧换算, 6) == 新成本`（判据见 §10.6，
   不要直接比原值）。
2. **成本双跑**：79 个已发布食谱 × 1kg 净食，新旧成本差异必须是 `0.00%`
   （允许个别 0.01 元的舍入边界，须逐条解释）；再抽 428 张历史订单快照复算一遍
   （照 11-06 的做法）。
3. 脚本产出对账报告，随 PR 提交。

## 6. 边界情况

| 场景 | 行为 |
|---|---|
| 建档时只填了采购商品，没填价 | 商品照建，成本保持 0，原料打「未定价」标；不算走完 |
| 一条食材有多条采购商品 | 成本只由**第一次**初始化 + 之后每次报销覆盖；商品之间互不影响，采购时可任选 |
| 已有价的老食材新建一条商品 | **不覆盖**已有成本（只补空）；该商品的价只用于采购 |
| 报销里同一原料多笔 | 按金额加权平均写一个成本（现有逻辑） |
| 报销把价写低/写高很多 | 三道闸不变：0 元/负数拒、5 倍离谱拒、超 8% 挂起等人工 |
| 毫升类原料 | 成本是「元/ml」，换算按密度；同一套逻辑 |
| 食材没有任何采购商品 | 补货建议、采购清单不再猜「买几袋」，直接标「待补采购商品」 |
| 食谱引用 0 成本食材 | 编辑时行内标红；发布时拦住；下单不拦 |
| 存量无采购商品的老食材 | 折算后成本仍>0 的照常用；=0 的进「待定价」清单，由运营补商品 |
| 批量导入的食材（清单里带商品价） | 走 B3，导入完自动有成本，不用再手工补 |
| 「复制新增」出来的食材 | **不继承**原原料的成本，落 0，打「待补采购商品」标（避免把别条的成本带过来） |

## 8. 风险与回滚

| 风险 | 处置 |
|---|---|
| 折算把某个原料的价算错 | 先备份、再加逐条对账；对账不过不上线 |
| 有代码仍假设「食材换算可能不是 1」 | B10 加断言 + 全仓扫 `purchaseToBaseRatio` 的读取点 |
| 发布阻拦挡住正常操作 | 只拦 0 成本；提示里直接给「去补采购商品」的链接 |
| 初始化价是错价 | 闸门对初始化同样适用（0 元/5 倍直接拒）；历史可追溯 |

## 10. 评审补丁（2026-11-07 · 设计评审后定稿）

### 10.1 采购记录的折算改用采购商品的换算（重要修正）

**问题**：`purchasing.service.ts` 的 `resolvePurchaseToBaseRatio()` 读的是**原料档案**的换算。
把食材换算固定成 1 之后，员工按旧方式填「买了 2 袋」会被记成 **2 克**。

**决定**：折算改为**优先取该行采购商品的换算**，没有 SKU 才退回原料档案。

**为什么必须改**：实际买的是某个商品，换算就该跟商品走。这不是为了配合本次改造，
而是一条本来就存在的缺陷——一条原料有两个不同规格的商品时（500g / 400g），
今天填「2 件」算出来的基数就对不上。折算对了，`actualCost ÷ actualBaseQuantity`
算出来的「元/g」才对。

**影响**：新增 B11；**存量采购记录不回改**（`actual_base_quantity` 已落库）。
附带：`actualQuantity`（按采购单位计的展示数量）分母同样改用商品换算，
否则会出现「2 袋 = 800 克 + 数量显示 1.6 袋」这种对不上的数字。

### 10.2 没有采购商品的原料，采购清单怎么出

**决定**：**照常列出，不丢项**。单位显示基准单位（g / ml），行上标「待补采购商品」，
`estimatedCost` 用档案成本 × 需要量。`resolveProcurementExecutionProfile()` 的返回值
形状不变，只多一个 `needsProcurementSku` 标志。

§5.3 写的「采购清单价格预览不动」，指的是**这个功能不删、不缩水**，
不是「这个函数一行不许改」。两处以本节为准。

### 10.3 R3 不落到数据库层

**决定**：不给 `Ingredient` 加状态列。「走没走完」是**派生判断**：
`FOOD` 且没有启用中的采购商品。

落点只有三处：AI 收尾那一屏、新建食材保存后弹的卡、原料列表的筛选；
再加发布时兜底。批量导入、AI commit、seed **一律不拦**——它们各自有完整的路径。

这样做的好处：不新增状态字段（少一个会和真实数据打架的东西），
坏处是「未完成」不是一个事件，只能靠列表筛出来。

### 10.4 价格历史覆盖三种原料；库存页改价必须改

**决定**：
- 新表 `ingredient_price_history` **三类原料都写**（手工改价是三类共用的），
  但只在食材页展示。
- 库存页对食材的「改价格」改成「**改成本（元/克）**」：输入框标单位、
  旁边实时折算「≈ ¥39.90 / 1 袋（按默认商品 500g）」、并走写入闸（0 元 / 5 倍直接拒）。
  列入改动面 F9。

**为什么**：折算后所有食材都是「元/克、6 位小数」，在这个框里填 39.9 就是
39.9 元/克——§1.2 正是拿它当反面例子，不改就是明知故犯。

### 10.5 「来源」是替换，不是并列

**决定**：把现有 `priceBasis` 卡片的来源判定**整体换成读新流水表**的最新一条
（`REIMBURSEMENT` / `INIT_FROM_SKU` / `MANUAL` / `MIGRATION`），
同时更新 `ingredientForm.priceBasis.regression.spec.ts`。
**不新加并列的 `costSource`**——两套来源判定必然有一天互相打架。

### 10.6 对账判据

```
round(旧成本 ÷ 旧换算, 6) == 新成本
```

直接比原值在 6 位小数下不会恒等（旧值本身可能是更长的数），会制造假红。
