## 0. 一句话

把「一张订单 = 一个单号 = 一个运费」改成「**一次发货 = 一票 = 1~N 张订单 + 1~M 个包裹**」。
合并和拆包不是两个功能，是同一个模型的两个方向：包裹里装几张单，就是合并；一张单被装进几个包裹，就是拆包。
运费按**净重占比**从包裹分到订单，尾差落在这张包裹里排序最后的那张单上。

## 3. 模型

```
一次发货（一票）
├── 订单：A、B            ← 合并发生在这一层
└── 包裹：1、2            ← 拆包发生在这一层
     ├── 包裹 1（单号 SF…，运费 20.00）= A 的 7 袋 + B 全部
     └── 包裹 2（单号 SF…，运费 12.00）= A 的 7 袋
```

**不变量**

| # | 不变量 |
|---|---|
| I1 | 一张订单在同一时刻只能属于一票「未撤销」的发货 |
| I2 | 一票里的订单必须是**同一顾客 + 同一收货地址** |
| I3 | 一票里的订单必须都可发货（鲜食 `FREEZING`；试吃装 `PAID/FREEZING`） |
| I4 | 一个包裹恰好一个运单号；运费 ≥ 0，最多两位小数 |
| I5 | Σ（订单分到的运费）= Σ（包裹运费），**精确到分** |
| I6 | 每张订单的**袋数必须全部分配**到包裹，不能多也不能少（多规格订单按规格分别校验） |

> 袋是实物单位（110g / 250g 一袋），拆包只能整袋挪；克重只用于**算钱**。
> 两者都来自订单的分装方案，员工不用手填重量。

### 4.5 `Order.actual_shipping_fee` 怎么办

保留原列，提交时把「这张单在各包裹里的分摊额之和」写回去。
好处：老报表、老接口、老页面**一行都不用改**；新页面读包裹明细，老页面继续读这个数。

> 回填：**不回填历史订单**。老订单没有 `order_shipment` 记录时，读路径降级成「把订单上的单号 / 运费当成一个虚拟包裹」。428 张历史单不动，风险最低。

## 5. 员工端流程

### 5.1 入口

待发货列表（`staff-orders/index.vue`）右上角加「合并发货」：
点它进入**选择态**，每张卡片左上角出现勾选框，底部浮出「合并发货 · 已选 N 单」。
不点这个按钮时，列表和现在完全一样（不打扰日常操作）。

> 2026-11-10 补记：这个入口最初做在旧「后台订单」列表上，但该页在 10-21
> 已被「订单中心」取代、不再有任何入口，合并发货因此点不到。现把开关搬到
> 「订单中心」列表（自动切到鲜食 / 待发货），下面的发货单流程原样复用。

### 5.2 合并

1. 勾选 2~N 张单（跨地址或跨顾客时，勾第二张直接提示「收货地址不同，不能合并」）
2. 点「合并发货」→ 进「发货单」页
3. 页面顶部：`共 2 单 · 总净重 4.18kg · 总 22 袋`
4. 默认只有 **1 个包裹**，里面装着全部订单的全部袋数
5. 填快递公司、单号、**这个包裹实付的运费**
6. 点「确认发货」→ 返回列表，两张单一起变成「已发货」

### 5.3 拆包

在「发货单」页点 **「＋ 再拆一个包裹」**：

1. 新建包裹 2，**默认是空的**
2. 每张订单在**每个包裹**下都有「袋数」加减器（`− 7 +`）；**订单有多个分装规格时按规格分行**（`110g × 14` 一行、`250g × 4` 一行），员工分的是"这个规格的几袋"。下面一行小字显示「还剩 N 袋未分配」
3. 员工把袋从包裹 1 挪到包裹 2，直到全部为 0
4. 每个包裹**各自**选快递、填单号、填运费

> 系统不判断「该不该拆」、不提示超重、不按重量自动分袋 —— 这是老板 2026-11-07 明确要求的。

### 5.4 混合（一单拆两包、另一单只进第一包）

同一个界面天然支持：包裹 1 里 A 填 7 袋、B 填 4 袋；包裹 2 里 A 填 7 袋、B 填 0 袋。
分摊时 A 同时从两个包裹各拿一份。

### 5.5 提交校验（一次性拦住，不让人半路失败）

| 校验 | 提示 |
|---|---|
| 每张订单的袋数都分配完 | 「A 还有 3 袋没装进任何包裹」 |
| 多规格订单：**每个规格**的袋数都分配完 | 「A 的 110g 那档还有 2 袋没装」 |
| 每个包裹至少 1 袋 | 「包裹 2 是空的，删掉它或者装点东西」 |
| 每个包裹都有快递公司 + 单号 + 运费 | 「包裹 2 还没填运费」 |
| 运单号不能在同一票里重复 | 「两个包裹填了同一个单号」 |
| 订单仍是可发货状态 | 「这单刚被别人发了，刷新看看」 |
| 订单没有属于别的票 | 同上 |

全部通过才提交；提交在**一个事务**里完成，任何一步失败整票回滚。

## 6. 运费分摊算法

**每个包裹单独分，再把订单在各包裹拿到的份额相加。**

```
对每个包裹 p：
  totalW = Σ(该包裹里各订单的 weight_g)
  feeCent = round(p.actual_shipping_fee × 100)          // 换成"分"，整数运算
  对包内每张订单 o：
     raw = feeCent × o.weight_g / totalW
     cent[o] = floor(raw)
  left = feeCent − Σ cent[o]                            // 只可能是 0..(订单数-1) 分
  按「重量从大到小、同重量按下单时间」排序，把 left 分给**排序最后的那张单**
  （也就是老板说的"最后一单吃零头"）
```

- 用整数「分」算，避免浮点误差
- 每个包裹分摊完，`Σ allocated_fee = 包裹运费`，一分不差（I5）
- 订单级 `actual_shipping_fee = Σ 它在各包裹的 allocated_fee`

**例 1（合并，1 包 2 单）**：A 1.54kg、B 2.64kg，包裹实付 20.00

| 订单 | 占比 | 分摊 |
|---|---|---|
| A | 36.84% | 7.37 |
| B | 63.16% | 12.63 |
| 合计 | | 20.00 ✓ |

**例 2（拆包，1 单 2 包）**：A 14 袋分两包，包 1 运费 20.00、包 2 运费 12.00
→ A 的运费 = 20.00 + 12.00 = **32.00**（单包裹场景不需要分摊）

**例 3（混合）**：A（1.54kg，7 袋在包 1、7 袋在包 2）、B（2.64kg，全在包 1）

| 包裹 | 包内重量 | 运费 | A 分到 | B 分到 |
|---|---|---|---|---|
| 包 1 | A 0.77 + B 2.64 = 3.41kg | 20.00 | 4.52 | 15.48 |
| 包 2 | A 0.77 | 12.00 | 12.00 | 0 |
| **合计** | | **32.00** | **16.52** | **15.48** |

## 7. 接口

| 方法 | 路径 | 用途 |
|---|---|---|
| `GET` | `/admin/orders/pending-shipment` | 待发货列表（供选择态用，可按顾客 / 地址聚合） |
| `POST` | `/admin/order-shipments` | 提交一票发货（多订单 + 多包裹 + 分摊） |
| `GET` | `/admin/order-shipments/:id` | 一票详情 |
| `PATCH` | `/admin/order-shipments/:id/packages/:packageId` | 改这个包裹的单号 / 运费（= 升级版「改运费」） |
| `POST` | `/admin/order-shipments/:id/wechat-upload` | 微信发货信息上传 / 重试 |

`POST /admin/order-shipments` 请求体（示意，非最终字段名）：

```
{
  packages: [
    {
      carrierCode: "SF",
      trackingNumber: "SF0206400913347",
      actualShippingFee: 20.00,
      items: [ { orderId: "A", bags: 7 }, { orderId: "B", bags: 4 } ]
    },
    { ... }
  ]
}
```

订单侧的 `trackingNumber` / `carrierCode` 写「第 1 个包裹」的值（兼容老读法），`shippedAt` 写票的时间。

## 8. 微信发货信息

⚠️ **微信是按「支付单」上报的**（`order_key` 用 `transaction_id` / `out_trade_no`，
见 `wechat-shipping-upload.service.ts`），所以**一票多单不能一次报**：
合并的 A、B 是两笔支付，必须**各报一次**。

- 上传粒度：**按订单**，不是按票
- 每张订单的 `shipping_list` 只放**这单实际所在的包裹** —— 不能放全部，
  否则顾客会看到一个根本没装他东西的包裹
- 单包订单 → `delivery_mode: 1`；多包订单 → `delivery_mode: 2` + `is_all_delivered: true`
- 重试沿用现有按订单的 pending 接口（`/staff/shipping/wechat-shipping-uploads/pending`）
- **上线前必须真机验一次**：拆成两包的订单，微信物流卡片是否两个单号都显示

| 3 | 分摊结果落库 | 出问题能查、能对账；不靠每次重算 |

| 5 | 提交后只能改单号 / 运费 | 改袋数等于重新分摊，容易把已发的账搞乱 |
| 6 | 多规格订单拆包时**按规格分行**分袋 | 否则「7 袋」到底是 770g 还是 1750g 说不清，按重量分摊就没有唯一答案 |
| 7 | 微信发货信息**按订单各报一次**，只报这单所在的包裹 | 微信按支付单上报，一票多单根本报不进去 |
| 8 | A 阶段就把「改运费」改成写包裹 | 否则订单级字段和分摊结果会打架（I5） |

### 17.2 与设计不一致的地方（都是实施时才发现的）

| # | 设计写的 | 实际做的 | 原因 |
|---|---|---|---|
| 1 | A 阶段把老的「填写运单并发货」内部改走新表 | **保持原样，不写票** | 避免动已经跑通的状态机；合并/拆包走新入口，老单按「虚拟包裹」降级渲染 |
| 2 | 提交后同步发通知 + 同步上报微信 | **异步发起**（`void`，不等） | 10 单合并 ≈ 20 次微信请求，串行会顶到小程序 15s 超时 |
| 3 | 拆包页按「订单 × 规格」一行 | 同订单同规格的**多道菜合并成一行** | 两个 item 同规格时 key 会撞，袋数被覆盖 |
| 4 | 订单主单号取「第 1 个包裹」 | 取**这单自己**所在的最靠前包裹 | 只装在包裹 2 的单会拿到别人的单号 |
| 5 | 零头「最后一单吃」 | 全给排序最后一单（不分摊到多单） | 与 §6 表述对齐，合计仍精确 |
