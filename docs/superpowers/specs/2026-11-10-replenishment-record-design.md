# 补货改版：从「计划单」到「下单即记 + 到货确认」设计

- 日期：2026-11-10
- 提出：老板
- 状态：待确认

- 范围：小程序「采购管理 → 补货」的整条链路（录入、识别、到货、库存、报销、提醒），含必要的后台（admin-web）配套

## 0. 一页纸

补货只服务「囤货」：不预先做计划，老板看库存或凭业务判断，直接在盒马/沃尔玛/淘宝/iHerb 下单。系统只做三件事：

1. **下单就记**：传订单截图 → AI 读出商品行、单价、数量、运费、包装费、优惠、实付、订单号、预计到货 → 核对（删个人行、改数量价格、修原料）→ 保存成一条**补货记录**，状态是「在途」，库存不动。
2. **到货才入库**：货到了在记录上点一次「已到货」，整单进库存；库存数字只算已到货，「够不够买」用在库 + 在途。
3. **钱能报销**：报销沿用日采流程；订单截图就是采购凭证；给员工的转账凭证只在「领款人不是审核人」时需要，老板自己买、自己审不需要。

目标：一单（≤10 行）从传图到保存 **1 分钟内**，人工只处理 0～2 行。

不做：计划单/购物清单、「开始采购/确认完成」、微信推送、超市小票识别。

---

## 1. 要解决的问题

1. **流程比场景重**：现在补货 = 建单 → 开始采购 → 逐条记录 → 确认完成 → 去报销。老板一个人做，买之前没有计划，买完才需要记账，「开始」和「完成」不产生任何信息。
2. **建单后改不了**：不能加原料、不能改计划量；同一天只允许一张待处理补货单，漏买一样东西只能删整单重建——而删除会把已录的采购记录一起删掉。
3. **补货和日采混在一个列表**：没有类型筛选，补货单容易被日采淹没；「未开始/采购中」也看不出来。
4. **没有在途概念**：下单后货没到，库存已经算上（或反过来完全不算），补货建议会重复提示已经买过的东西。
5. **AI 识别只服务日采**：2026-11-04 的设计明确「补货单的截图识别本期不做，补货仍手填」；补货恰恰是最适合截图识别的场景（电商订单、囤货、量少次多）。

## 2. 目标 / 非目标 / 反目标

### 目标

- 下单即记：传图 → 核对 → 保存，一条补货记录 ≤1 分钟。
- 识别覆盖多平台订单详情页；商品详情页用于补系统里没有的采购商品。
- 在途和在库分开；到货才入库；补货建议用「在库 + 在途」算。
- 报销不漏、不重复；补货记录的金额与订单实付对得上（有个人商品时能解释差额）。
- 到货有提醒，但不打扰：只在小程序内，超期标红。

### 非目标（本期不做）

- 不做计划单、购物清单、补货建议单。
- 不做「开始采购」「确认完成」这两个动作。
- 不做微信订阅消息/服务通知推送。
- 不做超市小票识别；不做订单列表页（一屏多单）的自动拆分。
- 不在小程序里新建**原料**（原料建档仍在后台/原料创建流程）；只新建**采购商品**。
- 不改日采的流程与页面结构。
- 不做供应商管理、比价、自动下单。

### 反目标（做到了也算失败）

- 一次核对要改 3 行以上，或一单超过 2 分钟。
- 在途被算进在库，或已下单的东西再次提示补货。
- 个人商品被记进公司账，或公司商品被标成个人后无人发现。
- 报销金额与订单实付对不上，且页面没有任何说明。
- 为了补货把日采、现有报销审核、库存流水弄坏。
- 用户需要理解「单据」「状态机」这些概念才能用。

### 约束

- 技术栈：uni-app 小程序 + NestJS/Prisma 后端 + Vue 3 后台；不引入新框架。
- 复用现有：AI 截图识别与核对页、采购商品（SKU）、采购记录、库存流水、报销单与审核、私有 COS。能复用就不另写一套。
- 补货与日采共用 `purchase_list` / `purchase_record` / `reimbursement`，改动必须向后兼容历史数据。
- 小程序端为主；后台只做查看与必要的字段展示，不要求后台完成补货录入。
- AI 识别有配额与成本上限；失败必须能降级为手填，不能阻断记账。
- 推送不做：微信订阅消息需要模板与用户授权，员工侧没有现成模板，本期不引入。
- 一人操作、手机现场使用：所有主路径不超过 3 次点击（记一笔 → 传图 → 保存）。

## 3. 使用场景与流程

### 现在

```
采购管理 → 补货 → 创建补货单（选日期、看建议、选原料、填计划量）
→ 详情 → 开始采购 → 逐条记录（选 SKU、填件数金额）→ 确认完成（入库）
→ 去报销 → 勾清单、填运费包装、传凭证 → 提交
```

### 改版后

```
采购管理 → 补货 → 记一笔
  → 选 1～5 张订单截图（每张 = 一笔订单；同一订单多页请截长图）
  → AI 识别（约 3 秒/单）+ 按全库匹配原料/采购商品
  → 核对页：按订单切换；删个人行、改数量/单价、修原料、建新商品
  → 保存 → 每条订单生成一条「补货记录」，状态 = 在途；库存不动
  → 货到 → 在「待收货」里点「已到货」→ 整单入库
  → 报销：选记录 → 金额/费用/截图已预填 → 提交 → 审核 → 转账凭证（员工单）
```

关键差异：

- 买之前没有任何系统动作；系统只在「买完」和「货到」两个时点介入。
- 报销和到货互不阻塞：下单付了钱就能报销，货没到不影响报销；到货只影响库存。
- 「补货记录」对外不再叫「补货单」，避免被理解成计划。

## 4. 已锁定的业务规则

| 编号 | 规则 | 来源 |
|---|---|---|
| N1 | 补货不建计划单、不列购物清单；决定买什么完全靠库存和业务判断 | 老板 2026-11-10 |
| N2 | **一张订单 = 一条补货记录**；一次可传 1～5 张，每张算一笔订单；同一订单多页不做合并，引导截长图 | 老板 + 旧设计 16.4 |
| N3 | 下单即记：保存时点 = 下单时点，记录立即进入「在途」 | 老板 |
| N4 | 到货由人确认：整单点一次「已到货」；截图已显示「已送达/签收」的，保存时可直接算已到货 | 老板 + 实现建议 |
| N5 | 库存数字只算已到货；「够不够买」用「在库 + 在途」算 | 老板 |
| N6 | 记录金额 = 采购行合计 + 运费 + 包装费 − 优惠/关税；无个人商品时等于订单实付 | 老板 2026-11-10 |
| N7 | 个人商品不生成采购记录；整单都是个人商品则不生成补货记录 | 老板 + 旧设计 R6 |
| N8 | **按重量买的（斤/公斤/克/两）直接按重量记，不强制采购商品（SKU）**；仅限基准单位为 G/ML 的原料；基准单位是「个/件」的（如鸡蛋）仍走商品 + 净含量 | 老板 2026-11-10，替代旧 R2 |
| N9 | 新商品：订单行信息够（品牌/品名/规格/价格）→ 一键建采购商品；信息不够 → 拍商品详情页补 | 老板 |
| N10 | 报销复用日采流程；订单截图 = 采购凭证；转账凭证只在「领款人 ≠ 审核人」时需要 | 老板 |
| N11 | 到货提醒只在小程序内：待收货入口 + 数量 + 超期标红；不推送 | 老板 |
| N12 | 对外没有「开始采购/确认完成」；内部实现也不要求用户理解状态 | 老板 |
| N13 | 同一天可以有多条补货记录（不同订单），取消「一天只能一张待处理补货单」 | 本设计 |
| N14 | 历史补货单保持可查看、可报销；不强制迁移到新流程 | 本设计 |

| 旧规则 | 旧内容 | 本设计 |

## 5. 页面与交互

### P1 采购管理首页（改造）

- 「补货」入口卡片保留，右侧显示「待收货 N」；有超期时 N 标红。
- 采购清单列表**只显示日采**（或加「日采/补货」筛选，默认日采），不再混排。补货有自己的页面。
- 日采的日期选择、生成、预览逻辑不变。

### P2 补货页（新）

结构从上到下：

1. 顶部「待收货 N」卡片（仅 N>0 时显示），点进待收货列表。
2. 主按钮「记一笔补货」→ 进入上传/识别。
3. 记录列表，按创建时间倒序；每条显示：渠道、订单号后 4 位、下单日期、品种数、实付金额，以及**两个独立徽章**（到货：在途/已到货；报销：未报销/报销中/已报销）；在途超期的整条标红。
4. 筛选：全部 / 在途 / 待报销 / 已报销 / 已作废；到货和报销不是互斥状态，不能用四选一。

### P3 上传与识别

- 一次 1～5 张图；每张 = 一笔订单；同一订单多页提示截长图。
- 上传页三条指引：订单详情页、金额展开、不要把订单列表页当订单。
- 识别中显示进度；前端等待 **20 秒**后提示「还在识别，请稍等」但不判失败；服务端沿用现有模型超时（按段数约 45～90 秒），超时才失败、不扣配额。
- 识别到「订单列表页」时直接拒绝并提示「请打开单个订单再截图」。

### P4 核对页（改造现有 P4）

- 按订单切换（1～5 个 tab）；当前订单顶部显示：渠道（可改）、订单号（可改）、下单时间、商品金额、运费、包装费、优惠/调整、实付、预计到货。
- 行级状态：
  - **已匹配**（绿）：订单行 → 采购商品 → 原料。
  - **按重量**（绿）：订单行是斤/公斤/克/两，直接对应原料，不需要商品。
  - **需新建商品**（黄）：原料匹配上了，但原料下没有可用商品；点开预填品牌/品名/规格/单价，确认即建。
  - **未匹配**（红）：找不到原料；必须处理（选原料、建商品、或标个人），**默认不自动标个人**。
  - **个人**（灰）：员工手动标记，不生成记录、不计入报销。
- 每行可改：数量、单价、匹配原料、单位、标记个人/取消个人；可删除行（AI 多读）、添加行（AI 漏读）。
- 金额只提示不拦截：行合计与商品金额、实付对不上时，顶部显示差额，不弹框（沿用旧设计 2026-11-05 修订）。
- 底部「保存」：一次保存所有订单，每笔订单生成一条补货记录。

### P5 新建采购商品（复用现有页，改造入口）

- 从订单行进入时预填：品牌、品名、规格、单价、采购单位、换算比（能读出来的）。
- 信息不够（没有净含量/规格）时才引导拍商品详情页；详情页识别仍走现有草稿能力。
- 保存后回到核对页，该行自动匹配到新商品。

### P6 补货记录详情（替代现有补货详情）

- 顶部：渠道、订单号、下单时间、预计到货、状态、实付、本次报销金额。
- 商品行：名称、规格、数量、单价、金额；来源截图可点开看原图。
- 在途：底部「已到货」按钮（整单）+「去报销」（报销与到货互不阻塞）。
- 已到货：显示到货时间；底部「去报销 / 查看报销单」；只允许改渠道、订单号、备注；改数量/价格/删行/作废要先「撤销到货」。
- 已到货但未报销：可「撤销到货」→ 退回在途 → 改完再确认；撤销前提是这批入库未被下游消耗。
- 已报销但未到货：只读，但**仍可点「已到货」**（到货和报销互不阻塞）；入库照常。
- 部分到货：先改数量/删掉没到的行，再点「已到货」；不做「部分到货」单独状态。
- 已报销：只读（未到货时仍可点「已到货」），显示报销单号。
- 不出现「开始采购 / 确认采购完成 / 撤回完成」。

### P7 待收货（新）

- 列表：渠道、订单号、下单日期、预计到货、已等天数、实付；超期标红置顶。
- 每条一个「已到货」按钮；点完从列表移除、进库存。
- 空态：「没有在途的补货」。

### P8 报销（复用日采，预填）

- 选记录时显示：渠道、订单号、下单日期、本次报销金额（已扣个人）、截图张数。
- 金额、运费、包装、凭证预填；补货记录不再单独填运费/包装（费用在记录里）。
- 自己买、自己审：不需要转账凭证（沿用现有 self-review 规则）；员工单仍需。

### 退役/保留

- 退役：现有「创建补货单」页（计划量、补货建议）、补货详情里的开始/完成/撤回、采购清单列表里的补货混排。
- 保留：库存管理页的补货建议（作为参考，不生成单据）、AI 识别/核对/新建商品、报销流程、库存流水。

## 6. 数据与状态

### 6.1 容器

沿用 `purchase_list`（`kind = STOCK_REPLENISHMENT`）作为「一条补货记录」的容器，避免另起一套报销/库存链路。新增字段（建议，最终以 migration 为准）：

| 字段 | 类型 | 说明 |
|---|---|---|
| orderNo | VarChar(40)? | 订单号快照 |
| channel | VarChar(30)? | 渠道码（字典 `purchase_channel`） |
| orderPlacedAt | DateTime? | 下单时间 |
| expectedDeliveryAt | DateTime? | 预计到货（AI 读不到则按渠道默认） |
| arrivedAt | DateTime? | 到货确认时间；null = 在途 |
| subtotalAmount | Decimal(10,2)? | 商品金额 |
| shippingFee | Decimal(10,2)? | 运费 |
| packagingFee | Decimal(10,2)? | 包装费 |
| discountAmount | Decimal(10,2)? | 优惠/调整 = 商品 + 运费 + 包装 − 实付，可正可负 |
| paidAmount | Decimal(10,2)? | 订单实付（含个人商品） |
| personalAmount | Decimal(10,2)? | 个人商品合计 |
| reimbursementAmount | Decimal(10,2)? | 本次报销金额 = 实付 − 个人；报销服务直接读这个数 |
| voidedAt | DateTime? | 作废时间（取消/退款） |

> `purchase_order_import` 已有 channel/orderNo/orderTime/subtotal/shippingFee/packagingFee/paid，可直接作为识别来源；记录上保留快照，避免列表查询依赖导入表。需新增 `expectedDeliveryAt`（识别结果 + 手工可改）。

### 6.2 状态：到货和报销是两个独立维度

**不能用一个四状态互斥模型。**「已报销但还没到货」是常见情况（淘宝 3 天、iHerb 14 天），必须能同时表达。

| 维度 | 取值 | 判定 |
|---|---|---|
| 到货 | 在途 / 已到货 | `arrivedAt` 为空 / 非空 |
| 报销 | 未提交 / 报销中 / 已报销 / 被驳回或需重提 | 报销单状态 |
| 作废 | 否 / 是 | `voidedAt` |

页面展示两个徽章，例如「在途 · 未报销」「在途 · 已报销」「已到货 · 报销中」。

规则：

- **待收货** = `arrivedAt` 为空且未作废，与报销状态无关；「待收货 N」按这个算。
- **已报销但未到货**：仍在待收货里，仍可点「已到货」；除「到货」这个动作外只读。
- **可编辑** = 未作废 + 报销未提交/被驳回/需重提 + 到货维度为在途（已到货要先撤销到货）。
- **报销锁定**：报销单「待审核/已报销」时记录只读（「到货」动作除外）；「驳回/需重提」时解锁（现有代码提交即锁、驳回后永久锁死，需在报销服务里补解绑）；删除报销单也解锁。
- 内部 `purchase_list.status` 仍可在保存时置 `COMPLETED`（只为复用报销「只认 COMPLETED」的校验），页面不展示这个字段。
- 入库在「确认到货」时发生；保存不写库存。
- 旧数据：历史 COMPLETED 补货单回填 `arrivedAt = completedAt`（它们已经入过库），避免显示成在途。

### 6.3 在途数量

- **补货在途** = 该记录下采购记录的 `actual_base_quantity` 之和（`arrivedAt` 为空、未作废）。
- 注意：现有 `inventory.service` 里的 `inTransitQuantity` 指的是**日采清单里还没买到的部分**，不是补货在途。不要复用、不要相加。
- 新增独立口径 `replenishmentInTransitQuantity`；库存页显示「在库 / 补货在途 / 日采待买 / 可用」四个数。
- 可用（补货建议用）= 在库 + 补货在途；日采的净额缺口继续用它自己的「日采待买」。

### 6.4 金额

- 商品行：`数量 × 单价` 写入采购记录 `actualCost`，用于库存成本和单价展示。
- 订单级：商品金额、运费、包装费、优惠/调整（= 商品金额 + 运费 + 包装 − 实付，可正可负）、实付。
- **本次报销金额 = 实付 − 个人商品合计**，保存时算好写入 `reimbursementAmount`；改商品行的数量/单价不改变这个数（报销以实际付款为准）；改「个人标记」或手工改「实付」时重算。
- 报销服务对补货记录**直接读 `reimbursementAmount`**；对日采仍沿用「Σ采购记录 + 报销单级费用」。这样优惠/关税不会让「行合计 + 费用」和实付打架，也不会触发 `voucherAmount ≥ 报销金额` 校验失败。
- 无个人商品时，本次报销金额 = 实付；有个人商品时，页面显示「实付 ¥X，含个人 ¥Y，本次报销 ¥Z」。
- 费用不与个人商品分摊（沿用 R6）：费用全额计入本次补货，个人商品只在总额里扣除。
- 商品行金额合计与实付的差额（优惠/调整）只在订单级展示，不摊到行，避免把折扣摊进单价。

### 6.5 采购明细

- 保存时按非个人行创建 `purchase_item`：原料、可选 SKU、数量、单位、金额；一个订单行对应一条采购记录，同一商品多行不合并。
- 按重量行：`quantityUnit = 斤/公斤/克/两`，`procurementSkuId = null`，换算到基准单位写 `actual_base_quantity`（斤 = 500g、两 = 50g、公斤 = 1000g、克 = 1g）；不写 SKU 价历史。
- 按重量只适用于基准单位 G/ML 的原料；基准单位是 PCS 的原料（鸡蛋等）按重量买时，降级为「需新建商品」，用净含量换算，不做「每斤几个」。
- 按重量行**不写回原料档案价**（避免把「元/斤」写成「元/袋」），价格只留在本次记录；后续做「按重量商品」再统一。
- 按件行：沿用现有 SKU + 净含量换算，金额 = 单价 × 件数。

## 7. AI 识别与匹配的改造

### 7.1 输入

- 订单详情页：盒马、沃尔玛/极速达、山姆、淘宝/天猫、iHerb、其他电商。
- 商品详情页：只用于新建采购商品。
- 不支持：超市小票、订单列表页（一屏多单）。
- 一次 1～5 张，每张一笔订单；同一订单多页不合并。
- 识别不再要求「先开始采购」：导入记录挂在草稿补货记录上，保存时转正；旧接口里的 `startedAt` 校验要去掉。

### 7.2 识别内容

沿用现有 schema：渠道、订单号、下单时间、商品行（原文名、规格、数量、单位、单价、行小计）、商品金额、运费、包装费、实付、是否完整。新增：

- `expectedDeliveryAt`：从「预计 X 送达」「送达日期」「签收时间」读取；读不到给 null。
- `deliveredAt`：截图明确显示「已送达/已签收」时给出日期；用于 N4 的「保存即已到货」。
- 页面类型：`order_detail` / `product_detail` / `order_list` / `unknown`；`order_list` 直接拒绝。

### 7.3 匹配

- 从「按清单匹配」改为「按全库匹配」：
  1. 订单行 → 采购商品（优先规格、品牌、关键词）；命中则带出原料。
  2. 没有商品 → 按原料名/别名匹配原料；命中但无可用商品 = 需新建商品。
  3. 原料也匹配不上 = 未匹配（红），人工选原料或标个人。
- 未匹配**不再默认标个人**（旧行为会静默漏记新原料）。
- 按重量单位（斤/公斤/克/两）直接给原料候选，不要求商品。
- 记住「这个叫法在这个渠道对应哪个原料/商品」（现有 alias 表），下次自动匹配。

### 7.4 配额与降级

- 新用途 `REPLENISHMENT_ORDER_IMPORT`（或沿用 `PURCHASE_ORDER_IMPORT`），单独配额；默认每人每天 30 次、全系统每月 3000 次（可配）。
- 失败/超时：不落库、不扣配额，提示「识别失败，可重试或手填」。
- 重复图：按「上传人 + 图片指纹（sha256）」拦截，跨记录也拦（同一张订单图不能记两次）；`DISCARDED` 的不参与去重。
- AI 不可用时：允许纯手填一条补货记录（保底，不阻断）。

## 8. 库存与补货建议

- 入库时点：确认到货；沿用现有 `inboundFromPurchaseRecords`（按「采购记录 + 原料」幂等）。
- 只对 `procurementStrategy` 为补货/混合的原料入库（现状）；日采原料混进补货记录时不入库，必须在详情页明确提示「此项不进入库存」，不能静默。
- 补货建议：
  - `currentStock` 仍返回在库；
  - 新增 `replenishmentInTransitQuantity`（补货在途）和 `availableQuantity`；**不要复用现有 `inTransitQuantity`**（它是日采待买，口径不同，相加会重复计数）；
  - 建议量用 `availableQuantity` 计算（缺口 = 目标 − 可用）；
  - 库存页/补货页显示「在库 / 补货在途 / 日采待买 / 可用」四个数。
- 同一天多张记录不再受限；「够不够」由可用量判断，不靠单据唯一性。

## 9. 报销

- 资格：补货记录已保存（status=COMPLETED）、未作废、没有处于「报销中/已报销」的关联；**不要求到货**。被驳回或需重提的记录解锁后可以重新提交。
- 一次可选 1～N 条记录（可同日、可跨日、可不同渠道），沿用日采的多选提交。
- 金额：报销单里补货部分的金额 = Σ `reimbursementAmount`（实付 − 个人）；运费/包装已在记录里，不再在报销单上重复填。日采部分仍按 Σ 采购记录 + 报销单级费用，两者相加得到报销总额。
- 凭证：订单截图（私有 key）作为采购凭证；提交时至少 1 张。
- 转账凭证：领款人 = 审核人（自己买自己审）时不需要；否则必须先上传（沿用现有规则）。
- 差额：凭证金额（订单实付）与报销金额不一致时，页面显示差额和原因（个人商品、退差、优惠）。
- **锁定**：报销单「待审核/已报销」时补货记录只读（「到货」动作除外）；「驳回/需重提」时解锁（需在报销服务里补解绑，现状是提交即锁、驳回后永久锁死）；删除报销单也解锁。日采清单是否同步改由实现者决定，但共用代码应保持一致。
- 驳回/重提/撤回：沿用现有流程。

## 10. 提醒

- 预计到货日：
  - AI 读到就用；
  - 读不到按渠道默认：盒马/沃尔玛/山姆 +1 天，淘宝/天猫 +3 天，iHerb/跨境 +14 天，其他 +3 天（可配）。
- 超期：当前时间超过预计到货日 23:59 且未到货 → 标红、置顶。
- 展示：采购管理首页「补货」入口显示待收货数；补货页顶部「待收货 N」；待收货列表按超期天数排序。
- 不做推送；不做每日弹窗。

## 11. 权限与审计

- 入口与接口沿用 `AuthGuard + StaffGuard`；补货记录保留 `createdById`。
- **可见范围**：补货页、待收货、在途对员工全局可见（只读）——在途影响所有人的库存，藏起来会让页面数字和补货建议对不上。
- **操作范围**：编辑、确认到货、撤销到货、作废、改金额，限「创建人 + 管理员」；列表不再按创建人过滤。
- 本期补上单据级归属校验（解决现状审核 P1-6）：详情、记录增删改、到货、作废、删除都校验 `createdById` 或管理员。
- 截图存私有 COS；列表/详情用短期签名 URL。
- 保留识别原始结果、模型、提示词版本、确认人；采购记录保留来源截图 key。
- 作废、改金额、改原料留痕（至少记录操作人和时间）。

## 12. 兼容与迁移

- 历史补货单：保留查看/报销；COMPLETED 的回填 `arrivedAt = completedAt`；PENDING 的仍可按旧流程完成，或由管理员一键标记到货。
- 采购管理列表默认只显示日采；补货记录在补货页查看。
- 后台（admin-web）：
  - 采购单列表可按 kind 筛选（已有）；
  - **补货单不能「追加订单/剔除订单/重新计算」**（现状审核 P0-3）；
  - 补货详情展示渠道、订单号、在途/到货、费用、本次报销金额。
- 报销的后端规则：补货记录的费用计入本次金额；报销单级的 `platformShippingFee / platformPackagingFee` 只用于日采。
- 现有 `completePurchase / reopenPurchaseList / startPurchase` 保留给历史数据，不再被新流程调用。

## 13. 验收标准

1. **时间**：10 行以内的订单，从上传到保存 P50 ≤ 60 秒、P90 ≤ 90 秒（真机、4G）。
2. **识别**：用历史 10 张截图 + 本次 9 张多渠道样本回归，行数、单价、数量、商品金额、运费、包装费、实付 100% 一致。
3. **匹配**：≥80% 的行自动匹配；每单人工处理 ≤2 行。
4. **个人商品**：整单个人 → 不生成记录；混合 → 个人行不生成记录，报销金额 = 实付 − 个人合计（±0.01）。
5. **重量**：「3 斤羊心」记成 3 斤、1500g，金额 37.39；库存增加 1500g。基准单位是「个」的原料按重量买（如鸡蛋 5 斤）必须被拦住并引导用商品净含量，不能算成 5 个。
6. **在途**：保存后库存不变、补货在途 +1500g；「可用」= 在库 + 补货在途；补货建议不再重复提示。日采待买与补货在途是两个数，不混算。
7. **到货**：点一次「已到货」→ 库存 +1500g，在途清零；重复点不重复入库；到货后改数量必须走「撤销到货」。
8. **提醒**：超过预计到货日未确认 → 入口/列表标红；确认后消失。
9. **报销**：自己买自己审不需要转账凭证；员工单没有转账凭证不能通过；带优惠/关税的订单，报销金额 = 实付 − 个人，且 `voucherAmount ≥ 报销金额` 校验通过。
10. **双维度**：已报销但未到货的记录仍出现在待收货，仍可点「已到货」，库存正确增加；页面同时显示「在途 · 已报销」。
11. **驳回**：报销被驳回/需重提后，记录解锁、可改、可重新提交；待审核/已报销时只读。
12. **超时**：识别 20 秒只提示「还在识别」，不判失败；服务端超时才失败，失败不扣配额。
13. **兼容**：历史补货单可查看、可报销；日采流程回归通过。
14. **异常**：识别失败/超时/重复图/订单列表页 都有明确提示，不产生脏数据。

## 14. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| AI 把订单列表页当订单 | 记错单 | 页面类型判断 + 直接拒绝 + 提示重传 |
| 混合订单个人商品漏标 | 多报 | 核对页个人行显式灰显；报销差额显示个人金额；审核抽查 |
| 在途虚高（下单后取消/退款） | 建议少买 | 记录可作废；作废后在途立即扣减；超期提醒 |
| 忘记点「已到货」 | 库存偏低、建议多买 | 待收货入口 + 超期标红；可用量含在途，避免重复买 |
| 按重量行没有 SKU | 价格历史/比价缺失 | 只影响比价，不影响入库和报销；后续可补「按重量商品」 |
| 旧流程与新流程并存 | 用户困惑 | 旧补货单只读/历史入口；新入口只走新流程 |
| 费用/优惠口径 | 报销金额对不上 | 统一用「实付 − 个人」写入 `reimbursementAmount`；差额页面可见；回归测试 |
| 报销驳回后记录锁死 | 员工没法改、没法重报 | 待审核/已报销锁定，驳回/需重提解锁；删除报销单解锁 |
| 「在途」两个口径混用 | 重复计数、少买 | 日采待买和补货在途分字段、分数展示，不相加 |
| 按重量行遇到 PCS 原料 | 换算不出库存 | 只允许 G/ML 直接按重量；PCS 走商品净含量，并在核对页拦住 |
| 到货后直接改数量 | 账面库存与记录不一致 | 到货后只改渠道/订单号/备注；改数量走「撤销到货」并检查是否已消耗 |
| 识别配额/成本 | 用不了 | 单独配额 + 失败不扣 + 手填兜底 |

## 15. 留给实现者的决定

以下不影响用户看到的行为，由实现者按现有代码结构决定：

1. **容器与状态**：沿用 `purchase_list` + `COMPLETED` + `arrivedAt`，还是新增 `ORDERED` 状态/独立表。约束：报销保存后即可用；入库只在到货；历史数据不受影响。
2. **识别前的草稿**：先为每张图建草稿记录再识别，还是识别成功后再建；约束：草稿对用户不可见、失败要能清理、不触发「同日唯一」。
3. **金额字段存储**：`reimbursementAmount / paidAmount / personalAmount / discountAmount` 放 `purchase_list` 还是只放导入表；约束：报销服务能直接读、列表不依赖多次 join、金额可追溯。**口径已定：报销金额 = 实付 − 个人**。
4. **多图多单**：一次 1～5 张、每张一单的实现；约束：同一订单多页不合并；保存时按订单分组，一个订单一条记录。
5. **撤销到货/作废的实现**：接口可重入、回滚库存幂等、检查下游消耗；约束：已消耗时禁止，未报销才可撤。
6. **历史迁移**：completed 回填 arrivedAt；PENDING 旧单的处理方式。
7. **渠道默认到货天数**：先写死常量，后续进配置。
8. **后台页面**：补货详情的字段展示与按钮隐藏。
9. **配额口径**：新用途独立配额还是复用现有导入配额。
10. **报销锁定解绑的范围**：只对补货记录生效，还是日采一起改；约束：共用代码行为一致，历史上「驳回后永久锁死」应被修掉。
11. **现有 `inTransitQuantity` 字段的处理**：新增独立字段并保留旧字段，或改名；约束：日采净额缺口数字不变，不能把两个口径相加。
12. **权限实现**：全局只读 + 创建人/管理员可写的落地方式；约束：不破坏现有员工端其他页面。

## 16. 问题边界（明确不讨论）

- 不做采购计划、补货预测算法、自动补货。
- 不做供应商/比价/议价。
- 不做退货退款流程（记录可作废/编辑，退款差额靠报销差额说明）。
- 不做财务总账科目调整。
- 不改日采的「开始采购/确认完成」。
- 不做微信推送。
