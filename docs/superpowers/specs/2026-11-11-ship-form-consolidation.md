# 发货表单合并：三处发货入口共用一套实现（2026-11-11）

> 状态：已上线（小程序体验版 + 后端）
> 触发：老板在订单中心发货时发现「每发一单要跳一次详情页」，随后要求「把两套发货表单合成一套」。

## 1. 为什么要做

改造前，小程序里有三处「填写发货信息」：

| 用在哪 | 形态 | 当时的差异 |
|---|---|---|
| 鲜食订单详情 / 订单中心列表 | 底部抽屉 | 标准版 |
| 补剂订单详情 | 页面自己的弹窗 | 接口不同、地址自己一套编辑框、**发货后不上报微信** |
| 合并 / 拆包发货页 | 整页（多包裹） | 一包一张快递单、运费分摊 |

三处各写了一遍「拍存根 → 识别 → 核对结论 → 手动确认」，也各写了一遍运费校验。
后果：改一次发货规则要改三处；补剂那条路连微信上报都漏了（顾客微信里一直显示待发货）。

## 2. 现在的结构

```
components/shipping/
  StaffShipDrawer.vue        单笔发货抽屉（鲜食、补剂共用；kind 区分接口）
  ShipRecipientSummary.vue   顾客 / 狗狗 / 收货地址 + 复制地址（抽屉、合并页共用）
  WaybillReceiptBlock.vue    存根块的样子（纯展示）
utils/
  waybill-receipt-machine.ts 存根识别状态机（三处共用，唯一真源）
  waybill-receipt-view.ts    存根块该显示什么（四种颜色 + 能不能发货/手动）
  order-address.ts           地址取数、复制文本、地址指纹（合并判重用）
  order-ship.ts              狗狗汇总文案
  ship-fee.ts                实际运费校验（必填、两位小数）
api/
  ship-submit.ts             单笔发货提交：鲜食/补剂各走各的接口，再决定微信上报
```

三个入口现在分别是：

1. **鲜食订单详情**：打开 `StaffShipDrawer(kind=food)`。
2. **订单中心列表**：点「发货」→ 现拉一次订单详情（要当前地址）→ 在列表页直接开同一个抽屉 → 发完关掉、刷新列表，人留在原地发下一单。
3. **补剂订单详情**：打开 `StaffShipDrawer(kind=supplement)`；地址编辑仍由页面自己提供（`@fix-address`），改完地址 `address-revision +1`，抽屉据此作废存根结论。
4. **合并 / 拆包页**：保留整页（多包裹、分袋、分摊），但顶部用 `ShipRecipientSummary`，运费校验用 `parseShipFee`。

## 3. 关键口径（别改坏）

- **硬锁在服务端**：客户端只是别让人白填一屏；`enforceWaybillCheck` 由后端默认强制。
- **mismatch / duplicate 绝不回填、绝不给手动**：给一个就是绕过硬锁。
- **手动确认只对当时那个单号有效**：确认完改号，结论作废（合并页 2026-11-11 起也收紧了）。
- **地址改了就作废存根结论**：鲜食详情走 `onFixAddress` 重开、补剂走 `addressRevision`。
- **补剂微信上报只做一次**：后台在发货接口里上报，结果随响应返回（`wechatShippingUpload`）；
  小程序**不再**补调上报接口 —— 补剂单没有「已上报」标记，重复调会用掉微信唯一一次重新发货机会。
  后台没返回结果时，如实提示「未同步，请到网页后台补」，不假装成功。

## 4. 验证

- 新增单测：存根状态机 9 条、发货提交 9 条（含「补剂只调一次」）、运费 5 条、地址指纹 5 条。

## 5. 还没做的（下一轮）

1. 补剂单的「微信上报失败」没有补报入口：后台没有补剂版待上报清单，`listPendingUploads` 只扫鲜食表。
2. 后台补剂发货的「快递公司」仍是可选；不选就必然跳过微信上报（小程序端有默认值，不受影响）。
3. 微信上报调用没有超时；微信卡住时发货接口会跟着等。
4. 承运商映射里 `POSTB`（邮政包裹）没有微信编码，这类单上报可能失败。
5. `supplement_order` 没有 `wechatShippingUploadedAt`，无法做严格幂等；目前靠「只在发货时调一次」保证。
