## 一、为什么改

三个概念现在共用一份「补剂候选」数据，任何一道门都会误伤另外两件：

1. **不推荐就买不到。** 候选的准入写死为「`diyEnabled` 且 `supplementRetailEnabled`」(`supplement-candidate.service.ts#getEligibilityReason`)，于是把「要不要给顾客推荐」和「能不能卖」绑成了一个与条件。海带粉胶囊已具备分装条件但没上架、海藻粉只用于生产，两者都进不了候选——这道门本身没错，错在它是唯一的门。
2. **购买了但没有自己的口径。** 「购买预分装补剂」的清单直接从候选派生（`buildSupplementPurchaseLines` 过滤 `purchasable`），候选少一个，购买清单就少一个；下单时后端又拿同一份候选校验（`supplement-order.service.ts#resolveServerDosageLines` 要求 `ingredientId` 必须命中 `item.candidates`）。所以预分装没有独立的商品清单。
3. **生产开关完全不参与。** `procurementEnabled` 既不影响候选、也不影响上架，可以出现「上架了但生产没有这一款」，反过来也可以「食谱在用、生产没开」。
4. **补剂的推荐商品数据存在但没被读。** 后台原料详情可配「DIY 制作单推荐商品」（`recommended_product`：链接/口令/图片/规格），小程序只给食材加载（`collectFoodIngredientIdsForRecommendations` 明确排除 SUPPLEMENT），补剂弹窗拿候选顶替。于是「推荐购买」对补剂等于没实现。
5. **术语已经混了。** 后台「上架清单」里那个筛选项叫「可用于生产」，判的却是「`diyEnabled` 或 被食谱引用」（`admin-web/src/api/supplementShop.ts`）。同一句话在两个页面指两件事。

线上存量（2026-11-15 核对）：补剂 34 个，全部已归组；开生产 27、已上架 21、开 DIY 推荐 32；配了推荐商品的只有 9 个；**6 个等价组里有 2 个以上成员开了生产**，2 个组里有 2 个以上成员已上架。这些是拆分后要一起体检的数据。

## 二、目标 / 非目标

### 目标

- 三个口径各自独立：**生产**、**预分装**、**DIY 推荐**；任一开关的增减不影响另外两个。
- 制作单上补剂的「产品」= 参考产品，顾客不可选，也不因上下架变化。
- 「查看商品 / 换一个」只服务 DIY 推荐（外链佣金），没有推荐商品就不出这个入口。
- 「购买预分装补剂」有自己的商品口径：等价组 ∩ 已上架 ∩ 分装档案齐全；数量与价格都按这款产品算。
- 顾客端不出现「能买但产不出」「推荐了但打不开」的死路。

### 非目标

- 不重做成品鲜食的生产排产、扣料和标签。
- 不改等价组的科学口径、审核流程和成员管理。
- 不做「下单后换产品如何补退差价」的规则（单列下一期，见第九节）。
- 不改补剂分装（员工端 `staff-production` 补剂模式）的操作流程，只改它拿到的商品来源。

### 反目标（做成就等于失败）

- 顾客在制作单上「选」了一款，但我们实际生产/分装用的是另一款，而页面没说。
- 推荐商品与「我们卖的商品」混在同一个弹窗里，顾客分不清哪个要付钱给我们。
- 为了拆口径，要求运营给 34 个补剂各维护三份清单。

## 三、四个概念

| 概念 | 定义 | 数据来源 | 谁决定 |
|---|---|---|---|
| **参考产品** | 这份配方按哪款产品算出来的；补剂用量的换算依据 | 食谱行引用的原料（`recipe_item.ingredient_id`） | 配方设计者，不在本期改 |
| **生产用产品** | 做成品鲜食时实际从仓库拿的那一罐 | 生产开关 `procurementEnabled` | 运营；生产端缺货时可临时换（第九节） |
| **预分装产品** | 分装成小袋寄给顾客的那一款 | 上架 `supplementRetailEnabled` + 分装档案齐全 | 运营；每单默认取规则值，分装端可临时换 |
| **DIY 推荐商品** | 顾客自己去淘宝/京东/iHerb 买的那瓶 | `recommended_product`（按原料挂，含链接/口令/图片） | 运营；`diyEnabled` 控制是否露出 |

关系：

- 参考产品是**展示与换算**的锚，不随任何开关变化。
- 生产用产品只影响我们怎么做，不影响顾客看到什么。
- 预分装产品只影响顾客买什么，不影响我们怎么做。
- 推荐商品只影响顾客自己去哪买，不影响我们任何一环。

## 四、池子与过滤（等价组不退回）

等价组 = 同一营养素、同一形态/来源的等效池。三个口径各自在池内过滤：

| 口径 | 池子 | 过滤 | 默认取谁 |
|---|---|---|---|
| 生产 | 等价组（无组时=自己） | 生产开关 | 参考产品若开生产 → 它；否则组内优先级最高的开生产成员 |
| 预分装 | 等价组（无组时=自己） | 已上架 + 分装档案齐全 | 参考产品若已上架 → 它；否则组内优先级最高的已上架成员 |
| DIY 推荐 | 该原料挂的推荐商品 | 商品启用（`is_active`） | 排序第一个 |

要点：

- 「大部分重合、个别不重合」是自然结果：只开生产不开上架 → 只进生产池；只开上架不开生产 → 只进预分装池。**不需要三份人工清单。**
- 跨产品替换（参考产品不可售 → 用组内另一款）由补剂商城总开关 `equivalenceEnabled` 控制，保留为一键关闭的保险丝。**关闭时**预分装池 = 参考产品 + 该食谱行的旧备选（`recipe_supplement_alternative`），不跨等价组；**打开时**才扩到整个组。这样关掉开关不会让原本能买的那几道食谱突然归零。
- 食谱级旧备选（小麦胚芽油等）不再作为「顾客的选择项」展示，只作为兜底池的成员参与默认值计算。
- 该开关另有 `supplement-equivalence-recommend.service.ts` 在读，但它只把值透给后台当提示，改文案不影响它。开关名称与含义都不动，只把后台说明改成「允许跨产品替换预分装产品」。
- 组内优先级沿用现有 `equivalence_priority`。若将来出现「预分装默认必须是某一款」的个别情况，再在组上加一个可空的 `repack_default_ingredient_id` 覆盖；**本期不加字段**，先按规则跑。

## 五、页面行为

### 5.1 DIY 制作单 · 补剂行

四列不变：补剂名称 / 产品 / 建议添加时机 / 制作单总量。「产品」列固定显示**参考产品**的品牌 / 规格；没有品牌规格时显示「—」。

入口按可用性独立出现，互不牵连。「购买预分装」**只有整单一个入口**（底部固定栏，延续现状），行上只标注这一项能不能买：

| 有推荐商品 | 本行有预分装产品 | 行上显示 | 行上入口 |
|---|---|---|---|
| 有 | 有 | 参考产品 +「可分装」小标 | 「查看商品」（推荐） |
| 有 | 无 | 参考产品 + 状态标签 | 「查看商品」 |
| 无 | 有 | 参考产品 +「可分装」小标 | 无 |
| 无 | 无 | 参考产品 + 状态标签 | 无 |

状态标签三态，避免「仅生产」说谎：

1. 本行有预分装产品 → 不显示标签，只在行尾加「可分装」；
2. 该补剂的池子里**有**已上架产品，但本行算不出（档案缺项 / 单位不可换算 / 浓度缺失）→ 「暂不可购买」，并给客服入口；后台同时报一条体检问题；
3. 池子里**没有任何**已上架产品 → 「仅生产，不单独出售」。

- 标签文案从「仅生产，不可购买」改为「**仅生产，不单独出售**」——买不到是指我们不卖，不是顾客买不到。
- 「查看商品 / 换一个」徽章只由**推荐商品数量**决定（0 个不出、1 个「查看商品」、≥2 个「换一个」），与候选数无关。
- 弹窗内容改成推荐商品卡片：商品名、品牌、规格、形态、推荐渠道、去购买（复制口令/链接）。**不再显示**候选补剂、不再有「确认选择」——顾客选了也不影响我们，这个动作要删掉。
- 如果参考产品与预分装产品不是同一款，在预分装入口那一行加一句「分装寄送：{品牌 规格}」，避免下单后才意外。

### 5.2 购买预分装补剂（下单页）

- 整单**一个入口**（底部固定栏），清单行 = 有预分装产品的补剂行；每行显示预分装产品的品牌/规格和按它算出的用量。
- 价格按预分装产品计价，不按参考产品。
- 没有预分装产品的行不出现在清单里，页面底部提示「本单有 N 项补剂仅用于生产，不单独出售」。
- 全部都没有时，「购买预分装补剂」按钮不出现。

## 六、后端

### 6.1 新接口：`GET /recipes/:id/supplement-plan`

替换现有 `supplement-candidates`。返回每行的四块信息，前端不再自己拼：

```
{
  totalWeightG, weightSource, recipeVersion,
  items: [{
    recipeItemId, sourceIngredientId, name,
    preparationMethod, addTimingLabel, sortOrder,
    reference: { ingredientId, name, brand, productModel, displayUnit, amount, unit,
                 targets[], status: 'OK' | 'NO_TARGETS' | 'MISSING_CONCENTRATION' },
    recommendedProducts: [{ id, name, brand, productModel, purchaseChannel,
                            purchaseLink, imageUrl, displayUnit }],
    repack: null | { ingredientId, name, brand, productModel, displayUnit,
                     amount, unit, available, unavailableReason }
  }]
}
```

- **版本**：带 `diySheetId` 时按制作单冻结的 `recipe_version` 解析（与下单同一口径），不带时才取最新版；响应里回传 `recipeVersion`，供前端对账。
- **价格**：接口**不返回单价**——它可被分享链接访问，露出进货价等于公开成本。价格只由报价接口（带登录 + 加价规则）给。
- `reference`：只算展示与用量，不看任何开关。
- `repack`：按第四节规则解析；`available=false` 时给 `unavailableReason`（未上架 / 档案不全 / 单位不可换算 / 用量算不出 / 商城总开关关闭）。
- `recommendedProducts`：按参考产品 ID 批量查 `recommended_product`，只返回启用项。

### 6.2 下单校验

`resolveServerDosageLines` 改为：`line.ingredientId` 必须等于该行的 `repack.ingredientId`；用量、规格都取 `repack`，价格走原有报价链路。不再要求命中「候选列表」。两边都用制作单冻结的 `recipe_version`，从根上消除「页面按新版算、下单按旧版算」的偏差；若制作单指向的版本已不存在，直接报「食谱已更新，请刷新制作单」，不做猜测。

### 6.3 旧版小程序兼容（一个版本周期）

补剂订单线上已经有单（累计 7 单，最近 2026-11-13），而旧版小程序要等审核才换得掉，所以一期**双向兼容**：

- `GET /recipes/:id/supplement-candidates` 继续返回旧结构，内容按新口径重算（候选 = 预分装池），旧版仍能显示；
- 下单接口接受旧格式行（不带 `repack` 标记）：命中新 `repack.ingredientId` 直接通过；命中旧候选列表里的其他成员时按「同组且已上架」放行并记一条 warn 日志，便于下架旧版后复盘；
- 新版前端带 `schemaVersion=2` 时走严格校验；
- 小程序发布满一个版本周期后删旧接口与旧分支。

### 6.4 推荐商品批量接口

现有 `GET /recommended-products?ingredientIds=` 已可用，只需前端把补剂 ID 一起带上。后端不用改。

## 八、迁移与兼容

- **已保存的制作单**：`supplementSelections` 里的「顾客选的产品」不再参与任何计算，只保留存档。打开旧制作单时按新规则重算展示。
- **已下单的补剂订单**：订单快照里冻结的商品与价格不动，历史订单照旧。
- **legacy 食谱级备选**（`recipe_supplement_alternative`，目前仅小麦胚芽油等少数几道）：只要跨产品替换关闭、或该原料没有等价组，它就作为预分装池的兜底成员，保证这几道食谱不回退；同时在后台列表标「未归组」，推动尽快归组。
- **接口**：见 6.3，旧接口保留一个版本周期，返回旧结构但内容按新口径重算。
- **索引/字段**：本期不加字段；若将来要求「预分装默认指定某款」，再加组上的可空字段。

## 九、待老板拍板

**只有第 1 条挡一期，另外两条是二期/三期，先定方向即可。**

1. **预分装默认要不要允许「跨产品」**（挡一期）：参考产品没上架时，默认换到组里已上架的另一款（海藻粉 → 海带粉胶囊），还是保持「不可买」等运营去上架？前者顾客马上能买，但收到的不是配方里写的那款；后者不改口径，但海藻粉那类食谱仍然只能看到「仅生产」。这题的实际动作就是：补剂商城总开关 `equivalenceEnabled` 开还是不开（现在是关的）。
2. **生产门禁的判定口径**（二期）：同组里「生产开」超过 1 个就拦（现在有 6 个组命中，要先清数据），还是只检查「食谱引用的产品必须开生产」？
3. **下单后再换产品的价格规则**（三期）：分装端缺货换款时，是「只换同价或更便宜、不补不退」、「补退差价」，还是「下单后不允许换」？

## 十、我的判断（不用老板回答，先按这个做）

- 制作单的产品列**不加**「可更换」入口：顾客不选我们的产品，多一个入口只会多一次误解。
- 「购买预分装」**只有整单一个入口**，不做到每一行：顾客是一次买齐这一单缺的补剂，不是逐行下单。
- 推荐商品为 0 时**不显示**「查看商品」：没有链接的入口等于死路。
- 预分装数量与价格一律按预分装产品重算，不沿用参考产品的换算结果——两款浓度不同（海藻粉 450μg/平勺 vs 海带粉胶囊 325μg/粒），沿用会补错量。
- `repack` 不下发单价，价格只由报价接口给：计划接口可被分享链接访问，不能露成本。
- 行状态分三态（可分装 / 暂不可购买 / 仅生产），不让「仅生产」替数据缺项背锅。
- 旧版小程序走双向兼容一个版本周期，不为了干净接口牺牲在线的购买流程。
