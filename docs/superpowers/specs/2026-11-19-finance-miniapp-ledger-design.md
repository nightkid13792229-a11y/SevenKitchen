## 一、为什么重做：现有模块算的是假账

不是界面问题，是口径问题。逐条对过代码：

1. **收入不扣退款。** `finance-report.service.ts#getOverview` 只取 `order.amountTotal`，退款记录一列都没读。收入天然偏高。
2. **四类收入只算了一类。** 只查了 `order` 表。`SupplementOrder`（补剂商城）、`CustomRecipeOrder`（定制食谱设计单）完全没进财务。（试吃装因为也是 `Order`，反而被算进去了。）
3. **成本按「报销打款」时点认。** 只取 `reimbursement.status = REIMBURSED` 且 `paidAt` 在区间内。老板自己垫钱买、自己懒得报销时，成本直接消失；月初报销慢的时候，利润虚高。
4. **真实快递费记了却没用。** `Order.actualShippingFee`（发货时人工录入的真实运费）在 finance 里引用次数为 0，财务用的是报销单里手填的 `platformShippingFee`。要么漏算，要么重复。
5. **固定费用不录就等于没有。** 房租、工资只能手建支出账单，模板存在但没人建就是零。这是「利润凭空变好」最大的一个洞。
6. **看不了「上个月」。** 只有今天/本周/本月三个按钮，没有自定义区间，没法横向比较。
7. **没有「垫付」这个概念。** 老板个人垫了多少钱、公司还了多少、还欠多少，系统里查不到。
8. **贡献分析是估算的。** 按规则分摊成本，账没准之前它只会误导。

结论：这套东西不是修一修能好的，收支两端的事件模型都要重立。

## 二、目标 / 非目标 / 反目标

### 目标

- 老板**随时打开**就知道本月到现在赚了多少，不用等到月底。
- 每一笔收入和支出都有出处，点得进去看到是哪张单。
- 固定费用设一次，往后每月自动出现，不用记。
- 月报自动生成，并且和首页是同一套数（不允许两个页面两个数）。
- 全程不需要老板理解「借贷」「科目」「权责发生制」这些词。

### 非目标（本期不做）

- 不做贡献分析（哪道菜更赚钱）——账准了以后再说。
- 不做标准财报（资产负债表、现金流量表表格版）、不做税务计算与申报。
- 不做应收应付账龄、不做折旧、不做多币种、不做发票管理。
- 不做对公银行流水导入/自动对账。
- 不改动补货、报销、代客下单的既有业务流程（只在需要的地方加字段/加提示）。

### 反目标（做到了也算失败）

- 小程序和后台出现两套不一样的数。
- 同一笔采购既算采购、又算报销，重复扣两次。
- 未付款的订单被算成收入。
- 老板要打电话问「这个数是怎么来的」。
- 记一笔要填 6 个字段、超过 30 秒。

## 四、口径（这是整份文档最重要的部分）

### 4.1 收入：四个来源

| 来源 | 表 | 计入时点 | 金额 |
|---|---|---|---|
| 鲜食/定制鲜食/试吃装订单 | `Order`（type = FRESH_FOOD / CUSTOM_SERVICE / TASTING_PACK） | `paidAt` | `amountTotal` |
| 补剂商城 | `SupplementOrder` | `paidAt` | `amountTotal` |
| 定制食谱设计单 | `CustomRecipeOrder` | 支付成功时间 | `actualPaidAmount ?? amount` |
| 线下收款 | 同上三张表，但 `paymentMethod` 不是线上支付 | 同上 | 实收金额 |

- 线上/线下判定**不能写 `paymentMethod === 'WECHAT_PAY'`**。实际取值至少包括 `WECHAT_PAY`、`WECHAT`（默认值）、`ADMIN`、`OFFLINE_WECHAT`、`RESHIP`。规则：`paymentMethod ∈ {ADMIN, OFFLINE_WECHAT, OFFLINE_ALIPAY, OTHER}` → 线下，其余非空值 → 线上（补剂/定制按各自字段）。
- **未付款的订单不算收入。** 判断依据是支付成功时间，不是下单时间。
- 线下收款必须走代客下单（老板已同意）。
- **代客下单要一步到位。** 现在代客下单建出来是「待付款」，还得另进订单详情点一次「确认收款」才写 `paidAt`。这一步漏点，钱就消失了——正是老板最怕的事。改为：代客下单表单里「已收款」默认勾选，勾了就直接落成已付单，`paidAt` = 下单时间。
- 兜底：未勾「已收款」的代客单，在财务首页顶部显示一条「有 N 笔线下收款待确认」的提醒，点进去直达订单。
- **0 元单不进收入**：重做单（`remakeFromOrderId`）、补发单（`reshipFromOrderId`）、赠送单（`paymentMethod = RESHIP` 或金额为 0）全部排除，否则明细里会出现一堆 0 元噪音。

### 4.2 退款：冲减收入，不抹掉历史

- 退款按**退款成功日**冲减当月收入，一条负数记录。
- 覆盖范围（已核过 schema）：
  - 鲜食订单：只有 `OrderRefundRecord(success=true)`，记的是**微信原路退回**。
  - 补剂订单：`SupplementOrder.refundStatus / refundAmount / refundedAt`。
  - 定制食谱设计单：`CustomRecipeOrder` 上的 `refundAmount / refundedAt / offlineRefundAmount / offlineRefundedAt`（这张表有线下退款登记）。
  - **鲜食订单**：新增「线下退款登记」（表见 §6.6），入口放在**小程序订单中心 → 订单详情**里，符合老板的使用习惯（他本来就在那里管单）。
    - 只能对「已付款 + 线下收款」的订单登记；累计退款金额不能超过实收金额。
    - 登记只是财务动作，**不改变订单状态**；要取消订单仍走现有取消流程。两件事分开，避免退了一部分钱却把整单作废。
    - 登记后当月收入减少，并留操作人和时间。
- 起账日（11-01）之前的订单在 11 月退款时，会出现「当月收入被历史退款拉低」。处理方式：明细里单独一行标「历史订单退款」，月报上单独列示，不混在正常退款里，避免让当月经营看起来莫名变差。
- 不做「退回原月份」的追溯调整（既不现实也容易把已经看过的数改掉）。

### 4.3 手续费：6‰ ×（实收 − 已退）

- 只对线上支付（微信商户号收款）产生；线下转账没有手续费。
- 每笔线上收入按 `金额 × 6‰` 记一笔支出，类别「支付手续费」。
- 退款发生时，按 `退款金额 × 6‰` 记一笔**负支出**（钱回到账上）。
- 官方依据（已查证）：微信支付退款时手续费按轧差计算，已收手续费按比例返还。
  <https://pay.weixin.qq.com/doc/v3/merchant/4013071200>
- 例外：**线下转账退款**（钱从个人微信退给顾客）不走微信支付，原支付没被撤销，手续费不退 → 这种退款不产生负手续费。
- **v1 把费率固定成代码常量 0.006**：`GlobalConfig` 里没有财务字段，本期不为一个数字加列做迁移；微信真调费率时需要改代码发版。v2 再做配置项。

### 4.4 支出：只有五个来源

**关键原则：订单不产生支出。** 食材成本在「采购」那一步就已经花了，订单只是把食材消耗掉，不能再算一次。

| 来源 | 表/计算 | 计入时点 | 类别 |
|---|---|---|---|
| 采购（日采 + 补货） | 分两条路，见下 | 补货按 `orderPlacedAt`，日采按各记录 `purchasedAt` | 食材 / 补剂 / 包材；运费→物流、包装→包材 |

**采购要分两条路取数（2026-11-19 补）**：只有补货单（`kind = STOCK_REPLENISHMENT`）写了 `paidAmount / subtotalAmount / shippingFee / packagingFee`，按订单买的日采单（`ORDER_DEMAND`）这些字段是空的，只有逐条 `PurchaseRecord.actualCost`。所以：

- **补货单**：实付 − 个人消费，按「商品行 + 运费 + 包装费」的权重摊到各分类；个人消费不得专项冲运费/包装费（否则快递费会被抹成 0）。
- **日采单**：Σ `PurchaseRecord.actualCost`，按行类型归类；个人消费从商品合计里扣。
- 同一张单只走一条路，避免重复计算。
| 真实快递费 | `Order.actualShippingFee` | `shippedAt` | 物流配送 |
| 固定费用 | `ExpenseBill` | 按费用所属月 | 房租 / 水电 / 宽带 / 工资 / 社保 / 税费 / 服务器 |
| 支付手续费 | 计算得出（§4.3） | 支付/退款日 | 支付手续费 |
| 一次性支出 | 新表 `finance_manual_entry` | 发生日 | 设备工具 / 其他 |

补充规则：

- **采购金额以采购单实付为准，不是商品行合计。** 采购单上有 `subtotalAmount / shippingFee / packagingFee / discountAmount / paidAmount`；支出取 `paidAmount`（为空时按 `subtotal + shipping + packaging − discount` 兜底）。这样补货单的运费、包装费、优惠差额都有出处，不会凭空消失。
- **剔除个人消费。** `personalAmount` 表示「个人买的东西、不该报销」，支出金额 = 采购单实付 − 个人消费。这部分不算公司成本。
- **日采和补货都算**（`kind = ORDER_DEMAND / STOCK_REPLENISHMENT`）；草稿（`isDraft`）、作废（`voidedAt`）排除。
- **分类拆分**：一张单里可能同时有食材、包材、补剂。商品行按各自类型归类；运费归「物流配送」、包装费归「包材」；优惠按行金额占比摊减。
- **报废、损耗不单独计成本。** 报废的物料在采购时已经算过支出，再算一次就是重复。库存盘点、报废记录继续用于库存管理，但**不进财务报表**。
- **设备按购买当月全额计入**，不做折旧（两个人、一年买几次，不值得）。
- **赠品 / 试吃**：下 0 元代客单，收入为 0，成本已经包含在采购里。不需要额外功能，也不会重复计成本。
- **报销单本身不产生支出**（见 §4.5）。

### 4.5 报销单和固定费用的边界（防重复计算）

这是最容易算错的地方，规则写死：

1. 采购的支出**以采购单实付为准**，报销单不整体计入支出。
2. 报销单只补「采购单之外」的附加费：`customFees`（杂费），按报销提交日、按对应类别计入支出。
   - `platformShippingFee` / `platformPackagingFee` **只有在报销没有关联采购单时**才单独计入。一旦关联了采购单，运费和包装费已经包含在采购单实付里，再加一次就是重复。
3. **房租、工资、社保、税费不再允许从报销单录入**（自定义费用的这几个选项下线），一律走固定费用账单。这样同一笔固定费用只有一条来路。
4. 一致性提示（报销金额与「采购单实付 + 附加费」的差异）**本期不做**，放到下一版；本期靠「报销只补杂费」这条规则先把重复计算堵住。
5. 报销打款是内部资金移动，**不进财务**（见 §4.6）。

### 4.6 不设「往来 / 垫付」这一层（2026-11-19 变更）

老板是个体户，公司账户和个人本质是一个口袋：他不会从公司账户把钱还给自己，缺钱时直接从商户号提现。搭档的垫付是**实时报销**，账上不会留余额。所以：

- **不做「公司欠我」「欠搭档」「我欠公司」这些数**，首页也不显示。
- **不做内部往来转账登记表**（原计划的 `finance_inter_account_transfer` 取消）。
- 报销打款、提现，都是内部资金移动，**既不进收入也不进支出**。
- 「这笔钱是谁付的」仍然记录（公司账户 / 某人个人），只作为明细里的一个标签，帮你判断现金从谁口袋出去，**不汇总、不累计、不构成债务**。

| 概念 | 处理 |
|---|---|
| `PurchaseList.personalAmount`（个人消费） | 从公司支出剔除 |
| `payerType / payerUserId`（谁付的钱） | 只在明细显示「我垫的 / 公司账户」，不汇总 |
| 报销打款 | 不进财务 |
| 商户号提现 | 不进财务；余额不显示，老板直接去商户平台看 |

### 4.7 期间与归属

- 收入、采购、快递费、手续费、手工支出：按**发生日/支付日**归入当月（现金口径）。
- 固定费用：按**费用所属月**（`ExpenseBill.recognitionStart/End`）归入，不按付款日——11 月的房租 12 月才付，也要算 11 月的成本。
- **跨月账单按月平均分摊。** 服务期跨几个月的账单（例如年付宽带 1200 元），按服务期月数平均拆到每个月，不做「整笔计入起始月」。否则年付那个月的利润会塌一块、后面 11 个月虚高。
- 时区：一律按上海时间切日切月（沿用 `docs/TIMEZONE_HANDLING.md` 的既有约定）。
- **日期型字段（`@db.Date`）一律写 UTC 零点**：手工条目的发生日、线下退款日、账单费属期间都是 `@db.Date`，写上海零点会落成前一天——11-01 的记录会掉到 10-31，直接从 11 月账里消失（2026-10-19 有过同款事故）。

### 4.8 起账日

- 硬起点 **2026-11-01**。
- 日期选择器不允许选到 11-01 之前；若查询区间跨过起点，自动裁到 11-01 并提示「起账日之前不统计」。
- 11 月的固定费用由老板在系统里建模板后补生成（见 §5.4）。


- 结余旁边一行小字解释：「= 收入 − 支出，已经扣掉房租、工资、社保」。
- 三个大数都能点，点进去看明细（已按类别筛好）。
- 结余为负时数字标红，并给一句人话解释。
- 日期范围标签清楚显示「进行中」，避免误以为是完整月度。
- **没有「欠款 / 垫付 / 商户号余额」这些块**（§4.6）。想看钱从谁口袋出去，去明细里看每条的「我垫的 / 公司账户」标签。

### 5.2 收支明细

- 倒序列表：日期、类别、金额、来源单号、付款方。
- 顶部筛选：收入 / 支出 / 全部；按类别；按月份。
- 每一条能点进来源单据（订单详情、补货记录、账单、手工条目）。
- 有退款时，退款行显示为负数并标「退款」「历史订单退款」。

### 5.3 记一笔（手工支出/收入）

只给系统抓不到的：设备、税费、其他垫付、零星收入。

- 字段：金额、日期（默认今天）、收入/支出、类别、付款方（公司/个人）、备注、凭证照片（可选）。
- 交互：金额键盘直接弹出、类别记住上次选择，**目标 15 秒内记完**。
- 手工条目可编辑、可作废（作废保留记录并标灰，不物理删除）。

### 5.4 固定费用

- 列表：名称、类别、金额、周期（每月/每季/每年）、几号、下次应付、启用状态。
- 周期枚举新增 `QUARTERLY`（现在只有 `MONTHLY` / `YEARLY`），税费这类按季缴的用得上。另保留 `servicePeriodMonths` 表示服务期长度：年付宽带设为 12，账单会按月分摊（§4.7）。
- 新建/编辑/停用：金额、周期、日期、开始月份、付款方都能改。**停用只影响以后，不改历史账单。**
- 待付区：本月应生成的账单，一键「已付」（可改实付金额），点完往来立即更新。
- 「补生成本月」按钮：月中才建模板时，把当月这笔补出来（解决 11 月只剩十几天的情况）。
- 生成规则：同一模板 + 同一期间只生成一张（唯一约束，重启/重跑不会重复）。

### 5.5 月报（与首页同一页，切月份即可）

- 不做独立页面：首页顶部的月份切换器选到一个**完整月份**，页面就是月报；选「本月至今」就是进行中的账。同一套取数，保证两个视图数字一致。
- 完整月份时多一行对比：「比上月 +¥1,200」；11 月没有上月，只显示本月并注明「从 11 月起账」。
- 收入、支出分类明细列表（可展开合计）。
- 本期不做导出/分享（截图够用）。「发给会计」的导出留到下一期。

### 5.6 权限

- 仅 `ADMIN`。`STAFF` 和顾客都看不到入口，直接调接口也返回 403。
- 财务页面的数据查询、写入都走管理员校验（复用现有 `AuthGuard`，若没有角色闸就补一个）。

| 字段 | 说明 |
|---|---|
| id | uuid |
| order_id | 订单 |
| amount | Decimal(10,2)，本次退款金额 |
| refunded_at | 实际退款日 |
| method | `WECHAT` / `ALIPAY` / `CASH` / `OTHER` |
| note | 备注 |
| proof_keys | 凭证（可选） |
| created_by_id / created_at | 操作人、时间 |
| voided_at / void_reason | 预留作废字段（读侧已排除）；**v1 不做作废入口**，登记错了先按负数补登，v1.1 再给入口 |

- 校验：同一订单累计（未作废）退款金额 ≤ 该单实收金额。
- 与 `OrderRefundRecord`（微信原路退回）分开两张表，互不影响；财务统计时两者都作为收入减项。

### 6.7 不建全量表的原因

考虑过建一张 `finance_ledger_entry` 全量流水表（每个事件写一行），最后**不这样做**：

- 老板要的是「数对得上」，不是「记账凭证」。全量表多一层同步，就多一处会漂移。
- 数据量很小（一年几千条），实时按源表聚合完全够用。
- 明细页在服务层按期间合并排序、在内存分页，单月通常 < 500 条，超过 5000 条截断并提示缩小范围。
- 这样「系统算出来的数」永远等于「单据上真实发生的事」，不存在两边对不上要修数的场景。

## 九、验收标准（老板验收，不是工程师验收）

1. 11 月任意一天打开首页，**收入 − 支出 = 结余**，且三个数点进去能和明细逐条对上。
2. 随便点一笔支出，能看到：哪天、哪个类别、哪张单、谁付的钱、有没有凭证。
3. 做一笔退款，当天首页收入自动减少，手续费那行自动出现一笔负的。
4. 建一个「房租」模板（比如每月 5 号、5000 元），当月账单自动出现；点「已付」后，当月支出增加 5000、结余减少 5000。
5. 月中新建模板时，点「补生成本月」，能把本月这笔补出来。
6. 月报和首页切换同一个月份，数字完全一致。
7. 用搭档的账号登录，看不到财务入口；直接调接口返回 403。
8. 连续三天不记账、不再碰系统，首页的数字不会自己变（没有隐藏的估算逻辑）。
9. 在一张「线下收款」的订单详情里登记 200 元退款，当月收入减少 200，明细里出现一行「线下退款」，并且不能再登记超过实收金额的退款。

## 十、已知限制（写清楚，免得以后被当成 bug）

1. **现金口径**：买进来的食材就算当月花掉，不做库存资产化。大额囤货的月份支出会偏高。
2. **起账日之前的退款**会拉低当月收入，单独标「历史订单退款」。
3. **报废/损耗不单独计成本**（采购时已计）。
4. **设备不折旧**，按购买当月全额。
5. **手续费率固定在代码里（0.006）**，微信调费率时要改代码发版。
6. 若同一笔费用既进了报销单自定义费、又建了固定费用账单，会重复计算——靠「自定义费用选项下线」+ 一致性提示防，不做硬性拦截。
7. 现金（`CASH`）渠道预留但不做特殊处理。
8. 月报不做导出，截图用。
