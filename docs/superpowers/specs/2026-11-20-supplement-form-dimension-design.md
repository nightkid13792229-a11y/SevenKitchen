# 补剂形态：从「固定四档」改成「维度驱动」设计

- 日期：2026-11-20
- 提出：老板（"B 族怎么办？以后还要新增其他类型呢？有没有更聪明、解耦性更高的方案？"）
- 状态：待评审（本稿只写设计，评审通过后才动代码）
- 范围：`admin-web`「AI 添加原料」补剂线的**第 1 步（定形态）**与其后端检索；不改第 2 步比价算法、不改第 3 步图建档、不改写入与落地配置
- 前置：三步流程已上线（`?v=2`），形态建议现为固定四档

## 0. 一句话

**固定「问什么」，不固定「答什么」。** 维度（形态 / 来源）写死在代码里且几乎不增；每个维度下有哪些取值，由**知识库原文**和**市场商品标题**两个来源实时长出来，代码不再维护"品类 → 档位"的表。

## 1. 为什么改

### 1.1 现在的样子

四档写死：`有机络合 / 无机盐 / 氧化物 / 其他`。这是**矿物质**的分法，且由提示词强制模型逐格填写。

### 1.2 它坏在哪

| 场景 | 现在的表现 |
|---|---|
| 矿物质（铜、铁、锌） | 表能用；铁这次四格全"证据不足"，但库里其实有氧化铁不可用的原句——那是检索问题，另说 |
| 鱼油 / Omega-3 | 四格问不到点子上；真正要比的是甘油三酯型 / 乙酯型 / rTG / 磷虾 / 藻油 |
| 维生素 D | 该问 D2 / D3、油基 / 干粉，四格没有 |
| **B 族** | **B 不是一类，是八类**：B1（盐酸硫胺素/苯磷硫胺/TTFD）、B3（烟酸/烟酰胺/肌醇六烟酸酯）、B6（吡哆醇/P5P）、B9（叶酸/甲基叶酸）、B12（氰钴胺/甲钴胺/羟钴胺/腺苷钴胺）……按品类写表至少要 5 张，且互不相同 |
| 益生菌、关节、纤维 | 各有一套完全不同的形态维度，表会继续膨胀 |
| 新品类 | 每来一类就要改一次代码 + 发一次版 |

### 1.3 结论

"品类 → 固定档位"是**把答案写进代码**，而答案由市场供给和文献共同决定，二者都在变。所以改的是这个结构。

## 2. 目标与非目标

**目标**

- 新增营养素（含 B12、益生菌、任意新品类）**不需要改代码**。
- 每一行候选都要能回答两个问题：**有没有原文依据**、**市场上买不买得到**。
- 没有依据就不推荐；没有候选就不硬凑。
- 抽出来的词要能归一（`bisglycinate` / `甘氨酸盐` / `甘氨酸螯合` 是同一个东西），认错能人工纠正。

**非目标**

- 不做多选（下一期）。
- 不改第 2 步比价口径与排序、不改第 3 步建档、不改写入与第 4 步。
- 不补知识库文献（那是内容工作）。
- 不做"理论上更好但买不到"的形态展示——没有市场的形态不出现，避免把人引到买不到的路上。

## 3. 概念模型

```
营养素 Nutrient（规范字段，如 vitamins.vitaminB12）
   └─ 维度 Dimension（代码固定，5 个）
        └─ 候选 Candidate（实时长出来，不是代码写死）
             ├─ 知识库依据 evidence[]（引用原文）
             └─ 市场供给 market（标题里出现过多少次、样例）
```

### 3.1 五个维度（代码里固定）

| 维度 | 说明 | 这一步问不问 |
|---|---|---|
| `FORM` 化学/产品形态 | 盐型、分子型、菌株型、脂肪酸型 | **问** |
| `SOURCE` 来源与原料 | 鱼 / 磷虾 / 藻油；天然 / 合成 | **问** |
| `DOSAGE_FORM` 剂型 | 胶囊 / 片 / 粉 / 液 | 不问，档案字段已有 |
| `POTENCY` 浓度与规格 | 每粒多少、每瓶多少 | 不问，比价表已在比 |
| `COMBINATION` 单方/复方 | 一瓶里有几种营养素 | 只作分支开关 |

所以第 1 步实际只有两张小表：**形态** + **来源**。维度不变，取值可变。

### 3.2 候选的状态

| 状态 | 含义 | 页面 |
|---|---|---|
| `EVIDENCED` | 知识库原文提到，且给出了判断 | 正常卡 + 出处（可展开看原句和页码），可推荐 |
| `MARKET_ONLY` | 只在商品标题里出现，库里没有 | 灰卡「市场有，库里没依据」，可人工选（沿用「仍用这一档」+ 确认 + 记档） |
| （无候选） | 两边都没有 | 不出现；若整张表为空 → 直接进比价 |

## 4. 两个抽取器

### 4.1 市场抽取（Market）

输入：iHerb 搜索结果标题（8～20 条，复用比价那步已有的搜索与缓存）

1. 先按营养素英文名搜一轮（`site:cn.iherb.com <nutrient>`）；
2. 模型从标题里抽**形态词与来源词**（不抽品牌、不抽规格、不抽剂量）；
3. 服务端过滤：候选必须满足「该标题里同时出现目标营养素的英文名或其别名」——否则丢弃（防把 "B-Complex" 的某个词算到 B12 头上）；
4. 归一化（见 §6）；
5. 输出 `{ key, label, count, samples[≤3] }`。

### 4.2 知识库抽取（KB）

输入：营养素英文名

1. 检索 3～4 条查询，按维度生成，不再只用 `absorption`：
   - `<nutrient> bioavailability`
   - `<nutrient> form`
   - `<nutrient> source`（或 `oxide` / `salt` / `strain`，按营养素类型）
2. 取页规则（**这部分是本次要修的检索缺陷**）：
   - 每条查询**轮流取**，每条至少 1 页、最多 2 页；
   - 同一文档最多 2 页；
   - 过滤目录/索引页；
   - 低于分数阈值的页不读（阈值先用真实数据跑一轮再定，先记录不拦）；
3. 模型从读到的原文里抽「形态名 + 对它的判断原句」；
4. **服务端逐字校验**：候选词必须作为子串出现在该页原文里，否则丢弃（这是"不许编"的技术保证）；
5. 归一化后输出 `{ key, label, quotes[{documentId,page,quote}] }`。

### 4.3 合并

| KB | 市场 | 结果 |
|---|---|---|
| 有 | 有 | `EVIDENCED` + 市场常见度 |
| 有 | 无 | `EVIDENCED`，标「市场上没见到」 |
| 无 | 有 | `MARKET_ONLY` |
| 无 | 无 | 不出现 |

## 5. 判断由谁给

- `EVIDENCED` 的候选：模型给 `verdict`（推荐 / 可用 / 不推荐）+ 一句理由，**必须带引用**；沿用现有 `enforceCitationRule`（引用必须是本次读过的页、文档必须在知识库清单里，引用丢光就降级为证据不足）。
- `MARKET_ONLY` 的候选：`verdict` 固定 `NO_EVIDENCE`，不给推荐，允许人工选，选中的事实写进档案快照（`humanOverride: true`，已有）。

## 6. 归一化与别名

同一个东西的不同叫法必须并成一个：

```
bisglycinate / bis-glycinate / 双甘氨酸盐 / 甘氨酸螯合  → FORM:bisglycinate
methylcobalamin / 甲钴胺 / 甲基钴胺素                  → FORM:methylcobalamin
rTG / re-esterified triglyceride / 再酯化甘油三酯       → FORM:rtg
```

规则：

1. 先查别名表（`supplement_form_term`），命中即用；
2. 没命中：用「小写 + 去空格 + 去连字符」的英文词做 `canonical_key`，`status = NEEDS_REVIEW`；
3. 后台能看到 `NEEDS_REVIEW` 的词，改一次就沉淀下来（这就是"越用越准"的地方）；
4. 中文名由模型给，缺了就先用英文。

## 7. 数据

**新增一张表**（一次 migration）：

```
supplement_form_term
  id, dimension ('FORM' | 'SOURCE'),
  canonical_key      -- 'bisglycinate'
  label_zh, label_en
  aliases            -- String[]，全部小写
  nutrient_keys      -- String[]，限定适用于哪些营养素（空 = 通用）
  status             -- 'AUTO' | 'NEEDS_REVIEW' | 'CONFIRMED'
  source             -- 'KB' | 'MARKET' | 'MANUAL'
  reviewed_by, reviewed_at, created_at
  @@unique([dimension, canonical_key])
```

**不新建证据表**：每次判断的引用随响应返回，并在写入档案时进 `selection_snapshot`（已有字段）。理由：形态判断是一次性决策，不需要长期存一份独立证据；档案快照已经够复盘。

**缓存**：市场抽取结果按营养素缓存 30 分钟（复用比价那步的 URL 缓存）。

## 8. 接口

`POST /api/v1/admin/ingredient-supplement-agent/form-advice`（路径不变，返回结构变）

```jsonc
{
  "nutrientKey": "vitamins.vitaminB12",
  "nutrientLabel": "维生素 B12",
  "dimensions": [
    {
      "key": "FORM",
      "label": "形态",
      "candidates": [
        {
          "key": "methylcobalamin",
          "label": "甲钴胺",
          "status": "EVIDENCED",
          "verdict": "ACCEPTABLE",
          "reason": "……",
          "citations": [{ "documentId": "...", "documentName": "...", "page": 123, "quote": "原文逐字" }],
          "market": { "count": 9, "samples": ["...", "..."] }
        }
      ]
    }
  ],
  "recommendation": { "dimensionKey": "FORM", "candidateKey": "methylcobalamin" },
  "gaps": ["知识库没有比较氰钴胺与甲钴胺在犬体内的差别"],

    "queries": ["vitamin b12 bioavailability", "..."],

```

`retrieval` 是**给复盘用的**：这次读了哪几页、为什么丢，一眼能看见。上一次铁的判断出问题，就是因为日志里连页码都没有。

分支：

- 只有 `MARKET_ONLY` → 顶部不出现"建议用"，写「库里没有依据，以下都是市场常见形态，请你判断」。

## 10. 前置：检索修复（独立可上线）

这是上一轮定位到的缺陷，必须先修，否则维度驱动抽出来的仍然是跑题的页：

1. 每条查询轮流取（至少 1 页、最多 2 页）；
2. 同一文档最多 2 页；
3. 过滤目录/索引页；
4. 记录分数，跑一轮真实数据后再定阈值；
5. 查询按维度生成（`bioavailability` / `form` / `source`），不再只用 `absorption`；
6. 日志记 `query` + 命中页码 + 分数。

验收：铁能引到 NRC「Iron oxide and carbonate … should not be used as dietary sources of Fe」。

## 11. 分阶段

| 阶段 | 内容 | 可独立验证 |
|---|---|---|
| 1 | 检索修复（§10） | 铁/铜对比：铁能引出氧化铁原句，铜结论不变 |
| 2 | 市场抽取 + 合并（KB 侧暂沿用现有） | 鱼油、B12 能列出市场形态 |
| 3 | KB 抽取 + 归一化表 + 页面重画 | 铜不退化；B12 有"有原文"的行 |
| 4 | 收尾：删掉固定四档代码与旧页面分支 | 全量测试 + 四种补剂回归 |

## 12. 验收口径

1. **铜不该变差**：仍出「无机盐可用 / 氧化物不可用 / 螯合无依据」；
2. **铁该变好**：能引用到氧化铁不可用的原句；
3. **鱼油**：出「甘油三酯型 / 乙酯型 / rTG / 磷虾油 / 藻油」中至少 4 个市场候选；
4. **B12**：出「甲钴胺 / 氰钴胺 / 羟钴胺」中至少 3 个，且至少一个带原文；
5. **复合维生素**：不出现形态表，直接进比价；
6. 任何标"有原文"的行，点开能看到**页码和逐字原句**；
7. 加一个新营养素（例如维生素 K2）**不改代码**也能出表。

## 13. 风险

| 风险 | 表现 | 应对 |
|---|---|---|
| 标题抽取噪声 | 品牌、规格、剂量混进形态词 | "同标题必含目标营养素"过滤 + `NEEDS_REVIEW` 人工纠错 |
| 归一化不准 | `glycinate` 与 `bisglycinate` 分成两个 | 别名表；先按英文词形归，人工合并 |
| KB 抽不到词 | 整屏灰 | 可接受（书的缺口）；页面明写"库里没提到，以下是市场形态" |
| 成本变高 | 多一次模型调用（抽取）+ 一轮搜索 | 市场结果缓存 30 分钟；搜索复用比价那步 |
| 页面变复杂 | 两个维度、三种状态 | 默认只展开"有原文"和"推荐"；其余折叠 |

## 14. 留给 builder 的决定

- 两个抽取器是两次模型调用还是合并成一次（建议分开，提示词更短、错误更好定位）。
- `supplement_form_term` 的后台维护入口放哪（先只读+改状态，不做完整 CRUD）。
- `retrieval` 是否对前端可见（建议默认折叠，给"这次读了哪几页"）。
- 分数阈值定多少（先用真实数据看分布）。
- 旧的四档枚举是删除还是保留作为 `FORM` 的一个子集（建议删除，避免两套并存）。
